## 1. What was built

### `internal/drift` (new package) — the cross-node consistency engine

Five pure check functions, each `func(inventory.Snapshot) []Finding`, one
per `docs/features/topology.md` §6 family:

| File | Check | Fixable? |
|---|---|---|
| `bridge.go` | `bridge_divergence` — same-named-bridge presence, VLAN-awareness, and VID-set divergence across nodes. | VLAN-awareness/VID-set divergence: yes (bridge-property harmonization, aligns the minority to the majority value). Presence divergence: no. |
| `mtu.go` | `mtu_consistency` — within-node path (bridge MTU vs. its port(s), recursing through an enslaving bond) and cross-node (same-named bridge's MTU differing across the cluster). | Cross-node: yes (MTU alignment, aligns outliers to the majority). Within-node path: no (ambiguous which layer is "correct"). |
| `sdn.go` | `sdn_realization` — an SDN zone lists a node as a member but that node has no bridge matching the zone's declared bridge name. | No (creating the bridge needs a physical-port decision). |
| `pending.go` | `pending_interfaces` — an interface PVE reports `pending` (staged `interfaces.new`, never reloaded). | No (reload is a real infra action outside the v1 op vocabulary; requires review). |
| `filerun.go` | `file_runtime_divergence` — an entity's own live (netlink) state vs. its declared (interfaces file / PVE) state: bridge/bond port-or-slave membership, and MTU. | No (which side reflects intent is ambiguous). |

`types.go` defines `Finding{ID, Check, Severity, Detail, Nodes, Refs,
Fixable}` plus unexported `fixOps []change.Op`/`fixTitle string`. `ID` is a
deterministic string (`check + "|" + sorted-refs-or-nodes`) — never random
or time-based, which is what makes acceptance criterion 5 ("no finding
flapping") hold: the same underlying divergence always produces the same
ID across cycles.

`service.go`'s `Service` wraps a `*inventory.Graph`: `Findings()` runs all
five checks fresh and returns them sorted; `FixOps(id)` re-runs the checks
and returns the matching finding's precomputed `[]change.Op` (never trusts
a cached/client-supplied op list); `RunLoop(ctx)` drives the documented 30s
cycle (`DefaultInterval`), comparing the finding-ID *set* between cycles
and firing `OnChange(count)` only when it actually changed (this is the
hysteresis/dedup mechanism — a literal count comparison would miss "one
finding replaced by a different one, count unchanged", so it's an ID-set
comparison instead).

Fix computation reuses `internal/change`'s real op vocabulary
(`change.OpBridgeUpdate` / `BridgeUpdateParams`) — a fixing changeset is
built through `change.Service.Create`, i.e. the normal
stage→validate→diff→apply→confirm pipeline, never a bypass.

### Inventory model extension: `Pending`

`PhysNic`/`Bond`/`Bridge`/`VlanIface` gained a `Pending string` field
(`""`/`"new"`/`"changed"`/`"deleted"`, mirroring `pve.PendingState`),
single-source (`pve-network` only — the only collector that observes PVE's
staging concept), following the exact ownership-table/resolve.go pattern
`MTUDeclared` already uses. `FromPVENetwork` now sets it from
`NetworkInterface.Pending`. This is what `pending_interfaces` reads;
without it there was no way to see "this interface is staged but never
reloaded" anywhere in the graph. `merge_test.go`'s exhaustive ownership-table
test was extended (`setField`'s per-type switch) to cover the new field —
required for that test to keep passing, not incidental.

### `internal/pvemock` extension: `links[].members`

`LinkInfo` gained an optional `Members []string` field
(`hostreader.go`'s `Links()` uses it, when non-empty, in place of deriving
live bridge/bond membership from the declared `bridge_ports`/`slaves` —
falls back to the old behavior otherwise, so every pre-existing fixture is
byte-for-byte unaffected). This is what lets a fixture express "someone ran
`ip link set X master Y` outside vnprox" — a genuine live-vs-declared
divergence that was previously *impossible* to construct in this mock
(`Links()` had always derived live membership from the same declared config
`InterfacesFile()` renders, by construction). `testdata/clusters/messy-brownfield.yaml`
now has a new "MESS 10" (pve1: `eno3` declared but unreferenced by any
bridge_ports, live-enslaved to `vmbr0` via the new `members:` override) —
appended to the fixture's own `mess:` list, which is served at `GET
/mock/mess` and is the fixture's documented contract with itself.

- **Interpretation call on the five check families' exact scope**, flagged
  since the spec sentence is a comma-separated list, not five strictly
  delimited definitions: cross-node bridge MTU divergence is filed under
  `mtu_consistency` (not `bridge_divergence`) since the spec's "MTU
  consistency" family reads as MTU-specific; same-named-bridge *presence*
  is filed under `bridge_divergence` since the spec text explicitly lists
  presence there. This means two different checks can flag the same root
  cause from two lenses (as they do for messy-brownfield's `vmbr99`:
  `bridge_divergence` catches the presence gap, `sdn_realization` catches
  the same gap via the zone-membership angle) — treated as intentional
  defense-in-depth, not a bug to dedupe, and documented per-family in each
  check file's own doc comment.
- **`GET /drift` does not yet fan out to peers** (unlike `GET /audit`/`GET
  /snapshots`, T-303). Each daemon's drift findings are already
  cluster-wide in scope (the checks read the merged inventory graph, which
  already covers every node's PVE-visible state), so this is a smaller gap
  than it sounds — the only thing genuinely missing is a peer's own
  degraded/stale host-poller view of *itself*, which the existing
  `staleness` mechanism on `/topology` already surfaces independently.
  Flagged in `docs/api.md`'s new paragraph rather than silently omitted.
