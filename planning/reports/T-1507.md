## What was built

**`internal/migration`** (new package) — the pre-flight bandwidth-headroom planner:

- `Planner.Plan(ctx, guest inventory.Ref, targetNode string) Assessment` (`plan.go`). Never returns
  a Go error: every failure mode (unresolvable guest, missing mesh/traffic/capacity data) folds into
  `Assessment.Caveats` instead, mirroring `internal/probe.Run`/`internal/latmesh`'s own "the attempt
  itself is the answer" honesty contract.
- `capacity.go`: `resolveLinkCapacityMbps` proxies "the migration network"'s physical capacity —
  no live reader of PVE's `datacenter.cfg migration: network=...` exists in this codebase (the same
  documented gap `internal/flow/classify.go`/`internal/latmesh` already carry) — with the
  highest-capacity bridge the source/target node carry in common (`internal/xnode.BridgesByName`,
  the identical grouping T-1303's own guest-fabric `Discoverer` uses), summing member
  `PhysNic`/`Bond` `speedMbps` on each node and taking the lesser side. Falls back to a documented
  1000 Mbps assumption (flagged) when no shared bridge resolves.
- `mesh.go`: `selectMeshLink` reads T-1303's mesh (`MeshProvider`, the same `Heatmap` method
  `internal/findings.LatMeshProvider` already establishes as a "small interface, real type satisfies
  it for free" seam) for the corosync fabric first — the literal risk this card exists to warn about
  — falling back to the guest fabric; picks the *worst* reading within a tier (a dual-stack/
  multi-bridge pair can produce more than one `LinkHeat`) rather than an arbitrary one, since this is
  a warning system. The resolved loss% derates the resolved capacity multiplicatively.
- Current utilization: `MigrationTrafficProvider.MigrationTrafficMbps(ctx, node)` — a Mbps figure
  the composition root computes from T-1504's classifier over the same recent `flow_samples` window
  `service_traffic_on_wrong_network` already reads (no second flow reader).
- Dirty-page-rate estimate: `Config.DirtyRateFraction` (default 1%/sec of guest RAM, guest RAM read
  from PVE's own `GetGuestConfig`'s `memory` field via `GuestConfigReader`) — a fixed, documented
  heuristic constant, never a measurement (no live guest instrumentation this arc). Feeds the
  verdict/caveat logic; `estimatedTransferSec` itself is the simpler `memoryMB*8/headroomMbps`
  arithmetic (hand-verifiable), sentinel `-1` when `headroomMbps` is 0.
- `Assessment.BestEffort` is unconditionally `true` on every response.

**`POST /migration/preflight`** (`internal/api/migration.go`): `netRead`-gated, `{guest,
targetNode}` -> `Assessment`. `400 validation_failed` on a missing `targetNode` or a `guest` that
doesn't parse to a `guest`-kind `Ref`.

**Guest inspector integration** (`web/src/topology/MigrationPreflightTab.tsx` + `migrationQueries.ts`
+ `api/migration.ts` + `api/types.ts`'s `MigrationAssessment`): a new "Migration" tab on the guest
inspector (gated by `isGuestKind`, alongside T-1304's "Interior" tab, `InspectorPanel.tsx`) — a
target-node text input, a "Check headroom" button (`useMigrationPreflightMutation`), and a rendered
verdict/headroom/estimated-transfer/caveats block. No "migrate" action exists anywhere in this tab
or this codebase's frontend — this stays a read-only advisory call the operator consults before
triggering the actual migration in PVE itself.

**Production wiring** (`cmd/vnproxd/migration.go`): `Planner{Graph: <live graph>, GuestConfig:
sdnPVEClient (the collectors' own read-only PVE identity, reused — internal/sdn.Service's identical
precedent), Mesh: latMeshSvc, Traffic: migrationTrafficAdapter}`. `migrationTrafficAdapter` mirrors
`serviceclassify.go`'s `flowClassifyAdapter` exactly: lazily `.set(flowRepo, flowClassifier)` once
`setupFlows` returns, sums `ServiceClassMigration`-classified bytes over the same 300s/5000-row
bounded window, converts to Mbps.

## Advisory verdict output shape (pinned for T-1604/T-1103)

```go
// internal/migration
type Verdict string // "ok" | "tight" | "insufficient"

type Assessment struct {
    HeadroomMbps          float64  `json:"headroomMbps"`
    EstimatedTransferSec  float64  `json:"estimatedTransferSec"` // -1 sentinel when HeadroomMbps==0
    Verdict                Verdict  `json:"verdict"`
    BestEffort             bool     `json:"bestEffort"`           // always true this arc
    Caveats                []string `json:"caveats"`              // never nil, possibly empty
}
```

Wire shape (`docs/api.md`'s new "Migration planner" section):
`{"headroomMbps":<num>,"estimatedTransferSec":<num>,"verdict":"ok"|"tight"|"insufficient","bestEffort":true,"caveats":[...]}`
— exactly five keys, no more, no less (asserted by an exact-key-set test in `internal/api/migration_test.go`
and a byte-exact JSON golden test in `internal/migration/plan_test.go`).

## Deviations from the task card

- **`Plan`'s signature is `Plan(ctx context.Context, guest inventory.Ref, targetNode string)
  Assessment`**, not the card's literal `Plan(guest Ref, targetNode string) Assessment` — `ctx` is
  needed for the `GuestConfigReader`/`MeshProvider`/`MigrationTrafficProvider` calls it makes, and
  every other I/O-performing method in this codebase takes `ctx` first. A pure two-arg signature
  would have meant either a package-global context (never done elsewhere) or blocking calls with no
  cancellation — not a design reversal, just Go idiom.
- **Capacity/congestion are proxies, not live PVE reads**, both flagged explicitly in every affected
  `Assessment.Caveats` entry and in `planning/reports/needs-hardware-validation.md`'s new "Migration
  network planner (T-1507)" section (two new entries) — see `internal/migration/doc.go`'s "The
  migration network" section for the full reasoning. This is a **quietly narrower scope than the
  card's own wording implies** ("computing headroom from T-1303's mesh link-capacity/utilization
  data") since T-1303's mesh carries no capacity/bandwidth data at all (only RTT/loss) — the
  card context itself already documents this exact gap for `internal/latmesh` and for
  `internal/flow/classify.go`'s migration-network source, so this is the same "quietly narrower
  scope, flagged in the report" precedent those two tasks already set, not a new one.
- No `docs/data-model.md` change — the planner is entirely stateless (no new app-store table); the
  card's own deliverables list didn't request one either.
