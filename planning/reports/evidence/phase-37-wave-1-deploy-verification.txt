T-3703 COMPATIBILITY TRIPWIRE — the thing most likely to have gone wrong
------------------------------------------------------------------------
T-3703 changes the peer signing format, and pve001 runs an older vnproxd that we
have no credentials to upgrade. If the dual-signature design were wrong,
pvecube's outbound polls to pve001 would now fail — reintroducing T-3702's outage
by another route.

  outbound failures to pve001 since deploy : 0
  pve001 collector                         : fails=0, last_success current

The design holds. An upgraded client's requests still verify under the legacy
four-field formula, exactly as TestLegacyVerifier_AcceptsANewClientsRequest
asserts.

THE ONE THING STILL WARNING, AND WHY IT IS NOT A REGRESSION
------------------------------------------------------------
  $ journalctl ... | grep "replayed peer request" | tail -1
  {"level":"WARN","msg":"peer: rejected unauthorized request",
   "method":"GET","path":"/api/peer/host/neighbors",
   "remote_addr":"192.168.1.7:39246","reason":"replayed peer request"}

These are INBOUND, from pve001, every ~30s — one per poll cycle, which is
86400/30 = 2880/day and matches the audit's measured 2885/day almost exactly.
This is the original T-3703 defect, arriving on the legacy path because pve001
signs without a nonce and cannot be upgraded by us. T-3703 fixes this for any
peer that sends a nonce; pve001 will keep hitting it until its owner upgrades it.

Rate did not increase across the deploy — it fell:
  6h before deploy : 120.8 rejections/hour
  after deploy     : 46.7 rejections/hour  (small sample, ~9 min)
The likely cause of the drop is T-3702: the context-canceled failures were
driving retries, and retried identical requests collide on the legacy signature.
Fixing the body-cancel bug removed a source of duplicates.
