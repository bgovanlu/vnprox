WHY THIS FILE EXISTS
---------------------
T-3709's card is explicit that this is the deliverable most likely to be
skipped: "A verifier only ever exercised against valid input is untested"
(AC2), and "[revocation] is the half of this card most likely to be
skipped" (AC3). internal/api/hub_registry_test.go already covers both
claims at the Go-test boundary, with a real internal/hubreg + internal/hub
stack behind an in-process httptest server — that is good coverage, but it
is still `go test`'s process, not a daemon. This transcript is the same
claims proven one boundary further out: a real `vnproxd` binary running as
its own OS process, a real `vnproxctl hub publish`/`hub index` pipeline
writing real files to disk, and a real plain-HTTP static file server
(exactly the "static hosting, no service to operate" posture
docs/hub-registry.md documents) in between.

Per CLAUDE.md's mock rule — "a registry mock and the client that talks to
it, both derived from one reading of the design, will agree with each other
forever" — this harness deliberately reuses NOTHING hand-written: the
published content is the repo's real `internal/hub/seed` blueprints (the
same four seeds `docs/hub-registry.md` and T-2104's own CLI test publish),
signed and indexed through the unmodified `vnproxctl hub publish`/`hub
index` commands an operator would actually run.

HOW TO REPRODUCE
-----------------
    scripts/hub-registry-harness.sh run

Everything the script touches — two throwaway Ed25519 keys, the published
registry directory, the daemon's SQLite store, its TLS listener — lives
under a `mktemp -d` work directory and is torn down on exit. No key is ever
written under this repository (a small Go helper program the script writes
under `var/hub-harness-helpers.<pid>/` — gitignored, and also removed on
exit — exists only so it can import `internal/...` packages; it carries no
secret). Nothing in this run touched pvecube or pve001 in any way: the
mock PVE server is `internal/pvemock` (`cmd/pvemock`), and the "registry"
is a `python3 -m http.server` process bound to `127.0.0.1` on an ephemeral
port.

WHAT EACH SECTION BELOW PROVES
-------------------------------
  1-3   Build the real binaries; publish the four real seed blueprints
        through the real publish/index CLI pipeline (not a fixture).
  4-5   Serve the published tree over local HTTP; start a real vnproxd
        with `[hub] registry_url` pointed at it — the exact operator-facing
        shape docs/hub-registry.md's "Operator setup" documents.
  (d)   A real install, through the real client, the real T-2803 gate and
        the real per-installation trust store (`trustNewKey`).
  (e)   AC2, first half: a published ARTIFACT is tampered after publish
        (the index is left alone). Install is refused with
        `status: invalidSignature` — a per-artifact verdict inside a 200.
  (f)   AC2, second half, and a DIFFERENT failure than (e): the INDEX
        itself is edited after signing. The daemon (restarted to force an
        uncached re-fetch) refuses the WHOLE catalog — HTTP 502, zero
        entries, never a partial list — and is shown recovering cleanly
        once the pristine index is restored.
  (g)   AC3, by entry: one artifact is revoked by (type, id), re-signed,
        and is shown gone from `GET /hub/index` and refused by
        `POST /hub/install` (404) — while a DIRECT check of that same
        artifact's own bytes (bypassing the registry client and the T-2803
        gate entirely) shows its Ed25519 signature still verifies. That
        gap is the point: revocation is a catalog decision, not a claim
        that the bytes were forged.
  (h)   AC3, by signer fingerprint: a second revocation names only the
        publisher's fingerprint, never an id. Every remaining entry from
        that signer disappears, including one never named in any revoke
        command — "the one that matters in a real compromise"
        (docs/hub-registry.md).

RESULT: all five checks (d)-(h) PASS. See the Summary section at the foot
of the transcript.

NOT COVERED BY THIS HARNESS (out of scope for this run, tracked elsewhere)
================================================================================
This harness proves the CLIENT-SIDE verifier and revocation mechanism work
end to end against a real daemon and a real self-hosted registry — the
generic self-hosting path any operator can use today. It does NOT touch
the PUBLIC registry.vnprox.com, and cannot: per T-3709's CORRECTION
2026-08-24, both of registry.vnprox.com's signing keys live only on
pve001, a host this project has no credentials for and no authorisation to
modify. Concretely, this means:
  - the public registry cannot be re-published, re-keyed or made to serve
    a revocation by anyone working from this repository today;
  - the "revoke and verify the revocation is honoured" half of this
    transcript is real and reproducible against a SELF-HOSTED registry,
    but is NOT currently reproducible against registry.vnprox.com itself.
See docs/hub-registry.md's "Known limitation" note and
docs/security.md's hub section for the operator-facing statement of this
gap, and planning/tasks/T-3709-hosted-registry.md's CORRECTION section for
the full account of how it was found.
