VERDICT: pinning a single root (`internal/peer.Trust`'s design) is correct for
this deployment's real PKI shape — a leaf-only chain issued directly by the root,
one hop, verifies cleanly with just the root in the trust store. No intermediate
case exists to test here (see open item below on custom certs, which is the only
way an intermediate would ever appear).

Also checked, same session: neither node has a custom `pveproxy-ssl.pem`
installed —
  $ ls -la /etc/pve/local/pveproxy-ssl.pem /etc/pve/local/pveproxy-ssl.key
  ls: cannot access '/etc/pve/local/pveproxy-ssl.pem': No such file or directory
— confirming both nodes still use the default pmxcfs-issued cert. The "custom
certificate installed" register item stays open for the reason it always was:
this cluster has never had one, and installing one to test the rejection path
would be a real change to pveproxy's TLS material on the user's live host.

against a genuinely bad path, and is independent evidence (beyond the

against real network state, both healthy (corosync ring0, 0% loss) and broken
(vmbr3, no carrier) paths on the same real cluster.
