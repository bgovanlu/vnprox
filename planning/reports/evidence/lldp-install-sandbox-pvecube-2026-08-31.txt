=====================================================================
2. Root cause, including why only ONE of the two nodes failed
=====================================================================

vnproxd runs under ProtectSystem=strict. Read from inside the running
daemon's own mount namespace:

$ PID=$(systemctl show -p MainPID --value vnprox.service)   # 954084
$ nsenter -t $PID -m -- findmnt -no TARGET,OPTIONS /
/ ro,nosuid,relatime,errors=remount-ro

`/` itself is read-only — not merely /var. That is the fact that decides the
fix: `dpkg -L lldpd` writes under /usr and /etc, so there is no ReadWritePaths
set short of granting /usr, /etc and /var that makes a direct apt work, and
granting those three is not a narrowing of the sandbox but the end of it.

The asymmetry ("1 of 2 nodes") is apt's auto/manual bookkeeping:

$ apt-mark showauto lldpd
lldpd
$ apt-mark showmanual lldpd
(empty)

On pvecube lldpd is marked *auto*. `apt-get install -y lldpd` therefore wants
to promote it to manual, and that promotion is a write to
/var/lib/apt/extended_states — the file the transcript names. On pve001 the
package is already manual, so apt has no bookkeeping to write, exits 0, and
the identical daemon on the identical sandbox reports ok. The failure was
never about the node's configuration; it was about one bit in apt's state
file, which is why "install lldpd on all nodes" split 1/2 rather than 0/2.

3c. The escape hatch — systemd-run is reachable from inside the sandbox, and
its child is outside it. This is the branch pvecube will NOT take (the
package is present), so it is verified directly rather than inferred.

$ nsenter -t $PID -m -- sh -c 'command -v systemd-run'
/usr/bin/systemd-run
$ nsenter -t $PID -m -- systemd-run --wait --collect --quiet --pipe \

`ro` inside, `rw` in the child of the same unit. --quiet --pipe also confirmed
clean: systemd-run's own "Running as unit ..." line never reaches stdout, so
it cannot leak into the error string the UI renders.

    daemon's namespace with `nsenter -m`, which is the mount namespace only,
    and section 4's probe carried ProtectSystem/ReadWritePaths/ProtectHome/
    PrivateTmp/NoNewPrivileges but not CapabilityBoundingSet,
    RestrictAddressFamilies, RestrictNamespaces or SystemCallFilter. Every
    run recorded in this file — probe and real button press alike — took the

    itself has never run through it from the fully hardened daemon. A future
    tightening of vnprox.service that broke it (dropping AF_UNIX, or denying
    the SCM_RIGHTS fd passing `--pipe` depends on) would not be caught by any

=====================================================================
7. Addendum, 2026-09-02: what a code review found afterwards
=====================================================================

Sections 1-5 measured the right things and their conclusions stand. What they
did not do is exercise the branch this file is named after, and a review of
the commit found seven defects concentrated there. Recorded here because the
green evidence above is exactly what would make a later reader trust the
untested half.

  - The peer route ran on peer.DefaultRequestTimeout (5s). A node genuinely
    needing the install spends longer than that in apt, so the coordinator
    gave up and recorded a failure for work that then succeeded unobserved.
    Cancelling also killed only the `systemd-run` client: the transient unit
    kept running under PID 1 holding vnproxd's stdout pipe, so CombinedOutput
    blocked until apt finished, and the separate `systemctl enable` step was
    skipped entirely — leaving lldpd installed but never enabled.

  - `systemctl enable` was documented as needing no sandbox escape. Section
    3b's own transcript disproves that: it shows systemctl exec'ing
    /usr/lib/systemd/systemd-sysv-install inside the daemon's namespace,
    which runs update-rc.d, which renames links under /etc/rc[2-5].d. It
    passed here only because those links were already S-links.

  - The "systemd-run is unavailable" message could never appear: it was
    searched for in the command's output, but a missing binary makes exec
    fail before Start, with the text in err and no output at all.

  - The "Read-only file system" special case inverted its own diagnosis once
    apt moved outside the sandbox. Section 2's mount line shows this node is
    `errors=remount-ro`, so the likeliest remaining cause of that string is a
    genuinely read-only disk — and the message asserted the disk was fine.

  - `systemctl enable` prints two informational lines before anything else on
    this node (section 3b), so reporting the first line of a failed enable
    reported "Synchronizing state of lldpd.service..." as the error.

  - The one-line error dropped apt's transcript everywhere. A dpkg postinst
    failure's actual diagnosis carries no `E:` prefix, and `--pipe` keeps it
    out of the journal, so on pve001 it would have been unrecoverable.

  - Concurrent presses were left to race on /var/lib/dpkg/lock-frontend;
    omitting `--unit` prevents systemd colliding, but systemd is not what
    serialises package installs.

All seven are fixed as of the commit that appends this section, each with a
test that fails against the previous code.

8. 2026-09-02: the full-hardening gap from section 6, closed
=====================================================================

Section 6 recorded that the escape had only ever been measured under a
partial directive set — `nsenter -m` (mount namespace alone) and a probe
carrying ProtectSystem/ReadWritePaths/ProtectHome/PrivateTmp/NoNewPrivileges
but not CapabilityBoundingSet, RestrictAddressFamilies, RestrictNamespaces or
SystemCallFilter. Those three are the directives most likely to break
`systemd-run --pipe`, since it needs an AF_UNIX connection to the system bus
and SCM_RIGHTS fd passing.

Re-run on pvecube against the deployed v4.2.0 binary, under vnprox.service's
own hardening this time including CapabilityBoundingSet,
RestrictAddressFamilies, SystemCallFilter=@system-service and the whole
Protect*/Restrict* set:

$ systemctl is-enabled lldpd ; systemctl is-active lldpd
enabled
active

$ systemd-run --wait --collect --quiet --pipe \
    -p ProtectSystem=strict -p 'ReadWritePaths=...as shipped...' \
    -p ProtectHome=yes -p PrivateTmp=yes -p NoNewPrivileges=yes \
    -p ProtectKernelTunables=yes -p ProtectKernelModules=yes \
    -p ProtectKernelLogs=yes -p ProtectControlGroups=yes \
    -p ProtectClock=yes -p ProtectProc=invisible \
    -p RestrictRealtime=yes -p RestrictSUIDSGID=yes \
    -p SystemCallArchitectures=native \
    -p 'CapabilityBoundingSet=CAP_NET_ADMIN CAP_NET_RAW CAP_NET_BIND_SERVICE CAP_DAC_OVERRIDE CAP_DAC_READ_SEARCH CAP_CHOWN CAP_FOWNER CAP_SETPCAP' \
    -p 'RestrictAddressFamilies=AF_INET AF_INET6 AF_NETLINK AF_UNIX' \
    -p 'SystemCallFilter=@system-service' \
    /opt/lldpprobe420
RESULT ok=true took=764ms
probe exit=0

$ systemctl is-enabled lldpd ; systemctl is-active lldpd
enabled
active

What this now establishes that section 4 did not: the `systemd-run` escape
works under the complete shipped hardening, not a subset of it, and the
`systemctl enable` half of the flow runs through that escape (v4.2.0 moved
it there — before, it ran client-side and would have hit EROFS on
/etc/rc[2-5].d on a node whose links were K-links).

What it still does not establish, and section 6's caveat therefore stands in
reduced form: apt itself has never run through the escape on this node,
because pvecube has lldpd and takes the skip path. The mechanism is now
measured under full hardening; the apt branch's own behaviour under it is
not. Closing that needs a node without lldpd — the T-3704 nested lab, not
vnprox-dev.

Probe binary removed from the node.
