=====================================================================
2. Root cause, including why only ONE of the two nodes failed
=====================================================================

vnproxd runs under ProtectSystem=strict. Read from inside the running
daemon's own mount namespace:

$ PID=$(systemctl show -p MainPID --value vnprox.service)   # 954084
$ nsenter -t $PID -m -- findmnt -no TARGET,OPTIONS /
/ ro,nosuid,relatime,errors=remount-ro

`/` itself is read-only — not merely /var. That is the fact that decides the
fix: `dpkg -L lldpd` writes under /usr and /etc, so there is no ReadWritePaths
set short of granting /usr, /etc and /var that makes a direct apt work, and
granting those three is not a narrowing of the sandbox but the end of it.

The asymmetry ("1 of 2 nodes") is apt's auto/manual bookkeeping:

$ apt-mark showauto lldpd
lldpd
$ apt-mark showmanual lldpd
(empty)

On pvecube lldpd is marked *auto*. `apt-get install -y lldpd` therefore wants
to promote it to manual, and that promotion is a write to
/var/lib/apt/extended_states — the file the transcript names. On pve001 the
package is already manual, so apt has no bookkeeping to write, exits 0, and
the identical daemon on the identical sandbox reports ok. The failure was
never about the node's configuration; it was about one bit in apt's state
file, which is why "install lldpd on all nodes" split 1/2 rather than 0/2.


=====================================================================
3. The two branch predicates, read inside the daemon's own namespace
=====================================================================

3a. The skip predicate — dpkg-query works inside the sandbox and says yes.

$ nsenter -t $PID -m -- dpkg-query -W -f='${db:Status-Status}\n' lldpd
installed
exit=0

3b. The enable step needs no escape, and is genuinely a no-op here.

$ systemctl is-enabled lldpd ; systemctl is-active lldpd
enabled
active
$ nsenter -t $PID -m -- systemctl enable --now lldpd
Synchronizing state of lldpd.service with SysV service script with /usr/lib/systemd/systemd-sysv-install.
Executing: /usr/lib/systemd/systemd-sysv-install enable lldpd
exit=0
$ systemctl is-enabled lldpd ; systemctl is-active lldpd
enabled
active

3c. The escape hatch — systemd-run is reachable from inside the sandbox, and
its child is outside it. This is the branch pvecube will NOT take (the
package is present), so it is verified directly rather than inferred.

$ nsenter -t $PID -m -- sh -c 'command -v systemd-run'
/usr/bin/systemd-run
$ nsenter -t $PID -m -- systemd-run --wait --collect --quiet --pipe \
      --description='vnprox sandbox escape probe' findmnt -no TARGET,OPTIONS /
/ rw,relatime,errors=remount-ro
exit=0

`ro` inside, `rw` in the child of the same unit. --quiet --pipe also confirmed
clean: systemd-run's own "Running as unit ..." line never reaches stdout, so
it cannot leak into the error string the UI renders.

4. End-to-end: the shipped function, under the shipped hardening
=====================================================================

A scratch binary calling host.InstallLLDPD at 8cdd427e — the same function
POST /api/v1/lldp/install calls — built from the repo tree, run on pvecube
under a transient unit carrying vnprox.service's own hardening directives
(ProtectSystem=strict, the same ReadWritePaths line, ProtectHome, PrivateTmp,
NoNewPrivileges, the Protect*/SystemCall* set). The binary was removed from
the node afterwards.

$ systemd-run --wait --collect --quiet --pipe \
    -p ProtectSystem=strict \

    -p ProtectKernelTunables=yes -p ProtectKernelModules=yes \
