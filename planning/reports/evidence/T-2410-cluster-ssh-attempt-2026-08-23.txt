the real cause of attempts 1–5's corruption, and the eventual PASS
=====================================================================

This file's "Conclusion" above was written by one of two agent processes
working T-3705 in parallel against this same repo checkout — this task
deliberately forked sub-agents for research, and at least one of them
independently decided to also attempt this job. **Both were running
`make build` (and therefore `npm ci`/`vite build`) against the same
`web/node_modules` directory at overlapping times.** Two concurrent `npm
ci` runs racing to delete-and-repopulate the same `node_modules` tree is
sufficient on its own to produce exactly the symptom both attempts saw —
a different package corrupted or truncated each time, never the same
twice, "succeeds standalone, fails inside the job seconds later" — without
needing to invoke any sandbox/filesystem theory at all. This is the
mundane explanation and it fits the evidence better than a filesystem
fault: once one of the two processes stopped running `npm ci` against
this tree, the very next attempt (below) passed cleanly on the first try.

A second, real contributing bug (independent of the race): `go: command
not found`. `scripts/ci-local.sh`'s `job_cluster_ssh` calls `make build`,
which invokes `$(GO) build`; this dev environment's `go` binary lives at
`~/.local/go/bin/go`, which is on an interactive shell's `PATH` but not
necessarily on a non-interactive `bash -lc` shell's PATH depending on how
it's invoked — one attempt failed at the Go build step specifically with
`go: command not found` until `PATH="$HOME/.local/go/bin:$PATH"` was set
explicitly alongside `nvm use 22`. `docs/development.md`'s environment
setup should be checked for whether this is already documented; if the
local Go install isn't on the default PATH `ci-local.sh` inherits, every
job that calls `make build` (not just `cluster-ssh`) is exposed to this,
not only under an agent's non-interactive shell.
