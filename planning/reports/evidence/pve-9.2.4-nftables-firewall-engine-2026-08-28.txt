LOAD-BEARING FINDING (answer the card's own question first):
============================================================================

PVE 9.2.4 ships TWO firewall compile engines side by side, both installed
and both running as systemd services on pvecube right now:

  - pve-firewall (Perl, package pve-firewall 6.0.4) — the legacy engine,
    compiles the ruleset to **iptables** (iptables-restore, PVEFW-* chains,
    Firewall.pm's compile_iptables_filter).
  - proxmox-firewall (Rust, package proxmox-firewall 1.2.3, binary
    /usr/libexec/proxmox/proxmox-firewall, its own proxmox-firewall.service
    + proxmox-firewall.timer) — the new engine, compiles the ruleset to
    **nftables** (table `inet proxmox-firewall`, table `bridge
    proxmox-firewall-guests` — table/chain names below are read straight
    out of the installed binary, not guessed).

Which engine actually runs is a **per-host boolean option** (`nftables`,
default `false`, described by PVE itself as "tech preview" —
`/usr/share/perl5/PVE/Firewall.pm` line ~1448) set in `host.fw`'s
`[OPTIONS]` block. `PVE::Firewall::is_enabled_and_not_nftables()` decides,
on every compile pass, which of the two actually writes rules — and drops
a flag file (`/run/proxmox-nftables-firewall-force-disable`) that tells
`proxmox-firewall` (the Rust daemon) to stand down whenever the legacy
path is the one in force. On pvecube, this flag file currently EXISTS
(see §3 below): the legacy iptables engine is what would install rules if
the firewall were turned on, not nftables — **the opposite of this card's
starting assumption**. Concretely: the option's own compiled-in default
is `nftables: false`, pvecube's `host.fw`/`cluster.fw` do not override it,
so **iptables is the currently-effective engine, not nftables**, even
though proxmox-firewall's nftables path is fully installed, enabled at the
systemd level, and clearly the direction PVE is investing in (see the
changelog activity in §5 — five point releases between Aug 2025 and May
2026).

Both engines currently produce **zero compiled rules** on pvecube, for a
reason that has nothing to do with which engine is selected: the
datacenter firewall itself is administratively disabled
(`cluster.fw`: `enable: 0`) — see §2. So the compiled ruleset this card's
inspector will read is legitimately empty on pvecube today, and this
transcript cannot show a live example of a populated table (see the
"What was NOT observed" section for exactly what that means for the
built inspector).

What was NOT observed (explicit, per CLAUDE.md's "say so, don't guess")
============================================================================

- No populated `nft -j list ruleset` output — the datacenter firewall was
  disabled for the entire capture window, and turning it on to observe
  compiled rules is exactly the live-config mutation this task's rules
  forbid. internal/host/nftables.go's parser is therefore validated
  against (a) the real empty-ruleset shape captured in §2, and (b) a
  hand-authored fixture built strictly from the table/chain vocabulary
  confirmed in §4 — never against a real populated document. This is
  called out in that file's own doc comment, not hidden.
- No confirmation of individual-rule expression shape (how a saddr/dport/
  action pentuple actually renders in JSON `expr`), nor of whether/how a
  compiled rule is tagged (via `comment` or otherwise) back to the
  specific pve-firewall/vnprox rule that produced it. This is the direct
  reason the compiled-ruleset inspector's rule-to-vnprox-rule attribution
  is implemented as an explicitly-labeled best-effort match (cluster/node
  scope only, against internal/fw's resolved ruleset) rather than a
  claimed exact mapping, and why guest/vnet-scope compiled entries
  (table `bridge proxmox-firewall-guests`) are labeled "not determinable"
  rather than guessed at — see internal/api/nftables.go's doc comment.
- No confirmation of the legacy iptables engine's exact PVEFW-* chain/
  rule text when populated (iptables-save was captured empty for the same
  reason). Out of scope for this card regardless — the card asks
  specifically for the nftables reader — but material to the finding
  above: on pvecube today, iptables is the engine that would actually
  populate if the firewall were turned on, so this inspector reading only
  nftables output will show an honest "no nftables ruleset here" empty
  state rather than the (nonexistent, in nftables terms) compiled rules a
  reader might expect if the firewall were enabled in its current,
  un-opted-in configuration.
