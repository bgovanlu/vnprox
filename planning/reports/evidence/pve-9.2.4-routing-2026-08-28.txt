Observations on the JSON shape (drives the parser's field tolerance):
- `dst:"default"` for the default route, not "0.0.0.0/0" — must special-case.
- `table` is present on "local"-table rows but ABSENT on main-table rows (main is implicit —
  `ip route show table all` without a `table` key means table 254/"main"). The parser must
  default an absent `table` field to "main", never treat it as "unknown".
- `type` is present (local/broadcast/anycast/multicast) only for non-unicast route types;
  absent means ordinary unicast — default type to "unicast" when absent.
- No top-level `table=254` numeric id ever appears in this iproute2 version's JSON — tables are
  named ("local","main") not numbered, except custom/policy-routing tables which iproute2
  renders by their /etc/iproute2/rt_tables name if known, else by number as a string.
- `gateway` present only for routes with a next hop IP (default route here); directly-connected
  routes carry `prefsrc` instead and no `gateway`.
- `flags` is always present, always an array (empty `[]` in every row observed here).
- v6 rows carry `pref` (RFC 4191 route preference: "medium" observed); v4 rows never do.

=== vtysh -c "show ip route vrf all json" (checked for non-default VRFs) ===
$ vtysh -c "show ip route vrf all json" | head -c 500
{"default":{"0.0.0.0/0":[{...same routes as above, now nested one level under a "default" key...

Shape difference vs. plain `show ip route json`: `vrf all` wraps the whole per-prefix map in an
outer {"<vrfName>": {...}} object; the plain command returns the per-prefix map directly with no
outer VRF wrapper (defaulting to VRF "default" implicitly, confirmed by each entry's own
"vrfName":"default" field). The parser (`internal/route/frr_rib.go`) therefore does NOT rely on
top-level shape to detect which command produced the bytes — it auto-detects "does the top-level
map's values look like arrays of route objects (plain form) or like nested per-prefix maps
(vrf-all form)" the same tolerant-shape-sniffing style frr.go's ParseBGPSummary already
established for the BGP-summary flat-vs-AFI-nested ambiguity — and always trusts each route
entry's own embedded "vrfName" field for grouping, never the wrapper key alone. vnprox's own
fetch uses the plain (non-`vrf all`) command day-to-day, since Real only reads one node's default
VRF path today (no VRF-lite zones are deployed on either cluster node); the tolerant parse means
a future EVPN-VRF-lite zone's RIB is not a rewrite.

=== Summary of what this means for the implementation ===
1. `ip -j route show table all` and `ip -j -6 route show table all` are both available and
   produce one flat JSON array each — this is the FIB reader's primary source, used in
   preference to the non-JSON `ip route show` text form named in the task brief.
2. `ip -j rule show` / `ip -j -6 rule show` are both available (JSON policy rules).
3. FRR 10.6.1 is running on pvecube with vtysh present; `show ip route json` /
   `show ipv6 route json` both work and are consumed for the RIB, using the "plain" (non-`vrf
   all`) command since Real only ever asks about its own node's default VRF today — matching
   `frr.go`'s existing `FRRBGPSummary`/`FRREVPNVNI` exec pattern (ErrFRRUnavailable when vtysh
   is not installed, exactly as those two already implement).
4. No SDN zones/VRFs are configured on pvecube right now, so this transcript cannot show a
   non-default-VRF RIB or a custom policy-routing table in the wild — the parser is written
   tolerant of both (embedded vrfName/table-name fields drive grouping, not response shape),
   per CLAUDE.md's "observe, don't invent" rule: nothing here that isn't in this transcript was
   assumed to exist, and nothing in this transcript was overridden by a guess.
