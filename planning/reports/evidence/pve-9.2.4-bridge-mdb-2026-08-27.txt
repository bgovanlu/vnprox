1. `bridge mdb show`
=======================================================================

FINDING: the MDB table on pvecube is NOT empty. It holds 4 entries, all for the same
multicast group ff02::fb (mDNSv6 / "link-local IPv6 multicast name resolution", the IPv6
equivalent of 224.0.0.251 mDNS). All four are `temp` (dynamically learned via snooping, will
age out — as opposed to `permanent`, a statically configured entry). This gives us a real,
non-fabricated example of a populated group/port/state row, but only for one group
(mDNSv6) and one state (`temp`); see "what we could NOT observe" below.

NOTE for the implementer: netlink's IFLA_BRIDGE info_data uses the `mcast_*` key prefix
(mcast_snooping, mcast_router, mcast_querier, ...); the sysfs files under
.../bridge/multicast_* use the longer `multicast_*` prefix but are the SAME underlying
kernel state (values agree exactly: mcast_snooping=1 == multicast_snooping=1,
mcast_router=1 == multicast_router=1, mcast_querier=0 == multicast_querier=0, etc). Since
`internal/host/netlink_linux.go` already fetches `LinkState` via netlink for bridges (per
`fdb.go`'s doc comment, "BridgeDetail" is populated there), the snooping/querier/router
state should be read off the SAME already-fetched netlink link attrs (`mcast_snooping`,
`mcast_router`, `mcast_querier`) rather than opening a second sysfs-file code path — sysfs
values above are recorded only to confirm they agree with netlink, not because sysfs is the
intended fetch route.

What was populated vs. NOT observed (read this before writing the parser)
=======================================================================
POPULATED / directly observed on pvecube:
  - `bridge -d -j mdb show` real JSON shape: array-of-one, {"mdb":[...],"router":{}}.
  - Row fields: index, dev, port, grp, state, protocol, flags (flags always empty array).
  - state value: "temp" (dynamically-learned, snooping-derived).
  - protocol value: "kernel".
  - grp value: an IPv6 multicast address (ff02::fb, mDNSv6) — group can be IPv6, not just
    IPv4/224.x.
  - Per-bridge multicast_snooping=1, multicast_querier=0, multicast_router=1 (all bridges,
    all uniform default values) — both via sysfs and via netlink's mcast_* linkinfo fields.
  - Per-port multicast_router=1 on every port of every populated bridge.
  - Bridges with NO mdb rows at all: vmbr1, vmbr3, vmbr99 (no entries shown for these in any
    `bridge mdb show` variant — confirms the parser must handle bridges absent from the MDB
    dump entirely, not just bridges present with zero rows).

NOT observed (do not fabricate these; treat as unknowns/gaps in the parser and tests):
  - A `permanent` MDB entry (statically added, e.g. `bridge mdb add ... permanent`) — every
    entry seen here is `temp`. Permanent-state formatting/behavior is inferred from the
    `bridge` command's own vocabulary (permanent vs temp are the only two documented mdb
    states), not verified against real output.
  - An IPv4 multicast group row (all 4 observed rows are the IPv6 mDNS group ff02::fb; no
    224.0.0.0/4 row was present).
  - A non-empty `flags` array (e.g. "offload" for hardware-offloaded entries) — not present
    on this host (no multicast-capable switch ASIC offload path here).
  - A `vid`/VLAN-tagged MDB row — none of this host's bridges have vlan_filtering enabled
    (`"vlan_filtering":0` in §7), so a VLAN-scoped MDB entry's JSON shape is UNVERIFIED.
  - A non-"kernel" protocol value (e.g. what a PIM/mrouted-injected static route would show).
  - A populated `"router"` map (i.e., an explicit multicast-router port entry) — every
    observed "router" object was empty `{}`. What that key's shape looks like when non-empty
    is UNVERIFIED against real output.
  - multicast_snooping=0 (disabled) on any bridge, or multicast_router values other than 1
    (0=never, 2=permanent) — this host's 7 bridges are 100% uniform stock defaults, so
    snooping-disabled and router=0/2 rendering are UNVERIFIED against real output.
  - Per-bridge `multicast_stats_enabled=1` behavior (stats counters) — always 0 here, so the
    stats-counter surface (`bridge -s mdb show` equivalents) is out of scope / unverified.

Conclusion: unlike the "expect empty" framing in the task card, pvecube's MDB table was NOT
empty — mDNS (well-known IPv6 mDNS group ff02::fb) traffic from guests/host produced real,
observable, populated rows. This is itself useful: it means the parser and fixtures below are
grounded in a real populated example rather than only an empty-table guess. But the observed
population is narrow (one group, one state, one protocol, no VLAN tagging, no permanent
entries, no router-port entries) — the gaps listed above are handled by keeping the parser's
field types permissive (plain strings for state/protocol) rather than closed enums, and the
empty-bridge case (vmbr1/vmbr3/vmbr99) is exercised directly since it's real, observed
behavior on this very host.
