GITLEAKS — full history, all refs
  $ gitleaks detect --source . --log-opts="--all" -f json \
      -r planning/reports/evidence/gitleaks-full-history.json -v \
      > planning/reports/evidence/gitleaks-full-history.stdout.txt 2>&1
  Result: "679 commits scanned" / "leaks found: 38"
  Note on the 679 vs 853 count: gitleaks diffs each commit against its parent(s); with default
  (non -m) git log traversal a merge commit has no isolated diff and contributes nothing new to
  scan, so 679 non-merge commits (git rev-list --all --no-merges) is the correct "content-bearing"
  denominator. 679 + 174 merge commits = 853, confirmed via:
    $ git rev-list --all --no-merges | wc -l   -> 679
    $ git rev-list --all --merges    | wc -l   -> 174
  Sanity re-run scoped to just the two named branches (should be a subset, and was):
    $ gitleaks detect --source . --log-opts="origin/sigstore-in-daemon" ...  -> 38 leaks (same set)
    $ gitleaks detect --source . --log-opts="origin/t-2409-e2e-store-isolation" ... -> 25 leaks (subset)

WHAT THIS METHOD DOES NOT COVER
  - Neither tool inspects binary blobs beyond gitleaks'/trufflehog's built-in archive/text
    extraction; no compiled binaries or images were committed in this history (verified separately:
    no .deb/.tar.gz/.bin artifacts under git-tracked paths), so this gap is believed moot here but
    was not exhaustively re-proven.
  - trufflehog's verification step only covers detectors with a known verification endpoint
    (GitHub, GitLab, AWS, etc.); it does not and cannot verify PVE tickets/tokens against a live PVE
    API (no such detector exists), nor could it validate the WireGuard-shaped test keys — those were
    instead confirmed synthetic by reading the test file's own text (explicit `mustNotHave`/`gone`
    assertions naming them as fixtures for a redaction test).
  - Both tools scan tracked git history/objects only. Anything ever force-pushed away and garbage-
    collected from every clone (there is no evidence of this happening) would not be visible to a
    scan run against this working copy; GitHub's own reflog/object retention was not queried (no
    API access to GitHub's server-side dangling-object store from this environment), so a purge
    on GitHub's end, if ever needed, cannot be confirmed clean from local tooling alone.
  - This is a point-in-time scan of the state as of 2026-08-27. It does not cover commits made after
    this scan ran.
