3. The REAL mechanism: `?pending=1` — verified against perl source AND live
============================================================================

Read (not executed) on pvecube, read-only file access:
  /usr/share/perl5/PVE/API2/Network/SDN/Zones.pm
  /usr/share/perl5/PVE/API2/Network/SDN/Vnets.pm
  /usr/share/perl5/PVE/API2/Network/SDN/Subnets.pm
  /usr/share/perl5/PVE/API2/Network/SDN/Controllers.pm
  /usr/share/perl5/PVE/API2/Network/SDN/Fabrics.pm
  /usr/share/perl5/PVE/API2/Network/SDN/Ipams.pm
  /usr/share/perl5/PVE/Network/SDN.pm

Every one of Zones/Vnets/Subnets/Controllers/Fabrics.pm's GET (list and
single-item) handlers accepts an optional boolean `pending` query param.
When set, the handler calls (PVE/Network/SDN.pm):

    sub pending_config {
        my ($running_cfg, $cfg, $type) = @_;
        my $pending = {};
        # ids present in RUNNING but changed/removed in staged config:
        #   -> $pending->{$id}->{state} = "deleted" | "changed"
        # ids present in STAGED config but new/changed vs running:
        #   -> $pending->{$id}->{state} = "new" | "changed"
        #   -> $pending->{$id}->{pending}->{$key} = <new value>  (only the
        #      keys that actually differ, not the whole object)
        ...
        return { ids => $pending };
    }

i.e. the wire shape of one `?pending=1` list entry is:

    {
      "zone": "...", "type": "...",       // identity + a few passthrough fields
      "state": "new" | "changed" | "deleted",   // ABSENT when in sync
      "pending": { "<field>": <new value>, ... } // ABSENT when in sync;
                                                   // present only for the
                                                   // fields that differ
    }

`Ipams.pm` has NO `pending` param at all (grep confirms zero hits) — IPAM
plugin instances are not part of PVE's pending/running SDN commit cycle
the way zones/vnets/subnets/controllers/fabrics are. Scoped out of this
fix's detection accordingly (see report).

Live confirmation (labz/labnet are currently in sync, so no live positive
example of a populated "state"/"pending" was observable without staging an
edit, which this task's mandate forbids — mutating pvesh calls against
pvecube are off limits):

$ pvesh get /cluster/sdn/zones --pending 1 --output-format json

============================================================================
4. PVE's own concept of "does the cluster have ANY pending SDN change" —
   directly relevant to why this must be a timing-based check, not an
   attribution-based one
============================================================================

/usr/share/perl5/PVE/Network/SDN.pm:

    sub has_pending_changes {
        my $running_cfg = PVE::Network::SDN::running_config();
        my $config_files = {
            zones => ..., vnets => ..., subnets => ..., controllers => ...,
            fabrics => ..., 'route-maps' => ..., 'prefix-lists' => ...,
        };
        for my $config_file (keys %$config_files) {
            my $pending_config = PVE::Network::SDN::pending_config(...);
            for my $id (keys %{ $pending_config->{ids} }) {
                return 1 if $pending_config->{ids}->{$id}->{pending};
            }
        }
        return 0;
    }

This is a bare cluster-wide boolean with NO per-user/per-session/per-
changeset attribution whatsoever — PVE has no concept of "whose" pending
edit a given zone/vnet/subnet carries. It is used exactly once in the API
(`/usr/share/perl5/PVE/API2/Network/SDN.pm`'s `POST /sdn/lock` handler):
acquiring the global SDN lock refuses (`die "configuration has pending
changes"`) unless the caller passes `allow-pending=1`. There is no API
that answers "is this specific pending change mine".

CONCLUSION THIS FIX IS BUILT ON: since PVE itself cannot distinguish "my"
pending edits from "foreign" ones, vnprox can't either by asking PVE — the
only sound boundary is TIMING. Reading `?pending=1` once, immediately
before this changeset's own SDNStageOp calls run (i.e. at the same moment
`apply.go`'s pre-apply snapshot captures `SDNConfig()`), means every entry
it returns necessarily predates and is therefore not caused by this
changeset — it is foreign by construction, not by inference.

============================================================================
5. Consequence for the mock
============================================================================

`internal/pvemock` already tracks a `Pending` marker
(PendingNone/PendingNew/PendingChanged/PendingDeleted) per zone/vnet/
subnet/controller/fabric object internally (T-401/T-402), and already
derives a `?running=1` view from it. That internal marker is exactly
equivalent to what real PVE's `pending_config()` computes (a per-object
new/changed/deleted classification) — it's just exposed on the wrong
query param today (the mock's DEFAULT view leaks it; real PVE's default
view never does, only `?pending=1` does — see §1). This task's mock change
adds real `?pending=1` support (state + a `pending` sub-object of changed
fields) built from that same existing internal marker, so the wire shape
now matches real PVE's confirmed behaviour above, and leaves the existing
(pre-existing, T-401-owned) default-view/`?running=1` behaviour untouched.
