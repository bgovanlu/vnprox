T-3901 evidence — bridge STP/RSTP state (root bridge, port role/state)
Host: pvecube (192.168.1.9), PVE 9.2.4, kernel 7.0.14-4-pve
Captured: 2026-08-27, read-only commands only (ip/bridge *show*, cat of /sys/class/net/**)

Why this transcript exists
---------------------------
CLAUDE.md: never model a PVE object or kernel interface from docs, mocks, or
release notes — observe it on pvecube first. T-3901 (STP/RSTP on the map)
needs the real field set for bridge-level STP state (root bridge ID, our own
bridge ID, stp_state) and per-port state, sourced before any parser/type/
fixture was written.

Headline surprise vs. what the task card assumed
--------------------------------------------------
Every bridge on pvecube has STP administratively OFF (`bridge-stp off` in
/etc/network/interfaces for all of vmbr0-3; PVE's own default). So there is
no live example of a *blocking* port or of root_id != bridge_id on this
host — no loop exists to force blocking. What IS observable and load-bearing
regardless of stp_state:
  - the kernel bridge always maintains root_id/bridge_id/root_port and a
    per-port `state` (disabled/listening/learning/forwarding/blocking) even
    when STP is administratively off — the port `state` on an up/forwarding
    port reads "forwarding" (3), and a down/no-carrier port reads
    "disabled" (0), which is IFLA_BRPORT_STATE, not gated on stp_state.
  - the Linux kernel's built-in bridge STP is classic 802.1D, not RSTP: it
    exposes no per-port "role" attribute (no alternate/backup role fields
    populated with real semantics) the way real RSTP/MSTP switches do.
    PVE ships no mstpd/RSTP userspace daemon by default. So "port role"
    for T-3901 must be *derived*, not read verbatim:
      root bridge:  root_id == bridge_id (this bridge is itself the root)
      root port:    (on a non-root bridge) the port whose port_no equals
                     the bridge's root_port
      designated:   any other port in state forwarding/learning/listening
      blocking:     port `state` == 4 (kernel BR_STATE_BLOCKING)
      disabled:     port `state` == 0 (also matches "no carrier"/down)
    This mapping is documented in the derivation code (internal/host/stp.go)
    with a reference back to this transcript rather than re-derived from
    docs.
  - a port's own `/sys/class/net/<port>/brport/*` directory is a real,
    independently-addressable path (not just reachable via the bridge's
    `brif/`) — confirmed the two resolve to the identical sysfs kobject via
    `readlink -f`. The reader below uses the per-port path directly rather
    than requiring the bridge name.
  - there is no `brport/stp_state` — stp_state is bridge-level only
    (`/sys/class/net/<bridge>/bridge/stp_state`), not per-port.

Field-name/value summary carried into the Go types (internal/host/stp.go)
---------------------------------------------------------------------------
Bridge-level (/sys/class/net/<bridge>/bridge/*):
  stp_state        int, 0=off 1=kernel STP 2=RSTP(userspace, e.g. mstpd) —
                    PVE never observed >0 on this host; parser accepts all
                    three per the kernel's own br_stp_set_enabled() values.
  root_id          "<priority-hex>.<mac>" e.g. "8000.a8b8e0000ee8"
  bridge_id        same format, this bridge's own ID
  root_port        int; ifindex-like port number (0 when this bridge is
                    itself the root — matches designated_root==bridge_id)
  root_path_cost   int
  priority         int (bridge priority component of bridge_id, decimal)
  forward_delay, hello_time, max_age, ageing_time: centisecond ints (kernel
                    convention, e.g. hello_time=200 -> 2.00s)
  topology_change, topology_change_detected: 0/1 flags — the "TCN flag"
                    internal/findings/health_stpburst.go's doc comment
                    already references as the only available cumulative-ish
                    signal; T-3901 does not re-derive that, it is a
                    different, steady-state surface.

Per-port (/sys/class/net/<port>/brport/*, equally reachable via
/sys/class/net/<bridge>/brif/<port>/*):
  state            int 0..4: 0=disabled 1=listening 2=learning 3=forwarding
                    4=blocking (kernel BR_STATE_* enum; matches `bridge -d
                    link show`'s state=disabled/forwarding string names)
  designated_root, designated_bridge: same "<prio-hex>.<mac>" format as the
                    bridge-level root_id/bridge_id
  designated_cost, designated_port: ints
  path_cost, priority, port_id, port_no: ints (port_id/port_no rendered as
                    hex strings by sysfs, e.g. "0x8001"/"0x1")
  root_block, bpdu_guard, hairpin_mode, isolated, learning: 0/1 flags — not
                    STP protocol state, but bridge-port config that
                    influences it; out of scope for T-3901's role/state
                    surface (kept for a future card if needed).

No native "port role" (root/designated/alternate/backup in the RSTP sense)
is exposed anywhere in sysfs or netlink for the Linux kernel's built-in
bridge STP — it must be derived from root_id/bridge_id/root_port/state as
documented above and in internal/host/stp.go's doc comment.
