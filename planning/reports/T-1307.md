# T-1307 · Guided diagnosis flows

## Summary

Implemented in full: a new `internal/diagnose` package (`Ladder`/`Step`/`Outcome`/`Result` — a
generic, dependency-light sequencer that owns no diagnostic logic of its own, only orchestration)
and `internal/api/diagnose.go` (`POST /diagnose {targetRef, escalateToCapture?}`), which registers
the five canonical ladder steps the card names — config check (`internal/sim.Simulate`, T-503),
live probe (`internal/probe.Run`, T-802/T-806), guest interior (T-1304's `fetchQEMUInterior`/
`fetchLXCInterior`), conntrack (T-1305's `fetchClusterConntrack`), and capture (T-1301's
`CaptureService.Start`) — as thin closures composing those already-shipped surfaces directly,
reusing `internal/api`'s own private target-resolution helpers rather than duplicating them. A
target (guest-nic, bare guest, or edge — bridge/bond/vlan/SDN VNet) resolves to a diagnostic
`src -> gateway` tuple from the target's own attached bridge/VNet `Gateway` field where known;
config-check/live-probe/guest-interior self-report `skipped` (never `error`) when they don't apply.
The verdict's `linkedFindingIds`/`suggestedFixRef` correlate against `GET /findings`' live stream
by `Refs` overlap (target itself, its owning guest, its attached bridge/VNet) plus any
`sim_divergence` finding the live-probe step itself just persisted — `suggestedFixRef` only ever
names an existing `Fixable` finding, resolved through the unchanged `POST /findings/{id}/fix`
route (no divergent fix-computation path, proven by an actual round-trip test). Capture only ever
starts when `escalateToCapture: true` **and** the session holds the `capture` capability (checked
in-step via a new `DiagnoseCapabilityChecker` seam, never a route-level 403) — a caller lacking it
gets that one step `skipped` while every other eligible step still runs. One `diagnose.run` audit
row per call. `docs/api.md` gets a new "Diagnosis" section documenting the stable `Result` shape
explicitly as the T-1701 MCP contract. Frontend: `web/src/diagnose/DiagnosisPage.tsx` (routed at
`/diagnose?ref=`), reachable from a new inspector header button and map right-click item on any
guest/guest-nic/edge entity, rendering the step-by-step ladder result and the verdict with a
"Review suggested fix" button wired to the same changeset-drawer flow `FindingsStreamPanel` uses.

## Deviations from the card (with reasons)

- **Single `diagnose.run` audit row per call, not one per reached-into-a-guest sub-step.** The
  live-probe step reaches into a guest (the same class of action `POST /simulate/verify` audits as
  `probe.verify`) and the guest-interior step likewise (`guest.interior_read`), but the card's own
  deliverable text says the whole route is "Audited as `diagnose.run`" — followed literally rather
  than additionally emitting a second, per-step audit row that isn't in the card's own contract.
  The live-probe step still persists a `sim_divergence` finding on divergence (via the exact same
  `recordDivergence` T-806 already uses), so a diverging observation is not lost from the findings
  stream even without its own `probe.verify` row — but a `GET /audit` browse of *just* `probe.verify`
  rows would not show a diagnose-triggered probe attempt that didn't diverge. Flagged rather than
  silently decided; an easy follow-up if a future task wants per-step audit granularity.
- **`web/e2e/diagnose.spec.ts` could not be proven green on this shared sandbox — and neither can
  the already-merged, unmodified `web/e2e/guest-interior.spec.ts` (T-1304).** Running the new spec
  against the real stack (pvemock → vnproxd → the production SPA build) initially failed because
  four of the six `testdata/dev-*.toml` stacks Playwright's shared `webServer` array boots had no
  `[blueprint]` override (T-1107 landed after those files were written) and so tried to write
  `/etc/vnprox/keys/blueprint-signing.key`, which this sandbox has no permission to create —
  breaking `vnproxd` startup for *every* spec in the suite, not just this one (fixed in the
  `testdata:` commit, mirroring `dev-alert.toml`'s own documented precedent for the identical class
  of gap with T-1001's metrics token). After that fix, `diagnose.spec.ts` still failed on a search-
  dialog timeout (`app01 guest` result never appearing within 120s). To isolate the cause, I
  temporarily reduced `playwright.config.ts`'s `webServer` array to just the primary stack
  (diagnostic only, reverted — `git diff` on that file is empty) and reran; the failure persisted
  identically. I then ran the **unmodified, already-merged** `guest-interior.spec.ts` in the same
  reduced config and got the **exact same failure signature** (identical error, identical `/api/ws`
  request taking ~121s to complete its upgrade, right at the timeout boundary) — proving this is a
  pre-existing environment limitation of this sandbox (most likely slow TCP-timeout behavior
  reaching the fixture's fake peer IPs, `10.10.0.12`/`10.10.0.13`, which `topology.spec.ts`'s own
  doc comments already flag as "unreachable from this machine" and a source of ongoing collector
  retry/staleness noise), not a defect in this task's own code. Per this task's own instructions
  ("If the shared dev host makes a clean Playwright run impossible, say so explicitly rather than
  claiming it passed"), I am reporting this plainly rather than claiming AC6 fully verified via
  e2e. `npx tsc --noEmit` and `npx eslint e2e/diagnose.spec.ts` both pass on the spec itself, so it
  is at minimum known-valid TypeScript exercising the intended user flow; the underlying
  functional contract it targets is proven at the Go/Vitest levels (AC5/AC6 above).
- **Verdict `confidence` heuristic is a deliberately simple, disclosed one** (`none`/`low`/`high`/
  `medium` based on ran-count/error-count/finding-count — see `internal/diagnose/ladder.go`'s
  `computeVerdict`), not a scored/weighted diagnosis — the card asks for "one readable verdict
  page," not a scoring algorithm, and `docs/api.md`'s Diagnosis section documents the exact
  branches so this is a stated contract, not a hidden heuristic.
- **`escalateToCapture`'s UI checkbox is not client-side capability-gated** (unlike other
  capability-gated affordances elsewhere in this app), because the frontend's `Capabilities` type
  has no `capture` field yet — that addition belongs to T-1302 (Capture UX), which had not landed
  on this worktree's base and is not one of this card's dependencies. The server-side gate is the
  real one regardless (item 3 above); the UI simply always offers the checkbox and shows the
  server's own stated skip reason if the session doesn't hold the capability. Noted for whoever
  lands T-1302 to reconcile.

## What the next agent should know

- `internal/diagnose` is intentionally generic and import-light (only `context`/`fmt`/`sort`/
  `time` beyond stdlib) — it is the package T-1701's MCP surface should import directly for the
  `Result`/`StepResult`/`Verdict` types and the `StepStatus`/`Confidence` vocabularies, rather than
  redefining them.
- The ladder is a registration table (`buildDiagnoseLadder` in `internal/api/diagnose.go`), not a
  hardcoded sequence — Phase 14's WireGuard/edge diagnostics card can append a `diagnose.Step` at
  its own construction call site without touching `internal/diagnose`'s own code, exactly as the
  card asked.
- `resolveDiagnoseTarget`/`resolveDiagnoseGatewayIP`/`firstGuestNic` (all in
  `internal/api/diagnose.go`) are the one piece of genuinely new target-resolution logic this task
  added (everything else composes existing helpers) — worth reading first if extending which
  targets the ladder accepts.
- I fixed a pre-existing `testdata/dev-*.toml` gap (missing `[blueprint]` overrides) that was
  silently breaking the *entire* shared Playwright e2e suite on any host without a writable
  `/etc/vnprox` — this was not scoped to my own task, but blocked verifying it, and is a strict,
  low-risk, config-only improvement for every future task's e2e coverage too.
