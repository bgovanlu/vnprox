# T-207 · Editing UI: changeset drawer, entity editors, guest NICs — completion report

## What I built

The whole write-side UX, entirely in `web/` (no backend changes). Every
mutation flows through the T-201/T-202/T-205 changeset APIs — there is no
direct-write path anywhere in this task's code.

### Wire types + API client (`web/src/api/`)

- **`types.ts`** (extended, not replaced): the full changeset wire vocabulary
  mirroring `internal/change`'s Go types — `OpType` (all 39), typed `OpParams`
  per editable op family (`iface`/`bond`/`bridge`/`vlan`/`guest`), `Op`
  (tagged union, `target` a Ref **string**, `undefined` only for `sdn.apply`),
  `Finding`/`Severity`, `Changeset`/`ChangesetStatus`, `Plan`/`PlanStep`,
  `ApplyLog`/`StepLog`/`RollbackLog`, `ChangesetDiff`/`FileDiff`/`OpSummary`,
  and the `ChangesetStatusEvent` WS shape. No `any`, no casts.
- **`changesets.ts`** (new): the only module that constructs a `/changesets*`
  request — `list/get/create/update/discard/validate/diff/apply/confirm/
  rollback`, each with CSRF + JSON handling via the existing `apiFetch`.

### The drawer + review/apply flow (`web/src/changesets/`)

- **`ChangesetDrawer.tsx`** — the persistent bottom-right drawer (spec §1):
  accumulate, reorder (↑/↓), remove, park/resume named drafts, per-op live
  validation badges, one-click `fix`, Review/Discard. Deliberately a plain
  floating panel, **not** the modal Radix `Drawer` primitive, so it stays
  usable while the user keeps editing elsewhere. Mounted once in `AppShell`.
- **`drawerMachine.ts`** — the pure view/gating state machine
  (`computeDrawerView`, `isDraftEditable`, `canReview`, `canApply`);
  never invents a client-side status, only maps the server `Status`
  (+ the one client-only "review requested" flag) onto a view.
- **`store.ts`** — zustand `persist` store (active draft id, drawer open,
  review-requested, warnings-ack) → survives reload (AC3).
- **`useDrawerActions.ts`** — the single op-accumulation entry point
  (`addOps`/`replaceOps`/`amendLastOps`) every editor/map-edit/bulk action
  funnels through, so the drawer, review screen and server ops array never
  disagree.
- **`ReviewApplyScreen.tsx`** — the three-tab review (spec §3): Summary op
  cards, File diff (real unified diffs from `GET /diff`), Plan (client
  preview mirroring `BuildPlan`, incl. an unsupported-op warning) →
  warnings-checkbox gate → Apply with a configurable 30–600s confirm window.
- **`CountdownBanner.tsx`** — the full-width commit-confirm countdown
  (spec §4) with Confirm / Roll-back-now, plus the terminal outcome banner
  (committed / rolled_back / failed). Everything renders from the
  `changeset` prop sourced fresh from `GET /changesets/{id}`; the drawer's
  `useChangesetWsBridge` subscribes to the `changesets` WS topic and
  invalidates that query on every `changeset.status` event → the countdown
  is WS-driven and reload-survivable (AC3).
- **`queries.ts`** — TanStack Query hooks + the WS bridge.
- **`opSummary.ts`** — pure human-readable op summaries (mirrors
  `internal/change/ifaces/summary.go`, extended to guest/sdn ops).
- **`opBuilders.ts`** — pure `Op` constructors (diff-against-initial for
  update ops; bridge port changes go through `bridge.port.add/remove`, never
  a `bridge.update` Ports field, per `params_bridge.go`).
- **`planPreview.ts`** — client mirror of `BuildPlan` for the pre-apply
  Plan tab (server has no plan until apply time).
- **`findingFields.ts`** — maps each stable finding `code` to the editor
  field that originated it (AC2: errors render on the drawer line **and**
  the form field) + `applyFixToOps` (the one-click `fix` patch, matched on
  the wire-documented (type,target) pair).
- **`FixButton.tsx`** — the one-click fix, shared by the drawer line and
  the review error list.
- **`capabilities.ts`** — per-node capability resolution from `GET
  /auth/me`'s `caps` map + missing-privilege tooltip text (AC4).

### Editors (`web/src/changesets/editors/`) — spec §5/§6

- **`BridgeEditor`** (Linux/OVS, ports multi-select with conflict hints,
  VLAN-aware toggle + VID-range editor, addresses/MTU/STP/comment),
  **`BridgeDeleteDialog`** (delete-with-reattach: generates the guest ops
  in the same changeset), **`BondEditor`** (mode selector with live "use
  this when…" guidance, slave picker showing link state/speed + conflict
  hints, LACP rate/hash-policy/miimon), **`VlanEditor`** (parent/VID/
  addresses/MTU with a "exceeds parent MTU" warning), **`InterfaceEditor`**
  (MTU/addresses/gateway/autostart/comment + the documented "renaming is
  out of scope, here's the manual procedure" note).
- **`EditorDialog`** — shared chrome incl. per-field + general error
  rendering and the capability-gated, tooltip-explained submit button.
- **`useEditorSubmit`** — drafts the op(s), then (T-202 validates on every
  draft change) splits the returned findings into per-field / general and
  keeps the dialog open on error, amending in place on re-submit.
- **`EditorLauncher` + `editorLauncherStore`** — one launcher (mounted in
  TopologyPage) opens whichever editor the map/inspector requests, wired
  with topology-derived candidate lists (`entityCandidates.ts`).

### Map integration (`web/src/topology/`)

- **`InspectorPanel.tsx`** (additive edit): capability-gated **Edit** /
  **Delete** buttons per entity kind (bridges route to the reattach
  dialog; bonds/VLANs draft a delete op after confirm).
- **`NewEntityMenu.tsx`** (new): the topology-toolbar "New ▾" create menu
  (bridge/bond/VLAN per writable node) — the "Node → … → New" entry point.
- **`TopologyPage.tsx`** (additive): `handleNodeDragStop` translates a map
  drag onto a target into a drafted op (`dragDropOps.ts`) with snap-back on
  an error-severity finding; mounts `EditorLauncher`; adds the New menu.

### Guests (`web/src/guests/`) — spec §6

- **`GuestsPage`** — cluster-wide guest-NIC list with node/bridge/VLAN
  filters, per-row disconnect/connect, and **bulk mode**: select N → reattach
  all to any bridge/VNet in the cluster (one changeset, one op per guest).
- **`guestNics.ts`** (pure list derivation from topology + expanded pills),
  **`queries.ts`** (composes the list from the existing `/topology` cache +
  guest-group expansion; no new backend route).

### Shared/nav (minimal additive edits, for T-206 merge-friendliness)

- `components/Tooltip.tsx` (new, self-contained provider), `main.tsx`
  (unchanged — Tooltip needs no app-level provider), `App.tsx` +
  `NavRail.tsx` (one `/guests` route + nav entry), `AppShell.tsx` (mounts
  the drawer).

  orchestration note. Added a per-run fresh
  SQLite DB in `playwright.config.ts` so accumulated drafts don't skew the
  drawer's resume list.
- **Pre-existing `topology.spec.ts` screenshot flake, NOT introduced here:**
  that T-107 screenshot compares the `.react-flow` canvas, whose height
  shrinks when a staleness banner appears. On this dev box `lldpctl` is
  absent, so the lldp source goes stale ~90s after daemon start (a caveat
  documented in that spec's own header). Because `changesets.spec.ts` sorts
  before `topology.spec.ts` and takes ~2 min, it can push the topology test
  past that 90s threshold, at which point the banner shrinks the canvas and
  the pixel diff exceeds tolerance. It passes when run first / on a box with
  `lldpctl`. Unrelated to T-207 logic; flagged for the integrator (options:
  run topology first, or install `lldpctl` in CI).

## Deviations / decisions (with reasons)

- **Drag gesture + successful-apply-confirm are unit-covered, not e2e** —
  see AC1. Both are headless-driver / no-real-hardware limitations, not
  logic gaps; documented in the spec header and flagged here as needing
  hardware validation for the real apply path.
- **`NewEntityMenu` added to the topology toolbar** can shift the committed
  `topology.spec.ts` screenshot baseline (canvas height) — the baseline is
  documented as machine-dependent; regenerate with `npm run e2e:update` on
  the reference box if needed. This is the
  only touch to a T-107-owned test artifact.
- **Bulk-reattach targets** were initially derived from currently-attached
  bridges only (which, on `three-node-vlan`, is just `vmbr0` for both
  guests — nothing to move *to*). Fixed to offer every bridge/VNet in the
  cluster, which is the actual feature ("Move VMs to another bridge").
- **`Drawer` primitive** gained a `bottom-right` side variant (additive);
  otherwise no shared-component behavior changed.
- **No new dependencies.** `@radix-ui/react-tooltip` was already in
  `package.json`.
