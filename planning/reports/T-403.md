# T-403 · Zone wizards

## 1. What was built

The five guided zone wizards from docs/features/sdn.md §2, with a wizard
framework built to reuse the real topology map components for a live
preview, per the task card.

**Wizard framework** (`web/src/sdn/wizards/`)

- `WizardShell.tsx`: the step engine every wizard is built on — a progress
  trail, a form pane on the left, the live preview pane on the right,
  Back/Next/Cancel/Create-draft navigation. Wizard state (every field)
  lives entirely in the wizard component's own React state; the changeset
  drawer is touched exactly once, from the last step's `onFinish` — there
  is no intermediate "stage as you go" behavior the way `useEditorSubmit`'s
  plain-editor pattern has. This is what makes acceptance criterion 5 hold
  structurally rather than by convention: abandoning a wizard at any step
  (Cancel, or just closing the dialog) unmounts local state with nothing
  ever having reached the server.
- `WizardPreviewPane.tsx`: renders the would-be topology through the real
  map components — `TopologyCanvas` + `toFlowElements` + `computeLayout`
  from `web/src/topology/`, the exact same functions `TopologyPage.tsx`
  itself uses — on synthetic entities from `previewEntities.ts`. Never a
  separate mini-renderer (unlike `web/src/blueprints/BlueprintPreviewDiagram.tsx`,
  a pre-existing simplified box-and-line diagram for the unrelated
  Blueprints feature — deliberately not the pattern followed here, since
  the task brief was explicit that the wizard preview must reuse the real
  components). Debounced via a new `useDebouncedValue` hook (80ms) so a
  rapid burst of field edits settles to exactly one layout recomputation
  (acceptance criterion 4).
- `previewEntities.ts`: pure, framework-free builders (`buildSimplePreview`,
  `buildVlanPreview`, `buildQinqPreview`, `buildVxlanPreview`,
  `buildEvpnPreview`) producing synthetic `TopologyNode[]`/`TopologyEdge[]`
  — a zone node, a vnet node, an optional subnet node, one bridge node per
  member node (existing/"ok" for VLAN/QinQ since the bridge is real;
  "planned" for Simple/VXLAN/EVPN since PVE creates it), plus per-type
  extras: QinQ's double-tag illustration (two chained synthetic "vlan"
  nodes wrapping the vnet), VXLAN's full-mesh VTEP nodes (mirroring
  `internal/inventory/link.go`'s real `EdgeVtepPeer` construction), and
  EVPN's BGP session graph (a controller hub node with one edge per peer
  address).
- `wizardOps.ts`: pure builders (`buildSimpleZoneOps` etc.) turning each
  wizard's finished params into the final `Op[]` — every op goes through
  T-402's own `opBuilders.ts` functions (`buildSdnZoneCreateOp` etc.),
  never a hand-built `Op` literal, per the task card's "uses T-402's sdn.*
  ops" requirement.
- `strings.ts`: every explanatory string across all five wizards, in one
  file, for copy review — written for a non-networking-expert per the
  spec's own bar (defines VLAN/VTEP/BGP/QinQ jargon in plain language the
  first time it's used, never assumes prior knowledge).
- `NodeCheckboxList.tsx`: shared "which cluster nodes" multi-select
  (`useClusterNodes.ts` derives the list from the already-cached
  `GET /topology` response, mirroring `TopologyPage.tsx`'s own
  `NewEntityMenu` node-list derivation).
- `useWizardCapability.ts`: gates the final "Create draft" step on
  `sdnWrite`, mirroring `SdnZoneEditor.tsx`'s own capability check exactly.
- `ZoneWizardPicker.tsx`: the entry point — a card grid picking one of the
  five wizards; wired into `SdnPage.tsx` as a new "+ New zone (guided)"
  button alongside the existing T-402 "+ New zone (advanced)" plain-form
  button (renamed from "+ New zone" so the two are distinguishable).

**Per-wizard behaviors**

1. **Simple/SNAT** (`SimpleZoneWizard.tsx`): name, member nodes, optional
   bridge name (blank = PVE auto-names it — `internal/change`'s own
   `zoneBridgeExistenceFindings` already treats an empty zone bridge as
   valid for `simple` zones), vnet, optional subnet with an SNAT toggle.
2. **VLAN** (`VlanZoneWizard.tsx`): existing VLAN-aware bridge + VID, with
   the LLDP trunk cross-check (acceptance criterion 2) — see below.
3. **QinQ** (`QinqZoneWizard.tsx`): service (outer) + customer (inner) VLAN
   tags with a double-tag illustration in both the copy and the live
   preview graph. Flagged limitation, see §3.
4. **VXLAN** (`VxlanZoneWizard.tsx`): peer addresses auto-suggested per
   member node (`useSuggestedPeers.ts`, seeded from each node's own bridge
   address — never overwrites a user's own edit), and the MTU derivation
   shown explicitly with a one-click "set to the safe value" fix
   (acceptance criterion 3) reusing T-402's own math, not reimplemented —
   see below.
5. **EVPN** (`EvpnZoneWizard.tsx`): controller reference, exit nodes (first
   = primary, a UI-only convention — no `primaryExit` wire field exists),
   and a BGP session graph preview for a scripted 3-peer input (acceptance
   criterion 3) — see below. Flagged limitation, see §3.

**LLDP trunk cross-check (VLAN wizard, acceptance criterion 2)**

- `lldpTrunkCheck.ts`: pure graph traversal (`bridgePhysNicRefs` —
  resolves a bridge's physical NICs, seeing through one level of bonding
  via `enslaved-by` edges; `lldpNeighborRefsForPhysNics` — via
  `lldp-adjacent` edges) plus the check itself (`checkVlanTrunk`: which
  neighbors' `taggedVlans` list doesn't include the chosen VID).
- `useLldpTrunkCheck.ts`: wires the already-cached `GET /topology` response
  plus one `GET /inventory/{ref}` fetch per candidate LLDP neighbor (a
  handful, not cluster-wide) — topology responses don't carry a neighbor's
  VLAN membership as a badge (`web/src/topology/projection.ts`'s own
  documented gap), so the cross-check reads it from `EntityDetail.fields`
  instead.
- **Backend gap closed**: `internal/pvemock`'s fixture LLDP shape and
  `internal/host/lldp.go`'s flat parser had no way to declare a switch
  port's *trunked* VLANs at all (only the single native/PVID `vlan`
  field) — real `lldpctl` reports both independently
  (`internal/host/lldp.go`'s `flexVlans`, already used by the "nested"
  schema), only the flat fixture schema was missing it. Added
  `tagged_vlans` to `pvemock.LLDPNeighbor` and `flatNeighborJSON`, and
  seeded `testdata/clusters/three-node-vlan.yaml` with a deliberate
  scenario: pve1/pve2 trunk VIDs 100/200/300, pve3 is missing 300 — the
  same scenario mirrored in the frontend test fixtures
  (`wizardTestUtils.tsx`).

**VXLAN MTU math (acceptance criterion 3)**

`vxlanMath.ts`'s `computeVxlanMtuDerivation` mirrors
`internal/change/validate_sdn.go`'s `underlayMTU`/`vxlanOverhead` constants
and `validate_advisory.go`'s `checkVxlanMTU` warning condition exactly
(1500 − 50 = 1450, the identical figure T-402's own acceptance criterion 3
names) — TypeScript can't import Go constants, so this is a doc-comment-
cross-referenced mirror, not a shared module; if either Go constant ever
changes, this file needs the matching edit (flagged in its own comment).
The wizard shows the arithmetic literally (`"1500 (underlying network
MTU) − 50 (VXLAN's wrapper overhead) = 1450 — the largest safe MTU for
this network."`) and a one-click fix button that sets the MTU field to the
derived safe value.

**EVPN BGP session graph (acceptance criterion 3)**

`previewEntities.buildEvpnPreview` renders a controller hub node connected
via `bgp-session` edges to one node per peer address; for a 3-peer input
this is exactly 3 nodes + 3 edges, asserted in
`previewEntities.test.ts` and end-to-end in `EvpnZoneWizard.test.tsx`.

**Two real bugs found and fixed** while wiring the VXLAN/EVPN wizards
(both directly blocked those wizards from working correctly, not
speculative cleanup):

1. `internal/change`'s `SdnZoneCreateParams`/`SdnZoneUpdateParams` never
   exposed `ExitNodes`/`Peers` — the read model
   (`internal/inventory.SdnZone`, `GET /sdn`) and the PVE wire type
   (`internal/pve.SDNZone`) have carried both since T-401, and
   `internal/pvemock`'s `SDNZoneSpec` already accepted them on write, but
   nothing above the PVE-client layer could actually *set* them via a
   changeset op. Threaded through `params_sdn.go` → `validate_referential.go`
   (exit nodes checked against known cluster nodes, like `nodes`; peers —
   underlay IPs, not node names — intentionally unchecked) →
   `apply_seams.go`'s `SDNZoneConfig` → `apply_sdn.go`'s restore-op
   diffing → `cmd/vnproxd/changeagent.go`'s gateway (both the production
   `pveGateway` and the test-only `fakePVEGateway`, which a new
   apply-level round-trip test, `TestApply_SDNZone_ExitNodesAndPeers_RoundTrip`,
   caught missing the fields too). Documented in `docs/api.md` and
   `docs/data-model.md` per docs/development.md's definition-of-done #4.
2. `web/src/changesets/opBuilders.ts`'s `buildSdnZoneCreateOp` silently
   dropped `controller` on create — the field is present in
   `SdnZoneFormValues` and `SdnZoneEditor.tsx`'s own Controller field
   (shown for `type === "evpn"`) writes into it, but the create-op builder
   never read it. An EVPN zone drafted through either the plain T-402
   editor or this task's wizard was being created with **no controller
   reference at all**, which real PVE requires for an EVPN zone to
   function. One-line fix plus a new regression test
   (`opBuilders.test.ts`'s `"sdn.zone.create carries controller when
   present"`).

**One accessibility bug found and fixed**: `NodeCheckboxList` was
originally nested inside `EditorDialog.tsx`'s `<Field>` (a `<label>`
wrapper) — nesting a `<label>` inside another `<label>` is invalid HTML,
and in practice broke every checkbox's computed accessible name (the outer
label's implicit "first labelable descendant" association collided with
each checkbox's own inner label), making every "which nodes" checkbox
unnamed to both assistive tech and `getByRole(..., {name})` queries.
`NodeCheckboxList` now owns its own `<fieldset>`/`<legend>` — the correct
semantic grouping for a checkbox set regardless, not just a test
workaround.

**`web/src/components/Dialog.tsx`** gains an optional `widthClassName`
prop (default `"max-w-lg"`, every existing call site unchanged) so the
wizard's two-pane form+preview layout can use a wider dialog
(`max-w-6xl`) without relying on Tailwind's same-specificity class-order
precedence (concatenating a second `max-w-*` into `className` is not
guaranteed to win — a known Tailwind footgun `tailwind-merge` exists to
solve, which isn't in this project's approved dependency list; a small,
additive prop is the minimal-footprint fix).

### Debounce verification note (acceptance criterion 4)

No browser profiler is available in this environment (same caveat prior
tasks' reports flag). Verified two ways instead: (1) the debounce
implementation itself — a single `setTimeout`/`clearTimeout` per value
change, 80ms, well under the 100ms budget with headroom for the actual
layout pass; (2) two timing-aware tests using `vi.useFakeTimers()` —
`useDebouncedValue.test.ts` proves the primitive settles exactly once,
80ms after the last of a rapid burst of changes, and
`WizardPreviewPane.test.tsx` proves the *component* (with a mocked
`computeLayout`) only ever calls the real layout function once per settled
burst, on the final graph, not on every intermediate change. This is a
deterministic, code-level proof of the debounce behavior rather than a
measured frame time; a manual browser check (React DevTools Profiler) is
the natural follow-up if a live environment becomes available.

## 3. Deviations from the task card (with reasons)

1. **QinQ zone wizard sends no zone-level service-VLAN tag as an op
   param.** Real PVE's QinQ zone type has a zone-level `tag`
   (service/outer VLAN) distinct from each VNet's own `tag` (customer/
   inner VLAN), but `internal/change.SdnZoneCreateParams` has never had a
   zone-level `tag` field for this — T-401's report already flagged this
   exact gap ("QinQ's inner/outer VLAN range... not added — out of
   scope") and T-402's independently ("QinQ zones are not bridge-checked
   ... no QinQ-specific bridge semantics to distinguish"). Adding a
   zone-level tag field would have meant threading a new field through
   the same ~12 files the `exitNodes`/`peers` fix touched (params, wire
   types, pvemock, validators, apply/restore, changeagent gateway, docs) —
   a second parallel field-threading change beyond what a "zone wizards"
   card's scope reasonably covers, especially with real PVE's exact QinQ
   wire semantics unverified in this environment either way. The wizard
   still collects a "service (outer) tag" field and uses it for the
   double-tag illustration (both in the copy and the live preview graph,
   per the spec's explicit "double-tag illustration" requirement) — it's
   just not sent as an op param. The review step tells the user this
   explicitly ("Service tag is shown for illustration only — set it
   directly in Proxmox's own SDN zone settings"). Flagged as a follow-up
   in `QinqZoneWizard.tsx`'s own doc comment: adding
   `SdnZoneCreateParams.ServiceVLAN` (mirroring `VrfVxlan`'s existing
   pattern exactly) is a small, well-scoped next step if a future task
   wants it.
2. **EVPN zone wizard has no way to *create* a controller** — only to
   reference an existing one by ID, exactly like `SdnZoneEditor.tsx`'s own
   pre-existing Controller field. `internal/blueprint`'s T-603 report
   explicitly flags this as a real, precisely-scoped gap and calls it "T-403's
   territory" ("add an `sdn.controller.create/update/delete` op family...
   this is squarely T-403's territory"). I read that report before
   starting and made a deliberate scope call: implementing full controller
   CRUD is its own substantial feature (a new inventory entity kind with
   no existing read-model support at all — no PVE-client list/get, no
   `internal/inventory.SdnController` entity, no collector polling, no
   pvemock mock endpoints, no apply-engine op family — essentially a
   second T-401+T-402-sized pair of tasks for one new entity type), out of
   proportion for a "zone wizards" card whose actual deliverable is the
   wizard framework + live preview + the five per-type flows. The EVPN
   wizard still fully satisfies its stated acceptance bar: it collects
   ASN/peers (preview-only) and exit nodes and renders the correct 3-peer
   BGP session graph before creation (acceptance criterion 3), and the
   zone it drafts correctly references an existing controller by ID via
   the now-fixed `controller` param (see the bug fix in §1). Flagged
   explicitly (not silently dropped) in `EvpnZoneWizard.tsx`'s doc
   comment, with the exact follow-up T-603's report already scoped.
3. **The `exitNodes`/`peers` write-path fix and the `controller`-drop fix
   are both "smallest reasonable extension" calls under CLAUDE.md's
   "if docs/api.md or docs/data-model.md don't fully specify something you
   need" allowance** — both are real, pre-existing gaps in already-merged
   T-401/T-402 code that this task's wizards genuinely needed working to
   satisfy their own acceptance criteria (a VXLAN/EVPN zone wizard that
   can't actually set peers/exit nodes, or an EVPN zone that's silently
   created with no controller, isn't a working wizard). Both are backed by
   new regression tests and documented in `docs/api.md`/`docs/data-model.md`
   per docs/development.md's definition-of-done #4.
4. **`fireEvent.change` used instead of `userEvent.type` for a handful of
   number (`<input type="number">`) fields in the component tests**
   (QinQ's "Service" tag field, VXLAN's VNI/MTU fields, EVPN's ASN field).
   Isolated and confirmed this is a jsdom/`@testing-library/user-event`
   environment quirk, not a real product bug: an otherwise byte-identical
   number field (VLAN wizard's own VID input) types correctly via
   `userEvent.type` in the same test harness, and the affected fields'
   `onChange` logic is proven correct directly via `fireEvent.change` (the
   value updates, state updates, the op carries it). Did not chase this
   further given the size of the rest of the task; noting it here in case
   a future test-infra task wants to dig into why `userEvent.type`
   intermittently drops keystrokes on some but not all real number inputs
   in this project's jsdom setup.
5. **No new backend route for "cluster node IPs"** (VXLAN's peer
   auto-suggest). docs/architecture.md's peer discovery is PVE-API-only,
   not frontend-exposed, and no dedicated "cluster node IP" endpoint
   exists anywhere in this codebase. The smallest reasonable read
   consistent with existing patterns: each member node's own bridge/VLAN
   interface address, already fetchable via the existing
   `GET /inventory/{ref}` route (`useSuggestedPeers.ts`) — no new backend
   surface at all. Reasonable for a homelab/small-cluster default; a
   future task adding a real "node underlay address" concept (e.g. for
   corosync link config) could give this a more authoritative source.
6. **Needs hardware validation**: same caveat every SDN-area task's report
   before this one has flagged — the LLDP `tagged_vlans` fixture plumbing
   and the wizard's own trunk-check reasoning are my own reconstruction of
   real switch/LLDP behavior, not verified against a live cluster/switch.
   `internal/host/frr.go`'s and `internal/pve`'s own existing "needs
   hardware validation" notes (T-402/T-404 reports) still apply unchanged
   to the `exitNodes`/`peers`/`controller` wire fields this task's fix
   exercises for the first time.

## 4. Acceptance criteria — status

1. **Golden ops per wizard, scripted input, against pvemock-shaped ops —
   met, all five.** Each wizard has one full end-to-end component test
   (render → step through the real UI → assert the exact `POST
   /changesets` body) plus its own pure-function coverage in
   `previewEntities.test.ts`/`wizardOps` call sites. "Against pvemock":
   the op family itself (`sdn.zone/vnet/subnet.create` + `sdn.apply`) is
   already proven against a real pvemock server end-to-end by T-402's own
   `apply_sdn_test.go` suite (unchanged here, still green) — this task's
   own new backend test (`TestApply_SDNZone_ExitNodesAndPeers_RoundTrip`)
   extends that same real-pvemock proof to the new `exitNodes`/`peers`
   fields the wizards rely on.
2. **VLAN wizard + LLDP fixture, VID missing on a switch port → inline
   warning naming the port — met.** `VlanZoneWizard.test.tsx`'s dedicated
   AC2 test; the underlying fixture data mirrors a real scenario seeded
   into `testdata/clusters/three-node-vlan.yaml` for the backend too.
3. **VXLAN MTU 1450 derivation shown visibly; EVPN session graph correct
   for 3 peers — met, both.** `VxlanZoneWizard.test.tsx` asserts the exact
   math string; `previewEntities.test.ts` and `EvpnZoneWizard.test.tsx`
   both assert the 3-node/3-edge session graph shape.
4. **Preview pane updates live, debounced, <100ms perceived — met, with
   the documented no-browser-profiler caveat.** See §2's dedicated note;
   two timing-aware fake-timer test suites (hook-level and
   component-level) plus code inspection.
5. **Abandoning a wizard leaves no draft residue — met, tested
   explicitly.** `SimpleZoneWizard.test.tsx`'s Cancel-mid-wizard test
   asserts zero `POST /changesets` calls; this holds structurally for
   every wizard (not just the one under test) since all five share the
   same `WizardShell`/local-state/finish-only-drafts architecture.
