## 2. What was tested and how

Everything is exercised against the `internal/pvemock` server (real
`httptest.Server` + `pve.Client`) with the `single-node` and `three-node-vlan`
fixtures. A fake `NodeAgent` models the committed/staged interfaces file
in-memory; its **reload goes through the real user-ticket PVE task path**, so
the mock's documented per-node network-reload failure flag is exercised for
real. A controllable `TimerFunc` fires the commit-confirm deadline
deterministically; a second suite uses the real `time.AfterFunc`.

**All six acceptance criteria were independently verified (not just claimed):**

1. **End-to-end (single-node)** — `TestApply_EndToEnd_SingleNode`:
   draft→validate→diff→apply→confirm→committed; asserts the WS status stream is
   exactly `[draft, validated, applying, awaiting_confirm, committed]`, the plan
   is `stage→reload`, every step logs `ok`, **the fixture file verifiably now
   contains the new bridge**, and pre+post snapshots exist.
2. **No-confirm auto-rollback + restart survival** —
   `TestApply_NoConfirm_AutoRollback` (deadline elapses → state restored
   **byte-identically** to the pre-snapshot, status `rolled_back`, attributed
   `system:rollback`, audit trail complete);
   `TestApply_TimerSurvivesRestart_DBReArm` (a **brand-new `Service` over the
   same DB with zero in-memory timer state** re-arms purely from the persisted
   `confirm_deadline` and rolls back on fire); and
   `TestApply_TimerSurvivesRestart_RealTimer` (a restarted `Service` using the
   **real `time.AfterFunc`** with a past deadline rolls back on its own
   goroutine, no test seam firing it). `ArmPendingRollbacks` also recovers a
   crash-interrupted `applying` changeset.
3. **Injected step failure at each position of a 5-step plan** —
   `TestApply_StepFailure_AtEachPosition` (three-node fixture, plan
   `[stage n1, reload n1, stage n2, reload n2, sdn.apply]`). For every position
   0–4 it asserts: completed steps rolled back, changeset `failed`, apply log
   pinpoints the exact failed step (before=ok, at=failed, after=skipped), the
   apply lock released, and the **property: both nodes' committed files ==
   their pre-apply content, byte-for-byte, for every position.**
4. **Lock contention** — `TestApply_LockContention`: a second apply while one is
   `awaiting_confirm` returns `*ErrChangesetLocked` (→ 409 `changeset_locked`);
   after confirm, the second apply succeeds.
5. **Committed rollback → restoring draft** —
   `TestRollback_CommittedCreatesRestoringDraft`: a committed `bridge.create`
   rolled back produces a **new** draft whose op is `bridge.delete vmbr3` and
   whose rendered diff **removes** the bridge (the exact inverse), leaving the
   committed changeset untouched.
6. **Coverage / race / honesty contract** — `internal/change` 90.3% (`go test
   -cover`), race-clean (`go test -race`), this report's §4.

Additional coverage: manual rollback of an in-window change (attributed to the
user, not `system:rollback`); rollback-incomplete → `failed`; unsupported-op
rejection at plan time; validation-blocked apply; not-found / illegal-transition
paths; sdn.apply-only plan (cluster-scope step + empty-scope refresh);
`hostNodeAgent` file logic (stage/reload-commit, reload-failure-restore,
discard) against a temp dir with a fake `ifreload`; and the API error mapping.

## 3. Deviations from the task card (with reasons)

1. **Reload / rollback are host-level (root) operations, not user-ticketed PVE
   calls.** Architecture §4 describes node-network apply as `PUT
   /nodes/{node}/network`, but the commit-confirm **auto-rollback timer fires
   with no live user session** and must still restore files and reload. The
   daemon runs as root and the peer API (`/api/peer/host/ifreload`,
   `/api/peer/host/restore`) is designed for exactly this. So the `NodeAgent`
   seam (stage/reload/discard) is host-level; **cluster-scope writes (sdn.apply)
   still use the user's own ticket** via `PVEGateway`, preserving D3's "PVE ACLs
   enforced by PVE." The API gates the apply route on `netWrite` (Sys.Modify),
   consistent with architecture §6's "host-level operations … gated on the
   session holding the equivalent PVE privilege."
2. **Added `awaiting_confirm → failed` to the status machine** (T-201's
   `changeset.go`, a one-line table edit + doc note + updated exhaustive test).
   T-201's own `StatusFailed`/`StatusRolledBack` doc comments explicitly reserve
   `failed` for the "couldn't even fully roll back" case and say "T-205 defines
   … vs. `StatusRolledBack`." Without this edge, a rollback that can't restore a
   node was silently stuck in `awaiting_confirm`. This is the documented intent,
   not a new decision.
3. **Executable op scope is node-file ops + `sdn.apply`.** `guest.nic.update`,
   `sdn.zone/vnet/subnet.*`, `fw.*`, `ipam.*` validate and draft fine but the
   planner rejects them at apply time with `*ErrUnsupportedOp` (→ 422) rather
   than approximating an execution. Reason: those families need `pve.Client`
   write+task methods that are not in T-101's delivered surface, and "nothing
   here may be approximated." The plan/executor/snapshot/confirm/rollback/lock
   machinery is fully general; adding a family is adding a client method + a
   `Step` kind. **This is the single biggest scope boundary — see §4.**
4. **Rollback of a *committed* changeset synthesizes inverses only for the
   exactly-invertible ops** (create↔delete, `bridge.port` add↔remove). Delete
   and update ops return `*ErrInverseUnsupported`: their faithful inverse needs
   the stored pre-snapshot **content**, which is T-206's snapshot→draft restore
   path. In-window (`awaiting_confirm`) rollback and the auto-rollback timer are
   unaffected — they restore from the pre-snapshot file directly and work for
   every op the engine can apply.
5. **Snapshot storage is inline plaintext content** (`{node,path,sha256,
   content}` in `files_json`), not the `content_zstd` the data-model comment
   names. T-206 owns the zstd-compressed, hash-deduplicated blob storage; T-205
   stores enough to restore byte-identically today. Flagged so T-206 knows to
   migrate the shape.

No new third-party dependencies were added.

## 4. Residual risk / honesty contract (READ BEFORE DEPENDENT WORK)

What the pvemock-backed suite **does** prove, and what it **cannot**:

**Proven against the mock (high confidence):**
- The full lifecycle, ordering, and per-step logging of the plan.
- Commit-confirm timing, DB-persisted deadline, and re-arm across a simulated
  restart — including with the **real** `time.AfterFunc`, and interrupted-apply
  recovery.
- Rollback correctness as a **property** (post-rollback file state == pre-apply
  file state, byte-for-byte, at every failure position of a 5-step plan).
- The single-applier lock (409) and every terminal-state transition + audit.
- Concurrency safety: `-race` clean, with confirm / manual-rollback /
  auto-rollback-timer all serialized by one mutex.

**NOT proven — needs hardware validation or a later task:**

1. **The production `hostNodeAgent` never touched a real ifupdown2.** Its
   file-manipulation logic (stage, backup, move-into-place, restore-on-failure,
   discard) is unit-tested against a temp dir with a **fake** `ifreload`; the
   real `ifreload -a` exec, the real `/etc/network/interfaces{,.new}` semantics,
   and — critically — whether a failed `ifreload` truly leaves the box
   reachable so the restore-and-re-reload can run, are **unverified**. This is
   the primary hardware-validation item.
2. **Failure-injection mechanism, per step, was not uniform.** pvemock's
   documented failure flag natively covers **reload** (per-node
   `NetworkReloadFail`) and **sdn.apply** (`mock_fail`); the typed client can't
   pass a per-request `mock_fail` for sdn.apply without corrupting the reload
   steps, and the mock has no host-write failure flag. So in the 5-step test:
   reload steps fail via the **native mock flag**, and stage / sdn.apply steps
   fail via **seam faults** (`NodeAgent`/`PVEGateway` test doubles). The
   rollback-correctness property is asserted at all five positions regardless;
   only the *trigger* differs. Real ifupdown2 partial-apply failure modes are
   not modeled.
3. **Multi-node is coordinated from one daemon only.** The planner structures
   per-node steps and the executor drives multiple nodes' reloads (the 5-step
   test uses two nodes), but every reload here runs against the mock from the
   coordinating daemon. **Per-node local timers, peer-API staging/reload/
   restore of a *remote* node's file, and peer advisory locking are T-304.**
   The production `hostNodeAgent` operates on **local paths only** and will
   mis-handle a peer-node file step — do not route peer-node file steps to it
   until T-304 lands.
4. **SDN-apply rollback is not implemented.** `sdn.apply` is always the last
   plan step, so a *mid-apply* failure never needs to undo a succeeded
   `sdn.apply`; but **auto/manual rollback of a committed changeset that
   included `sdn.apply` does not revert the SDN state** (it restores node files
   only). Reverting applied SDN needs the pre-apply SDN config captured as a
   snapshot and re-applied — dependent on T-206's broader snapshot scope.
5. **Guest / SDN-write / firewall / IPAM ops are not executable** (§3.3) — any
   changeset containing them is refused at apply with 422 `unsupported_op`.
6. **Validation of the pre-apply revalidation's `allow_dangerous_ops` /
   protected-set path** is unit-covered, but the T-203 note (c) data-model gap
   (PhysNic/Bond have no `Addresses`, so protected-interface connectivity
   checks are meaningful only for Bridge/VlanIface) still applies — the apply
   engine inherits it and does not fix it.
7. **Narrow write-then-reload window in `hostNodeAgent.ReloadInterfaces`**
   (flagged by orchestrator review, not originally listed here): the staged
   content is written to the live `interfacesPath` *before* `ifreload -a` is
   invoked. A hard kill (SIGKILL, power loss) between that write and the
   reload call leaves the on-disk file showing the new (possibly bad) config
   while the running kernel/network state is still the old one, until the
   daemon restarts. `ArmPendingRollbacks` self-heals this on restart (it
   unconditionally restores every affected node from the pre-snapshot
   regardless of how far execution got), so this is self-healing *if the
   daemon comes back* — but not if the box stays down indefinitely (e.g.
   hardware failure). Worth a one-line mention in T-206/T-304 planning; not a
   blocking defect.

**Orchestrator review fix applied post-report:** `apply_restore.go`'s
`inverseOp` originally discarded the type-assertion `ok` for
`BridgePortAdd`/`BridgePortRemove` params (`p, _ := op.Params.(*...)`),
silently synthesizing `Port: ""` on a type mismatch instead of erroring.
Changed to check `ok` and return an error — theoretically unreachable given
T-201's strict-decode pipeline, but cheap to harden and flagged by
independent review as a swallowed-error smell. Verified `make check` still
green after the change.
