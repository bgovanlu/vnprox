## What I built

### 1. `planning/validation/harness/lib/common.sh` — the shared contract

Every section script sources this. It provides:

- **Dual-mode PVE API access** (`api_get <path>`): prefers `pvesh` (present on every stock PVE
  install, root-trusted local socket, no credential management needed) and falls back to
  ticket-based HTTP against `PVE_API_BASE_URL` only when `pvesh` is absent — which is exactly the
  case in dev/CI against `internal/pvemock` (a plain HTTP server with no `pvesh` binary). This one
  mechanism is what makes AC1 possible: the *same* script that needs "nothing on the target but a
  stock PVE install" is also the script `go test` runs against a mock server with zero
  modification.
- **`redact()`**: a `sed`-based function scrubbing PVE tickets (`PVE:...`), API-token secrets
  (the part after `user@realm!id=`), WireGuard/PSK-shaped 32-byte base64 keys, and
  `Authorization:`/`Cookie:` header values — called from inside `harness_item` itself, so a raw
  field is redacted *before* it's ever assembled into a blob, not as an afterthought pass.
- **`harness_item`/`harness_emit`**: hand-rolled JSON assembly (no `jq` dependency — not
  guaranteed on a stock PVE install) that captures a command's exit code and stdout+stderr
  verbatim (post-redaction), and prints exactly one evidence-blob JSON object to stdout. The
  script never computes or embeds a verdict — every item's `verdict_inputs` is just `exit_code`
  plus whatever raw signal a caller chooses to expose in `raw`; deciding what a value *means*
  belongs entirely to `expected/<section>.md` + `internal/validation.Triage`.
- **`harness_require_mutation_flag`**: the enforcement side of `MUTATES=1` — exits 2 with a clear
  stderr message unless `--i-understand-this-mutates` was passed.

### 2. Eight harness scripts, grouped exactly as T-1802's card names them

`pve-api.sh`, `host.sh`, `change-engine.sh` (**MUTATES=1**), `firewall.sh`, `sdn.sh`, `ipam.sh`,
`wireguard.sh`, `capture.sh` — matching T-1802's own "PVE API behavior, host reader/writer, the
change engine's local paths, firewall, SDN, IPAM, WireGuard, and capture" grouping verbatim,
rather than the ~33 individual `##` headings in `needs-hardware-validation.md` (a literal
one-script-per-heading reading would be 33 scripts, not the "roughly eight human turns" the card
asks for). Each script's header comment names exactly which `needs-hardware-validation.md`
bullets it feeds, and each `harness_item`'s `checklist_ref` field quotes the specific bullet.

Coverage is deliberately a **representative starting set** (32 items total across the 8 scripts),
not an attempt at all 105 checklist items — T-1801's deliverable is the machinery and a working
demonstration of it, not the burndown itself (that's T-1802). The README documents how to add an
item or a whole new section, and `internal/validation`'s tests will catch a malformed addition
(missing companion `expected/*.md`, bad table syntax, an unbanner'd mutating verb).

`change-engine.sh` is the one script that mutates: it re-PUTs a **named, human-chosen, never
defaulted** interface's current MTU back to itself and reloads it — a real stage→PUT→ifreload→
confirm round trip through PVE's actual network-config API (not vnprox's own code), which is the
only way to genuinely observe PVE's staging semantics and the "PUT request encoding" checklist
item rather than assume them. `PVE_TARGET_IFACE` has no default specifically so a human can't run
it against their management path by accident. Verified end-to-end against pvemock's
`single-node.yaml` (below) — including a real UPID task reaching `stopped`/`OK`.

### 3. `internal/validation` — schema, triage, and the tests that prove both

- `schema.go`: `Blob`/`Item`/`NodeInfo`/`PVEVersion` structs, `ParseBlob` (two-pass: a generic
  `map[string]any` decode to catch a field that's structurally *absent* — not just empty — before
  a typed decode, since `encoding/json` alone can't distinguish those), `Blob.Validate()`
  (schema version, RFC3339 timestamp, non-empty required fields, no duplicate item IDs).
- `triage.go`: `ParseExpected` (parses the markdown table format below out of an
  `expected/<section>.md`), `Triage` (compares a blob against parsed rows, returns
  match/divergence/item-missing/field-missing per row — never mutates the blob, never invents an
  interpretation beyond the row's own `meaning` text).
- Expected-outcome table format (documented fully in the README): `| id | pointer | op | expected
  | meaning |`, `pointer` ∈ `{raw, exit_code, command, checklist_ref, verdict_inputs.<key>}`, `op`
  ∈ `{equals, contains, not_contains, regex}`. I added `not_contains` beyond what the card
  sketched — needed for real cases like "no `pending` marker survives a successful reload" that
  `equals`/`contains` alone can't express as a positive assertion.

## What I tested and how

All five acceptance criteria are asserted by `go test ./internal/validation/...` (part of
`make check`'s `go test ./...`), not just exercised manually:

- **AC1** (`TestHarness_ReadOnlySectionsProduceSchemaValidBlobs`,
  `TestHarness_ChangeEngineMutatingSectionProducesSchemaValidBlob`): spins up
  `internal/pvemock`'s `Server` via `httptest.NewServer` in-process, runs each real harness script
  as a subprocess against it (no `pvesh` in the test environment, so every script genuinely
  exercises the HTTP fallback path), and `ParseBlob`s the stdout. All 8 sections pass, including
  `change-engine.sh`'s full stage→PUT→reload→poll-to-`stopped`→confirm-clean cycle against
  `single-node.yaml`'s spare `eno2` NIC. A companion test
  (`TestHarness_ChangeEngineRefusesWithoutMutationFlag`) confirms it refuses and prints nothing to
  stdout without the flag.
- **AC2** (`TestTriage_FlagsDeliberateDivergence`): `internal/validation/testdata/fixture-blob.json`
  + `fixture-expected.md` — the fixture's row for item `b` deliberately claims
  `verdict_inputs.http_status` is `200` when the blob actually contains `403`. The test asserts
  that row comes back `StatusDivergence` (not silently `StatusMatch`), alongside a genuine match,
  a `raw contains` match, and an `item-missing` case for an id that doesn't exist in the blob.
- **AC3** (`TestNoHarnessScriptMutatesWithoutBanner`, `TestMutationBannerCheck_CatchesAViolation`
  in `internal/validation/mutation_test.go`): greps every `harness/*.sh` **entry point** (not
  `lib/common.sh` — a sourced-only library, never run directly per the runbook) for
  `\b(set|create|delete|ifreload|ifup|ifdown)\b` and requires a `^MUTATES=1` line in the same file
  if any match. This genuinely caught real false-positive-shaped prose during development — my own
  first drafts of `pve-api.sh`/`host.sh`/`sdn.sh` said things like "not set", "set
  PVE_BOND_IFACE", and "requires staging a create" in comments/echo strings, and the test flagged
  all three until I reworded them — which is itself a small piece of evidence the check has teeth,
  reinforced by the synthetic-violation test that proves a `pvesh set` call is caught whether or
  not a banner is present.
- **AC4** (`TestRedact_ScrubsEverySecretClass` in `redact_test.go`): a genuine whitebox test — it
  shells out to `common.sh`'s actual `redact()` function (not a Go reimplementation of the same
  logic, which could silently drift from what the harness really does), one table-driven case per
  secret class: PVE ticket, API-token secret (header form and bare form), WireGuard private key,
  WireGuard PSK, and a `Cookie:` header. A companion test confirms ordinary non-secret JSON output
  is left untouched (guards against over-redaction eating real evidence, not just under-redaction
  leaking secrets).
- **AC5**: `planning/validation/README.md` — written to be read cold (see "what T-1802 needs to
  know" below for a note on why I'm confident of this, not just asserting it).

Also added (not one of the five numbered criteria, but directly load-bearing for T-1802):
`TestRealExpectedFilesParse` confirms every real `expected/<section>.md` this card ships parses
without error and has a companion for every `harness/<section>.sh` — catching exactly the kind of
mistake I made and fixed above (a malformed table row) before it reaches T-1802.

Ran the full suite repeatedly during development
(`go -C <worktree> test ./internal/validation/... -v`) and the full `make check` twice (once to
catch `golangci-lint` field-alignment/shadow issues — fixed via `golangci-lint run --fix`, once
clean modulo the npm audit finding above). `go build ./...` and `go vet ./...` are clean.
`gofmt -l` on every new file is empty.

## Deviations from the card, with reasons

- **Coverage is 32 items across 8 sections, not all 105 checklist items.** The card's own AC1
  language ("harness itself is testable") and deliverable list (harness, schema, redaction,
  triage, runbook — not "every checklist item ported") point at machinery, not exhaustive
  coverage; T-1802's card is the one titled "burndown". Flagging this explicitly rather than
  letting it look like an oversight: if T-1802's author disagrees and wants full coverage staged
  here first, that's a legitimate call, but it wasn't what I read the card to be asking for.
- **`firewall.sh` has no single matching `needs-hardware-validation.md` heading to point at.**
  That doc has no dedicated "Firewall" section (its firewall-adjacent items live under the T-1805
  section, owned by that card, plus one k8s finding-precision item). I built a read-only baseline
  against `internal/pvemock/README.md`'s documented firewall API surface instead, and said so in
  the script's own header comment — flagging here so it doesn't read as a missed cross-reference.
- **Added a fourth triage op, `not_contains`**, beyond what the card sketched. Needed for
  "no pending marker after reload" and similar must-be-absent checks that `equals`/`contains`
  can't express without an awkward workaround. Small, additive, covered by tests.
- **`pve-api-05` (ticket expiry) has no expected-outcome row.** It's genuinely not a pass/fail
  signal on its own (it just timestamps ticket issuance) — the checklist item is about whether
  `TicketRenewAfter`'s margin beats a real ~2h ticket lifetime, which needs a human/triage
  judgment call against that timestamp, not an automatable comparison. Documented as such in
  `expected/pve-api.md`'s preamble rather than faked with a row that would produce a meaningless
  verdict.

## What T-1802's author needs to know without reading the code

- **Run `planning/validation/README.md` top to bottom before doing anything else** — it's written
  assuming zero chat context, on purpose (that's AC5). It covers: which scripts are safe to run
  freely vs. need `--i-understand-this-mutates` and why, exactly what to paste back, what an agent
  does with it, mutating-script recovery if something goes wrong, the evidence-blob schema, the
  expected-outcome table format, redaction's guarantees (best-effort, not absolute — flag anything
  that looks like a leaked secret but doesn't match a known pattern), and known limitations
  (`pvesh`'s exact JSON shape vs. the HTTP fallback's is itself unconfirmed against real hardware
  — expect to adjust some `contains`-op rows after the first real run).
- **Triage entry point**: `internal/validation.ParseBlob(raw)` → `internal/validation.Triage(blob,
  expected)` where `expected` comes from `internal/validation.ParseExpected(mdBytes)`. `Triage`
  returns one `Result` per expected row with a `Status` (`match`/`divergence`/`item-missing`/
  `field-missing`) — never silently drops a row, never guesses.
- **Ticking `needs-hardware-validation.md`**: I deliberately left it untouched — I have no
  hardware evidence to tick anything against, and the standing rule ("an agent may never tick a
  checklist item it did not receive evidence for") is exactly what this card exists to make
  operationally possible, not something T-1801 itself gets to spend.
- **The npm audit finding above is real and needs a decision** before `make check` is fully green
  in a fresh worktree — it's CI/`web/audit-allowlist.json` territory (T-1806), not something this
  card's scope covers or that I was authorized to fix by editing the allowlist.
- **Section scripts are individually extensible** — see the README's "adding a new item" section.
  `internal/validation`'s test suite (`go test ./internal/validation/...`) will catch a broken
  addition (bad table syntax, missing companion file, an un-bannered mutating verb) before it ever
  reaches a human running it against `pvecube`.
