# T-1501 — Kubernetes overlay mapping engine (read-only, CNI-aware)

## What I built

A new `internal/k8s` package: a **read-only forever** kubeconfig client + REST reader, CNI
detector, node↔guest correlator, pod/service overlay model, a `K8sResolver` mirroring
`internal/flow.GraphResolver`'s shape, and the `k8s_nodeport_exposed_without_fw_rule` finding —
plus the store table, API routes, and unified-findings-stream wiring that make it reachable end
to end.

### `internal/k8s` (the engine)

- **`kubeconfig.go`** — a minimal kubeconfig (v1) parser (`gopkg.in/yaml.v3`, already an approved
  dependency via T-1101 — no second YAML library) covering `clusters`/`users`/`contexts`/
  `current-context`, resolving to a `ResolvedConfig` (server URL, CA data, and either a bearer
  token or a client cert+key — read only from the base64-inlined `*-data` fields, never a
  filesystem-path variant). Unresolvable input fails closed (`ErrNoCurrentContext`/
  `ErrUnknownCluster`/`ErrUnknownUser`/`ErrNoServer`/`ErrNoCredential`), never guessed.
- **`client.go`** — `Client`, a `net/http`-only reader with exactly four exported methods —
  `Nodes`, `Pods`, `Services`, `KubeSystemDaemonSets` — each issuing exactly one
  `http.MethodGet` request against one of the card's four named paths (`/api/v1/nodes`,
  `/api/v1/pods`, `/api/v1/services`, `/apis/apps/v1/namespaces/kube-system/daemonsets`). Every
  request funnels through one unexported `getJSON` helper that hardcodes the method — there is no
  parameter, code path, or exported function anywhere in this package that can issue anything but
  a GET.
- **`cni.go`** — `DetectCNI`: Calico (`calico-node` kube-system DaemonSet) / Cilium (`cilium`
  kube-system DaemonSet) checked first (a DaemonSet name is a stronger signal than a node
  annotation a node-agent writes after the fact), then Flannel (`flannel.alpha.coreos.com/
  backend-type` node annotation); anything else is `CNIUnknown`.
- **`correlate.go`** — `CorrelateNodes`: a k8s node's `status.addresses` `InternalIP` matched
  against a caller-supplied `GuestIPIndex` (built by `internal/api/k8s.go` from the identical
  IPAM-allocation-based lookup this codebase's other IP→guest resolutions already use). An
  unmatched node reports `matched: false` with an empty ref — never a wrong guess.
- **`overlay.go`** — `Overlay`/`BuildOverlay`: pod CIDRs per node (real — `Node.spec.podCIDR`/
  `podCIDRs`, as the cluster's own API reports them), full service/pod listings, node
  correlations, and the detected CNI. **Deliberately carries no "service CIDR"**: none of the four
  read-only endpoints this package is allowed to call exposes kube-apiserver's own service-CIDR
  flag, so synthesizing one by bounding-boxing observed `ClusterIP`s would be a guess dressed up
  as a fact — see the package doc comment's "Pod/service network model" section for the full
  reasoning, and the note for T-1502 below.
- **`resolver.go`** — `K8sResolver`, deliberately shaped like `flow.GraphResolver`
  (`Refresh`/`Resolve(ip) (string, bool)`) so a future classifier can compose the two identically.
  Match precedence: exact Service `ClusterIP` → exact Pod IP → pod-CIDR containment (names the
  owning node's pod subnet, never a specific pod/service) → no match. `Refresh` is per-cluster-ID
  additive/replacing, so registering N clusters builds one resolver spanning all of them.
- **`nodeport.go`** — `CheckNodePortExposure` / `k8s_nodeport_exposed_without_fw_rule`: for every
  NodePort/LoadBalancer service port, evaluates every *matched* correlated node's backing guest
  ruleset plus the cluster-scope ruleset (real `pve-firewall` visibility rule) for an explicit,
  enabled, inbound `ACCEPT` rule covering the port. Fires per service+port when at least one
  matched node lacks coverage; silent when covered; **never evaluates an unmatched node** (no
  finding fires or is suppressed based on a node this package couldn't resolve to a guest).
  Scope limitation, stated plainly in the code and in `needs-hardware-validation.md`: no macro/
  alias/ipset/security-group expansion, and no default-policy fallback — `internal/sim/match.go`
  already has that richer engine if false positives turn out to matter in practice.
- **`service.go`** — `Poller`: caches each cluster's most recent `Overlay`+findings, updated by
  `Poll` (called synchronously on every `GET /k8s/{clusterId}/overlay` request — the route always
  computes fresh, per `docs/architecture.md` §7's invariant) and read by the findings-stream
  adapter between overlay views. **Documented scope decision:** this package does not implement
  its own background polling scheduler (a `T-1303`-style ticker) — no such scheduler
  infrastructure exists yet on this task's dependency base (T-103/T-1002 only). A real background
  poller is a named follow-up in the report, not silently pretended to exist.
- **`internal/k8smock`** — an `httptest.Server` double serving the four named endpoints from a
  small, hand-readable YAML fixture format (`testdata/k8s/cluster-{flannel,calico,cilium,
  unknown}.yaml`), mirroring `internal/pvemock`'s own httptest-server-driven-by-fixture
  convention, plus a request `Recorder` for the zero-write-surface test. Two more fixtures under
  `testdata/k8s/` are real kubeconfigs (`kubeconfig-token.yaml`, bearer-token auth;
  `kubeconfig-clientcert.yaml`, client-cert auth with a throwaway self-signed cert/key generated
  solely for the fixture).

### Storage, API, and findings-stream wiring

- **`internal/store/k8sclusters.go`** + `migrations/0019_k8s_clusters.sql`: `k8s_clusters`
  (id, name, `kubeconfig_enc`, added_by, added_at, cni_detected, status) — app-owned registration
  intent only, never a shadow copy of the cluster's own state. `kubeconfig_enc` is AES-256-GCM
  ciphertext of the **entire raw kubeconfig text**, sealed with the identical
  `internal/store.SessionCipher` `sessions.pve_ticket_enc`/`alert_rules.target_secret_enc`/
  `ingress_targets.credential_enc`-shaped columns already use — not a second cipher or key pair.
- **`internal/api/k8s.go`**: `GET /k8s/clusters`, `POST /k8s/clusters` (netWrite+CSRF, audited
  `k8s.cluster.add`), `DELETE /k8s/clusters/{id}` (netWrite+CSRF, audited `k8s.cluster.remove`),
  `GET /k8s/{clusterId}/overlay` (netRead, live poll). Node↔guest correlation and the NodePort
  firewall check are both built locally from the live `*inventory.Graph` snapshot plus an
  optional `*ipam.Service.AllAllocations` — no dependency on any not-yet-merged package (this
  worktree's base predates T-1401/T-1403/T-1406's ingress/edge/wireguard packages; see
  "Deviations" below).
- **`internal/findings`**: new `SourceK8s = "k8s"`, a `K8sProvider` seam (`adapt_k8s.go`, mirroring
  `IPAMProvider`'s "producer returns the unified `Finding` shape directly, composition root does
  the conversion" pattern so this package never imports `internal/k8s`), wired into
  `Engine.Config`/`Engine.Findings()`. `cmd/vnproxd` wiring of a concrete `K8sProvider` adapter
  over `k8s.Poller.CachedFindings()` is **not yet done** — see "Deviations" below.
- **`docs/api.md`**: new "Kubernetes (T-1501)" section (routes, `K8sCluster`/`Overlay`/
  `K8sNodePortFinding` shapes, CNI detection); `GET /findings`'s source enum and `AlertRule.
  sourceFilter` vocabulary both extended with `k8s`.
- **`docs/data-model.md`**: `k8s_clusters` table added to §2, in migration order after
  `changeset_schedules` (0010) as 0011 — this worktree's base only had migrations through 0010
  (T-1103), not the later ones (`ingress_targets`, `wireguard_tunnels`, etc.) the shared/`main`
  checkout has landed since; see "Deviations."

## Deviations from the task card (with reasons)

1. **Worktree base predates several packages the task card's context implicitly assumes exist.**
   This worktree's branch point is right after T-1103 (scheduled changesets) — before
   T-1206 (PBS awareness), T-1401 (WireGuard), T-1403 (Edge & NAT), T-1406 (Ingress visibility),
   and the rest of Phase 12–14's later tasks that the shared `main` checkout has since merged.
   Concretely: there is no `internal/edge` package, no `internal/api/edge.go`'s
   `EdgeIPAMSource`/`buildGuestLookup` to reuse, and no `internal/ingress` package's exact route
   template to copy verbatim. I built `internal/api/k8s.go`'s guest-correlation/firewall-lookup
   helpers directly against the live `*inventory.Graph` + `*ipam.Service.AllAllocations` (both of
   which *do* exist at this base), following the same interface-seam/nil-safe-degraded-mode
   conventions every other route file in this package already establishes (`layouts.go`/
   `alertrules.go`/`firewall.go`), rather than reusing code that isn't in this tree. Functionally
   equivalent; no card requirement is unmet. This also means the migration number is `0011`
   (immediately after `0010_changeset_schedules.sql`), not `0019` as it would land against a
   caught-up `main`.
2. **No background polling scheduler.** The card's data flow (`K8sResolver`/findings-stream
   attribution) implies findings should reflect roughly-current cluster state, but this task's
   dependency set (T-103/T-1002 only) predates any scheduler infrastructure (a `T-1303`-style
   ticker) this codebase could reuse. `internal/k8s.Poller` caches the most recent poll per
   cluster and is updated synchronously by every `GET /k8s/{clusterId}/overlay` call; the unified
   findings stream reports whatever was most recently observed that way. A real background
   poller (mirroring a future latency-mesh-style scheduler) is a named, documented follow-up —
   stated in `internal/k8s/service.go`'s own doc comment, not silently pretended to exist.
3. **`cmd/vnproxd` wiring is not included in this change.** `internal/api/router.go`'s `Options`
   gained the `K8sClusters`/`K8sSecretCipher`/`K8sPoller`/`K8sGraph`/`K8sIPAM`/`K8sAudit` fields
   and `internal/findings.Engine.Config` gained `K8s K8sProvider`, both fully wired and tested at
   the package level (`internal/api/k8s_test.go` exercises the real router end to end with fakes
   satisfying every seam) — but `cmd/vnproxd/server.go` itself was **not** touched to construct
   the real `store.NewK8sClusterRepo`/`k8s.NewPoller`/a `K8sProvider` adapter and pass them into
   `api.Options`/`findings.Config`. This is a small, mechanical wiring step (the exact shape
   `cmd/vnproxd/server.go` already does for every other route family — see e.g. how
   `ingressTargetRepo`/`sessionCipher` get threaded into `Options` in the shared checkout's
   version of that file) deliberately left for the composition-root task/agent that also
   reconciles this worktree with the packages merged since its branch point, so as not to hand-
   splice code for packages (ingress, edge, wireguard) this worktree doesn't have. Flagged here
   rather than guessed at.
4. **Kubeconfig storage stores the full raw YAML text, not just the resolved fields.** The card
   says "credential material encrypted at rest" — I store the entire kubeconfig (not just the
   extracted token/cert) so a future re-poll can pick up a *changed* `current-context` or a
   rotated credential without requiring re-registration; only the resolved, in-use credential is
   ever sent over the wire to the cluster.
5. **No new `inventory.Ref` `Kind` was added.** The card doesn't ask for one, and
   `docs/data-model.md` §1 explicitly documents the `Kind` enum as closed; k8s services/pods are
   modeled as their own `k8s.Overlay`/`k8s.NodePortFinding` shapes with their own ref-like string
   scheme (`ServiceRef`/`PodRef`/`PodSubnetRef` — `"k8s-svc:<clusterId>/<ns>/<name>"` etc.),
   documented as deliberately *not* an `inventory.Ref` in `resolver.go`'s doc comment.

## Notes for T-1502 (the data-model shapes it renders)

- **`GET /k8s/{clusterId}/overlay`** is the one route T-1502 needs: `{clusterId, cni, podCidrs:
  [{node, cidr}], services: [{namespace, name, type, clusterIp?, ports: [{name?, port, nodePort?,
  protocol}]}], pods: [{namespace, name, node?, podIp?, phase?}], nodes: [{k8sNode, internalIp?,
  guestRef?, matched}], generatedAt, nodePortFindings?: [{clusterId, namespace, service, port,
  nodePort, proto, refs, detail}]}`. `nodes[].guestRef` is the exact string a topology-layer
  correlation line should draw to (an `inventory.Ref` string, resolvable against the existing
  graph the same way every other ref-drawing UI code already does); `matched: false` means "draw
  this node with no correlation line," never a guessed one.
- **Pod → node-guest → bridge → bond drilldown** (T-1502's `PodDrilldown.tsx`): a pod's `node`
  field names the k8s node (`Node.metadata.name`), which is *not* directly a guest ref — join it
  against `overlay.nodes[].k8sNode` to get `guestRef`, then hand that ref to whatever existing
  guest→bridge→bond hop-rendering primitive T-902 already has (this task does not build or know
  about that renderer).
- **No "service CIDR" shape exists.** Render `podCidrs` as CIDR regions (real data); render
  `services[].clusterIp` as individual points/labels, not a region — there is nothing to draw a
  service-CIDR polygon from, by design (see doc.go's "Pod/service network model" section). If
  product wants a visual "service network" region anyway, that has to come from an
  operator-supplied value at cluster-registration time (a new field on `POST /k8s/clusters`) —
  not invented from observed `ClusterIP`s.
- **`K8sResolver` (flow attribution, if T-1502 or a future T-1504-style task wants it now)**:
  `internal/k8s.NewK8sResolver()` + `.Refresh(overlay)` + `.Resolve(ip) (string, bool)`, shaped
  identically to `flow.GraphResolver` — composes as a second resolution stage exactly the way
  that package's own doc comment anticipates. Not wired into `internal/flow`'s pipeline by this
  task (out of scope — T-1504 owns the classifier that would consume it).
- **Findings**: `GET /findings?source=k8s` (or the `k8s` value in an `AlertRule.sourceFilter`)
  surfaces `k8s_nodeport_exposed_without_fw_rule` once `cmd/vnproxd` wiring (deviation #3 above)
  lands; until then the seam is fully built and tested but not connected to a running daemon.

## Needs-hardware-validation

Four items added to `planning/reports/needs-hardware-validation.md` under a new "Kubernetes
overlay mapping engine (T-1501)" heading: real CNI variance beyond the three named defaults
(non-default installs, a fourth CNI), node pod-CIDR advertisement across less-common CNI/IPAM
modes, kubeconfig credential-form coverage (managed-provider exec-plugin kubeconfigs are
explicitly unsupported, not guessed at), and firewall-rule visibility precision for the NodePort
finding (no macro/alias/ipset/security-group expansion — `internal/sim/match.go` has that richer
engine already, named as the natural extension point if false positives matter in practice).

## New dependency flag (per CLAUDE.md)

None added. `client-go`'s transitive dependency graph (apimachinery, klog, multiple auth-plugin
packages, generated clientsets far larger than the four read-only list calls this package needs)
was rejected in favor of the hand-rolled `net/http` + `gopkg.in/yaml.v3` reader the card itself
asked for — `gopkg.in/yaml.v3` is not new (already approved via T-1101). Stated in
`internal/k8s/doc.go`'s "Why not client-go" section as well, per the card's explicit instruction
to document this resolution.
