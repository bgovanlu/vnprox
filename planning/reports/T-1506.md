# T-1506 — SR-IOV & accelerated NIC lifecycle

## What was built

**Inventory (`internal/inventory`, `internal/host`, `internal/pvemock`)**

- `PhysNic.SRIOVVFs` (docs/data-model.md §1's already-documented field) extended from a bare VF
  count into `[]VirtualFunction` (new type: `Ref` — Kind `vf`, `"<pfName>/vf<index>"`; `PF Ref`;
  `MacAddr`, `VLAN`, `SpoofCheck`, `Trust`, `PCIAddr`; `AssignedGuest Ref`, resolved live, never
  baked into this collector-owned field). New `inventory.KindVF` Ref kind for VF identity.
  Host-netlink-only, deliberately excluded from the merge/provenance/delta machinery — copied
  straight through in `resolvePhysNic`, mirroring `Bridge.FDB`'s identical precedent exactly (one
  contributing source, no field to merge/flag conflicts on).
- `internal/host`: `VF`/`VFSpec`/`VFEntry` types, `LinkState.VFs`, real netlink collection
  (`buildLinkState`, `attrs.Vfs`) with best-effort PCI-address resolution via the PF's
  `/sys/class/net/<pf>/device/virtfnN` symlink (`sysfsVFPCIAddr`), and `host.ResolveVFPlan` — the
  single shared function that expands a `vf.provision` op's `count`/`vfs` + top-level defaults into
  a concrete per-VF plan, called by both `internal/change`'s validators and `internal/change/ifaces`'
  mutator so they can never disagree about what an op configures.
- `internal/pvemock`: `VFEntrySpec` (fixture-declared, `LinkInfo.vfs`) and `VF` (state), same
  "spec vs. state" convention `FDBEntrySpec`/`FDBEntry` already establish. `FixtureHostReader.Links`
  copies a physical-kind link's declared VFs through.
- `Guest.HostPCI map[string]string` carries raw `hostpciN` passthrough config verbatim from PVE
  guest config — populated in `FromPVEGuests`, the source the guest↔VF correlation below reads.
- New fixture `testdata/sriov/pf-vf-topology.yaml`: one node, `eno1` (PF with 2 VFs, one consistent
  one not), `eno2` (plain PF, no VFs), and a guest whose `hostpci0` names `eno1`'s vf0 PCI address.
- Golden test `internal/collect/sriov_test.go` (AC1): exercises the real `pvemock → host.Reader →
  internal/collect → inventory.Graph` pipeline end to end and asserts the exact `PhysNic`/
  `VirtualFunction` projection, no real SR-IOV hardware involved.

**Guest↔VF correlation and policy comparison (`internal/topology`)**

- `topology.ResolveVFAssignments(snap, pfRef)`: joins a PF's VFs against every guest's `HostPCI`
  config on the same node (PCI-address parsing handles both PVE's full and short address forms,
  `parseHostPCIAddr`), live at read time — mirrors `Detail()`'s existing FDB owner-labeling override
  exactly, and is wired into `GET /inventory/{ref}`'s `SRIOVVFs` field the same way (AC2). An
  unmatched VF stays the zero `AssignedGuest` Ref — never guessed.
- `bridgeFor` exported as `BridgeFor` (was already `vlancheck.go`'s PF→bridge-via-bond resolver) so
  it's shared, not duplicated, by the drift check and the changeset validator below.
- `topology.VFPolicyMismatch(vf, bridge)`: the pure VLAN/spoof-check-vs-bridge-policy comparison
  both halves of `vf_spoofcheck_mismatch` (AC3) share — a non-VLAN-aware bridge rejects any tagged
  VF; a VLAN-aware bridge rejects `spoofCheck: false` or a VLAN outside its declared VID set.

**`vf_spoofcheck_mismatch` (AC3, both halves)**

- Standing drift finding: `internal/drift/sriov.go`'s `checkVFSpoofcheckMismatch`, registered in
  `drift.checkFuncs` (drift's sixth family). Detection-only (`Fixable: false`), matching
  `checkPendingInterfaces`' stance — correcting an already-diverged VF is a real infrastructure
  action outside the v1 op vocabulary's read side; the remediation is a fresh, reviewed
  `vf.provision` changeset.
- Changeset-validate-time check: `internal/change/validate_referential.go`'s `checkVFProvision`,
  raised as a blocking error (`codeVFSpoofcheckMismatch`) on a staged `vf.provision` op whose
  resolved plan would diverge.

**Change engine (`internal/change`, `internal/change/ifaces`) — AC4**

- New `vf.*` op group (docs/data-model.md §3): `vf.provision` only (no update/delete — a fresh
  `vf.provision` supersedes, mirroring `nat.masquerade`'s "no silent overwrite of a generated
  rule" convention this codebase already uses, applied here on my own judgment since no `nat.*`
  precedent exists yet in this worktree's base — see Deviations below). **Target is the PF's own
  `physnic` Ref**, not a synthetic per-VF id — one op provisions a whole VF batch on one PF in a
  single shot; `count` XOR explicit `vfs` (each with its own optional overrides), plus top-level
  `vlan`/`macAddr`/`spoofCheck`/`trust` defaults.
- Applied via the **ordinary node-file path** (`internal/change/ifaces/vfop.go`,
  `host.VFProvisionCommands`: a post-up/post-down stanza appended to the PF's own existing iface
  stanza — sysfs `sriov_numvfs` + per-VF `ip link set ... vlan/mac/spoofchk/trust`), reusing the
  existing `StepStageFile`/`StepReload` machinery. No new `StepKind`, no new Gateway seam, and
  rollback works **for free** through the same pre-snapshot whole-file restore every other
  node-file op already relies on — verified by `internal/change/apply_vf_test.go`'s golden
  stage→validate→diff→apply→confirm test and its no-confirm auto-rollback counterpart (both against
  the fixture-backed `applyHarness`/`host.Reader`).
- Schema validation: exactly one of `count`/`vfs`, `count` positive, no shared `macAddr` across
  `count > 1` VFs, VLAN range and MAC syntax checks (table test, 11 cases).
- Referential validation: PF must exist (`codePFNotFound`); staged VF plan checked against
  `topology.VFPolicyMismatch` (table test, both directions).

## Deviations from the task card (with reasons)

1. **`vf.provision`'s `Op.Target` is the PF's own `physnic` Ref, not a synthetic per-VF id.** The
   card's deliverables list "params: PF Ref, count or explicit VF list, ..." — read literally, that
   implies `PF` is a *params* field distinct from `Target`. I instead made `Target` **be** the PF,
   for two reasons: (a) it's the entity whose VF pool is actually being (re)configured — matching
   this vocabulary's own convention (`bond.create`'s target is the new bond, not a separate
   "owning node" param); (b) `count` mode provisions VFs that don't have caller-chosen identities
   yet, so there's no natural single "new entity" ref the way `nat.masquerade.create`'s
   caller-chosen rule id works — the PF is the only stable anchor available in both `count` and
   explicit-`vfs` modes. This also makes the mandatory `TouchesMgmtPath` case simpler and more
   robust (a plain `touched(op.Target.ID)` check, no per-tunnel/per-rule stored-carrier lookup
   needed) and mirrors the default `isIfaceNamespaceKind` branch's own existing PhysNic handling —
   though an explicit case was still added per the standing rule's letter, not just its
   already-covered-by-default spirit.
2. **No `nat.*`/`route.static.*`/`wg.*` precedent existed in this worktree to literally mirror.**
   My isolated worktree branches from `2e67795` (right after T-1103 merged) — T-1401 (WireGuard)
   and T-1403 (NAT/route, the mgmt-path cases the card explicitly names as the mirror target) are
   sibling Phase-14 tasks that hadn't landed on this base, and T-1506's own listed dependencies are
   only T-103/T-205. I read their eventual shape off the shared main checkout (which had them, from
   other agents' concurrent work) purely for **style/pattern reference** — the actual
   `mgmttouch.go`/`ifaces` code I wrote targets my worktree's real, simpler baseline and does not
   assume those op groups exist. The orchestrator's merge step will reconcile the two independently
   evolving `mgmttouch.go` switches (each new case is additive and order-independent).
3. **No `vf.deprovision`/`vf.release` op.** The card's deliverables name exactly one op
   (`vf.provision`); I kept to that literally rather than inventing scope. A real deployment will
   eventually want a way to shrink a VF pool back down — flagged here as a natural, small follow-up,
   not implemented.
4. **`internal/host.VFProvisionCommands`' generated marker comment is documentation-only, not a
   decodable round-trip format** (unlike the `nat`/`route` marker convention this card's mgmttouch
   instruction references). There's no `vf.update`/`vf.delete` op that would ever need to find a
   previous `vf.provision`'s lines again by scanning for a marker — a VF's actual live state is
   independently observable via host-netlink once real hardware applies the rendered commands, so
   there is nothing to "read back apart" the way a NAT rule (whose *only* record is its generated
   line) needs. Kept the comment simple rather than building unused decode machinery.
5. **`sriov_numvfs` re-sequencing is not modeled.** `VFProvisionCommands` always writes the target
   VF count directly; real SR-IOV drivers commonly require resetting to `0` before increasing an
   already-nonzero count. Flagged explicitly in
   `planning/reports/needs-hardware-validation.md` rather than guessed at, since the correct
   sequencing is driver-specific and unverifiable against `internal/pvemock`.

## Needs-hardware-validation (flagged from day one, per the arc's standing constraint)

Three entries appended to `planning/reports/needs-hardware-validation.md` under "SR-IOV virtual
function lifecycle (T-1506)": (1) real VF creation and kernel/driver behavior (including the
`sriov_numvfs` re-sequencing gap above), (2) PCI-address resolution via the `virtfnN` sysfs
symlink (`internal/host.sysfsVFPCIAddr`) — specifically whether its index always matches netlink's
own VF `id` one-for-one, and (3) firmware-level spoof-check enforcement (whether `spoofchk on` is
genuinely enforced by a given NIC's firmware, not just accepted by the `ip link set` call). No
acceptance criterion in this task requires real SR-IOV hardware.
