## 1. What was built

### The starting point was further along than the card implied

Reading `internal/store` before writing anything showed most retention machinery already existed:
snapshot retention with a pin floor (T-206), flow/latency/WAN sample rings with age+row-cap bounds
(T-1002/T-1303/T-1405), a downsampled long-horizon capacity rollup (T-1606), baseline-profile/
posture-score/finding-event pruning, and a `.pcap` auto-purge sweep (T-1301). **Audit had no
retention at all**, and **snapshot retention had a real, dangerous gap**: nothing protected a
snapshot linked to a changeset still `applying`/`awaiting_confirm` — only `committed` snapshots
within `snapshot_pin_days` were floored. This card's actual scope narrowed to: fix that gap
(AC2, done first, per the dispatch), add audit retention, add compaction, add the
`store_near_capacity` finding, and document every class's policy in one place.

### AC2 — the snapshot in-flight guardrail

`SnapshotRepo.Prune` (`internal/store/snapshots.go`) now excludes, **unconditionally, regardless of
age**, any snapshot linked to a changeset with status `applying` or `awaiting_confirm`:

```sql
SELECT s.id FROM snapshots s
WHERE s.taken_at < ?
AND NOT EXISTS (
    SELECT 1 FROM changesets c
    WHERE c.id = s.changeset_id
    AND (
        c.status IN ('applying', 'awaiting_confirm')
        OR (c.status = 'committed' AND s.taken_at >= ?)
    )
)
```

Both in-flight statuses are covered, not just `awaiting_confirm` (the card's literal wording) — a
changeset can sit in either arbitrarily long if the daemon is down (no rollback timer runs while
stopped), and `applying` is exactly the window `recoverInterruptedApply` resumes from after a crash
mid-apply (`internal/change/apply_errors.go`'s own vocabulary: "in flight (status applying or
awaiting_confirm) cluster-wide").

**The test was written first and is explicit**: `TestSnapshotRetention_AC2_InFlightChangesetNeverPruned`
(`internal/store/retention_test.go`) seeds a snapshot **500 days old** against the **most aggressive
possible** retention config (1-day keep, 1-day pin), one subtest per in-flight status, plus two
controls — an equally-old snapshot for a *terminal*-status changeset, and an equally-old *committed*
changeset past its pin window — both proven to still prune under the identical config, so the
"protected" subtests can't be passing because the harness silently deletes nothing at this age.

### The T-1805 interaction — stated and tested, not left implicit

This is the question the dispatch (and the orchestrator's review) specifically asked to be closed
before merge, because it's exactly the failure mode this card exists to prevent — pruning stranding
or destroying state a *pending* mutation depends on. Answer: **retention never touches the
`changesets` table at all** — it isn't one of the classes this card bounds (see §5, "what this card
deliberately does not prune"). So the sealed revert ticket (`changesets.revert_ticket_enc`/
`revert_ticket_expires_at`, T-1805) rides along completely untouched by anything this card adds. The
one thing that *does* need an explicit guarantee is the **snapshot** an unattended revert restores
SDN/firewall pre-state from — and that's exactly AC2's guardrail above.

Rather than leave that as an inference from "retention doesn't touch changesets" +  "AC2 protects the
snapshot", I added a test that drives both real retention entry points (`SnapshotRetention` **and**
`AuditRepo.PruneRetention`, so an actual prune pass runs and deletes something in every table it
touches) against a changeset that is `awaiting_confirm`, holds a real sealed ticket via
`SealRevertTicket`, and has a 500-day-old linked snapshot — then asserts, directly against the store
after retention ran:

- the changeset row survives with `status == "awaiting_confirm"` unchanged;
- `ChangesetRepo.RevertTicket` returns the **exact same ciphertext bytes and expiry** as before
  retention ran;
- the pre-apply snapshot still exists.

`internal/store/retention_test.go`'s
`TestRetention_T1805_PrunedStoreStillPermitsUnattendedRevertOfInFlightChangeset`. Both preconditions
`change.Service.doRollbackLocked`'s unattended-revert path needs (an unsealable ticket, a restorable
snapshot) hold after a real retention pass — a pending unattended revert is exactly as possible after
retention as before it.

### Audit retention (new — this table had none)

`AuditRepo.Prune`/`PruneRetention`/`RunPruneLoop` (`internal/store/audit.go`), mirroring
`MetricSampleRepo`'s existing shape exactly. **No pin/in-flight floor** — deliberately, since an audit
row is a historical record of an already-attempted action that no live rollback ever reads back from
(unlike a snapshot). Default **730 days (2 years)**, argued in `DefaultAuditRetentionDays`'s doc
comment: audit is the compliance/forensic record (docs/security.md's Audit section — "every mutation
attempt, including denied and rolled back"); common regimes a deployment plausibly falls under (SOC 2,
PCI-DSS) commonly ask for a 1-year floor, 2 years gives margin over an annual audit cycle without
treating the table as a literal warehouse. No "0 = forever" escape hatch, matching the existing
`snapshot_keep_days`/`snapshot_pin_days` validation stance — an unbounded table is exactly the failure
this card exists to prevent, so "keep longer" means configuring a larger number, never disabling the
ceiling.

### Compaction

`internal/store/compact.go` (new), two pieces:

- **`EnsureIncrementalVacuum`** — a one-time, explicit conversion to SQLite's
  `auto_vacuum=INCREMENTAL` mode, called once by `cmd/vnproxd` at startup, **before** the daemon
  begins serving (same timing class as schema migrations). A fresh/already-converted store is a fast
  no-op; an **existing** pre-T-1905 store pays a one-time full-`VACUUM` cost proportional to its size
  on the first startup after upgrading — logged (`took` duration) rather than silent, and documented
  in `docs/deployment.md`'s new "Sizing and retention" section as an upgrade-timing consideration.
- **`Compact`/`RunCompactionLoop`** — once converted, `PRAGMA incremental_vacuum(N)` in bounded
  batches (`DefaultCompactionMaxPages` = 2,000 pages/~8MB, every `DefaultCompactionInterval` = 6h),
  each an ordinary write transaction. Under WAL mode a writer never blocks a reader, so this never
  needs the daemon to stop serving.

**Why not a plain `VACUUM`, and why not swap a `VACUUM INTO` copy into place live** — both rejected,
with the reasoning recorded in `compact.go`'s package doc comment: a plain `VACUUM` rebuilds the whole
file under one exclusive lock (blocks every reader/writer for its duration — the wrong shape for a
live daemon); swapping a fresh `VACUUM INTO` copy into place while the daemon's connection pool still
has the old file open is unsafe (pooled connections keep file descriptors on the old, renamed-away
inode — writes would land somewhere nothing ever reads again). That swap is what `vnproxctl restore`
does, deliberately requiring the daemon to be stopped first (T-1901) — compaction must not require
that.

**Tested, including concurrency, not just "it compiles":**
`TestCompact_ReclaimsMeasurableSpace` seeds ~2MB of audit rows, deletes ~99% of them, and asserts
`Compact` measurably shrinks `SizeBytes()`. `TestCompact_DoesNotBlockConcurrentReads` runs a goroutine
hammering `AuditRepo.List` throughout a real `Compact` call and asserts every read succeeds — AC3's
"the daemon serves reads throughout", proven rather than assumed from the WAL-mode argument alone.

### The `store_near_capacity` finding

`internal/findings/health_storecapacity.go` (new), source `store`, check `store_near_capacity`.
Reuses `store.DB.SizeBytes()` — **the exact same size source T-1903 already exposes** as
`vnprox_store_size_bytes` via `api.StoreInfoProvider` — through a small `cmd/vnproxd` adapter
(`storeCapacityAdapter`, `cmd/vnproxd/storecapacity.go`) that also attaches the local node name. No
second measurement was invented (no `statfs` on the underlying filesystem); this was the task's
explicit instruction and is also consistent with T-1903's own "mirror, don't invent a second notion"
precedent for every other daemon self-observability signal.
`cmd/vnproxd/storecapacity_test.go`'s `TestStoreCapacityAdapter_ReportsSizeAndLocalNode` asserts the
adapter's reading is byte-identical to a direct `db.SizeBytes()` call, so this claim is checked, not
just stated.

Default threshold **4 GiB** (`config.DefaultStoreWarnBytes`, `[retention] store_warn_bytes`), argued:
a PVE node's root filesystem, shared with pmxcfs and the hypervisor's own writes, is commonly
provisioned in the tens of gigabytes, so a vnprox store crossing several GiB is already a strong
signal regardless of the specific partition size. Hysteresis-debounced exactly like every other
finding in `internal/findings` — 2 consecutive findings-cycle observations to fire, 2 to clear
(`storeCapacityRise`/`Fall`, the same shape `peerUnreachableRise`/`Fall` uses) — tested directly:
`TestStoreCapacityFindings_AC4_FiresAtThresholdAndClearsBelow` drives a single breaching cycle (no
finding yet), a second (fires), a single clearing cycle (still active), a second (clears).

## 2. Defaults, stated and argued (summary — full argument in `docs/data-model.md` §13)

| Class | Default | Argument (one line — full reasoning in code doc comments + §13) |
|---|---|---|
| Audit | 730 days (2y) | Compliance/forensic artifact; 2y gives margin over an annual audit cycle without being a literal warehouse. |
| Snapshots | 90d keep / 7d pin **+ unconditional in-flight guardrail** | The rollback safety net; bounded by count-of-days for the ordinary case, never destroyed while it might still be needed for the dangerous case (AC2). |
| Flows / latency / WAN samples | 60min / row cap (unchanged, pre-existing) | Short raw-sample ring by design; downsampled onward into `baseline_profiles`/`capacity_aggregates`. |
| Capacity aggregates | ~13mo (unchanged, pre-existing) | The arc's one deliberate long-horizon exception — a downsampled daily rollup, not raw samples. |
| Captures | 6h (unchanged, pre-existing) | Shortest-lived, largest-in-bytes class; T-1301's existing auto-purge sweep. |
| Store-size warning | 4 GiB | Not a data class — a derived signal reusing T-1903's own size source; PVE root partitions are commonly tens of GB, so several GiB of vnprox's own data is already a strong signal. |

## 4. Deviations from the task card, with reasons

- **Most of the "deliverables" already existed.** The card describes building retention for flows,
  capacity samples, latency-mesh history, and captures from scratch; T-1002/T-1303/T-1405/T-1606/
  T-1301 (all merged before this card ran) already built every one of those. This report does not
  re-claim that work; it documents it (§13) and focuses the actual new work on the real gaps: the
  AC2 guardrail fix, audit retention, compaction, and the finding.
- **Compaction is a periodic daemon-internal loop plus a one-time explicit startup conversion, not a
  single always-non-blocking mechanism.** A plain `VACUUM` and a live `VACUUM INTO`-and-swap were both
  considered and rejected (§1's Compaction section has the full reasoning); the one-time
  `auto_vacuum=INCREMENTAL` conversion for a pre-existing store genuinely does hold an exclusive lock
  for its duration, which is why it's deliberately scoped to before-serving startup, not the periodic
  loop. This is stated as a real, if narrow, deviation from "must not block the daemon's reads" —
  it's true of steady-state compaction, not of the one-time upgrade conversion, and that distinction is
  documented in three places (`compact.go`, `docs/data-model.md` §13, `docs/deployment.md`'s sizing
  section) so it isn't a surprise on a real upgrade.
- **`changesets` is not retention-bounded by this card**, stated explicitly in §13 rather than left as
  a silent gap — not one of the classes the card names, and every guardrail this card adds treats the
  table as a read-only reference.

No new third-party dependency, Go or npm. No frontend change (backend/docs only).
