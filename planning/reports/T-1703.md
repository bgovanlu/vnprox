# T-1703 · Multi-tenancy & self-service — completion report

## What I built

A delegated, **server-side-scoped** multi-tenancy layer plus a request-changeset
approval workflow, composed from already-frozen primitives (the store, the
change-engine lifecycle, T-1005 alert routing, T-1207's group-claim mapping
pattern). Multi-tenancy only ever **narrows** a member's view and adds **no**
mutation path around the change engine.

### Store (migration `0030_tenants.sql`, numbered per orchestration)
- `tenants`, `tenant_scopes`, `tenant_members`, `changeset_requests` tables
  (ON DELETE CASCADE from `tenants`). `internal/store/tenants.go` (`TenantRepo`)
  + `tenants_test.go`. `kv_test.go` schema-version bumped `27` → `30`.

### Change engine (`internal/change`)
- New additive lifecycle status `StatusRequested` with transitions **only** to
  `draft` (approve) or `discarded` (reject) — **no path to `applying`/`validated`**,
  so a request-changeset can never reach apply without an approver converting it.
- `Service.CreateRequest` (creates in `requested`, validated like a draft) and
  `Service.Approve` (`requested` → `draft`). The exhaustive state-machine test
  (`changeset_test.go`) updated to 9 statuses with the new edges.

### `internal/tenant` (new package)
- `Service`: `ScopeFor` / `ScopeForTenant` (resolve a principal's visible-Ref set
  from the store, union across memberships or one tenant), `CanApprove`
  (approver-and-not-requester role check), `RecordRequest` / `MarkApproved`,
  `Approvers`, `IsMemberOf`.
- `Scope`: immutable, server-derived visible-Ref set + per-tenant role;
  `Visible`/`VisibleAny` are fail-closed set membership.
- `GraphExpander`: expands a coarse scope Ref (VNet/bridge/guest) to its member
  guests/subnets/NICs live against the shared inventory graph, so scoping a
  tenant to one VLAN yields exactly that VLAN's members without freezing them.
- `MapGroupsToTenants`: OIDC group-claim → tenant-membership mapping (T-1207's
  pattern; grants no capability by itself).

### API (`internal/api`)
- `tenantScopeMiddleware` resolves the caller's `Scope` server-side and attaches
  it to the request context; wired into `/topology`, `/findings`, `/ipam/*`,
  `/flows` read groups. Filters applied to the in-memory projection **before
  serialization** (`filterTopologyForScope`, `filterFindingsForScope`,
  `filterSubnetsForScope`, `filterFlowsForScope`, search filter, inventory-detail
  and ipam-allocations 404 guards).
- `tenantWSGuard` fail-closes the `/api/ws` upgrade for tenant-scoped principals
  (`403`) — the cluster-wide delta feed is not yet per-subscriber filtered, so a
  tenant member is refused rather than handed unscoped cross-tenant deltas.
- Tenant admin CRUD (`/tenants…`), request-changeset creation branch on
  `POST /changesets {tenantId}`, `POST /changesets/{id}/approve`, and
  `GET /dashboard?tenantId=` (scoped tile counts).
- `ApprovalNotifier` seam → `cmd/vnproxd/tenant.go` bridges to T-1005's
  `findings.Notifier` (a routed `source:"tenant"` finding to the approver group).

### Wiring / docs
- `cmd/vnproxd/server.go`: `TenantRepo` + `tenant.Service` (with `GraphExpander`
  over the live graph) + approval notifier, always wired but **inert until an
  admin creates a tenant** (no membership ⇒ unscoped reads).
- `docs/api.md` (Tenants & self-service section), `docs/data-model.md` (new
  tables + prose), `docs/security.md` (Tenant authorization + two threat-model
  rows).

## Where server-side tenant scoping is enforced (the review checkpoint)

- **Data-access layer, not the UI.** The authority is the tenant store, resolved
  from the *authenticated* identity every request (`tenant.Service.ScopeFor`),
  never a client value. `internal/api.tenantScopeMiddleware` attaches the `Scope`;
  each scoped handler filters its projection through `Scope.Visible` **before
  serialization** — the `internal/auth.forceReadOnly` enforcement-point pattern,
  not a bypassable response filter.
- **No cross-tenant leakage across list / search / error / count.** Lists drop
  out-of-scope items; `/inventory/search` filters to visible Refs; the scoped
  dashboard counts only in-scope Refs; a **direct out-of-scope Ref lookup is
  `404`, not `403`** (`/inventory/{ref}`, `/ipam/subnets/{cidr}/allocations`) so
  existence is never confirmed to a hostile client crafting other tenants' IDs.
  A non-member requesting a foreign `tenantId` (create-request, dashboard) is
  also `404`.
- **Requests flow through the change engine.** `POST /changesets {tenantId}`
  creates a `requested` changeset only after verifying every op's target Ref is
  in the tenant's scope (zero/out-of-scope target ⇒ `403`); it is blocked from
  apply until an approver converts it to a `draft`. A member can never approve; an
  approver can never approve their **own** request (separation of duties). No new
  mutation path exists — the approver still applies through the ordinary flow.

## Deviations / notes for the next agent

- **`POST /changesets {tenantId}`, not a new route.** The card names this exact
  contract; since chi allows one handler per method+path, I branch inside the
  existing create handler on the optional `tenantId` field (unset = unchanged
  ordinary-draft behavior). Documented in `docs/api.md`.
- **Op scope-check is fail-closed.** A request-changeset op with a **zero** target
  (cluster-wide ops like `sdn.apply`) is rejected — a tenant may only request
  changes to resources it can see. This is stricter than the card's minimum and
  is stated in the security doc.
- **WS `/api/ws` leak — closed fail-closed (review blocker, fixed).** The
  `/api/ws` topology.delta feed is cluster-wide and not yet filtered per
  subscriber, so a tenant-scoped principal subscribing would receive unscoped
  cross-tenant deltas. This is now **structurally closed**: `tenantWSGuard`
  (`internal/api/tenant.go`), wired into `mountWSRoute`, resolves the caller's
  tenant scope with the same `tenant.Service.ScopeFor` the REST middleware uses
  and **denies the upgrade with `403`** for any tenant-scoped principal (a
  resolution error fails closed with `500`). A non-tenant/admin principal is
  unaffected. Proven by `TestTenantScoping_WSUpgradeDeniedForTenant`
  (`internal/api/tenant_test.go`): tenant member → `403`, operator → `200`.
  A tenant getting NO live feed is safe; a tenant getting an unscoped feed is a
  leak. **Follow-up (still open, non-blocking):** full per-subscriber WS delta
  filtering, which would let a tenant member receive a live feed narrowed to its
  scope instead of none — until then the guard denies rather than leaks.
- **No frontend UI.** The ACs are all backend/API; the card's UI (scoped
  dashboard page, approval queue) is deferred. Existing Vitest suite unchanged and
  green. The API contracts are documented so the UI task can build on them.
- **OIDC session integration is at the mapping-function level.** `MapGroupsToTenants`
  is tested (AC5) but not yet auto-applied to persist memberships on OIDC login —
  the intended wiring is for the OIDC callback to upsert `tenant_members` from the
  mapped groups; left as a small follow-up so this card didn't reopen T-1207's
  session flow.
- **Graph-expansion needs real-graph-fixture validation** for coarse scopes
  (VLAN/VNet → members) against a live PVE topology; the expander is unit-tested
  against a hand-built snapshot, and the api ACs use explicit refs so the
  enforcement pipeline is proven independently of the expansion heuristic.
