## `flowEdges.ts` contract (for T-1007's history-playback build-on)

`web/src/topology/flowEdges.ts` is a **pure, framework-free** module — no React/canvas/WS import —
so T-1007 can feed it a historical/replayed record window exactly like the live path does.

```ts
export interface FlowEdge {
  id: string;              // flowEdgeId(from, to) = `${from}=>${to}::flow`
  from: string;             // srcRef (always a resolved inventory Ref — Bridge or SdnVnet)
  to: string;               // dstRef (ditto)
  bytes: number;            // summed over the input record set
  packets: number;          // summed over the input record set
  recordCount: number;      // how many flow.Records contributed
  lastAt: number;           // max(record.at) among contributors, unix seconds
  bytesPerSec: number;      // bytes / windowSeconds
}

export interface ComputeFlowEdgesParams {
  records: readonly FlowRecord[];
  windowSeconds?: number;    // default 60 — records with `at < now - windowSeconds` are excluded
  now?: number;              // unix seconds; defaults to the real wall clock, override for tests/replay
  nodeIds?: ReadonlySet<string>; // both endpoints must be members, or the edge is dropped (LOD/filter safety)
}

export function computeFlowEdges(params: ComputeFlowEdgesParams): FlowEdge[]
export function flowEdgeId(from: string, to: string): string
export function flowEdgeStrokeWidth(bytesPerSec: number): number // log-scaled, clamped [1.5, 5]
```

Behavior contract T-1007 should rely on:
- A record contributes an edge **only if both `srcRef` and `dstRef` resolved** (per T-1002's "never
  guessed" contract) **and they differ** — a same-ref conversation never produces a paintable edge
  (no distinct second endpoint), though it's still fully visible in the Flow Explorer.
- Aggregation is **directed**: `a=>b` and `b=>a` are tracked as two separate `FlowEdge`s, never
  merged/summed together.
- `now`/`windowSeconds` are the only "time" concept this module knows — for history playback,
  T-1007 supplies whatever `now` the scrubber is currently positioned at and whatever window makes
  sense for that view; the function is otherwise stateless and re-derives its whole output from
  `records` every call (cheap: a single pass + Map, no memoization inside the module — callers
  should memoize on `(records, windowSeconds, now, nodeIds)` themselves, exactly like
  `TopologyPage.tsx` does via `useMemo`).
- Output is always sorted by `id` (deterministic), so a caller diffing two `computeFlowEdges` calls
  (e.g. for a scrubber's frame-to-frame diff) can rely on stable ordering.
- Rendering consumes `FlowEdge` by mapping to `canvasDraw.ts`'s `FlowOverlayEdge` (`{id, from, to,
  strokeWidth}`) via `flowEdgeStrokeWidth(edge.bytesPerSec)` — T-1007 can reuse this mapping
  verbatim, or substitute its own width function if a scrubbed/aggregate window needs different
  visual scaling.

## Bugs found and fixed (surfaced by actually running the e2e scenario, not part of the shipped
defect surface, but worth flagging for whoever reads this next)

1. **`testdata/dev-alert.toml` (T-1005) was missing the `[metrics] key_file` override** every other
   `dev-*.toml` has had since T-1001 added the Prometheus scrape-token requirement — it fell back to
   the production default (`/etc/vnprox/keys/metrics.key`), which needs root and doesn't exist in a
   dev/CI sandbox, so `vnproxd --config testdata/dev-alert.toml` failed to start at all.
   `web/playwright.config.ts`'s webServer array boots **every** configured stack regardless of which
   spec file is targeted, so this silently broke the *entire* `web/e2e` suite locally (not just
   `alert-rules.spec.ts`'s own stack) until fixed. One-line fix, same pattern every other
   `dev-*.toml` already uses (`var/dev-alert-metrics.key`).
2. **The v2 canvas's fit-to-view can fire before elkjs's async layout resolves real node
   positions.** `TopologyCanvasV2.tsx`'s "fit once per distinct element set" effect is keyed on node
   count/ids (`elementSignature`), not position — if it fires while every node is still at its
   `{x:0,y:0}` placeholder (before `TopologyPage.tsx`'s `computeLayout` promise resolves), it fits to
   a degenerate single-point bounding box and never re-fits once the real, spread-out layout arrives
   (the signature doesn't change, only positions do). In practice this rarely surfaces (the race is
   usually won by elk), but `flows.spec.ts` hit it reliably. **Not fixed in product code** (out of
   this task's scope — a real T-901/T-902-era timing issue, not something T-1003 introduced) — worked
   around in the test itself by toggling a real layer off/on once, which forces a fresh fit against
   whatever positions are current by then (well after elk has settled). Flagging here so whoever picks
   up v2-canvas work next has this written down rather than rediscovering it.
3. **Initial e2e attempt used a bridge↔SdnVnet pair** (`bridge:pve1:vmbr0` /
   `sdn-vnet::vlanz/vnet100`) for the synthetic cross-entity flow — rejected once visible: the
   `vlanz` zone's own SDN entity elk-lays-out **directly between** a vnet and its realizing bridge
   (the same intermediate hop the real topology graph has, since there's a genuine "zone realizes
   bridge" edge), so a straight line between the vnet/bridge endpoints' centers reliably hit-tested
   that third node instead of the Flows-layer overlay edge. Switched to two same-layer bridges on
   different cluster nodes (`bridge:pve1:vmbr0` / `bridge:pve2:vmbr0`), which sit in separate
   layout columns with clear space between them.
4. **`FlowPairPanel.tsx` was originally anchored `bottom-4 left-4`** (chosen to avoid
   `InspectorStack`'s `bottom-4 right-4`) — this collides with `NavRail`'s persistent
   `fixed`/`z-50` left column, which intercepted every click on the panel's "View in Flow Explorer"
   link. Moved to `top-20 right-4` — the one fixed corner neither `NavRail` (left, full height) nor
   `InspectorStack` (bottom-right) already claims.

None of the four above are part of T-1003's shipped feature defect surface — 1 and 2 are pre-existing
gaps in other tasks' code that this task's own e2e run happened to surface first; 3 and 4 are
test/component fixes made and verified within this task before considering it done.

## Design notes / deviations

- **"Flows" toggle lives in `LayerToggleBar.tsx`, not as a 5th `Layer` union member.** The four base
  layers (`phys`/`l2`/`sdn`/`guest`) are server-emitted `TopologyNode.layer` values
  (`docs/features/topology.md` §1); "Flows" is a client-only map-painting overlay with the exact
  same per-session (not persisted-layout) lifetime `trafficMode` already has. Extending `Layer`
  itself would have implied a server-side concept that doesn't exist. `LayerToggleBar` was chosen
  as the rendering *location* (task card explicitly named this file) via two new optional props,
  keeping the component's existing 4-layer contract byte-for-byte unchanged when unused.
- **Flows layer is v2-canvas-only**, per the task card's own wording ("paints... over the T-902
  canvas renderer"). The toggle button itself stays visible under the v1 renderer/Switch view (so a
  user discovers it exists) but paints nothing there — `flowsPaintable` in `TopologyPage.tsx` gates
  both the network activity (no fetch/WS subscription starts when not paintable) and the rendering.
- **No `docsLink`-style real in-app "flow source setup" page exists** (the empty-state hint's
  "Flow source setup reference" link points to `https://sflow.org`, an external, stable, real
  reference — the same "external stable doc" convention the physical-layer's "Set up lldpd" hint
  already uses for `man7.org`, since no in-app docs viewer exists to link to `docs/api.md`'s own
  Flows section instead).
- **`useLiveFlowRecords`'s default window/limit (60s / 500 records)** are this task's own choice,
  not specified by the card — documented in `flowEdges.ts`'s `ComputeFlowEdgesParams` doc comment;
  easy to make configurable later if a real deployment needs a different tradeoff between "how long
  a quiet conversation's edge lingers" and "how much history a single fetch pulls."
