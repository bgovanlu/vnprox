# T-1602 · Microsegmentation planner core — completion report

## What I built

A new `internal/microseg` package (the planner core) plus the routes and wiring that expose it, and a small exported firewall-evaluator seam on `internal/sim` so the dry-run reuses the path simulator's own evaluation engine.

### `internal/microseg` (the deliverable)
- **`Propose(subj, corpus, profile, existing, cfg) Proposal`** — the minimal-covering-set synthesis. It projects every corpus flow onto the target guest (direction + peer subnet + service tuple), excludes anomalous flows, groups observed-good flows by `(direction, proto, port, peer-subnet)`, greedily includes the heaviest groups until byte coverage reaches the threshold (default 99.5%), and emits an ordered ACCEPT allow-list plus one trailing match-all `DROP` per governed direction. The `Proposal` carries the honesty fields (`CoveragePct`, `UncoveredFlowCount`, `ObservedGoodBytes/CoveredBytes`, `ExcludedAnomalyFlows`, `AlreadyCoveredGroups`).
- **`DryRun(prop, corpus, cfg) Report`** — replays each flow against the proposed ruleset via `sim.EvaluateFirewall` and buckets it `WouldAllow` / `WouldBlock` / `CannotDetermine` / `Ungoverned`.
- **`Stage(prop) []change.Op`** — emits only `fw.rule.create` ops targeting the subject's ruleset; the whole default-deny policy is expressed as rule-creates (no `fw.options.update`, no new op type, no second mutation path). Returns a draft's worth of ops; never calls `Apply`/`Confirm`.
- **`GuestRulesetRef(node, kind, vmid)`** — a caller convenience to build the `guest/<kind>/<vmid>` ruleset ref.

### `internal/sim` (reuse seam, no new evaluator)
- Refactored `decideDirection` from a method to a free function (it never read `Engine` state) and added **`sim.EvaluateFirewall(view, dir, FwFlow, aliases, ipsets) FwEval`** — a thin, type-converting wrapper over the exact `decideDirection`/`matchRule` path `Simulate` uses. The dry-run calls this; there is no second firewall evaluator.

### `internal/baseline` (shared subject semantics, no drift)
- Added exported wrappers `PeerSubnet` and `HourSubject` so the planner's subnet grouping and its anomaly-exclusion subject matching use baseline detection's own aggregation/bucketing rather than a re-derived copy.

### API + wiring
- `internal/api/microseg.go`: `MicrosegService` seam, `POST /microseg/propose` + `POST /microseg/dry-run`, both `netRead`-gated and read-only; serializes the honesty fields and the loud `cannotDetermine` bucket (all buckets `[]` not `null`).
- `cmd/vnproxd/microsegwire.go`: the adapter that gathers the guest's flow corpus (from `flow_samples`), its stored baseline (from `baseline_profiles`, so exclusion is independent of the training corpus), and its live resolved firewall view, then calls the pure functions. Late-binds `flowRepo` like `baselineService`.
- Docs: `docs/api.md` gained a Microsegmentation section; `docs/data-model.md` §3's `fw` row notes the reused op group carries this without a schema change.

**No store migration was added** (the planner is stateless — proposals are computed on request), so `internal/store/migrations` and `kv_test.go`'s `"26"` literal are untouched, per the card's instruction.

## Safety analysis (required — cross-referenced by test names)

1. **Observed-good excludes anomalies (load-bearing).** `Propose` runs `baseline.Detect` against the supplied *independent* baseline profile over the corpus and removes every flagged flow before synthesis (`observedgood.go`'s `excluder`, keyed by baseline's own subject strings). A transient compromise inside the training window cannot legitimize itself into an allow rule.
   - `TestPropose_ExcludesAnomalousFlows` (table over all three T-1601 classes), `TestDryRun_VolumeSpikeBurst_NeverAllowed`.
2. **Coverage is stated, never rounded up.** The covering set stops at the byte threshold and leaves the long tail uncovered; `CoveragePct`/`UncoveredFlowCount` report it exactly.
   - `TestPropose_CoverageThresholdLeavesTail`, `TestProposeNASGuest_CoverageAndMinimality`.
3. **The dry-run cannot silently approximate.** Every flow is classified by `sim.EvaluateFirewall`; an undecidable flow goes to `CannotDetermine` (with a reason), never `WouldAllow`.
   - `TestDryRun_CannotDetermine`, `TestDryRun_SelfConsistency`, `TestDryRun_HeldOut`.
4. **No auto-enforcement.** `Stage` emits only `fw.rule.create` ops and never references `change.Service.Apply/Confirm`.
   - `TestStage_EmitsOnlyFwRuleCreateOps`, `TestStage_OpsMarshalRoundTrip`, `TestPackage_NoApplyOrConfirmReference` (static AST import-boundary check).

## Dry-run soundness boundaries (explicit)

**What the dry-run proves:** for each replayed flow, exactly what the *proposed ruleset* does to it — which ACCEPT matches it, or that the trailing match-all deny drops it — computed by the same firewall rule-walk the path simulator uses. Reachability is not re-derived (an observed flow was, by definition, reachable). Where the evaluator cannot decide (e.g. an address-restricting rule against a flow whose peer address is unparseable/unknown), the flow is reported `CannotDetermine`, never assumed allowed.

**What it does not prove (by construction, disclosed):**
- **Conntrack / NAT / guest-internal firewalls** are not modeled — the same limits `internal/sim` discloses on every path result. The dry-run is a static rule-order decision, not a live-packet or stateful evaluation.
- **`volume_spike` and connectivity.** A firewall ACCEPT rule governs *connectivity*, not *rate*. A volume anomaly on an already-permitted service therefore stays permitted (correctly) — the exclusion only prevents a service seen *solely* during a spike from getting a rule. This is why `TestPropose_ExcludesAnomalousFlows`'s volume_spike case asserts "the burst legitimizes no new rule" while the spike-only case (`TestDryRun_VolumeSpikeBurst_NeverAllowed`) asserts would-block. This distinction is documented in both test and package comments.
- **Ungoverned directions.** The proposal governs only directions it observed traffic for; a flow in an ungoverned direction is reported `Ungoverned` (the policy changes nothing for it), not silently "safe" or "blocked".
- **Standalone-policy evaluation.** The dry-run evaluates the proposed ruleset as the guest's policy end-state (ACCEPT allow-list + trailing deny). Reconciling with any pre-existing guest rules is the reviewer's job (T-1603); the `Existing`-view suppression already avoids proposing duplicates of rules PVE effectively has, and suppresses *only* on a definitive allow (an indeterminate/deny existing evaluation proposes the rule — the safe bias).

## Deviations from the card
- **`fw.RuleView` does not exist** in `internal/fw`; the card's signature used it loosely. Proposal rules are `[]inventory.FwRule` (the canonical rule shape the `fw.*` op vocabulary and resolver already use).
- **`Propose` takes a `Subject{GuestRef, RulesetRef}`**, not a bare guest ref. The planner matches flows by the guest ref (which, coming from `flow_samples`, carries no qemu/lxc kind) but must stage against the `guest/<kind>/<vmid>` ruleset ref; the caller (the cmd adapter, which has live inventory) resolves the kind and supplies both. Documented in `Subject`.
- **`Report` adds `CannotDetermine` and `Ungoverned`** beyond the card's `{wouldAllow, wouldBlock, coveragePct}`. `CannotDetermine` is mandated by the honesty contract (a flow the evaluator can't prove permitted must be surfaced loudly); `Ungoverned` prevents mislabeling out-of-scope flows.
- **Security-group synthesis** (`fw.group.create`) is not implemented — every AC and the exit demo are guest-based, and `Stage` emitting a subset ("only `fw.rule.create`") satisfies AC5. The `Subject`/`Stage` shape leaves group targeting as a clean future extension.

## Needs hardware validation
- The trailing match-all `DROP` default-deny pattern and the `guest/<kind>/<vmid>` ruleset-id staging are exercised only against `internal/pvemock`/synthetic fixtures. Applying a proposed policy against a live PVE guest and confirming pve-firewall enforces the ACCEPT-then-DROP order as modeled is a hardware-validation item — as is `internal/fw.Resolve`'s pre-existing cluster→guest chain simplification the dry-run inherits (already flagged by T-501/T-503).
