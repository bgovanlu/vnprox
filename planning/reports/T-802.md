## What was built

**`internal/pve` (`guest.go`)**
- `AgentExec(ctx, node, vmid, command []string) (pid int, err error)`: `POST
  /nodes/{node}/qemu/{vmid}/agent/exec`, always sending the argv (array) form of PVE's `command`
  field to avoid in-guest shell-quoting ambiguity. qemu-only, matching `GetGuestAgentInterfaces`'s
  existing precedent (no LXC guest-agent route).
- `AgentExecStatus(ctx, node, vmid, pid) (ExecResult, error)`: `GET
  /nodes/{node}/qemu/{vmid}/agent/exec-status?pid=`, one poll. `ExecResult{Exited, ExitCode,
  Signal, OutData, ErrData, OutTruncated, ErrTruncated}`; the wire type decodes PVE's
  `exited`/`*-trunc` 0|1-int convention (mirroring this codebase's other confirmed PVE
  numeric-boolean quirks).

**`internal/probe` (new package)**
- `PVEExecer` interface (`AgentExec`/`AgentExecStatus`) — `*pve.Client` satisfies it directly,
  mirroring `internal/ipam.PVEReader`'s "small interface, real type satisfies it" seam over the
  same client package.
- `Run(ctx, client, Request) Result`: execs the protocol-appropriate command, polls exec-status on
  a 200ms interval to a bounded deadline (`DefaultTimeout` 5s, overridable), and classifies the
  outcome. Never returns a Go `error` — every failure (unsupported proto, transport failure, poll
  timeout, cancelled context) is represented in the returned `Result` (`Outcome` one of
  `reachable`\|`unreachable`\|`timeout`\|`error`, plus `Detail`/`ExecError`).
- `classify` interprets a completed exec's exit code/output per protocol (icmp: 0=reachable,
  1=unreachable, else=error; tcp: 0=reachable, 1=unreachable with a best-effort "refused" text
  sniff, else=error).
- `command.go`'s `buildCommand` is the flagged, deliberately-narrow needs-hardware-validation
  surface: exactly one target profile (Linux + iputils-ping + netcat-openbsd), not a guessed
  "portable" command — see the needs-hardware-validation entry below.

**`internal/api` (`simulate.go`, `router.go`)**
- `POST /simulate/verify`: same request shape as `/simulate/path` (`src`/`dst`/`proto`/`port`),
  `src` restricted to `guest-nic` resolving to a qemu guest (400 otherwise); `proto` restricted to
  `tcp`\|`icmp` (400 otherwise; `tcp` additionally requires `port>0`). Runs `sim.Simulate` for
  `simulated` (byte-identical to `/simulate/path`) and `probe.Run` for `observed`, computing
  `diverges` per the card's exact semantics (a confident `simulated.verdict` disagreeing with a
  non-`error` `observed.outcome`). `dst` resolution for a `guest-nic` target calls the destination
  guest's own live `GetGuestAgentInterfaces` (never the inventory graph, which does not carry guest
  IPs); `external` and an unresolvable `guest-nic` dst both yield a clean `observed.outcome:
  "error"` (no PVE session required to know that). No live PVE session → `422
  pve_session_required` (reusing T-701's code for the same underlying condition). Audited as
  `probe.verify` on every request that passes validation (`ProbeClientProvider`/
  `simulateVerifyAuditor` seams, mirroring `PVEGatewayProvider`/`lldpInstallAuditor`'s exact
  patterns); nil-safe (route only mounts with a non-nil `ProbeClientProvider` and an `AuthService`
  implementing `UsernameLookup`).
- `Options.ProbeClients`/`Options.ProbeAudit` wired in `cmd/vnproxd/server.go` via a new
  `probeClientProvider` (`cmd/vnproxd/changeagent.go`, mirroring `pveGatewayProvider`'s exact
  session-lookup pattern) and the existing `auditRepo`.

**`internal/pvemock`**
- `handleGuestAgentExec`/`handleGuestAgentExecStatus`: `POST`/`GET
  .../agent/exec[-status]`, gated on the same `VM.Audit` privilege `network-get-interfaces` uses
  (flagged — see needs-hardware-validation). Never runs a real command: `parseProbeCommand` decodes
  exactly the two argv shapes `internal/probe.buildCommand` emits (coupling documented on both
  sides), matches against the guest's `AgentExecOutcomes` fixture table (`GuestSpec`, new
  `agent_exec_outcomes`/`agent_unreachable` YAML fields, additive/optional — every existing
  fixture's parse is unaffected), and synthesizes an exec-status result `internal/probe.classify`
  reclassifies back to the same outcome. `AgentUnreachable: true` makes the exec call itself 500,
  modeling a guest with no reachable QEMU guest agent. `State` gained a small `pid -> execResult`
  table (`execs`/`execSeq`/`execMu`) for this.
- `testdata/clusters/sim-lab.yaml` (the fixture the deliverable specifically names): added vm-c's
  `agent_interfaces` (a live-resolvable guest IP for `guest-nic` dst resolution), vm-a's
  `agent_exec_outcomes` (a declarative scripted-outcome example), a new qemu guest **vm-d**
  (vmid 303) with `agent_unreachable: true` for the AC5 scenario, and **one new firewall rule** on
  vm-c: a pos-1 `ACCEPT tcp/22` (the pos-0 `DROP tcp/80` rule is untouched and still matches first
  for tcp/80). This last change is flagged: see "Doc/AC drift" below.

## Doc/AC drift (flagged)

AC3 says "a tuple matching an **existing** allow Simulate case" against sim-lab. Empirically, before
this task, sim-lab had **no** allow verdict for any vm-a→vm-c/vm-b tuple: the cluster firewall's
`policy_in: DROP` with no cluster/guest ACCEPT rule anywhere means every unrestricted port already
defaults to `deny` (verified by running `/simulate/path` directly against the fixture before
touching it — vm-a→vm-c tcp/22 was `deny`, not `allow`, prior to my change). The only actual `allow`
verdict in the original fixture is guest→external (`source-guest-out` only, no `dest-guest-in`
check) — but `POST /simulate/verify` cannot live-probe `external` (no concrete host), so that
existing case can't be the AC3 vehicle either. I resolved this by adding the minimal fixture change
that makes an allow case exist (vm-c's new pos-1 `ACCEPT tcp/22` rule) rather than reinterpreting the
AC — this is consistent with the deliverable's own instruction to add a scriptable outcome table
"to the sim-lab fixture," and I verified (via `web/e2e/simulator.spec.ts`/`user-guide-tasks.spec.ts`
static review — grep for rule counts/content assertions) that no existing Playwright spec asserts
anything about vm-c's rule list that this addition would break; the existing tcp/80 deny assertion
is unaffected since rule matching still hits the pos-0 DROP first for that port. Flagging per
CLAUDE.md rather than silently declaring "close enough."

## Design decisions not fully pinned by the card (flagged as judgment calls)

- **Capability gate**: `POST /simulate/verify` reuses `netRead` (same as `/simulate/path`) rather
  than the unused `guestNet` capability already defined in `internal/auth/caps.go`. The card didn't
  specify a capability; `guestNet` derives from PVE's `VM.Config.Network` privilege, which is a
  poor semantic match for "execute a diagnostic command via guest agent" (real PVE's own privilege
  for guest-agent actions is `VM.Monitor`, which this codebase does not model as a capability at
  all). `netRead` was the closest existing, already-wired fit for a read/diagnostic route. If a
  later task adds a dedicated guest-agent capability, this route should probably move to it.
- **dst resolution for `guest-nic`**: resolves the target IP *live* via the destination guest's own
  `GetGuestAgentInterfaces` call, never from the inventory graph (which docs/api.md's Path simulator
  section already documents as not carrying guest IPs). This is a live diagnostic route, so live
  resolution is the honest choice, but it means a `guest-nic` dst on an LXC guest (no guest agent)
  or a qemu guest with a down/absent agent yields `observed.outcome: "error"`, not a 400 — treated
  as "the resolution attempt is itself an answer," consistent with the card's honesty contract.
- **src type restriction**: an LXC (or otherwise unresolvable) `guest-nic` src is `400
  validation_failed`, not a 200/`error` outcome — the card only explicitly required ip/external src
  → 400; I extended the same treatment to a resolvable-but-non-qemu src since `AgentExec` is
  categorically inapplicable there (a request-shape problem, not a probe-attempt problem).
