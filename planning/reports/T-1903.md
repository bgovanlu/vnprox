## 1. What was built

### The gap, and the scope decision

Before this task, `GET /metrics` reported only cluster-derived state (`vnprox_iface_*`,
`vnprox_findings_open`, `vnprox_drift_open`, `vnprox_changesets`, `vnprox_build_info`) — nothing
about vnproxd itself. This task adds fourteen new series across six areas (HTTP, the collector,
the change engine, the store, peer RPCs, WebSocket), all on the same `GET /metrics` route with the
same two-gate auth, documented in full in `docs/features/monitoring.md` §9.

**No new dependency.** `internal/metrics/self.go` is a small, hand-rolled counter/histogram
implementation rather than a `prometheus/client_golang` import — `go.mod`/`go.sum` are unchanged
(verify: `git diff go.mod go.sum` is empty). `internal/api/metrics_exporter.go` already hand-renders
the exposition text format for the T-1001 families; this follows that precedent rather than adding
a dependency for what is structurally the same rendering job.

**Push vs. pull, deliberately.** Nine families are push-model (`internal/metrics.Registry`, updated
in-process as things happen); five are pull-model (read fresh from an existing source of truth at
scrape time: collector consecutive-failures from `collect.Collector.Status()` — the exact
bookkeeping `GET /health` already exposes, per the card's "mirror, don't invent a second notion" —
plus store size/schema and the WS connection count). This kept the collector change to one new
optional hook (`OnPoll`) rather than a second staleness tracker, and needed zero new state for the
WS gauge (`topology.Hub.ConnCount` already existed, just wasn't exposed through the interface).

### Backend

**`internal/metrics/self.go` (new)** — `Registry`: `counterVec`/`histogramVec` primitives (label-key
map, `sync.Mutex`, cumulative-bucket histogram math) plus nine typed `Observe*` methods, one per
push family, and `WriteTo` rendering all of them in Prometheus text format. Every vec caps its own
distinct label-combination count (4,000) and folds overflow into one `cardinality_overflow` bucket
with a one-time `WARN` log — belt-and-suspenders under the structural guarantee described below.

**`internal/api/redmetrics.go` (new)** — `redMetricsMiddleware`, mounted first in `NewRouter`'s
middleware stack (wraps every request, including `GET /metrics` itself and the SPA fallback).
`routeLabel(r)` reads `chi.RouteContext(r.Context()).RoutePattern()` — chi's own matched-pattern
string, never `r.URL.Path` — falling back to the literal `"unmatched"` for anything no route
matched. `internal/metrics.StatusClass` reduces a status code to one of six classes.

**`internal/api/metrics_exporter.go` (extended)** — `MetricsExporterConfig` gained `Self
*metrics.Registry`, `Collectors CollectorHealth` (reused), `Store StoreInfoProvider`, `WS
WSConnCounter`; `handleMetricsExport` renders the push families then the three pull families, each
independently nil-safe. `NewRouter` fills the four new `MetricsExporterConfig` fields from the
matching `Options` fields (`SelfMetrics`/`Collectors`/`Store`/`Topology`) so `cmd/vnproxd` wires
each dependency exactly once.

**`internal/collect` (extended)** — `Config.OnPoll func(source, node string, dur time.Duration, err
error)`, nil-safe, called from `loop.go`'s `attempt` (pve/lldp), `refresh.go`'s `RefreshNow`
(on-demand path), and `host.go`'s per-node `hostPollOnce` — every existing `recordResult`/
`recordNodeResult` call site got exactly one adjacent `reportPoll` call. `Status()`'s own
bookkeeping is untouched.

**`internal/change` (extended)** — `Config.Metrics MetricsRecorder` (`ObserveChangeOutcome(op
string, success bool)`, `ObserveAwaitingConfirmDuration(outcome string, dur time.Duration)`).
Scoping is deliberate and stated in `apply.go`'s doc comment: **only a call that passed its
state-machine precondition check and attempted a real transition is recorded** — a "wrong status" /
"not found" / "locked" / "validation blocked" rejection is visible via HTTP RED's own
`status_class` and the audit trail already. `Apply` records at its two terminal functions
(`finishFailedApply`/`finishAwaitingConfirm`); `Confirm` at its own transition/persist
failures and success; `Rollback`'s `awaiting_confirm` branch and `autoRollback` (T-1805's
unattended revert) both funnel through `doRollbackLocked`, which now records via a single `defer`
covering every one of its return points, so no path can be missed; `Rollback`'s `committed` branch
(creating a restoring draft) is recorded as `op=rollback` too.

**`internal/store` (extended)** — `instrument.go` (new): `*DB` grew `ExecContext`/`QueryContext`/
`QueryRowContext`/`BeginTx` methods that time-and-delegate to the identical underlying `*sql.DB`
call, plus `SetQueryObserver`, `SizeBytes`, `SchemaVersion` (reusing `migrate.go`'s existing
`currentSchemaVersion`/`latestSchemaVersion`). Every repository's ~200 call sites were mechanically
changed from `r.db.sqlDB.Foo(...)` to `r.db.Foo(...)` (a `sed` pass over 37 files, verified by
`grep` that no `.sqlDB.` call remains outside `store.go`/`instrument.go`) — a pure timing wrapper,
behavior-identical for every caller that doesn't care about the new series.

**`internal/peer` (extended)** — `ClientOptions.Metrics MetricsRecorder`
(`ObservePeerCall(node, endpoint, outcome string, dur time.Duration)`), read at `do`'s existing
success/untrusted/unreachable/breaker-open exit points. `endpoint` is `path` with its query string
stripped — every one of `do`'s ~30 call sites already builds `path` from a literal template with
dynamic values only ever in the query string, so this needed no per-call-site change.

**`cmd/vnproxd` wiring** — one `selfMetrics := metrics.NewRegistry(logger)` right after `store.Open`,
wired to `db.SetQueryObserver`, `setupCollect`'s `OnPoll`/peer client, the coordination
`peer.Client`, `change.Config.Metrics`, and `api.Options.SelfMetrics`/`Store`. Two small adapter
helpers (`pollMetricsHook`, `peerMetricsRecorder`) guard against Go's typed-nil-in-interface
footgun for `setupCollect` (a standalone function a future test could call with a nil registry) —
the inline call sites in `runDaemon` itself never see a nil `selfMetrics`, so they pass it directly.

### Frontend

**`web/src/grafana/DaemonMetricsPanel.tsx` (new)**, shipped alongside `MetricsPanel.tsx` (T-1001,
`web/grafana-panel/README.md`'s "contract not source" boundary) with the identical contract: same
`promParse.ts` parser, same fixture-scrape-driven test, no live Grafana dependency. Flat
counter/gauge families render as a label/value table like `MetricsPanel`; histogram families are
reduced to one `count`/`avg` row per label combination (rendering every `_bucket{le=...}` sample as
its own row would be far too dense for a summary panel — a real percentile view belongs in a proper
Grafana heatmap panel against the raw series).

### Docs

`docs/features/monitoring.md` §9 (new): every series' type, labels, and cardinality bound, the
push/pull split, the scoping rule for change-engine recording, and the T-1906 untrusted/unreachable
distinction carried through to `vnprox_peer_calls_total`. `docs/api.md`'s Metrics-exporter
subsection gained one paragraph pointing at §9 rather than duplicating the table.

## 2. Cardinality analysis (AC1)

| Series | Labels | Bound |
|---|---|---|
| `vnprox_http_requests_total` | `route`, `method`, `status_class` | `route`: chi route pattern or `"unmatched"` — bounded by this daemon's own registered route table (a few hundred, fixed at build time) + 1. `method`: ≤6. `status_class`: 6 (never a raw code). |
| `vnprox_http_request_duration_seconds` | `route`, `method` | Same. |
| `vnprox_collector_polls_total` | `source`, `node`, `outcome` | `source`: 3 (closed). `node`: cluster size (`""` for `pve`). `outcome`: 2. |
| `vnprox_collector_poll_duration_seconds` | `source`, `node` | Same minus `outcome`. |
| `vnprox_collector_consecutive_failures` (pull) | `source`, `node` | Same minus `outcome`. |
| `vnprox_change_outcomes_total` | `op`, `outcome` | 4 × 2 = 8, fixed. |
| `vnprox_change_awaiting_confirm_seconds` | `outcome` | 3, fixed. |
| `vnprox_store_query_duration_seconds` | `op` | 6, fixed (`select`\|`insert`\|`update`\|`delete`\|`other`\|`tx`). |
| `vnprox_store_size_bytes` / `_schema_version` / `_schema_migration_pending` (pull) | *(none)* | 1 each. |
| `vnprox_peer_calls_total` | `node`, `endpoint`, `outcome` | `node`: cluster size. `endpoint`: ~30 compile-time-literal RPC path templates. `outcome`: 3. |
| `vnprox_peer_call_duration_seconds` | `node`, `endpoint` | Same minus `outcome`. |
| `vnprox_ws_connections` (pull) | *(none)* | 1. |

**Enforcement is structural, not conventional.** `routeLabel` sources the HTTP route label from
`chi.RouteContext(r.Context()).RoutePattern()`, which chi builds by joining each matched
sub-router's *pattern string* — it is never populated from a resolved URL parameter, so there is no
code path here that could leak a raw ID even by mistake. `TestHTTPRED_RouteLabelNeverLeaksRawID`
(`internal/api/redmetrics_test.go`) drives a real request through the *real production router* with
a concrete, distinctive changeset ULID in the URL, scrapes `GET /metrics`, and asserts that ID
string appears nowhere in the body — the regression test a future author who reintroduces
`r.URL.Path` would trip. `TestRouteLabel_UnmatchedRouteIsBoundedLabel` covers the no-match case.
Every `counterVec`/`histogramVec` additionally caps its own series count (4,000) as a backstop
(`internal/metrics/self_test.go`'s `TestCounterVec_CardinalityCapCollapsesToOverflowBucket` /
`TestHistogramVec_CardinalityCapCollapsesToOverflowBucket`).

## 3. Measured scrape overhead (AC4)

Measured, not estimated: `internal/api/scrape_overhead_test.go` builds a registry with a
deliberately generous full series set (60 HTTP routes × 3 methods × 5 status codes, 32 collector
nodes, 32 peer nodes × 30 endpoints, every change-engine/store label combination) — larger than any
vnprox deployment (a self-hosted single-cluster appliance) is expected to reach — and times real
`GET /metrics` calls end to end through the router.

- `TestMetricsScrape_OverheadBudget`: 20 samples, **avg 73.5ms**, body **1.81MB**, on this sandbox's
  virtualized CPU (QEMU).
- `BenchmarkMetricsScrape` (`-bench=BenchmarkMetricsScrape -benchmem`): **72.7ms/op, 8.1MB/op,
  149,353 allocs/op**.

**Documented budget: under 500ms.** Chosen as a sub-second bound, imperceptible against
Prometheus's multi-second scrape cadence (default `scrape_timeout` 10s; most operators configure
5-60s) for a route hit by at most one or two scrapers on a schedule, never a hot request path. The
measured ~74ms leaves ~6.7× headroom under that budget even at this stress-test series size; a
realistic deployment (far fewer than 32 nodes, and not every route/status/endpoint combination
co-occurring) would measure substantially lower. `149,353 allocs/op` is the one number worth a
future look if this ever needs tightening — it comes from `fmt.Fprintf`-per-sample in `self.go`'s
`writeSample`; not a problem at current scale, but a `bytes.Buffer`-targeted formatter (avoiding
`fmt`'s reflection path) would be the next lever if series counts grow an order of magnitude.

## 5. Deviations from the task card, with reasons

- **The card's framing mentioned `vnprox_session`** among today's exported families; no such series
  exists (`docs/api.md`'s Metrics-exporter table and the exporter code both confirm the documented
  set is `vnprox_iface_*`, `vnprox_findings_open`, `vnprox_drift_open`, `vnprox_changesets`,
  `vnprox_build_info`). Treated as imprecise framing, not a real series to preserve/extend —
  `vnprox_session` is a cookie name (`internal/auth.SessionCookieName`), unrelated to metrics.
- **Change-engine recording is scoped to post-precondition attempts only** (§1/§4 above), not every
  `Apply`/`Confirm`/`Rollback` call. This is a considered choice, not an oversight: the card's own
  AC2 example ("a rolled-back changeset ... moves the expected series") is satisfied, and a
  precondition rejection is already visible via HTTP RED's `status_class` and the full audit trail —
  duplicating it here would only add noise to a series meant to answer "is the apply pipeline
  healthy," not "how many bad requests did clients send."
- **No `GaugeVec` primitive was built.** Every gauge-shaped series this task needed turned out to be
  pull-model (collector consecutive-failures mirrors `Status()`; store size/schema/WS connections
  read fresh at scrape time) — no push-model gauge was ever needed, so `internal/metrics/self.go`
  only implements `counterVec`/`histogramVec`. Documented as a deliberate scope reduction, not a gap.
- **Query-duration instrumentation is transparent at `*DB`, not per-repository-method.** Touching
  ~200 individual call sites with a bespoke label per query would have been both a much larger diff
  and a much larger risk surface for this task's size; the chosen design (§1) gets full coverage at
  one choke point with a mechanical, verifiable transform instead.

No other deviations. No new third-party dependency (§1).

## 6. For the next agent (T-1904, `vnproxctl doctor`)

T-1904 depends on this task explicitly ("reports on what T-1903 measures"). Concretely useful to it:

- **`store.DB.SchemaVersion(ctx) (current, latest int, err error)`** is the exact schema-vs-binary
  read doctor's card asks for — already built, already tested, reuse it rather than re-deriving
  `currentSchemaVersion`/`latestSchemaVersion` a second time. `vnprox_store_schema_migration_pending`
  is the same signal exposed as a metric, for anyone who wants it in Grafana instead of/alongside
  `doctor`'s own output.
- **`api.CollectorHealth`/`collect.Collector.Status()`** (unchanged by this task, just newly
  surfaced as `vnprox_collector_consecutive_failures`) is the existing per-source/per-node
  staleness read — doctor's "collector health" check, if it wants one, should read this rather than
  add a fourth notion of collector health (T-1903's own card warned against exactly that).
  `store.DB.SizeBytes()` is disk-headroom's data source for the size half of that check.
  `peer.PeerTrustState` is not re-exposed as a metric label enum in a doctor-consumable form
  (`vnprox_peer_calls_total`'s `outcome` label carries it, but there is no "current peer trust
  state" gauge) — if doctor wants "which peers are currently untrusted," it should go to
  `peer.Client.PeerStatuses()`/`TrustReport` directly (T-1906's own surface), not this task's
  RPC-outcome counters, which are historical/cumulative, not current-state.
- **`internal/metrics.Registry` has no public accessor for reading current values back out** — it
  is a write-then-render type (`Observe*` in, `WriteTo` scrape-format out), not a queryable store.
  If doctor wants to reason about live metric values in-process (rather than scraping its own
  `GET /metrics` over HTTP), it will need either a new accessor on `Registry` or to scrape the real
  endpoint — worth deciding explicitly rather than discovering it mid-implementation.
- The **149,353-allocs-per-scrape** number (§3) is fine at today's scale and not something doctor
  needs to work around, but if a future task adds a `doctor` check that scrapes `GET /metrics`
  itself (e.g., "is the metrics endpoint healthy") on a tight timeout, budget accordingly against
  the measured ~74ms figure, not the 500ms ceiling.
