  reuses `topology/queries.ts`'s `useTopologyQuery` to find bridges and their directly-attached

## Deliberate deviations from the task card's prose

1. **Pending-changesets tile's deep link is not a `/changesets` route.** The task card's
   deliverables bullet lists `/changesets` alongside the other tiles' target routes, but
   `App.tsx` has no such route — changesets are worked in the persistent global `ChangesetDrawer`
   (mounted in `AppShell.tsx`, opened by setting `changesets/store.ts`'s `activeId`/`drawerOpen`),
   not a routed page. This tile's "Open drawer" button opens that drawer on the most-recently-updated
   pending changeset (or reveals the drawer's own empty state if none exist) — the actual mechanism
   every other op-producing feature in this codebase already uses to reach a changeset. AC3's "deep
   link to owning page" is satisfied in spirit; `DashboardPage.test.tsx` asserts the drawer opens
   with the correct `activeId`, and `dashboard.spec.ts`'s e2e coverage exercises a routed tile
   instead (findings-by-severity → `/tools`) to keep the e2e file's own scope tight, per AC6's "at
   least one tile's deep-link end to end."
2. **`/audit` is capability-gated on `audit`, not `netRead`** (docs/api.md: "Requires the `audit`
   capability ..., not `netRead`"), unlike every other tile's route (findings, changesets,
   protected-interfaces/status, metrics/live are all `netRead`-gated). The dashboard mounts under
   the same `RequireAuth`/`AppShell` structure as every other page (there is no per-route capability
   guard anywhere in this app — capability gating happens server-side, per-request, and client-side
   only as disabled-affordance styling on write controls); a session with `netRead` but not `audit`
   simply sees that one tile's fetch fail with a normal `403`, surfaced the same non-crashing way
   `AuditPage.tsx`'s own fetch already handles it. Noted here since "mounts under the same `netRead`
   capability gate as topology" in the task brief slightly overstates the uniformity across all six
   tiles' underlying routes.
3. **LoginPage.tsx's post-login redirect target was intentionally left untouched.** It still falls
   back to `/topology` (a hardcoded default, unrelated to the router's index route), not `/`. Every
   other e2e spec in this repo (`topology.spec.ts`, `changesets.spec.ts`, `onboarding.spec.ts`,
   `readonly-crawl.spec.ts`, `user-guide-tasks.spec.ts`, `lacp-inspector.spec.ts`, `evpn-tab.spec.ts`,
   ...) asserts `page.waitForURL("**/topology")` immediately after login; repointing that fallback at
   `/` would be a much larger, cross-cutting change well outside this card's stated scope (which
   named only `App.tsx`'s index route and `NavRail.tsx`). `dashboard.spec.ts` therefore verifies the
   dashboard via the NavRail's new Home entry and a direct `page.goto("/")`, not via asserting login
   itself redirects there. Flagging this as a product-decision point for whoever owns the phase: if
   the dashboard is meant to be the literal first thing a user sees after logging in (not just
   reachable at `/`), `LoginPage.tsx`'s fallback and every one of those e2e specs' `waitForURL` calls
   would need a coordinated follow-up change.

## Read-only verification (AC5)

or `.post(`/`.put(`/`.delete(` call — zero matches. Every API function the dashboard imports
(`fetchFindings`, `listChangesets`, `fetchMgmtStatus`, `fetchTopology`, `fetchMetricsLive`,

`AppShell` route structure the topology page uses (see deviation #2 above for the one per-tile
capability nuance). `readonly-crawl.spec.ts`'s new `/` entry independently confirms zero enabled
mutating controls render on the page for a `netRead`-only session.
