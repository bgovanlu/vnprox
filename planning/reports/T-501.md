## What was built

### 1. Data model (`internal/inventory`)

`FwRuleset` already existed (an earlier task had scaffolded rules/options ingestion); this task extended it with the alias/ipset/security-group shapes docs/data-model.md's contract needed and T-501's own deliverable called for:

- `FwAlias{Name, CIDR, Comment}`, `FwIPSet{Name, Comment, Entries []FwIPSetEntry}`, `FwIPSetEntry{CIDR, Comment, NoMatch}`, `FwGroup{Name, Comment, Rules []FwRule}` — new types in `internal/inventory/entity.go`, each with `clone()`/`fieldMap()` wiring so they participate correctly in the graph's delta/provenance machinery.
- `FwRuleset` gained `Aliases`, `IPSets`, `Groups` fields. `Groups` is documented as cluster-scope-only (real PVE has no per-node/per-guest security groups; pvemock's own route mounting confirms this).
- `inventory.FromPVEFirewall` (`ingest.go`) takes a new `FirewallObjects` bundle (aliases/ipsets+entries/groups+rules, all raw `pve.*` shapes) and maps them onto the ruleset entity, alongside the rules/options it already mapped.
- `internal/collect/pve.go`'s `pollFirewall` now also calls a new `fetchFirewallObjects` per scope (aliases, ipsets with entries; groups+their rules only for cluster scope), feeding the above. Individual object-fetch failures are logged and skipped, matching every other step in this poll cycle's "don't blank out what's already known" policy.

No new `Kind`/entity was introduced — aliases/ipsets/groups live as fields on the existing `fw-ruleset` entity, avoiding new graph plumbing (edges, merge-ownership entries) that wasn't otherwise needed.

### 2. Resolution engine (`internal/fw`, new package)

Pure, I/O-free library per the task card:

- `Snapshot`/`BuildSnapshot` — a plain data snapshot (cluster ruleset, per-node map, per-guest map keyed by the guest's own `inventory.Ref`) assembled from a flat `[]inventory.Entity` list. No `*inventory.Graph` reference is ever held inside the package.
- `Resolve(snap, guestRef) (ResolvedView, error)` — the guest's full effective evaluation order per docs/features/firewall.md §1 ("cluster rules → security groups → guest rules → default policies"): cluster's own rules first, then the guest's own rules, with any rule whose `Direction == "group"` expanded in place (the reference line itself occupies one position; its group's rules splice in immediately after, tagged `OriginGroup`). Each entry carries an `Origin` (`cluster`/`group`/`guest`) and a stable `Pos`. Disabled rules are *not* filtered — the resolved view stays a complete, honest picture; a future verdict computation (T-503) filters `!Enabled` itself.
- `DefaultPolicy` resolution: guest's own `policy_in`/`policy_out` if set, else cluster's, else pve-firewall's own hardcoded default (`DROP` in / `ACCEPT` out) — a documented, defensible choice since neither the spec nor api.md pins this exact three-tier fallback explicitly.
- `ScopeBanners(snap, scope, node, ruleset)` — the "Datacenter firewall is OFF: none of these rules are active" banner (verbatim per docs/features/firewall.md §2's own example), cascading to every affected node and guest scope even when that scope's own toggle is nominally on (acceptance criterion 3's explicit requirement).
- `UsageCounts(snap)` — "referenced by N rules" for every alias/ipset/security group, honoring real pve-firewall's scope-visibility rule: cluster-scope objects are referenceable from any rule anywhere (cluster/node/guest rules, and every security group's own rules); node-/guest-scope objects are only referenceable from their own ruleset's rules.
- `MacroExpansion`/`KnownMacros` — a representative ~23-entry built-in macro catalog (HTTP, HTTPS, SSH, DNS, SMTP family, IMAP/POP3 families, FTP, NTP, Ping, Telnet, Rsync, VNC, Syslog, SNMP, LDAP family, HKP, MySQL, PostgreSQL) with proto/port expansion previews — explicitly documented as *not* exhaustive (real pve-firewall ships several dozen; this covers what the fixtures/tests need to demonstrate the mechanism honestly).

**Purity enforcement (acceptance criterion 5):** `.golangci.yml` gains a `depguard` rule scoped to `**/internal/fw/**` denying `net`, `net/http`, `os`, `os/exec`, `io`, `database/sql`, and every internal package that itself does I/O (`internal/pve`, `internal/pvemock`, `internal/peer`, `internal/store`, `internal/host`, `internal/api`, `internal/change`) plus `nhooyr.io/websocket`. Verified live: a throwaway `import "net/http"` inside the package was confirmed to fail `golangci-lint run` with a clear `depguard` message before being reverted.

**Documented design decision, flagged per CLAUDE.md:** docs/features/firewall.md §1 literally states the guest resolved view's order as "cluster rules → security groups → guest rules → default policies" — this implementation applies the cluster ruleset's own rules *directly* to every guest's resolved view. Real pve-firewall's actual iptables realization is stricter: cluster.fw's top-level `[RULES]` only ever apply to each node's *host* chain; they reach a guest's chain only when referenced via a security group. I followed the product spec's documented (simpler, more visible) model literally rather than re-litigating it, but this is a real divergence from stock PVE behavior worth flagging for hardware validation and for whoever builds T-503 (the path simulator, which needs to decide whether to inherit this same simplification or model the stricter host/guest separation). See `internal/fw/resolve.go`'s `Resolve` doc comment for the same note in-code.

### 3. API (`internal/api/firewall.go`)

- `GET /firewall/rulesets?scope=cluster|node|guest` — cluster: the single ruleset; node/guest: with `?node=`/`?ref=`, that one's detail (guest additionally gets the resolved view in the same payload); without it, `{items: [...]}` for hierarchy navigation.
- `GET /firewall/objects` — every alias/ipset/group with usage counts + reference locations, plus the macro catalog.
- Both netRead-gated, matching every other read route's capability convention. `FirewallGraph` is a one-method (`Snapshot() inventory.Snapshot`) seam so `*inventory.Graph` satisfies it directly — wired into `cmd/vnproxd/server.go`'s router options as the daemon's existing graph.
- docs/api.md's originally one-line-per-route documentation is filled in with the actual JSON shapes this task produces (definition-of-done #4), since the doc didn't pin an exact schema beyond the route's existence.

## Deviations from the task card

1. **Cluster rules apply directly to every guest's resolved view** (rather than only via security-group references, which is real pve-firewall's actual host/guest chain separation). This follows docs/features/firewall.md §1's literal wording, not a guess — flagged above and in-code as a documented simplification worth hardware validation, and as something T-503 needs to consciously decide whether to inherit.
2. **Group-reference rule representation**: no existing PVE-shaped type in this repo had an explicit "this rule references a security group" field. I adopted the convention `Direction == "group"`, `Action == <group name>` (matching the real Proxmox REST API's own `"type":"group"` rule shape, which I recalled from PVE documentation) — documented in `internal/fw/resolve.go`'s `appendRule` and used consistently across the new fixture, ingest code, and tests. No existing code assumed a different convention, so this isn't a breaking change to anything else in the repo.
3. **API response shapes for `/firewall/rulesets` and `/firewall/objects`** were designed from scratch — docs/api.md pinned only the route's existence and a one-line purpose, not a schema. The chosen shapes are now documented in docs/api.md per definition-of-done #4.
4. **New fixture instead of extending an existing one**: `three-node-vlan.yaml`'s firewall sections are mostly empty and could have hosted these scenarios, but `single-node.yaml`/`messy-brownfield.yaml` already have exact-rule-count assertions in `pvemock/firewall_test.go` that a shared-fixture edit would risk breaking. A dedicated `firewall-scenarios.yaml` avoided that coupling entirely.
5. **No `internal/firewall` service package**: rather than adding a separate "service" package (mirroring `internal/topology`/`internal/drift`'s pattern of wrapping `*inventory.Graph`), the glue (`fw.BuildSnapshot(graph.Snapshot().All())`) lives directly in `internal/api/firewall.go` behind a one-method `FirewallGraph` interface. This is thinner than a dedicated package would be and keeps `internal/fw` unambiguously the only "firewall" package in the module; flagging in case a future task expects a `internal/firewall.Service` type to exist.
