New package `internal/change/ifaces` (chosen over extending `internal/host`,
per the task card's either/or, to keep zero write-contention with T-102's

### Op vocabulary implemented (docs/data-model.md §3's iface/bond/bridge/vlan groups)

`iface.update`, `bond.create`, `bond.update`, `bond.delete`,
`bridge.create`, `bridge.update`, `bridge.delete`, `bridge.port.add`,
`bridge.port.remove`, `vlan.create`, `vlan.update`, `vlan.delete` — the full
set the card lists. `sdn.*`/`fw.*`/`guest.*`/`ipam.*` ops are out of scope

### Exported surface (for T-201 naming reconciliation)

- **Package**: `github.com/bgovanlu/vnprox/internal/change/ifaces`
- **`Op` interface**: `Kind() OpType`, `Ref() inventory.Ref` — targets are
  `internal/inventory.Ref` (the same `{Kind,Node,ID}` triplet already shared
  by `internal/inventory`/`internal/topology`/`internal/api`), not a new Ref
  type.
- **Concrete op types**: `IfaceUpdate`, `BondCreate`, `BondUpdate`,
  `BondDelete`, `BridgeCreate`, `BridgeUpdate`, `BridgeDelete`,
  `BridgePortAdd`, `BridgePortRemove`, `VlanCreate`, `VlanUpdate`,
  `VlanDelete` — every field is documented in `op.go`. OVS vs. Linux
  bridging/bonding is selected via `Target.Kind` (`inventory.KindBridge` vs.
  `inventory.KindOVSBridge`, `inventory.KindBond` vs.
  `inventory.KindOVSBond`) rather than a separate bool, matching
  `docs/data-model.md`'s own Kind vocabulary.
- **`Mutate(f *host.File, op Op, changesetID string) error`** and
  **`MutateAll(f *host.File, ops []Op, changesetID string) error`** — the
  AST mutators, directly testable against `internal/host.File`.
- **`UnifiedDiff(oldPath, newPath, oldContent, newContent string) string`**
  — stdlib-only unified diff renderer (no third-party diff dependency).
- **`DiffChangeset(ctx, reader host.Reader, ops []Op, changesetID string) (*ChangesetDiff, error)`**
  — the diff-generation logic, callable with only a `host.Reader` and a
  concrete op slice; no changeset store or HTTP involved.
- **`FileDiff{Node, Path, Unified, Changed}`**, **`OpSummary{Op, Target, Node, Summary}`**,
  **`ChangesetDiff{Files []FileDiff, Ops []OpSummary}`** — JSON-tagged,
  matching `docs/api.md`'s "per-file unified diffs + structured op
  summaries" diff shape.
- **`DecodeOp(json.RawMessage) (Op, error)`** / **`DecodeOps(json.RawMessage) ([]Op, error)`**
  — decode the `docs/api.md` `{"op","target","params"}` envelope (and a
  JSON array of them) into concrete `Op` values, so this package can be
  driven directly from a store's persisted `ops_json` without depending on
  `internal/change`'s in-progress `Op` type at compile time.
- **`ChangesetLookup` interface** (`Ops(id string) ([]Op, error)`) and
  **`NewDiffHandler(lookup ChangesetLookup, reader host.Reader, idParam func(*http.Request) string) http.HandlerFunc`**
  — the thin, router-agnostic handler for `GET /changesets/{id}/diff`. It
  is **not** wired into `internal/api/router.go`: that file's
  `mountChangesetRoutes`-equivalent doesn't exist yet (T-201 owns the
  changeset store/CRUD surface and hasn't landed in this worktree), and
  wiring a route needs the real store plus auth/capability middleware
  neither of which this task owns. The integrator mounts it once T-201
  lands, e.g. `r.Get("/changesets/{id}/diff", ifaces.NewDiffHandler(store,
  hostReader, func(r *http.Request) string { return chi.URLParam(r, "id") }))`,
  with a small adapter satisfying `ChangesetLookup` from T-201's store
  (filtering its full `Op` union down to the iface/bond/bridge/vlan groups,
  converting via `DecodeOps` if it persists the `{op,target,params}` wire
  shape, or constructing this package's concrete types directly from
  already-decoded fields otherwise).

## Mutation semantics (what "minimal edit" means here)

- **Untouched stanzas byte-identical**: Create ops only ever *append* new
  `host.Entry` values (`appendStanza`/`appendStanzaRaw`/`prepareAppend`);
  Update/PortAdd/PortRemove ops edit the one targeted `Entry`'s `Body` slice
  in place (`e := &f.Entries[idx]`), leaving every other `Entry` in the same
  slice position, byte-identical. Verified directly against the parsed AST
  (not string diffing) by `requireOriginalEntriesPreserved`.
- **Comments preserved**: edits go through `setOption`/`setOptionList`,
  which replace only the option lines with a matching key, leaving every
  other `BodyItem` (comments, blank lines) untouched. One real bug caught
  and fixed during development: a stanza parsed from the middle of a file
  often carries a trailing `BodyBlank` item (the blank line separating it
  from the next stanza belongs to the still-open stanza per
  `interfaces_parse.go`'s parser, not a separate top-level entry) — naively
  appending a new option at the end of `Body` would open a blank line in
  the middle of the rendered stanza. Fixed via
  `insertBeforeTrailingBlanks`, caught by hand-inspecting the first golden
  file (`bond-update-03.interfaces`) before locking it in.
- **`# managed by vnprox (changeset <id>)` marker**: added as the first
  `BodyComment` item of every stanza a Create op produces; verified by both
  golden tests and the randomized property test.
- **Deterministic new-stanza ordering**: new stanzas are appended in the
  order their Create ops appear in the caller's `ops`/`MutateAll` slice —
  no map iteration anywhere in the append path.
- **OVS vs. Linux convention**: OVS bridges/bonds use
  `allow-ovs <name>`/`allow-<bridge> <name>` instead of `auto <name>`,
  matching `testdata/interfaces/04-ovs-bridge.interfaces` and
  `05-ovs-bond.interfaces` exactly (`allowPrefixEntry` in `entryutil.go`).

## What was tested and how

`go test ./internal/change/ifaces/...` — 34 top-level test functions (some
table-driven/sub-tested), **90.5% statement coverage**
(`go test ./internal/change/ifaces/... -coverprofile=... ; go tool cover
-func=...`), all green; `go vet ./...` and `golangci-lint run ./...`
(repo-wide) both 0 issues; `govulncheck ./...` (repo-wide) no
vulnerabilities; `gofmt -l` clean. `git status` confirms only
`internal/change/ifaces/` is new — no other package was touched.

1. **Golden tests (AC1)** — `golden_test.go`, 14 cases (one per op type,
   plus OVS variants for `bond.create`/`bridge.create`), each applying one
   op to a specific T-102 corpus fixture and byte-comparing the rendered
   file against `testdata/golden/*.interfaces`. Golden files were
   bootstrapped by the test harness itself (`checkGolden` writes-then-locks
   on first run) and then hand-inspected (`cat -A`) before being treated as
   ground truth — this is how the trailing-blank-line bug above was
   caught.
2. **Property tests (AC2/AC3)** — `property_test.go`:
   - `TestProperty_CreateOpsPreserveOriginalContent` runs a 3-op Create
     sequence (bond → bridge → vlan) against **all 15** of T-102's
     round-trip corpus fixtures and asserts the untouched-prefix invariant
     plus that the output re-parses cleanly. This is AC3 ("asserted across
     the corpus") done literally across the whole corpus, not just the
     files golden-tested.
   - `TestProperty_RandomizedCreateOpsMatchIntent` runs 300 seeded-random
     iterations (`rand.NewSource(42)`) generating random bond/bridge/vlan
     Create ops (random slaves/ports/VID/MTU/mode/autostart) against a
     randomly chosen corpus file, applies the op, **re-parses the rendered
     bytes from scratch**, and checks the entity-level facts a collector
     would read back out (name/family/method, slave/port membership,
     vlan-raw-device linkage, MTU, autostart wiring via `AutoIfaces()`,
     the managed-by marker) match the op's stated intent. This is the AC2
     property test; see the "deviation" note below on why it checks
     `host.Entry`/`AutoIfaces()` facts rather than a true
     `inventory.Bond`/`Bridge`/`VlanIface`.
3. **Untouched-stanza byte-identity (AC3)** — covered by both the golden
   tests' `requireOriginalEntriesPreserved` calls and the corpus-wide
   property test above.
4. **Diff endpoint correctness for a multi-node draft (AC4)** —
   `changeset_test.go`'s `TestDiffChangeset_ThreeNodeVlan` builds a 3-op
   draft touching `pve1`/`pve2`/`pve3` of
   `testdata/clusters/three-node-vlan.yaml` (via
   `pvemock.NewFixtureHostReader` + `host.NewFixtureReader`, the exact
   adapter chain `internal/host/fixture_test.go` already uses), and checks:
   one `FileDiff` per node in first-appearance order, each diff containing
   the expected edit (`+\tmtu 9000`, `+auto vmbr0.100`, the managed-by
   marker, `+\t#spare uplink`), and one `OpSummary` per op in input order.
   `TestNewDiffHandler_OK`/`_NotFound`/`_LookupError`/`_DiffError` exercise
   the HTTP handler end to end against `httptest`.
5. Additional unit coverage: `diff_test.go` (the LCS diff/hunk algorithm in
   isolation — identical content, single hunk, multi-hunk grouping, no
   trailing newline); `op_test.go` (wire envelope decode round-trips and
   error paths); `coverage_test.go` (every op's not-found/exists error
   path, `Summarize` over every op type, OVS bond mode defaulting, the
   multi-name `auto`/`allow-*` line regeneration branch, comment
   overwrite/removal, autostart insertion into a previously-unstarted
   stanza, `bridge.port.remove` clearing the last port cleanly).

## Deviations from the task card / things to flag

- **Package location**: chose `internal/change/ifaces` over extending
  `internal/host`, per the card's explicit either/or. Rationale: T-102 is
  merged and stable, but a new subpackage avoids any file-level overlap
  with it or with T-201's concurrent work directly in `internal/change/`.
- **Own `Op` type, not `internal/change`'s**: per instruction, this
  package does not import or wait on `internal/change`'s Op tagged union
  (being built concurrently). Field/type names were derived independently
  from `docs/data-model.md` §3's Core Types table (Bond/Bridge/VlanIface
  field lists) and the op vocabulary table, not from any assumption about
  what T-201 will land with. **The integrator needs to reconcile**: T-201's
  Op likely wraps `params` as a single polymorphic blob per op; this
  package's `DecodeOp`/`DecodeOps` already speak that exact wire envelope,
  so the cheapest integration path is probably "T-201's store keeps
  `ops_json` around and calls `ifaces.DecodeOps` for the iface/bond/bridge/
  vlan ops it needs to hand to this package", rather than converting
  in-memory types.
- **Fields not explicitly listed in docs/data-model.md**: the op vocabulary
  table only names op types, not full param schemas. I added `Autostart`
  and `Comments` to every Create/Update op (not just `iface.update`, where
  the doc explicitly lists them) since every entity in practice needs an
  auto-line and a comment convention; also added `MIIMon` (default 100,
  matching the corpus convention) to bond ops, and a `Bridge` field to
  `BondCreate` for OVS bonds (the `ovs_bridge` option an OVS bond stanza
  needs). Flagging in case T-201's frozen schema differs.
- **`iface.update`'s target ambiguity**: interfaces(5) allows multiple
  stanzas per name (one per address family — see corpus file 09). This
  package's `Mutate` always resolves a target name to the *first* matching
  `KindIface` entry (`findIface`). Multi-family patch semantics (e.g.
  editing the `inet6` stanza specifically) are not modeled; flagging as a
  gap if T-207's dual-stack editor needs it — the fix would be adding a
  `Family` discriminator to `IfaceUpdate.Target` or a new field.
  Family/method choice for new stanzas is always plain `inet` for `bond.create/bridge.create/vlan.create` (dual-stack IPv6 creation is a documented gap, matching v1 scope elsewhere in the codebase — see `docs/features/change-management.md` §5's "Renaming NICs is out of scope v1" precedent for this kind of v1 scoping call).
- **Unified diff is not byte-identical to GNU `diff -u`**: it's a
  stdlib-only LCS-based line differ (no third-party dependency, per
  `docs/development.md`'s "prefer stdlib") producing the same
  `---`/`+++`/`@@ -l,c +l,c @@` structure with 3 lines of context, but does
  not emit the `\ No newline at end of file` marker line — a missing
  trailing newline is just rendered with one added. Good enough for a
  diff-review UI; flagging in case a future task wants literal `diff -u`
  parity.
- **"Inventory-level effect" in the property test**: there is no existing
  `internal/inventory.FromInterfaces`-style adapter (only
  `FromNetlinkLinks`/`FromPVENetwork`, which ingest netlink/PVE-API shapes,
  not this package's raw AST) to route the property test through the real
  ingestion pipeline. Building one was out of scope for this task (it would
  mean writing new `internal/inventory` code). The property test instead
  re-parses the rendered bytes from scratch and checks the same
  entity-level facts (`bond-slaves`, `bridge-ports`, `vlan-raw-device`,
  `mtu`, autostart wiring) that adapter would read — a faithful proxy,
  but flagging the gap in case a stronger end-to-end check (through actual
  `internal/inventory.Bond`/`Bridge`/`VlanIface` construction) is wanted
  later.
- **`GET /changesets/{id}/diff` is not wired into `internal/api/router.go`**:
  by design (see "Exported surface" above) — there is no changeset
  store/route to wire it into yet in this worktree. `NewDiffHandler` is
  ready; wiring is the integrator's job at merge time.
- **`make check`'s web steps do not run in this worktree**: `web/node_modules`
  isn't installed (pre-existing condition, not caused by this task — I
  did not touch anything under `web/`), so `make test`'s vitest step and
  `make lint`'s eslint/tsc step fail with "not found" errors unrelated to
  this change. All Go-side steps of `make check` (gofmt, `go vet ./...`,
  `golangci-lint run ./...`, `go test ./...`, `govulncheck ./...`) pass
  clean, repo-wide.
- **No hardware validation needed**: this task only manipulates an
  in-memory AST and reads fixture/mock data; nothing here touches a live
  PVE host or `ifreload`.
