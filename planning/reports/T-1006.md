## What was built

**`internal/fwlog/analytics.go`** (new): `Analyze(entries []StreamEntry, snap fw.Snapshot, now time.Time,
window time.Duration, topN int) Analytics` aggregates a `RingBuffer.Snapshot()` into:

- `HitCounts []RuleHitCount` — per-`RuleRef` hit count + last-seen timestamp within `window`.
- `TopBlocked{Sources, Destinations}` — top-N addresses among DROP/REJECT-actioned lines within
  `window`, counted regardless of correlation status (an ambiguous/unmatched DROP line still names a
  real blocked address).
- `UnusedRules []UnusedRule` — every enabled rule reachable in a known guest's current resolved view
  (`LiveRuleRefs`, iterating `snap.Guests`) with zero hits within `window`; `DaysSinceLastHit` is `-1`
  (never fabricated as 0 or the window length) when the rule has no observed hit anywhere in the
  currently-retained buffer.

**Design decision on rule identity across a move** (flagged per CLAUDE.md, since the task card's
"REUSE `Correlation.rule`'s `RuleRef` — no new correlation logic" reads, at first glance, as "use
each entry's own *cached* `Correlation`" — which is unsatisfiable together with the card's other
requirement, "so a moved/renumbered rule's history follows it by identity, not position": `RuleRef`'s
only fields are `{guestRef, origin, groupName, pos}` (docs/api.md's already-fixed shape), so a rule's
cached `Correlation.Rule.Pos` from *before* a `fw.rule.move` can never equal its `Pos` *after* the
move — there is no way to bridge the two from the stored value alone. The implementation instead
**re-invokes `Correlate`** (the existing, unmodified function) fresh against the *current* resolved
ruleset for every buffered entry, rather than trusting each entry's ingestion-time-cached
`Correlation`. Since an entry's own `direction`/`action`/`proto`/`dport` never change after the fact,
re-resolving after a move finds the *same* conceptual rule at its *new* position with its hit count
intact. This reuses `Correlate` verbatim (no new matching logic, no new heuristic) — it is simply
invoked a second time, at query time, exactly the same way `Service.Tick` already invokes it once at
ingestion time. `TestAnalyze_RuleIdentityFollowsAMove` (analytics_test.go) proves this directly:
resolves the same buffered entry against a before/after snapshot pair simulating a `fw.rule.move`
and confirms the hit count follows the rule to its new `Pos`.

**`(*fwlog.Service).Analytics(now, window, topN) Analytics`**: wraps `Analyze` with the Service's own
buffer + `cfg.Snapshot.FirewallSnapshot()` (the same live-graph seam ingestion-time correlation
already uses) — no new dependency wiring beyond what T-505 already built.

**`GET /firewall/analytics?scope=&ref=&windowHours=`** (`internal/api/fwlog.go`): `windowHours`
defaults to 24 and governs `hitCounts`/`topBlocked`/`unusedRules` uniformly (matching AC1's "a rule
with zero matches over the window ... a rule that matched within the window does not" — one window,
not three independent ones). `scope=guest&ref=<guest ref>` narrows `hitCounts`/`unusedRules` to that
guest (post-filtering `Analyze`'s already-computed result, documented as leaving `topBlocked`
cluster-wide — a blocked address isn't a per-guest concept the way a rule is). `ref` required when
`scope=guest` (400 otherwise); invalid `windowHours` is 400.

**`fw_rule_unused` finding** (`internal/findings/health_fwruleunused.go`, new): `source: "health"`
(the existing enum value — **confirmed no new `Source` constant was added**; `SourceHealth` is reused
verbatim), `check: "fw_rule_unused"`, `severity: "info"`, `fixable: false`, one finding per
`fwlog.UnusedRule` from `svc.Analytics(now, DefaultFwRuleUnusedWindow /* 30d */, fwlog.DefaultTopN)`.
Hysteresis-exempt (a 30-day-smoothed signal has nothing left to debounce; clears the very next cycle
per AC3). `Refs` names the guest ref (map-linkable); the finding's own **id** deviates from the
standard `health:<check>|<refs-or-nodes>` scheme (documented in docs/api.md) since more than one
unused rule can share a guest — it is `health:fw_rule_unused|<guestRef>|<origin>|<pos>[|<groupName>]`,
the rule's full identity. `DocsLink` is a `/firewall?scope=guest&ref=...&pos=...&origin=...` deep
link into the rule editor at the exact rule row — not a docs page, the same documented deviation
`sim_divergence` (T-806) already established, extended here because a docs page can't name a specific
rule. Wired into `findings.Engine` via a new `FwAnalyticsProvider` interface (mirrors
`MgmtProvider`/`CorosyncProvider`'s shape exactly) and a lazily-set `fwAnalyticsAdapter` in
`cmd/vnproxd/findings.go` (same pattern as `mgmtStatusAdapter`, needed because `findings.Engine` is
built before `*fwlog.Service` exists in `server.go`'s startup order — `fwAnalyticsAdapterVal.set(fwlogSvc)`
right after `setupFwlog` runs).

**Frontend** (`web/src/fwlog/`): `AnalyticsTab.tsx` — a hit-count table, two recharts horizontal bar
charts (top blocked sources/destinations, single-hue magnitude encoding per the dataviz skill's form
heuristic — no categorical palette needed for a one-series chart), and an unused-rule list, each rule
identity rendered through the *existing* `ruleDeepLinkPath` (web/src/fwlog/deeplink.ts, unchanged) —
the same `scope/ref/pos/origin/group` contract T-504's simulator and T-505's log viewer already
established, so "edit rule" lands on the exact row via `FirewallPage.tsx`/`ResolvedViewTable.tsx`'s
existing `data-focused` highlight with zero new consuming-side code. `FwLogViewer.tsx` gained a
`Log`/`Analytics` tab pair (`role="tab"`/`"tabpanel"`, mirroring `SdnPage.tsx`'s established
hand-rolled tab pattern); `Log` stays the default active tab, so every pre-existing
`FwLogViewer.test.tsx` assertion (which never selects a tab) keeps passing unchanged.
