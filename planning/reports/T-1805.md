# T-1805 · Unattended revert for `fw.*` and `sdn.apply` via apply-time revert ticket — completion report

**Branch:** `worktree-agent-a0c35f67fdb4fbe28` (isolated worktree; not pushed, not merged — orchestrator to review and merge).
**Decision implemented:** `docs/roadmap-proven.md` **D1** — capture a revert ticket at apply time. No alternative design was substituted; nothing about D1 turned out to be technically blocked.

---

## 1. What was built

### The hole, precisely

`planning/reports/T-502.md` deviation #1 flagged it and no card owned it since. PVE firewall and
SDN writes go out under the *user's own* PVE ticket (`docs/architecture.md` §6) — that is what
makes vnprox unable to exceed a user's PVE ACLs, and it is also why, once the HTTP request that
started an apply has ended, there is **no credential left with which to undo them**. Node-file
changes are different: `NodeAgent` writes `/etc/network/interfaces` and execs `ifreload` as root,
so the daemon can restore them with no user context. The asymmetry meant:

- a `fw.*`-only changeset that reached `awaiting_confirm` and then timed out was **never** reverted;
- neither was one whose daemon was killed mid-window;
- and — found while reading the code, worse than the card assumed — `fw.*` had **no restore on any
  path at all** beyond same-request executor rollback. `doRollbackLocked` handled SDN, QoS,
  WireGuard and switch ports; it had no firewall branch, so even a *manual* `POST
  /changesets/{id}/rollback` with a perfectly live session left the firewall change in place. A
  sealed ticket alone would therefore have closed nothing.

### Backend

**Schema (migration 33)** — `internal/store/migrations/0033_changeset_revert_ticket.sql`:
`changesets.revert_ticket_enc BLOB` (sealed, nullable) and `changesets.revert_ticket_expires_at
INTEGER` (nullable). Additive and forward-only; an existing row migrates to "no sealed ticket",
which is exactly the pre-T-1805 behaviour. `internal/store/kv_test.go`'s schema-version assertion
is bumped to `33`.

**Store (`internal/store/changesets.go`)** — the ciphertext is deliberately kept **out of**
`store.Changeset`. Three dedicated accessors are its entire surface: `SealRevertTicket`,
`RevertTicket`, `WipeRevertTicket`, plus `WipeExpiredRevertTickets` for the expiry sweep.
`Insert`/`Update`/`Upsert` do not name the column, so an ordinary changeset persist can neither
clobber a live ticket nor resurrect a wiped one (asserted). Only the **expiry** — a bound, not a
secret — joins the row struct, because the operator-facing coverage report is computed from it.

**Change engine (`internal/change/reverticket.go`, new)** — `RevertTicket`, the
`RevertTicketSource` PVEGateway extension, the `RevertGatewayFactory` seam, `SecretUnsealer`, the
`UnattendedRevert` coverage type, and the four operations: `sealRevertTicket` (apply time),
`revertGatewayFor` (the one unseal site), `wipeRevertTicket`, `SweepExpiredRevertTickets`.

**Firewall pre-state made restorable** — `fwStateSnapshotPath`
(`/var/lib/vnprox/firewall.state`) joins the existing SDN/QoS/WireGuard/switch synthetic snapshot
files in the pre-apply snapshot row, holding each touched ruleset's
`SnapshotFirewallScope` pre-image. `Plan.hasFw()`, `Service.restoreFwState`, and a new firewall
branch in `doRollbackLocked` are what the sealed ticket is actually *spent on*. The executor's own
`fwPre` cache is now seeded from that snapshot instead of re-reading each scope from PVE.

**Lifecycle wiring (`internal/change/apply.go`)**:

| Point | Behaviour |
|---|---|
| `Apply`, after the pre-snapshot, **before the first mutating step** | seal the ticket; compute `UnattendedRevert` |
| `finishAwaitingConfirm` | attach the coverage report to the response, audit the coverage decision, warn-log a partial window |
| `Confirm` | wipe, inside the same lock hold as the status transition |
| `Rollback` (manual) / `autoRollback` (timeout) → `doRollbackLocked` | if no live gateway and the plan needs one, unseal; restore SDN **and firewall**; wipe unconditionally, even when the persist failed |
| `finishFailedApply` | wipe |
| `recoverInterruptedApply` (crash during `applying`) | unseal, restore SDN + firewall, wipe |
| `Discard` (`DELETE /changesets/{id}`) | wipe, unconditionally |
| `ArmPendingRollbacks` (startup) | `SweepExpiredRevertTickets` first, then re-arm |

**PVE client (`internal/pve`)** — `Config.Ticket`/`Config.CSRFToken` build a **sealed-ticket
client**: it authenticates with exactly the ticket it was handed and **never renews and never logs
in** (`ticketAuth.sealed`). `Client.RevertCredentials` is the single, narrowly documented accessor
that yields a ticket for sealing; it returns `ok=false` for any non-ticket client, so the daemon's
read-only `vnprox@pve!daemon` API token can never be substituted. `pve.TicketLifetime` (2h) is the
basis for the sealed ticket's expiry.

**API** — `changesetResponse.unattendedRevert` (`{required, available, coversUntil, fullWindow,
reason}`), present on the apply response and on `GET /changesets/{id}` for an `awaiting_confirm`
changeset, omitted otherwise.

**Wiring (`cmd/vnproxd`)** — `pveGateway.RevertTicket` (the ticket source), `revertGatewayFactory`
(builds the sealed-ticket client), and `revertTLSConfig` factored out of `setupAuth` so the revert
client makes the *same* TLS trust decision as the login client whose ticket it reuses.

### Frontend

- `web/src/changesets/revertCoverage.ts` (new, pure, framework-free): `opNeedsRevertTicket` /
  `changesetNeedsRevertTicket` / `revertTicketOpFamilies` (mirroring `Plan.needsRevertTicket`),
  `preApplyRevertNotice` (the review dialog's statement) and `revertCoverageBanner` (the in-window
  statement, read verbatim from the server's report).
- `ReviewApplyScreen.tsx`: a notice, recomputed as the operator changes the confirm window, saying
  plainly which parts of the changeset depend on their Proxmox login, for how long, what is kept
  and when it is deleted, and what happens if the session expires first. It says nothing at all for
  a changeset whose revert needs no ticket.
- `CountdownBanner.tsx`: the server's real coverage line during the window — full coverage, a
  live countdown to the reduced-coverage cut-off, or a prominent "will NOT undo itself".
- `web/src/api/types.ts`: the `UnattendedRevert` type.

### Docs

`docs/architecture.md` §4 (a new bullet on what the unattended rollback can actually revert) and §6
(the D1 reasoning, including the two rejected alternatives and why); `docs/security.md` (a new
"Apply-time revert ticket" credential-class note, an amendment to the "one privileged internal
identity" paragraph, and a threat-model row); `docs/api.md` (the `unattendedRevert` contract, plus
an amendment to T-402's stale "a rollback with no live session skips the SDN portion" paragraph);
`docs/data-model.md` §2 (the two columns and a full paragraph on the write/read isolation and wipe
guarantees); `docs/features/change-management.md` §4 (the operator-facing version).
`planning/reports/needs-hardware-validation.md` gains a T-1805 section (6 items).

Two load-bearing stale code comments were corrected rather than left to mislead: `PVEGateway`'s
"IMPORTANT, flagged limitation" doc block (now a credential note describing the closed gap and what
it means for an implementer) and `RestoreFirewallScope`'s "same-request rollback only".

## 2. Safety analysis — every claim, mapped to its test

### Claim 1 — "The ticket is a credential at rest and is treated as one."

Sealed with the existing `store.SessionCipher` (AES-256-GCM), keyed from
`/etc/vnprox/keys/session.key` — the identical primitive and key `sessions.pve_ticket_enc` and
`clusters.credential_enc` use. **No second cipher and no second key pair was introduced**; the
change engine reuses its existing `Config.Sealer` and type-asserts it to `SecretUnsealer` rather
than taking a second cipher field, precisely so a mis-wiring cannot produce two.

| Test | What it proves |
|---|---|
| `store.TestChangesetRepo_RevertTicketEncryptedAtRest` | The direct counterpart of `TestWireGuardRepo_PrivateKeyEncryptedAtRest`, same shape: the plaintext ticket (and a fragment of it) is absent from the stored column **and from the raw SQLite file's bytes** (after a WAL truncate checkpoint), and only the cipher recovers it. |
| `change_test.TestRevertTicket_AC3_NeverLeaksToAnySurface` | Table-driven, one case per surface, against a real ticket really at rest: the sealed ciphertext, the `Apply` response, the `GET /changesets/{id}` model, the `GET /changesets` list model, the audit log, the **daemon log** (a real `slog` JSON handler captured for the whole apply+seal path), every raw WS `changeset.status` broadcast, and the raw DB file. Both the ticket and the CSRF token are checked. Includes a positive control that the cipher round-trips the exact credential, so the absences are about encryption rather than the value never having existed. |
| `api.TestRevertTicket_AC5_ReadModelHasNoFieldForTheCredential` | Reflection over `change.Changeset`, `api.changesetResponse`, `store.Changeset`: the sealed ticket has **no field** anywhere in the read model. This is stronger than the `presharedKey`/`redactOpSecrets` precedent the card cites — there is nothing to strip, so `GET /changesets` cannot carry it by construction. |
| `store.TestChangesetRepo_OrdinaryUpdateNeverTouchesTheRevertTicket` | An ordinary changeset persist neither clobbers a live ticket nor resurrects a wiped one — the invariant that lets the rest of the engine persist freely. |

### Claim 2 — "Its lifetime is bounded from both ends."

| Test | What it proves |
|---|---|
| `change_test.TestRevertTicket_AC4_WipedOnEveryTerminalPath` | The card's four cases as four subtests — **confirm**, **manual rollback**, **confirm-window expiry**, **changeset deletion (`DELETE /changesets/{id}` → `Discard`)** — each asserted **directly against the stored row** (`ChangesetRepo.RevertTicket`, bypassing every service layer): zero ticket bytes and a NULL expiry. Each subtest first asserts the precondition that a ticket *was* there. |
| `change_test.TestRevertTicket_AC4_WipedWhenTheApplyItselfFails` | The fifth exit implied by "whichever comes first": an apply that never reaches the window still sealed a ticket (it is sealed before the first mutating step) and so still wipes. |
| `change_test.TestRevertTicket_AC4_ExpiredTicketIsSweptAndRefused` | Two subtests: the startup sweep clears a ticket whose PVE session expired, and the revert path itself **refuses** an expired ticket (never unsealing it into a gateway) and wipes it on the way out. |
| `store.TestChangesetRepo_WipeRevertTicket` | The wipe is idempotent and never errors for an unknown changeset — it must never be the reason a terminal transition fails. |
| `store.TestChangesetRepo_WipeExpiredRevertTickets` | Only tickets at or past expiry are cleared; a live one is untouched. |

The wipe is not best-effort in the code either: in `doRollbackLocked` it runs unconditionally
*before* the persist error is returned, so a failed persist cannot leave a credential behind.

## 4. The `sdn.apply` determination, with evidence

**`sdn.apply` gets the same treatment. It was never a credential-independent exclusion.**

The card asked me to check T-502's observation that `sdn.apply`'s step "is already excluded from
`rollbackAfterFailure`'s node iteration for reasons that may be independent of credential
availability", and not to assume the answer. Investigated:

1. `rollbackAfterFailure` (`internal/change/apply_exec.go`) iterates `e.plan.affectedNodes()` and
   calls `undoNode` per node. `affectedNodes()` collects `Step.Node` from every step; `BuildPlan`
   emits `StepSDNStage` and `StepSDNApply` with **no `Node` field** because they are cluster-scope
   PVE API calls, not per-node file operations. The exclusion from the *node* iteration is
   therefore purely a scope mismatch — `undoNode` restores an interfaces file, which SDN does not
   have — and is entirely independent of credentials.
2. SDN was never actually excluded from that function's rollback: the same function's **first
   statement** is `if e.hasSDNPre && e.anySDNStepSucceeded() { … e.svc.restoreSDN(…) }`. SDN has
   its own cluster-scoped restore path and always has.
3. The only thing missing was a credential on the unattended path: `restoreSDN`'s own doc comment
   recorded that `pveGW == nil` (the auto-rollback timer) was reported as a failed-but-non-fatal
   rollback entry, and `doRollbackLocked` already called it under `plan.hasSDN()`.

So for SDN the sealed ticket is sufficient on its own — `Plan.needsRevertTicket()` is
`hasFw() || hasSDN()`, and `doRollbackLocked` now unseals when it has no live gateway. `restoreSDN`
reverts the staged config *and* re-runs `ApplySDN`, so the running config converges back too; that
re-apply is precisely the `sdn.apply` revert. `TestRevertTicket_AC7_SDNChangesetRevertsOnConfirmTimeout`
applies `sdn.zone.create` + `sdn.apply` against pvemock, lets the window elapse with no session, and
asserts the zone is gone and the ticket wiped.

`fw.*` was the harder half, and the reason is worth recording for whoever reviews this: the
firewall pre-image lived **only in the executor's memory** (`e.fwPre`), so even with a credential
there was nothing durable to restore from. Persisting it (`fwStateSnapshotPath`) and adding the
`doRollbackLocked` branch was necessary, not scope creep — see deviation D1 below.

## 7. Deviations from the task card, with reasons

**D1 — I added firewall restore to `doRollbackLocked`, not only a credential.** The card frames the
work as "seal a ticket and revert with it". In fact `fw.*` had no restore in `doRollbackLocked` at
all, and its pre-image existed only in executor memory, so a sealed ticket would have had nothing
to spend itself on and AC1 would have been unachievable. This card therefore also adds
`fwStateSnapshotPath` to the pre-apply snapshot, `Plan.hasFw()`, `Service.restoreFwState`, and the
`doRollbackLocked` branch. Side effect worth noting for the reviewer: **manual** `POST
/changesets/{id}/rollback` of a firewall changeset now works too, which it never did.

**D2 — The ticket is sealed at the start of `Apply`, not at `finishAwaitingConfirm`.** Sealing
before the first mutating step means a daemon killed *during* the apply (`recoverInterruptedApply`)
also finds the credential, not only one killed during the window. The cost is that a failed apply
briefly has a sealed ticket — handled by wiping in `finishFailedApply`, tested.

**D3 — Coverage is `fw.*` + all `sdn.*`, not `fw.*` + `sdn.apply` alone.** The `sdn.zone/vnet/subnet`
stage ops share `restoreSDN` with `sdn.apply` and are ticket-scoped for the identical reason;
covering them costs nothing and excluding them would have been arbitrary.

**D4 — `ipam.alloc.*` is deliberately NOT claimed.** `Plan.needsRevertTicket()` excludes
`StepIpamAlloc`. `doRollbackLocked` has never reverted IPAM allocations on any path (only the
same-request executor rollback does, which always holds a live gateway), so reporting
`unattendedRevert.required` for an IPAM-only changeset would promise coverage that does not exist.
This is a **pre-existing gap this card does not close**, flagged here rather than papered over. It
is small (a leaked reservation, not a lockout) and is a natural candidate for T-2002's
flagged-follow-up burndown.

**D5 — `GET /changesets` (the list) does not carry `unattendedRevert`; `GET /changesets/{id}`
does.** Computing it per row would mean a `BuildPlan` per changeset on every list call for a field
only meaningful in one status. The card's requirement ("apply responses carry whether unattended
revert is available … and until when") is met, and the single-changeset read carries it so the
statement survives a page reload.

**D6 — The card says `GET /changesets` "strips the sealed field entirely (`redactOpSecrets`'
precedent)". I implemented something stronger: structural absence.** The ciphertext has no field on
`store.Changeset`, `change.Changeset`, or `changesetResponse`, so there is nothing to strip and no
future handler can accidentally reintroduce it. Asserted by reflection
(`TestRevertTicket_AC5_ReadModelHasNoFieldForTheCredential`).

**D7 — "Changeset deletion" is `DELETE /changesets/{id}` → `Discard`.** There is no row-delete for
changesets anywhere in the store (retention prunes snapshots and blobs, never changesets), so
`Discard` is the deletion the API exposes. The wipe there is unconditional rather than gated on a
state check — a discardable changeset is a draft and should never hold a ticket, which is exactly
why the wipe should not depend on that continuing to be true.

**D8 — The sealed ticket is not replicated to an HA standby.** `ChangesetRepo.Upsert` (T-1704's
replication path) does not carry the column. Replicating a live user credential to a second host to
buy coverage across a mid-window failover is a materially worse trade than the status quo it would
improve on; an HA failover mid-window leaves the firewall/SDN portion exactly where it was before
this card (node files still revert). Stated in `docs/security.md` and `docs/data-model.md` as a
residual, not hidden.

**D9 — No new dependency.** No third-party package was added, in Go or npm.

## 8. Needs hardware validation

Added as a new `## T-1805` section in `planning/reports/needs-hardware-validation.md` (6 items).
The two that most affect whether the operator-facing promise is exactly true:

- **PVE ticket lifetime near the boundary.** `pve.TicketLifetime` is the documented 2h and the
  whole `coversUntil` report derives from it. If real PVE rejects a ticket for a *mutating* call
  before the nominal 2h, `coversUntil` over-promises by that margin.
- **`RestoreFirewallScope`'s delete-all-then-recreate against a live `pve-firewall`.** The scope
  restore replays the whole ruleset; if real `pve-firewall` compiles and applies the intermediate
  empty state, the restore needs reordering or bracketing. pvemock does not model a compile loop.

The rest: a sealed ticket working from a fresh client with no cookie jar; the end-to-end
firewall-only lockout healing on iron (this is T-1804 scenario 5 and the card's real acceptance
test); the same after a kill/restart and a hard reset; and reduced-coverage reporting matching the
