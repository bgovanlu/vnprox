# T-1502 — Kubernetes overlay map layer & service-flow attribution UX

## What I built

A ninth client-only map layer ("Kubernetes"), flow-explorer attribution, and a "why is this pod
unreachable" drilldown panel — entirely on top of T-1501's already-shipped read surface
(`GET /k8s/clusters`, `GET /k8s/{clusterId}/overlay`). No backend routes were added; this is
frontend + read wiring, exactly as scoped.

### `web/src/topology/layers/` (new directory, as the card names)

- **`k8sOverlay.ts`** — `computeK8sOverlay(overlay)`: a pure `K8sOverlay -> {nodes, edges}`
  transform, mirroring `web/src/wireguard/wgTunnelEdges.ts`'s exact shape. Three synthetic node
  kinds per registered cluster: `k8s-pod-cidr` (one region per k8s node's advertised pod-network
  block — the "pod/service CIDR regions" the card names), `k8s-pod` (one per pod —
  `internal/k8s/overlay.go`'s own doc comment says `PodSummary` exists specifically "for T-1502's
  pod-drilldown selection"), and `k8s-service` (one per service with a `ClusterIP`; a headless
  service produces no node — nothing to anchor to). Synthetic ids reuse
  `internal/k8s/resolver.go`'s own `k8s-svc:`/`k8s-pod:`/`k8s-podnet:` ref-string format verbatim,
  so a map node id and a flow-attribution ref are always the identical string for the same entity.
  A matched k8s node's entities anchor into their correlated PVE guest's own node column and draw
  a `k8s-correlation` edge from the guest to its pod-CIDR region (the "node<->guest correlation
  lines" deliverable); an unmatched node's entities render in the cluster-spanning band instead of
  guessing a column — never a wrong placement.
- **`k8sUnderlay.ts`** — `computePodUnderlayChain`: the underlay half of the drilldown, an ordered
  walk (guest -> guest-nic -> bridge -> bond) over the real topology graph's `attached-to`/
  `port-of`/`enslaved-by` edges (the same edge-kind vocabulary `projection.ts`'s
  `computeHoverHighlight` already reads — a new small purpose-built ordered walk, since
  `computeHoverHighlight` returns an unordered highlight *set*, not a hop list, and its helpers
  aren't exported). One path per guest NIC; an unrendered/unmatched guest produces an empty array,
  never a guessed hop.
- **`k8sFlowAttribution.ts`** — the Flow Explorer's `k8sService` column. **Deliberately not a wire
  field on `flow.Record`**: unlike T-1504's `serviceClass` (genuinely backend-computed, needs live
  inventory data the frontend doesn't have), k8s attribution is a display-time join between two
  routes the frontend already has open (`GET /flows`, `GET /k8s/{clusterId}/overlay`) — so it's a
  TypeScript port of `internal/k8s.K8sResolver.Resolve`'s exact match precedence (exact Service
  ClusterIP, then exact Pod IP, then pod-CIDR containment, else no attribution), the same
  "kept in sync by hand" convention this codebase already uses for other mirrored backend
  algorithms (e.g. `wgEdgeStatus.ts`'s handshake-staleness threshold). Attribution is display-only
  and never filters a row.
- **`PodDrilldown.tsx`** — the "why is this pod unreachable" panel, mirroring
  `FlowPairPanel.tsx`'s floating-panel convention (bottom-center, since top-right/bottom-right are
  already claimed by `FlowPairPanel`/`InspectorStack`). Selecting a pod or pod-CIDR region shows
  the pod's k8s-side facts plus the full underlay chain; selecting a service shows its
  type/ClusterIP/ports and, when present, the `k8s_nodeport_exposed_without_fw_rule` finding's own
  detail text (a service isn't pinned to one node, so it has no underlay chain of its own).
- **`k8sQueries.ts`** — `useK8sClustersQuery`/`useK8sOverlaysQuery` (TanStack Query, mirroring
  `wgTunnelsQuery.ts`), fanning `GET /k8s/{clusterId}/overlay` out across every registered cluster.

## A regression found and fixed along the way (not part of this task's own surface, but blocking a
sibling spec)

While verifying this task doesn't break other specs, `flows.spec.ts` started failing
non-deterministically (sometimes at the client-side navigation to `/flows`, sometimes at the
canvas-pixel-paint assertion — different failure points across runs, consistent with a timing
race, not a logic bug). Bisection (isolating each hunk of my `TopologyPage.tsx` diff) traced it to
`k8sQueries.ts`'s `useK8sOverlaysQuery`: it built its `overlays` return value with a fresh `[]` +
loop **every render**, so `useQueries`' already-fresh-per-render array identity propagated a new
array reference downstream even when the Kubernetes layer was off and nothing had actually
changed. That defeated every `useMemo` in the chain (`k8sOverlay` -> `extraNodes`/`extraEdges` ->
`elements`), forcing a fresh object identity into the v2 canvas/elk-layout pipeline on *every*
render — exactly the pitfall `web/src/guests/queries.ts`'s `useAllGuestNicsQuery` already
documents and avoids ("`useQueries` returns fresh array instances... keying off its serialized
data instead avoids an infinite recompute loop"). Fixed by memoizing `overlays` on a stable
fingerprint (`dataUpdatedAt`/presence per result) instead of rebuilding it unconditionally. After
the fix: `flows.spec.ts` passed 3/3 consecutive full runs (previously failed 3/3), and
`k8s-overlay.spec.ts` still passes. This is a real lesson worth flagging for any future task that
adds a `useQueries`-based hook to a component in this render pipeline.

## Deviations from the task card

- **No wire-level `k8sService` field on `flow.Record`/`GET /flows`.** The card's wording ("Flow
  explorer gains a `k8sService` column populated via T-1501's `K8sResolver`") is satisfiable two
  ways: a new backend field (T-1504's `serviceClass` precedent), or a client-side port of
  `K8sResolver`'s own algorithm composed against data the frontend already fetches. I chose the
  latter — no backend route/field changed, keeping this task's surface strictly frontend + read
  wiring as instructed, and following the exact precedent this codebase already has for
  "mirrored backend algorithm, kept in sync by hand" (`wgEdgeStatus.ts`). If a future task wants
  `k8sService` to be part of the documented `GET /flows`/`GET /history/events` wire contract (e.g.
  for `internal/apicontract`'s golden fixtures, or a non-JS consumer), that's a small, isolated
  backend addition on top of this — `K8sResolver` already exists and already mirrors
  `GraphResolver`'s shape for exactly this purpose.
- **`web/src/topology/layers/` did not previously exist** (WireGuard/Flows/Latency/MTU overlays
  live directly under `web/src/wireguard/`/`web/src/topology/`) — the task card names this path
  explicitly ("web/src/topology/layers/, following the existing layer-toggle convention"), so I
  created it fresh as this task's own contribution; nothing else was moved into it.
- **`cmd/k8smock` and the `internal/k8smock.NewHandler` refactor are new, e2e-only additions**,
  not named in the card. Flagged as the resolution to "prove UI acceptance criteria with... the
  `web/e2e` Playwright harness" — a genuine e2e spec needs a real, externally-reachable mock k8s
  server; `internal/k8smock`'s existing `httptest`-based `NewServer` can't be reached from outside
  the Go test process it runs in. No new third-party dependency; `NewHandler`'s extraction is a
  zero-behavior-change refactor (verified: `go test ./internal/k8smock/... ./internal/k8s/...
  ./internal/api/...` all still pass).
- **Fixed two pre-existing `golangci-lint` fieldalignment findings** (`internal/change/ifaces/op.go`,
  `internal/findings/engine.go`) unrelated to this task's own surface — inherited from the `main`
  branch this worktree fast-forwarded onto (other Phase 15 tasks' merged structs), blocking
  `make lint`/`make check`. Mechanical, behavior-preserving field reordering via
  `golang.org/x/tools/go/analysis/passes/fieldalignment`'s own `-fix` mode; `go test` for both
  packages re-verified green after.
