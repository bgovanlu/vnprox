# T-208 · Raw interfaces editor — report

## What was built

### Backend (`internal/change`, `internal/change/ifaces`, `internal/api`)

- **New op `iface.raw.replace`** in both `internal/change` (op.go,
  `IfaceRawReplaceParams{Content, BaseHash}` in params_iface.go) and
  `internal/change/ifaces` (op.go's `IfaceRawReplace{Target, Content}`).
  Target is a `inventory.KindNode` ref (`node:<n>:<n>`) — the op replaces
  a whole file, not one entity, so it reuses the existing `node` Kind
  rather than inventing a new one.
- **`ifaces.Mutate`'s `IfaceRawReplace` case** (mutate.go) doesn't AST-edit
  in place like every other op — it re-parses `Content` into a fresh
  `host.File` and swaps `f.Entries` wholesale. Because `host.File.Render()`
  reproduces an unmutated parse byte-for-byte, this means
  `DiffChangeset`'s existing parse→`MutateAll`→`Render`→`UnifiedDiff`
  pipeline and `apply_exec.go`'s `computeStagedFile` both handle the new
  op with **zero special-casing** — the full-file diff and the staged
  file are just `Content`, byte-identical.
- **`apply_plan.go`**: `OpIfaceRawReplace` added to `nodeFileOpTypes`, so
  `BuildPlan` stages+reloads it exactly like `iface.update`/etc.
- **Validation — "reuse T-202 pipeline on the parsed entity delta"**
  (`internal/change/validate_raw.go`, new file):
  `expandRawReplace(target, before, after)` parses both the live file and
  the new content through `internal/inventory.FromInterfaces` (declared-
  only entities on both sides, so the comparison never mixes in runtime-
  only netlink/PVE-API fields) and diffs them by `Ref` into synthesized
  `bond.create/update/delete`, `bridge.create/update/delete` (+
  `bridge.port.add/remove` for port-membership changes),
  `vlan.create/update/delete`, and `iface.update` (physnic MTU only —
  physnics have no create/delete op) ops. Those synthesized ops are fed
  into the *existing* `ValidateWithSafety` pipeline unmodified, so e.g. a
  raw edit that deletes the management bridge's stanza produces the exact
  same `safety.protected_interface`/`safety.guest_bearing_bridge` findings
  a `bridge.delete` op would — **AC2, verified by
  `TestService_Create_RawReplace_DeletesManagementBridge_BlockedBySafety`**.
  `rawReplaceExclusiveFindings` rejects mixing a raw op with any other
  node-file op targeting the same node in one changeset (ambiguous net
  effect otherwise) — runs on the ops *as received*, before expansion, so
  it doesn't trip on its own synthesized ops.
- **`internal/change/raw_service.go`** (new): `Service.ReadRawInterfaces`
  (live file + sha256, the editor's "open" call), `Service.validate` (the
  new single entry point Create/UpdateDraft/Validate call — expands raw
  ops, runs `ValidateWithSafety`, merges findings) and
  `Service.expandRawReplaceOps` (the hash-conflict guard: compares
  `BaseHash` against the live file's current hash, producing a blocking
  `raw.hash_conflict` finding on mismatch instead of silently clobbering
  an intervening edit — **AC3**). `LintRawInterfaces` (pure
  `host.ParseInterfaces` wrapper → line-precise `LintMarker`) backs the
  live-lint endpoint.
- **New finding codes** (`validate_codes.go`): `raw.parse_error`,
  `raw.hash_conflict`, `raw.not_exclusive_with_other_ops` — a small class
  outside the schema/referential/safety/advisory pipeline, since they
  concern the raw op/file itself rather than a decoded per-entity op.
- **New API routes** (`internal/api/changesets.go`): `GET
  /nodes/{node}/interfaces/raw` → `{node, content, sha256}`; `POST
  /interfaces/lint` → `{content}` → `{errors: [{line, message}]}`. Both
  mounted in the existing `netRead` changesets route group (lint needs no
  CSRF — it mutates nothing server-side).
- **Docs**: `docs/api.md` gains a "Raw interfaces editor (T-208)" section;
  `docs/data-model.md` §3's op table gains `iface.raw.replace` next to
  `iface.update`.

### Frontend (`web/src/changesets/rawEditor/`, `web/src/pages/ToolsPage.tsx`)

- **`interfacesLanguage.ts`**: a Monarch grammar for interfaces(5)
  (comments, `auto`/`allow-*`/`iface`/other reserved keywords, address
  families/methods, common `bridge-`/`bond-`/`ovs_` options, CIDR/IPv6
  addresses) plus `registerInterfacesLanguage`, typed against a minimal
  `MonacoLanguagesLike` subset so the grammar and its registration are
  unit-testable without importing Monaco at all.
- **`MonacoRawEditor.tsx`** (default export, the `React.lazy` target): the
  one module that imports `monaco-editor` — specifically
  `monaco-editor/esm/vs/editor/editor.api.js` (the standalone editor core)
  rather than the package root (`editor.main`, which eagerly bundles every
  built-in language's full contribution: CSS/HTML/JSON/TypeScript language
  *services* plus ~80 basic-language grammars). Imperatively creates one
  `monaco.editor` instance, pushes `value`/`markers`/`readOnly` in via
  effects (never recreating the editor on every render, so cursor/undo
  history survive prop updates), disposes on unmount.
- **`useRawEditor.ts`**: the DOM-free state machine — load
  (`GET .../raw`), debounce-then-lint (`POST /interfaces/lint`, 250ms),
  save (builds the op, calls the existing `useDrawerActions().addOps` —
  the raw editor is "another editing surface" through the *same*
  accumulation path every entity editor uses, not a bespoke write path),
  and reload (the hash-conflict banner's action). Inspects the saved
  changeset's findings for the hash-conflict code (dedicated banner +
  reload button) and for *any other* error-severity finding regardless of
  which `ref` it landed on (`rawEditorOps.errorFindings`) — necessary
  because T-203's safety interlock attributes its findings to the
  *synthesized* delta op (e.g. `bridge:pve1:vmbr0`), not to the raw op's
  own `node:pve1:pve1` ref.
- **`RawEditorPanel.tsx`**: the chrome — syntax-error count, Save button
  (capability-gated + tooltip), hash-conflict banner with a Reload button,
  blocking-findings list, success banner, `<Suspense>`-wrapped lazy Monaco.
- **`ToolsPage.tsx`**: replaced the placeholder with a node picker (same
  `nodeGroup`-derivation pattern `TopologyPage`'s `NewEntityMenu` uses) +
  `RawEditorPanel`.
- **`web/src/build/bundleSplit.test.ts`** (AC4): runs a real `vite build`
  into a scratch temp dir (never the tracked `web/dist`) and asserts a
  separate `MonacoRawEditor-*.js` chunk exists, is substantial (>500KB —
  proof it's the real editor, not a stub), and that Monaco's own runtime
  marker string (`MonacoEnvironment`) appears in that chunk but **not** in
  the main `index-*.js` entry chunk — a content-based proof the split
  actually happened, not just a plausibly-named file existing.
- **New dependency**: `monaco-editor` (already present in `package.json`/
  `package-lock.json` before this task and explicitly listed in
  `docs/development.md`'s approved-components table as "Editor | Monaco
  (raw interfaces editor, lazy-loaded)" — this task wires it up but adds
  no new package). `web/node_modules` was not installed in this worktree
  (per T-204/T-207's reports); `npm ci` was run to populate it.

## Deviations from the task card / things to flag

- **`GET /nodes/{node}/interfaces/raw` and `POST /interfaces/lint` are new
  routes not previously in `docs/api.md`.** The card requires the raw
  editor to open against *some* live-file source and to lint client
  content; no prior task exposed either. I added both, documented them in
  `docs/api.md`, and kept them capability-gated (`netRead`) alongside the
  existing changeset read routes for consistency.
- **`iface.raw.replace` targets a `KindNode` ref**, not a new dedicated
  Kind — reusing the existing `node` entity Kind (rather than inventing
  e.g. a `KindInterfacesFile`) since the op's target really is "this
  node's whole file" and `internal/inventory`'s `Ref` vocabulary already
  has a Kind for the node itself. Flagging in case a future task wants a
  more specific Kind for file-level targets generally.
- **Exclusive-op-per-node schema check
  (`raw.not_exclusive_with_other_ops`)** is not explicitly required by the
  card, but I added it: mixing a raw-replace op with an AST-level edit of
  the *same* node's file in one changeset is genuinely ambiguous (the raw
  op discards the whole tree; ordering would silently decide which
  "wins"). A raw op alongside ops on *other* nodes is unaffected. This
  runs against the ops the caller submits, before expansion adds the raw
  op's own synthesized delta for that same node (which would otherwise
  trip the check against itself) — see `validate_raw.go`'s
  `rawReplaceExclusiveFindings` doc comment for the full reasoning.
- **`errorFindings` (web) deliberately does not filter by ref** — a real
  correctness fix made mid-implementation. My first pass only checked
  findings whose `ref` matched the raw op's own `node:<n>:<n>` target,
  which silently missed every T-203 safety finding (those are attributed
  to the *synthesized* delta op's ref, e.g. a bridge). Caught while
  writing `useRawEditor.test.ts`'s AC2 coverage; fixed before considering
  the AC done. Flagging since it's the one place a shallow reading of "op
  X's findings" would have quietly broken AC2's actual UI requirement.
- **No new Playwright e2e spec for T-208.** T-207 added a full
  `changesets.spec.ts` walkthrough for its ACs; I did not add an
  equivalent for the raw editor (open → lint → save → hash-conflict →
  reload against a real pvemock-backed daemon). All three of the card's
  behavioral ACs (1–3) are covered at the unit level on both the Go
  service and the React hook, which is where the actual logic lives — the
  UI chrome (`RawEditorPanel`/`MonacoRawEditor`) is thin glue over that
  logic. **Needs hardware/e2e validation**: the real Monaco editor
  mounted in a browser (markers rendering, typing latency), and the full
  open→edit→save→countdown→apply round trip against a live pvemock
  daemon (mirrors T-207's own flagged gap for "successful apply →
  countdown → confirm").
- **Monaco's core chunk is ~2.5MB minified** even after switching to the
  minimal `editor.api` subpath import — this is Monaco's own editor
  engine (text model, view layer, standalone services), not further
  splittable without dropping Monaco itself; flagging as an inherent cost
  of the card's explicit choice of Monaco, not a regression to chase.
- **`internal/change/ifaces` and `internal/change`'s own `OpIfaceRawReplace`
  constants are independently declared** (same pattern T-204's report
  flagged for the rest of the op vocabulary) — `apply_exec.go`'s existing
  `changeOpsToIfaces` adapter (marshal `change.Op` → JSON → `ifaces.DecodeOps`)
  already bridges them with no changes needed, since both packages' wire
  field names (`content`) agree.
- **No hardware validation needed for the parts that were tested**: the
  Go-side raw-replace/expansion/hash-guard logic only manipulates
  in-memory ASTs and fixture/mock node agents; nothing here touches a
  live PVE host or `ifreload`.

  `web/src/pages/ToolsPage.tsx` + `web/src/api/rawInterfaces.ts` — no
  other T-207 file was touched beyond `web/src/api/types.ts` (additive:
  one `OpType` union member, one params interface, one `OpParams` union
  member) and `web/src/pages/ToolsPage.tsx` (full replacement of the
  placeholder body).
- If a future task wants the raw editor reachable from the map/inspector
  (rather than only the Tools page), `RawEditorPanel` already takes a
  single `node: string` prop and needs no other wiring — it could be
  mounted anywhere a node name is known.
- `internal/change/validate_raw.go`'s entity-delta diff only compares the
  fields each op's params struct actually carries (Mode/Slaves/MTU for
  bonds; Ports/VlanAware/STP/Vids/Addresses/Gateway/MTU/Comments for
  bridges; Addresses/MTU for VLANs; MTU only for physnics) — it does not
  attempt to detect every conceivable interfaces(5) option a raw edit
  might change (e.g. bond `xmitHashPolicy`/`lacpRate` changes *are*
  covered; something entirely outside the modeled op vocabulary, like a
  custom `pre-up` script line, is not and would not by itself trigger any
  finding). This mirrors the existing op vocabulary's own scope, not a
  new gap this task introduced.
