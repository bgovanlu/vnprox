## 1. What was built

### `internal/blueprint` (new package) — format, instantiation engine, capture, starters

- **`types.go`/`validate.go`**: the versioned Blueprint JSON format
  (`blueprintVersion: 1`, `Params []ParamDef`, `Entities []EntityTemplate`
  with `{{param}}` placeholders and a per-blueprint/per-entity
  `NodeSelector{mode: "all"|"single"}`), plus structural validation (known
  entity kinds, known param types, every `{{token}}` referencing a
  declared param or the builtin `{{__nodes__}}`) and param-value validation
  (CIDR/IP/VID/VID-list/node-list type checks — T-603 AC4's "bad CIDR/VID
  rejected").
- **`substitute.go`/`params.go`/`expand.go`**: placeholder substitution
  (whole-value substitution preserves the param's JSON type; partial
  matches like `"{{zone}}/{{name}}"` produce a string), param resolution
  (defaults, required-param checks), and node-selector expansion into
  concrete `(Ref, Kind, Fields)` tuples.
- **`adapters.go`**: per-kind (bridge/bond/vlan/sdn-zone/sdn-vnet/sdn-subnet)
  create/diff logic — the idempotency core (AC1/AC2): an expanded entity
  absent from `inventory.Snapshot` becomes a `*.create` op; present and
  matching becomes no op; present and divergent becomes an update op naming
  only the diverging fields. Bridge port-membership divergence is the one
  special case, emitting `bridge.port.add`/`bridge.port.remove` ops instead
  of a `bridge.update` (mirroring `BridgeUpdateParams`' own doc comment:
  port membership isn't one of its fields anywhere else in this codebase
  either).
- **`instantiate.go`**: `Instantiate(bp, req, snap) ([]change.Op, error)` —
  the whole pipeline (validate → resolve params → expand → diff), a pure
  function that never touches the store or the change engine; the caller
  hands the result to `change.Service.Create` (same "compute an op patch,
  let the normal changeset lifecycle own it" pattern `internal/drift`'s
  `FixOps` established for T-305).
- **`capture.go`**: `Capture(snap, node)` — "blueprint-ify" a node's live
  bonds/bridges/VLAN interfaces into an unsaved Blueprint, turning every
  declared address into a named, `addressSuggest`-eligible CIDR param
  (names/ports/slaves/VIDs stay literal). SDN entities are deliberately not
  captured (they're cluster-scoped, not per-node — nothing for a per-node
  capture to own).
- **`suggest.go`**: `SuggestAddress`/`SuggestForParam` — next-free-host-address
  computation directly off `inventory.Snapshot`'s already-declared
  addresses (see §3 below for why this doesn't go through `internal/ipam`).
- **`starters.go`**: the five bundled read-only starters as Go literals
  (round-trip through the same JSON (un)marshaling every other Blueprint
  does; asserted against `Validate` in `starters_test.go`).
- **`service.go`**: `Service` — List (starters + saved rows)/Get/Save
  (rejects overwriting a starter id, mints a ULID for a new blueprint)/
  Delete (rejects a starter id)/Capture/Instantiate/SuggestAddress; the
  seam `internal/api` depends on.

### `internal/store` — persistence

`blueprints.go` + `migrations/0004_blueprints.sql`: a `blueprints` table
(id/name/blueprint_json/created_by/created_at/updated_at). Only
user-authored/captured/copied-from-starter blueprints are rows; the five
starters are compiled into the binary, never persisted (CLAUDE.md's
app-owned-data rule: a blueprint is a template a user wrote, not a shadow
copy of PVE config).

### `internal/api` — routes

`blueprints.go` implements docs/api.md's documented `GET/POST /blueprints`
and `POST /blueprints/{id}/instantiate`, plus four additive routes
documented retroactively in `docs/api.md` per docs/development.md's
definition-of-done #4 (the same convention T-302/T-303/T-305/T-306 used):
`GET /blueprints/{id}` (detail/export), `DELETE /blueprints/{id}`,
`POST /blueprints/capture`, `GET /blueprints/{id}/suggest?param=`. Gating
mirrors `changesets.go`/`drift.go`: reads need `netRead`, writes need
`netWrite` + CSRF; instantiate only ever creates a *draft* changeset
through the existing `ChangesetService.Create` seam, never applies
anything. Wired into `cmd/vnproxd/server.go` sharing the daemon's one live
`*inventory.Graph` (never a separate copy).

### `web/src/blueprints` — UI

- `paramValidation.ts` (+ tests): framework-free CIDR/IP/VID/vidList/
  nodeList input validation mirroring the backend's own rules (AC4).
- `preview.ts` (+ tests): builds a `{nodes, edges}` preview graph from a
  blueprint's entities (bridge "ports"/bond "slaves"/vlan "parent"/sdn
  "zone"/"vnet" references become edges); `BlueprintPreviewDiagram.tsx`
  renders it as a simple layered box-and-line diagram.
- `ParamForm.tsx` (+ Testing-Library tests): one input per param, inline
  validation errors, and a "Suggest" button on `addressSuggest` params
  calling `GET /blueprints/{id}/suggest`.
- `queries.ts`: TanStack Query hooks for list/get/save/delete/capture/
  instantiate/suggest.
- `BlueprintsPage.tsx`: list (starters + saved) → detail (preview + param
  form) → Instantiate (opens the resulting draft in the existing changeset
  drawer, same as `DriftFindingsPanel`'s "Create fixing changeset" flow) →
  Import (file picker, always creates a new saved blueprint)/Export
  (downloads the `GET /blueprints/{id}` JSON as a file)/Capture-from-node/
  Delete. Wired into `App.tsx`'s routes and `NavRail.tsx` as `/blueprints`.
- `docs/api.md`/`docs/data-model.md` updated with the Blueprint JSON shape
  and the additive routes.

## 3. Deviations from the task card, with reasons

**IPAM dependency (T-405) doesn't exist on this branch's base.** The task
card says "IPAM-aware address suggestions via the IPAM picker" / "T-405's
picker". On `main` as of this branch, `internal/ipam` is an empty stub
(`doc.go` only) and `web/src/pages/IpamPage.tsx` is a placeholder — T-405
depends on T-401 and hasn't landed (confirmed by reading both files before
starting; this isn't a guess). AC4 ("address params get next-free
suggestions") is a hard requirement regardless, so `suggest.go` computes
next-free-address directly off `inventory.Snapshot`'s already-declared
bridge/VLAN addresses and SDN subnet gateways — no subnet-utilization
tracking, no PVE IPAM-plugin bridge, no picker UI component. **Follow-up
for whoever picks up T-405**: once the real IPAM subnet/allocation service
and its picker component exist, `blueprint.SuggestAddress`/`SuggestForParam`
should be replaced (or reimplemented on top of) that service, and
`ParamForm.tsx`'s inline "Suggest" button should become a proper picker
launch — the param form's validation logic (`paramValidation.ts`) doesn't
need to change either way.

**T-401/T-402's actual state differs from the task brief, in vnprox's favor.**
The brief said T-401 (SDN read) and T-402 (SDN ops/apply) were unmerged,
in-progress work in other worktrees. I verified directly against this
branch's base (not the orchestrator's brief) before deciding what the SDN
starters could do, and found:

- `internal/inventory` **already has** full `SdnZone`/`SdnVnet`/`SdnSubnet`
  entity types and `FromPVESDN` ingestion, and `internal/collect` already
  wires PVE SDN polling into the live graph (`internal/collect/pve.go`'s
  `pollSDN`, asserted by its own `golden_test.go`). T-401's inventory-read
  work is done on `main`.
- `internal/change` **already has** the full `sdn.zone/vnet/subnet.*` op
  vocabulary and referential/schema validators (op.go, params_sdn.go,
  validate_referential.go, validate_schema.go). What's *not* done yet
  (confirmed via `apply_exec.go`/`apply_plan.go`: only `sdn.apply` is an
  executable step; individual `sdn.zone/vnet/subnet.*` ops are refused at
  apply with `422 unsupported_op`, per `web/src/changesets/planPreview.ts`'s
  own `unsupportedOps` handling) is **apply execution** of those ops
  against real PVE — which is T-402's job and is genuinely out of scope for
  this task (T-603 only needs to produce a valid, idempotent *draft*).

Net effect: **four of the five starters (single-NIC homelab, dual-NIC
mgmt+trunk, LACP-bond+storage-VLAN, VXLAN overlay) are fully complete** —
idempotent create/skip/update against real inventory state, no caveats.
Applying an instantiated VXLAN-overlay draft end-to-end will 422 today
until T-402 lands apply execution for `sdn.zone/vnet/subnet.*` ops, exactly
like every other SDN-write drafting path in this codebase already does —
this is a pre-existing, already-surfaced limitation of the change engine in
general, not something T-603 introduces or needs to work around.

**The EVPN datacenter starter is partial** — this is the one real gap, and
it is *not* about T-401/T-402's status. PVE's EVPN zone type references a
controller (BGP ASN/peers) by string ID (`SdnZoneCreateParams.Controller`),
but **no `sdn.controller.create` op exists anywhere in this codebase's op
vocabulary** (`internal/change/op.go` has no controller op at all, on any
branch) — creating an EVPN controller itself has never been implemented as
a changeset operation. The starter therefore creates the zone/vnet/subnet
assuming a controller with the given id already exists (hand-configured in
PVE, or via a future controller wizard) and cannot provision one from
scratch. **Follow-up, precisely scoped**: add an `sdn.controller.create/
update/delete` op family (params, validators, inventory read-model for
`SdnController` — none of that exists yet either) — this is squarely
T-403's territory (SDN zone wizards) per `planning/implementation-plan.md`,
not a blueprint-engine gap. Once that op exists, the EVPN starter just
needs one more `EntityTemplate` (`kind: "sdn-controller"`) and its own
adapter in `internal/blueprint/adapters.go` — no engine changes needed.

**"iface" entity kind not implemented.** The generic engine supports six
kinds (bridge/bond/vlan/sdn-zone/sdn-vnet/sdn-subnet); I did not add a
seventh for bare-physnic `iface.update` (mtu/comments/autostart). No
starter needs it (`internal/inventory.PhysNic` has no `Addresses` field at
all in this codebase's model — physical NICs don't carry IP addresses;
only bridges/VLAN ifaces do), and it isn't required by any acceptance
criterion. Flagging in case a future starter wants bare-NIC MTU management.

**No dedicated JSON-file starter assets.** The five starters are Go
literals in `starters.go` rather than embedded `.json` files. They
round-trip through exactly the same `encoding/json` (un)marshaling as
every saved/imported blueprint (nothing in `Validate`/`Instantiate`
distinguishes a literal-built `*Blueprint` from a decoded one), and
`starters_test.go` asserts every one passes `Validate` — a typo fails the
test suite, not a user's instantiate call. This is a smaller footprint
than `embed.FS` wiring for five small, static templates; happy to switch
to embedded JSON files if a future task wants starters editable without a
rebuild.

**No new third-party dependencies.** Everything above uses only stdlib +
already-approved deps (`encoding/json`, `net`, `oklog/ulid` via
`store.NewULID`, `modernc.org/sqlite` via the existing store package,
`@tanstack/react-query`/Tailwind/clsx on the frontend — all already in
`docs/development.md`'s locked stack).

## 5. Anything the next agent must know

- The blueprint instantiation engine assumes entity templates are listed
  in dependency order (a bond before a bridge that ports it, a zone before
  its vnet before its subnet) — the change engine's own referential
  validator folds a changeset's ops forward in list order
  (`internal/change/validate_referential.go`), the same convention
  `web/src/changesets/dragDropOps.ts` already relies on. There's no
  automatic topological sort; if a future starter or a user-authored
  blueprint gets this wrong, the resulting changeset will carry a
  `codeParentNotFound`/`codeZoneNotFound` finding at validate time (not a
  silent wrong result).
- `internal/blueprint.Instantiate`/`Capture`/`SuggestAddress` are all pure
  functions of an `inventory.Snapshot` — no I/O, no locking concerns,
  trivially testable without pvemock. `Service` is the only piece that
  touches the store.
- The EVPN starter's `controller` param currently has no create path
  anywhere in the codebase (see §3) — don't be surprised if a future SDN
  task expects to find `sdn.controller.create` already defined; it isn't.
- `internal/store`'s pinned schema-version test
  (`kv_test.go`'s `TestKVRepo_SchemaVersionIsPresentAfterOpen`) now expects
  `"4"` (bumped from `"3"` for the new `0004_blueprints.sql` migration) —
  the next task adding a migration needs to bump it again.
