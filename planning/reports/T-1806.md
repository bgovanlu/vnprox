# T-1806 — Trustworthy CI and branch protection

## Summary

`CI` failed on every one of the last 30 recorded runs (`gh run list --workflow=ci.yml --limit 30`
→ 30/30 `failure`, independent of the diff) — `check` and `fuzz` were both deterministically red,
not flaky. Root-caused and fixed both, replaced the permanent `npm audit` red X with an expiring,
argued allowlist, closed a `golangci-lint` concurrency hazard found mid-card, fixed one genuine
intermittent test flake found by repeated local measurement, and filed a new, larger finding
(the Playwright e2e suite has never been run by anything) as a bug card. Branch protection (AC4)
is written up as exact `gh` commands for a human to run; I have no repo-admin access to apply it
myself.

## What I built

### 1. `fuzz` job: anchored `-fuzz` patterns (`.github/workflows/ci.yml`)

`go test -fuzz=<pattern>` matches **every** fuzz target in the package under test whose name
matches `<pattern>` as an **unanchored** regexp, and refuses to fuzz at all if more than one
matches. `internal/host` alone has five fuzz targets (`FuzzParse`, `FuzzParseBGPSummary`,
`FuzzParseEVPNVNI`, `FuzzParseLLDP`, `FuzzParseDHCPLeases`); the job's `-fuzz=FuzzParse` matched
all five, so every invocation printed `will not fuzz, -fuzz matches more than one fuzz test` and
failed — 100% reproducible, on every push, regardless of the diff. That is the actual reason
"fuzz fails independent of the diff": not flakiness, a static/deterministic bug in the CI
invocation itself.

Fix: every step now anchors its pattern (`-fuzz='^FuzzParse$'`, etc.), including the two steps
(`FuzzPeerAuth`, `FuzzParseAll`) whose package currently has only one fuzz target — so a future
sibling target added to `internal/peer` or `internal/fwlog` can't silently reintroduce this.
Verified locally: each of the 7 anchored invocations runs cleanly in isolation
(`go test -run='^$' -fuzz='^Fuzz...$' -fuzztime=1-3s ./internal/...`).

### 2. `npm audit`: expiring allowlist, not a permanent red X

`web/audit-allowlist.json` + `web/scripts/auditAllowlist.mjs` (pure logic) +
`web/scripts/check-audit-allowlist.mjs` (CLI, called from `make check`). Behavior:

- Extracts every **high/critical root** advisory from `npm audit --json` (a root advisory is one
  a package is named in directly, not a bare string reference from a package that merely depends
  on a vulnerable one — npm's report nests both shapes under `vulnerabilities`).
- A high/critical advisory **not** in `web/audit-allowlist.json` still fails the build (this is
  the part that keeps it a gate, not a mute — proven by a dedicated unit test:
  `"fails on an advisory that isn't in the allowlist at all"`).
- An allowlisted advisory whose `expires` date has passed **also** fails the build, with the
  boundary case (`expires` == today → still passes) covered explicitly.
- Each entry is `{id, package, rationale, expires}`. The four rationales are specific to vnprox's
  own usage, not boilerplate — e.g. dompurify's `CUSTOM_ELEMENT_HANDLING` bypass is inert here
  because vnprox never configures DOMPurify's custom-element allow-list; react-router's CSRF
  advisory only affects RSC mode, and vnprox is a client-only Vite SPA with no SSR/RSC. Starting
  inventory (per the card): `brace-expansion` (GHSA-mh99-v99m-4gvg), `postcss`
  (GHSA-r28c-9q8g-f849), `dompurify` via `monaco-editor` (GHSA-c2j3-45gr-mqc4), `react-router`
  (GHSA-qwww-vcr4-c8h2). All four expire 2026-10-30 (~3 months out).
- Tested: 16 unit tests in `web/scripts/auditAllowlist.test.mjs` (parsing/validation, advisory
  extraction, evaluate() including the expired-entry and expires-today cases) plus an end-to-end
  manual check: setting `brace-expansion`'s `expires` to `2020-01-01` and running
  `node scripts/check-audit-allowlist.mjs` against the real lockfile reproduces the failure
  (`exit 1`, "allowlist entry expired 2020-01-01"); restoring it passes (`exit 0`).
- Note: `dompurify`'s advisory is currently `low` severity in this lockfile's actual `npm audit`
  output (not `high`), so it doesn't presently trigger the high/critical gate at all — the script
  warns (non-fatally) that this allowlist entry is "stale" (npm audit no longer reports it at
  high+). Left in per the card's explicit starting inventory; harmless if unused, and the
  rationale still holds if its severity is ever reclassified upward.

### 3. `golangci-lint` concurrency hazard (found mid-card, not in the original brief)

`golangci-lint` acquires a file lock on start and, by default, **hard-errors**
("parallel golangci-lint is running") if a second instance starts while the first holds it,
rather than waiting. This repo's own orchestration convention runs concurrent tasks in separate
git worktrees, each running its own `make check` — a sanctioned pattern that collides with this
lock every time two such runs overlap in wall-clock time, independent of either task's diff. This
surfaced as a real collision between two sibling agents' worktrees during this card's own
measurement (see Testing below), not as a bug in the code under test.

Fix: `make lint`/`make check` now pass `--allow-serial-runners` to both the local-binary and
`go run ...@version` golangci-lint invocations, so a second concurrent run **waits for the lock**
instead of failing. Verified: launched two `golangci-lint run --allow-serial-runners ./...`
invocations against this repo at the same time; both exited 0 (the second's start was simply
delayed).

### 4. A genuine intermittent test flake, found and fixed

`web/src/sdn/wizards/SubnetStep.test.tsx`'s "refines an auto-filled gateway to the live
allocation grid's free address..." test asserted `last?.gateway === "10.60.0.3"` inside a
`waitFor`, then checked the gateway `<input>`'s DOM value with a **bare, synchronous** `expect`
immediately after. `last` is a plain JS variable the test harness's `onChange` callback assigns
synchronously; the DOM only reflects that same `onChange` once React commits the harness's
`setValue` re-render. Under full-suite CPU contention (many vitest worker threads running
concurrently), the commit can lag a tick behind the variable assignment, so the DOM check
occasionally observes the stale value. In 20 isolated single-file runs it never failed (no
contention → no observable race window); it failed once in 10 full-`make check` runs under real
contention, which is exactly the signature of this class of bug. Fix: fold both assertions into
the same retried `waitFor` (see the diff) so a slow-to-commit DOM state simply gets re-polled
instead of asserted on once. I swept the sibling `SimpleZoneWizard`/`VlanZoneWizard`/
`QinqZoneWizard`/`VxlanZoneWizard`/`EvpnZoneWizard` wizard tests for the same
capture-then-synchronous-DOM-check shape; none of their other `waitFor` usages share it (they
either assert only on the DOM inside the `waitFor`, or on a stub's own recorded state that isn't
fed back into the DOM at all).

## A new finding: the Playwright e2e suite has never been run by anything

Filed as **T-1806-bug-01** in `planning/tasks/phase-18.md` (full writeup there). Short version:

- `web/e2e/` holds **31** spec files (not 32 — see note below), cited by **14** task cards and
  **43** implementation reports as acceptance evidence.
- **Zero** CI jobs and **no** `make` target invoke Playwright — grepped `ci.yml`,
  `packaging-matrix.yml`, `release.yml`, and `Makefile`; no hits. It only runs via
  `npm run e2e`, by hand.
- I characterized (did not fix — out of this card's scope, and explicitly not requested): in a
  quiet environment (verified nothing on the harness's ports, no stray backend processes), the
  harness itself works. `npm run build` succeeds; Playwright's `webServer` array boots all eight
  mock-PVE/vnproxd/k8smock backend pairs it defines (confirmed via distinct listening ports in
  the server logs) regardless of which single spec is targeted — running even one spec pays the
  full fleet's startup cost. Two representative specs, run individually against this worktree's
  base commit (`0029eb9`, pre-T-1805/T-1907): `dashboard.spec.ts` (2 passed, 33.7s) and
  `mgmt-redundancy.spec.ts` (2 passed, 33.2s).
- **This does not contradict** a separate finding (relayed to me: a sibling task's controlled A/B
  test found `mgmt-redundancy.spec.ts` failing on a clean checkout of current `main`) — `main` has
  since merged T-1805 and T-1907 past this worktree's branch point, either of which could plausibly
  explain a regression this stale commit wouldn't show. Both facts together are the real
  characterization: the harness mechanics work, but the suite is unenforced, unreproduced by CI,
  and has at least one concretely reported failure against current `main` that no CI gate ever had
  a chance to catch.
- **Spec-file count note:** I count 31 `*.spec.ts` files on this worktree's branch point
  (`0029eb9`); T-1907 (physical-layer collapse), merged to `main` after that point, plausibly adds
  a 32nd, which would reconcile the discrepancy with the "32" figure I was given.
- Recommendation written into the bug card (not implemented): e2e doesn't belong in `make check`
  (Chromium + 8 backend stacks + specs already exceeding `ci.yml`'s <10min budget); a dedicated
  required job or — given the suite has never once been verified in aggregate — a nightly first to
  establish a baseline, promoting to required once that baseline is credible. Either way, fix
  `mgmt-redundancy.spec.ts` against current `main` first.

## AC4 — branch protection (requires repo-admin action)

`main` currently has no branch protection (`gh api repos/bgovanlu/vnprox/branches/main/protection`
→ 404). A repo admin needs to run:

```sh
gh api --method PUT repos/bgovanlu/vnprox/branches/main/protection \
  --input - <<'EOF'
{
  "required_status_checks": {
    "strict": true,
    "contexts": ["check", "cross-arm64", "fuzz", "package"]
  },
  "enforce_admins": true,
  "required_pull_request_reviews": {
    "required_approving_review_count": 1
  },
  "restrictions": null,
  "allow_force_pushes": false,
  "allow_deletions": false
}
EOF
```

Verify afterward with `gh api repos/bgovanlu/vnprox/branches/main/protection` (expect `200`, not
`404`). Full context and rationale for each field is in `docs/development.md`'s new "Branch
protection on `main`" section. Adjust `required_approving_review_count` to the team's actual
review process (1 is a floor).
