# T-201 · Changeset model, store, draft API — completion report

## What was built

### `internal/change` (new package contents)

- **`op.go` / `params_*.go`** — `Op`, the tagged union `{"op","target","params"}`
  covering the full documented v1 vocabulary (docs/data-model.md §3):
  39 op types across `iface`(1)/`bond`(3)/`bridge`(5)/`vlan`(3)/`sdn`(10,
  incl. `sdn.apply`)/`guest`(1)/`fw`(14)/`ipam`(2). Each op has a typed
  params struct (`params_iface.go`, `params_bond.go`, `params_bridge.go`,
  `params_vlan.go`, `params_sdn.go`, `params_guest.go`, `params_fw.go`,
  `params_ipam.go`, plus `params_common.go` for the shared `VidRange`).
  `Op.Target` is encoded on the wire as a `"kind:node:id"` string (reusing
  `inventory.Ref.String()`/`ParseRef`), matching the Ref-as-string
  convention already used throughout `internal/topology`'s JSON types,
  rather than a nested object — flagged as a documentation-interpretation
  decision below.
  - Strict JSON (de)serialization: `Op.UnmarshalJSON` uses its own
    `json.Decoder` with `DisallowUnknownFields()` at both the envelope
    level and the params level, validates the op type against the known
    vocabulary, and requires a target for every op except `sdn.apply` (the
    one op with no natural target entity). All decode failures are a typed
    `*OpDecodeError{Path, Message}` carrying the offending JSON path (e.g.
    `"op"`, `"target"`, `"params.mtuu"`).
  - `paramFactories` is a closed registry from `OpType` to a params
    constructor; `op_test.go` asserts it exactly matches the documented
    vocabulary (no op without a factory, no factory for an undocumented
    type).

- **`changeset.go`** — the `Changeset` aggregate and its `Status` state
  machine (`draft|validated|applying|awaiting_confirm|committed|
  rolled_back|failed|discarded`), plus the `Finding`/`Severity` wire types
  (docs/api.md's finding shape) that T-202 will populate. `allowedTransitions`
  is a full (from,to) adjacency table; `Transition`/`CanTransition` are the
  only way to move a `Changeset` between statuses, and illegal transitions
  return a typed `*ErrIllegalTransition` rather than mutating silently.
  Only `draft`/`validated` are ever mutable or discardable (`Editable()`);
  the four terminal statuses (`committed`/`rolled_back`/`failed`/
  `discarded`) have no outgoing edges at all — draft CRUD (and, later,
  T-205) can never resurrect a historical record.
  - **Decision flagged for review**: manual rollback of an already-`committed`
    changeset (docs/features/change-management.md §4: "offered for 7 days
    ... creates a new restoring changeset via the normal flow") is modeled
    as *not* a transition of the committed changeset's own `Status` — it's
    T-205's job to create a brand-new `Changeset` that goes through this
    same table from `draft`. If T-205 intends something different (e.g.
    marking the original `rolled_back` too), that's a one-line change to
    `allowedTransitions`.

- **`service.go`** — `Service`: draft CRUD (`Create`, `Get`, `List`,
  `UpdateDraft`, `Discard`) on top of **T-003's existing**
  `*store.ChangesetRepo` and `*store.AuditRepo` — see "Deviation" below,
  no new migration was added. WS `changeset.status` events fire on every
  *actual* status transition (initial `draft` on create, `validated ->
  draft` on editing a validated draft, `-> discarded` on discard) via the
  `Broadcaster` interface (`Broadcast(topic string, payload []byte)`),
  satisfied by `topology.Service.Broadcast` (new, see below). Audit
  entries (`changeset.create`, `changeset.discard`) go through the same
  `*store.AuditRepo` pattern `internal/auth` uses.

- **`errors.go`** — `*OpDecodeError`, `*ErrIllegalTransition`.

### `internal/api`

- **`changesets.go`** (new) — `mountChangesetsRoutes` registers every
  documented changesets route:
  - Real: `GET /changesets?status=`, `POST /changesets`,
    `GET /changesets/{id}`, `PUT /changesets/{id}`, `DELETE /changesets/{id}`.
  - Stubbed 501 (per the task's explicit instruction): `POST
    /changesets/{id}/validate`, `GET /changesets/{id}/diff`, `POST
    /changesets/{id}/apply`, `POST /changesets/{id}/confirm`, `POST
    /changesets/{id}/rollback` — these exist at the right path/method now
    so T-202/T-205 (and T-207's frontend) can code against the real shape
    immediately; they return `{"error":{"code":"not_implemented",...}}`
    with HTTP 501.
  - Capability gating: GET routes require `netRead`; every mutating route
    requires `netWrite` (T-201 acceptance criterion 3) and, when the
    `AuthService` backend also implements the new `CSRFEnforcer` interface
    (satisfied by `*auth.Service` via `cmd/vnproxd`'s existing adapter, no
    changes needed there beyond wiring), the CSRF middleware too.
  - `*change.OpDecodeError` → `400 validation_failed` with
    `{"details":{"path":...}}`; `store.ErrNotFound` → `404 not_found`;
    `*change.ErrIllegalTransition` → `409 invalid_transition` (a new but
    stable error code, since docs/api.md's code list is explicitly
    non-exhaustive — `"validation_failed", "pve_denied",
    "changeset_locked", "peer_unreachable", ..."`).
- **`router.go`** — added `Options.Changesets ChangesetService` and one
  line mounting the new routes (same nil-safe pattern as
  `Topology`/`Layouts`).

### `cmd/vnproxd/server.go`

Wires a real `change.Service` into the router: `store.NewChangesetRepo(db)`

## Deviation from the task card (and why)

The card's deliverable list says "a new sqlite migration + repo for
changesets (following T-003's existing migration/repo pattern)". **T-003
already built this** — `internal/store/migrations/0001_init.sql` already
has the exact `changesets` table from docs/data-model.md §2, and
`internal/store/changesets.go` already has a full `ChangesetRepo`
(Insert/Get/List/Update) with its own round-trip tests
(`changesets_test.go`). This task's dependency graph
(`T-201 depends on T-003`) already accounts for this — T-003's own task
card explicitly scopes "repository types **per table** ... in the data
model doc" — so I built directly on top of the existing repo rather than
adding a redundant migration or a second repo type. No new
`internal/store/migrations/NNNN_*.sql` file was added.

## What was tested and how

- `internal/change/op_test.go`: every one of the 39 documented op types
  round-trips JSON (marshal → unmarshal → re-marshal equality), both as a
  lone `Op` and inside a `[]Op` slice (the actual on-disk shape). Negative
  cases: unknown op type, unknown envelope field, unknown params field,
  missing target (denied for a normal op, allowed for `sdn.apply`),
  malformed target ref, missing op type — each asserts the exact `Path` on
  the returned `*OpDecodeError`. A vocabulary-size assertion
  (`TestOpVocabulary_SizeMatchesDataModelDoc`, hand-counted against the
  doc's table = 39) and a factory-completeness assertion
  (`TestKnownOpTypes_MatchesVocabulary`) guard against silent vocabulary
  drift.
- `internal/change/changeset_test.go`: the full 8×8 = 64-cell
  `(from,to)` transition table is exhaustively checked against an
  independently-hand-written expectation (not derived from the
  implementation, so it actually catches a bug in either), covering T-201
  acceptance criterion 2. Also asserts denied transitions never mutate the
  changeset, and that all four terminal statuses have zero outgoing edges.
- `internal/change/service_test.go`: `Service` CRUD against a real
  temp-file SQLite DB (`store.Open`) — create/get/list/update/discard,
  status-machine interaction (editing a validated draft reverts it to
  draft and broadcasts; editing/discarding a non-editable changeset
  returns `*ErrIllegalTransition`), audit-entry content, WS broadcast
  counts (including the "no broadcast on a same-status edit" negative
  case), and two different authors' drafts coexisting in `List` (T-201
  acceptance criterion 4, at the service layer).
- `internal/api/changesets_test.go`: full HTTP-level integration tests via
  `httptest` + a real `change.Service` (temp SQLite) + a capability-aware
  `fakeAuthWithCaps` test double (extends the existing `fakeAuth`/
  `fakeAuthWithUser` doubles from `topology_test.go`/`layouts_test.go`):
  unauthenticated → 401, missing `netWrite` on create → 403 (while
  `netRead`-only can still list/get) — acceptance criterion 3 — missing/
  present CSRF header, create→get→list round trip, 400 on both an unknown
  op type and an unknown param field with the exact `details.path`,
  update-draft replacing ops, discard→409-on-second-discard, **two
  different authenticated users' drafts coexisting and both appearing in

- `internal/topology`: existing `hub_test.go`/`service_test.go` suites

## Anything the next agent must know

- **T-202 (validators)**: `change.Finding`/`change.Severity` are already
  defined in `changeset.go` with the exact docs/api.md wire shape
  (`severity/code/message/ref?/fix?`, `fix` being `[]Op`) — populate
  `Changeset.Findings` and don't redefine the type. The `POST
  /changesets/{id}/validate` route is registered in
  `internal/api/changesets.go`'s `mountChangesetsRoutes` pointing at
  `handleChangesetNotImplemented()`; swap that one line for a real
  handler backed by a new method on `ChangesetService` (you'll need to
  extend that interface in `internal/api/changesets.go`, not touch
  `router.go` again). `Op`/`Params` are ready to validate against directly
  — every param field you need for schema checks (ranges, enums) is
  already typed and decoded by the time a `Changeset` reaches you.
- **T-205 (apply engine)**: the status machine already encodes the
  legal transitions you'll drive through (`draft/validated -> applying ->
  awaiting_confirm -> committed/rolled_back`, or `applying -> failed`).
  `Changeset.Plan`/`ApplyLog`/`ConfirmDeadline` fields exist and round-trip
  through the store already (`toStoreRow`/`fromStoreRow` in `service.go`)
  as opaque `json.RawMessage`/`*int64` — you own their actual shape.
  Re-read this report's "Deviation" note on rollback-of-committed: I did
  **not** wire `committed -> rolled_back` as a legal transition of the same
  changeset object, on the reading that docs/features/change-management.md
  §4 means a *new* changeset gets created instead. If your design needs
  the original mutated in place, that's a one-entry change to
  `allowedTransitions` in `changeset.go` plus updating
  `changeset_test.go`'s independent expectation table (don't just flip the
  test to match — re-verify against the docs first).
- **T-207 (editors UI)**: the wire contract for `Op` is `{"op": "<type>",
  "target": "kind:node:id"|null, "params": {...}}` — `target` is a
  **string**, not a nested object, and is `null` only for `sdn.apply`.
  `POST /changesets` body is `{"title": "...", "ops": [...]}`; `PUT
  /changesets/{id}` body is `{"ops": [...]}` with an **additional,
  undocumented-in-api.md but supported** optional `"title"` field for
  renaming a parked draft in place (docs/features/change-management.md §1:
  "named drafts can be parked and resumed") — flagged here since it's an
  extension beyond the literal api.md text, not a contradiction of it.
  `changeset.status` WS events are on the existing `/api/ws` connection
  under the `"changesets"` subscribe topic, shaped exactly
  `{"event":"changeset.status","id":...,"status":...,"confirmDeadline"?:...}`.
- **Everything under `web/` was untouched** (per this task's scope), but
  `web/node_modules` did not exist in this worktree (a fresh checkout
  artifact, not something I created); I ran `npm ci` there purely to be
  able to run `make check`'s web-only steps end to end — no `package.json`/
  `package-lock.json`/source changes.
- No new third-party Go dependencies were added (only stdlib +
  already-approved `internal/store`/`internal/inventory`/`go-chi/chi`).
