# T-1901 · Backup, restore, and disaster recovery of vnprox state — completion report

**Branch:** isolated worktree (`agent-a8e579bf0230e053b`); committed, **not pushed, not merged** — orchestrator to review and merge.

---

## 1. What was built

### The hole, precisely

There was no backup story at all. `docs/deployment.md`'s entire "Backup" section was one paragraph
telling an operator to copy `/var/lib/vnprox/vnprox.db` — which, since the daemon runs in WAL mode
(`internal/store.Open`'s DSN), is **not a backup**: committed transactions live in
`vnprox.db-wal` until a checkpoint, so `cp vnprox.db` yields a structurally valid SQLite file
missing its most recent commits. That is worse than no advice, because the result *looks* fine.
`internal/store/backup_test.go`'s `TestSnapshotTo_CapturesCommitsStillInTheWAL` reproduces exactly
that as a control before asserting anything about the fix.

What was on the line: every changeset and diff, every pre/post rollback snapshot, the full audit
trail, layouts, tenants and blueprint state.

### New packages and files

**`internal/store/backup.go` (new)** — three primitives nothing else in the codebase had, all
deliberately avoiding `Open` (which always migrates):

| Function | Why |
|---|---|
| `SnapshotTo(ctx, src, dest)` | `VACUUM INTO` — a consistent point-in-time copy from a second connection, already checkpointed (no sidecars), safe to take **while the daemon runs**. Chmods the result `0600`. |
| `InspectSchemaVersion(ctx, path)` | reads `kv.schema_version` read-only (`query_only(1)`), **without migrating**. This is what lets restore say "this store is from a newer build" without becoming the thing that migrates it. A file that is not a database errors rather than reporting `0`. |
| `LatestSchemaVersion()` | what this build understands, so a downgrade is refused *before* the target file is touched. |

**`internal/store/runtimelock.go` (new)** — `RuntimeLock`: an advisory whole-file `flock` on
`<db>.lock` that the daemon holds for its lifetime, plus `RuntimeLockHeld` for the probe side.
Rationale for flock over the alternatives is in the file's doc comment: a pidfile goes stale and
then *permanently blocks recovery* (the wrong failure direction for a disaster-recovery command);
`systemctl is-active` is both unavailable in a container and untrustworthy here, because
`vnprox.service` is `Type=simple` and reports active before the store is even opened (T-1807's
finding); and SQLite's own locking says nothing, since WAL exists precisely to let a second process
write concurrently. The kernel releases an flock however the holder dies, so it cannot go stale.

**`internal/config/recovery.go` (new)** — `LoadRecoveryOnly`, mirroring T-607's `LoadStorageOnly`
rationale: the full `Load` resolves a TLS certificate and fails on a host that has none, and
"this node's certificate is the broken thing" is one of the situations these commands exist for.
It additionally returns `[server] listen` (for the liveness probe) and every declared key-file path,
so `--include-keys` collects what *this node's config* says it has rather than a hardcoded list.

**`internal/backup/` (new package)**

| File | Contents |
|---|---|
| `secrets.go` | The declared **secret-class inventory**: 20 classes, each with a name, an operator-facing "what an attacker gets", a storage kind (`sealed-column` / `hashed-column` / `key-file` / `external`) and, where applicable, its `table.column`. Single source of truth for the `--include-keys` warning, AC2's table, and T-1902's redaction list. |
| `manifest.go` | Archive header + the entry-name **allowlist** (`validEntryName`) and manifest self-consistency checks. |
| `archive.go` | The container: gzip+tar, manifest first, then exactly the declared entries in order. `Write`, `Inspect` (validates, writes nothing), `Extract` (same validation, real sink). Absolute streamed budgets (`Limits`). |
| `collect.go` | The `Collector` seam T-1902 reuses, plus `Staging` (a `0700` scratch dir that digests everything recorded into it). |
| `backup.go` | Collectors (store / config / keys), `Create`, `KeyWarning`, `ArchiveName`, `Prune`. |
| `liveness.go` | `DaemonLiveness` — the two-signal live-daemon check. |
| `restore.go` | `Inspect`→decide→stage→migrate→swap, with rollback and the unexported hook seam AC4's failure injection uses. |
| `errors.go` | Ten sentinels, one per refusal reason, so a rejection is diagnosable rather than "some error". |

**`cmd/vnproxctl/backupcmd.go` (new)** — `vnproxctl backup` and `vnproxctl restore`, joining the
**daemon-independent** family (`status`/`snapshots`/`rollback-now`) and keeping its 0/1/2 exit-code
convention unchanged. `backup` is safe against a live daemon; `restore` is defined by its absence.

**`cmd/vnproxd/server.go`** — acquires the runtime lock immediately before `store.Open`, released on
shutdown. **Deliberately non-fatal**: failing to take it logs a `WARN` and carries on exactly as
before this landed, so a mechanism that exists to make a *restore* safe can never become a new way
for the daemon to refuse to start.

**Packaging** — `packaging/systemd/vnprox-backup.{service,timer}`, installed by the `.deb` and
**never enabled** by `postinst` (the same stance it already takes for `vnprox.service` on a fresh
install). `prerm` disables the timer on remove so no dangling enablement symlink is left behind.

**Docs** — `docs/deployment.md`'s one-paragraph "Backup" replaced by a "Backup and disaster
recovery" section (taking, key material, scheduling, restoring, restore-to-different-hardware);
`docs/security.md` gains a "Backup archives (T-1901)" section and **three** threat-model rows.

**No new dependency**, Go or npm. Archive format is `archive/tar` + `compress/gzip` (stdlib);
`golang.org/x/sys/unix` (already a direct require) supplies `Flock`.

## 2. Safety analysis — every claim mapped to the test that proves it

### Claim 1 — "A backup without `--include-keys` contains no key material, structurally." (AC2)

The claim is not "we remembered not to copy the key". It is that **there is no plaintext secret
anywhere to copy**: every credential in the schema is a `*_enc` column (AES-256-GCM under
`internal/store.SessionCipher`) or a `*_hash` column, and the key that opens the former is a file
the archive does not contain.

| Test | What it proves |
|---|---|
| `TestBackup_AC2_NoKeyMaterialWithoutTheFlag` | **21 subtests, one per inventory class.** The fixture seeds a distinct plaintext marker for every class through the real repos, takes a real backup, then scans the **decompressed** archive — manifest, store pages, config, all of it, concatenated — for each marker. Scanning the compressed `.tar.gz` would be the comforting version of this test; scanning what a `tar -xz` actually yields is the real one. |
| ” (the **control**, asserted before any class) | An *unsealed* value — an operator note in `annotations.content`, genuinely not a secret — carrying its own marker **must be found** by the same scanner. If it is not, the test `t.Fatalf`s with "every 'secret not found' assertion below proves nothing". This is what stops 21 green subtests from meaning "the scan looks in the wrong place". |
| ” (final assertions) | The manifest says `includesKeyMaterial: false`, declares zero secret classes, carries no `RoleKey` entry and nothing under `keys/` — **and** the store entry is present, so "no secrets found" is not the trivial consequence of an empty archive. |
| `TestSeed_CoversEverySecretClass` | Every class in the inventory has a seeded marker. Adding a class without teaching the fixture to seed it **fails the suite** rather than silently narrowing AC2's coverage. |
| `TestSecretClasses_CoverEverySealedColumn` | Checks the inventory against the **real migrated schema**, not against itself: it walks `sqlite_master` for every `*_enc`/`*_hash` column and fails if any is unnamed by a `SecretClass`. It additionally fails if fewer than 10 such columns are discovered, so the discovery query cannot quietly break and leave the check vacuous. **This test found a real gap while being written** — `changeset_schedules.callback_token_hash` was missing from my first inventory. |

### Claim 2 — "`--include-keys` is loud, honest, and marked." (AC2, safety analysis)

| Test | What it proves |
|---|---|
| `TestKeyWarning_NamesEveryClass` | The warning names **every** key-file class *and* every sealed-column class the session key unlocks, by name **and** by `table.column` — because "contains key material" is not actionable and "contains the key that decrypts every PVE credential, every WireGuard private key and every sealed revert ticket" is. It also asserts the warning states what the safe alternative is, so a blocked operator does not reach for something worse. |
| `TestBackup_AC2_WithKeysContainsExactlyWhatItPromises` | The flag actually includes the key material (a flag that warned loudly and then shipped nothing would be theatre); the sealed columns stay **sealed** even here (`--include-keys` ships the key, not decrypted columns); the manifest is marked; `secretClasses` matches the key-file set exactly; the filename ends `-with-keys.tar.gz`; the archive is `0600`; extracted key entries are `0600`. |
| `TestBackupCommand_IncludeKeysWarnsBeforeItWrites` (CLI) | The warning reaches **stderr on the `--yes` path** — the one automation actually takes — not only the interactive one, so it lands in whatever log ran the command. |
| `manifest.go`'s `validate` + `TestArchive_AC5_…/"key entry in an archive that claims to hold no key material"` | The header marking is enforced in **both** directions: an archive carrying a key entry while declaring `includesKeyMaterial: false` is rejected. Without this, reading `false` in a manifest would tell an operator nothing. |

The `-with-keys` filename suffix is a safety feature, not cosmetics: it is the one part of the
marking visible in an `ls`, an rsync log, or a filename pasted into a chat window, without anyone
opening the file.

### Claim 3 — "The archive is untrusted input on restore, and is rejected before anything touches disk." (AC5)

`TestArchive_AC5_MaliciousArchivesAreRejected` — **24 table-driven cases**, every one built by
`rawArchive`, a hand-rolled tar writer that bypasses this package's own `Write` entirely (an
attacker does not use our writer, so neither does the test). Each case asserts three things:

1. `Inspect` rejects it with the **specific sentinel** naming why — a generic "some error" would let
   a decompression bomb pass as a digest mismatch and nobody would notice;
2. `Extract` rejects it identically; and
3. a **canary file planted next to** the extraction directory is byte-identical afterwards, and no
   file exists outside that directory. The layout is deliberate: a working `../` lands squarely on
   the canary.

| Attack class | Cases |
|---|---|
| Traversal | `../../../../etc/vnprox/keys/session.key`, absolute `/etc/...`, `store/../../escaped.db`, `..\..\escaped.db` |
| Type confusion | symlink entry, hard-link entry, device-node entry (the two-stage "extract a symlink with a safe name, then write through it" attack) |
| Bombs | a 4 MiB-expanding entry over the total budget; 40 entries over the count budget; a 128 KiB manifest over the manifest budget |
| Truncation | cut mid-entry; cut before the gzip header |
| Structure | not gzip at all; manifest not first; no manifest; entry not declared by the manifest; manifest declaring more entries than exist; header size ≠ manifest size; duplicate names; unknown format version; unknown kind; unknown role; a manifest with an unknown field; corrupt gzip checksum |
| Tampering | entry body not matching its declared digest |

| Companion test | What it proves |
|---|---|
| `TestArchive_AC5_TheRejectionTestIsNotVacuous` | A **benign** archive from the *same builder*, extracted by the *same call*, is accepted and yields the right bytes. Without this, all 24 rows could be passing because `rawArchive` produces something the reader rejects for an unrelated reason. |
| `TestArchive_InspectWritesNothing` | Walks the filesystem before and after `Inspect` of both a good and a traversing archive and asserts it is byte-for-byte unchanged. This is what makes "rejected before anything touches disk" **literal**, since `Restore` runs `Inspect` over the whole file before creating so much as a staging directory. |
| `TestArchive_InspectStopsAtTheBudgetRatherThanReadingEverything` | The bomb defence is a **streaming** bound: with a 16 MiB-expanding archive and a 64 KiB budget, the reader consumes < 64 KiB of compressed input before refusing. A reader that consumed the whole thing and then complained would still have done the work the attacker wanted. |
| `TestValidEntryName` | 24 rows on the allowlist alone, since it is the single load-bearing function for traversal safety. |

**Counterfactual performed.** I replaced `validEntryName`'s body with `return name != ""` and re-ran:
the traversal, absolute-path, mid-path and backslash rows all failed. Two of them
(`../…` and `store/../../escaped.db`) failed on `Inspect` only — `Extract` still refused them via
its independent `filepath.Rel` containment barrier. That is defence in depth working as designed,
and it is worth recording that the second layer is real rather than decorative. Reverted.

**One design note worth flagging:** the "corrupt gzip checksum" row initially **passed nothing** —
tar's end-of-archive marker precedes gzip's trailer, so reaching the end of the tar stream does not
verify the CRC32. Fixed by draining the gzip reader after the last entry; the test now catches it,
and `walk`'s code comment records why the drain is there so it is not removed as dead code.

### Claim 4 — "Restore refuses to run against a live daemon." (AC4)

Two **independent** signals; either one refuses. Both are tested with the *real* mechanism, not a
stub — a stubbed liveness check would prove only that the stub was called.

| Test | What it proves |
|---|---|
| `TestRestore_AC4_RefusesAgainstALiveDaemon/"runtime lock held"` | A real `flock` is taken; `Restore` returns `ErrDaemonRunning`, the error names `systemctl stop vnprox`, and the store is byte-identical. **Then the lock is released and the identical restore succeeds** — proving the refusal was about liveness, not about something else in the archive. |
| `…/"listen address bound by an older daemon that takes no lock"` | The case that actually matters in the field: a **pre-v3.2 daemon takes no lock at all**, and is the one most likely to be running when someone reaches for a restore. The test asserts, as a precondition, that the lock is *not* held, then binds a listener and asserts the refusal names the address. Then closes the listener and re-runs successfully. |
| `…/"dry run is refused too"` | A `--dry-run` that reported "this would work" against a live daemon would be actively misleading. |
| `TestRunDaemon_HoldsTheStoreRuntimeLock` (`cmd/vnproxd`) | **The one that matters for the wiring.** Drives a real `runDaemon` against the checked-in dev config and asserts the property from the outside, in operator order: (1) before start, no lock and a restore is permitted — this is what stops (2) from passing vacuously; (2) while serving, the lock is held, the liveness check is `ErrDaemonRunning`, and a real `backup.Restore` is refused *before it even reads the archive path* (the path deliberately does not exist, so a "no such file" error would mean the ordering is wrong); (3) after shutdown the lock is released and restore is permitted again, so a stopped daemon never permanently blocks recovery. |

**Counterfactual performed.** Removed the `AcquireRuntimeLock` call from `runDaemon`; the test failed
with "the running daemon does not hold the store runtime lock". Reverted.

The listener probe also fires for a *different* service on that port (PBS on 8007, the collision
`docs/deployment.md` already documents). That is the correct trade and is stated in `liveness.go`:
a refused restore costs one diagnostic message that names the address; the opposite error costs the
store.

### Claim 5 — "Restore is atomic: an interrupted restore leaves the original intact." (AC4)

The ordering is the design: steps 1–6 are all *decide* (refuse a live daemon → validate the archive
writing nothing → refuse a downgrade from the manifest → extract into a private directory *beside*
the target → cross-check the extracted store's own schema → forward-migrate **the staged copy**),
and only step 7 *acts* — two renames within one directory, with the first undone if the second
fails. A failed migration cannot touch the live store because the live store is never opened.

`TestRestore_AC4_AtomicityUnderInjectedFailure` injects a failure at each of the three points where
the consequences differ, via an **unexported** hook struct (no production caller can reach it):

| Injection point | What it represents |
|---|---|
| `afterStage` | the common real failure: validated and migrated, then something else went wrong |
| `afterMoveAside` | the only genuinely dangerous window in the operation; the rollback path is what closes it |
| `beforeMoveAside` | the boundary: decide has finished, act has not begun |

Each case first makes the **live** store differ from the archive (an extra row), so "intact" means
"the live one", not "either of two identical files", then asserts:

1. the store file is **byte-identical** (SHA-256 of the raw file, taken without ever opening it —
   "still openable" is a property a half-restored store also has);
2. the live-only row is still readable and correct, and the table count is unchanged; and
3. **no debris**: no stranded `.pre-restore-` copy (which would mean the original was moved aside
   and not put back) and no `.vnprox-restore-` staging directory (which would mean a plaintext store
   copy was left on disk).

`TestRestore_AC4_TheAtomicityTestIsNotVacuous` is the guard: the same fixture, the same call, no
injection — the restore **must** succeed, the store fingerprint **must** change, the live-only row
**must** be gone, the previous store **must** be kept at the documented path and still readable, and
no `-wal`/`-shm` from the old store may survive the swap.

**Counterfactual performed.** Made `undoMoveAside` a no-op and re-ran: the `afterMoveAside` case
failed with the store file missing entirely. Reverted.

### Claim 6 — "Forward migration is supported; downgrade is refused, and a forged manifest cannot get past it." (AC3)

**The forward half** is `internal/store/backup_upgrade_test.go` (`package store_test`, so it can
import `internal/backup` without an import cycle), built on **T-1807's fixture corpus rather than a
second one**. `internal/store/export_test.go` re-exports `openFrozenAtPath` /
`freezeAndSeed` / `assertSeededThrough` / `checkV1` to the external test package; the wrappers add
nothing and decide nothing, so the corpus stays single-sourced and T-1807's exhaustiveness check
still fails on a migration landing without a seed/assert pair.

`TestBackupRestore_AC3_AcrossASchemaUpgrade` runs **32 subtests, schema 1 through 32**, driven by
`store.SeededVersionsAvailable()` so the next migration widens it automatically. Each: freeze a
store at version *V*, seed it with T-1807's cumulative corpus, back it up through the real
`backup.Create`, restore it into a **different directory** through the real `backup.Restore`, then
assert the manifest recorded *V*, the plan reported *V*→33, the restored store reads 33, and
**T-1807's own per-version assertions** (specific column values, per table) all hold. It also fails
setup if the corpus reports fewer than 32 versions or if its highest version is not below latest.

`TestBackupRestore_AC3_TheUpgradeTestIsNotVacuous` runs the same round trip twice at the same schema
version — once seeded, once not — and asserts `store.CheckSeededV1` (T-1807's pure-function variant,
which returns problems as a `[]string` precisely because Go propagates subtest failures
unconditionally) reports **no** problems for the first and **some** for the second. It logs the
count: `7 problem(s) for an unseeded store, e.g. "sessions row lost across migration"`.

**The refusal half** is `TestRestore_RefusesADowngrade`, three subtests:

| Subtest | What it proves |
|---|---|
| "archive from a newer build" | A store whose `schema_version` is bumped past what this build knows is refused with `ErrSchemaDowngrade`, the error names both versions, the target store is byte-identical, and **nothing was staged** — the refusal happens from the manifest, before extraction. |
| "manifest lies about the schema version" | The manifest travels *inside* the archive, so it is exactly as untrusted as the rest. A forged manifest claiming version 1 over a version-38 store is caught by the cross-check against the store itself (`ErrSchemaMismatch`), target untouched, no debris. |
| "same version restores fine" | The control. Without it, both refusals could be passing because restore refuses everything. |

**Counterfactual performed.** Disabled the staged-store cross-check: the forged-manifest case then
got past the manifest check and was only caught later by `migrate()`'s own `ErrSchemaTooNew` — still
on the **staged** copy, so the live store was safe either way, but with a much worse error. The
cross-check is therefore defence in depth that buys an earlier, clearer refusal rather than the sole
barrier; recording that honestly rather than overclaiming. Reverted.

`TestRestore_RefusesASupportBundle` covers the fourth refusal: T-1902's bundle will share this
format with a deliberately redacted payload, and restoring one would install an incomplete store.

### Claim 7 — "The store copy is consistent, and taking it does not require stopping the daemon."

| Test | What it proves |
|---|---|
| `TestSnapshotTo_CapturesCommitsStillInTheWAL` | The **control runs first**: a plain byte copy of the WAL-mode store is asserted to be a *readable SQLite file* (so the failure being demonstrated is "missing committed data", not "corrupt") and then asserted to be **missing** a just-committed row. Only then is `SnapshotTo` asserted to capture it. If a future SQLite/driver change ever made the naive copy safe, the control fails loudly instead of this test passing for the wrong reason. Also asserts no `-wal`/`-shm` sidecars beside the snapshot (a stale WAL renamed into place would be replayed over the restored store) and `0600` permissions. |
| `TestSnapshotTo_WorksWhileTheStoreIsBeingWritten` | A goroutine hammers `audit_log` while the snapshot is taken; the result is still a readable store. This is the cron case. |
| `TestInspectSchemaVersion` | A migrated store reports latest; a frozen store reports its frozen version and **stays frozen across two reads** (inspection must not migrate); a garbage file errors rather than reporting `0` (an attacker blob must not look like "a fresh store"); a missing file errors. |
| `TestRuntimeLock_DetectsAHolder` | Not held before anything runs — **and asking does not create the lock file** (a probe that leaves state behind changes what the next probe sees); held while held; a second acquisition returns `ErrRuntimeLockHeld`; released after `Release`; re-acquirable afterwards (the file surviving on disk is not a stale lock); `0600`. |

### Claim 8 — "Retention cannot destroy what it was asked to keep."

| Test | What it proves |
|---|---|
| `TestPrune_KeepsTheNewestAndTouchesNothingElse` | Prune deletes files, so the negative assertions are the point: another tool's backup, a stray note, a vnprox-shaped name that does not match the timestamp pattern, and a *directory* with a matching name all survive; `keep >= count` is a no-op; `keep = 0` disables retention entirely. Newest is decided by the **timestamp in the filename** (zero-padded, UTC, lexicographically sortable), not mtime — mtime would be wrong the moment an archive is copied. |
| `TestCreate_KeepPrunesButNeverTheArchiveItJustWrote` | Four successive backups with `--keep 2`; each asserts its own archive still exists immediately after the prune, and the directory ends with exactly two. |
| `TestCreate_NoStagingResidue` | The staging directory holds an **unencrypted store copy** (and under `--include-keys`, the session key). Asserted gone on both the success and the failure path, along with any `.partial` archive. |
| `TestArchive_WriteLeavesNoPartialFileOnFailure` | An interrupted backup leaves nothing that looks like an archive next to the good ones, where retention or an operator could mistake it for one. |

### Claim 9 — "`--dry-run` describes what will actually happen."

`TestRestore_DryRunChangesNothingAndMatchesTheRealRun` walks the whole target tree (paths, sizes,
modes) before and after the dry run and asserts it is unchanged, then runs the real restore with
identical options and asserts the plan's store path, schema transition, key paths and **notes** are
identical. The notes are generated from the archive rather than written down, so the
restore-to-different-hardware story cannot go stale relative to what was actually restored
(`TestRestore_NotesDescribeWhatDoesAndDoesNotCarryOver` asserts they name the peer cluster secret,
`/etc/pve`, the hostname requirement, `--restore-config`, and — for a key-bearing archive restored
without `--restore-keys` — that the sealed columns will not decrypt).

### What is deliberately *not* claimed

Stated in `docs/security.md` rather than left implicit:

1. **The archive is not encrypted and not signed.** Per-entry SHA-256 against a manifest that travels
   inside the same file detects corruption and casual tampering; it is **not** an authenticity
   control, because an attacker who can rewrite the archive can rewrite the manifest with it. The
   mitigating structure is that restoring a forged archive installs app-owned *history*, not a
   mutation path — every mutation still flows through the change engine.
2. **A default archive still exposes metadata**: node names, interface names, IP addressing,
   changeset titles, audit usernames and actions. Not a secret class, but a map of the network.
3. **`--restore-keys` overwrites this node's key material** with another node's. Existing files are
   moved aside, but the operator owns that decision.
4. **The peer cluster secret is never collected**, under any flag — it is pmxcfs-replicated
   cluster-shared state, not this node's to hand out. Listed in the inventory as
   `StorageExternal` so the inventory is complete, and named in the restore notes as something that
   must be re-established.

## 4. What was tested and how

- **`internal/backup`** — 5 test files, 22 tests / 78 subtests. Every archive in the AC5 table is
  hand-built by a tar writer that bypasses this package's own writer. Every fixture is a **real**
  migrated store seeded through the real repos with a real `SessionCipher`. Liveness is tested with
  a real `flock` and a real bound listener, never a stub.
- **`internal/store`** — `backup_test.go` (4 tests) and `backup_upgrade_test.go` (2 tests / 32
  subtests, `package store_test`).
- **`internal/config`** — `recovery_test.go` (4 tests), including a control asserting the full
  `Load` genuinely *fails* on the same file, so the test is not merely asserting two loaders agree.
- **`cmd/vnproxctl`** — `backupcmd_test.go` (7 tests / 5 subtests) driving `run()` end to end:
  round trip, the `--include-keys` warning on the automation path, the live-daemon refusal and its
  exit code, `-o json` for both commands, the `ExitUsage` boundary, a malformed archive, `--help`,
  and that `keyPathsFor` reads the config rather than a hardcoded list.
- **`cmd/vnproxd`** — `runtimelock_test.go`, a real `runDaemon` against the checked-in dev config.
- **Race** — `go test -race ./internal/backup/ ./internal/store/ ./cmd/vnproxctl/`: clean.
- **Counterfactuals** — four, each verified to fail and then reverted: disabling the entry-name
  allowlist (AC5 rows fail), disabling `undoMoveAside` (AC4 atomicity fails), disabling the
  staged-store schema cross-check (AC3 forged-manifest fails), removing the daemon's lock

## 6. Deviations from the task card, with reasons

**D1 — The daemon gained a runtime lock file.** The card says "refuse to run against a live daemon"
but not how. Every available signal was either stale-prone (pidfile), untrustworthy
(`systemctl is-active` against a `Type=simple` unit — T-1807's own finding), or meaningless (SQLite
locking under WAL). An flock held for the process's lifetime is none of those. It is a change to
`cmd/vnproxd`, so it is **deliberately non-fatal**: a daemon that cannot take the lock logs a `WARN`
and behaves exactly as it did before this landed, and the listener probe still covers it. The lock
file lives next to the store, so `apt purge` already removes it.

**D2 — Two liveness signals, not one.** A lock alone would miss the daemon most likely to be running
during a restore: a *pre-T-1901* one, which takes no lock at all. The listener probe covers that,
at the cost of also firing when something unrelated owns the port. Stated in `liveness.go` and
tested from both directions.

**D3 — `restore` restores the store only; config and keys are opt-in.** The card says "atomic
replacement" of the store and lists what must be re-established on different hardware. Silently
adopting another node's `vnprox.toml` (its listen address, its certificate paths) is a good way to
make a restored node unreachable, so `--restore-config` and `--restore-keys` are separate,
default-off flags. The archived config is always in the tarball for the operator to diff. Both flags
move any existing file aside rather than overwriting.

**D4 — Retention lives in the CLI command (`--keep`), not the daemon.** The card says "sane
retention, not a new scheduler inside the daemon". `--keep` is the ceiling, applied by the command
after a successful write; a timer or cron line is the scheduler. This keeps retention testable in Go
(`TestPrune_*`) instead of as a `find -delete` inside a unit file. Store-level retention is T-1905's
card and is untouched here.

**D5 — Ship the systemd timer disabled rather than only documenting a cron line.** The card asks for
"a documented cron-friendly invocation". A unit an operator can `systemctl enable --now` is strictly
better than a line they must copy correctly, and shipping it disabled matches `postinst`'s existing
stance on `vnprox.service`. The cron equivalent is documented alongside it.

**D6 — An interactive confirmation for `--include-keys`, on top of the warning.** The card requires
a flag and a warning. A warning printed immediately before doing the thing anyway is easy to scroll
past, so the flag additionally requires typing `include-keys` — read from `/dev/tty`, not stdin, so
`--include-keys < /dev/null` in a script is not silently answered "yes" by an empty stdin. `--yes`
exists for genuine automation and **still prints the warning**.

**D7 — The archive is neither encrypted nor signed.** Considered and rejected for this card: an
encrypted archive needs a key, and the only key vnprox has is the one the archive deliberately
excludes, so it would either be useless or reintroduce exactly the problem `--include-keys` exists
to make explicit. A signed archive needs a signing identity and a verification story that does not
exist yet. Both are stated as residual risks in `docs/security.md` rather than quietly omitted, and
the mitigating structural point (a restored store is history, not a mutation path) is stated with
them.

**D8 — `store.SnapshotTo`/`InspectSchemaVersion` live in `internal/store`, not `internal/backup`.**
They are properties of the store (its journal mode, its migration scheme), not of backup, and
`InspectSchemaVersion` needs `currentSchemaVersion`, which is unexported. T-1905 and T-1902 can use
them directly.

**D9 — Two exported test helpers added to `internal/store` via `export_test.go`.** Required to reach
T-1807's corpus from a test that must import `internal/backup` (which imports `internal/store`, so
`package store` would cycle). The wrappers are pure re-exports and are invisible outside
`package store_test`. This was the alternative to inventing a second corpus, which the dispatch
explicitly ruled out.

**D10 — No new dependency**, Go or npm. No frontend change: backup and restore are deliberately
CLI/daemon-independent, and putting a "restore my store" button in a web UI served by the daemon
being restored would be a category error.

## 7. Needs hardware validation

Two items added to `planning/reports/needs-hardware-validation.md`; neither blocks the card, and
everything above runs entirely against real SQLite, real archives and a real `runDaemon`.

1. **`VACUUM INTO` against a genuinely busy store on real hardware.** Verified here against a
   concurrently-written store, but on a real node the store is larger and the root filesystem is
   shared with pmxcfs and PVE's own I/O. What should be measured on iron: wall time and peak extra
   disk usage for a `VACUUM INTO` of a months-old store, and whether the daemon's own writes visibly
   stall during it (they should not — the vacuum holds a read transaction).
2. **The systemd timer on a real node.** `packaging/systemd/vnprox-backup.service` runs under
   `ProtectSystem=strict` with `ReadWritePaths=/var/lib/vnprox` and a narrow capability set. That
   composition is verified only by `systemd-analyze verify` here; a real `systemctl start
   vnprox-backup.service` on a PVE node is the check, along with confirming `--keep`'s prune works
   under the unit's sandbox.

## 8. For the next agents

### T-1902 (support bundle) — what to reuse and how

The card's author note says the bundle is "structurally a backup with a harsher redaction policy and
a narrower scope". That is exactly the shape this package was built to. **Do not add a second
archive format.**

- **`Kind`.** `manifest.KindSupportBundle` already exists and is already accepted by the reader;
  `Restore` already refuses it (`ErrWrongKind`, tested). Write bundles with that kind and you get
  the whole container for free.
- **`Collector` is your allowlist enforcement point.** `Name()` / `Emits() []SecretClass` /
  `Collect(ctx, *Staging)`. AC2 of your card ("adding a new field to a collected structure without
  declaring it fails a test") maps directly: a bundle collector's `Emits()` must be **empty**, and
  the natural test is "for every collector, scan its staged output for every marker in the inventory
  and fail on any hit" — the same shape as `TestBackup_AC2_NoKeyMaterialWithoutTheFlag`, which you
  can lift wholesale including its **unsealed control** (see `seed_test.go`'s `unsealedMarker`;
  without that control the test is decorative).
- **`Staging` refuses undeclared entries.** Nothing reaches an archive without a recorded digest, so
  a collector cannot emit something the manifest does not describe.
- **`SecretClasses()` is your redaction inventory**, already covering every class your card
  enumerates — PVE tokens/tickets, session/metrics/blueprint keys, WireGuard private and preshared
  keys, federation credentials, webhook target secrets, and T-1805's revert tickets — plus five your
  card does not name (OIDC-mapped PVE credentials, switch credentials, k8s kubeconfigs, alert-rule
  target secrets, ingress credentials, and the scheduled-apply callback token). It is enforced
  against the live schema by `TestSecretClasses_CoverEverySealedColumn`, so it cannot rot.
- **`configCollector` is where the redacting variant belongs.** A backup captures `vnprox.toml`
  verbatim because a backup must reconstruct the node; a bundle needs the redacted one. Add a
  sibling collector, do not add a mode to this one.
- **The store must NOT be in a support bundle**, or the bundle carries the whole audit trail and
  every sealed credential's ciphertext into a forum thread. Collect derived facts (schema version,
  row counts, the last N redacted changesets), never `store/vnprox.db`.
- **`--dry-run`.** Your AC4 wants dry-run output to match a real run. `Restore`'s `Plan` shows the
  pattern that makes that structurally true: **one** function produces the plan, and `DryRun` only
  decides whether to act on it. Do not build two code paths and compare them.
- **`peer.Trust.Status()` / `Client.TrustReport()`** were flagged by T-1906 as bundle-ready and
  contain no secrets by construction.

### T-1905 (retention)

- `store.SnapshotTo` is your safety net: a prune that is about to delete something should be
  preceded by a backup an operator can actually take, and `docs/deployment.md` now documents one.
- `store.LatestSchemaVersion` / `InspectSchemaVersion` are available if you need them.
- The archive-file retention here (`backup.Prune`, filename-timestamp ordering, never touching files
  it does not own) is deliberately *separate* from store-row retention and should stay that way —
  different data, different guarantees, different failure modes.

### Everyone else

- **Anyone adding a sealed column**: add a `SecretClass` in `internal/backup/secrets.go` and a marker
  in `internal/backup/seed_test.go`'s `secretMarkers`, or `TestSecretClasses_CoverEverySealedColumn`
  and `TestSeed_CoversEverySecretClass` will fail with a message telling you exactly that.
- **Anyone adding a migration**: `TestBackupRestore_AC3_AcrossASchemaUpgrade` widens automatically
  once T-1807's `versionSeeds` gains the new entry (which T-1807's own check already forces).
- **`internal/store/export_test.go`** is the bridge for any future external test package that needs
  T-1807's corpus. Add re-exports there, not a second corpus.
- **The daemon's runtime lock** is non-fatal on purpose. If a future card wants to make two daemons
  on one store a hard error, that is a separate, deliberate decision — do not turn this warning into
  a fatal by accident.
