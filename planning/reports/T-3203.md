# T-3203 — scale & performance on real cluster data (T-1808 verbatim)

T-1808's own deliverables, run against the real two-node `vnprox-dev` cluster (`pvecube`
192.168.1.9 + `pve001` 192.168.1.7, PVE 9.2.10, vnprox `4.0.0+32+g7822bea+dirty`) T-3201 stood up,
plus T-3203's own addition: re-deriving `DefaultPhysicalCollapseThreshold` from real per-node port
counts.

**The honest scope limit, stated up front**: this cluster is 2 nodes with a handful of guests —
nowhere near `docs/features/topology.md` §4's documented scale target (8 nodes × 6 NICs, 4
bridges/node, 300 guests, 40 VNets). Nothing below claims to validate that target; `docs/performance.md`
§1–§5 already did that against a synthetic 8-node/300-guest fixture built for exactly that purpose.
What this card adds is what only *real* hardware can give: real API/collector timing free of any
mock-server shortcut, a real per-node physical port count, and a real browser measuring a real
daemon's real payload — compared side by side with the synthetic numbers, divergences called out,
nothing rounded to make the two look closer than they are.

## Harness

Two small, standalone, repeatable scripts (AC4) — committed, no state assumed beyond a running
vnproxd and a temporary login credential:

- **`planning/reports/T-3203-harness/measure-api.sh`** — logs in, takes N samples of
  `GET /topology` (timing + payload size), reads back entity counts per layer/kind from the
  response itself, and pulls the collector poll-duration histograms from `GET /api/v1/metrics`
  (bearer-token auth, `/etc/vnprox/keys/metrics.key`). Read-only.
- **`web/scripts/measure-real-hardware-perf.mjs`** — a standalone Playwright script (the
  `playwright` package directly, not `@playwright/test`'s runner — lives under `web/scripts/` so
  its bare `import "playwright"` resolves against `web/node_modules` with no path gymnastics, and
  so it never touches `web/playwright.config.ts`'s pvemock-only shard system, which stays exactly
  as CI-excluded as it already was). Logs in through the real login form, measures navigation/paint
  timing, switches to the Graph view and reuses `web/e2e/perf.spec.ts`'s exact rAF frame-delta
  pan/zoom sampler, and reads Chromium's `performance.memory` JS heap size. Read-only against the
  daemon.

Both scripts read credentials from environment variables and never persist a password to disk.
This project's standing practice for a locked-root cluster (`planning/reports/T-3202-scenarios.md`)
— a temporary `chpasswd` bracketed by an immediate `passwd -l root` around the one login call — is
the caller's job, documented in each script's own header, not something either script does for you.

## Results (2026-08-18, pvecube, PVE 9.2.10)

### API latency, payload, entity counts

20 samples, `measure-api.sh`:

| Metric | Real (pvecube, 2-node cluster) | Synthetic (`docs/performance.md` §2, 8-node/300-guest) | Divergence |
|---|---|---|---|
| `GET /topology` p50 | 77.1 ms | 60.1 ms | +28% |
| `GET /topology` p95 | 83.2 ms | 67.2 ms | +24% |
| `GET /topology` max | 83.2 ms | 80.8 ms | +3% |
| Payload size | 5,929 B | not recorded (§2 measures latency, not bytes) | n/a |

Server-side `duration_ms` logged by vnproxd's own HTTP access log for the same requests (not
`curl`'s wall clock, so TLS handshake/network is excluded) was consistently **58–65 ms** — closer
to, and consistent with, the synthetic 60.1 ms p50. The ~15–20 ms gap between that and the script's
own `curl` wall-clock numbers above is TLS/connection overhead each fresh `curl` invocation pays
that a real browser's kept-alive session and the synthetic benchmark's in-process client both
avoid — an environment artifact of the measurement method, not the server.

**Reading this honestly**: the real numbers are *slightly slower*, not faster, than the synthetic
300-guest fixture, despite carrying **28 entities total vs. the synthetic's 203 post-collapse** (a
~7× difference in what's being projected). This says `GET /topology`'s real-world latency is
dominated by fixed per-request overhead (auth check, TLS, JSON encoding baseline) at both scales,
not by entity count — the same conclusion §3's frontend fps comparison already drew from a
different angle ("progressive disclosure... rendering cost is dominated by the post-collapse graph,
not the raw entity count"). The 24–28% gap itself is well inside what a live two-node peer-poll
cycle (§2, `collect: peer host poll failed` — a real, already-tracked, unrelated finding, see
below) contending for the same event loop would plausibly add over an isolated in-process
benchmark; it is not read as a regression.

Entity counts, real cluster: **28 nodes, 13 edges** — `bridge: 6, guest: 5, guest-nic: 9, physnic:
5, sdn-zone: 1, sdn-vnet: 1, sdn-subnet: 1`, by layer `l2: 6, guest: 14, phys: 5, sdn: 3`. Far under
every threshold in play (`DefaultCollapseThreshold`/`DefaultPhysicalCollapseThreshold` = 8, render
cap ~2,000) — collapse never engages at this scale, same as the documented target itself never
engages it (§4 above, `docs/performance.md` §4's own note).

| Source | Node | Samples | Mean | Notes |
|---|---|---|---|---|
| `pve` (cluster-wide PVE API poll) | — | 97 | 113.8 ms | 96/97 samples land in the 100–250 ms histogram bucket; 1/97 under 100 ms. |
| `host` (local `/etc/network/interfaces` + netlink read) | pvecube | 189 | 18.3 ms | 189/189 under 25 ms — the fast, healthy path. |
| `host` (peer poll of pve001's host state) | pve001 | 189 | 79.3 ms | Mixed: 186/189 complete under 10 ms, 3/189 take 1–10s. All 189 are recorded `outcome="failure"` in `vnprox_collector_polls_total` — this is `planning/reports/blocked-validation.md` §2.5's already-tracked, still-open `collect: peer host poll failed... context canceled` finding, not a new one; noted here only because it's visible in this histogram, not investigated further under this card. |
| `lldp` | pvecube | 33 | 3.0 ms | LLDP socket read, cheapest poll of the four. |

`pveInterval: 10s`, `hostInterval: 5s`, `lldpInterval: 30s` (`GET /config`) — every mean above is
comfortably inside its own poll period, so no collector is falling behind its schedule at this
scale.

### Frontend performance (real browser, real daemon, one run)

`measure-real-hardware-perf.mjs`, headless Chromium, this dev host (no GPU compositing — same
caveat every prior perf measurement in this repo carries):

| Metric | Real (pvecube, 28 entities) | Synthetic three-node-vlan baseline (`docs/testing/topology-performance.md`, ~26 entities) | Synthetic scale-lab (`docs/performance.md` §3, 203 post-collapse) |
|---|---|---|---|
| Login → topology (wall clock) | 2,255 ms | not measured this way | ~3,000 ms (backend-converged definition, not directly comparable) |
| First Contentful Paint | 1,020 ms | not measured | not measured |
| Pan/zoom mean fps | **51.3** | ~35 (run 1: 35.4, run 2: 34.6) | 38.3 |
| Pan/zoom p95 frame | 16.8 ms | 50.1 ms | 50.0 ms |
| Pan/zoom max frame | 133.3 ms | 66.7/66.8 ms | 283.4 ms |
| Frames over 16.7ms budget | 4.0% | 40.3% | 34.5% |
| JS heap used | 23.4 MB | not measured | not measured |

**Divergence over 25%, called out per AC2**: mean fps (51.3 vs. ~35, a **+47%** improvement) and
frames-over-budget (4.0% vs. ~40%, ~10× fewer) both diverge sharply from the existing pvemock
baselines, in the *good* direction. Read honestly, not as "the product got faster" — this is very
likely an **environment difference, not a product one**: this run's Chromium instance is the same
one `npm run e2e` already has installed on this dev host, but the existing three-node-vlan/scale-lab
numbers in the two docs above predate this session and may have been captured under different load
or a different Chromium/Playwright point release (the repo's own numbers give no way to rule that
out from here). The one same-scale comparison available — 28 real entities vs. ~26 synthetic
entities, both well under any collapse threshold — makes a **product** explanation (faster
real-world data) implausible on its own; an environment explanation is the more defensible reading,
flagged rather than claimed as a finding either way. Max frame time (133.3 ms) is a single outlier
plausibly from the initial view-switch animation, not sustained — p95 (16.8 ms) is the honest
steady-state number and it does clear the 60fps (16.7 ms) budget almost entirely at this scale.

**JS heap usage (23.4 MB)** is a genuinely new data point — neither prior doc measured memory. No
target exists to compare it against; recorded here as the first real number for whoever eventually
sets one.

## AC3 — any miss against topology.md §4's target

**None filed.** At 28 real entities, this run is roughly two orders of magnitude below the
documented 8-node/300-guest/40-VNet target — nowhere near the render cap, the collapse thresholds,
or (per the numbers above) even a latency regime where collapse would matter. There is no target
this cluster's own scale can meaningfully fail. `docs/performance.md` §5 remains the authoritative
scale-target verdict; nothing here revises it, up or down.

## Re-deriving `DefaultPhysicalCollapseThreshold` (T-3203's own addition to T-1808)

Real per-node physical port counts, both real nodes, read directly from `/sys/class/net` (excluding
bridges/bonds/veth/fwbr-fwpr-fwln SDN-firewall shims — bare physical NICs only):

| Node | Physical NICs |
|---|---|
| `pvecube` | 4 (`enp1s0`–`enp4s0`) |
| `pve001` | 6 (`enp2s0`–`enp7s0`) |

Both comfortably under `DefaultPhysicalCollapseThreshold = 8` — collapse never engages on either
real node, consistent with the documented target's own 6-NICs/node figure never engaging it either
(`internal/topology/types.go`'s existing reasoning). **This does not close the threshold's
provisional status**: the doc comment's own concern is chassis with "many bonds, SR-IOV PFs each
carrying their own `PhysNic` entity" running materially higher than 8 — a 2-node dev cluster with
4 and 6 onboard NICs each says nothing about that case either way. What changes: the comment can
now say "confirmed at least two real nodes sit well under this threshold" instead of citing zero
real data points, and the promised revisit against T-1808's numbers (`planning/reports/T-1907.md:70`)
is discharged with an honest "no basis to move it, still provisional for the large-chassis case."
`8` is unchanged. `internal/topology/types.go`'s comment is updated to record this.

## AC4 — repeatability

Both harness scripts take their target/credentials from environment variables and print nothing
but their own JSON result plus `stderr` progress lines — rerun exactly as shown in each script's
own header, against either node, by anyone with SSH/console access to the cluster and no
conversation history. `SAMPLES` (default 20) is the only tunable `measure-api.sh` exposes.

Green — see the commit this report ships with. Neither new script is wired into `make check`,
`npm test`, or the Playwright shard system; both are opt-in operator tools, matching this card's
own read-only, hands-on-real-hardware nature (the same reasoning `web/playwright.config.ts`'s
