# T-1401 — WireGuard tunnel engine & changeset integration core

**Status:** complete. `make check` green (golangci-lint 0 issues; all Go tests;
1198 frontend Vitest tests; govulncheck clean; npm audit clean). Branch:
`t-1401-wireguard` (not pushed).

## What was built

A first-class WireGuard `wg.*` changeset op group flowing through the ordinary
stage → validate → diff → apply → confirm/rollback lifecycle — **no second
mutation path**. Every deliverable from the card:

- **`internal/wireguard`** (new): X25519 keygen via stdlib `crypto/ecdh` (no new
  third-party crypto dependency — `GenerateKeypair`/`PublicKeyFor`), tunnel/peer
  intent model, wg-quick config render (`RenderConfig`) + external-peer export
  (`RenderPeerConfig`), a `wg show <if> dump`-equivalent parser (`ParseDump`,
  which deliberately discards the interface's private-key column), and the new
  **WireGuard state fixtures** (`fixtures.go` + `testdata/three-peer.dump`:
  healthy / stale-handshake / endpoint-drift / external-peer-export scenarios).
- **Op group `wg.*`** (`internal/change`): `wg.tunnel.create/update/delete`,
  `wg.peer.add/remove`; new Ref kinds `wg-tunnel`/`wg-peer`
  (`internal/inventory`). External peers are `wg.peer.add {external:true}` —
  modeled read-only, config-export-only, never targeted by an apply step of
  vnprox's own.
- **App store** (`internal/store`): `wireguard_tunnels`/`wireguard_peers`
  (migration `0016_wireguard.sql`) + `WireGuardRepo`. The private key is stored
  AES-256-GCM-sealed with the **same `SessionCipher`** `sessions.pve_ticket_enc`
  uses (not a second cipher/key pair); only the public key is plaintext.
- **Change-engine integration**: `StepWgApply` step kind, a daemon-level
  `WGGateway` seam (always wired, no user ticket — so rollback works on the
  unattended commit-confirm-timeout path too), pre-apply WireGuard-state
  snapshot, and full rollback on both the same-request-failure and
  confirm-timeout paths. `mgmttouch.go` extended: a `wg.*` op whose carrier
  interface is on a node's resolved mgmt/corosync path is `touchesMgmtPath`
  (inherits T-703's typed-ack / 180s-floor ceremony, **no override**). Schema
  validation for wg params (`schema.wg_key_invalid`,
  `schema.wg_port_out_of_range`).
- **Findings** (`source: "wireguard"`): `wg_handshake_stale` /
  `wg_endpoint_drift`, computed fresh from the live poll (`WGProvider` seam),
  hysteresis-debounced (a single missed poll doesn't fire), never persisted.
- **Read routes** (`internal/api`, netRead, read-only): `GET
  /wireguard/tunnels`, `GET /wireguard/tunnels/{id}/pubkey`, `GET
  /wireguard/tunnels/{id}/peer-config`. No write route exists — WireGuard is
  mutated only through the `wg.*` ops.
- **cmd/vnproxd wiring**: `hostWGGateway` (keygen on-node, sealed key, on-node
  config write + fixed-argv `wg`/`wg-quick` exec, snapshot/restore rollback) and
  `wireGuardReadService` (store config + live `wg show dump` status) backing both
  the read routes and the findings provider; wired into change/findings/api.
- **Docs**: `docs/api.md` (WireGuard section + `wireguard` finding source),
  `docs/data-model.md` (§3 op group, Ref kinds, §9 + schema tables),
  `docs/security.md` (WireGuard credential-storage note, cross-referencing the
  AES-256-GCM primitive).

## Deviations / decisions

- **Tunnel identity = client-chosen op target id** (like SDN zone ids), not an
  apply-time-generated ULID, so create/update/delete/peer ops reference the same
  target consistently and the `{id}` routes address it directly. The migration
  comment still says "ULID" — a ULID is a fine choice for that id, just not
  mandated.
- **Peer ops don't carry a carrier**, so `TouchesMgmtPath` computes the
  mgmt-path flag from `wg.tunnel.create/update`'s `carrier` field only; a
  peer-only changeset on a mgmt-path tunnel isn't independently flagged. In
  practice a mgmt-path tunnel's create op is in the same changeset and triggers
  the ceremony for the whole changeset. Documented in `mgmttouch.go`.
- **Cluster wg routing is not implemented**: a `wg.*` op targeting a non-local
  node is rejected clearly by `hostWGGateway.ensureLocal` — the same single-node
  scope `hostNodeAgent` documents. The read service lists the local node's store
  only (no peer fan-out), like the corosync check. Both are flagged follow-ups.

## Federation seam (T-1201) — for the next agent

Federation is not yet in this repo. External/non-federated peers are the modeled
shape: `wireguard_peers.cluster_id` (and `wireguard.Peer.ClusterID`) is the
declared-but-unused linkage field a federation-managed internal peer will set.
T-1407 (tunnel-aware federation transport) is expected to add the `clusters`
table's `wgTunnelId` linkage and consume T-1401's `wg_handshake_stale` finding /
tunnel status to collapse a down-tunnel peer's per-surface unreachable noise into
one `tunnel_down_peer_unreachable` finding. Nothing in T-1401 blocks on
federation; the seam is inert until then.

## What T-1402 needs (map edges + "connect two clusters" wizard)

- The tunnel/peer/finding model is fixed here. T-1402 renders a `wg-tunnel` edge
  and paints it from the three finding states: healthy (recent handshake),
  `wg_handshake_stale` (amber), `wg_endpoint_drift` (dashed/flagged). Those two
  finding checks + `GET /wireguard/tunnels`' `status`/per-peer
  `observedEndpoint`/`endpointDrifted`/`lastHandshakeUnix` are the live inputs.
- The wizard stages **one** changeset whose ops are `wg.tunnel.create` +
  `wg.peer.add` on both ends plus the `fw.rule.create` ops the link needs — all
  already valid op types; nothing new is required from T-1401. `touchesMgmtPath`
  is computed for it automatically if a carrier is on the mgmt path.

## Needs hardware validation

- Real WireGuard kernel-module behaviour: `wg-quick up/down`, `wg syncconf`, and
  `wg show <if> dump` output are exercised only against injected no-op runners
  and fixture dumps — never a live `wg`. The surrounding safety machinery
  (keygen, sealing, store, snapshot/rollback, mgmt-path flag, findings) is real
  and agent-agnostic.
- Endpoint-drift / handshake-age thresholds (`WgHandshakeStaleThreshold` = 5m)

## Fix pass — adversarial-review gating findings (post-merge)

Two GATING findings from the T-1401 adversarial review, fixed on top of the
merged code. Both stay inside the change engine — no second mutation path, no
override to the mgmt-path ceremony.

### Finding 1 (MAJOR) — preshared key was persisted plaintext in `ops_json` and echoed by `GET /changesets`

The PSK rode `WgPeerAddParams.PresharedKey` as an ordinary op field: plaintext
in `changesets.ops_json` and returned verbatim by the netRead read surface,
even though the store sealed it into `wireguard_peers.preshared_key_enc`.

- `WgPeerAddParams` now has a sealed-at-rest `PresharedKeyEnc []byte` field;
  `PresharedKey` is write-only (ingest-only) (`internal/change/params_wg.go`).
- `change.Service` grew a `SecretSealer` seam (`Config.Sealer`, the daemon's
  `*store.SessionCipher`); `sealOpSecrets` seals the plaintext into
  `PresharedKeyEnc` and clears `PresharedKey` at stage/create time — called by
  both `Create` and `UpdateDraft`, **before** persistence. Fail-closed: a
  plaintext PSK with no configured sealer is rejected, never persisted in the
  clear. Idempotent for GET→PUT round-trips (`internal/change/service.go`).
- The read surface strips both the plaintext and the sealed field from every
  changeset response via `redactOpSecrets` in `toChangesetResponse`
  (`internal/api/changesets.go`) — GET returns neither form.
- At apply, `hostWGGateway.addPeer` unseals `PresharedKeyEnc` just-in-time
  (`peerPresharedKey`) and re-seals into `preshared_key_enc` exactly as before;
  a hand-built plaintext op is still honored (`cmd/vnproxd/wireguard.go`).
- Wired `Sealer: sessionCipher` in `cmd/vnproxd/server.go`.
- Regression tests: `TestSealOpSecrets_NoPlaintextPSKAtRest` /
  `_FailClosedWithoutSealer` / `_Idempotent` (no plaintext in `ops_json`, seal
  round-trips) `internal/change/wg_psk_internal_test.go`;
  `TestChangesets_WgPeerPresharedKeyNotEchoed` (create response + GET never
  carry the PSK) `internal/api/wg_psk_test.go`;
  `TestHostWGGateway_PeerPresharedKeySealed` (sealed-in-op peer applies; stored
  column decrypts to the real PSK) `cmd/vnproxd/wireguard_test.go`.

### Finding 2 (MAJOR) — mgmt-path interlock bypassed by carrier-less wg ops

`TouchesMgmtPath` only saw a tunnel's carrier when it appeared in op params, so
a standalone `wg.peer.add/remove`, a carrier-less `wg.tunnel.update`, or a
`wg.tunnel.delete` on an already-existing mgmt-path tunnel fell through
unflagged and skipped T-703's typed-ack + 180s floor.

- `TouchesMgmtPath` now takes a `tunnelID -> WgTunnelCarrier` map
  (`WgCarrierSource`) and resolves an existing tunnel's stored carrier for
  `wg.peer.*` (via the `"<tunnelID>/<pubkey>"` target), `wg.tunnel.delete`, and
  carrier-less/off-path `wg.tunnel.update` (`internal/change/mgmttouch.go`).
- The API layer builds the map once per request from the WireGuard read
  service (`change.WgCarrierSource`, new `Options.WgCarriers`), threaded through
  every changeset handler + the apply pre-check (`internal/api/changesets.go`,
  `internal/api/router.go`); `wireGuardReadService.TunnelCarriers`
  (`cmd/vnproxd/wireguard.go`) supplies it, wired in `server.go`.
- The scheduling gate (`schedule.go`, the unattended path) uses the same lookup
  via `Config.WgCarriers`, so a scheduled carrier-less wg op on a mgmt-path
  tunnel is blocked the same way.
- The `params_wg.go` invariant comment now matches the delivered coverage.
- Regression test: `TestTouchesMgmtPath_WireGuard_StoredCarrier`
  (`internal/change/mgmttouch_test.go`) — peer-add/remove, delete, and
  carrier-less update on a mgmt-path tunnel are all flagged; the same ops on an
  off-path tunnel, on another node, or with no carrier lookup are not. Existing
  `TouchesMgmtPath` call sites updated for the new signature.

### Residual risk / notes

- A GET→PUT round-trip that re-submits ops fetched from a read response drops
  the PSK (the sealed field is redacted on read); the frontend does not
  round-trip the PSK (it is set once at stage time), so this is a non-issue in
  practice — re-editing a peer's PSK means re-supplying it.
- `TunnelCarriers` lists the local node's store only, inheriting T-1401's
  documented single-node scope (cluster wg fan-out is the same follow-up).
- The T-1401 safety-analysis test cross-references remain valid;
  `TestTouchesMgmtPath_WireGuard` is unchanged in intent (params-carrier cases)
  and joined by the stored-carrier regression above.
