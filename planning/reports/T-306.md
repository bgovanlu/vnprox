# T-306 — MAC/FDB browser

**Status:** complete. `make check` green (gofmt clean, `go vet` clean,
golangci-lint 0 issues, full Go suite passes, eslint clean, `tsc --noEmit`
clean, full Vitest suite passes — 238/238 frontend tests, govulncheck clean,
`npm audit --audit-level=high` clean).

## 1. What was built

**`internal/host` — FDB staleness + fixture support.** `FDBEntry` gained a
`Stale bool` field, populated in `netlink_linux.go` from the kernel's
`NUD_STALE` neighbor state (the same bitmask `Permanent` already reads
`NUD_PERMANENT` from) — this is the actual staleness signal AC3 tests
against, not a collector-poll-freshness concept. Fixtures previously could
not express FDB data at all (`FixtureReader`'s doc comment said so
explicitly); `internal/pvemock`'s `LinkInfo`/`LinkState` gained a fixture-
declarable `FDB []FDBEntrySpec`/`[]FDBEntry` (mac/port/vlan/master/
permanent/stale), and `internal/host/fixture.go`'s `fixtureBridgeDetail`
now converts it through. New `internal/host/fdb.go`: `FDBRow` +
`FlattenFDB([]LinkState) []FDBRow`, a pure flatten of every bridge's FDB
into a bridge-tagged list — no new I/O, works for both `Real` and
`FixtureReader` results.

**`internal/peer` — `GET /api/peer/host/fdb`.** T-301's report flagged this
route's absence as T-306's own deliverable; added it. It is deliberately
*not* a new `HostReader` interface method: a bridge's FDB is already
embedded in `Links()`'s `BridgeDetail`, so `handleFDB` just calls
`Reader.Links()` and flattens (`host.FlattenFDB`) — a distinct method would
mean either `Real` doing a second redundant netlink dump per request or
`FixtureReader` needing a second adapter path for data the existing method
already carries. `Client.FDB` added symmetrically. Route/response shape
documented in `docs/api.md`'s Peer API section, same retroactive-doc
pattern T-302/T-303 used.

**`internal/inventory` — `Bridge.FDB`.** New `FDBEntry` type and a `Bridge.FDB
[]FDBEntry` field, populated in `FromNetlinkLinks`/`resolveBridge` straight
through from the `host-netlink` partial (bypassing `pick`/`ownershipRules`
— it's single-source and would otherwise spam `topology.delta` on every MAC
learn/age) and deliberately excluded from `fieldMap` so it never triggers a
delta or provenance entry. Because `Bridge` entities are already ingested
cluster-wide by T-303's existing peer fan-out (`hostPollOnce` polls every
reachable node's `Links()`, local and peer alike), this is the only wiring
needed for FDB to become cluster-wide — no new poll loop, no new fan-out
call. `docs/data-model.md`'s `Bridge` row updated to list it.

**`internal/topology` — the actual browser logic.** New `fdb.go`:
`buildMacIndex` (one pass over the snapshot indexing every `GuestNic.Mac` →
owning `Guest` ref/name and every `PhysNic.Mac` → its own ref/name, guest
winning any collision), `FDB(snap)` (every bridge's FDB, ownership-labeled
and sorted), `FDBSearch(snap, q)` (same ranked exact/prefix/substring/fuzzy
scoring `Search`/`matchScore` already use for `/inventory/search`, with MAC
separators stripped so `"aabb"` matches `"AA:BB:..."`). `Detail()` (the
`GET /inventory/{ref}` bridge inspector) now overrides its generic
JSON-reflected `fields.FDB` with the same owner-labeled rows, so the
inspector needs no separate fetch.

**`internal/api` — `GET /fdb`.** New `fdb.go`: `FDBService` interface
(`*topology.Service` satisfies it directly, no adapter), one route —
blank `?mac=` lists everything cluster-wide, non-blank switches to ranked
search — gated on `capNetRead` like every other live-network-state read.
Wired into `router.go`'s `Options.FDB` and `cmd/vnproxd/server.go`.

**Frontend (`web/src`).** `api/types.ts` gained `FDBRow`/`FDBOwner`/
`FDBResponse`; `api/fdb.ts` wraps `GET /fdb`. New `tools/MacFdbBrowser.tsx`
(search box + results table; owner badges; a guest/vnprox-known owner row
is clickable, calling the existing `useTopologyStore().select` action and
navigating to `/topology` to open that entity's inspector — reusing
`TopologyPage`'s selection state rather than building a second one), wired
into `ToolsPage.tsx` below the raw editor. `InspectorPanel.tsx` gained an
`FDB (n)` tab, shown only for bridge/ovs-bridge kinds, rendering
`fields.FDB` (runtime-narrowed via a small type guard, since `fields` is
generic JSON) with the same clickable owner deep-link.

## 3. Deviations / scope notes (flagged, not silent)

- **No new `internal/collect` poll loop for FDB.** The card's "FDB reader
  … exposed via peer API and merged" reads as if FDB might need its own
  collection/fan-out path. It doesn't: `Bridge.FDB` rides along on the
  `Links()` read `hostPollOnce` already performs for every node (local and
  peer), so it is cluster-wide for free the moment `resolveBridge` carries
  it through. `GET /api/peer/host/fdb` exists as its own documented
  endpoint per the task's explicit instruction, but nothing in the actual
  merge path calls it — it's a standalone "just the FDB, not the full link
  state" read, not part of the collector's data flow. Flagging in case a
  dedicated FDB poll/cache was the intended design instead.
- **`FDBEntry` excluded from `Bridge.fieldMap`/`ownershipRules`.** Every
  other multi-source `Bridge` field goes through `pick`/provenance/delta.
  FDB is single-source and churns constantly (every MAC learn/age), so
  routing it through the same machinery would spam `topology.delta` WS
  events on ordinary traffic instead of only on real topology changes. It
  carries no provenance entry as a result — a deliberate, documented
  asymmetry with the rest of `Bridge`, not an oversight.
- **Fixture staleness is fixture-declared (`stale: true`), not
  netlink-`NUD_STALE`-derived, for `FixtureReader`.** Fixtures don't model
  live kernel neighbor-cache state at all (the same reason they never
  modeled FDB before this task); a fixture author says an entry is stale
  directly, the same way they'd declare any other observed fact.
- **No pagination on `GET /fdb`.** Unlike `/audit`/`/snapshots`, the full
  listing has no `limit`/`cursor`; search is capped at
  `topology.DefaultSearchLimit` (50, same as `/inventory/search`). A
  cluster's total learned-MAC count could exceed a comfortable single
  response at very large scale — not addressed here, matching the card's
  "S" sizing and `/lldp`'s/`/ports`' precedent (also unpaginated).
- **Owner index only covers `GuestNic`/`PhysNic` MACs**, per
  `docs/data-model.md`'s existing `Bridge`/`Bond`/`VlanIface` contract
  (none of those three carry their own MAC as an inventory field — only
  `PhysNic` does). A bond's or bridge's own MAC therefore won't resolve to
  "vnprox-known" even though the kernel reports one; extending that would
  mean adding `mac` to `Bond`/`Bridge`/`VlanIface` in `docs/data-model.md`,
  out of this card's scope.

## 4. Notes for the next agent

- `internal/topology/fdb.go`'s `buildMacIndex` is snapshot-scoped and
  rebuilt on every `FDB()`/`FDBSearch()`/`Detail()` call — fine at current
  scale (mirrors `Search()`'s own per-call full scan) but worth caching on
  the `Service` if a future task needs `GET /fdb` on a very hot path.
- The frontend's guest-owner deep-link reuses `topology/store.ts`'s
  existing `selectedId` zustand state rather than a URL param — clicking a
  deep-link from Tools navigates to `/topology` and relies on that store
  already being populated before `TopologyPage` reads it. This works
  today (zustand state persists across route changes within the SPA) but
  would need reconsideration if `useTopologyStore` is ever scoped
  per-page instead of module-global.
- Needs hardware validation: none — this task's surface is pure Go
  read-side logic (netlink `NUD_STALE` bit) plus fixture/mock-backed
  tests; the `NUD_STALE` read itself follows the same pattern
  `NUD_PERMANENT` already used in `internal/host` (T-102, presumably
  already validated).
