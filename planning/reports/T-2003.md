# T-2003 · Change review: approvals, comments, side-by-side diff — completion report

**Status:** implemented; `make check` (backend + frontend) is green; both Playwright specs
touched this round pass against the real stack.

## 1. What was built

The changeset is this product's unit of work; this card gives it a real review surface —
per-op/changeset comments, an explicit review-approval gate, a side-by-side config diff that
covers SDN alongside node-file ops, and a shareable review link — by **generalizing**
T-1703's tenant request-changeset approval queue rather than building a second mechanism.

### Backend

- **`internal/store/migrations/0034_changeset_review.sql`**: two new app-owned tables.
  `changeset_comments` (id, changeset_id, op_id '' = changeset-level, author, body,
  created_at) and `changeset_approvals` (changeset_id PK, status approved|rejected, decided_by,
  reason, decided_at — an absent row is the implicit "none" state every pre-T-2003 changeset
  is in). Both `ON DELETE CASCADE` off `changesets(id)`.
- **`internal/store/changesetcomments.go` / `changesetapprovals.go`**: the two repos
  (Insert/Get/ListForChangeset/Delete/**DeleteForOps** for comments; Get/Upsert/**Clear** for
  approvals — `DeleteForOps`/`Clear` are the op-removal/edit-invalidation primitives below).
- **`internal/change/op.go`**: `Op` gains an optional `ID` field (`json:"id,omitempty"`) — a
  stable, server-assigned identifier a comment attaches to, since nothing else about an Op is
  otherwise a stable identity (two `bridge.update`s against the same target are legitimately
  different edits). Additive to the wire envelope; a pre-T-2003 client's JSON is untouched.
- **`internal/change/review.go`** (new): `Comment`, `ApprovalStatus`/`ApprovalState`,
  `ApprovalConfig` (Required/AllowSelfApproval/Approvers — the deployment policy), and
  `Service.AddComment/ListComments/DeleteComment/ReviewApprove/ReviewReject/GetApproval`, plus
  the two unexported helpers `assignOpIDs` (stamps an id onto every op that arrives without
  one) and `cleanupOrphanedComments`/`clearApproval` (the op-removal/edit-invalidation
  machinery, called from `UpdateDraft`). `ErrReviewNotConfigured`/`ErrCommentOpNotFound`/
  `ErrSelfApprovalForbidden`/`ErrNotAnApprover` are the new error types.
- **`internal/change/service.go`**: `Config` gains `Comments`/`Approvals`/`Approval` (all
  nil-safe/optional — a `Service` built without them behaves byte-identically to pre-T-2003);
  `create`/`CreateRequest`/`UpdateDraft` call `assignOpIDs`; `UpdateDraft` additionally computes
  the removed-op-id set (comparing the *outgoing* op-id set, captured before `assignOpIDs`
  touches the *incoming* ops, against the new one) and calls `cleanupOrphanedComments` +
  unconditional `clearApproval`.
- **`internal/change/apply.go`**: `beginApply` gains the approval gate — when
  `s.approval.Required`, refuses (before any revalidation/snapshot/mutation) unless
  `isApproved` (fail-closed: no approvals store, a read error, or any status other than
  `"approved"` all refuse identically) — and `Diff` now appends the SDN config diff (below) to
  `ChangesetDiff.Files`.
- **`internal/change/apply_errors.go`**: `ErrApprovalRequired` — a new, additive apply-refusal
  error (mapped to `422 approval_required`), never a repurposing of `validation_failed`
  (changeset may be perfectly valid) or `invalid_transition` (approval is orthogonal to the
  status state machine, which is completely untouched).
- **`internal/change/diff_sdn.go`** (new): the config-diff side-by-side extension.
  `sdnConfigDiffFiles` renders up to three additional `ifaces.FileDiff` entries
  (`/etc/pve/sdn/{zones,vnets,subnets}.cfg`, the same synthetic cluster-scoped paths T-402's
  pre-apply snapshot already uses) for a changeset touching `sdn.zone/vnet/subnet.*` ops —
  before/after canonical-JSON unified diffs, computed purely by folding this changeset's own
  ops onto the **live inventory snapshot** (not a live PVE read): `projectSDNZoneConfigs`/
  `VnetConfigs`/`SubnetConfigs` mirror `validate_sdn.go`'s `effectiveZones`/etc. net-effect-
  folding style, just carrying every field instead of only the ones a particular check needs.
  Deliberately no `PVEGateway` parameter (see §3 below) — the diff route needs no live PVE
  session, unlike apply/rollback's own SDN portion.
- **`internal/api/changesets.go`**: the four new routes (`POST/DELETE .../comments[/{id}]`,
  `POST .../review/approve|reject` — **not** `/changesets/{id}/approve`, which is T-1703's
  existing tenant-request route and means something different), `changesetResponse` gains
  `comments`/`approval` (additive, `omitempty`), and a new `withReview` helper that decorates
  **every** single-changeset response (create/update/validate/apply/confirm/rollback/get, not
  only GET — see the frontend-cache note in §2) the same way `withMgmtFlag` already decorates
  `touchesMgmtPath` everywhere. `writeApplyError` gains the `ErrApprovalRequired` → `422
  approval_required` mapping; a new `writeReviewError` maps the four review-specific errors.
- **`internal/config/config.go`**: `[changesets]` section — `approval_required` (default
  `false`), `allow_self_approval` (default `true`, via the `*bool` not-set-vs-false pattern
  `rawMetrics.Enabled` already established), `approvers` (default empty = anyone with
  `netWrite`).
- **`cmd/vnproxd/server.go`**: wires `Comments`/`Approvals` repos and the `[changesets]`
  policy into `change.Service`'s `Config`.

## 2. A frontend bug this task found and fixed: the cache-clobber trap

`useChangesetQuery`/every changeset mutation hook calls `queryClient.setQueryData(changesetKey(id), <that call's own response>)`. My first pass decorated `comments`/`approval` on `GET /changesets/{id}` only. That is **wrong**: `ReviewApplyScreen` re-validates on every mount (`docs/features/change-management.md` §2: "runs again immediately before apply"), and `POST .../validate`'s response would then overwrite the query cache with an object carrying no `comments`/`approval` at all — the review screen would show an approved changeset's decision, then silently blank it the moment the screen opened. Fixed by decorating **every** single-changeset response with `withReview`, mirroring `touchesMgmtPath`'s own already-established "every route decorates this" precedent. `TestChangesetsReview_SurvivesValidateApplyConfirmRollback` (`internal/api/changesets_review_test.go`) is the regression guard: it walks create → review/approve → update (asserts the edit cleared it, but the *field* is still present) → validate, asserting every one of those responses carries the `approval` field.

## 3. AC2 — server-side enforcement, and how it's proven

**The gate lives in `internal/change.Service.Apply`'s `beginApply` (apply.go), before any revalidation, snapshot, or mutation.** It reads `changeset_approvals` fresh on every call. Nothing about the decision is client-suppliable: the request body for `POST /changesets/{id}/apply` carries no approval-related field at all (unchanged from before this task), and the check runs identically regardless of caller.

Bypass proof, at three independent layers, all in this round's new test files:

1. **Service layer, direct Go call — `internal/change/review_test.go`.**
   `TestApply_ApprovalRequired_RefusesUnapproved` calls `h.svc.Apply(...)` directly (no HTTP,
   no router) against a real `*change.Service` with `Approval.Required: true`; asserts
   `*change.ErrApprovalRequired`, that the changeset status is untouched (`draft`), and — the
   structural half of the proof — that `h.agent.stageCalls == 0` (the fake `NodeAgent` records
   every stage attempt; zero proves the gate ran before any node was ever touched).
   `TestApply_ApprovalRequired_AllowsAfterApprove`, `_RejectedStillRefuses`, and
   `_EditClearsApproval` cover the gate genuinely lifting, a rejection *not* satisfying it, and
   an edit invalidating a prior approval, respectively.
2. **HTTP layer, UI fully bypassed — `internal/api/changesets_review_test.go`.**
   `TestChangesetsApply_ApprovalRequired_RefusedByDirectAPICall` issues a raw
   `httptest.NewRequest`/`ServeHTTP` `POST /api/v1/changesets/{id}/apply` — no browser, no JS,
   no frontend code path at all — against the real router wired to a real `*change.Service`
   whose `NodeAgent` is `panicNodeAgent{}` (panics on any node touch): asserts `422
   approval_required` and that the changeset is unchanged.
   `TestChangesetsApply_ApprovalRequired_UnblockedAfterReviewApprove` proves the *converse*
   structurally: after `POST .../review/approve`, the identical apply call no longer answers
   `approval_required` — it gets far enough to reach `panicNodeAgent`, which the router's
   panic-recovery middleware turns into a `500`, proving execution actually crossed the gate.
   `TestChangesetsReviewApprove_SelfApprovalForbidden_DirectAPICall` is AC3.
3. **CLI, via `vnproxctl` — `cmd/vnproxctl/changesets_review_test.go`.**
   `TestRemoteChangesetsApply_ApprovalRequired_RefusedByVnproxctl` drives
   `vnproxctl remote changesets create -f ...` then `vnproxctl remote changesets apply <id>`
   end to end against a real `*change.Service` (same `panicNodeAgent{}` proof) behind a small
   HTTP shim that calls the real `Apply`/`Create` methods and maps the real error value the
   same way `internal/api`'s `writeApplyError` does; asserts `ExitPending` (422's documented
   exit code) and that stderr names `approval_required`. The sibling
   `_NotConfigured_AppliesFine` test is the control, proving the refusal is genuinely the gate
   and not an unrelated harness failure.

AC3 (self-approval): `TestReviewApprove_SelfApprovalForbiddenByPolicy`/`_PermittedByPolicy`/`_NotAnApprover` (service layer) and the HTTP-layer test above.

Frozen-surface analysis (docs/architecture.md §10/§13, the task's explicit warning): `change.Changeset` is **not** actually returned verbatim by any MCP tool (`internal/mcp/server.go`'s `handleChangesetCreate`/`Validate` convert through `toChangesetView`, a separate, narrower struct with no `ops`/`comments`/`approval` field at all) — I deliberately did **not** add my new fields to `changesetView` either, and `TestChangesetView_JSONSchema_Stable` (`internal/mcp/frozen_payload_test.go`, new) pins that. `*ifaces.ChangesetDiff` **is** returned verbatim by `changesets.diff` (`handleChangesetDiff` returns `diff` directly) — my SDN-diff extension only appends more `FileDiff` entries to the existing `Files` slice, no field renamed/removed; `TestChangesetDiff_JSONSchema_Stable` (`internal/change/ifaces/frozen_mcp_payload_test.go`, new) pins `FileDiff`/`OpSummary`'s field set. Both regression guards follow the exact pattern `internal/sim.TestRuleRef_JSONSchema_Stable` established for T-2002-bug-01. `Op.ID` is additive to the wire envelope and, since `changesetView` carries no `ops` field, is not reachable from any MCP tool at all. The `internal/apicontract` golden-fixture suite (the changeset-API-freeze enforcement per docs/architecture.md §13.3) required regenerating 12 golden files after `Op.ID` landed — reviewed line-by-line (`git diff`): every changed line is exactly `+ "id": "<op-id>"`, nothing else. `redactedChangeset` (`internal/apicontract/golden_test.go`) was extended to redact the new per-op id the same way it already redacts the changeset's own id, keeping the goldens deterministic run-to-run.

## 5. Deviations / scope notes (flagged, not silent)

- **No new `vnproxctl` subcommands for comments/review-approve/review-reject.** The task's
  vnproxctl requirement was specifically the AC2 apply-refusal bypass proof (done, §3);
  `vnproxctl remote changesets` already has no `comment`/`review` subcommands and I didn't add
  any, to keep this round's surface area to what the card actually asks for. A follow-up card
  could add them following `runRemoteChangesetsGetOrAction`'s existing pattern.
- **List (`GET /changesets`) does not carry `comments`/`approval`.** Only the canonical
  single-changeset responses do (see §2's decoration list) — a deliberate choice to avoid an
  N+1 store read per list item; the "resumable drafts" list has never needed per-item findings/
  plan detail either, and nothing in the card requires it there.
- **SDN config-diff before/after uses the live inventory snapshot, not a live PVE read**
  (`diff_sdn.go`'s own doc comment). This means its per-vnet/subnet id spelling follows
  `internal/change`'s own Ref.ID convention (`<zone>/<vnet>`, the bare CIDR), **not** the
  apply-time snapshot's PVE-wire-id spelling (`pve.SDNVnetID`/`SDNSubnetID`'s bare-name
  conversion) — a pre-existing convention split T-402 already introduced at that exact
  boundary (documented in those functions' own doc comments), not something this task created;
  I inherited it rather than solved it, and noted it explicitly in `diff_sdn.go`. Both
  representations are internally self-consistent (a real before/after pair from the same
  source); only the exact string spelling of a vnet/subnet id can differ between the review-
  time diff and the snapshot taken moments later at apply.
- **Reject does not transition the changeset's lifecycle `status`.** A rejected changeset stays
  `draft`/`validated`, still editable — approval is deliberately orthogonal to the status state
  machine (review.go's own package doc comment), the same way `T-1703`'s tenant approve *does*
  transition status (`requested` → `draft`) because that one genuinely is a lifecycle gate on a
  different axis (whether apply is reachable at all vs. whether it's *authorized*).
- **`internal/api/tenant.go`'s two `toChangesetResponse` call sites** (`handleApproveChangeset`,
  `createRequestChangeset`) do **not** get `withReview` decoration — they also don't carry
  `touchesMgmtPath` decoration today (a pre-existing gap predating this task); left as-is
  rather than expanding scope into T-1703's own file.
- **`internal/change/ifaces.FileDiff.Node` is `""` for the three new SDN entries** (cluster-
  scoped, no single owning node) — the frontend's File-diff tab header now conditionally omits
  the `node:` prefix rather than rendering an empty one.

## 6. Notes for the next agent

- **The route-vs-drawer interaction is the one real trap here.** `AppShell` mounts exactly one
  `<ChangesetDrawer/>` app-wide; anything that wants to show `ReviewApplyScreen` must go through
  `useChangesetDrawerStore` (`setActiveId`/`openReview`), never mount a second instance
  directly — I found this the hard way (the e2e spec's own navigate-to-the-shared-link step
  caught the resulting duplicate-dialog bug before it shipped; see `ChangesetReviewPage.tsx`'s
  doc comment).
- **`Op.ID` is now the stable identity a future feature can hang per-op state off of** (not just
  comments) — `assignOpIDs`/`opIDSet` (review.go) are generic enough to reuse.
- **T-2002's flagged gap** ("none of the nine frozen MCP tools has a payload regression guard")
  now has two more instances closed (`changesetView`, `ChangesetDiff`/`FileDiff`/`OpSummary`) —
  seven of nine still have none; a good candidate for finishing that card's own follow-up scope.
- **Any new e2e spec that leaves a changeset in a non-terminal status (`draft`/`validated`)
  pollutes every other spec in the same run.** `useResumableDraftsQuery` is not scoped by
  author, so `ChangesetDrawer` treats any such leftover as an "other draft" and refuses to fully
  hide (`changesets.spec.ts`'s T-207 walkthrough asserts exactly that at its end). Discard (or
  apply) whatever you stage before your test ends — see `change-review.spec.ts`'s
  `discardChangeset` helper for the direct-API pattern (mirrors `federation.spec.ts`'s
  `detachCluster`).
- **A real, pre-existing SPA bug, unrelated to this task, worth a ticket:** after
  spotlight-search → open an entity's inspector → close it with Escape, the *next* client-side
  nav-rail `<Link>` click updates `window.location` but the routed page content doesn't swap
  (verified with a throwaway debug spec, not committed — see §4's `changesets.spec.ts` bullet
  for the full repro). Direct navigation (`page.goto`) to the same route works fine, so the
  trigger is specifically that search/inspector-close → nav-click sequence. I did not chase this
  into `InspectorPanel.tsx`/`TopologyPage.tsx`/the router setup — none of which this task
  touched — since it's outside T-2003's scope, but `web/e2e/changesets.spec.ts`'s read-only
  spot-check test now fails on it honestly (previously it was passing a stale-DOM false
  positive on an unrelated `getByText` ambiguity, then failing anyway one assertion later; see
  §4 for both fixes I did make to the test itself).
