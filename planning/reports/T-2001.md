# T-2001 · Federation cluster editor UI — completion report

**Status:** implemented; `make check` green except a pre-existing, unrelated `npm audit`
gap (reported below, not silenced).

## What was built

`/federation/clusters` has had full CRUD routes, audit coverage, and capability gating
since T-1201 with no UI at all — attaching a cluster meant hand-crafting a `POST` with a
credential in it. This card closes that gap:

- **`web/src/settings/FederationClusters.tsx`** — the editor surface, mounted at
  `/settings/federation` (linked from a new "Federation" `Section` on `SettingsPage.tsx`,
  following its existing `Section` pattern rather than inventing a new page shape).
  Mirrors `AlertRules.tsx`'s list+detail-panel layout: attached clusters on the left
  (name, apiUrl, status badge), an attach/edit form on the right.
  - **Attach/edit form** covers both credential kinds (`ticket` username/password/realm,
    `token`), with client-side validation mirroring `internal/api/federation.go`'s own
    checks (name, absolute http(s) apiUrl, credential required on attach).
  - **Credential is write-only end to end.** `toFormState` never populates credential
    fields from a fetched cluster (the API never returns one — `federationClusterResponse`
    has no credential field at all), so there is nothing to leak into the DOM on selection.
    An edit that doesn't touch the credential fields (`credentialTouched: false`) omits
    `credential` from the `PUT` body entirely, rather than sending it empty/undefined.
  - **`wgTunnelSource`'s first UI consumer.** A `TunnelLinkage` block shows the effective
    `wgTunnelId` and distinguishes `"explicit"` (an operator's own override, badged
    accent) from `"peer"` (derived from a tagged WireGuard peer, badged amber), with the
    non-obvious T-1407 consequence stated inline for the explicit case: clearing the
    override does **not** unlink a cluster that still has a tagged peer — it falls back to
    the peer-derived link instead of disappearing. An explicit link additionally gets a
    "Clear override" action (`PUT` with `wgTunnelId: ""`, name/apiUrl carried through
    unchanged, no credential); a peer-derived link has no control at all — the copy tells
    the operator to retag/remove the peer through the WireGuard tunnel editor instead.
  - **Detach confirmation** (`Dialog`/`DialogContent`) names what is lost before the
    `DELETE`: the cluster's capsule in the aggregated global topology view, cross-cluster
    IPAM conflict detection against its subnets, and its rows in global audit/search.
  - **`netWrite` gating** via the existing `hasAnyCap`/`missingCapTooltip` helpers
    (`changesets/capabilities.ts`), gated on the `""` cluster-wide capability entry — the
    registry is this daemon's own local row, not any specific node's config, the same
    cluster-wide affordance class `AlertRules.tsx` already gates the identical way. Every
    mutating control (Attach cluster / Save / Detach / Clear override) is disabled with
    the standard tooltip when missing; the list and read-only edit view render regardless.
- **`web/src/api/federation.ts`** — added `createFederationCluster`/`updateFederationCluster`/
  `deleteFederationCluster` plus their request types, alongside the T-1202 read functions
  already there. `PUT`'s omit-leaves-unchanged convention for both `credential` and
  `wgTunnelId` falls out of `JSON.stringify` dropping `undefined`-valued keys — no special
  serialization logic needed.
- **`web/src/settings/federationClustersQueries.ts`** — mutation hooks; reuses
  `useFederationClustersQuery` and `FEDERATION_CLUSTERS_QUERY_KEY` from
  `topology/federation/federationQueries.ts` (the T-1202/T-1407-followups read hook the
  connect-clusters wizard already uses) rather than duplicating the query, so there is one
  cache entry for "which clusters are attached." Mutations also invalidate
  `FEDERATION_TOPOLOGY_QUERY_KEY` so the global map's capsule view picks up attach/detach
  immediately.
- **`web/src/pages/FederationClustersPage.tsx`**, **`web/src/App.tsx`** — thin route wiring
  at `/settings/federation`, following the `AlertRulesPage.tsx` precedent exactly.

## `npm audit` gap (reported, not silenced)

`make check`'s `npm audit` step fails on advisories not present in
`web/audit-allowlist.json`: `GHSA-rgw5-rvv9-x895` (brace-expansion), `GHSA-fxqj-rqcc-2cmp`
(postcss), and five `undici` advisories (`GHSA-8xcm-r25x-g524`, `GHSA-4cwx-7wf7-3272`,
`GHSA-m8rv-5g2x-5cg5`, `GHSA-jr45-8vmc-qm54`, `GHSA-v3r7-h72x-cjcm`). This is **not** caused
by this task: `git diff main -- web/package.json web/package-lock.json` is empty — no
dependency was added or changed, `npm install` only populated `node_modules` from the
already-committed lockfile. The allowlist's four existing entries all target *different*
advisory IDs for the same packages (e.g. `GHSA-mh99-v99m-4gvg` for brace-expansion, not
`GHSA-rgw5-rvv9-x895`) and expire 2026-10-30, so this reads as new CVEs disclosed against
already-pinned transitive versions since the allowlist was last curated, not a version
bump this change introduced. Per `docs/development.md`'s CI section and this round's
briefing ("report it rather than silencing it"), left as-is for the next agent/maintainer
to triage and either patch the transitive deps or add reasoned allowlist entries.

## Deviations from the task card

- **"Tunnel linkage surfaced read-only"**: the card's deliverables list calls this
  read-only, while the design-guidance note ("an operator who doesn't know [the clearing
  consequence] will be confused by their own UI") reads as implying an actual clear
  affordance exists. Resolved by treating `wgTunnelSource` itself as strictly computed/
  read-only (never a value this UI lets an operator set directly) while still exposing one
  narrow, explicitly-labeled mutating action — "Clear override" — for the one case
  `docs/api.md` documents as non-obvious. No control exists to *set* a new `wgTunnelId`;
  that stays the connect-clusters wizard's job (tagging a peer inside the tunnel-creation
  changeset), per T-1407-followups' own report note that the wizard, not a side-channel
  registry write, is the correct place for that.
- **`readonly-crawl.spec.ts` was not extended** to cover `/settings/federation`. That
  generic crawl's `MUTATING_VERB_RE` deny-list doesn't include "attach" or "detach" (only
  "reattach", "connect", etc.) and would need a broader regex change to catch this page's
  own verbs — a change with blast radius across every other page the crawl already covers,
  and outside this card's scope. AC4 (disabled-with-tooltip gating, read view intact) is
  instead covered directly by both the Vitest gating test and the Playwright read-only-
  session test above, which is what the card's AC5 ("Vitest for the form logic, Playwright
  for the flow") asks for. Flagging this gap for T-2004 (accessibility/design-system
  second pass), which already owns exactly this kind of coverage sweep.

## Notes for the next agent

- **T-2003 (change review) depends on this card** per the phase's dependency note, to
  "absorb the cluster-scoping concepts the editor introduces." The concept surfaced here
  worth carrying forward: a federation cluster is a *registry row this daemon owns*, edited
  outside the change engine (direct CRUD, no stage/validate/diff/apply/confirm) — unlike
  every node-config mutation. If T-2003's review surface gains cluster-scoping, keep that
  distinction visible rather than implying cluster attach/detach goes through changeset
  review too.
- **`web/e2e/federation-clusters.spec.ts` reuses the default webServer fleet's "west"
  instance** (`127.0.0.1:38006`, `single-node.yaml`) exactly as `federation.spec.ts` does —
  no new port pair was added. `playwright.config.ts` runs `workers: 1, fullyParallel: false`
  so spec files never race each other for that shared instance's federation registry rows;
  this spec attaches/detaches its own uniquely-timestamped cluster name and cleans up via
  the UI's own Detach flow, leaving no residue for other specs.
- One flaky-looking but harmless thing observed while iterating: a `npx playwright test`
  run failed once with `pvemock: serving: listen tcp 127.0.0.1:48006: bind: address
  already in use` — transient (the port was free moments later on retry), consistent with
  this round's briefing that sibling agents are running their own e2e fleets concurrently
  on the same ports. Not a bug in this change; just retry if it recurs.
