# T-1104 · Event stream & automation tokens — report

**Status:** complete. Implemented by the subagent; committed by the orchestrator after the agent stalled at the commit step (deferred to a background `make check`). The orchestrator verified the code independently before committing (see Verification).

## What was built
- `internal/store/migrations/0011_api_tokens.sql` + repos — the app-owned `api_tokens` (id, name, token_hash, scopes_json, created_by, created_at, last_used_at, revoked_at) and `webhooks` tables.
- Bearer-token middleware alongside the existing session-cookie path, converging on the SAME capability-derived request context; bearer requests skip CSRF (not cookie-based) but stay rate-limited and are audited per use. A new `automation` scope drawn from the exact `internal/auth/caps.go` capability set gates the event/webhook routes. A token's scopes can never exceed the creating user's own derived capabilities at creation time.
- `POST /tokens` (one-time reveal) / `GET /tokens` (no secret) / `DELETE /tokens/{id}` (revoke) — audited `token.create`/`token.revoke`.
- A new WS topic `"events"` (automation scope): a superset envelope REUSING the existing `changeset.status`/`drift.changed`/`findings.changed` producers (not duplicated) plus a new `audit.appended` event.
- Webhook registration `POST/GET/DELETE /webhooks` — vnproxd POSTs the same envelope with an `X-VNPROX-SIGNATURE` HMAC-SHA256 header (mirrors the peer-API HMAC construction), retried with backoff; N consecutive failures raise a `webhook_unhealthy` finding, cleared on recovery.
- `docs/api.md` (Tokens/Webhooks route tables, `events` topic, `audit.appended` shape) and `docs/security.md` (token model, distinguished from the PVE ticket bridge).
