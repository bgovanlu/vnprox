# T-402 · SDN ops & apply orchestration

## 1. What was built

SDN mutations through the change engine, with the orchestrated cluster apply, per docs/features/sdn.md §4 and docs/data-model.md §3.

**Backend**

- **`internal/pve/sdn.go`**: write methods for the sdn.zone/vnet/subnet.* op family — `Create/Update/DeleteSDNZone`, `Create/Update/DeleteSDNVnet`, `Create/Update/DeleteSDNSubnet` — plus two identifier-convention helpers, `SDNSubnetID` (CIDR → PVE's dash-form wire id, e.g. `10.0.0.0/24` → `10.0.0.0-24`) and `SDNVnetID` (internal/change's `<zone>/<vnet>` Ref.ID → PVE's bare vnet name). Both document a real landmine discovered while wiring the actual write calls: internal/change's own Ref.ID conventions for these two entity kinds (established before this task) don't match PVE's own wire ids, and a literal `/` can't appear in a single URL path segment — every write/read call now converts at that boundary.
- **`internal/pvemock`**: a new per-node `SDNZoneStatusFail` mock override (`POST /mock/nodes/{node}/sdn-status-fail`, mirroring `NetworkReloadFail`'s exact pattern) — models a node whose SDN apply task itself succeeded but which nonetheless failed to realize the config, a failure mode no pre-apply validator could have predicted (unlike a genuinely-missing bridge, which the existing zone-status bridge check already catches pre-apply). This is what backs acceptance criterion 4's failure injection.
- **`internal/change`**:
  - `validate_sdn.go` (new): `sdnValidate` — zone bridge existence on every member node (simple/vlan zones, honoring a `bridge.create` in the same changeset) and vnet tag uniqueness within a zone, both blocking errors (real PVE would itself fail to apply either). Wired into `ValidateWithSafety` between the referential and safety classes. Zone node coverage turned out to already be fully covered by T-202's referential class (an empty `nodes` list is valid PVE semantics — "no restriction" — confirmed by an existing golden test I didn't want to contradict), so no new code was needed for that part of the card.
  - `validate_advisory.go`: `checkVxlanMTU` — a vxlan/evpn zone's MTU left with no headroom for VXLAN's 50-byte overhead over the assumed 1500-byte underlay warns (never blocks) with a one-click fix clamping to 1450 (acceptance criterion 3).
  - `validate_safety.go`: `vnetDeletionGuardFindings` — `sdn.vnet.delete` with running guest NICs still attached is blocked, net-effect-based exactly like T-203's `guestBearingBridgeFindings` (reattach-in-same-changeset clears it, honors `allow_dangerous_ops`) — acceptance criterion 2.
  - `apply_plan.go`: `BuildPlan` gains `StepSDNStage` (one per `sdn.zone/vnet/subnet.*` op, cluster-scope PVE API calls) emitted **before** the per-node stage/reload pairs and before the trailing `sdn.apply`, matching docs/data-model.md §3's documented category ordering exactly — acceptance criterion 1.
  - `apply_seams.go`: `PVEGateway` grows `SDNStageOp` (one cluster-scope zone/vnet/subnet write), `ApplySDN` (now reads back per-zone/per-node health after the `PUT /cluster/sdn` task — docs/features/sdn.md §4's "post-apply verification"), and `SDNConfig` (the staged config the pre-apply/rollback snapshot and diff are built from) — plus this package's own `SDNConfig`/`SDNZoneConfig`/`SDNVnetConfig`/`SDNSubnetConfig` types, kept decoupled from `internal/pve` to preserve this package's existing PVE-independence (it's still pure/testable with an injected snapshot, no live PVE dependency for the validator half).
  - `apply_exec.go`: executes `StepSDNStage`/`StepSDNApply`, records the apply task's UPID/node onto the step log for a task-log deep link even on failure, and reverts the SDN portion synchronously (still holding the live `pveGW` from the same `Apply` call) when any SDN step had already mutated PVE before a later step failed. A post-apply health failure surfaces as the new `*ErrSDNZoneUnhealthy`, mapped by `internal/api` to a `422 sdn_zone_unhealthy` — acceptance criterion 4.
  - `apply_snapshot.go`: `captureSnapshotFull` additionally snapshots SDN config (as three synthetic `/etc/pve/sdn/*.cfg`-path JSON blobs) in the same "pre" snapshot row the interfaces files use.
  - `apply_sdn.go` (new): `sdnAffectedZones`, `resolveSubnetVnet`, `sdnRestoreOps` (dependency-ordered inverse-op diffing), `restoreSDN` (issues them, then re-applies so PVE's running state converges too).
  - `Rollback(ctx, id, author, pveGW)` gains a `pveGW` parameter (threaded from the API layer exactly like `Apply` already was), so a manual rollback of an `awaiting_confirm` SDN-carrying changeset can also revert it.
- **`internal/api/changesets.go`**: `Rollback` route now fetches a gateway the same way `Apply` does; new `sdn_zone_unhealthy` error-code mapping.
- **`cmd/vnproxd/changeagent.go`**: `pveSDNGateway` is the production `PVEGateway` implementation for the new `SDNStageOp`/`ApplySDN`/`SDNConfig` methods.

**Frontend** (`web/src/sdn`, `web/src/changesets`)

- `api/types.ts`: `SdnZone/Vnet/SubnetCreate/UpdateParams` + `SdnApplyParams`, extending the `OpType`/`OpParams` unions.
- `changesets/opBuilders.ts`: `buildSdn{Zone,Vnet,Subnet}{Create,Update,Delete}Op` + `buildSdnApplyOp`.
- `changesets/opSummary.ts` / `findingFields.ts`: drawer-line summaries and finding→field mapping for the new op family.
- `sdn/sdnEditorStore.ts` + `SdnEditorLauncher.tsx`: dispatches whichever SDN editor is open, mounted in `SdnPage`.
- `sdn/editors/`: `SdnZoneEditor`, `SdnVnetEditor`, `SdnSubnetEditor` (create/edit forms), `SdnVnetDeleteDialog` (the delete-with-reattach flow, acceptance criterion 2, mirroring `BridgeDeleteDialog`'s T-203 shape), `SdnConfirmDeleteDialog` (plain confirm for zone/subnet, which carry no attached-guest interlock).
- `sdn/sdnCandidates.ts`: `vnetReattachTargets`, cluster-wide vnet candidates for the delete dialog.
- `sdn/SdnPage.tsx`: "+ New zone" header action; Edit/Delete buttons and "+ VNet"/"+ Subnet" create actions on each detail panel.

This is the plain form editor (T-402's own card: "forms per entity, drawer-integrated"), not the guided per-type wizard with live topology preview docs/features/sdn.md §2 describes — that's T-403's job.

## 3. Deviations / scope notes (flagged, not silent)

- **The SDN config pre-apply snapshot is a JSON stand-in for PVE's actual `/etc/pve/sdn/*.cfg` text**, stored under synthetic paths `/etc/pve/sdn/{zones,vnets,subnets}.cfg` in the snapshot's `files_json`. vnprox has no raw-text read of those files the way it does for `/etc/network/interfaces` (the PVE API only exposes SDN config as typed zone/vnet/subnet objects) — this is the smallest reasonable extension consistent with the existing snapshot machinery that still lets rollback restore from it. Flagged per docs/development.md's definition-of-done #4; no doc change needed since docs/api.md doesn't promise a literal file format for snapshot content.
- **Identifier-convention fix, not a new decision**: internal/change's pre-existing Ref.ID convention for sdn-vnet (`<zone>/<vnet>`) and sdn-subnet (the literal CIDR) targets doesn't match PVE's own wire ids. This was already implicit in `params_sdn.go`'s doc comments (written before this task) but never actually exercised against a real write call until now. `pve.SDNVnetID`/`SDNSubnetID` convert at the wire boundary in both `cmd/vnproxd/changeagent.go`'s production gateway and the test harness's `fakePVEGateway`; `internal/change`'s own `Op.Target.ID`/`SDNVnetConfig.ID`/`SDNSubnetConfig.ID` stay in the original convention throughout — no change to the public op wire shape (docs/api.md/params_sdn.go's JSON tags are untouched).
- **`sdn.subnet.update`/`sdn.subnet.delete`'s missing vnet field**: I deliberately did **not** add a `Vnet` field to `SdnSubnetUpdateParams`/`SdnSubnetDeleteParams` (which would have been the more obvious fix, mirroring `SdnSubnetCreateParams`), because several pre-existing golden/coverage tests assert these ops are valid with empty params. Instead, `resolveSubnetVnet` resolves the owning vnet at execution time from the changeset's own preceding ops or the live inventory snapshot. This isn't exercised by any of the four acceptance criteria (none of them update/delete a pre-existing subnet), but it's implemented and unit-tested (`apply_sdn_internal_test.go`) for correctness. Its inventory-snapshot fallback depends on the poll cycle having a `SdnSubnet` entity for the subnet, which is realistic but not instantaneous after a just-created subnet outside the same changeset.
- **The "post" (post-commit) snapshot still only captures node interface files, not SDN config.** `Confirm()` has no `PVEGateway` parameter to read SDN config with (unlike `Apply`/`Rollback`, which do), and no acceptance criterion needs it — flagged as a follow-up rather than plumbed through speculatively.
- **The auto-rollback timer (commit-confirm timeout) cannot revert an SDN-carrying changeset's SDN portion**, and neither can a daemon crash mid-apply recovery (`recoverInterruptedApply`) — both run with no live user session, and SDN's revert has no daemon-level, ticket-less write path the way node-file rollback does (`docs/architecture.md` §6: "no privilege escalation through vnprox" — there's no local root-owned equivalent to direct interfaces-file writes for `/etc/pve/sdn/*.cfg`). This is architecturally correct, not an oversight: SDN zone/vnet/subnet staging can't itself sever vnprox's own connectivity the way a bad `ifreload` can, which is the entire reason the commit-confirm timer/local-timer machinery exists in the first place — so the *synchronous* in-Apply-call rollback path (which does have a live gateway) is where AC4's scenario is actually exercised and is the one that matters. The auto-rollback/crash-recovery gap is recorded (a `RollbackLog`/audit entry, not a silent no-op) rather than pretending to succeed.
- **No per-op capability enforcement (`sdnWrite` vs `netWrite`) exists at the changeset HTTP route level.** `internal/auth.CapSDNWrite` was declared (derived from PVE's `SDN.Allocate` privilege) before this task but never checked anywhere — the changesets routes gate every op family uniformly behind the blanket `netWrite`. This is a pre-existing gap spanning every op family with its own capability (firewall ops have the identical gap), not created or worsened by T-402. The frontend does use the more precise `sdnWrite` flag for its own disabled-affordance UX (a real, useful improvement — a user with `netWrite` but not `SDN.Allocate` now sees the SDN editors correctly disabled with the right tooltip), but that's client-side-only until the backend gets equivalent per-op enforcement. Flagged, not fixed — a cross-cutting change belonging to whichever task owns the capability model's completion.
- **Subnet-with-allocations deletion guard** (listed in the task card's deliverables alongside the vnet guard) was **not implemented**: `internal/inventory` has no `IpAllocation` entity kind yet (a known, already-documented gap — `validate_projection.go`'s `allocsBySubnet` comment calls this out explicitly), and T-405 (Visual IPAM) is the task that adds it. Implementing a guard against data that doesn't exist in the inventory model would have meant either fabricating state or reaching for a live PVE read from inside a supposedly-pure validator (breaking this package's testability contract) — I did neither. No acceptance criterion required it.
- **QinQ zones are not bridge-checked** by `zoneBridgeExistenceFindings` (only `simple`/`vlan`) — this codebase's `SDNZoneSpec`/inventory model has no QinQ-specific bridge semantics distinct from `simple`/`vlan` to check against, and guessing at one risked a false positive/negative more than skipping it.
- **Needs hardware validation**: `pve.SDNSubnetID`/`SDNVnetID`'s exact conversion rules (dash-for-slash on subnet CIDRs; bare-name for vnets) are inferred from this codebase's own `pvemock` fixtures/tests (`three-node-vlan.yaml`'s subnet ids, `sdn_test.go`'s existing create call) rather than verified against a live PVE cluster — worth a hardware check before shipping, same caveat T-401's report already flagged for the read-side `?running=1` convention.
