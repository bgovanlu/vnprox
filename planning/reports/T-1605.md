### The four checks
- **`rogue_dhcp_server`** — a DHCP-offering source whose MAC is not the subnet's
  configured PVE-SDN DHCP range owner (`GET /sdn/dhcp` truth). `refs` names the
  offending MAC/interface, never the whole subnet.
- **`unexpected_ra`** — an IPv6 RA from a source not in the known PVE-configured RA
  set. A documented **no-op against an empty feed** (never fires, never errors)
  until T-1404's RA feed lands.
- **`arp_spoof_suspected`** — an IP whose resolved MAC churns ≥3 times within a
  2-minute trailing window (the `arpChurnTracker`), distinguishing rapid
  oscillation from a single DHCP-renewal reassignment.
- **`unknown_mac_protected_segment`** — a MAC learned (bridge FDB) on a bridge in
  `[security] protected_segments` that matches no known guest/PhysNic/LLDP-neighbor
  MAC in the inventory graph. Graph+config-derived — needs no feed.

## Deviations / notes for the next agent
- **No migration.** Rogue detection is stateless (churn state is in-memory, mirroring
  `stpBurstTracker`); `0024_oidc.sql` and `kv_test.go`'s `24` literal are untouched,
  as the task anticipated.
- **Two of four checks are live in production today; two are honest no-ops** pending
  their collectors — matching the card's own framing:
  - `arp_spoof_suspected` is fed by `internal/neighbor`'s cluster-wide table (live).
  - `unknown_mac_protected_segment` is graph+config-derived (live).
  - `rogue_dhcp_server` needs a raw DHCP-traffic / lease-file **server-identity**
    observation collector, which does not exist yet — the adapter supplies an empty
    offer feed (no false negatives), and the check logic + tests are complete.
  - `unexpected_ra` is a real no-op until **T-1404** (Phase 14) ships the RA feed —
    the check's own tests stub that feed's interface, exactly as the card scoped.
- **Design note.** The `unknown_mac_protected_segment` check reads bridge FDB and
  the known-MAC set directly from the inventory snapshot inside the engine, so it
  runs without the `RogueProvider` seam. The three feed-driven checks go through the
  seam. `protected_segments` matches bridge names (a bridge is the segment); VLAN-id
  matching could be added later if operators want per-VID protected segments.
- **Neighbor node attribution.** `ipam.Observation` (what `neighbor.Service.Neighbors`
  returns) carries IP+MAC but not node/iface, so the production `arp_spoof` finding's
  `nodes` is empty; the fixture path exercises node attribution via
  `NeighborObservation.Node`. If a future task threads node/iface through the neighbor
  source, the finding will pick it up with no check change.
- **Needs hardware validation:** the `rogue_dhcp_server` and `unexpected_ra`
  production feeds cannot be exercised against real PVE here; their check logic is
  fixture-proven but the live observation wiring is deferred to their collectors.
