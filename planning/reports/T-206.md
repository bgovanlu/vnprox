## 1. What was built

### Storage — `internal/store`

| Piece | What |
|---|---|
| `migrations/0002_snapshot_blobs.sql` | New forward-only migration: content-addressed `blobs` table (`sha256` PK, `content_zstd`, `size`), normalized `snapshot_files` (snapshot,node,path)→blob reference table, and a `note` column on `snapshots` for manual snapshots. |
| `blobs.go` | `BlobRepo`: `Put` (zstd-compress, `INSERT OR IGNORE` keyed on sha256 — the dedup), `Get` (decompress), `PruneOrphans` (anti-join delete of blobs no surviving snapshot references). |
| `snapshots.go` | `SnapshotRepo` gains `InsertFiles`, keyset-cursor `ListPage` (`"<takenAt>:<id>"` token per docs/api.md's `?limit=&cursor=`), and `Prune(cutoff, pinCutoff)` — deletes expired snapshot+snapshot_files rows **except** committed-changeset snapshots within the pin window. |
| `audit.go` | `AuditFilter` + cursor-paginated `ListPage` (user/action/target/result/changesetId/from/to, all ANDed), same keyset-cursor scheme. |
| `retention.go` | `SnapshotRetention` (one pass: snapshot prune → blob orphan reclaim) and `RunSnapshotRetentionLoop`, mirroring `MetricSampleRepo.RunPruneLoop`'s runGroup-actor contract. Defaults keep=90d, pin=7d. |

### Change engine — `internal/change`

- **Blob-backed snapshot capture** (`apply_snapshot.go`): `captureSnapshot`
  now stores each file's content once via `BlobRepo.Put` and persists
  `files_json` as `[{node,path,sha256}]` (no inline content) plus
  `snapshot_files` rows. Reads hydrate content from the blob store; a
  legacy pre-0002 row with T-205's inline `content` still decodes (fallback
  in `decodeSnapshotFiles`) since a SQL migration can't zstd-backfill.
  `Service.Config` gains `Blobs`; `applyConfigured()` now requires it.
- **Snapshot restore → draft, the general mechanism** (`restore_ops.go`):
  `restoreOpsForNode(node, targetContent, liveContent)` parses both
  interfaces(5) files through T-102's parser + T-104's entity ingest and
  structurally diffs the entities, emitting typed create/update/delete ops
  (bridge/bond/vlan/physnic-MTU; port membership via
  `bridge.port.add/remove` since `bridge.update` deliberately has no Ports
  field; name reused across kinds → delete+recreate). This **completes the
  T-205 deferral**: `ErrInverseUnsupported` is gone; rollback of a
  committed changeset (`buildRestoringOpsFromSnapshot`, `apply_restore.go`)
  now diffs the changeset's own pre-snapshot against live, which handles
  delete/update ops (and any op mix) that per-op inversion could not.
- **Snapshot service surface** (`snapshots_service.go`): `ListSnapshots`
  (paginated), `GetSnapshot` (metadata+file list), `CreateManualSnapshot`
  (captures every inventory-known cluster node; audited `snapshot.create`),
  `DiffSnapshots(from, to|"live")` (per-(node,path) unified diffs via
  T-204's `ifaces.UnifiedDiff`), `RestoreSnapshot` (→ normal draft via
  `Service.Create`; audited `snapshot.restore`).
- **F-10 (audit phase-2, assigned to this task): 7-day rollback window.**
  `Rollback` of a committed changeset now refuses with typed
  `*ErrRollbackWindowExpired` (→ 409 `rollback_window_expired`) once
  `now > committedAt + windowDays`; audited as
  `changeset.rollback/window_expired`. The window is
  `Config.RollbackWindowDays`, wired by the daemon to
  `[retention].snapshot_pin_days` so the offer can never outlive the
  pinned pre-snapshot it needs. Default 7 (`DefaultRollbackWindowDays`),
  matching spec §4 and `store.DefaultSnapshotPinDays`.

### API — `internal/api`

- `snapshots.go`: docs/api.md's five snapshot routes exactly. Reads gated
  netRead; manual-create and restore gated netWrite+CSRF (a restore is a
  normal draft creation). List returns `{items, nextCursor?}`.
- `audit.go`: `GET /audit` with user/action/target/result/changesetId/

- `router.go`: `Options.Snapshots`/`Options.Audit` + two mount calls.

### CLI — `cmd/vnproxctl` (AC4, the disaster path)

`snapshots list|restore` and `rollback-now` are now real and **fully
daemon-independent — the documented mechanism is: read `vnprox.toml` for
`storage.db_path` → open the SQLite store directly with the same
`internal/store` package the daemon uses (WAL mode also tolerates a live
daemon) → decompress the snapshot's blob(s) → write
`/etc/network/interfaces` locally (after writing a timestamped
`.vnprox-backup-*` copy of the current file, kept on success) → exec
`ifreload -a` directly. No HTTP anywhere on this path.**

- `snapshots restore <id>`: root-only (`os.Geteuid()`), picks the local
  hostname's file from the snapshot (`--node` override), restores +
  reloads with restore-backup-and-re-reload on a failed ifreload
  (mirroring `hostNodeAgent`'s sequence), audits directly to the DB as
  `snapshot.restore.cli` attributed to `root@cli(vnproxctl)`, and prints
  which *other* captured nodes still need their own local restore.
- `rollback-now <changeset>`: for `awaiting_confirm`/`applying` changesets
  (the dead-daemon disaster), restores the local node from the
  changeset's pre-snapshot and marks the row `rolled_back`/`failed`
  directly (the legal transitions from those states) so a restarted
  daemon's `ArmPendingRollbacks` doesn't re-arm over the fixed state. A
  `committed` changeset is refused with a pointer at `snapshots restore`
  (its rollback is a reviewed restoring draft — that needs the daemon;
  the file-level equivalent is exactly the snapshots-restore command,
  which is how docs/deployment.md words the recovery flow).
- All host-touching seams (`euid`, hostname, ifreload, paths, clock) are
  injected (`cliEnv`) — the tests run the full path against a temp dir
  with a fake ifreload and a real seeded SQLite file, **no daemon
  anywhere**.

## 3. Deviations from the task card (with reasons)

1. **New dependency: `github.com/klauspost/compress` (zstd).**
   docs/data-model.md names the blob format `content_zstd`; stdlib has no
   zstd. klauspost/compress is pure Go (keeps the no-cgo property of
   `modernc.org/sqlite`), the de-facto standard, and is now listed in
   docs/development.md's table. This is the required justification note.
2. **Diff viewer is unified-only.** The card says "side-by-side/unified
   diff viewer"; I read the "/" as either-or and shipped unified (the same
   format the API returns and the review screen uses). A side-by-side mode
   is a pure-frontend addition over the same `parseDiff.ts` output if
   product wants it.
3. **Restore flow hands off at the draft, not "into the changeset
   drawer".** T-207 owns the drawer and is being built concurrently; the
   History page creates the draft via the documented API and names it in a
   toast. When T-207's drawer lands, it will list the draft automatically
   (it's a normal draft); a deep-link/auto-open is a one-line follow-up in
   the drawer's own code, deliberately not reached into from here to avoid
   cross-worktree conflicts.
4. **`rollback-now` scope: in-flight changesets only; committed → pointed
   at `snapshots restore`.** docs/deployment.md's own troubleshooting text
   assigns the "restore the pre-snapshot" recovery for confirmed-bad
   changes to `snapshots list/restore`, and a committed changeset's proper
   rollback is a *reviewed restoring draft* (spec §4), which cannot exist
   daemon-down. Marking a committed row rolled_back directly would also
   violate the status machine (committed is terminal). The refusal message
   teaches the right command.
5. **Manual snapshots capture nodes known to the inventory graph.** With
   collectors down/empty, `POST /snapshots` captures nothing (empty node
   list) rather than guessing; pre/post snapshots are unaffected (their
   node set comes from the plan). Cluster-wide capture of *peer* file
   content shares T-304's NodeAgent peer-routing caveat below.
6. **`/audit` route documented for the first time.** docs/api.md had no
   audit endpoint despite the spec's §8 Audit UI; added the route + shape
   to the doc in this change, per docs/development.md's DoD rule. Same for
   the pagination envelope (`{items, nextCursor}`) — the doc named the
   params but no response shape; the envelope is now documented.
7. **F-10 window is configurable via `snapshot_pin_days`, not hardcoded
   7.** The spec's 7 days is the default; an operator raising the pin gets
   a matching longer rollback offer, and the two can never diverge in the
   dangerous direction (offer > pin). Flagging since the spec text says
   "7 days" flatly.

## 4. Residual risk / notes

1. **`vnproxctl`'s ifreload exec and real `/etc/network/interfaces`
   semantics are untested against real ifupdown2** — same hardware-
   validation item as T-205's `hostNodeAgent`; the file logic is
   unit-tested against a temp dir with a fake reload. **Needs hardware
   validation.**
2. **`vnproxctl` restore/rollback restores the LOCAL node only** (by
   design — daemon-down, there is nothing to coordinate through). It
   prints the other captured nodes so the operator runs it per node.
   T-304's peer routing does not change this command.
3. **Snapshot scope is still `/etc/network/interfaces` only.** SDN/
   firewall config files (and therefore T-205 §4.4's "SDN-apply rollback
   needs SDN config captured") remain out: capturing them needs read
   surfaces (`/etc/pve/sdn.*`, firewall files) that no task has delivered
   yet. The blob/dedup/retention/restore machinery is path-generic
   (`{node,path,sha256}` throughout), so adding a file class is additive.
   Flagged for T-303/T-304 planning.
4. **Restore-op synthesis has documented, review-visible gaps**
   (restore_ops.go doc comment): autostart/bond-comments/miimon aren't
   modeled by `internal/inventory` entities, so a *recreated* entity gets
   autostart=true and loses those two cosmetic fields; clearing a field to
   empty inherits the T-205-documented change→ifaces adapter gap for
   pointer-to-zero "remove" semantics; OVS bond re-creation is refused
   (typed error) rather than approximated because `inventory.Bond` doesn't
   carry `ovs_bridge`. Every restore goes through the normal review
   screen, so all of these are visible in the diff before anything
   applies.
5. **Pre-0002 snapshot rows are not backfilled into the blob store** —
   they keep working via the inline-content fallback, they just don't
   dedup. Dev-only data (T-205 never shipped); acceptable.
6. **`GET /snapshots` is "cluster-merged" trivially** — one daemon's DB.
   True for pre/post snapshots (the coordinating daemon captures all
   affected nodes' files into its own store), but each node's *manual*
   snapshots live in that node's DB until T-303's fan-out. The audit
   query is likewise single-node with the fan-out-ready shape the card
   asked to design for (filter+cursor per node, merge by `at` keyset).
7. **`web/e2e` untouched**: no Playwright spec added for History/Audit —
   the existing e2e harness boots only topology fixtures; History needs
   applied changesets to exist first, which is T-207's walkthrough
   territory. Vitest covers the logic per the ground rules.

## 5. Anything the next agent must know

- **T-207 (editing UI):** `POST /snapshots/{id}/restore` returns a normal
  draft changeset (201) — surface it in the drawer; consider auto-opening
  the drawer when `location.state` carries a draft id from History (the
  toast currently just names it). No shared web files were changed except
  the two `pages/*.tsx` placeholder bodies.
- **T-303 (fan-out):** `store.AuditRepo.ListPage`'s keyset cursor
  (`at:id`) merges across nodes by comparing tuples; `AuditFilter` is the
  per-node query shape. Same for `SnapshotRepo.ListPage`.
- **T-304:** `vnproxctl` is local-only by design (see §4.2); the daemon's
  snapshot capture for peer nodes rides on whatever NodeAgent routing
  T-304 adds — `captureSnapshot` is already node-parameterized.
- **Status-machine note:** `rollback-now` writes
  `awaiting_confirm→rolled_back` / `applying→failed` directly to the DB
  (documented in cmd/vnproxctl/rollback.go) — both legal transitions, but
  it is the one code path that bypasses `change.Service`; anyone adding
  transition side effects (e.g. WS broadcasts on state change) should
  remember the CLI can't emit them.
- **`ErrInverseUnsupported` is gone** (was T-205's deferral marker);
  `ErrRestoreUnsupported` (OVS-bond recreate) and
  `ErrRollbackWindowExpired` (F-10) are the new typed errors, both mapped
  in `writeApplyError`.
