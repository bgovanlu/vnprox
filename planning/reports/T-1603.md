# T-1603 · Microsegmentation review & dry-run UX — completion report

## What I built

The frontend review/dry-run UX over T-1602's existing `POST /microseg/propose` + `POST /microseg/dry-run` routes. This card owns no synthesis logic and introduces no enforcement path outside the ordinary ChangesetDrawer. No Go was touched (no backend change was required — the API and the `cmd/vnproxd` adapter already exist from T-1602); no migration and no new changeset op were added.

### `web/src/microseg/` (new directory)
- **`MicrosegPlanner.tsx`** — launched from the guest firewall inspector (embedded in `FirewallPage`'s `GuestPanel`). Calls `POST /microseg/propose`, renders the proposal as "*N rules cover X% of this guest's observed-good traffic*" with the uncovered-flow count stated plainly beside it (never rounded to "everything"), the anomaly-excluded count and already-covered-group count surfaced, and the proposed policy as a rule table. Hosts the dry-run controls (training window + held-out window), the `DryRunReport`, and the "Stage as changeset" action.
- **`DryRunReport.tsx`** — renders T-1602's honest **four-bucket** report. **Would-have-blocked** and **Cannot-determine** are surfaced FIRST and PROMINENTLY (dedicated, coloured sections with `role="alert"` when nonzero), never folded into a rosy summary. Would-allow / Ungoverned are the reassuring buckets and sit below, collapsed by default. The would-block section is always present and shows zero rows when empty (a positive "no flow would be blocked" note), so "checked, none" is unmistakable and never confused with a missing/error state.
- **`FlowRefTable.tsx`** — renders a `MicrosegFlowRef[]` in the same column shape as the Flow Explorer's rows (Time / Direction / Peer / Proto / Port / Bytes, + a Reason column for cannot-determine), reusing `flows/proto.ts`'s `protoName` and the shared `Table` components rather than a new flow table.
- **`format.ts`** — `formatCoveragePct` (the "never round a sub-100 coverage up to 100%" honesty helper), `formatBytes`, `formatFlowTime`.
- **`queries.ts`** — `useMicrosegProposeMutation` / `useMicrosegDryRunMutation` (TanStack mutations: each is an explicit, on-demand, read-only synthesis a reviewer triggers, never a background poll).

### Shared/API layer
- **`web/src/api/microseg.ts`** — `proposeMicroseg` / `dryRunMicroseg` (through the shared `apiFetch` wrapper, per "no fetch in components").
- **`web/src/api/types.ts`** — added `MicrosegFlowRef`, `MicrosegProposal`, `MicrosegDryRunReport`, matching `internal/api/microseg.go`'s JSON exactly (all four buckets typed as always-present arrays; `stagedOps: Op[]`; honesty fields).
- **`web/src/firewall/FirewallPage.tsx`** — mounts `<MicrosegPlanner guestRef={selected} />` in the guest inspector.

### Staging path (no bespoke apply)
"Stage as changeset" hands the server-computed `stagedOps` (`fw.rule.create` ops) into the existing drawer via `useDrawerActions().addOps` — the same draft-accumulation path every other editor uses — then opens the drawer on the just-staged changeset (`setActiveId`). Review and apply happen entirely through the normal changeset lifecycle. Staging is disabled until the current proposal has been dry-run at least once, and re-proposing invalidates that enablement (dry-run state is tied to the current proposal in component state and cleared on every new propose).

### Docs
- `docs/features/firewall.md` gained a "§7 Microsegmentation" section describing the propose → dry-run → stage flow and the four-bucket honesty contract (AC6).

## Deviations from the task card

1. **Launch point.** The card says the planner is launched "from a guest's or security group's inspector." I wired the **guest** inspector (`FirewallPage`'s `GuestPanel`), which is the shipped, routable inspector surface. There is no standalone security-group inspector page in the current UI (security groups live in the Objects tab as an object list); wiring a per-group launch would need a group-inspector surface that doesn't exist yet. The planner component itself is guest-ref-driven exactly as T-1602's API is (`POST /microseg/propose` takes a guest ref only), so this matches the backend contract; a group-scoped entry point is a small follow-up once a group inspector exists.
2. **AC4/AC5 e2e are `test.skip`, not passing runs.** Reason: the missing `[flows]` dev-fixture seeding described above. This is the only part of the card's acceptance not provable end-to-end from this worktree; everything else (AC1, AC2, AC3, AC6) passes under `make check`. Flagged rather than worked around by inventing a backend fixture loader (out of scope for an M UX card, and would risk the "no backend change" boundary).

- `GET /firewall/rulesets?scope=group&name=<group>` (`internal/api/firewall.go`), returning a security group's own `{name, comment?, rules}` — its own rule list was previously only visible in aggregate via `GET /firewall/objects`' usage counts, never on its own.

Shows the group's own rules, the guests it actually reaches (`GET /firewall/effects`, reused verbatim — not recomputed), and a guest picker that mounts the **exact same** `<MicrosegPlanner guestRef=.../>` component the guest-scoped launch (`FirewallPage`'s `GuestPanel`) uses.

Because the group-scoped launch point renders the identical `MicrosegPlanner` component rather than a second implementation, "the planner's proposal shape must match what the guest-scoped launch produces" (T-2002 AC3) holds by construction — there is only one code path from a guest ref to a proposal, regardless of whether the guest was reached by picking it directly or by picking it through a group.
