# T-701 completion report — Subnet gateways in the guided flow

## What was built

**Frontend (`web/src/sdn/wizards/`, `web/src/ipam/nextFree.ts`)**
- `web/src/ipam/nextFree.ts`: added `firstUsableIPv4(cidr)`, a pure IPv4 CIDR → first-usable-address
  helper (network+1 for /30 or wider, the network address itself for /31 or /32), mirroring
  `internal/ipam/addr.go`'s server-side convention and `internal/change/validate_fix.go`'s new
  `firstUsableIP` so the wizard's live guess and the validator's computed fix always agree.
- `web/src/sdn/wizards/SubnetStep.tsx` (new): the shared "Addresses" step extracted from all five
  wizards' copy-pasted subnet block. Gateway pre-fills to the CIDR's first usable address as the
  user types (via `firstUsableIPv4`), refined to the live allocation grid's own free address once
  `useIpamAllocationsQuery` resolves for a CIDR that overlaps a subnet vnprox already has IPAM data
  for (T-405's shared-component contract) — never overwriting a gateway the user typed themselves.
  An explicit "This network has a gateway" / "Keep this network isolated — no gateway" radio choice
  replaces the old silently-empty field; SNAT is disabled (with a plain-English reason) until a
  gateway is set; zone-type-specific gateway copy (`strings.ts`'s `gatewayZoneCopy`) explains what
  the gateway means for simple/vlan/qinq/vxlan/evpn; an EVPN-only live cross-check warns when SNAT
  is on but the wizard's own `exitNodes` selection is empty.
- `SimpleZoneWizard.tsx`, `VlanZoneWizard.tsx`, `QinqZoneWizard.tsx`, `VxlanZoneWizard.tsx`,
  `EvpnZoneWizard.tsx`: rewired to hold one `SubnetStepValue` state and render `<SubnetStep>`
  instead of each wizard's own copy-pasted CIDR/gateway/SNAT block (EVPN's was embedded in its
  "VMs attach here" step, not a separate step — `SubnetStep` drops straight into that step's JSX).
  Review-step copy now says "(isolated, no gateway)" when the isolated choice was made.
- `strings.ts`: added `gatewayModeHasGateway`/`gatewayModeIsolated`/`gatewayModeIsolatedHelp`,
  `snatDisabledNoGateway`, `gatewayZoneCopy` (per zone type), `evpnSnatNeedsExitNode`.

**Backend validators (`internal/change/validate_*.go`)**
- `validate_codes.go`: `schema.gateway_not_in_subnet` (schema class), `sdn.snat_requires_gateway`
  (sdn class), `sdn.evpn_gateway_missing` / `sdn.snat_requires_exit_node` (advisory class, but code
  strings kept in the `sdn.` namespace since they're SDN-shaped concerns — grouped by code prefix
  per the file's existing convention, with a comment explaining the class/prefix mismatch).
- `validate_schema.go`: `schemaGatewayInCIDR` — pure per-op check (create's `cidr` field, or the
  op's own `Target.ID` for update, since a subnet's id *is* its CIDR) with a `fixSetSubnetGateway`
  fix patch.
- `validate_fix.go`: `firstUsableIP`/`offsetIP` (Go-side twin of the frontend helper) and
  `fixSetSubnetGateway`.
- `validate_sdn.go`: `effectiveSubnet`/`effectiveSubnets` (net-effect-aware subnet state, folding
  `sdn.subnet.create/update/delete` across the snapshot + changeset), `effectiveVnetZones`
  (vnet → zone), `effectiveZone` extended with `exitNodes`, `snatRequiresGatewayFindings` (blocking:
  effective `snat=true` with no effective gateway).
- `validate_advisory.go`: `evpnSubnetAdvisoryFindings` (net-effect-aware subnet → vnet → zone
  trace: warns on a gatewayless EVPN subnet, or an EVPN SNAT subnet whose zone's effective exit
  nodes are empty).
- All net-effect-aware, so a subnet/zone/vnet edited across multiple ops in one changeset (e.g. a
  `sdn.subnet.update` enabling SNAT after an earlier `sdn.subnet.create` set the gateway, or a
  `sdn.zone.update` removing exit nodes in the same changeset as the subnet) is evaluated correctly
  — and independent of op origin (wizard, plain editor, raw `POST /changesets`).

**pvemock fidelity (`internal/pvemock/sdn.go`, `internal/pvemock/ipam.go`)**
- `sdn.go`: `subnetGatewayError` rejects SNAT-without-gateway and gateway-outside-CIDR with a 400
  on both subnet create and update.
- `ipam.go`: `registerSubnetGateway` upserts/refreshes/removes a `gateway: true` IPAM entry keyed
  by (subnet CIDR, gateway IP) on every successful subnet create/update. `effectiveIpams`/
  `defaultIpamID` synthesize a `{id: "pve", type: "pve"}` entry when a fixture declares zero IPAM
  plugins (needed for `single-node.yaml`, whose `sdn:` section is empty, to have anywhere to
  register a gateway record at all) — flagged in needs-hardware-validation.md as unconfirmed
  against real PVE.

**API (`internal/api/changesets.go`)**
- `handleApplyChangeset` now fails fast with `422 pve_session_required` when the changeset's plan
  (via `change.BuildPlan`, no snapshot/mutation performed) carries any `sdn_stage`/`sdn_apply`/
  `fw_apply`/`fw_verify`/`ipam_alloc` step and `GatewayFor` returned no gateway — closing the
  "no PVE gateway available ... (no user session)" mid-apply failure the root-cause analysis
  identified as the likely literal source of the user's "no gateway" report. `handleRollbackChangeset`
  is unchanged (its existing graceful-degradation-on-no-session behavior is already correct and
  documented in `docs/api.md`).

**Docs**
- `docs/api.md`: the four new finding codes + `pve_session_required`, in the existing
  "documented retroactively" style next to T-402's sibling entry.
- `docs/features/sdn.md` §2: a "Subnet gateway semantics, by zone type" note plus a summary of the

- `planning/reports/needs-hardware-validation.md`: a new "SDN subnet gateway (T-701)" section with

## Deviations from the task card (with reasons)

1. **AC4's "validator-bypassing changeset ... fails at the `sdn_stage` step ... rollback restores"
   test could not be written as a normal `Service.Apply` call.** `beginApply` always revalidates
   `cs.Ops` immediately before transitioning to `applying` (T-203's documented safety net) and
   refuses with `ErrValidationBlocked` on any error finding — with this task's new
   `sdn.snat_requires_gateway`/`schema.gateway_not_in_subnet` checks now in place, that shape is
   *always* caught before apply, through every path a real caller can reach (`Create`,
   `UpdateDraft`, or a direct DB-row edit — `beginApply` re-validates whatever `Get` returns
   regardless of how it got there). That is the correct, intended end state of this task, not a
   gap. I did not add a validation-bypass hook to production code to make the literal scenario
   reachable through the public API — that would be a genuine safety regression for a test's sake.
   Instead, `internal/change/apply_sdn_bypass_test.go` is a new white-box (`package change`) test
   that drives `BuildPlan` → `captureSnapshotFull` → `newExecutor` → `ex.run` directly, skipping
   only `beginApply`'s validation/locking/status-transition prologue (not the actual step-execution/
   rollback machinery), against a real pvemock server. It proves pvemock's new rejection still stops
   this shape at `sdn_stage` and T-402's existing rollback restores the fixture's pre-state, if this
   shape ever reached the executor by some other route (a future validator regression, a changeset
   applied by an older vnprox build, etc.) — the defense-in-depth property AC4 is really asking for.
2. **Touched `internal/pvemock/ipam.go` and `internal/api/ipam_test.go`/`internal/api/changesets_test.go`**,
   outside the literal `internal/pvemock/sdn.go` file-territory line. Both were necessary: the
   gateway-IPAM-record write path lives in `ipam.go` (subnet writes are in `sdn.go`, IPAM state is
   in `ipam.go`), and AC4/AC5's own acceptance criteria call for a "readable via `GET /ipam/subnets`
   allocations" check and an "API layer" regression test respectively. Neither overlaps T-702's
   listed territory.
3. **`single-node.yaml`'s empty `sdn:` section has no IPAM plugin configured**, so AC4's "against
   `single-node`" gateway-registration check needed `ipam.go`'s new `effectiveIpams`/`defaultIpamID`
   fallback (synthesize a `{id: "pve"}` entry when zero are configured) — otherwise there would be
   nowhere to write the gateway record for that fixture at all. Flagged as unconfirmed against real
   PVE in `needs-hardware-validation.md`. I did not modify `single-node.yaml` itself (T-702's
   territory — it already shows a NIC-count change from that concurrent task in `git status`; my new
   pvemock test against it does not depend on NIC count).
4. **`make check`'s lint step currently fails**, but not from anything in this task: `eslint .`
   reports two pre-existing errors in `web/src/topology/EntityNode.mgmt.test.tsx` and
   `web/src/topology/InspectorPanel.tsx` — both untracked/modified files belonging to the concurrent
   T-702 agent's topology/management-path work (confirmed via `git status`), not touched by this
   task. `eslint` on every file this task touched (`web/src/sdn/wizards/`, `web/src/ipam/`) is clean
   except one benign `react-refresh/only-export-components` *warning* (not an error, doesn't fail
   the command) on `SubnetStep.tsx` for exporting both the component and the `emptySubnetStepValue`
   constant/`SubnetStepValue` type from one file — the same pattern several other shared wizard
   files already use for types (e.g. `WizardShell.tsx`'s `WizardStep`).
5. **`internal/change/validate_codes.go`'s new struct-adjacent code required a `fieldalignment`
   auto-fix** (`golangci-lint`'s govet fieldalignment check on `effectiveSubnet` in
   `validate_sdn.go`) — ran `go run golang.org/x/tools/go/analysis/passes/fieldalignment/cmd/fieldalignment@latest -fix ./internal/change/...`,
   which only reordered that one struct's field declaration order; no behavior change.

## What the next agent must know

- `SubnetStep.tsx`/`SubnetStepValue` is now the single place subnet-gateway UI logic lives; any
  future zone wizard (or a plain SDN subnet editor form, if one grows a gateway field) should reuse
  it rather than re-copying the old inline block.
- The `defaultIpamID`/`effectiveIpams` fallback in `internal/pvemock/ipam.go` changes pvemock's
  behavior for *any* fixture with zero configured IPAM plugins (not just `single-node.yaml`) — every
  IPAM write/read route now resolves through it. If a future task adds a fixture that deliberately
  wants "no IPAM available at all" as a test condition, it will need to explicitly configure a
  no-op/broken IPAM shape rather than relying on the previous "zero plugins configured" meaning
  "not resolvable."
- `planRequiresPVEGateway` (`internal/api/changesets.go`) duplicates the step-kind list
  `apply_exec.go`'s own `nil` gateway guards use; if a future task adds a new step kind that also
  needs a live `PVEGateway`, both places need updating together (or that guard list should be
  centralized — flagged here as a small, deliberately-not-fixed follow-up since it was out of this
  task's scope).
