# T-404 · EVPN/BGP status

## 1. What was built

FRR/BGP EVPN observability per docs/features/sdn.md §3: `GET /sdn/evpn/status`
aggregates every cluster node's FRR state and exposes a peering matrix,
session detail, VNI list, exit-node health, and flapping-session findings.

**Backend**

- **`internal/host/frr.go`**: `ParseBGPSummary`/`ParseEVPNVNI`, pure parsers
  for `vtysh -c "show bgp summary json"` / `"show evpn vni json"` output,
  following `lldp.go`'s exact pattern (defensive, panic-recovering,
  tolerant of shape variance). Handles: nested-per-address-family blocks
  (modern FRR) vs. the flat single-AFI shape older/simpler dumps produce;
  numeric fields as JSON numbers or numeric strings (`flexInt`, reusing
  `lldp.go`'s helper plus a new `flexInt64` for msec fields); FRR's
  parenthetical Idle-reason convention (`"Idle (Admin)"` →
  `state:"Idle", stateReason:"Admin"` — the closest thing to a "last
  error" FRR's summary JSON carries); `show evpn vni json`'s
  object-keyed-by-VNI or bare-array shapes. `ErrFRRUnavailable` mirrors
  `ErrLLDPUnavailable` exactly for the "vtysh not installed" case.
- **`internal/host/reader.go`/`netlink_linux.go`/`netlink_other.go`**:
  `Reader.FRRBGPSummary`/`FRREVPNVNI` added to the interface;
  `Real` runs fixed-argv `vtysh -c "show bgp summary json"` /
  `"show evpn vni json"` (never shell-interpolated,
  `BGPSummaryCommand`/`EVPNVNICommand` fields, overridable for tests),
  distinguishing "vtysh not installed" from other exec failures exactly
  like `LLDP` does.
- **`internal/host/fixture.go`**: `FixtureReader` delegates to a new
  `pvemockReader` method pair, mapping `pvemock.ErrFRRUnavailable` onto
  `host.ErrFRRUnavailable`.
- **`internal/pvemock`**: `NodeSpec.FRR *FRRSpec` (nil = no FRR on that
  node at all — T-404 AC2's fixture-modeled "absent FRR" case);
  `FRRSpec`/`BGPPeerSpec`/`EVPNVniSpec` YAML-tagged fixture types;
  `FixtureHostReader.FRRBGPSummary`/`FRREVPNVNI` render a node's declared
  FRR state into the same wire shapes the real parser consumes
  (`frr_render.go`'s `marshalBGPSummary`/`marshalEVPNVNI`, mirroring
  `marshalLLDP`'s "render fixture data through the real parser"
  precedent) — no separate mock-only code path.
- **`internal/peer`**: `HostReader.FRRBGPSummary`/`FRREVPNVNI` added;
  `GET /api/peer/host/frr/{bgp-summary,evpn-vni}` routes wrap the raw
  vtysh JSON as `{available, content?}` (unlike `/host/lldp`'s raw
  passthrough) so "FRR entirely absent on a peer" travels as a clean 200
  rather than an error status. `Client.FRRBGPSummary`/`FRREVPNVNI` decode
  that envelope back into `(available bool, raw []byte, err error)`. No
  protocol-version bump — following T-303's `links` / T-306's `fdb`
  precedent, new read-only peer routes are additive at the existing
  version (only routes the write/coordination path depends on force a
  bump).
- **New `internal/evpn` package**: `Service.Status(ctx)` fans out to the
  local node (via `host.Reader`) and every peer (via `peer.Client`,
  through a `nodeFRRReader`/`peerFRRReader` adapter pair mirroring
  `internal/collect/host.go`'s `nodeHostReader`/`peerHostReader` exactly),
  merges each node's BGP peers (preferring the `l2VpnEvpn`
  address-family observation for a given peer address), and derives
  exit-node health from an injected, nil-safe `SDNZoneSource`
  (`*sdn.Service` satisfies it). `flap.go`'s `flapTracker` is a small,
  mutex-guarded rolling per-(node,peerAddr) state history — the `Service`
  instance is long-lived within one daemon process and accumulates this
  history across repeated calls to `Status`, since flap detection is
  fundamentally about change over time and a single live snapshot alone
  can never show it. Individual node/peer failures never blank the whole
  response (`Status.Partial`/`FailedNodes`, mirroring `GET /audit`'s
  cluster-fan-out convention); a node with no FRR at all reports
  `frrInstalled:false` cleanly, never as a failure (AC2).
- **`internal/api/evpn.go`**: mounts `GET /sdn/evpn/status` behind the
  same `sdnRead` capability `GET /sdn` uses.
- **`cmd/vnproxd/server.go`**: wires `evpn.Service` from the same
  `realHost`/`peerClient`/`localNode`/`sdnSvc` every other node-local
  observability route already uses, with explicit typed-nil guards for
  `evpnPeers`/`evpnSDN` (the same "non-nil interface wrapping a nil
  concrete pointer" footgun `clusterStatusSource`'s own comment in this
  file already calls out).
- **`testdata/clusters/evpn-lab.yaml`**: extended with `frr:` blocks for
  all three nodes — pve1↔pve2 Established, pve1↔pve3 `Idle (Admin)`,
  pve2↔pve3 `Active`, so the fixture exercises all three matrix colors
  and gives pve3 (the zone's declared exit node) a real unhealthy
  exit-node-health case, not an all-green fixture.

**Frontend** — `web/src/sdn/` (integrated into T-401's existing SDN
cockpit page, not a separate route):

- `SdnPage.tsx` gained a tab switcher (`Configuration` / `EVPN / BGP`);
  the EVPN tab mounts the new `EvpnView`.
- `EvpnView.tsx`: findings banner (reuses the existing shared
  `FindingsList` component), the peering matrix (nodes × peer addresses,
  `StatusDot`-colored cells, click to select), a session detail panel
  (prefixes, uptime, last error/state reason, recent flap count), a VNI
  table, and an exit-node health list.
- `evpnStatus.ts`: pure logic split out for Vitest (no RTL) —
  `evpnStateEntityStatus` (Established→ok/green, Idle→down/red,
  Connect/Active/OpenSent/OpenConfirm→degraded/amber), `buildEvpnMatrix`,
  `resolveEvpnSelection`, `formatEvpnUptime`.
- `web/src/api/evpn.ts` + `web/src/api/types.ts` (`EvpnStatus`/
  `EvpnNodeStatus`/`EvpnPeer`/`EvpnVni`/`EvpnExitNodeHealth`/
  `EvpnFinding`) + `queries.ts`'s `useEvpnStatusQuery` (10s
  `refetchInterval` — flap detection needs repeated polling to become
  accurate, not just a single fetch on mount).

  oscillation (5 alternating observations) crosses the threshold, a

- `internal/api`: `evpn_test.go` — **AC1** end to end through the actual

## 3. Deviations / scope notes (flagged, not silent)

- **`GET /sdn/evpn/status`'s exact response shape and the two new peer
  routes are additions beyond docs/api.md's one-line contract**
  (`"FRR/BGP peering state per node (peers, prefixes, up/down)"`). Both
  documented in docs/api.md in this same change, per docs/development.md's
  definition-of-done #4 — the same pattern T-401/T-302/T-303/T-306 already
  established for undocumented-but-necessary route/field additions.
- **`internal/evpn.Service` is stateful (holds flap history in memory),
  unlike every other read-view service in this codebase** (`internal/sdn`,
  `internal/topology`'s query surface) which are pure per-request
  readers. This is a deliberate, necessary deviation from that pattern:
  flapping is inherently about change across repeated observations, which
  a stateless per-request read can never detect from a single snapshot.
  I judged this the smallest change consistent with the architecture
  rather than building a new background-collector subsystem
  (`internal/collect`-style) — `internal/metrics`'s own doc comment in
  `docs/architecture.md` §2 already earmarks exactly this "collector with
  its own short-horizon history" shape for counter rings, so this isn't
  a new architectural pattern, just the second package to use it. One
  consequence worth flagging: flap accuracy depends on `GET
  /sdn/evpn/status` being polled regularly (the frontend does, every
  10s, via `useEvpnStatusQuery`'s `refetchInterval`) — a client that only
  ever fetches once will never see a flapping finding regardless of
  actual session behavior. This is documented in docs/api.md's response
  shape section.
- **No protocol-version bump for the two new peer routes** — see T-303's
  `links`/T-306's `fdb` precedent, both of which were also additive reads
  at an already-shipped protocol version. Flagged explicitly in
  docs/api.md's Peer API section rather than left to look like an
  oversight.
- **`mergePeers`' address-family preference is "prefer l2VpnEvpn, else
  first-seen"**, not a full per-AFI session model — a peer negotiating
  both `ipv4Unicast` and `l2VpnEvpn` collapses to one `Peer` entry (the
  EVPN one). This matches the feature's own scope (EVPN/BGP
  *observability*, not a general BGP AFI/SAFI browser) but would need
  revisiting if a future task wants to show every AFI a session
  negotiates.
- **Exit-node health is a simple "FRR installed AND every observed peer
  session is Established" rule**, not a deeper EVPN-specific health
  model (e.g. checking the L3 VNI/VRF specifically, or route-count
  sanity). Reasonable for a first cut per the spec's one-line "exit-node
  health" ask; flagging in case a future task wants finer-grained
  semantics.
- **FRR field-name assumptions in the parser/fixture renderer are my own
  best-effort reconstruction of real FRR `vtysh` JSON**, not verified
  against a live FRR instance (no FRR/hardware access in this
  environment, per CLAUDE.md's "you do NOT have a live Proxmox cluster"
  — extended here to "no live FRR instance either"). The parser is
  deliberately tolerant (flexible int/string decoding, multiple shape
  variants, defensive against unknown/extra fields) specifically to
  absorb the gap between my reconstruction and real output. **Needs
  hardware/live-FRR validation** before shipping — flagging per CLAUDE.md's
  "real PVE access" note, extended to FRR.
- **Pre-existing gap noticed, not touched**: `FuzzParseLLDP`
  (T-302) is not registered in `.github/workflows/ci.yml`'s `fuzz` job,
  unlike `FuzzParse` (T-102) and `FuzzPeerAuth` (T-301). Out of scope for
  this task to fix; noting it here so it isn't mistaken for something
  T-404 was supposed to add and didn't.

## 4. Notes for the next agent

- `internal/evpn.Service`'s `Config.SDN` field is the exit-node-health
  seam; if a future task moves `internal/sdn`'s live-PVE-per-request
  design onto a poll cycle (T-401's own report flagged this as a
  possible future direction), `internal/evpn` picks up the change for
  free — it only depends on the small `SDNZoneSource` interface, not
  `internal/sdn`'s concrete implementation strategy.
- The peering matrix/session detail/VNI list/exit-node health UI is
  read-only, matching every other T-40x observability surface in the SDN
  cockpit — no write affordances were added, consistent with "all
  mutations flow through the change engine."
- `internal/host/frr.go`'s corpus (`testdata/frr/{bgp,evpn}/`) is a good
  starting point for hardware validation: replacing the hand-constructed
  fixture files with captured real `vtysh -c "show bgp summary json"` /
  `"show evpn vni json"` output from an actual FRR/EVPN lab, then
  re-running `TestParseBGPSummary_*`/`TestParseEVPNVNI_*`, would confirm
  or correct the shape assumptions flagged above.
