## What was built

### 1. `internal/sim` — the pure engine (new package)

`Simulate(Input, Request) Result` plus a reusable `Engine` (`NewEngine(Input)` builds indexes once; `(*Engine).Simulate` is cheap for repeated calls — the UI and the 10k benchmark). Pure over an inventory snapshot; **zero I/O imports**, lint-enforced by a new `sim-purity` depguard rule in `.golangci.yml` (verified live: a throwaway `import "net/http"` failed `golangci-lint`). Uses `net/netip` for pure address math.

Pipeline, in order (short-circuiting honestly at each stage):

- **Endpoint resolution** (`endpoint.go`): guest NIC (→ attachment bridge/VNet, effective VLAN, per-NIC firewall flag, IP from the optional side-table), IP literal (→ containing subnet/VNet), or external. Unknown entity kinds / absent NICs → fatal `not-evaluated` → `indeterminate` (never a confident verdict).
- **L2 path** (`l2.go`): shared bridge-name / VNet + fabric-VLAN domain identity; same-node adjacency; cross-node trunk checks over VLAN-aware bridge VID sets ("trunk pruning"), naming the uplink bond in the exact spec message (`"VLAN 30 is not trunked on bond0 of node pve2"`); VXLAN/EVPN overlay reachability; simple-zone node-locality; QinQ service-VLAN trunking (inner tag caveated); LLDP trunk cross-check (advisory).
- **L3 path** (`l3.go`): subnet membership; EVPN inter-VNet VRF routing; non-EVPN "no inter-VNet route" and cross-zone "no route … different zones without exit node"; external egress via SNAT / SDN exit node / plain-bridge host gateway, with the SNAT-asymmetry and inbound-DNAT caveats.
- **Firewall** (`firewall.go` + `match.go`): evaluated via **`internal/fw.Resolve`** (T-501) — not reimplemented — at each enforcement point the path crosses in PVE order (source-guest OUT, then dest-guest IN), with a tri-state matcher (proto / port / macro expansion / alias / ipset with `nomatch` / default policy). An undecidable rule (unresolvable object, or an address test against an unknown IP) short-circuits to `indeterminate` rather than guessing.
- **Caveats** (`caveats.go`): every `Result` carries a caveat list; standing "simulated / conntrack / guest-internal-firewall" notes are always appended.

`POST /simulate/path` added in `internal/api/simulate.go` (+ `simulate_test.go`), netRead-gated, wired via a `SimulatorGraph` one-method seam into `router.go` Options and `cmd/vnproxd/server.go`. Response shapes documented in `docs/api.md` (definition-of-done #4).

### 2. Verdict model — the added `indeterminate` state (flagged deviation)

`docs/api.md`'s one-liner pinned `allow|deny|unreachable`. AC5 requires "never a confident verdict" for unknown/unsupported kinds. Rendering one of the three confident verdicts in those cases would be a lie, so the engine adds a fourth verdict **`indeterminate`**, always accompanied by ≥1 `blocker`-severity caveat. `docs/api.md`'s Path-simulator section is updated in this change with a flagged note documenting it (and the full response schema) for T-504.

## Deviations & limitations (candid)

1. **`indeterminate` verdict added** to the wire (see above) — flagged, doc updated.
2. **Guest IPs are not in the inventory graph.** IPAM allocations / guest-agent reports are fetched by `internal/pve` but never ingested as inventory entities (confirmed: no IPAM entity kind, `internal/collect` doesn't poll it into the graph). The engine therefore takes an **optional `Input.GuestIPs` side-table**; the API layer currently passes none, so guest→guest questions that hinge on an address-restricted rule return `indeterminate` + `guest-ip-unknown` rather than a confident allow/deny. This is the honest outcome, but it under-delivers the "guest-agent IPs" deliverable at the HTTP layer. **Follow-up for the orchestrator/T-504:** wire resolved guest IPs (from `pve.ListIPAMs`/agent) into `Input.GuestIPs`, or add an IPAM entity to inventory. The engine, matrix, and differential tests already exercise the side-table fully.
3. **T-501 cluster→guest simplification inherited.** `fw.Resolve` folds cluster rules directly into every guest's resolved view (its documented deviation #1). The engine trusts that substrate (AC2 requires it) but **surfaces `fw-cluster-host-guest-simplification`** whenever a cluster-origin rule is decisive, so the verdict is never silently wrong per real PVE's stricter host/guest chain separation. Needs hardware validation.
4. **Node-scope firewall not applied to guest-forwarded traffic** — modeled as a caveat, not evaluated (guest↔guest bridged traffic doesn't hit host chains). Reasonable per iptables semantics; would need hardware validation for edge cases (e.g. traffic routed through the host).
5. **Did not touch `internal/fw`** (T-502 concurrency constraint). No bug found there that blocked the honesty contract.

## Needs hardware validation

- Deviations #3 and #4 (host/guest chain separation; node-chain applicability to forwarded traffic).
- LLDP-absence ⇒ "not trunked" is treated as advisory only (config VID set is authoritative), because switches frequently omit tagged VLANs from LLDP — worth confirming against real switch LLDP output.
