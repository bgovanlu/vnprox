# T-1406 · Ingress visibility

## Summary

Implemented read-only discovery of the reverse-proxy layer sitting between a port-forward and its
actual backend — HAProxy, nginx, Caddy, Traefik — behind a small `IngressDiscoverer` interface
(`Discover(ctx, Target) (ProxyState, error)`) deliberately shaped so T-1702's future plugin SDK can
make it pluggable: a plugin registers an additional vendor `Kind` against the same `Registry` map
with no change to routes or projection logic. Every vendor implementation issues only HTTP GET
requests against a target's own status/admin endpoint — never a mutating call — and discovery only
ever iterates the operator-configured `ingress_targets` app-store table, never a network scan. A
pure projection (`internal/ingress.ProjectChains`) correlates T-1403's `GET /edge/nat` port-forward
model with freshly discovered backends to draw the full WAN → port-forward → proxy guest → backend
guest chain, surfaced via `GET /ingress/status` and rendered on the Edge cockpit page.

## What I built

- **`internal/ingress`** (new package): `IngressDiscoverer` interface, `Target`/`Backend`/`ProxyState`/
  `Kind` model, `Registry` (a `map[Kind]IngressDiscoverer` that itself satisfies `IngressDiscoverer`
  — the concrete seam T-1702 extends by registering a new `Kind`), and four vendor implementations
  (`haproxy.go`, `nginx.go`, `caddy.go`, `traefik.go`), each a single GET against the vendor's own
  real status/admin endpoint convention. `chains.go`'s `ProjectChains` is the pure WAN → port-forward
  → proxy guest → backend guest correlation, decoupled from `internal/edge`'s concrete types
  (`PortForwardRef`/`GuestLookup` are this package's own structurally-identical types, converted at
  the `internal/api` call site) so this package stays a leaf with no dependency on the edge/NAT
  projection it correlates against.
- **`internal/ingress/ingressmock`** (new package, the card's fixture-family deliverable): exported
  `httptest.Server` constructors for all four vendors' status-endpoint doubles, each with a
  `Recorder` tracking every request received — reusable as-is for T-1702's future plugin-discoverer
  conformance set, the same role `internal/pvemock` plays for PVE itself.
- **`internal/store/ingress.go`** + **`internal/store/migrations/0017_ingress_targets.sql`**:
  `ingress_targets` table (id, kind, address, `credential_enc` — AES-256-GCM via the identical
  `SessionCipher` `sessions.pve_ticket_enc`/`alert_rules.target_secret_enc`/
  `wireguard_tunnels.private_key_enc` all use — addedBy, addedAt) and `IngressTargetRepo`
  (List/Get/Insert/Delete), app-owned intent only per the new-domain invariant.
- **`internal/api/ingress.go`** (new): `GET/POST/DELETE /ingress/targets` (netRead / netWrite+CSRF,
  audited `ingress.target_add`/`ingress.target_remove`) and `GET /ingress/status` (netRead, no
  request body) — the latter fans out `Discover` concurrently across every configured target
  (each independently timeout-bounded), reuses T-1403's `edge.ProjectNAT`/`buildGuestLookup` for the
  port-forward and guest-correlation inputs (no second interfaces-file read path), and calls
  `ingress.ProjectChains` to build the response's `chains[]`.
- **`internal/api/router.go`** / **`cmd/vnproxd/server.go`**: wired `IngressTargets`/
  `IngressSecretCipher`/`IngressDiscoverers` (the last defaulting to
  `ingress.NewDefaultRegistry(nil)`) into `router.Options`, reusing the existing `sessionCipher`/
  `EdgeInterfaces`/`EdgeGraph`/`EdgeIPAM` wiring rather than duplicating it.
- **Frontend** (`web/src/api/ingress.ts`, `web/src/api/types.ts` additions, `web/src/edge/edgeQueries.ts`
  extension, `web/src/edge/EdgeCockpit.tsx` extension): a new "Ingress visibility" section on the
  existing Edge cockpit page (T-1403's own "Edge layer" — a nav-rail page, not a canvas layer; see
  T-1403's report for why, and "Deviations" below) rendering each connected chain as a labeled
  `role="group"` sequence (WAN → port/proto → proxy guest → target → backend guest(s)), plus a
  minimal target-management panel (list + netWrite-gated add/remove) so the read-only invariant is
  actually meaningful in the UI (a target only ever gets polled because an operator explicitly added
  it here).
- **Docs**: `docs/api.md`'s new "Ingress visibility (T-1406)" section, `docs/architecture.md` §7's
  storage-table addition, `docs/data-model.md`'s new §10 + `CREATE TABLE` snippet.

## Deviations from the task card (with reasons)

- **Worktree base did not actually have T-1403 merged in, despite the dispatch note saying it was.**
  This worktree branched from a commit (`2e67795`, the phase-13-17 planning commit) that predates
  T-1401/T-1403/T-1404 landing on `main` — those merges happened in *other* worktrees that were
  fast-forwarded onto `main` after this worktree was created. I merged `main` into this branch first
  (a clean fast-forward, since this worktree had no prior commits of its own) to pick up
  `internal/edge`, `internal/wireguard`, `internal/ipv6`, etc. before starting any T-1406 work. Flagged
  here since the next agent picking up a sibling card (T-1405, T-1407) may hit the same stale-base
  situation and should check `git log --oneline 2e67795..main` (or the equivalent) before assuming
  its dependencies are actually present.
- **"Edge layer" is T-1403's nav-rail `EdgeCockpit` page, not a canvas/map layer.** The task card
  (and this card's own framing) says "extends T-1403's Edge layer... on the Edge layer," which in
  T-1403's original card language meant a map layer via T-901's renderer — but T-1403's actual
  shipped implementation (documented in its own report) is a plain nav-rail page with tables, not a
  canvas layer. I extended that same page rather than building a first canvas-layer integration
  T-1403 itself didn't establish; the chain visualization is a labeled DOM sequence, not a graph
  edge. If a future task adds T-1403's originally-scoped map layer, this chain visualization should
  move/adapt there too.
- **HAProxy discovery uses the HTTP `;csv` stats page, not the admin/runtime unix socket.** The card
  says "HAProxy (stats socket/CSV)"; I chose the HTTP CSV export specifically because AC4's own
  wording ("grep-verifiable, read-only HTTP verbs only") implies HTTP as the transport for every
  vendor, and a raw stats-socket command, while semantically read-only, isn't naturally expressed as
  an HTTP verb. The classic CSV stats page doesn't carry a server's dial address in HAProxy versions
  before 2.0; newer HAProxy's `addr` column does, and `ParseHAProxyCSV` uses it when present, falling
  back to the server name otherwise (documented in that file).
- **nginx correlation depends on nginx Plus's JSON API; open-source `stub_status` yields no
  backends.** This is an accurate reflection of what each format actually exposes (`stub_status` has
  no per-upstream-server data at all), not a scope cut — documented in `nginx.go`'s doc comment.
- **Traefik health is reported per-service, not per-server.** Traefik's `GET /api/http/services`
  doesn't expose per-server health independently of the owning service's `status`; documented as a
  simplification in `traefik.go`.
- **No changeset op group for `ingress_targets`.** Adding/removing a discovery target changes no
  network config, so — mirroring `alert_rules`/`webhooks`' own precedent — it's an ordinary audited
  CRUD route, not a `stage→validate→diff→apply→confirm/rollback` changeset op.
- **`docs/data-model.md` updated even though AC6 only names `docs/api.md` and `docs/architecture.md`
  §7.** Added for consistency with every other new-table task in this phase (T-1401, T-1403); noted
  here since it's additional to what AC6 literally requires.

## Notes for the next agent

- **The `IngressDiscoverer` interface T-1702 will make pluggable:**
  ```go
  type IngressDiscoverer interface {
      Discover(ctx context.Context, target Target) (ProxyState, error)
  }
  ```
  `Target{ID, Kind, Address, Credential}` is the only input; `ProxyState{TargetID, Kind, Reachable,
  Backends, Error}` is the only output. `Registry` (`map[Kind]IngressDiscoverer`, itself satisfying
  `IngressDiscoverer`) is the concrete plugin point: T-1702 should let a plugin call something like
  `registry[pluginKind] = pluginDiscoverer` (or an equivalent registration call) with **no other
  change** to `internal/api/ingress.go` or `internal/ingress/chains.go` — both already treat
  `discoverer ingress.IngressDiscoverer` as an opaque interface value, never a concrete `Registry`.
  `internal/ingress/registry_test.go`'s `TestRegistry_IsPluggable` demonstrates this exact shape
  (registering a fifth, fictitious "envoy" kind and confirming it dispatches correctly alongside the
  four shipped vendors) — a good starting point for T-1702's own conformance test.
- **The `ingressmock` doubles are the conformance set.** `internal/ingress/ingressmock` is a real
  (non-`_test.go`) package specifically so a future T-1702 plugin-discoverer test suite can import it
  directly, the same way `internal/pvemock` is imported far outside its own package.
- **Correlation only ever matches on a bare host, never host+port.** `ingress.HostOnly` strips both
  scheme and port before comparing a port-forward's `intIp` against an `ingress_targets.address` or a
  discovered backend's own `host:port` — if a future card needs port-aware correlation (e.g. two
  proxies fronting different ports on the same host IP), `HostOnly`/`ProjectChains` will need a
  second pass.
- **`GET /ingress/status` fans out concurrently** (`internal/api/ingress.go`'s `discoverAll`) with an
  8s per-target ceiling on top of each discoverer's own client timeout — a slow/unreachable target
  never delays another target's result, but a page with many configured targets will still block the
  whole response on the slowest one; if that becomes a problem, streaming partial results (e.g. over
  the WS `events` topic) would be the next step, not attempted here.
