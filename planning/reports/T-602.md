## 1. What was built

### `internal/findings` (new package) — the unified stream

One `Finding` shape (`{id, source, check, severity, detail, nodes, refs?,
fixable, docsLink?}`) and an `Engine` that composes four producers into
one deterministically-ordered, JSON-stable stream:

- **drift** (`adapt_drift.go`): adapts `drift.Finding` verbatim via a
  `DriftProvider` seam (`Findings()`/`FixOps(id)`), prefixing the id
  `"drift:"`. `internal/drift` itself is **untouched** — see §3 below.
- **lldp** (`adapt_lldp.go`): adapts `topology.VlanFinding` via an
  `LLDPProvider` seam (`VlanFindings()`), dropping `vlan_cross_check_ok`
  entries (a clean match isn't an actionable finding).
- **ipam** (`adapt_ipam.go`): an `IPAMProvider` seam already returning the
  unified `Finding` shape directly. **Deferred** — see §4.
- **health** (`health_*.go`, all new): the seven §5 checks not already
  covered by drift's own `mtu_consistency` family:
  - `health_bondslave.go` — bond slave down (from
    `inventory.Bond.SlaveDetail`, already collected; no fix).
  - `health_carrier.go` — bridge with no carrier uplink (bridge->[bond]->
    physnic resolution over already-collected `LinkUp`; no fix).
  - `health_stpburst.go` — STP topology-change bursts. **No cumulative STP
    TCN counter exists** in sysfs/netlink as vishvananda/netlink surfaces
    it, so this uses a documented functional proxy: churn in a bridge's
    live forwarding-port set (`PortNames`) within a 10-minute window,
    ≥3 changes = a "burst". **Needs hardware validation** against a real
    switched topology to confirm the proxy tracks genuine STP TCN events.
  - `health_service.go` — dnsmasq/frr down, fed by the new
    `host.Reader.Services` collector (§2).
  - `health_stalepending.go` — `interfaces.new` pending >1h. Deliberately
    a *different*, stateful check from drift's own immediate
    `pending_interfaces` (see that file's doc comment) — tracks a
    first-seen timestamp per ref and only fires past the 1h threshold.
  - `health_thresholds.go` — error/drop rate thresholds off
    `metrics.Sampler.Live()` per T-601's own report note ("no new sampler
    work required"). Defaults (1 err/s, 1 drop/s, documented as this
    task's own choice, not spec-mandated numbers) live in
    `HealthThresholds`, overridable via `Config.Thresholds`.
- `hysteresis.go`: a small `debouncer` (rise/fall consecutive-cycle
  counts) every stateful health check uses — AC3.
- `engine.go`: `Engine.Findings()` (on-demand), `FixOps(id)` (strips the
  `"drift:"` prefix and dispatches back to `DriftProvider.FixOps` — only
  drift's bridge/MTU families are computable; everything else carries a
  `DocsLink`), `RunLoop` (30s default cadence, `OnChange` fires on unified
  ID-set change — the same pattern `drift.Service.RunLoop` uses).
- `notify.go` + `pvenotify.go`: transition-based notification (AC5).
  `Engine` tracks the last-notified severity per finding id; a
  notification fires only on `new`/`escalated`/`resolved` transitions
  that meet `NotifyThreshold` (default `warning`), never on a steady-state
  repeat. `PVENotifier` (production `Notifier`) fans a transition out to
  every enabled PVE notification target via a new minimal client,
  `internal/pve/notification.go` (`ListNotificationTargets`,
  `TestNotificationTarget`).

**PVE notification API limitation (flagged, not resolved):** PVE's public
notification-target API (as understood at the time this was written) only
exposes a generic test-trigger route (`POST
/cluster/notifications/targets/{name}/test`), not a way for a third-party
caller to push arbitrary message content through a target — the target's
own secret (webhook auth header, SMTP creds) never leaves PVE. So today the
hook reliably *fires* (wiring/cadence/transition semantics fully correct
and tested), but the operator sees PVE's generic test-notification text,
not vnprox's own finding detail. Needs verification against a live cluster
/ a newer PVE API surface before this is a complete P1. See
`internal/pve/notification.go`'s doc comment for the full reasoning.

### `internal/host` — new collector: `Services`

Extended `host.Reader` with `Services(ctx, node) (map[string]bool, error)`
for `WatchedServices = ["dnsmasq", "frr"]`. Threaded end-to-end the same
way `Stats` already is:

- `Real` (Linux): `systemctl is-active <unit>` via `os/exec`
  (`services_linux.go`); a unit never installed is omitted from the map,
  not reported down. Non-Linux stub returns `ErrUnsupportedPlatform`.
- `FixtureReader`/`pvemock`: `NodeSpec.Services map[string]bool` (fixture
  override), defaulting every watched unit to `true` (healthy) when
  undeclared — no existing fixture needed changes.
- `peer.Client.Services` / `peer.Server`'s `GET /api/peer/host/services` —
  cluster-aware per the ground rules (a peer node's own dnsmasq/frr status
  is reachable the same way Stats/Links already are).
- `collect.Config.OnServices` — a new hook piggybacked on the existing
  host-loop poll tick (mirrors `OnStats`/T-601's sampler hook exactly), fed
  to `Engine.IngestServices` in `cmd/vnproxd`.

`internal/change`'s `nodeAgentReader` and every test-side fake
`host.Reader`/`peer.HostReader` implementation got a mechanical `Services`
stub (unsupported/no-op) to keep compiling — see the `host:` commit for
the full file list.

## 3. `internal/drift` refactor note (explicitly requested)

**No refactor was made.** `internal/drift`'s `Finding` type, `Service`,
`RunLoop`, `GET /drift`, and `POST /drift/{id}/fix` are byte-for-byte
unchanged. `internal/findings` composes `*drift.Service` as one of four
producers behind a new, additive `DriftProvider` interface seam (which
`*drift.Service` already structurally satisfies — no method signature
changes needed on drift's side at all).

This was a deliberate choice over renaming/generalizing `internal/drift`
into the unified package, for two reasons: (1) it keeps the diff to
exactly what T-602 needs, and (2) several other in-flight/concurrent
worktrees (T-502, T-503, T-505 per this task's own instructions, plus
Phase 4/5 work) may already depend on `drift.Finding`/`drift.Service`'s
exact current shape — changing it would risk merge conflicts or breakage
in code this agent cannot see. If a future consolidation pass wants to
fold `internal/drift` fully into `internal/findings` (or vice versa), the
seam is already in place (`DriftProvider`) to do that later as a pure
refactor with no behavior change.

## 5. Deviations from the task card, with reasons

- **STP topology-change-burst is a proxy, not a direct kernel counter**
  (§1 above) — Linux exposes no cumulative STP TCN counter through sysfs
  or through vishvananda/netlink; inventing one with unverifiable
  semantics seemed worse than a documented, defensible proxy (forwarding-
  port-set churn). Flagged as needing hardware validation.
- **PVE notification delivery doesn't carry finding content** (§1 above)
  — a genuine limitation of PVE's public notification-target API as
  understood without a live cluster to verify against; the hook's
  fire-once-per-transition *semantics* are fully implemented and tested
  (AC5), but the *payload* an operator actually reads is PVE's generic
  test-notification text today. Flagged as needing verification against a
  live cluster / a newer PVE release.
- **`GET /findings` filtering is a new query-shape addition**, not
  documented in the original `docs/api.md` contract — added in this same
  change per docs/development.md's definition-of-done #4, the same
  pattern T-302/T-305/T-601's own additive routes used.
- **Numeric thresholds for error/drop rate** (1 err/s, 1 drop/s) and
  hysteresis windows (rise/fall cycle counts, STP burst's 10-minute/3-
  change window, stale-pending's literal 1h from the spec) are this
  task's own engineering choices where the spec didn't name a number —
  documented in code (`HealthThresholds`, each check's own const block)
  and overridable via `Engine.Config`.

## 6. Anything the next agent must know

- `internal/findings.Engine` is the new composition root for "everything
  that produces a Finding". A future producer (IPAM, or anything else)
  should implement a small `XProvider` interface returning either its own
  native type (adapted in a new `adapt_x.go`) or the unified `Finding`
  type directly (like the IPAM seam) — follow `adapt_lldp.go` or
  `adapt_ipam.go` as the template, not `adapt_drift.go` (which is the one
  case with an id-prefixing/FixOps-dispatch wrinkle worth understanding
  before copying).
- The health checks' hysteresis state lives on `Engine` itself (one
  `*debouncer`/tracker per check family) — it is **not** persisted across
  a daemon restart. A restart briefly re-observes fresh (a bond slave
  already down before restart takes `RiseCycles` cycles to re-fire) —
  consistent with drift's own in-memory-only `lastIDs` state, not a new
  gap this task introduced.
- `docs/features/monitoring.md` §5 itself was intentionally left
  unedited (it's the binding spec this task implements against); the
  STP-burst-proxy and threshold-default rationale live in code comments
  and this report instead.
