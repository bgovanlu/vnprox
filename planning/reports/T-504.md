## What was built

### 1. Path simulator page (`web/src/simulator/`, new package)

`Tools → Path simulator` (`SimulatorPage.tsx`, wired into `web/src/pages/ToolsPage.tsx` as its first/flagship section):

- **Endpoint pickers** (`EndpointPicker.tsx`): a 3-way kind selector (Guest NIC / IP address / External). Guest NIC mode reuses the exact same `GET /inventory/search` client the map's spotlight search already uses (`topology/queries.ts`'s `useSearchQuery`), filtered to `kind==="guest-nic"` results, rendered in a `<ul aria-label="… guest NIC results">` (needed once the map and the picker could both show a button with the same "*guest*/*nic*" text on the same page — see the E2E section). IP mode shows a **subnet-context hint** (`ipSubnetContext.ts`, pure IPv4 CIDR-containment math over topology nodes of kind `sdn-subnet`, whose label *is* the CIDR per `docs/data-model.md`) computed entirely client-side from data already in hand — no extra network round trip.
- **Proto/port + service presets** (`servicePresets.ts`): derives presets from the existing `GET /firewall/objects` macro catalog (`internal/fw.KnownMacros`, already exposed to the frontend) rather than a second, disconnected list, per the task's own guidance.
- **Result panel** (`ResultPanel.tsx`): a verdict banner with **4 distinct colors/labels** — `allow`→emerald "Allowed", `deny`→red "Blocked", `unreachable`→amber "Unreachable", `indeterminate`→violet **"Could not determine"** (never rendered as pass/fail, with a pointer to the blocker caveats below, per T-503's honesty contract) — an always-present "Simulated" badge (unconditional, not gated on the `simulated` caveat's presence — every result from this route genuinely is a static simulation), the hop-by-hop list, a blocking-rule card with the firewall-editor deep link (AC1), a missing-link card (AC2), and the caveat list, **always rendered in full, never collapsed** (AC3 — no accordion/"show more" control exists in this component at all).
- **URL-shareable state** (`urlState.ts`): `encodeSimState`/`decodeSimState` round-trip a `SimulateRequest` through the `/tools` query string (`srcKind`/`srcRef`/`srcIp`, `dstKind`/…, `proto`, `port`); `SimulatorPage` reads it once on mount and keeps it in sync (`replace`, not `push`) as the user edits, so a plain page reload or a pasted link reproduces the exact same result (AC4).
- **Map path-highlight** (`pathHighlight.ts`): turns a result's `hops[]` into node/edge id sets by walking consecutive hop pairs against the topology's own edges (matching `toFlowElements.ts`'s `edgeId` convention, now exported), plus a `blockingNodeId` (the enforcement-point endpoint's own ref) and `missingNodeIds` (`Missing.atRef`). Fed into `SimulatorPage`'s embedded `TopologyCanvas` via `toFlowElements`'s new optional `pathHighlight` param.

## Deviations & a real bug found (flagged, not silently worked around)

1. **`internal/sim/firewall.go`'s `ruleRef` never populates `RulesetRef` for `origin: "guest"`** (only for `cluster`/`group`, where it points at the *cluster* ruleset's own ref — not useful for a deep link either way). Found while integration-testing the deny scenario against a real fixture: a naive `blockingRuleDeepLinkPath(rule.rulesetRef)` would have produced a dead link (`ref=`) for the single most common deny case ("this guest's own rule blocked it"). **Not fixed in `internal/sim`** (out of this task's scope — "pure consumer" constraint). Instead, `deeplink.ts`'s `blockingRuleGuestRef` derives the correct guest ref from the *resolved endpoint* at the blocking rule's own `enforcementPoint` (`ResolvedEndpoint.guest`, always a `guest:<node>:<vmid>` ref string for a guest-nic endpoint — confirmed via `internal/sim/endpoint.go`), which also matches T-505's own established convention (always link into the *guest's* resolved view, regardless of a rule's true origin) better than `rulesetRef` would have anyway. **Backend follow-up recommended:** populate `RulesetRef` for the guest-origin case too (or drop the field from the wire contract if it's never meant to be authoritative) so a future consumer doesn't have to know this workaround.
2. **React Flow nodes never became visible in this sandbox's headless Chromium** during E2E testing — `@xyflow/react` renders a node `visibility: hidden` until its own internal `ResizeObserver`-driven measurement lands (`@xyflow/system`'s `nodeHasDimensions`), and that measurement never arrived in this specific container (confirmed the raw `ResizeObserver` API itself does fire correctly here for a plain unrelated element — this is specific to how `@xyflow/react` observes its nodes, not a broken browser API). Fixed by supplying `initialWidth`/`initialHeight` on every constructed `FlowNode` in `toFlowElements.ts` — a documented `@xyflow/system` fallback that `nodeHasDimensions` checks *ahead of* the ResizeObserver path. This is a genuine robustness improvement (every real user currently gets a brief, likely-imperceptible "hidden nodes" flash on load too), not a test-only hack, and it unblocked the E2E map-interaction tests entirely.
3. **A right-click context-menu open/close race**: the same native `contextmenu` event that opens `ContextMenu` could immediately close it again, because the component's `window`-level `click`/`contextmenu` listeners were being attached (via `useEffect`) before that same initiating event had necessarily finished dispatching to `window`. Fixed by deferring listener attachment by one macrotask (`setTimeout(…, 0)`).
4. **No new dependency added.** Considered `@radix-ui/react-context-menu` for the right-click menu; built a small dependency-free `ContextMenu.tsx` instead (see above).

## Follow-up closed (T-2002)

The backend follow-up recommended above — `internal/sim`'s `RuleRef.RulesetRef` unpopulated for `origin: "guest"` — is closed by **populating the field correctly for every origin and keeping it**, not removing it. T-2002 initially removed the field instead (reasoning: even a fully-populated `RulesetRef` could never replace this task's own `blockingRuleGuestRef` derivation, since a cluster/group-origin rule's `RulesetRef` names the *cluster* ruleset, never the guest whose resolved view the deep link needs to open, and grepping found zero in-repo consumers) — but that removal broke a frozen contract: `cmd/vnproxd/mcpwire.go`'s `mcpSimulatePath` returns `sim.Result` verbatim as the **frozen v1 `simulate.path` MCP tool's payload** (`docs/architecture.md` §13.1, decision D10, additive-only — no field is ever removed without a version bump). An external MCP client reading `rulesetRef` wouldn't show up in an in-repo grep, so "no consumer found" was necessary but not sufficient. Caught in review before merge; reworked to restore the field with `RulesetRef` now populated for `origin: "guest"` too (`internal/sim/firewall.go`'s `ruleRef` looks up the guest's own ruleset via `e.fw.Guests[guest]`), so it's genuinely true for all three origins rather than half-true for two. `deeplink.ts`'s guest-ref derivation (`blockingRuleGuestRef`) is unchanged either way — it was never a workaround for a bug, it was always the correct design for what the deep link's target actually is, and it still deliberately ignores `rulesetRef` (a different, also-real value: which ruleset an MCP client would target with a `fw.rule.*` op, not which guest's resolved view to open). Two regression tests now guard the frozen shape: `internal/sim.TestRuleRef_JSONSchema_Stable` and `cmd/vnproxd.TestMCPSimulatePath_FrozenPayloadFields`. A follow-up bug card (`T-2002-bug-01`, `planning/tasks/phase-18.md`) proposes generalizing this guard to the other eight frozen MCP tools, which have no equivalent coverage today.
