## How capability scope is enforced server-side (the 🔒 invariants)

Enforcement is **structural**, not advisory, at three layers:

1. **Stage-only seam (compiler-enforced).** Plugin code only ever receives `plugin.Stager` (via a scoped
   `Host`). `Stager` has exactly `Create` and `Validate`. The SDK binds `*change.Service` through the
   `changeCreator` interface which lists only those two methods — `Apply`/`Confirm`/`Rollback` are not in
   the interface, so no plugin, in-process or over gRPC/procshim, can name them. Verified by
   `TestStagerSurface_HasNoMutationMethods` and `TestChangeCreatorSeam_HasNoMutationMethods` (reflection
   over the interface method sets), with `TestChangeServiceHasMutationMethods` as the control proving the
   concrete service *does* have them (so the seam deliberately withholds them). This is T-1702 AC3.
2. **Op-class ceiling (checked before `internal/change`).** `scopedStager.Create` runs `RequiredCap` over
   every op and rejects the **whole batch** with `ErrCapabilityExceeded` if any op needs a capability the
   plugin's declared `Scope` lacks — *before* calling `change.Service.Create`. A plugin scoped `{netRead}`
   cannot construct a `netWrite`-class op; a `{netRead,fwWrite}` plugin cannot sneak a `netWrite` op into a
   mixed batch. Verified by `TestScopedStager_RejectsOutOfScopeOp` / `_AllowsInScopeOp` /
   `_MixedBatchRejectedWholesale` (the fake change service records that `Create` was never reached). This
   is T-1702 AC2. The mapping is fail-safe: an unmapped/future op defaults to `netWrite` (strongest), so a
   new op can never be staged under a weaker cap.
3. **Registration ceiling (checked at install).** A plugin cannot even *register* an extension point whose
   entry ceiling its scope doesn't meet: the write-adjacent `switchDriver` requires `netWrite`, the four
   read-only points require `netRead`. `Scope` is built only from `internal/auth` AllCaps (a fabricated cap
   name is refused), so the SDK introduces **no new privilege**. Install/enable/disable/uninstall each
   write an audit row recording the scope (T-1702 AC5).

Out-of-process plugins run as supervised subprocesses (`procshim.Host`) with **no DB/file access** — only
the capability-scoped `Stager` channel. A dead subprocess degrades gracefully (the registry omits its
tiles/findings, logs, does not crash), proven by `TestFaultInjection_KillMidFlight`.

## Deviations (with reasons)

1. **Out-of-process transport is stdlib framing, not the gRPC runtime.** The card names an "out-of-process
   gRPC option" with a `.proto`. Pulling in `google.golang.org/grpc` + protoc-generated code is a **major new
   dependency** (CLAUDE.md's standard-library-first rule; the govulncheck surface in `make check`) for what the
   boundary actually needs: a supervised subprocess, a typed request/response per interface method, and
   graceful degradation. `internal/plugin/procshim` therefore carries the identical contract as
   **length-delimited proto3-JSON over the subprocess's stdio** — `wire.proto` documents the messages 1:1 with
   the Go interfaces; the transport is stdlib only. The `plugins.transport` value is still `"grpc"` (the
   out-of-process class). No new dependency was added anywhere in this task. If a true gRPC/HTTP2 transport is
   later required (e.g. for non-Go plugins over a socket), it slots behind the same `Registration` seam without
   touching the capability model.
2. **Install is a registry/config-time operation, not a bare API POST.** Per the deliverables (built-ins
   register in-process; the Hub, T-1705, installs third-party plugins through this registry), the API surface
   exposes list + enable/disable/uninstall. Install/enable/disable/uninstall are all audited at the registry
   level (AC5) regardless of trigger.

## Migration coordination note (for the next agent / merge)

Migration is numbered **0029** with **0028 intentionally absent** (reserved for a concurrent task, per the
task card). `internal/store/migrate.go` applies migrations by sorted version skipping any `<= current`, with
**no contiguity requirement**, so 0029 applies cleanly over 27. **Merge caution:** a DB already advanced to
schema_version 29 by this branch will *skip* a later-arriving 0028 (28 ≤ 29). Fresh dev/test DBs are unaffected
(they apply 27→29 in one pass). The two reserved-number branches must reconcile ordering at merge time — this
is the known cost of the reserved-number scheme the card mandated, not a bug in either branch.
