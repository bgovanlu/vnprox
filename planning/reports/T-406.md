# T-406 · DHCP management

## 1. What was built

PVE dnsmasq DHCP management per docs/features/sdn.md §5: range editing,
static reservations bound to guest MACs (kept as one dataset with the IPAM
grid), a per-node dnsmasq lease-file reader fanned out across the cluster,
and a live leases view.

**Backend**

- **Range editor on subnet forms** — already fully built by T-402
  (`SdnSubnetUpdateParams.DHCPRanges`, `SdnSubnetEditor`'s "DHCP range(s)"
  field, `apply_sdn.go`'s create/update/restore plumbing, pvemock's
  `dhcp_range_start`/`dhcp_range_end`). This task added the golden
  round-trip test T-402 didn't (`internal/change/apply_dhcp_test.go`'s
  `TestApply_SDN_DHCPRange_AddThenChange`): a changeset creates a
  zone/vnet/subnet with a range, applies, asserts pvemock's running view;
  a second changeset (after injecting the just-created zone/vnet/subnet
  into the test harness's inventory, modeling a poll cycle catching up —
  see that test's own doc comment) updates the range, applies, asserts
  the new range — acceptance criterion 1.
- **DHCP-range-overlap advisory validator** (`internal/change/
  validate_advisory.go`'s `checkDHCPRangeOverlap`, wired into
  `advisoryValidate`): a staged/updated subnet's DHCP range overlapping
  one or more existing IPAM allocations produces a `SeverityWarning`
  finding (`advisory.dhcp_range_overlap`) naming every overlapping
  address and its hostname/MAC — never blocking, since real PVE itself
  permits a DHCP pool to coexist with statically-reserved addresses
  inside its range. The allocation data is threaded in as
  `SafetyOptions.Allocations []DHCPRangeAllocation` (already-fetched,
  pure data — the same pattern `Protected` already establishes), fetched
  fresh per validation call by a new, optional `Service.Config.Allocations
  AllocationsSource` seam (`internal/change/service.go`) — nil disables
  the check, matching every other optional Config field's degraded-mode
  treatment. `internal/change` deliberately never imports `internal/ipam`
  directly: `cmd/vnproxd/changeagent.go`'s new `dhcpAllocationsAdapter`
  is the conversion boundary (mirrors `pveGateway`'s own role for every
  other `internal/pve`-typed dependency this file adapts). Acceptance
  criterion 4.
- **Static reservations bound to guest MACs, one dataset** — the change-
  engine side of this was already complete: T-405's `ipam.alloc.create`
  op already carries a `MAC` field (per that task's own report, flagged
  as "no further change-engine work needed" for T-406). What this task
  added is the *view*: `internal/ipam/dhcp.go`'s `Service.DHCP(ctx, zone)`
  builds `Reservation` rows directly from the exact same
  `allocationsByCIDR` read `Allocations`/`Subnets` already use to render
  the grid — filtering to MAC-bound, non-gateway entries on DHCP-enabled
  subnets. There is no second reservation store: a reservation created or
  released via `ipam.alloc.create`/`ipam.alloc.delete` (the same PVE-IPAM
  write both this view and the grid read) shows up or disappears from
  both surfaces from that one write. `GuestRef` correlates a reservation
  (and, separately, a lease) to a known guest by MAC, reusing the same
  MAC-index approach `merge.go`'s `allocated_dark` conflict check already
  established. Acceptance criterion 2.
- **Leases reader per node via the peer API** (T-405's exact deferred
  interface point): `internal/host/dnsmasq.go`'s `ParseDHCPLeases`
  defensively parses dnsmasq's standard `.leases` line format
  (`<expiry> <mac> <ip> <hostname|*> <client-id|*>`) — skips and counts
  any malformed line (wrong field count, unparsable expiry/MAC/IP)
  rather than erroring the whole read, recovers from a panic as a last
  resort, and is fuzzed clean (`FuzzParseDHCPLeases`, run manually for
  60s, 0 crashes across ~700k executions). `host.Reader`/`Real`/
  `FixtureReader` gain `DHCPLeases(ctx, node)`; `Real`'s implementation
  globs `/var/lib/misc/dnsmasq.*.leases` (**needs hardware validation** —
  this glob is this repo's own best inference, PVE's exact per-zone
  dnsmasq lease-file naming isn't otherwise documented here). New
  `internal/peer` route `GET /api/peer/host/dhcp-leases` (+
  `Client.DHCPLeases`) fans a peer's raw lease content back, at the
  existing protocol version 2 (additive read, no bump — same precedent
  T-303's `links`/T-306's `fdb`/T-404's `frr/*` routes set). New
  **`internal/dhcp` package**: `Service.Leases(ctx)` implements
  `ipam.LeaseSource` (T-405's exact interface point), fanning the read
  across the local node (`host.Reader`) and every peer
  (`peer.Client`/`PeerSource`), mirroring `internal/evpn`'s
  `nodeFRRReader`/`peerFRRReader` local-vs-peer adapter shape — one
  unreachable/errored node never blanks another's leases. Wired into
  `ipam.Config.Leases` in `cmd/vnproxd/server.go`. Acceptance criterion 3.
- **`GET /sdn/dhcp?zone=`** (`internal/api/dhcp.go`): `{reservations:
  [Reservation], leases: [Lease], generatedAt}`, gated on the same
  `sdnRead`-derived capability `GET /ipam/*` uses. Documented in
  docs/api.md per docs/development.md's definition-of-done #4, alongside
  the new peer route.
- **`internal/topology`**: `GuestNic` nodes gain a `"mac="` badge in
  `project.go`'s `badgesOf` (mirroring the existing `"vmid="` convention
  on `Guest`) — the data source for the frontend's guest MAC picker,
  reusing the existing `GET /topology` payload rather than adding a
  dedicated "list every MAC" route.
- **pvemock/fixtures**: `NodeSpec.DHCPLeases` (raw fixture-declared
  lease-file text, rendered verbatim by `FixtureHostReader.DHCPLeases`);
  `testdata/clusters/ipam-lab.yaml` (T-405's fixture) extended with a
  `dhcp_range_start`/`dhcp_range_end` on its subnet and a `dhcp_leases`
  corpus including malformed lines, so this task's tests reuse T-405's
  existing brownfield scenario instead of standing up a new fixture.

**Frontend** (`web/src/sdn/`, `web/src/guests/`, `web/src/ipam/`)

- `api/types.ts` + `api/dhcp.ts`: `DhcpReservation`/`DhcpLease`/
  `DhcpView` mirroring `internal/ipam/dhcp.go` field-for-field;
  `fetchDhcpView(zone?)`.
- `sdn/queries.ts`'s `useDhcpViewQuery` — 30s `refetchInterval`
  (docs/features/sdn.md §5: "live-ish 30s refresh"; leases change
  independently of any changeset apply, unlike everything else this app's
  WS `changeset.status` event drives).
- `sdn/DhcpView.tsx` (+ pure `dhcpView.ts`): a new "DHCP" tab in
  `SdnPage.tsx` (alongside T-401's Configuration and T-404's EVPN/BGP
  tabs) rendering reservations and leases as two tables, with a zone
  filter dropdown sourced from the same `GET /sdn` tree the Configuration
  tab already fetches.
- `guests/MacPicker.tsx` (+ pure `macPicker.ts`): the "MAC picker from
  inventory (guest NICs)" the task card asks for — sourced from
  `useAllGuestNicsQuery` (the same cluster-wide guest-NIC composition
  `GuestsPage.tsx` already uses), reading the new `mac=` topology badge.
  Wired into `web/src/ipam/CellDetailDialog.tsx`'s existing reserve panel
  alongside the free-text MAC field: picking an option fills the same MAC
  state `handleReserve` already turns into an `ipam.alloc.create` op (not
  a new/parallel code path), and prefills the hostname field unless the
  user already typed one.

## 3. Deviations from the task card (with reasons)

1. **Range editor and the underlying `DHCPRanges` change-engine plumbing
   were already fully built by T-402** (which landed concurrently/before
   this task per the orchestrator's context) — this task's actual new
   work for acceptance criterion 1 was the golden round-trip test, not
   the feature itself. Flagged since the task card described it as this
   task's deliverable; T-402's own report already flagged this
   dependency forward ("T-406 extends `sdn.subnet.update`'s range editor
   on the same `SdnSubnetEditor` this task built").
2. **`GET /sdn/dhcp`'s exact response shape (`Reservation`, `Lease`,
   `DHCPView`, and the `?zone=` query param) is my own design** —
   docs/api.md's original contract had no DHCP route at all (the task
   card's context doc, docs/features/sdn.md §5, only describes the
   feature in prose). Modeled closely on `GET /sdn/evpn/status`'s own
   precedent (T-404: a dedicated route, its own small seam interface,
   documented retroactively). Full shape now in docs/api.md.
3. **`GET /api/peer/host/dhcp-leases`'s `{content: string}` envelope
   (rather than FRR's `{available, content?}`) is a deliberate,
   documented choice, not an oversight**: unlike FRR (where
   installed-vs-not is a meaningful binary the UI needs to distinguish
   from "installed but nothing to report"), a node running no
   DHCP-managed SDN zone at all is the overwhelmingly common case for
   DHCP leases, not an exceptional one — an empty result is itself a
   complete, correct answer with nothing further to flag.
4. **`internal/host.Real.DHCPLeases`'s lease-file glob
   (`/var/lib/misc/dnsmasq.*.leases`) is inferred, not verified against
   real PVE** — flagged in the field's own doc comment, in docs/api.md,
   and here per CLAUDE.md's "needs hardware validation" allowance. If
   this proves wrong, only `Real.DHCPLeaseGlob`'s default needs to
   change (it's already overridable) — no other code depends on the
   exact path.
5. **The DHCP-range-overlap check (acceptance criterion 4) required a
   new, small architectural seam in `internal/change`**
   (`Service.Config.Allocations AllocationsSource`, `SafetyOptions.
   Allocations`) that the task card didn't explicitly call for. This was
   the smallest change consistent with `internal/change`'s existing
   "pure validators, live data injected by the caller" architecture
   (mirrors `SafetyOptions.Protected`'s exact shape) rather than having
   the validator package reach for a live PVE/IPAM read itself (which
   T-402's own report explicitly flagged as something they'd deliberately
   avoided for the sibling "subnet-with-allocations deletion guard" —
   "reaching for a live PVE read from inside a supposedly-pure validator
   would break this package's testability contract"). I judged the two
   cases differently: T-402's guard needed *inventory-graph* state (no
   seam existed for that at all), whereas this check's data
   (`DHCPRangeAllocation`) is exactly the same shape/freshness contract
   `Protected` already established — an optional, pre-fetched-by-the-
   caller input, not a live dependency the pure package owns. Flagged
   here since it's new surface area beyond a strict reading of the task
   card's four bullet points.
6. **No dedicated `ipamRead`/`dhcpRead` capability** — `GET /sdn/dhcp`
   reuses `capIPAMRead` (itself an alias for `capSDNRead`, T-405's own
   documented deviation), consistent with treating DHCP as the same
   SDN-adjacent read surface IPAM already is. Smallest reasonable
   extension; no new capability flag needed in `docs/api.md`'s `/auth/me`
   contract.

## 5. Anything the next agent must know

- `internal/dhcp.Service` and `internal/evpn.Service` share the exact
  same local-vs-peer fan-out shape (`nodeXReader`/`peerXReader`,
  `PeerSource`, `Config{Host, Peers, LocalNode}`) — if a future task adds
  another per-node-state-fanned-across-the-cluster read, follow this
  pattern rather than inventing a new one.
- `internal/change.AllocationsSource`/`SafetyOptions.Allocations` is a
  small, generic-looking name but is currently DHCP-range-overlap-
  specific in shape (`DHCPRangeAllocation`'s four fields). If a future
  advisory check needs different live-fetched data, either broaden this
  seam thoughtfully or add a sibling one — don't overload
  `DHCPRangeAllocation` for an unrelated purpose.
- `ipam.Reservation`'s `VMID` will be `0`/omitted for any reservation
  created via a bare `ipam.alloc.create` with only a MAC (the common
  DHCP-reservation case) — such a cell renders `CellReserved`, not
  `CellAllocated`, in the grid (`merge.go`'s existing, unchanged
  behavior: "no VMID: a manual reservation, not tied to any guest"). This
  is correct and expected, not a bug — `TestService_DHCP_
  ReservationIsOneRecordNotTwo`'s own comment calls it out explicitly so
  a future reader doesn't "fix" it.
- `internal/ipam.NeighborSource` (T-405's other deferred interface point,
  ARP/neighbor-table enrichment) remains unwired — out of this task's
  scope, still a clean follow-up candidate using the exact same
  `internal/dhcp`-style local-vs-peer fan-out shape.
- `Real.DHCPLeaseGlob`'s default path needs hardware validation (§3.4
  above) — the single place to fix if it's wrong.
