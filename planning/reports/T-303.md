# T-303 — Cluster fan-out

**Status:** complete. `make check` green (Go lint 0 issues, `go vet` clean,
govulncheck clean, `npm audit --audit-level=high` clean, full Go + Vitest
suites pass — 209/209 frontend tests, all Go packages). Full repo test
suite (including the new 3-daemon harness) run clean across 5+ repeated
invocations to check for timing-related flakiness (see §4).

## 1. What was built

**`internal/collect` — cluster-wide host poller.** `Config` gained an
optional `Peer *peer.Client` field (nil preserves the exact pre-T-303
local-only behavior — every existing caller/test). `hostPollOnce` now polls
this daemon's own node directly via `Host` (unchanged) *and*, when `Peer`
is set, every other node currently known via the peer address book learned
from the same `GET /cluster/status` poll `pvePollAll` already issues (no
extra PVE round trip). A new `peerHostReader` adapts `*peer.Client` + a
`peer.Peer` into the same small `nodeHostReader` interface the local
`host.Reader` already satisfies, so ingestion (`inventory.FromNetlinkLinks`
/ `FromInterfaces`, `Scope{Node: n}`) is identical regardless of transport
— "uniform ingestion, node-tagged, source-tagged" per the card.
`Collector.Status()` now reports one `"host"` `SourceStatus` per cluster
node (each with its own `Node` field, `ConsecutiveFailures`, etc.) instead
of a single local-node entry; a departed peer's host-scoped entities and
staleness bookkeeping are retired alongside its PVE-sourced ones. `"pve"`
and `"lldp"` are unchanged (the latter deliberately: T-302, running
concurrently, owns LLDP's own cluster-wide collection — see §3).

**`internal/peer` — new read-only routes (additive, no protocol version
bump).** `GET /api/peer/host/links` (remote netlink reads — the poller
above needs it, and it was flagged "deliberately not yet part of the
contract" in T-301's `HostReader` doc comment); `GET /api/peer/audit` and
`GET /api/peer/snapshots` (one node's own local page, filtered/
cursor-paginated exactly like the public routes) plus `Client.Port()`
(a small accessor `pve.go` needs to build peer addresses from cluster-status
rows without a second discovery call). Everything added through the
package's already-exported client/server surface; `middleware.go`,
`sign.go`, `secret.go`, `breaker.go` untouched.

**`internal/api` — audit/snapshot cluster fan-out.** New
`clusterfanout.go`: a generic `mergeClusterPage[T]` — decode an opaque
per-source cursor map, fetch up to `limit` items from every
non-exhausted source (local + peers, via `ClusterPeers`/`PeerAuditSource`/
`PeerSnapshotSource`, satisfied directly by `*peer.Client`), merge-sort by
`(at desc, tie desc, node desc)`, and compute each source's correct
resume cursor for the next page (a source whose fetched batch was only
partially consumed resumes from its first unconsumed item; one whose fetch
errored retries the exact same window next page — never losing or
duplicating an item, and never silently dropping a peer). `handleListAudit`
and `handleListSnapshots` use it only when `PeerAudit`/`PeerSnapshots` is
configured (nil ⇒ byte-identical pre-T-303 responses). Response envelopes
gained optional `partial`/`failedNodes` fields (omitted entirely on full
success, so no existing golden-shape test could break).

**`cmd/vnproxd` wiring.** `setupCollect` now also builds and returns a
`*peer.Client` (reusing the same PVE client the collectors already build,
for `GET /cluster/status`-based discovery — no second PVE client);
`server.go` wires it into `collect.Config.Peer`, `peer.Server`'s new
`Audit`/`Snapshots` readers (via new `cmd/vnproxd/peerdata.go` adapters —
`internal/peer` deliberately doesn't import `internal/store`/`internal/change`,
so this small conversion lives in the wiring layer, same pattern
`collectorHealthAdapter` already uses), and `api.Options.PeerAudit`/
`PeerSnapshots`.

**Docs.** `docs/api.md`: documented the three new peer routes, the
`partial`/`failedNodes` envelope fields, and updated the `/topology`
staleness example/prose for per-node `"host"` entries. `docs/architecture.md`
§2: flagged the new `API --> PEER` edge the component diagram doesn't show
(audit/snapshot fan-out calls `*peer.Client` directly rather than through
`internal/change`, since that data isn't change-engine-owned).

## 2. What was tested and how

- `internal/peer`: table-driven handler tests for `/host/links`,
  `/audit`, `/snapshots` (filter/cursor/limit parsing, 503 when
  unconfigured), plus a `TestTwoDaemonHarness_Links` extending T-301's
  existing two-daemon read-endpoint harness.
- `internal/api/clusterfanout_test.go`: **`TestMergeClusterPage_Property`**
  — 300 randomized trials (varying node count, per-node item count with
  heavy timestamp collisions to force interleaving, and page size) walking
  every page to exhaustion and asserting the concatenation exactly equals
  the single globally-sorted merge, with an explicit no-duplicates check —
  this is card AC3. Also a failed-then-healed-node test (no loss/
  duplication, self-heals) and a permanently-dead-node test (documents the
  "stays partial forever, never silently drops it" tradeoff).
- `internal/api/cluster_http_test.go`: HTTP-level tests through the full
  router (auth middleware, JSON envelope) proving the `peers == nil` path
  is byte-identical to before, and that a live merge with one failing peer
  produces the right merged items + `partial`/`failedNodes`.
- `internal/collect/clusterharness_test.go` + `clusterharness_ac_test.go`:
  a **real three-daemon harness** — three independent
  `*collect.Collector`/`*inventory.Graph`/`*topology.Service` instances,
  each with its own `pvemock`-backed PVE server (a fixture clone reordered
  so `GET /cluster/status` reports a different node as "local" per
  daemon) and its own `peer.Server` reachable over real loopback HTTP,
  exactly the shape `cmd/vnproxd` wires in production. Three tests map
  directly to the card's four ACs:
  - `TestClusterHarness_HostFanoutIdentical` (AC1): every daemon's graph
    ends up with a `SourceHostNetlink` contribution, and an identical
    per-node NIC fingerprint, for every cluster node — proof the fan-out
    actually crossed the peer API cluster-wide, not just locally.
  - `TestClusterHarness_PeerDownDegradesAndHeals` (AC2): killing one
    peer's listener degrades only its own `"host"`/node band
    (`ConsecutiveFailures` rising, last-known entities retained) without
    affecting any other node's; restarting the same listener (no daemon
    restarted) heals it.
  - `TestClusterHarness_NodeTagAttribution` (AC4): every daemon's view of
    every node's NIC carries exactly that node's own fixture-distinguishing
    MAC, never another node's.
  - AC1's literal wording ("any daemon's `/topology`") is exercised one
    layer down, at the inventory graph `topology.Service` projects from,
    rather than through the HTTP handler — `GET /topology` itself was
    already covered end-to-end by T-106; re-proving that projection here
    would have tested T-106, not T-303.

Every test above ran green across 5+ repeated full-suite invocations,
including the timing-sensitive 3-daemon harness (see §4 for a specific
tuning note).

## 3. Deviations / scope notes (flagged, not silent)

- **LLDP and drift left alone.** The card's last deliverable line reads
  "`GET /lldp` and `/drift` (T-305 fills logic) fan out likewise." T-302
  (LLDP, running concurrently in another worktree) explicitly owns "30s
  collector locally + via peer API cluster-wide" as *its own* deliverable,
  and neither `GET /lldp` nor `GET /drift` exists yet in `internal/api` (no
  router file for either). I did not touch `internal/collect`'s
  `lldpPollOnce` or create either route, per the task instructions not to
  block on/duplicate T-302's LLDP internals. The reusable pieces this task
  built — the cluster-wide host-fan-out pattern in `internal/collect`, and
  `mergeClusterPage`/`ClusterPeers` in `internal/api` — are available for
  T-302 and T-305 to reuse or reference; I could not guarantee they
  actually will, since I don't control that concurrent work.
- **Snapshot detail/diff/restore stayed node-local.** The card says "list
  fan-out" explicitly; `GET /snapshots/{id}`, `/snapshots/diff`, and
  `POST /snapshots/{id}/restore` still only see locally-stored snapshots.
  A snapshot created via a changeset coordinated through a *different*
  node won't resolve by id on this one yet — a reasonable follow-up, out
  of this card's literal scope.
- **`ProtocolVersion` not bumped.** The three new peer routes are
  additive-only; an older peer simply 404s on them (surfaced as a normal
  fetch error, not a crash) rather than being refused outright via
  `CheckCompatible`. This seemed better for rolling upgrades than forcing
  a hard incompatibility; flagging in case the intended policy is stricter.
- **`API --> PEER` added to the dependency graph** — see docs/architecture.md
  §2's flagged note above.
- **Peer discovery reuses the collectors' PVE client**, not a second one —
  slightly more coupling than a from-scratch design might choose, but
  avoids two independent PVE client instances (and two sets of credentials/
  connections) per daemon for what is fundamentally one `GET
  /cluster/status` view.

## 4. Notes for the next agent

- The 3-daemon test harness needed two non-obvious tuning fixes to be
  reliable, both purely test-environment artifacts (not product bugs, and
  not things to "fix" in `internal/peer`): (1) `internal/peer`'s HMAC
  signature covers a whole-second Unix timestamp plus a short-lived
  exact-replay cache, so *any* test harness polling faster than ~1s risks
  two requests to the same path colliding in the same wall-clock second
  and being (correctly) replay-rejected — the harness uses >1s intervals,
  per-daemon offsets, and a random startup stagger to avoid this; (2) the
  circuit breaker's default 15s reset timeout is real-deployment-appropriate
  but too slow for a fast test loop to wait out, so the harness overrides
  `BreakerResetTimeout` down to 1.5s via the already-exported
  `ClientOptions` field. Anyone extending this harness (T-304's own
  multi-node test needs will likely want something similar) should reuse
  `internal/collect/clusterharness_test.go`'s pattern rather than
  rediscovering these two gotchas.
- `mergeClusterPage`'s cursor-advancement rule and its correctness proof
  are written out in full in its doc comment in
  `internal/api/clusterfanout.go` — worth reading before extending it (the
  "exclusive vs. inclusive" cursor semantics bug it currently guards
  against with an explicit `c == 0` case is easy to reintroduce).
- Needs hardware validation: none of this task's surface touches real PVE
  or host syscalls beyond what T-104/T-301 already validated against
  fixtures; the peer HTTP transport itself was already flagged by T-301.
