# T-1105 — vnproxctl parity

## What I built

An HTTP-backed command family for `vnproxctl` that gives CI/GitOps parity with
the UI's read and changeset surfaces, plus the Terraform-plan-style
`vnproxctl apply spec.yaml --plan/--apply` GitOps entry point. Everything talks
only to vnproxd's documented `/api/v1` surface (`docs/api.md`) over a T-1104
bearer token — no second mutation path, no PVE username/password flow from the
CLI.

New files (all under `cmd/vnproxctl/`):

- `exitcodes.go` — the documented, stable exit-code table (see below).
- `output.go` — the shared `-o table|json` flag plumbing + JSON renderer.
- `remoteclient.go` — the bearer-token HTTP client (`doJSON`), the shared
  `remoteFlags`/`buildRemoteClient` (fails fast on a missing token before any
  dial), and the API-error→exit-code mapping.
- `remote.go` — `vnproxctl remote <subcommand>` dispatch + `topology`,
  `findings`, `drift`, `audit`.
- `remote_changesets.go` — `vnproxctl remote changesets list|get|diff|create|validate|apply|confirm|rollback|discard`.
- `applycmd.go` — `vnproxctl apply <spec> --plan|--apply` (spec import →
  diff/plan-pending exit; or apply → poll-to-committed → auto-confirm, with an
  injectable clock so the timeout path needs no real sleeps).
- `status_json.go` — `status -o json` (retrofit, without touching the existing
  table path).

Retrofitted `-o json` onto the three pre-existing commands (`status`,
`snapshots list`/`restore`, `rollback-now`) additively — the flag defaults to
`table`, so their existing output is unchanged unless `-o json` is passed.

Docs: `docs/deployment.md` gains a "vnproxctl remote/apply" section documenting
the command family, the naming-collision resolution, and the exit-code table.
`cmd/vnproxctl/main.go`'s package doc + `--help` usage updated.

## Naming-collision resolution (documented choice)

The pre-existing `status`/`snapshots`/`rollback-now` are deliberately
daemon-INDEPENDENT direct-SQLite/local-exec disaster-recovery tools (per
`main.go`'s own doc comment — "works when the daemon is down"). The new
commands are the opposite: they require the daemon up, talk HTTP, and need a
bearer token. **I put every new HTTP-backed command under its own top-level
`vnproxctl remote <subcommand>` namespace** (plus a standalone `vnproxctl
apply` for the spec/GitOps flow), leaving the three existing top-level names,
flags, and output completely untouched. This is written up in `remote.go`'s
package doc comment and `docs/deployment.md`, and pinned by the regression test
`TestRun_ExistingCommandsUnchangedByRemoteFamily` (main_test.go).

## Documented exit-code table (CI contract)

| Code | Name | Meaning |
|---|---|---|
| 0 | success | completed; for `apply --plan`, spec matches live exactly |
| 1 | error | generic/unexpected failure (404/5xx, decode error) |
| 2 | usage | bad flags/args, or `remote`/`apply` with no token — checked before any daemon call |
| 3 | pending | daemon `422 validation_failed`, OR `apply --plan` found a non-empty diff |
| 4 | auth | `401`/`403` (missing/invalid/revoked token, or insufficient scope) |
| 5 | network | daemon unreachable (dial/TLS/timeout) |
| 6 | apply-timeout | `apply --apply` didn't reach `committed` within `--apply-timeout` |

The three pre-existing commands keep their original 0/1/2 convention unchanged;
codes 3-6 are only ever returned by the new family.

## Acceptance criteria

1. **PASS** — `remote changesets list -o json` returns JSON matching
   `GET /changesets`; no token → fails fast with ExitAuth and no daemon call
   attempted. (`TestRunRemoteChangesetsList_JSONMatchesAPIShape`,
   `TestRunRemoteTopology_NoTokenFailsFastAuthExitCode`,
   `TestBuildRemoteClient_NoTokenFailsFastWithoutDialing`.)
2. **PASS** — `apply spec.yaml --plan` prints the diff and exits ExitPending
   (3) when ops are non-empty; exits 0 when the spec matches live.
   (`TestRunApplyPlan_PendingChangesExitsPendingCode`,
   `TestRunApplyPlan_CleanSpecExitsZero`.)
3. **PASS** — `apply spec.yaml --apply` end-to-end: import → apply → poll →
   auto-confirm → exit 0 on committed; a stuck changeset exits ExitApplyTimeout
   (6) with a short timeout and no real sleeps (injected fake clock).
   (`TestRunApplyApply_EndToEndSuccess`,
   `TestRunApplyApply_StuckPastTimeoutExitsApplyTimeout`.)
4. **PASS** — every new command supports `-o json`; table test asserts the flag
   is wired on each (new family + apply, and the retrofitted three).
   (`TestEveryRemoteCommandSupportsOJSON`, `TestEveryLegacyCommandSupportsOJSON`.)
5. **PASS** — naming-collision resolution documented (remote.go doc comment +
   docs/deployment.md); existing three commands' behavior/output unchanged
   (regression test `TestRun_ExistingCommandsUnchangedByRemoteFamily`, plus the
   pre-existing status/snapshots/rollback tests still pass untouched).
6. **PASS** — a revoked token gets ExitAuth on the next call.
   (`TestRunRemoteTopology_RevokedTokenGetsAuthExitCode`,
   `TestDoJSON_ErrorEnvelope`.)
7. **PASS** — `make check` green (see below).

## Testing

`make check` run in the foreground, exit 0: gofmt/vet clean, golangci-lint 0
issues, all Go tests pass, web Vitest 1124 tests pass, govulncheck clean, npm
audit clean. Backend tests use `httptest.NewTLSServer` fakes standing in for
vnproxd's `/api/v1` (every remote/apply command defaults `--insecure=true`, the
same convention `status` already uses); `apply --apply`'s poll loop is driven
by an injected `applyClock` so the timeout path is deterministic with no real
sleeps. Legacy `-o json` retrofits are tested against the same daemon-down
SQLite fixture (`seedDisasterFixture`) the pre-existing table tests use.

No live-PVE dependency: the CLI only ever speaks HTTP to vnproxd, so no
"needs hardware validation" items were introduced.

## UI surfaces intentionally excluded from CLI parity

The card scopes CLI parity to "the UI's read and changeset surfaces". I
implemented topology, findings, drift, audit, and the full changeset lifecycle
(create/validate/apply/confirm/rollback/discard) plus the spec/GitOps flow.
Deliberately **not** given CLI commands (out of scope — read views the card
didn't name, or write surfaces that are their own op families reachable via
`remote changesets create` with a hand-built ops body): SDN/IPAM/EVPN/DHCP read
views, firewall rulesets/log/analytics, metrics/flows/history, blueprints,
protected-interfaces, path simulator, token/webhook management, and the
changeset *schedule* routes (T-1103). A caller needing any of those can still
POST an arbitrary changeset via `remote changesets create -f`. Noting this so a
follow-up can extend `remote` with more read subcommands if demand appears.

## Notes for the next agent
