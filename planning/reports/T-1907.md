# T-1907 — Physical-layer progressive collapse

## What I built

Server-side physical-layer collapse in `internal/topology`, mirroring
`collapse.go`'s existing guest-layer mechanism (threshold → synthetic
summary node → expand-on-demand) rather than inventing a second pattern —
closing the last unclosed gap from T-607's docs audit
(`docs/features/topology.md` §4 has documented "physical layer collapses to
per-node summary" since v1.0; only guest-layer collapse existed until now).

- **`internal/topology/collapse_physical.go`** (new): `collapsePhysical`
  groups a node's `PhysNic` entities purely by cluster node (not by
  attachment point, unlike guest collapse) — the docs' own wording is "a
  per-node summary", singular, and a node's NICs fan out to whichever
  bonds/bridges happen to be configured, or nowhere. Above
  `DefaultPhysicalCollapseThreshold`, the individual `physnic` nodes are
  replaced with one `phys-group:<node>` pill (`"N NICs"`, worst-of aggregate
  status, `count=N` badge, `CollapsedCount`), carrying its absorbed refs
  directly on `Node.Members` (a new field — see below for why). Synthesized
  `enslaved-by`/`port-of` edges from the pill to each distinct bond/bridge
  its members fed into (badged `count=N`, painted worst-of) keep it wired
  into the L2 layer instead of rendering as an island. LLDP neighbors and the
  synthetic `KindSwitch` nodes `switches.go` merges them into are untouched
  — only bare `physnic` entities collapse (mirrors T-902's own documented
  scope cut for its client-side capsule).
- **`internal/topology/types.go`**: `DefaultPhysicalCollapseThreshold` (see
  "Threshold" below) and `Node.Members []string` (omitempty) — the new
  field a `phys-group` pill uses to carry its collapsed refs directly,
  since (unlike a guest-group pill) it has no single shared attachment
  target for the frontend to query membership from.
- **`internal/topology/project.go`**: one two-line hookup after
  `collapseGuests` — `collapsePhysical` runs on the same `nodes`/edge set,
  its group edges appended alongside the guest ones. No other change to
  `Project`'s shape.
- **Frontend** (`web/src/topology/`): `projection.ts` gains
  `isPhysGroupId`/`parsePhysGroupId` (mirroring the guest-group pair);
  `expand.ts` gains `physNicDetailToTopologyElements`/`expandPhysicalGroup`
  (fetches each member ref's own `GET /inventory/{ref}` detail — unaffected
  by collapse, since it reads the live graph directly — to reconstruct
  exactly what the uncollapsed projection would have produced); `queries.ts`
  gains `usePhysGroupExpandQuery`. `EntityNode.tsx`/`canvasDraw.ts` grow an
  `isPhysGroup` flag reusing the *exact same* pill rendering as
  `isGuestGroup` (rounded pill, "click to expand" hint) — no new component.
  `switchModel.ts`/`SwitchFaceplate.tsx`/`SwitchView.tsx` extend the uplink-
  bay/free-port rendering with the same `isGroup`/`count` pattern
  `SwitchAccessPort` already has, so the pill also renders correctly in the
  default Switch view. `TopologyPage.tsx`: `handleNodeClick` and the
  `InspectorStack` selected-ref guard now also recognize a phys-group id
  (route to expand, never the inspector); a new `PhysGroupExpansion`
  component mirrors `GuestGroupExpansion`.
- **`docs/features/topology.md` §4** reconciled (AC5): the section now
  describes T-1907's server-side collapse as the actual resolution of the
  T-607 gap, and corrects the previous "Resolved gap (closed T-902)"
  paragraph, which had claimed the gap was closed by T-902's *client-side,
  zoom-driven, v2-renderer-only* LOD capsule — a real, valuable, but
  different mechanism (renderer-density-driven, not entity-count-driven; in
  scope for `physnic`+`bond`+`ovs-bond`, not just bare NICs; not part of the
  actual `GET /topology` response). Both mechanisms are documented as
  coexisting and composing without conflict (the LOD capsule only matches
  raw `physnic`/`bond`/`ovs-bond` kinds, never the synthetic `phys-group`
  kind, so a server-collapsed node's one pill just renders at every zoom
  level while the LOD capsule remains free to additionally fold in any
  bonds it didn't absorb). `docs/performance.md` §4 and `docs/roadmap.md`'s
  Post-1.0 backlog updated to match (their prior wording said the gap "was
  never implemented" as of the T-607/T-607-audit timeframe — corrected to
  say it has since been closed by this task, without erasing the historical
  record of what T-607 actually found at the time).

## Threshold: `DefaultPhysicalCollapseThreshold = 8` (provisional)

T-1808 (scale validation on real hardware) has not run. Argument for 8,
explicitly provisional pending that data:

- At the documented §4 scale target (8 nodes × 6 NICs/node), every node's
  physical layer sits at exactly 6 — **under** 8, so collapse never engages
  at the scale the product is actually verified against. This matters:
  T-607/`docs/performance.md` §4 already measured the physical layer at only
  ~50-65 elements cluster-wide there, nowhere near the ~2,000-element render
  cap the guest-layer collapse exists to protect against. A threshold that
  collapsed at the documented target would be a behavior change against an
  already-established, already-measured baseline for no real benefit.
- 8 is the same magnitude `DefaultCollapseThreshold` already established as
  "small enough to read as individual chips, large enough that a summary
  earns its keep" for the guest-per-bridge case. Reusing it keeps one mental
  model ("more than 8 of the same kind of thing in one place collapses")
  instead of an unrelated second number invented from nothing.
- Follow-up: once T-1808 lands real per-node physical port counts (dense
  chassis, many bonds, SR-IOV PFs), revisit this number against those
  measurements specifically — the target-scale argument above only shows the
  threshold doesn't *wrongly* engage at the documented scale, not that 8 is
  the *right* number for a materially larger real deployment.

## Two real defects found getting the E2E spec green (the honest account)

### 1. Out-of-range ports (not mine to keep fixed, but mine to know about)

My original `web/playwright.config.ts` addition used ports **68006/68007**,
following this file's own established `Nx006/Nx007` pattern (8006, 18006,
28006, 38006, 48006, 58006) one increment too far. TCP ports max at 65535,
so both were invalid. Playwright's own webServer bring-up threw a bare
`TypeError: Invalid URL` while constructing the health-check URL for that
entry — **before any spec ran**, aborting the entire run and breaking all 32
specs in the suite, not just mine. Nothing in CI runs this suite (filed as
`T-1806-bug-01`), so nothing caught this before merge.

I initially misdiagnosed this as sandbox resource contention: I ran an A/B
test removing my two webServer entries and reproduced a *superficially
similar* failure (a 120s timeout instead of the `TypeError`) on an unrelated
spec, and concluded "environmental, not mine." That methodology was weaker
than it looked — my own topology source changes were still in the tree for
that comparison, and (as below) there was a second, independent defect
(a missing production build) also in play, producing a similarly-shaped
timeout for an entirely different reason. A sibling task independently ran
the same spec against a clean pre-T-1907 commit and got a clean pass, which
is what actually isolated the port defect. The merge coordinator moved my
two ports to **61006/61007** (in range, no collision) across
`web/playwright.config.ts`, `testdata/dev-physcollapse.toml`, and
`web/e2e/physical-collapse.spec.ts`, and that fix is already merged —
**recorded here for the lesson, not re-applied**: an A/B test that varies
one file while leaving the rest of a diff in the tree does not isolate that
diff, and a superficially similar failure signature is not evidence of the
same root cause.

### 2. Missing production build (mine, found and fixed this pass)

Even after the port fix, my own spec still failed both tests with `Test
timeout of 120000ms exceeded` waiting for `getByLabel('Username')` — the
login form never appeared. Root-caused by isolating my webServer pair alone
(a temporary single-pair `playwright.config.ts`, ~15s boot instead of ~2min)
and inspecting the captured trace: the server responded to `/login`,
`*.css`, and `*.js` with **HTTP 200 in single-digit milliseconds** (not
slow at all), but the browser logged `Refused to apply style ... MIME type
('text/html')` and `Failed to load module script ... MIME type of
"text/html"` — i.e. the requested asset paths were 404ing (silently, since
vnproxd's own logs showed 200 — the 200 was the SPA-fallback `index.html`
being served for every path) and the SPA's JS bundle never executed, so
React never mounted, so no login form ever appeared, regardless of how long
the test waited.

Cause: `web/dist/` in this worktree contained only a stale, previously-
committed `index.html` (referencing hashed asset filenames) with **no
`assets/` directory at all** — I had run `npx playwright test` directly
throughout this task instead of `npm run e2e` (`"e2e": "npm run build &&
playwright test"`, per `package.json`), so the production bundle was never
actually built in this worktree. Every other webServer pair I'd run
alongside it had the exact same broken `web/dist` — so this affected any
spec I ran directly via `npx playwright test`, mine or not, which is why my
own earlier "confirms environmental contention" A/B test reproduced a
failure on `mgmt-redundancy.spec.ts` too: both specs were failing for the
same reason (no built app to serve), which looked identical to, but was not,
resource contention. Fixed by running `npm run build` (regenerates
`web/dist/assets/*` with content-hashed filenames matching `index.html`)
before invoking Playwright directly. `web/dist/assets/*` is gitignored
build output — nothing to commit for this fix, only the lesson: **run `npm
run e2e`, not `npx playwright test` directly, or always build first.**

### 3. A genuine, if minor, spec defect — fixed

Once both of the above were out of the way, one real assertion bug in my
own spec surfaced: it hardcoded `10` as the collapsed NIC count and as the
"exactly these 10, nothing else" expectation. Querying the real backend
directly (`GET /api/v1/topology` against a manually-booted instance)
showed the actual `phys-group:pve1` pill's `collapsedCount` was **12**, not
10, and its status **`unknown`**, not the `down` I'd expected from the
fixture's one deliberately-link-down NIC.

Root cause, confirmed via `internal/host/netlink_linux.go` (`netlink.
LinkList()`, called unconditionally, no dev-mode simulation) and `internal/
inventory/merge.go`'s ownership table (`"linkUp": {Precedence:
[]Source{SourceHostNetlink}}`, exclusive): the local node's host-interfaces
collector always reads the **real** machine's real netlink — and since
`cmd/vnproxd` runs directly on this sandbox for the dev/e2e stack, "pve1"
*is* this sandbox. Its two real interfaces (`lo`, one real ethernet NIC —
confirmed via `ip -o link show`) merge into the fixture's 10 declared ones
(→ 12), and `linkUp` being host-netlink-exclusive means a fixture-declared
`link_up: false` for a name the real host has never heard of resolves to
`unknown` (never-reported), never `down`. This is not a fixture bug and not
new to this task — it is a fact about every single-node-style fixture in
this repo whenever it is the "local" node; existing fixtures/specs simply
never depended on an exact NIC count or a specific down-NIC status for
pve1's own interfaces, so nothing surfaced it before.

**This is a genuine "the spec was wrong" case, argued and fixed, not a
worked-around one:** an exact hardcoded NIC count is not a property this
architecture can guarantee across environments, so asserting it was the
mistake. Fixed `web/e2e/physical-collapse.spec.ts` to assert generically
(`/^Expand \d+ collapsed NICs$/`, `>= FIXTURE_NIC_COUNT`) and, post-expand,
to check only that the fixture's own ten NICs are each individually present
by exact name — never "exactly N total, nothing else." Documented the same
finding in `testdata/clusters/phys-collapse.yaml`'s own header comment (the
`link_up: false` on `eno8` is kept for stylistic parity with other fixtures
but annotated as not e2e-observable as `down`, for the reason above — the
down-status-painting behavior itself is still verified, just at the Go
layer in `collapse_physical_test.go`, which doesn't go through a real host
collector at all).

## What the next agent must know

- The threshold (8) is provisional. When T-1808 lands, re-check it against
  real per-node physical port counts specifically (not just the documented
  §4 scale target, which this task already confirmed stays under threshold
  either way).
- **Always run `npm run e2e` (or `npm run build` immediately before `npx
  playwright test`), never `npx playwright test` alone against a worktree
  that hasn't been built.** A stale/missing `web/dist` produces a failure
  that looks exactly like environmental flakiness or backend slowness (200
  responses in single-digit ms, but the page never functionally loads) —
  it cost significant time this session before the actual trace/console
  output made it obvious. `web/dist/assets/*` is gitignored, so this is
  never "fixed" by a commit; it has to be built fresh in whatever
  environment runs the suite.
- **Every single-node-style dev/e2e fixture whose local node is the actual
  machine running `cmd/vnproxd`** (this one, `single-node.yaml`, three-node-
  vlan's own local node, etc.) has its physical-layer entity set polluted
  by that real machine's real interfaces (`internal/host/netlink_linux.go`'s
  unconditional `netlink.LinkList()`, no dev-mode override) — and
  `linkUp`/`mac`/`driver`/etc. are host-netlink-*exclusive* per `internal/
  inventory/merge.go`'s ownership table, so a fixture-declared `link_up:
  false` for a name the real host doesn't have never resolves to `down` in
  a live run, only `unknown`. Any future fixture/spec relying on an exact
  physical-entity count or a specific link-down status for the *local*
  node's own NICs will hit this. Cluster-scoped entities (bridges, SDN,
  guests) and *peer* nodes' data are unaffected — peer host polls go over
  the (failing, in dev) peer HTTP API, not local netlink.
- The Switch faceplate has one known, narrow, cosmetic limitation, called
  out in `testdata/clusters/phys-collapse.yaml`'s own doc comment: if a
  single collapsed phys-group pill's members fan out to *more than one*
  distinct bond/bridge target (the data layer handles this correctly —
  `collapse_physical_test.go` proves it), the Switch faceplate — which
  assumes one rendered "port" belongs to exactly one uplink bay — will
  render the *same* pill once per target it's wired to. Not a data-loss bug
  (either instance expands to the identical member set via the shared
  `Members` list), just a visual duplication the faceplate's per-bridge
  structure wasn't designed to dedupe. The dedicated E2E fixture avoids this
  case on purpose to keep its own assertions unambiguous; a real deployment
  could hit it.
- `web/e2e/physical-collapse.spec.ts` is green, run twice, in the
  foreground, with `e2e/mgmt-redundancy.spec.ts` in the same invocation
  (4 passed, 42.5s) — this is an observed result, not an inference.
