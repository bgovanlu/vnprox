# T-1907 — Physical-layer progressive collapse

## What I built

Server-side physical-layer collapse in `internal/topology`, mirroring
`collapse.go`'s existing guest-layer mechanism (threshold → synthetic
summary node → expand-on-demand) rather than inventing a second pattern —
closing the last unclosed gap from T-607's docs audit
(`docs/features/topology.md` §4 has documented "physical layer collapses to
per-node summary" since v1.0; only guest-layer collapse existed until now).

- **`internal/topology/collapse_physical.go`** (new): `collapsePhysical`
  groups a node's `PhysNic` entities purely by cluster node (not by
  attachment point, unlike guest collapse) — the docs' own wording is "a
  per-node summary", singular, and a node's NICs fan out to whichever
  bonds/bridges happen to be configured, or nowhere. Above
  `DefaultPhysicalCollapseThreshold`, the individual `physnic` nodes are
  replaced with one `phys-group:<node>` pill (`"N NICs"`, worst-of aggregate
  status, `count=N` badge, `CollapsedCount`), carrying its absorbed refs
  directly on `Node.Members` (a new field — see below for why). Synthesized
  `enslaved-by`/`port-of` edges from the pill to each distinct bond/bridge
  its members fed into (badged `count=N`, painted worst-of) keep it wired
  into the L2 layer instead of rendering as an island. LLDP neighbors and the
  synthetic `KindSwitch` nodes `switches.go` merges them into are untouched
  — only bare `physnic` entities collapse (mirrors T-902's own documented
  scope cut for its client-side capsule).
- **`internal/topology/types.go`**: `DefaultPhysicalCollapseThreshold` (see
  "Threshold" below) and `Node.Members []string` (omitempty) — the new
  field a `phys-group` pill uses to carry its collapsed refs directly,
  since (unlike a guest-group pill) it has no single shared attachment
  target for the frontend to query membership from.
- **`internal/topology/project.go`**: one two-line hookup after
  `collapseGuests` — `collapsePhysical` runs on the same `nodes`/edge set,
  its group edges appended alongside the guest ones. No other change to
  `Project`'s shape.
- **Frontend** (`web/src/topology/`): `projection.ts` gains
  `isPhysGroupId`/`parsePhysGroupId` (mirroring the guest-group pair);
  `expand.ts` gains `physNicDetailToTopologyElements`/`expandPhysicalGroup`
  (fetches each member ref's own `GET /inventory/{ref}` detail — unaffected
  by collapse, since it reads the live graph directly — to reconstruct
  exactly what the uncollapsed projection would have produced); `queries.ts`
  gains `usePhysGroupExpandQuery`. `EntityNode.tsx`/`canvasDraw.ts` grow an
  `isPhysGroup` flag reusing the *exact same* pill rendering as
  `isGuestGroup` (rounded pill, "click to expand" hint) — no new component.
  `switchModel.ts`/`SwitchFaceplate.tsx`/`SwitchView.tsx` extend the uplink-
  bay/free-port rendering with the same `isGroup`/`count` pattern
  `SwitchAccessPort` already has, so the pill also renders correctly in the
  default Switch view. `TopologyPage.tsx`: `handleNodeClick` and the
  `InspectorStack` selected-ref guard now also recognize a phys-group id
  (route to expand, never the inspector); a new `PhysGroupExpansion`
  component mirrors `GuestGroupExpansion`.
- **`docs/features/topology.md` §4** reconciled (AC5): the section now
  describes T-1907's server-side collapse as the actual resolution of the
  T-607 gap, and corrects the previous "Resolved gap (closed T-902)"
  paragraph, which had claimed the gap was closed by T-902's *client-side,
  zoom-driven, v2-renderer-only* LOD capsule — a real, valuable, but
  different mechanism (renderer-density-driven, not entity-count-driven; in
  scope for `physnic`+`bond`+`ovs-bond`, not just bare NICs; not part of the
  actual `GET /topology` response). Both mechanisms are documented as
  coexisting and composing without conflict (the LOD capsule only matches
  raw `physnic`/`bond`/`ovs-bond` kinds, never the synthetic `phys-group`
  kind, so a server-collapsed node's one pill just renders at every zoom
  level while the LOD capsule remains free to additionally fold in any
  bonds it didn't absorb). `docs/performance.md` §4 and `docs/roadmap.md`'s
  Post-1.0 backlog updated to match (their prior wording said the gap "was
  never implemented" as of the T-607/T-607-audit timeframe — corrected to
  say it has since been closed by this task, without erasing the historical
  record of what T-607 actually found at the time).

## Threshold: `DefaultPhysicalCollapseThreshold = 8` (provisional)

T-1808 (scale validation on real hardware) has not run. Argument for 8,
explicitly provisional pending that data:

- At the documented §4 scale target (8 nodes × 6 NICs/node), every node's
  physical layer sits at exactly 6 — **under** 8, so collapse never engages
  at the scale the product is actually verified against. This matters:
  T-607/`docs/performance.md` §4 already measured the physical layer at only
  ~50-65 elements cluster-wide there, nowhere near the ~2,000-element render
  cap the guest-layer collapse exists to protect against. A threshold that
  collapsed at the documented target would be a behavior change against an
  already-established, already-measured baseline for no real benefit.
- 8 is the same magnitude `DefaultCollapseThreshold` already established as
  "small enough to read as individual chips, large enough that a summary
  earns its keep" for the guest-per-bridge case. Reusing it keeps one mental
  model ("more than 8 of the same kind of thing in one place collapses")
  instead of an unrelated second number invented from nothing.
- Follow-up: once T-1808 lands real per-node physical port counts (dense
  chassis, many bonds, SR-IOV PFs), revisit this number against those
  measurements specifically — the target-scale argument above only shows the
  threshold doesn't *wrongly* engage at the documented scale, not that 8 is
  the *right* number for a materially larger real deployment.

## AC2 (losslessness) — tested as equivalence, not a spot check

- **Backend** (`internal/topology/collapse_physical_test.go`):
  `TestDetail_PhysicalCollapseMembers_HaveReconstructableData` builds a node
  with 9 PhysNics (up/down/never-reported-unknown, one enslaved-by a bond,
  one port-of a bridge, the rest free) and, for every ref the group's
  `Members` names, calls the real `topology.Detail` (the exact function the
  frontend's expand path also calls) and asserts its `Fields`/`Related`
  carry everything needed to reconstruct byte-for-byte the same
  kind/label/node/status-relevant fields and structural edges `buildNodes`/
  `buildEdges` would have produced pre-collapse. `TestProject_
  PhysicalCollapse` and `TestProject_PhysicalCollapse_CoexistsWith
  GuestCollapse` cover the collapse mechanics themselves (grouping,
  `CollapsedCount`, badges, synthesized group→target edges with correct
  per-target counts and worst-of status, AC1's regression case of an
  under-threshold node staying individually rendered, and non-interference
  with guest-layer collapse in the same `Project` call).
- **Frontend** (`web/src/topology/expand.test.ts`): a `describe` block per
  branch of the reconstruction rule (up+enslaved-by target, down+port-of
  target with edge status matching, never-reported→unknown never down, a
  genuinely free NIC with zero synthesized edges) asserts
  `physNicDetailToTopologyElements` produces the *exact* expected node/edge
  objects (`toEqual`, not a subset match) against hand-derived expected
  values mirroring `project.go`'s own rules (`badgesOf` has no PhysNic case
  → `badges: []`; status from `LinkUp`/`LinkUpSet` exactly matching
  `statusOf`'s PhysNic branch). `expandPhysicalGroup` itself is tested for
  the full fetch-every-member flow, malformed-id rejection, and one
  member's fetch failing without losing the others (mirrors
  `expandGuestGroup`'s own test shape).

## What the next agent must know

- The threshold (8) is provisional. When T-1808 lands, re-check it against
  real per-node physical port counts specifically (not just the documented
  §4 scale target, which this task already confirmed stays under threshold
  either way).
- The Switch faceplate has one known, narrow, cosmetic limitation, called
  out in `testdata/clusters/phys-collapse.yaml`'s own doc comment: if a
  single collapsed phys-group pill's members fan out to *more than one*
  distinct bond/bridge target (the data layer handles this correctly —
  `collapse_physical_test.go` proves it), the Switch faceplate — which
  assumes one rendered "port" belongs to exactly one uplink bay — will
  render the *same* pill once per target it's wired to. Not a data-loss bug
  (either instance expands to the identical member set via the shared
  `Members` list), just a visual duplication the faceplate's per-bridge
  structure wasn't designed to dedupe. The dedicated E2E fixture avoids this
  case on purpose to keep its own assertions unambiguous; a real deployment
  could hit it.
- `web/e2e/physical-collapse.spec.ts` needs running on a host that isn't
  fighting several concurrent `go run` compiles + a real Chromium instance
  for CPU — this sandbox could not do it for any spec this session, mine or
  pre-existing (see the A/B test above). It's ready to run as-is.
