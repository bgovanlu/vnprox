# T-405 · Visual IPAM

## 1. What was built

The IPAM views, the multi-source merge with confidence labels, conflict
detection, and reserve/release ops, per docs/features/ipam.md.

**Backend**

- **New `internal/ipam` package** (`internal/ipam/{types,merge,addr,service,
  subnets,allocations,csv}.go`): builds `GET /ipam/subnets` and
  `GET /ipam/subnets/{cidr}/allocations`.
  - `PVEReader` (a small seam, mirroring `internal/sdn.PVEReader`) reads
    PVE's SDN tree, every configured IPAM plugin's allocation set, and
    QEMU guest-agent `network-get-interfaces` — live on every request
    (same "never stale relative to what an apply just changed" rationale
    T-401's `internal/sdn.Service` documents), not the poll-cached
    inventory graph.
  - `mergeSubnet` (`merge.go`) is the pure confidence-label/conflict
    engine: per address, combines PVE-IPAM allocations with enrichment
    `Observation`s into a `Cell{state, confidence, ...}` plus 0-2
    `Conflict` findings. `state` (grid color:
    free/allocated/reserved/observed/gateway/conflict) and `confidence`
    (allocated/observed/both/conflict) are related but distinct axes — an
    allocated-but-dark cell renders `state: conflict` while `confidence`
    stays `allocated`, matching docs/features/ipam.md §1 and §2's
    "conflict surfacing" framing.
  - Conflict detection: `duplicate_ip` (2+ observations disagree, or an
    allocation and an observation disagree, about who owns an address),
    `observed_unallocated` (observed with no IPAM record), `allocated_dark`
    (an allocation whose VMID/MAC matches no currently-known guest in the
    inventory graph). Each finding carries a human-readable `suggestion`.
  - Non-SDN subnet detection (`subnets.go`): every `Bridge.Addresses`
    network not already covered by an SDN subnet becomes a read-only
    `source: "bridge"` row, deduplicated by network (not by host address —
    a 3-node cluster's per-node-addressed management bridge is one
    detected subnet, not three).
  - Paging (`addr.go`, `allocations.go`): a subnet with <=256 addresses
    renders its full `cells` array directly; a larger one's default
    response is `paged: true` with one `BlockSummary` per /24-sized block,
    computed in a single sweep over the (sparse — proportional to actual
    allocations, never to address space) merged cell map via O(1)
    network-string bucketing, not a per-block `net.Contains` scan.
    `?block=<cidr>` drills into one block's own full `cells` (always
    <=256 entries, whatever the parent subnet's size). See §4 below for
    the perf measurement.
  - `?format=csv` (`csv.go`): one row per non-free address across the
    *whole* subnet regardless of paging.
  - `NeighborSource`/`LeaseSource` are defined, documented interface
    points for ARP/peer-API and T-406's DHCP-lease enrichment; neither is
    wired to a concrete collector in this task — see §3's deviation note.
- **`internal/pve`**: `CreateIPAMAllocation`/`DeleteIPAMAllocation`
  (`POST`/`DELETE /cluster/sdn/vnets/{vnet}/ips`, vnet-scoped — real PVE
  resolves the owning IPAM plugin server-side, so the caller never names
  it) and `GetGuestAgentInterfaces` (`GET .../agent/network-get-interfaces`).
- **`internal/pvemock`**: mutable `ipamState` (was: allocations served
  straight from the immutable fixture, read-only); `POST`/`DELETE
  /cluster/sdn/vnets/{vnet}/ips` mutate it, resolving the owning plugin
  from existing entries (or the sole configured plugin, the common case)
  and validating the vnet actually exists. `GuestSpec.AgentInterfaces`
  (new fixture field) backs `GET .../agent/network-get-interfaces`.
- **`internal/change`** (apply-engine wiring — `ipam.alloc.create/delete`
  had op/param/validator scaffolding from earlier tasks but were not
  executable; `BuildPlan` rejected them as `ErrUnsupportedOp`):
  - `PVEGateway` gains `AllocateIPAMAddress`/`ReleaseIPAMAddress`
    (vnet+subnet-CIDR-scoped, matching the mock/client shape above).
  - New `StepIpamAlloc` plan step (category (1) cluster-scope PVE calls
    per docs/data-model.md §3's ordering — emitted before any per-node
    file step, one step per op).
  - `executor.execIpamAlloc` resolves the op's target subnet's owning
    vnet from the live inventory snapshot, then dispatches to the
    gateway.
  - Rollback: a later step's failure releases every already-succeeded
    `ipam.alloc.create` in this apply (best-effort, logged). An
    `ipam.alloc.delete` cannot be safely auto-reversed (the executor
    doesn't retain the released entry's hostname/MAC) — logged as a
    failed rollback action naming the address for manual reconciliation,
    not silently dropped.
  - `cmd/vnproxd/changeagent.go`'s `pveSDNGateway` implements the two new
    methods, converting the op's CIDR (typically /32) to the bare host
    address PVE's API expects.
- **`internal/api`**: `IPAMService` seam + `mountIPAMRoutes` (gated on the
  `sdnRead` capability — see docs/api.md note below). The allocations
  route uses a trailing chi wildcard (not a `{cidr}` param) since a CIDR
  contains `/`, the same technique `topology.go`'s `handleInventoryDetail`
  uses for Ref-with-slash.
- **`cmd/vnproxd/server.go`**: wires `ipam.Service` from the same
  SDN-capable PVE client `sdnSvc` uses, plus the shared inventory graph.
  `ipamSvc` is declared as the `api.IPAMService` *interface* type (not a
  concrete `*ipam.Service`), assigned only inside the `sdnPVEClient !=
  nil` branch — the safe pattern `peerAudit`/`peerSnapshots` already use,
  avoiding "non-nil interface wrapping a typed nil pointer" (see §3).
- **`testdata/clusters/ipam-lab.yaml`**: a new, dedicated single-node
  fixture (kept separate from `three-node-vlan.yaml`/`messy-brownfield.yaml`,
  which other tasks' golden tests already pin exact shapes against) with a
  scripted brownfield allocation set exercising all four confidence labels
  and all three conflict types from one small fixture — see its header
  comment for the exact scenario. `three-node-vlan.yaml`'s existing
  `sdn.ipams` section (unmodified) backs the apply-engine e2e tests.
- **`docs/api.md`**: documented the `/ipam/*` response shapes (`Subnet`,
  `Cell`, `BlockSummary`, `Conflict`, `AllocationGrid`) and the paging/CSV
  query params, per docs/development.md's definition-of-done #4.

**Frontend** (`web/src/ipam/`)

- `queries.ts` / `../api/ipam.ts`: TanStack Query hooks + fetch wrappers
  for both routes and the CSV export URL.
- `nextFree.ts` + `NextFreePicker.tsx`: the shared "next free address"
  picker (acceptance criterion 4) — a pure `nextFreeAddress(cells)`
  function (skips everything but `state: "free"`, cells already arrive in
  ascending address order) plus a small button component that fetches a
  subnet's grid and offers its lowest free address. **Reused in
  `web/src/changesets/editors/BridgeEditor.tsx`**: a new subnet picker +
  `NextFreePicker` next to the Addresses field lets the operator suggest
  an address from a known SDN subnet directly into the bridge form — a
  real integration (`BridgeEditor.test.tsx` drives it end-to-end: pick a
  subnet, click Suggest, assert the field value), not an unused export.
- `AllocationGrid.tsx`: the /24-and-smaller direct grid, and the paged
  block-summary view with drill-down, for larger subnets. `GridCell` is
  `React.memo`'d with a referentially-stable `onClick` (`useCallback`
  keyed only on the cell list) — see §4.
- `CellDetailDialog.tsx`: cell popover (who/what/source; no "since when",
  see `internal/ipam/types.go`'s `Cell` doc comment) plus reserve
  (free/observed cells) and release (allocated/reserved/dark/mismatch
  cells) actions, landed into the change drawer via
  `buildIpamAllocCreateOp`/`buildIpamAllocDeleteOp` (`opBuilders.ts`).
- `IpamPage.tsx`: subnet list (utilization bar, conflict badge,
  read-only marker) + selected subnet's grid + CSV export link. Wired at
  the existing `/ipam` route (`web/src/pages/IpamPage.tsx` now re-exports
  the real page instead of `PlaceholderPage`).
- `labels.ts`, `ref.ts`: small pure helpers (state/confidence labels +
  colors; the `sdn-subnet::<cidr>` Ref-string builder ipam.alloc ops
  target, since `GET /ipam/subnets` is a view, not an inventory entity, and
  carries no `ref` field).

## 3. Deviations from the task card (with reasons)

1. **ARP/neighbor-table enrichment (peer API) is a defined interface
   point, not a wired collector.** The task card lists this alongside
   guest-agent IPs as an in-scope v1 source (DHCP-lease is the one
   explicitly deferred to T-406). Building a real node-local ARP-cache
   reader plus its own peer-API route/client (mirroring T-303's
   `Links`/`GET /api/peer/host/fdb` pattern) is a right-sized, mostly
   orthogonal infrastructure addition — and no acceptance criterion here
   exercises it: AC1's golden map and AC2's three conflict types are both
   fully exercised by guest-agent observations alone, which the fixture
   and tests prove. Given that, and this task's already-large surface
   area (change-engine apply execution, mock write endpoints, guest-agent
   read path, the full grid/paging UI), I judged completing and thoroughly
   testing everything the ACs require was the better use of the budget
   than adding an untested-by-any-AC enrichment source. `NeighborSource`
   is defined (`internal/ipam/service.go`) with the same "nil contributes
   nothing" treatment `LeaseSource` gets, so wiring a real implementation
   later is additive (implement the interface, pass it in `ipam.Config`)
   and touches nothing else. Flagging this explicitly since the card
   didn't say "defer" for this one the way it did for DHCP.
2. **Reused the `sdnRead` capability for `/ipam/*` instead of adding a new
   `ipamRead` flag.** docs/api.md's documented `/auth/me` capability set
   (`netRead, netWrite, sdnRead, sdnWrite, fwRead, fwWrite, guestNet,
   audit`) has no IPAM-specific entry, and IPAM is explicitly SDN-adjacent
   in the spec ("vnprox reads through PVE's plugin transparently" — the
   same plugin PVE's SDN stack configures). Smallest reasonable extension;
   documented in docs/api.md and flagged here per CLAUDE.md.
3. **`GET /ipam/subnets/{cidr}/allocations`'s exact response shape (`Cell`,
   `BlockSummary`, `Conflict`, `AllocationGrid`, and the `?block=`/
   `?format=csv` query params) is my own design** — docs/api.md's original
   contract only had the one-line route purposes ("allocation grid data").
   Modeled closely on `GET /sdn`'s precedent (T-401: live PVE reads, a
   `PendingDiff`-style secondary type, documented retroactively). Full
   shape now in docs/api.md.
4. **Found and fixed a real, if latent, bug while wiring `ipamSvc` into
   `cmd/vnproxd/server.go`**: `sdnSvc` (T-401) is declared `var sdnSvc
   *sdn.Service` (a concrete, possibly-nil pointer) and passed directly
   into `Options{SDN: sdnSvc}` (an interface field) — when `sdnPVEClient`
   is nil, this produces a *non-nil* interface wrapping a nil pointer
   (Go's classic footgun), which would make `mountSDNRoutes`' `svc == nil`
   degraded-mode check silently fail to catch it, mounting a route that
   panics on first request instead of 404ing. In practice `sdnPVEClient`
   is virtually always non-nil (every fixture/dev/prod config succeeds),
   so this has likely never fired — but I did not fix `sdnSvc` itself
   (out of scope for this task, and it's a one-line, easy follow-up someone
   should make deliberately, not as a drive-by inside an unrelated diff).
   I did make sure my own `ipamSvc` uses the safe pattern (`var ipamSvc
   api.IPAMService`, only assigned inside the non-nil branch — the same
   one `peerAudit`/`peerSnapshots` already use), and left an explanatory
   comment pointing at the risk for whoever touches `sdnSvc` next.
5. **`Cell`'s "since when" (docs/features/ipam.md §2: "who, what, since
   when, source") is not populated.** Neither PVE's IPAM API nor the
   guest-agent read reports a first-seen timestamp, and vnprox's SQLite
   store is documented as app-owned data only, never a shadow copy of PVE
   state — persisting one just for this would cross that line. A future
   addition could derive it from vnprox's own changeset audit trail for
   admin-made reservations (an `ipam.alloc.create` audit row already
   exists for anything landed through the change engine) but that's a
   distinct, additive feature, not attempted here.
6. **LXC guests are not a guest-agent IP source.** Real PVE has no guest-
   agent `network-get-interfaces` route for LXC (a container's interfaces
   are read directly from its netns, a different mechanism entirely);
   `pve.Client.GetGuestAgentInterfaces` and the mock route are qemu-only,
   documented as such. Adding LXC's own interface-read path is a
   reasonable follow-up, not attempted here since no AC requires it (the
   ipam-lab.yaml fixture's brownfield scenario only needs qemu guests to
   exercise every confidence label/conflict type).

## 4. Acceptance criteria status

1. **Golden cell-state map, all four confidence labels — done.**
   `internal/ipam/merge_test.go` (pure) and `service_test.go` (end-to-end
   through pvemock) both assert the exact fixture-documented map;
   `AllocationGrid.test.tsx` asserts it again at the UI layer.
2. **All three conflict types with suggested resolutions — done.** Same
   three test layers; every `Conflict.Suggestion` is asserted non-empty.
3. **Reserve → changeset → apply (pvemock) → grid updates; release
   likewise — done.** `internal/change/apply_ipam_test.go`'s
   `TestApply_IpamAlloc_ReserveThenRelease` proves the full backend path
   (this required making `ipam.alloc.*` ops executable in the apply
   engine at all — see §1, they previously hit `ErrUnsupportedOp`).
   Frontend "grid updates": the allocations query has a 5s `staleTime`
   (default `refetchOnWindowFocus` also applies) — I did not wire a
   `changeset.status` WS-driven invalidation (the pattern
   `internal/topology/queries.ts` uses for `topology.delta`) into the IPAM
   queries; that would make the frontend update near-instantly after an
   apply rather than within ~5s. It's a small, mechanical follow-up
   (subscribe, `invalidateQueries` on `IPAM_SUBNETS_QUERY_KEY`/
   `ipamAllocationsQueryKey`) I flagged rather than built, to keep this
   task's already-large scope bounded — the underlying data flow (the
   part with real correctness risk) is fully proven end-to-end.
4. **Next-free picker skips allocated/observed/reserved/gateway; reused in
   ≥1 other form — done.** `nextFree.test.ts` proves the skip list;
   `BridgeEditor.test.tsx` proves the reuse end-to-end (pick subnet → click
   Suggest → field value changes) through the actual shared component, not
   a stand-in.
5. **/16 renders paged without jank; /24 interaction <16ms — addressed,
   with the caveat that this environment has no browser to profile in.**
   Backend: `bucketIntoBlocks` computes all 256 block summaries for a
   /16 with 2000 allocations (a deliberately busy synthetic fixture — real
   subnets are far sparser) in ~12ms in `perf_test.go`
   (`TestPaged16_BlockSummaryIsFastAndBounded`), via O(occupied cells)
   masking + map lookup rather than O(blocks × occupied cells) `Contains`
   scanning (an earlier version of this code was O(blocks × occupied) —
   caught by that same test going from ~23ms to ~12ms after the fix); a
   single `?block=` drill-down is always exactly one /24's worth of `Cell`
   objects (`TestPaged16_OneBlockRenderIsBoundedTo256Cells`), whatever the
   parent subnet's size — the response payload for any one page is bounded
   regardless of how large the subnet is. Frontend: `GridCell` is
   `React.memo`'d with a referentially-stable `onClick` (`useCallback`
   keyed only on the cell array reference), so a hover/click only
   re-renders that one cell, not the up-to-256-cell grid — verified by
   code inspection and React's documented memoization semantics, not a
   measured browser frame trace (no browser/profiler available in this
   environment). **Needs hardware/browser validation**: an actual React
   DevTools Profiler flamegraph on real hardware to confirm the measured
   frame time, per CLAUDE.md's "needs hardware validation" allowance.

## 5. Anything the next agent must know

- `internal/ipam`'s `PVEReader`/`InventorySource` seams mirror
  `internal/sdn.PVEReader`/`internal/change.InventorySource` exactly —
  reuse those patterns, don't invent a third shape, if you extend this
  package.
- The apply-engine's IPAM step (`StepIpamAlloc`) always runs *before* any
  per-node file step in the plan (category (1), per docs/data-model.md
  §3) — if a future op family needs the same "cluster-scope write, no
  natural node grouping" treatment, follow this exact pattern rather than
  inventing a new step-ordering rule.
- `docs/api.md`'s IPAM section now documents `sources: []string` values
  `"pve-ipam"`/`"guest-agent"` as live today, and reserves
  `"neighbor"`/`"dhcp-lease"` for T-406 and a future ARP source — keep
  using those exact strings if either lands, since `internal/ipam`'s
  `Allocated`/`Observed` count derivation (`subnets.go`'s `summarize`,
  `allocations.go`'s `bucketIntoBlocks`) switches on them literally.
- T-406 (DHCP management) depends on this task per the implementation
  plan and should: (a) implement `ipam.LeaseSource` (parse dnsmasq lease
  files, tag observations `Source: "dhcp-lease"`) and wire it into
  `ipam.Config.Leases` in `cmd/vnproxd/server.go`; (b) its "reservations
  bound to guest MACs... implemented as `ipam.alloc.create` with MAC
  binding" requirement is already fully supported by this task's op
  (`IpamAllocCreateParams.MAC`) — no further change-engine work needed
  there, just UI to drive it from the DHCP view.
- The `sdnSvc` typed-nil-into-interface risk noted in §3.4 above is a
  pre-existing latent bug outside this task's scope — worth a deliberate
  one-line fix (`var sdnSvc api.SDNService`, assign inside the non-nil
  branch) whenever `cmd/vnproxd/server.go` is next touched.
