## 2. Deviations, gaps, and one unresolved flake

**`internal/drift` coupling (flagged per the orchestrator's brief).** The
health-findings step is a thin consumer of `GET /drift` only: a count +
severity breakdown, linking out to the existing `Tools` drift panel rather
than rendering any part of the findings list itself. No deep structural
coupling to `drift.Finding`'s shape beyond `{severity, id}` (for the
`SEVERITY_ORDER` breakdown and the drift-panel link). **Check this file
(`web/src/onboarding/OnboardingWalkthrough.tsx`'s `HealthStep`) when T-602
merges** — the orchestrator's brief flagged that task as concurrently
reshaping `internal/drift` into a unified findings interface in another
worktree; this should be a small patch to adapt if the shape changes, per
the brief's own risk note.

**LLDP install has no dev-sandbox override.** `POST /lldp/install` runs a
real `apt-get install -y lldpd` + `systemctl enable --now lldpd`
(`internal/host/lldp_install_linux.go`) with no equivalent to
`dev_interfaces_dir`'s sandboxing. `onboarding.spec.ts` asserts the offer
renders but does not click it (documented in the spec file). **Follow-up
for whoever next touches this path**: a dev-config override (mirroring
`[safety].dev_interfaces_dir`'s pattern) would let a future e2e spec exercise
the actual install action end to end without mutating the real test/CI
machine's package state.

**Onboarding walkthrough overlay redesign, mid-task.** The interrupted
subagent that built most of the walkthrough (before a session-limit
interruption I resumed from) had rendered it as a `fixed`-positioned
floating card (tried bottom-left, then top-right). Both positions turned
out to intercept pointer events on pre-existing page controls under real
e2e testing — bottom-left sat on React Flow's own bottom-left zoom/fit-view
`<Controls/>`; top-right collided with the topology page's own top-row
New/Search toolbar. Fixed by rendering it in normal document flow (a
banner between `TopBar` and `<main>`, pushing content down) instead —
documented in `AppShell.tsx`/`OnboardingWalkthrough.tsx`. This is a
one-time architectural correction, not something the next agent needs to
revisit, but it's a deviation from the original visual design worth
knowing about if a design review compares against an earlier screenshot/
mock.

**One residual, not-fully-root-caused e2e flake.** `topology.spec.ts`'s
committed screenshot baseline (`topology-three-node-vlan.png`) intermittently
mismatches (`1158x694` expected vs. a shorter received height, e.g. `592`)
when run as part of the **full** `npx playwright test` invocation (all five
spec files sequentially in one worker), but passes reliably and exactly
matches when run **in isolation**. I traced this most of the way:
- Confirmed via direct DOM instrumentation that the onboarding banner
  suppression added for this file (a CSP-compliant `MutationObserver` +
  direct `.style.setProperty` fix — CSP's `style-src 'self'` silently
  blocks an injected `<style>` element, which cost significant debugging
  time) works correctly: `display: none`, a `0x0` bounding rect, and the
  canvas measuring exactly the expected `1158x694` in an isolated run.
- The mismatch only reproduces under the full-suite's accumulated load
  (18 prior tests in one browser/worker), with a **different, non-repeating**
  received height each time (381, 553, 592, 610) — not a fixed offset,
  which argues against a deterministic layout bug in my change and for
  generic resource-contention flakiness in this sandbox (independently
  observed elsewhere in this session: one Vitest test and `perf.spec.ts`
  each flaked once under similar full-suite load, both passing cleanly on
  re-run).
- Verified via a temporary `git worktree` at the pre-onboarding commit that
  this exact test passed cleanly there — so the *feature* (mounting new UI
  on first login) is a genuine, correctly-handled behavior change, and my
  suppression fix is verified correct in isolation; I could not fully pin
  down why the full-suite run is still occasionally short a variable amount
  of pixels within my remaining effort budget.
- This test's own header comment already documents it as machine-dependent
  ("regenerate with `npm run e2e:update` when running on a different
  machine") — I did not regenerate the committed baseline, since doing so
  would encode this sandbox's specific flakiness as the new "reference
  environment," which seems wrong. Flagging for the orchestrator rather than
  either silently ignoring it or overwriting the baseline unilaterally.
  `make check` does not run Playwright at all, so this does not affect that
  gate.

**No new third-party dependencies.** `internal/docexport` uses only stdlib
(`encoding/json` already-imported types, `net`, `os`); the frontend uses only
already-approved deps.

## 4. Anything the next agent must know

- `internal/docexport.Service`'s three dependencies (`Inventory`, `SDN`,
  `Ports`/`Topo`) are the exact same seam types `internal/api`'s other
  routes already use (`FirewallGraph`-shaped, `sdn.Service`,
  `topology.Service`) — cmd/vnproxd/server.go wires the identical concrete
  values, never a second read path.
- `auth.Config.ReadOnly` only forces capability *flags* false; it does not
  (and per docs/security.md's existing "two enforcement layers" framing,
  should not) change anything about how PVE ACLs are enforced — a
  read_only-mode session with a real PVE write privilege still can't write
  through vnprox's own gates, but PVE's own API would still enforce its own
  ACLs independently if somehow bypassed. This is the intended, documented
  scope (T-604 may want to fold this into its security-verification.md
  claim inventory — I added one sentence to docs/security.md noting it,
  not a full claim-to-evidence entry).
- The onboarding progress payload (`OnboardingProgress` in `api/types.ts`)
  is versioned (`version: 1`) but there is no migration path if the shape
  ever needs to change — a future change should treat an unrecognized
  `version` the same way the 404 case is treated (fall back to
  `freshOnboardingProgress()`), not just add fields.
- `web/dist/index.html` is a **tracked placeholder stub** (T-002,
  `.gitignore`'s `web/dist/*` / `!web/dist/index.html` pair) — every
  `npm run build` overwrites it with real build output, which must be
  `git checkout -- web/dist/index.html`'d back before committing. I hit this
  twice; flagging clearly since it's an easy, silent mistake for the next
  agent running `npm run build` in this repo.
