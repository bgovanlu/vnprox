## 1. What was built

New package `internal/peer` (all files new except `doc.go`, rewritten):

| File | Purpose |
|---|---|
| `secret.go` | `SecretStore`: loads the cluster secret, generating one (32 random bytes, hex-encoded, 0600) under `DefaultSecretPath` (`/etc/pve/vnprox/cluster.secret`) if absent. Concurrent-generation-safe: content is written to a temp file first and published via `os.Link` (atomic "does this name already exist" + no partially-written file ever visible under the final name), so every racing loader converges on the exact same secret. `Watch` polls for on-disk changes (pmxcfs replicating another node's freshly-generated secret, or a rotation) and hot-reloads. |
| `sign.go` | Canonical request string (`method\nrequestURI\nhex(sha256(body))\ntimestamp`), `sign`/`verifySignature` (HMAC-SHA256, `hmac.Equal` constant-time compare), `ReplayWindow` (±30s). |
| `middleware.go` | Server-side `authMiddleware`: header presence, timestamp parse + window check, body-size cap, signature verify, then an exact-replay cache (keyed on the signature itself — collision-free short of a SHA-256 break) — all before `next` is ever called. |
| `server.go` | `Server`/`ServerOptions`, `HostReader`/`HostWriter` seams (3 and 3 methods respectively — matches docs/api.md's documented routes exactly, not `change.NodeAgent`, so this package doesn't import `internal/change`), `MountRoutes` registering all 8 documented `/api/peer/*` routes with the auth middleware wrapping the whole subtree. |
| `client.go` | `Client`: PVE-cluster-status-based discovery (`Peers`, excluding the `Local` row — empty for a real single-node cluster too), per-peer `circuitBreaker`, signed requests, one wrapper method per documented route, `CheckCompatible` (protocol-version refusal). |
| `breaker.go` | Closed/open/half-open circuit breaker, clock-injectable for tests. |
| `version.go` | `ProtocolVersion` (independent of the daemon release version and the SQLite schema version) + `VersionInfo`. |
| `errors.go`, `types.go` | `ErrPeerUnreachable`/`ErrPeerIncompatible`/`ResponseError` (docs/api.md's `peer_unreachable` code, plus one I introduced: `peer_incompatible` — api.md doesn't name a code for the version-mismatch refusal architecture §5 describes, so I picked a doc-convention-consistent one; flagging since it isn't yet written into api.md itself, mirroring how T-203's report retroactively documented `/protected-interfaces`). Wire request/response shapes and the shared `{"error":{"code","message"}}` envelope. |

## 2. What was tested and how

All in `internal/peer/*_test.go` (table-driven where the shape fits) plus one
`cmd/vnproxd` end-to-end wiring test:

- **AC1** (`server_test.go`): `TestTwoDaemonHarness_ReadEndpoints` — two independent `Server`s, each with its own fixture-backed reader (distinct per-node content), talking through one `Client`; also write-endpoint and health/version variants.
- **AC2** (`middleware_test.go`): `TestAuthMiddleware_SecuritySuite` table-drives missing/garbage-signature/garbage-timestamp/expired/future-skew/wrong-secret/tampered-body, each asserted 401 **and** that a `handlerSpy` was never invoked; `TestAuthMiddleware_ReplayedRequestRejected` (same signed request twice); `TestAuthMiddleware_SPASessionCookieGrantsNothing` (a `vnprox_session` cookie neither helps nor is required).
- **AC3** (`client_test.go`): `TestClient_DeadPeerFastFailsAndRecovers` — a listener bound-then-closed (deterministic refused-connection dead peer), asserts `errors.Is(err, ErrPeerUnreachable)`, that the open-breaker call is fast (well under the request timeout, no network attempt), and that pointing the same `Peer.Node` at a live server after the reset timeout heals it.
- **AC4** (`client_test.go`): `TestClient_CheckCompatible_VersionMismatch` — matching-version success path against a real `Server`, mismatch path against a stub HTTP handler, asserting `errors.Is(err, ErrPeerIncompatible)`.
- **AC5**: `FuzzPeerAuth` (`fuzz_test.go`) drives the middleware's header-parsing/hex-decoding/HMAC-verification path with garbage timestamps, signatures, and bodies. Ran `go test -fuzz=FuzzPeerAuth -fuzztime=60s` locally: clean, ~1.7M execs, 29 corpus entries, no crashes.
- Secret handling (`secret_test.go`): generate-when-absent + 0600 perms, load-existing, reject-malformed, an 8-goroutine concurrent-generation-convergence test (this is what caught the `os.Link`-vs-`O_CREATE|O_EXCL` race described below), and `Watch` picking up an on-disk rotation.
- Breaker state machine (`breaker_test.go`): threshold-open, half-open recovery, failed-probe reopen, success resets failure count.
- `internal/api/router_test.go`: `TestPeerRoutesMounted`/`TestPeerRoutesOmittedWhenNil` — wiring-level, not auth-level (that's `internal/peer`'s own job).
- `cmd/vnproxd/peerwiring_test.go`: full `runDaemon` brought up against `dev.toml`, asserting an unsigned `GET /api/peer/version` gets 401 and a `peer.Client` signing with the daemon's own *generated* secret file succeeds — proof the daemon wiring (not just the package's unit tests) is correct end-to-end.

Everything above also passes with `-race`. `go test ./internal/pvemock` continues to pass unmodified (this task didn't touch it — the two-daemon harness uses hand-rolled fixture readers, not pvemock's, since AC1 only needs "distinct fixture-backed hosts", not the full PVE surface).

## 3. Bug found and fixed during testing

The concurrent-generation test caught a real race in the first draft of
`generateSecretFile`: `O_CREATE|O_EXCL` on the final path directly lets a
losing goroutine observe the winning goroutine's file *after it's created
but before it's written* (read back 0 bytes → spurious "secret too short"
error). Fixed by writing full content to a temp file first and publishing
via `os.Link` (fails atomically with `ErrExist` if the destination already
has an entry, and — because the content already exists in full under the
temp name before the link is made — nothing is ever visible at the final
path in a partially-written state). Verified with `-race -count=20`.

## 4. Deviations from the task card (with reasons)

1. **No `/api/peer/host/fdb` route.** The task card's deliverable bullet
   parenthetically lists "fdb" alongside interfaces/lldp/stats, but
   `docs/api.md`'s Peer API section — the frozen contract CLAUDE.md says to
   follow exactly — only documents `interfaces`, `lldp`, `stats`,
   `stage-interfaces`, `ifreload`, `restore`, `health`, `version`. T-306's
   own card separately claims "FDB reader … exposed via peer API" as *its*
   deliverable. I followed the contract doc over the card's shorthand and
   left FDB out; flagging in case this was meant to land now instead of in
   T-306.
2. **`peer_incompatible` error code is new**, not in `docs/api.md`'s error
   code list. Architecture §5 requires the refusal; api.md just doesn't
   name a code for it. Picked one consistent with the existing naming
   convention; a future task should add it to api.md's documented codes
   (same retroactive-documentation pattern T-203 used for
   `/protected-interfaces`).
3. **`internal/config` gained a `[peer]` section and now imports
   `internal/peer`** (for `peer.DefaultSecretPath`) — technically outside
   the "internal/api, cmd/vnproxd" wiring scope named in the dispatch
   instructions, but unavoidable: without a dev-writable override, `make
   dev`/`devconfig_test.go` would try to create `/etc/pve/vnprox/` on every
   dev machine and CI runner. Mirrors the existing `[storage]` precedent
   exactly (same shape, same reasoning).
4. **`peer.Client` is not yet instantiated by `cmd/vnproxd`.** Nothing in
   this phase consumes it (T-302/303/304 will). Wiring a live discovery
   loop with no caller would be speculative and untested at the daemon
   level, so I left it as a fully-built, fully-tested library the next
   tasks construct when they need it — only the *server* side (which does
   need to be live for AC1-class two-daemon tests to mean anything in
   production) is wired into `runDaemon`.

## 5. Needs hardware validation

- TLS trust between real peer daemons: production peers present the node's
  PVE certificate (`docs/architecture.md` §9), typically signed by PVE's
  own cluster CA (`/etc/pve/pve-root-ca.pem`), which this client doesn't yet
  pin — it inherits `net/http`'s default system trust store via
  `ClientOptions.HTTPClient`/`TLSClientConfig` (left as a caller-supplied
  override; the default is unset). Tests use plain HTTP for this reason
  (`Scheme: "http"` against `httptest.Server`) since TLS chain validation
  isn't this package's concern to reimplement — but *which* CA a production
  `cmd/vnproxd` peer client should pin was not specified anywhere I found
  and needs a real cluster to get right.
- `hostNodeAgent.RestoreInterfaces`/real `host.NewReal()` reads are only
  exercised via fixtures/fakes here, same "needs hardware validation" caveat
  `changeagent.go`'s existing doc comment already carries for the reload
  path.

## 6. For the next agent (T-302/303/304)

- Use `peer.NewClient` + `internal/host.Reader`/`peer.HostReader`'s
  structural parity to build the "local vs. remote, callers never
  special-case" dispatcher the task cards ask for — that unifying layer is
  explicitly T-303's deliverable, not built here.
- `Client.Peers` already excludes the local node and empty-IP rows; a
  single-node cluster gets an empty slice, not an error.
- The breaker is per-`Peer.Node` (keyed by node name, not address) — if a
  peer's IP changes between discovery calls, its breaker state carries over
  by design (a node that was flapping stays cautious even after a
  reassigned IP), but a stale open breaker will also mask a brand-new IP
  actually being reachable until the reset timeout elapses. Worth revisiting
  if that's ever the wrong tradeoff.
