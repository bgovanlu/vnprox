## 2. `internal/sim`'s `RuleRef.RulesetRef` — removed from the wire contract, not populated

**Argued decision:** removed, not populated. `RulesetRef` was only ever set for `origin: cluster`/
`origin: group` (pointing at the cluster ruleset), left empty for `origin: guest` — the case T-504's
report flagged as the single most common deny scenario producing a dead link. The tempting fix is
"populate it for guest origin too," but that only half-fixes the field: even where `RulesetRef`
*was* populated (cluster/group origin), it names the wrong thing for the deep link's actual
purpose. The link's target was never "the ruleset this rule is defined in" — it is always "the
*guest* whose resolved view to open" (T-505's own established convention, which the resolved view
renders a cluster-origin rule in context of, via `OriginBadge`). For a cluster/group-origin rule,
those two refs are different rulesets entirely. `deeplink.ts`'s `blockingRuleGuestRef` already
derives the correct value from `ResolvedEndpoint.guest` at the blocking rule's `enforcementPoint` —
and it has to, regardless of whether `RulesetRef` is populated, because `RulesetRef` structurally
cannot answer "which guest" for two of the three origins it can take. A fully-populated
`RulesetRef` would therefore still leave `blockingRuleGuestRef`'s derivation in place — it would
just be dead code sitting next to a wire field nothing reads. Grepping the whole repo before
removing it confirmed zero consumers beyond the deep-link tests that explicitly assert it's
ignored.

**Built:**
- `internal/sim/types.go`: `RuleRef` no longer has a `RulesetRef` field (doc comment explains why,
  with cross-references).
- `internal/sim/firewall.go`: `ruleRef` no longer computes/sets it.
- `internal/api/simulate.go`: `simBlockingRule` (the JSON DTO) drops the field; `toSimulateResponse`
  updated.
- `web/src/api/types.ts`: `SimBlockingRule` drops `rulesetRef`.
- `web/src/simulator/deeplink.ts`: doc comment rewritten — the guest-ref derivation is no longer
  described as working around an incomplete field (there's no field to work around); it's simply
  the correct, permanent mechanism.
- `docs/api.md`: `blockingRule`'s documented shape drops `rulesetRef`, with an explicit note of why
  (cross-referencing this report).
- Test fixtures that constructed a `SimBlockingRule`/`RuleRef` literal with `rulesetRef: "..."`
  updated across `web/src/simulator/deeplink.test.ts`, `web/src/simulator/ResultPanel.test.tsx`,
  `web/src/firewall/focusRule.test.ts`.

**Tested:** `go build ./...`, `go vet ./...`, and the full `internal/sim`/`internal/api` test suites
pass with the field gone (no test asserted its presence beyond the ones updated above, confirming
it truly had no other consumer). Frontend: `tsc --noEmit`/`eslint` clean, all `internal/sim`-facing
Vitest suites pass.

## 3. Security-group inspector + group-scoped microseg planner launch

T-1603's own report named this precisely: "there is no standalone security-group inspector page in
the current UI... a group-scoped entry point is a small follow-up once a group inspector exists."

**Built:**
- **Backend:** `GET /firewall/rulesets?scope=group&name=<group>` (`internal/api/firewall.go`),
  extending the existing `scope=` dispatch rather than inventing a new route — returns
  `{name, comment?, rules: [RuleView]}`, a security group's own rule list (previously visible only
  in aggregate via `GET /firewall/objects`' usage counts, never on its own). 404 for an unknown
  group, 400 for a missing `name`. `docs/api.md` updated.
- **Frontend:** `web/src/firewall/GroupInspector.tsx` — a new inspector surface showing the group's
  own rules (read-only table) and every guest the group's rules actually reach (`GET
  /firewall/effects`, T-502's existing rule-effects preview, reused verbatim — not recomputed). A
  guest picker lets the reviewer choose one of those guests and mounts the **exact same**
  `<MicrosegPlanner guestRef=.../>` component the guest-scoped launch (`FirewallPage`'s
  `GuestPanel`) already uses.
- **Launch point:** `ObjectsPanel.tsx`'s security-groups table gained an "Inspect" action per row
  (only for groups — aliases/ipsets have no inspector). `FirewallPage.tsx` gained a `"group"` scope
  reached only via that action (not a top-level tab — a security group is an object drilled into
  from Objects, not a hierarchy level like Datacenter/Nodes/Guests), with an "← Back to objects"
  return path.

**Why AC3 ("same proposal shape") holds by construction:** the group-scoped launch renders the
identical `MicrosegPlanner` React component and therefore calls the identical
`POST /microseg/propose` code path as the guest-scoped launch — there is exactly one way from a
guest ref to a proposal in this codebase, regardless of whether the guest was reached by picking it
directly or by picking it through a group's reach list. No second synthesis path was written to
diverge from.

**Tested:**
- `internal/api/firewall_test.go`: `TestFirewallRulesets_GroupScope` (200, correct
  name/comment/rules), `TestFirewallRulesets_GroupScope_MissingName400`,
  `TestFirewallRulesets_GroupScope_UnknownGroup404`.
- `web/src/firewall/GroupInspector.test.tsx` (new): renders the group's own rules and comment;
  lists the guests the group reaches; launches the planner for a chosen guest and asserts the same
  `MicrosegPlanner` component mounts (`data-testid="microseg-planner"`); degrades honestly when a
  group matches no guests; shows a not-found message when the group itself doesn't exist; back

- `web/src/firewall/ObjectsPanel.test.tsx`: new tests asserting "Inspect" renders only for the
  groups table (not aliases/ipsets) and calls `onInspectGroup` with the right name, and that no

## 4. Per-step audit granularity in the diagnosis ladder

T-1307's own report flagged this precisely as a deliberate simplification with a named follow-up:
"a `GET /audit` browse of just `probe.verify` rows would not show a diagnose-triggered probe
attempt that didn't diverge... an easy follow-up if a future task wants per-step audit
granularity."

**Built:** `internal/api/diagnose.go`'s `handleDiagnose` now calls a new `auditDiagnoseSteps` in
addition to the existing `auditDiagnoseRun` (unchanged, still writes one `diagnose.run` summary
row). `auditDiagnoseSteps` appends one `diagnose.step` audit row per ladder step (five per call),
each with:
- `target`: the same diagnosed `targetRef`.
- `result`: `"skipped"`\|`"error"`\|`"ok"`, mapped from that step's own `StatusSkipped`/
  `StatusError`/`StatusRan` — a step that never applied to the target audits as `"skipped"`, not
  folded into a misleading `"ok"`.
- `detail`: `{runId, step, status, summary}` — `runId` is the sibling `diagnose.run` row's own
  audit id (`Append`'s returned `int64`), so `GET /audit` can group a run's steps back together
  without inventing a second correlation mechanism; `step`/`status`/`summary` mirror that step's
  `StepResult` fields verbatim, so a reviewer reconstructs exactly what the response said, from
  audit rows alone, after the fact.
- `At`: the step's own `RanAt` (the ladder's injected clock), not a fresh `time.Now()` — matches
  when that step actually executed, and keeps tests deterministic.

This is additive, not a replacement: `diagnose.run`'s own row/shape is untouched, so any existing
"browse by `diagnose.run`" query is unaffected. `docs/api.md`'s Audit section documents the new
`diagnose.step` action and its detail shape; the Diagnosis section's capture-escalation paragraph
is updated to mention both rows.

**Tested:** `internal/api/diagnose_test.go`'s new `TestDiagnose_PerStepAuditRows` — runs the full
five-step ladder against `sim-lab.yaml`, then reads the audit log back via `h.audit.List` and
asserts: exactly one `diagnose.run` row and exactly five `diagnose.step` rows; every step row's
`target` is the diagnosed ref; every step row's `runId` equals the `diagnose.run` row's own id;
every step row's `status`/`summary` matches that step's entry in the actual HTTP response
(`res.Steps`) verbatim; every ran step's audit `result` is `"ok"`; all five canonical step names
are represented. The pre-existing `TestDiagnose_AllStepsEligible_GuestNicTarget`'s own
`diagnose.run`-row-count assertion still passes unchanged (it counts by action name, unaffected by
the new rows existing alongside it).
