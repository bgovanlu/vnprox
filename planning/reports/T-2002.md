## 2. `internal/sim`'s `RuleRef.RulesetRef` — populated correctly for every origin, kept

**Argued decision (final, after a review correction — see "Course correction" below): populate,
don't remove.** `RulesetRef` was only ever set for `origin: cluster`/`origin: group` (pointing at
the cluster ruleset), left empty for `origin: guest` — the case T-504's report flagged as the
single most common deny scenario producing a dead link. The fix is to populate it for `origin:
guest` too: `internal/sim/firewall.go`'s `ruleRef` now looks up the blocked guest's own ruleset
(`e.fw.Guests[guest]`) and uses its ref, exactly mirroring the existing cluster/group branch. The
field is now genuinely true for all three origins it can take, not half-true for two of them.

This is a different value than what `web/src/simulator/deeplink.ts`'s deep link uses, and stays
that way deliberately: the link's target is never "the ruleset this rule is defined in" — it is
always "the *guest* whose resolved view to open" (T-505's own established convention, which the
resolved view renders a cluster-origin rule in the context of, via `OriginBadge`). For a
cluster/group-origin rule those two refs are different rulesets entirely, so
`deeplink.ts`'s `blockingRuleGuestRef` still derives the guest ref from `ResolvedEndpoint.guest` at
the blocking rule's `enforcementPoint`, ignoring `RulesetRef` even though it's populated. That is
not dead code sitting next to an unused field, though — `RulesetRef` is real, useful information
for a *different* consumer: something that wants to target a `fw.rule.*` changeset op at the exact
ruleset a blocking rule lives in (an MCP automation client is the concrete example; see "Course
correction").

**Course correction (mid-task, coordinator review):** this task's first pass **removed**
`RulesetRef` from the wire contract instead of populating it, reasoning that even a
fully-populated field could never replace `blockingRuleGuestRef`'s derivation (true) and that
grepping the whole repo found zero consumers (also true, but insufficient). The coordinator caught
what the grep couldn't: `cmd/vnproxd/mcpwire.go`'s `mcpSimulatePath` returns `sim.Result`
**verbatim** as the payload of the `simulate.path` MCP tool, one of the nine tools in the **frozen
v1 MCP manifest** (`docs/architecture.md` §13.1, decision D10). That freeze's deprecation policy is
explicit: additive-only, no field ever removed or renamed without minting a new version. An
external MCP client (a T-1701 AI operator) reading `rulesetRef` today would never show up in an
in-repo grep, so "no consumer found" was true of this repository and not of the actual wire
contract. Removing the field broke that promise; restoring it and populating it correctly resolves
the original half-true-field problem without breaking the freeze. Filed as a follow-up bug card,
`T-2002-bug-01` (`planning/tasks/phase-18.md`), proposing a systematic version of the regression
guard this correction added (below) across all nine frozen MCP tools, none of which have one today.

**Built:**
- `internal/sim/types.go`: `RuleRef` keeps `RulesetRef string \`json:"rulesetRef"\`` (doc comment
  explains the frozen-contract history and cross-references this report).
- `internal/sim/firewall.go`: `ruleRef` now takes the guest ref and populates `RulesetRef` for
  `origin: guest` (guest's own ruleset) in addition to the existing `cluster`/`group` branch
  (cluster ruleset).
- `internal/api/simulate.go`: `simBlockingRule` (the JSON DTO) keeps the field; `toSimulateResponse`

- `web/src/api/types.ts`: `SimBlockingRule` keeps `rulesetRef: string`, doc comment updated.
- `web/src/simulator/deeplink.ts`: doc comment explains `rulesetRef` is populated but deliberately

- `docs/api.md`: `blockingRule`'s documented shape keeps `rulesetRef`, with an explicit note that
  this shape is frozen (§13.1) and who each field is really for.
- **Two new regression guards**, directly answering the coordinator's "add a regression guard"
  ask:
  - `internal/sim/rulesetref_test.go`: `TestRuleRef_RulesetRefPopulatedForEveryOrigin` (a
    guest-origin and a cluster-origin deny, asserting `RulesetRef` is non-empty and correctly

  - `cmd/vnproxd/mcpwire_test.go`: `TestMCPSimulatePath_FrozenPayloadFields` — drives a real

## 3. Security-group inspector + group-scoped microseg planner launch

T-1603's own report named this precisely: "there is no standalone security-group inspector page in
the current UI... a group-scoped entry point is a small follow-up once a group inspector exists."

**Built:**
- **Backend:** `GET /firewall/rulesets?scope=group&name=<group>` (`internal/api/firewall.go`),
  extending the existing `scope=` dispatch rather than inventing a new route — returns
  `{name, comment?, rules: [RuleView]}`, a security group's own rule list (previously visible only
  in aggregate via `GET /firewall/objects`' usage counts, never on its own). 404 for an unknown
  group, 400 for a missing `name`. `docs/api.md` updated.
- **Frontend:** `web/src/firewall/GroupInspector.tsx` — a new inspector surface showing the group's
  own rules (read-only table) and every guest the group's rules actually reach (`GET
  /firewall/effects`, T-502's existing rule-effects preview, reused verbatim — not recomputed). A
  guest picker lets the reviewer choose one of those guests and mounts the **exact same**
  `<MicrosegPlanner guestRef=.../>` component the guest-scoped launch (`FirewallPage`'s
  `GuestPanel`) already uses.
- **Launch point:** `ObjectsPanel.tsx`'s security-groups table gained an "Inspect" action per row
  (only for groups — aliases/ipsets have no inspector). `FirewallPage.tsx` gained a `"group"` scope
  reached only via that action (not a top-level tab — a security group is an object drilled into
  from Objects, not a hierarchy level like Datacenter/Nodes/Guests), with an "← Back to objects"
  return path.

**Why AC3 ("same proposal shape") holds by construction:** the group-scoped launch renders the

guest ref to a proposal in this codebase, regardless of whether the guest was reached by picking it
directly or by picking it through a group's reach list. No second synthesis path was written to
diverge from.

## 4. Per-step audit granularity in the diagnosis ladder

T-1307's own report flagged this precisely as a deliberate simplification with a named follow-up:
"a `GET /audit` browse of just `probe.verify` rows would not show a diagnose-triggered probe
attempt that didn't diverge... an easy follow-up if a future task wants per-step audit
granularity."

**Built:** `internal/api/diagnose.go`'s `handleDiagnose` now calls a new `auditDiagnoseSteps` in
addition to the existing `auditDiagnoseRun` (unchanged, still writes one `diagnose.run` summary
row). `auditDiagnoseSteps` appends one `diagnose.step` audit row per ladder step (five per call),
each with:
- `target`: the same diagnosed `targetRef`.
- `result`: `"skipped"`\|`"error"`\|`"ok"`, mapped from that step's own `StatusSkipped`/
  `StatusError`/`StatusRan` — a step that never applied to the target audits as `"skipped"`, not
  folded into a misleading `"ok"`.
- `detail`: `{runId, step, status, summary}` — `runId` is the sibling `diagnose.run` row's own
  audit id (`Append`'s returned `int64`), so `GET /audit` can group a run's steps back together
  without inventing a second correlation mechanism; `step`/`status`/`summary` mirror that step's
  `StepResult` fields verbatim, so a reviewer reconstructs exactly what the response said, from
  audit rows alone, after the fact.
- `At`: the step's own `RanAt` (the ladder's injected clock), not a fresh `time.Now()` — matches
  when that step actually executed, and keeps tests deterministic.

This is additive, not a replacement: `diagnose.run`'s own row/shape is untouched, so any existing
"browse by `diagnose.run`" query is unaffected. `docs/api.md`'s Audit section documents the new
`diagnose.step` action and its detail shape; the Diagnosis section's capture-escalation paragraph
is updated to mention both rows.

**Tested:** `internal/api/diagnose_test.go`'s new `TestDiagnose_PerStepAuditRows` — runs the full
five-step ladder against `sim-lab.yaml`, then reads the audit log back via `h.audit.List` and
asserts: exactly one `diagnose.run` row and exactly five `diagnose.step` rows; every step row's
`target` is the diagnosed ref; every step row's `runId` equals the `diagnose.run` row's own id;
every step row's `status`/`summary` matches that step's entry in the actual HTTP response
(`res.Steps`) verbatim; every ran step's audit `result` is `"ok"`; all five canonical step names
are represented. The pre-existing `TestDiagnose_AllStepsEligible_GuestNicTarget`'s own
`diagnose.run`-row-count assertion still passes unchanged (it counts by action name, unaffected by
the new rows existing alongside it).

   extending the e2e fleet for four small, mostly-backend-adjacent UI additions, especially given
