## 5. Soak test (AC3)

**Deviation from the literal task-card wording, stated plainly:** this task ran as a background automated agent in one continuous session — a genuine, uninterrupted 24 wall-clock-hour run was **not** executed, per this task's own explicit instructions anticipating exactly this situation.

What was actually done:

- **A real ~61-minute continuous soak** (`testdata/genscale/soak`): a real Go HTTP client driving a real `vnproxd` (via `testdata/dev-scale.toml`, `scale-lab.yaml`, the project's established dev-loop pattern) with continuous churn the entire time — read-path traffic (topology/findings/audit polling every 5s), draft-changeset churn (create→validate→delete every 45s, no permanent DB growth), and 2 full real apply→confirm cycles (every 20 minutes).
- Sampled RSS (`/proc/<pid>/status`), goroutine count (via a new, off-by-default `VNPROX_DEBUG_PPROF_ADDR` diagnostic endpoint, `cmd/vnproxd/debugpprof.go` — never on the main TLS listener, no API contract change), and SQLite file size (incl. WAL/SHM) every 60s+ — 63 samples, committed as a real artifact: `planning/reports/T-607-artifacts/soak-samples.csv`.
- **Results:** RSS 43.6-57.2 MB, no trend (first-10 vs last-10 samples statistically indistinguishable); goroutines 40-44, no trend; DB size plateaued at exactly 4,365,816 bytes for the final 36 consecutive samples (~29 minutes) after one WAL checkpoint. Flat, by every measure taken.
- **DB-growth ceiling:** reused T-601's own measurement (per this task's instructions, not re-derived) — ~24.3 MiB for a full 24h/100-entity/30s-resolution run, documented ceiling 200 MiB, ~8x headroom. This soak's own growth (4.37 MiB, dominated by draft-changeset WAL churn and 2 real apply cycles, not metric-sample accumulation) is consistent with that ceiling holding.
- **A real, dev-environment-only bug this soak found** (not a leak): both real apply/confirm cycles' *create* half succeeded fully; both *delete* halves failed validation with `referential.target_not_found`. Root cause (confirmed by direct investigation, not guessed): in dev/mock mode, `bridge.create`'s file write lands in the `dev_interfaces_dir` sandbox, but `pvemock`'s own in-memory network model — what the next changeset's validation reads back — is never updated, because the apply engine never calls PVE's `PUT /nodes/{node}/network` for node-network ops at all; it writes `/etc/network/interfaces` and execs `ifreload` directly (see §7's docs-audit finding on this same subject). Real production has no such gap (a real PVE node's own API reads back the same file it writes). Does not affect the RSS/goroutine flatness result, which is what the soak actually exists to prove.

**Honest bottom line:** flat over the ~61 minutes actually observed, zero trend in either direction. Whether flatness holds for the remaining ~23 hours of a literal 24h run cannot be claimed as *observed* — it's inferred from (a) the trend already being flat rather than slowly rising, (b) a workload with 5s/45s/20min-period churn that doesn't leak in 61 minutes having no structural reason to start leaking at hour 6, and (c) the DB-ceiling argument above. This is the documented substitution this task's own instructions asked for, presented honestly, not as an unqualified 24h claim.

## 7. Real product bugs found and fixed during this verification pass

Three, in increasing order of how deep they were found:

1. **SDN write UI permanently disabled on every real multi-node cluster (severe).** While driving the SDN zone wizard to completion for E2E coverage, the "Create draft" button was found permanently disabled for *any* multi-node session, including root. Root cause: `internal/auth.BuildCapabilities` only ever populates a `""` cluster-wide caps-map key when the node list is empty; a real cluster's session has only per-node keys. Five pre-existing SDN editor/delete dialogs (`SdnZoneEditor`, `SdnVnetEditor`, `SdnSubnetEditor`, `SdnConfirmDeleteDialog`, `SdnVnetDeleteDialog`) plus the zone wizards' own `useWizardCapability.ts` all checked `capsForNode(session, "").sdnWrite`, which silently evaluates to `false` always in the real (non-empty-node-list) case. Every existing unit test's mock session fixture happened to include an artificial `""` entry, masking this from unit coverage entirely — only caught by actually completing a wizard against the real stack. Fixed by switching to the already-correct, already-used-elsewhere `hasAnyCap(session, cap)` helper (`web/src/changesets/capabilities.ts`) across all six call sites. Commits `130f93b`, `32276f9`.
2. **Missing capability gating on several SDN/firewall write-trigger buttons.** `SdnPage.tsx`'s zone/vnet/subnet edit/delete/create buttons, `ObjectsPanel.tsx`'s shared object delete, and `RuleEditor.tsx`'s per-rule delete/enable-toggle/drag-reorder/add-rule had no capability gating at all — a read-only or under-privileged session saw them enabled (the backend still rejected the actual write; no privilege escalation was possible, but this violates the documented "every write affordance disabled-with-tooltip" UX contract, T-605 AC4). `docs/security-verification.md` had already flagged the `ObjectsPanel.tsx` instance (T-604) but left it unfixed; this task's own E2E read-only crawl re-caught it plus the others. Fixed with the same `capsForNode`/`missingCapTooltip` pattern used successfully elsewhere (e.g. `InspectorPanel.tsx`). Commit `db8441d`.
3. **`vnproxctl`'s disaster-recovery path required a PVE TLS certificate it never needs.** Found by literally re-running `packaging/test/upgrade.sh` (T-606's own container test) as this task's AC5 requires. `vnproxctl snapshots list/restore` and `rollback-now` — documented as working "even when the UI is unreachable" — called the full `config.Load`, whose `validate()` unconditionally resolves a PVE TLS certificate and fails fast if none exists (a bare container, or the exact disaster scenario where the daemon's own cert is what's broken, both hit this). Pre-existing since T-206 (that task's own test fixture comment already worked around it with a valid dev cert); not something any T-607 change introduced, and not caught until this task's literal packaging-matrix rerun. Fixed with a new `config.LoadStorageOnly` that parses just the `[storage]` section without running `validate()`. Commit `a4726a4`.

All three are documented in `CHANGELOG.md`'s v1.0.0 entry.
