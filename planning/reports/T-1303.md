# T-1303 · Latency & loss mesh — completion report

## What was built

**New `internal/latmesh` package** (extends `internal/probe`'s honesty-contract conventions,
does not duplicate its guest-exec engine — see the package doc comment for why):

- `Fabric`/`Pair`/`Reading`/`Sample`/`LinkHeat` (`types.go`) — the core vocabulary. `Pair.LinkID`
  is the stable, content-derived key (`"<fabric>[:<label>]|<fromNode>-><toNode>"`, e.g.
  `"corosync:ring0|pve1->pve2"`).
- `DiscoverPairs(snap, coro, localNode)` (`pairs.go`) — a node-local, deterministic pairing
  algorithm: corosync-ring pairs from `internal/host.CorosyncConfig` (reused, not re-parsed) and
  guest-fabric pairs from `internal/xnode.BridgesByName`'s existing cross-node grouping (reused).
  Always originates at `localNode` — see "Deviations" below for the cluster-scope rationale.
- `Prober` interface + `RealProber` (`prober.go`) — issues a real `ping -c 5 -W 3` burst per tick
  and parses iputils-ping's own summary line (loss%/avg-rtt), defensively (unparsable summary ⇒
  100% loss, never a panic, mirroring `host.ParseCorosyncStatus`'s stance).
- `Service` (`service.go`) — `Tick`/`RunLoop` (probe + persist), `RunPruneLoop` (retention-window
  AND hard-row-cap bound, mirrors `internal/flow.Service` exactly), `Heatmap`/`History`/`Baseline`
  (query surface). `LatMeshHeatmap()` satisfies `findings.LatMeshProvider` structurally (no
  adapter — the same seam `metrics.Sampler`/`MetricsProvider` establishes).
- `Baseline(samples) (p50, p95, lossPct, ok)` (`baseline.go`) — pure, nearest-rank percentile
  function; golden-tested against `testdata/latmesh/baseline.json`.
- `GraphDiscoverer` (`discoverer.go`) — the production `Discoverer`, re-reading the live
  inventory snapshot + local `corosync.conf` fresh every tick.

**Storage**: `internal/store/migrations/0011_latency_samples.sql` (`latency_samples` table) +
`internal/store/latmesh.go` (`LatencySampleRepo`: `InsertBatch`/`QueryRange`/`LatestPerLink`/
`PruneOlderThan`/`PruneToCap`, mirroring `FlowSampleRepo` field-for-field).

**Findings**: `internal/findings/health_latmesh.go` — `path_latency_degraded`/`path_loss`
(source `health`, `fixable: false`, standard 3-rise/2-fall hysteresis on the *rolling* window
value, not the raw per-tick reading — see that file's doc comment). New `HealthThresholds.
LatRttWarnMs`/`LatLossWarnPct` (defaults 80ms/2%). Wired into `Engine.Config.LatMesh` /
`healthFindings()`.

**API**: `internal/api/latmesh.go` — `GET /latmesh/heatmap`, `GET /latmesh/history?linkId=&
fromTs=&toTs=`, netRead-gated, node-local only (no peer fan-out — see "Deviations"). Mounted via
`router.go`'s `Options.LatMesh`.

**Config**: `[latmesh]` section (`probe_interval_sec`/`retention_minutes`/`max_rows`, defaults
10/60/500,000) — `internal/config.LatmeshConfig`, documented in `docs/deployment.md`.

**Composition root**: `cmd/vnproxd/latmesh.go`'s `setupLatMesh` builds the `Service` (real
`GraphDiscoverer` + `RealProber` + `LatencySampleRepo`) and its two run-group actors
(`RunLoop`, `RunPruneLoop`); wired into `findings.Config.LatMesh` and `api.Options.LatMesh` in
`server.go`.

**Frontend**: `web/src/topology/latencyMode.ts` (pure color/width mapping, mirrors
`trafficMode.ts`; a violet/fuchsia/pink palette, deliberately non-overlapping with
`trafficMode.ts`'s blue/green/amber/red stops and `canvasDraw.ts`'s cyan flow-overlay colors —
asserted directly in `latencyMode.test.ts`), `computeLatencyOverlayEdges` (resolves
`GET /latmesh/heatmap` links to on-canvas node ids), `canvasDraw.ts`'s new `drawLatencyOverlay`
(a static, color-scaled overlay pass, drawn after `drawFlowOverlay` — not unit-tested directly,
per that file's own documented "needs a real `CanvasRenderingContext2D`, jsdom has none"
convention), a "Latency" toggle in `LayerToggleBar.tsx` + `useTopologyStore`
(`latencyLayerActive`/`toggleLatencyLayer`, mirroring the T-1003 Flows-layer pattern exactly),
`web/src/api/latmesh.ts` + `latMeshQueries.ts` (a plain poll — no WS event exists for the
heatmap), and `LatMeshLink`/`LatMeshHeatmap`/`LatMeshSample`/`LatMeshHistory` types in
`web/src/api/types.ts`. Wired end-to-end into `TopologyPage.tsx`/`TopologyCanvasV2.tsx`.

**Docs**: `docs/api.md` (new "Latency mesh" section + `GET /findings` shape addition),
`docs/data-model.md` (`latency_samples` table, both the DDL listing and its prose paragraph),
`docs/features/monitoring.md` (§1 map-integration note, §2 history-ring note, §5 the two new

## Deviations from the task card (with reasons)

1. **Fabric scope: only `corosync` and `guest`, not `migration`/`storage`.** Neither a PVE
   migration network (`datacenter.cfg`'s `migration: network=...`) nor a distinct storage network
   is modeled anywhere in `internal/inventory`/`internal/pve` today — no reader exists for either.
   Guessing an unverified shape risks exactly the "two names, one problem" duplication T-801
   exists to prevent, so this task identifies exactly the two fabrics it concretely can (both
   reusing existing readers: `internal/host.CorosyncConfig`, `internal/xnode.BridgesByName`).
   Flagged in `internal/latmesh`'s package doc comment, `docs/api.md`'s Latency mesh section, and
   `planning/reports/needs-hardware-validation.md`.
2. **`GET /latmesh/heatmap`/`GET /latmesh/history` are node-local only, no peer fan-out.** Each
   node's `Discoverer` only ever originates pairs from itself (the full cluster mesh is the union
   of every node's own outbound pairs — node A probes A→B, node B independently probes B→A), so a
   cluster-wide *merged* heatmap view needs a new peer route. This task's card context docs list
   no Peer API section (unlike T-1301/T-1305's cards), so this is scoped out and documented as a
   follow-up — the same precedent T-803's `corosync_link_degraded` check already set for an
   identical local-node-only gap.
3. **`Baseline()`'s wiring into `POST /simulate/verify` is not implemented.** The card explicitly
   asks for "a consumable function... wiring left to whichever card next touches that surface" —
   `Service.Baseline` exists and is golden-tested, but T-806's live-probe route is unchanged by
   this task, exactly as specified.
4. **Threshold constants (`LatRttWarnMs`/`LatLossWarnPct`, 80ms/2%) are Go-level defaults, not
   `vnprox.toml`-configurable.** Matches `error_drop_rate`'s existing precedent
   (`ErrorRatePerSec`/`DropRatePerSec` aren't TOML-configurable either) — only the scheduling
   knobs (`probe_interval_sec`/`retention_minutes`/`max_rows`) got a `[latmesh]` section.

## Discovered pre-existing bug (not caused by this task, not fixed — flagged per CLAUDE.md)

`TestRunDaemon_DevConfigServesHealth` and `TestRunDaemon_PeerAPIRequiresValidSignature`
(`cmd/vnproxd`) intermittently fail with "runDaemon did not return within 5s of context
cancellation". Root-caused via a goroutine dump (`go test -timeout 4s` to force a stack dump
mid-hang): `findings.Engine.RunLoop`'s `cycle()` calls `ipamFindingsAdapter.Findings()`
(`cmd/vnproxd/findings.go`), which builds its own **detached** `context.WithTimeout(context.
Background(), 10*time.Second)` — not derived from the daemon's shutdown context at all — before
calling into `ipam.Service.Conflicts` → `neighbor.Service.Neighbors` → a real peer HTTP dial. If
that dial is in flight when the daemon's shutdown `ctx` cancels, `Engine.cycle()` (and therefore
`RunLoop`, and therefore `runGroup.run`, which waits for every actor to return) blocks for up to
the full 10s, exceeding the test's 5s grace window. The same detached-`context.Background()`
pattern exists in two more places in `cmd/vnproxd/findings.go` (`probeFindingsAdapter.Findings`,
`fwAnalyticsAdapter`-adjacent code) — an established pattern in this file, not something this
task introduced.

**Confirmed pre-existing, not a regression from this task**: reproduced on a clean checkout of
this worktree's base commit (`2e67795`, via a detached `git worktree add`) at a **2/10** failure
rate over repeated runs; this branch measured **1/10** over an equivalent repeated run — within
the same noisy range, not a meaningfully worse rate. None of this task's code appears anywhere in
the blocked goroutine's stack trace. Not fixed here: the real fix (threading a cancellable
context through `findings.IPAMProvider.Findings()`) would change a Provider-interface signature
every ctx-less seam in `internal/findings` currently shares by design (`MetricsProvider.Live`,
`CorosyncProvider.CorosyncStatus`, this task's own `LatMeshProvider.LatMeshHeatmap` included) —
out of this card's scope and risky to retrofit safely across every implementer in the time
available. Recommend a dedicated follow-up task.
