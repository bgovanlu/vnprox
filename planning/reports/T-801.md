# T-801 — Cross-node consistency validator class

## What I built

Validator **class 4** (docs/features/change-management.md §2) — the cross-node
consistency class the change engine's `validate.go` explicitly left as an
unassigned insertion point. It folds a changeset's *projected* effect across
**every** cluster node (not just the node(s) an op targets) and compares
same-named entities, raising blocking errors for divergence the changeset would
introduce or leave uncorrected. It runs after safety and before advisory,
short-circuiting advisory on any error like every other class.

### The shared package (the import-cycle fix)

`internal/drift` already imports `internal/change` (for `change.Op` fix types),
so `internal/change` cannot import `internal/drift` back. I factored the three
pure comparison families into a new lower-level package **`internal/xnode`**
(imports only `internal/inventory`) that **both** packages import:

- `xnode.BridgeDivergences` — presence / VLAN-awareness / VID-set divergence.
- `xnode.CrossNodeMTU` — the cross-node half of drift's MTU family.
- `xnode.SDNRealizationGaps` — SDN zone node-membership vs. bridge realization.

Each returns a neutral `[]Divergence` (detail, nodes, refs, and one `BridgeFix`
per dissenting node for the fixable families). `internal/drift`'s `bridge.go` /
`mtu.go` / `sdn.go` are now thin adapters over these functions (`drift/adapter.go`),
keeping their historical warning/warning/error severities and `drift:`-prefixed
fix titles; `drift/helpers.go` was deleted (its helpers moved to xnode). The
change-side class (`internal/change/validate_crossnode.go`) calls the same three
functions against a projected snapshot, raises all findings to **blocking
errors**, and builds fix patches through **`change.CrossNodeFixOps`** — the one
op-construction function `internal/drift` also calls (op construction can't live
in xnode without re-introducing the cycle). No comparison logic is duplicated.

### Scoping

The change class reports a divergence only when the changeset touches the
subject bridge (a `bridge.create`/`update`/`delete`/`port.add`/`port.remove`
op). A same-named bridge or zone the changeset leaves alone stays the async
drift checker's job — this is what makes a bare `bridge.delete` reach the SDN
realization check (its bridge name is touched) while a pre-existing, unrelated
divergence does not fail an innocent lockstep changeset.

### Projection

`projectCrossnode` seeds a `projectedGraph` (an `xnode.Source`) from the base
snapshot's bridges/nodes/zones and folds the changeset's own bridge and
`sdn.zone.*` ops forward — the same "fold every op's net effect" the other
classes' projection does, tracking the bridge/zone *properties* the cross-node
comparisons read.

### Codes / docs

`crossnode.bridge_divergence`, `crossnode.mtu_consistency`,
`crossnode.sdn_realization` (all `severity: error`). Docs updated:
change-management.md §2 (retracted the "not a pre-apply validator class … real,
currently-accepted gap" paragraph; documented class 4's position, codes, and
fixable/not-fixable split), api.md (the three codes), and architecture.md §4
(closed the flagged "this class does not exist" correction).

## What the next agent must know

- **`internal/xnode` is the single home of the three cross-node comparison
  families.** Do not re-derive bridge/MTU/SDN-realization comparison logic
  elsewhere. T-803's `evpn_gw_inconsistency` check is told to "reuse T-801's
  cluster-fold helper" — that helper is `internal/xnode` (its `Source` interface
  + comparison functions and, if a projected view is needed, the
  `projectedGraph`/`projectCrossnode` pattern in `change/validate_crossnode.go`).
  The op-construction counterpart shared with drift is `change.CrossNodeFixOps`.
- **Severity is the consumer's, not xnode's.** xnode returns neutral
  `Divergence`s; drift maps them to warning/warning/error, change to all-error.
  A new consumer picks its own severity and finding wire type.
- **Scoping is change-side only.** xnode reports *every* divergence; the change
  class filters to bridges the changeset touches. A consumer that wants "all
  divergence" (like drift) simply doesn't filter.
- No new third-party dependencies. No new API routes (only finding codes).
  No hardware-validation items — this is pure, in-process comparison logic.
