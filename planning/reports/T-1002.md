## `flow.Record` shape (docs/api.md, T-1003/T-1004's contract)

```go
type Record struct {
    Node, SrcIP, DstIP, SrcRef, DstRef string
    Source                             Source // "sflow"|"netflow5"|"netflow9"|"ipfix"|"conntrack"
    At, Bytes, Packets                 int64
    SrcPort, DstPort, Proto, VLAN,
    IngressIfIndex, EgressIfIndex      int
}
```

JSON wire shape (both `GET /flows`' `items` and `flow.batch`'s `entries`):
`{at, node, srcIp, dstIp, srcPort?, dstPort?, proto, bytes, packets, vlan?, srcRef?, dstRef?,
ingressIfIndex?, egressIfIndex?, source}`. `proto` is the numeric IP protocol (6=tcp, 17=udp,
1=icmp, ...); `at` is the exporter's own unix-seconds timestamp for NetFlow/IPFIX, the listener's
receive time for sFlow (which carries no wall-clock field of its own).

## `GET /flows` and `GET /api/peer/flows` contracts

- **`GET /flows?guest=&vlan=&subnet=&port=&protocol=&fromTs=&toTs=&limit=&cursor=`**
  (`internal/api/flows.go`, netRead-gated): every filter optional and ANDed, unrecognized/
  malformed values match nothing (never `400`) except `vlan`/`port`/`fromTs`/`toTs` themselves
  being non-numeric (`400 validation_failed`, matching `GET /audit`'s convention exactly).
  `protocol` accepts a name (`tcp`/`udp`/`icmp`/`icmpv6`/`sctp`) or a raw number.
  `limit` defaults to 100, capped at 500. Response: `{items: [flow.Record], nextCursor?, partial?,
  failedNodes?}` — the `partial`/`failedNodes` pair is present only when a `PeerFlowSource` is
  wired (cluster fan-out) and at least one peer/discovery failed, omitted entirely otherwise
  (verified by `TestFlowsRoute_LocalOnly_UnchangedWhenNoPeerSource`).
- **`GET /api/peer/flows`** (`internal/peer`, HMAC-authenticated, internal only): same filter
  params (`proto` already numeric — resolved once on the coordinating daemon), no
  `partial`/`failedNodes` (a peer reports only its own local page). Response:
  `{items: [FlowRecord], nextCursor?}` where `FlowRecord` mirrors `flow.Record` plus an `id`
  (int64) used only as the cluster-merge pagination tiebreak and stripped before `GET /flows`
  returns its own response (`flowRecordResponse` in `internal/api/flows.go` has no `id` field).

## Design notes / deviations worth flagging

- **`srcRef`/`dstRef` resolve to a Bridge or SdnVnet ref, never a GuestNic ref.**
  `internal/inventory.Graph` does not carry guest IP addresses at all — the identical documented
  gap `POST /simulate/path`'s `guest-ip-unknown` caveat already discloses for the path simulator.
  `GraphResolver` therefore only ever lands on a bridge (address-CIDR match) or an SDN vnet
  (subnet-CIDR match, resolved through the vnet rather than a per-node realized-bridge lookup this
  package doesn't have the data to do honestly). This is the honest answer given what the graph
  actually carries, per the "never guessed" contract — a guest-IP-aware second resolver stage
  (e.g. fed by T-1004's conntrack sampler, which does observe real connection 5-tuples with
  process/socket context) is a natural follow-up, not attempted here.
- **NetFlow v5 and v9 share one listener/port**, dispatched by sniffing the wire header's version
  field (`flow.NewNetFlowListener`), rather than requiring two separately-configured ports for two
  protocol versions no single real exporter ever speaks simultaneously. `vnprox.toml`'s
  `[flows] netflow_port`/`netflow_enabled` cover both.
- **IPFIX variable-length Information Elements (RFC 7011 §7's `0xFFFF` length sentinel) are not
  supported** — a template field declaring it is recorded with length 0, making any data set using
  that template silently undecodable (dropped, counted, never a panic). Every fixture this task
  ships uses fixed-length fields only. Flagged for `planning/reports/needs-hardware-validation.md`
  review against real-world exporters that might require it.
- **sFlow IPv6 support is header-only** (Ethernet + IPv6 fixed header + best-effort TCP/UDP ports);
  extension header chains are not walked, so `Proto` can report an extension header's NextHeader
  value rather than the true upper-layer protocol on IPv6 traffic using them. Also flagged for
  `needs-hardware-validation.md`.
- **`GET /flows`'s `?subnet=` filter cannot be a pure SQL predicate** — flow_samples stores IPs as
  TEXT (dotted-decimal/colon-hex), whose lexical order doesn't match numeric address order, so
  CIDR containment is computed in Go over a bounded over-fetched scan window
  (`flowSubnetScanMultiplier`/`maxFlowSubnetScanRows` in `internal/store/flows.go`). Documented
  consequence: a subnet-filtered page may return fewer than `limit` items even when more matches
  exist further back in a very sparse subnet's history — callers must keep following `nextCursor`
  until empty, which every paginated route already requires anyway. Table-tested
  (`TestFlowSampleRepo_Query_Filters`).
- **No new third-party dependency.** Every decoder is `encoding/binary` + a small hand-rolled
  bounds-checked reader (`breader.go`) — per CLAUDE.md's dependency rule and the task card's
  explicit "NO third-party flow library" instruction.

## Bugs found and fixed (development-time, not part of the shipped defect surface)

`internal/flow/listener_test.go`'s UDP-based tests were flaky (~1-in-5 to 1-in-10) during
development, traced to a real race in the test helper, not the production code: a test polling
`net.ListenPacket` on the target address in a tight loop (to detect "the real listener has bound
it") could itself win the bind race against `Listener.Run`'s own single bind attempt, starving
`Run` permanently (its bind fails immediately, returns an error the test never inspected until
after timing out). Fixed by adding a test-only `Listener.ready` channel (unexported — not part of
the public API), closed by `Run` immediately after its own successful bind, which every test now
waits on instead of polling from the outside. Confirmed fixed: 10/10 clean runs plus a `-race` run
after the fix, versus repeated failures before it.

## Fixture generation

`testdata/flows/*.bin` were generated by a small standalone Go program (not committed — pure wire-
encoding logic, no dependency on `internal/flow`, run once via `go run` from the scratchpad and its
output copied into `testdata/flows/`) rather than by hand-editing bytes, to keep the golden
fixtures internally consistent (e.g. the NetFlow v9 template/data pair's field layout is generated
from one shared Go slice literal, not duplicated by hand in two places). `netflow5_truncated.bin`/
`netflow9_truncated.bin`/`ipfix_truncated.bin`/`sflow5_truncated.bin` are straight byte-slice
truncations of the corresponding `_basic.bin` fixtures. `netflow9_data_no_template.bin` is a
freestanding v9 data datagram referencing template id 999, which the golden-test cache never
populates.

## flow-lab fixture

`testdata/clusters/flow-lab.yaml`: a 2-node pvemock cluster whose bridge addresses
(pve1's `vmbr0` = `10.0.0.0/24`, pve2's `vmbr0` = `10.1.1.0/24`) and one SDN zone/vnet/subnet
(`vlanz`/`vnet100`/`10.100.0.0/24`) are deliberately chosen to match IPs already baked into
`testdata/flows/*.bin`'s golden datagrams. `internal/flow/flowlab_integration_test.go` loads it
into a real `pvemock.Server`, polls it into a live `*inventory.Graph` via `internal/collect`
exactly the way `cmd/vnproxd` does, refreshes a `GraphResolver` from that graph, and asserts
several golden-fixture IPs resolve to the correct real bridge/vnet refs — plus that an IP no
fixture subnet covers (`8.8.8.8`, `netflow5_basic.bin`'s external destination) never resolves,
proving the "never guessed" contract end-to-end against real polled state, not just hand-built
unit-test entities (`resolve_test.go` covers that unit level separately).
