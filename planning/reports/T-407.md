## 0. Starting state

Before writing any code I surveyed what earlier tasks (T-102 interfaces(5)
parser, T-103/T-104 inventory, T-204/T-205 the ifaces writer/apply engine)
had already built for OVS as generic groundwork: the parser round-trips OVS
stanzas, `inventory.Kind` already has `ovs-bridge`/`ovs-bond`, `Bridge.Virt`
already distinguishes linux/ovs, `internal/change/ifaces`'s bond/bridge
mutators already branch on `ovs`, and `internal/change`'s referential/schema
validators already treat `KindOVSBridge`/`KindOVSBond` as bridge/bond
variants throughout. This significantly narrowed T-407's actual scope —
most of the file-format and op-plumbing groundwork existed; what was
missing was semantic completeness (OVS Int Ports, the runtime reader,
cross-kind validators, editor forms, map badge, fixtures) plus several real
gaps the survey turned up (see §4).

## 1. What was built

**`internal/inventory` — OVS Int Port semantics.** `VlanIface` gained
`Virt string` ("" | "ovs", mirroring `Bridge.Virt`'s exact shape/precedence
— no `*Set` companion needed, same reasoning) and `Trunks []VidRange`
(OVS-only trunk VID ranges). `interfacesOVSIntPort` (the interfaces(5)-text
path) now sets `Virt: "ovs"` and parses `ovs_options trunks=...`;
`FromPVENetwork`'s `OVSIntPort` case sets `Virt` too. `merge.go` gained
ownership rules for both new fields. **Real gap fixed:** `FromPVENetwork`
had no `"OVSBond"` case at all — an OVS bond reported via PVE's network API
contributed nothing to the graph, silently dropping the `pve-network`
cross-check source for every OVS bond. Added, mirroring the existing
`"bond"` case.

**`internal/change` — writer + validators.** `VlanCreateParams` gained
`OVS bool` and `Trunks []VidRange` (the "params carry ovs-specific fields"
case docs/data-model.md flagged, since `KindVlan` has no OVS-kind sibling
the way Bridge/Bond do). `BondCreateParams` gained `Bridge string` — **a
real gap**: `internal/change/ifaces.BondCreate.Bridge` (ovs_bridge
attachment) already existed and was already wired through `DecodeOp`, but
`change.BondCreateParams` never had a matching field, so there was no way
to actually set an OVS bond's bridge attachment through the change engine
end to end. `internal/change/ifaces/vlanop.go`'s `mutateVlanCreate` now
branches on `OVS`: writes `ovs_type OVSIntPort`/`ovs_bridge`/`ovs_options
tag=N trunks=...` and uses the `allow-<bridge>` autostart prefix (matching
ifupdown2's OVS convention), instead of `vlan-raw-device`/`auto`.

Validators (docs/features/change-management.md §5's "OVS bond mode enums
validated" / "tag/trunk consistency checked" / "mixing Linux-bridge ports
into OVS bridges and vice versa -> error"):
- `validOVSBondModes` (active-backup/balance-slb/balance-tcp/802.3ad/lacp)
  is a materially different enum from `validBondModes` (the Linux bonding
  driver's) — `bond.create`/`bond.update` now select the right one from
  `target.Kind`. Previously an OVS bond with a valid OVS mode like
  `balance-slb` would have been *rejected* by schema validation (not in the
  Linux-only enum) — a real bug.
- New referential check `checkOVSKindCompat` (code
  `referential.ovs_kind_mismatch`): rejects a Linux bridge/bond as a
  port/slave of an OVS bridge/bond and vice versa, wired into
  `checkPorts`/`checkSlaves`/`bridge.port.add`.
- `checkOVSBridgeParent`: an OVS bond's/Int Port's `bridge`/`parent` must
  name an existing OVS bridge; a plain VLAN's `parent` must *not* be an OVS
  bridge.
- Schema: OVS int port's `Trunks` range-checked; rejected outright
  (`schema.ovs_trunk_not_allowed`) when `ovs` is false. Referential:
  overlapping trunk ranges reused `checkVIDOverlap`. An untagged/trunk-only
  OVS Int Port (`vid == 0`) is excluded from the `(node,parent,vid)`
  duplicate-VID index (both in `referentialValidate` and
  `projection.fold`) so several trunk-only int ports on the same bridge
  don't spuriously collide on `vid=0`.

**`internal/pvemock` — real bugs found and fixed.** `render.go`'s
`RenderInterfaces` rendered an `OVSBridge`-typed fixture entry using the
*Linux* `bridge-ports`/`bridge-stp` vocabulary — every fixture-declared OVS
bridge was silently misclassified as a Linux bridge on the
`FromInterfaces`/inventory read path. Fixed with proper
`ovs_type`/`ovs_ports`/`ovs_bonds`/`ovs_bridge`/`ovs_options` rendering for
`OVSBridge`/`OVSBond`/`OVSIntPort`, plus the `allow-ovs`/`allow-<bridge>`
autostart convention. `fixture.go`'s `validateNodeNetwork` didn't validate
`OVSBond` slaves or `OVSIntPort` parent references at all; fixed.
`NetIface.VlanRawDevice`/`VlanID` are reused (not new fields) as the
`ovs_bridge`/tag carriers for `OVSBond`/`OVSIntPort` fixture entries,
matching the existing precedent `FromPVENetwork`'s `OVSIntPort` case
already set for those exact fields.

**`internal/host` — `ovs-vsctl` runtime reader (new file `ovsvsctl.go`,
~420 lines with tests/fixtures).** A new `OVSReader` interface (kept
*separate* from `Reader` — see §3's deviation note) with one method,
`OVSStatus`, returning `[]OVSBridgeStatus{Name, Ports[]OVSPortStatus{Name,
Tag, Trunks, BondMode, Interfaces[]OVSInterfaceStatus{Name, Type,
LinkState, Rx/TxBytes, Rx/TxPackets}}}`. Implementation issues three fixed-
argv commands (`ovs-vsctl -f json --columns=<fixed list> list
Bridge/Port/Interface`), decodes OVSDB's JSON wire format (the
set/map/uuid `["tag",value]` wrapper convention, including the "bare atom
for a 1-element set" special case), and joins the three tables by UUID.
Absent tooling: `exec.LookPath`'s "not found" is wrapped in
`ErrOVSUnavailable`, mirroring `ErrLLDPUnavailable`/`Real.LLDP` exactly.
`*Real` implements `OVSReader` on Linux; the `!linux` stub returns
`ErrUnsupportedPlatform` like every other `Real` method.

**`internal/topology` — map badge.** `badgesOf` now emits an `"ovs"` badge
for `KindOVSBond`/`KindOVSBridge` entities and for a `VlanIface` with
`Virt == "ovs"` (additive to `EntityNode`'s existing `data.kind` corner
label, which already read `"ovs-bridge"`/`"ovs-bond"`). An OVS Int Port's
tag/trunks reuse the existing `"tag="`/`"vlans="` badge vocabulary
(`badgeCarriesVlan` already parses both), so the VLAN filter highlights OVS
Int Ports with **zero frontend changes**.

**`web/` — editor kind selectors.** `BridgeEditor`/`BondEditor` gained a
create-time Linux/OVS kind selector driving the target Ref prefix
(`bridge:`/`ovs-bridge:`, `bond:`/`ovs-bond:`) and hiding Linux-only fields
(VLAN-aware/vids/STP for bridges; LACP rate/hash policy/MII monitor for
bonds) when OVS is selected; `BondEditor` also gained an "OVS bridge"
picker (new `ovsBridgeCandidates` in `entityCandidates.ts`) feeding the new
`bridge` param. `VlanEditor` gained a VLAN-sub-interface/OVS-Int-Port kind
selector: OVS mode swaps the parent picker to OVS bridges only, adds a free
Name field (OVS Int Ports aren't named by the `parent.VID` convention),
relabels VID as "Tag" (0 = untagged/native), and adds a Trunks field.
`opBuilders.ts` threads `bridge`/`ovs`/`trunks` through
`buildBondCreateOp`/`buildVlanCreateOp`. Per this codebase's established
convention (no `editors/*.test.tsx` exist for any editor today — logic
lives in and is tested through `opBuilders.ts`), I did not add new
component-mount tests; the kind-driven param logic is covered in
`opBuilders.test.ts`.

## 3. Deviations from the task card (with reasons)

- **`OVSReader` is a separate interface from `host.Reader`, not a 5th
  method on it.** `Reader`'s doc comment explicitly documents its
  four-method shape as a deliberate, cross-package contract
  (`pvemock.HostReader` mirrors it structurally; `FixtureReader` adapts
  between them). Adding a 5th method would break that documented parity
  for every existing implementer and test double, for a capability that is
  meaningfully different in kind (may be entirely absent, unlike the
  always-available netlink/file/LLDP/sysfs sources). `OVSReader` follows
  the same conventions (ctx+node signature, graceful-degradation sentinel
  mirroring `ErrLLDPUnavailable`) without touching the existing contract.
  Flagged per the task prompt's "if something truly blocks you, flag it
  instead of changing it unilaterally" — this wasn't a blocker, just a
  scope boundary I drew deliberately.
- **`OVSStatus` is not wired into the collector/inventory pipeline.** No
  `SourceHostOVS` inventory source, no collector poll loop calls it. This
  is a genuine scope cut, not an oversight: the two things `OVSStatus`
  would add over what's already there — (a) live OVS bond member link
  state, since `/proc/net/bonding` doesn't cover OVS bonds — has no
  inventory field to land in today (`Bond.SlaveDetail` is netlink/proc-
  bonding-only by ownership rule); (b) per-port stats — is already covered
  generically by the existing sysfs-based `Stats()` for any interface
  including OVS ports/bonds (they're real netdevices). Wiring it fully
  would mean extending `inventory.Bond` with an OVS-bond-only runtime
  field and a new `Source`/ownership-rule entry for a single field — a
  reasonable follow-up, not blocking any of the five acceptance criteria.
  Flagged here explicitly per the task's guidance.
- **`pvemock.NetIface` gained no new fields**; `VlanRawDevice`/`VlanID` are
  reused for `OVSBond`/`OVSIntPort`'s `ovs_bridge`/tag, matching the
  precedent `FromPVENetwork`'s pre-existing `OVSIntPort` case already
  established for the same fields. A cleaner `OvsBridge`/`OvsTag` field
  pair (matching real PVE's actual API field names) is possible but touches
  `pve.NetworkInterface`, `pvemock.NetIface`, and their JSON tags together
  for a benefit (real-PVE-field-name fidelity) that doesn't matter without
  hardware to validate against — noted as a "needs hardware validation"
  item if a future task gets real PVE access.
- **Editor components have no new `.test.tsx` files.** No editor
  (`BridgeEditor`/`BondEditor`/`VlanEditor`/`InterfaceEditor`) has a
  component-mount test anywhere in this codebase today; `opBuilders.ts`
  exists specifically so editor logic is Vitest-able without React Testing
  Library. I followed that existing convention rather than introducing a
  new one unilaterally.

## 4. Anything the next agent must know

- **Real hardware validation gap**: `internal/host/ovsvsctl.go`'s OVSDB
  JSON decoding (the `["tag",value]` set/map/uuid wrapper convention,
  including the "bare atom for exactly one set member" rule) is based on
  my understanding of the documented OVSDB wire protocol, exercised only
  against synthesized fixtures (`testdata/ovsvsctl/`) — there is no live
  Proxmox/OVS install to validate real `ovs-vsctl -f json` output against.
  Flagging this explicitly as **needs hardware validation** before treating
  `Real.OVSStatus` as production-trustworthy.
- `internal/change/restore_ops.go` still documents (pre-existing, T-205-era
  comment, unchanged by this task) that OVS bond re-creation during
  snapshot restore can't recover the `ovs_bridge` attachment because
  `inventory.Bond` doesn't carry it. That's still true after T-407 — I
  didn't extend `Bond` with a parent-bridge field since nothing in this
  task's acceptance criteria required inventory to carry it (the *writer*
  side already had `BondCreate.Bridge`/now `BondCreateParams.Bridge`; only
  the *reader*/inventory side has this gap). Worth closing in a follow-up
  if snapshot-restore-of-OVS-bonds becomes a priority.
- The OVS Int Port `(node,parent,vid)` duplicate-detection carve-out
  (untagged/trunk-only ports don't collide) only special-cases `vid == 0`.
  Two OVS Int Ports with the *same* non-zero tag on the same bridge still
  correctly collide (existing behavior, unchanged) — only the "several
  distinct trunk-only ports" case needed the fix.
- `docs/data-model.md` §1 and §3 were updated in this change to document
  the new `VlanIface.virt`/`trunks` fields and the `bond.create`'s `bridge`
  / `vlan.create`'s `ovs`/`trunks` params, per this task's "params carry
  ovs-specific fields" note.
