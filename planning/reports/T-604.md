### Real gaps found and fixed (not just verified)

The audit surfaced four genuine, previously-unaddressed security gaps:

1. **SQLite DB file permissions (`internal/store/store.go`).** The sqlite
   driver creates the main DB file and its WAL/SHM sidecars honoring the
   process umask — under the common `022` umask that's `0644`,
   world-readable, contradicting `docs/security.md`'s "SQLite DB and key
   files are root:root 0600" claim. `Open` now enforces `0600` explicitly
   after opening/migrating, including correcting a pre-existing
   looser-mode file on reopen (not just newly-created ones). Verified this
   was a real gap first (a scratch test proved the pre-fix mode was 0644
   under an adversarial umask) before writing the fix. Tests:
   `TestOpen_EnforcesFilePermissions`, `TestOpen_CorrectsPreExistingLoosePermissions`
   (`internal/store/store_test.go`).

2. **Session ids logged in full (`internal/auth`).** Eight call sites
   (`middleware.go`'s `SessionMiddleware`, `renewal.go`'s renewal/
   capability-refresh loop, `handlers.go`'s logout handler) logged the raw
   session id at Warn/Error level. The session id *is* the bearer
   credential in the `vnprox_session` cookie — logging it verbatim would
   let anyone with read access to the daemon's logs (a materially weaker
   privilege than host shell/root access — e.g. a centralized log
   aggregator, or `journalctl` group membership) hijack that session
   directly, bypassing HttpOnly/Secure/SameSite entirely (those flags only
   defend against browser-side/network attackers, never a log reader).
   Added `logSessionID` (`internal/auth/service.go`), truncating to an
   8-character correlation-handle prefix (enough for operators to tie
   multiple log lines to "the same session", the only reason these sites
   logged the id at all; not enough remaining entropy to be replayable),
   applied at all 8 sites. Tests: `TestLogSessionID_TruncatesToPrefix`
   (unit, `internal/auth/secretlog_internal_test.go`) and
   `TestRenewalFailureLog_NeverLeaksFullSessionID` (end-to-end, driving a
   real renewal failure through a captured `slog.Logger`,
   `internal/auth/secretlog_test.go`).

3. **No automated test for session idle/hard-cap expiry (`internal/auth`).**
   `docs/security.md`'s "vnprox sessions idle out at 2h, hard cap 12h"
   claim had no automated test at all — `SessionMiddleware`'s idle-slide
   and hard-cap logic (`middleware.go`) was exercised only indirectly.
   Added `internal/auth/sessionexpiry_test.go`: three tests driving a fake
   clock across both boundaries (idle expiry on inactivity, idle-timeout
   sliding forward under steady activity, and the hard cap firing despite
   continuous activity that would otherwise keep the idle timeout from
   ever lapsing). Note for future maintainers: session `ExpiresAt` is
   stored as whole Unix seconds, so idle/hard durations under test must be
   second-granular — an early draft using sub-second timeouts silently
   never expired, a real trap worth documenting (now documented in the
   test file itself).

4. **Systemd unit missing `RestrictAddressFamilies`/`SystemCallFilter`
   (`packaging/systemd/vnprox.service`).** Acceptance criterion 2's
   required directives were partially present (`ProtectKernelModules`,
   `ProtectKernelTunables` already landed from an earlier task) but
   `RestrictAddressFamilies` and a `SystemCallFilter` profile were absent.
   Measured against every socket/syscall path vnproxd actually exercises
   (rtnetlink via `vishvananda/netlink`, the HTTPS/WS server, the PVE/peer
   HTTP clients, and the fixed-argv subprocess execs already documented
   above `CapabilityBoundingSet`): `AF_INET`/`AF_INET6`/`AF_NETLINK` cover
   all of it (no cgo dependency in `go.mod`, so no `AF_UNIX` is needed for
   name resolution; `Type=simple` means no `sd_notify` socket either).
   `SystemCallFilter=@system-service` plus an explicit re-deny of
   `@mount @reboot @swap @privileged @resources @raw-io @debug @module
   @cpu-emulation @obsolete @clock` removes syscall groups none of
   vnproxd's documented operations need.

### CSP tightening (verified against the Playwright suite)

`internal/api/middleware.go`'s CSP already met `docs/security.md`'s
"strict CSP (self-only; no inline script; WS to self)" claim; tightened
further to the actual minimum the SPA uses: `object-src 'none'`,
`frame-src 'none'`, `worker-src 'none'`, `manifest-src 'none'` (no
`<object>`/`<embed>`/iframes/`Worker()`/service worker/web-app manifest
anywhere in `web/src` — elkjs's bundled layout runs on the main thread, not
a `Worker`), and `form-action 'self'` (all mutations are `fetch()` via
TanStack Query, never an HTML `<form>` submit). `TestSecurityHeaders`
(`internal/api/router_test.go`) extended to assert the new directives.

**How the Playwright verification was actually done** (not just "narrowed
and hoped"): ran the full 22-test suite with the tightened CSP, then
`git stash`ed the CSP change back to baseline and reran the same failing
tests against the *untightened* CSP. The same three failure modes
reproduced identically against both (a `readonly-crawl.spec.ts` pre-existing
Delete-button gap — see the ancillary finding below — and a
`topology.spec.ts` screenshot pixel-diff flake, both environment/product
issues unrelated to CSP), and `changesets.spec.ts` passed cleanly on retry
under baseline, confirming its one observed failure was pre-existing
flakiness, not a CSP regression. This environment is measurably resource-
constrained (shared with several other concurrent agent worktrees), which
made flakiness rates vary run-to-run; the controlled baseline-vs-tightened
comparison (not raw pass counts from any single run) is what actually
proves no regression. A later clean run (`test-results/.last-run.json`)
recorded `"status": "passed"` with an empty `failedTests` array for the
full 22-test suite under the tightened CSP.

### Secrets-in-logs sweep

Two complementary automated tests, plus one manual real-browser
confirmation:

- **`cmd/vnproxd/secretlog_test.go` (`TestSecretsNeverAppearInLogs`, part of
  `make check`/CI, not gated behind the opt-in Playwright suite):** a real

## 2. Deviations from the task card (with reasons)

- **The task card's context doc example says "run a real E2E flow
  (Playwright, web/e2e) ... build this as an automated test."** The
  *permanent*, CI-enforced automated test I built
  (`TestSecretsNeverAppearInLogs`) is a Go-level test in `cmd/vnproxd`
  against the real `runDaemon`, not a browser-driven Playwright spec. I
  judged this the better placement: it runs on every `make check`/CI
  invocation rather than only the opt-in Playwright suite, it captures the
  daemon's log output byte-exactly (no risk of missing lines to stdout
  buffering/multiplexing), and it avoids permanently modifying
  `web/playwright.config.ts`'s shared `webServer` commands — used by six
  other spec files across several completed tasks — for a config change
  whose only purpose is log capture. I did also do a real, one-time manual
  Playwright/browser-driven capture-and-grep (see above) to satisfy the
  literal "real E2E flow" spirit, but did not make that permanent CI
  infrastructure. Flagging this choice explicitly in case the orchestrator
  wants the Playwright version made permanent instead — it would need a
  `globalTeardown` script reading a tee'd log file, which I scoped out as
  a separate, riskier change I didn't want to land unreviewed alongside
  everything else in this already-large task.
- **Did not fix the `web/src/firewall/ObjectsPanel.tsx` read-only Delete
  button gap** discovered during Playwright verification (see
  `docs/security-verification.md`'s ancillary finding). It is a T-605
  ("every write affordance disabled-with-tooltip") UX-completeness gap,
  not a `docs/security.md` claim — the backend's `RequireCap`/PVE-ACL
  enforcement already blocks the actual mutation regardless of the
  button's UI state, so there is no privilege-escalation risk. Fixing
  frontend product components outside a specific, understood task's
  surface felt like scope creep on an already very large audit task;
  flagged instead, per the "prefer small, targeted diffs... do not
  restructure other tasks' surfaces" constraint.
- **Did not modify `docs/security.md` itself** despite finding one place
  where its literal wording is stale (ethtool is invoked via a direct
  `SIOCETHTOOL` ioctl, not a subprocess at all — a T-102-documented
  deviation, and actually a *stronger* security property than the
  documented "fixed argv" claim). Noted in
  `docs/security-verification.md` as a docs-freeze item for T-607 rather
  than silently editing the security doc mid-audit.

## 4. Gaps / things that could NOT be verified here (needs hardware validation)

Per CLAUDE.md, these are flagged rather than silently skipped — all are
also called out at the specific claim in `docs/security-verification.md`:

1. **Full systemd-unit functional parity as root under a real systemd PID
   1** (as opposed to the `systemd-run --user` smoke test done here). No
   passwordless root/sudo is available in this environment, and this
   repo's own `packaging/test/deb-install.sh` already documents the same
   limitation for `systemctl start vnprox` in its container-based tests
   (plain `debian:12`/`debian:13` containers don't run systemd as PID 1).
2. **`root:root` file ownership** for the SQLite DB and session key
   (the *mode*, 0600, is unit-tested and now enforced in code; the
   *ownership* half depends on the daemon actually running as root per a
   real install).
3. **Cluster secret distribution via pmxcfs** (`/etc/pve/vnprox/`) — no
   pmxcfs in this dev environment; the secret-loading/reload code itself
   is unit-tested independent of pmxcfs (`internal/peer/secret_test.go`).
4. **`vnprox@pve!daemon` installer-time role/token creation** with
   auditor-level privilege — this is T-606's documented territory
   (already flagged in that task's own report); this task verified only
   that the *code* never routes a write through the token-mode client.
