## Correcting the card's premise

The card's objective states "no test walks a v1.0-era database up to current." That was not
quite true: `internal/store/migrate_fromeach_test.go` already existed (from T-606, phase 6) and
already had the right *shape* — `openFrozenAt` (freeze a DB at schema version V by replaying only
migrations 1..V) and a table-driven `TestMigrate_FromEachPriorSchemaVersion` that seeds, migrates
to latest, and asserts survival. What it actually covered was narrower than the card assumed:
**only schema versions 0 (fresh install) and 1 and 2** — two hand-written cases, not the full
1..32 range. Every version from 3 through 32 (30 of the 32 shipped, pre-current versions) had
never been exercised as an upgrade source at all. So the honest framing is: the harness existed
and worked; the fixture *corpus* was 3/32 of what AC1 requires. This report is about closing that
gap, not building the harness from scratch.

## What I built

### 1. Fixture corpus: versions 1–32, one seed/assert pair each (AC1, AC2)

`internal/store/migrate_fromeach_test.go` (rewritten, +1150/-140 lines). Kept `openFrozenAt`
unchanged. Replaced the two hand-written cases with a registry:

```go
type versionSeed struct {
    seed   func(t *testing.T, db *sql.DB)
    assert func(t *testing.T, db *sql.DB)
}
var versionSeeds = map[int]versionSeed{ 1: {seedV1, assertV1}, ..., 32: {seedV32, assertV32} }
```

`freezeAndSeed(t, db, upto)` / `assertSeededThrough(t, db, upto)` compose every registered version
1..V in order, so a database frozen at version V is seeded with the **exact cumulative shape** a
real node upgrading from that release would have on disk — not a synthetic snapshot. Each
`seedVN` inserts only what migration N itself introduced (a new table, or a value in a column an
`ALTER TABLE` added); each `assertVN` checks specific column values per table (not row-count or
"no error"). `TestMigrate_FromEachPriorSchemaVersion` now runs one subtest per version 1..32 (plus
the pre-existing version-0/fresh-install case): freeze → seed cumulatively → `migrate()` to
latest → assert `schema_version == latest` → assert every seeded value survived, per table → run
`migrate()` again to confirm the already-latest no-op path.

**Reproducibility, per the card's design guidance:** nothing is a committed blob. Every fixture is
built at test time by replaying the real `migrations/*.sql` files and running Go code — deleting
the whole file and re-running `go test` regenerates the identical corpus.

**Exhaustiveness is enforced, not just achieved once:** before running any subtest,
`TestMigrate_FromEachPriorSchemaVersion` walks 1..latest-1 and `t.Fatalf`s if any version has no
`versionSeeds` entry, naming exactly which `seedVN`/`assertVN` to add. Verified this fires
correctly: temporarily deleted the `20: {...}` registry line and re-ran — got
`no versionSeeds fixture registered for schema version 20 — add seedV20/assertV20 ...` and the
test failed as designed; restored the line, re-verified green. This means the next migration to
land (0034) is a **build failure**, not a silent coverage gap, until its own seed/assert pair is
added — the "As new migrations land, this test automatically grows" claim in the old file's doc
comment was aspirational before; now it's actually enforced.

Version-by-version notes worth flagging:
- v21 (`clusters` table) and v28/v32/v33-adjacent ALTER TABLEs (`changesets.cluster_id`,
  `audit_log.cluster_id`, `changesets.origin`/`origin_token_id`, `clusters.wg_tunnel_id`) are
  exercised by `UPDATE`ing the already-seeded v1 row rather than inserting a fresh one — this
  matches what a real upgrade does (an old row gains a new column, not a new row).
- v16 (`wireguard_peers.tunnel_id`) and v30 (`tenant_scopes`/`tenant_members`/
  `changeset_requests` all `REFERENCES tenants(id)`) are the only tables with declared FKs beyond
  v1's `snapshots.changeset_id`; `openFrozenAt`'s DSN runs with `foreign_keys=1`, so these seeds
  insert the parent row first, in-function, same as real code would.
- Schema 33 (`0033_changeset_revert_ticket.sql`, this arc's own T-1805) has **no** `versionSeeds`
  entry by design — it's the current latest, not a "prior" version any fixture freezes at. Its
  forward application is exercised by every case above (all 32 migrate through it), and
  `TestOpen_CreatesAllTables` covers it from a fresh DB. The next migration to land becomes the
  new latest and picks up a version-33 entry then.

### 2. AC3: a destructive-migration probe that genuinely bites

`TestMigrate_DestructiveMigrationIsCaught` seeds v1, migrates to latest, then applies a synthetic
extra migration (`version: latest+1`, `DELETE FROM sessions; DELETE FROM kv WHERE k =
'install_id';`) on top — simulating a future release whose migration ships a bug that drops rows
instead of only adding schema — then calls the **exact same** check every other case relies on
and asserts it reports the loss.

This needed one real design decision, not just plumbing: **Go's `testing.T` propagates a
subtest's failure to its parent unconditionally**, regardless of what the parent does with
`t.Run`'s returned bool. My first draft ran the destructive scenario inside a `t.Run(...)` and
checked the returned bool — the probe correctly detected the data loss, but the outer test still
reported `FAIL` every time, because a failed subtest always fails its parent in Go's test
framework, with no way to opt out. Fixed by splitting `assertV1` into a pure `checkV1(db) []string`
(returns problem strings, no `testing.T` involved) and a thin `assertV1(t, db)` wrapper
(`for _, p := range checkV1(db) { t.Error(p) }`). The destructive test calls `checkV1` directly
and asserts `len(problems) > 0` as an ordinary value — no subtest, no propagation fight.

Verified genuinely: `go test -run TestMigrate_DestructiveMigrationIsCaught -v` →
`destructive migration correctly detected — data-preservation checks caught 2 problem(s):
[sessions row lost across migration: sql: no rows in result set  kv row lost across migration:
sql: no rows in result set]`, test itself green. I also manually reverted the delete to a no-op
SQL and confirmed the outer test then correctly fails ("checkV1 found NO problems ... AC3
failed") — proving the meta-test's own failure path works, not just its happy path.

Note the destructive SQL deliberately does **not** touch `changesets` (only `sessions`/`kv`):
`snapshots.changeset_id REFERENCES changesets(id)` with `foreign_keys=1` enforced means deleting
`changesets` while `snap-v1` still references `cs-v1` throws a real FK-constraint error rather
than silently succeeding — that would test SQLite's own FK enforcement, not this file's
assertions, and isn't what AC3 is asking for.

### 4. Packaging test (AC4): `packaging/test/upgrade-service.sh`, new

`upgrade.sh`/`deb-install.sh` both explicitly flag "systemctl start vnprox itself is NOT exercised
here: plain debian:12 containers do not run systemd as PID 1" — AC4 asks for exactly that
("the service comes back up"), so I closed the gap with a new script rather than stretching an
existing one. It builds a systemd-capable image on top of the target base (`apt-get install
systemd systemd-sysv`), boots it with `podman run --systemd=always ... /sbin/init`, and drives a
real `apt install` upgrade (`0.9.0` → `1.0.0`, same "no real prior tag exists yet" honesty note as
`upgrade.sh`) against a real `vnprox.service`, asserting via `systemctl is-active` + `ss` that it
serves before *and* after, with a different PID after (proof postinst actually restarted it, not
that it never stopped). Also asserts `/etc/vnprox/keys` content-hash **and** permissions (0700
dir / 0600 key file) survive — per the card's design guidance, that's the assertion that actually
matters (losing the session key makes every sealed credential unreadable, worse than a failed
upgrade), so it's checked two ways, not one.

Two real bugs found and fixed building this, both worth recording:

1. **Port collision, not a product defect.** First run bound vnprox's shipped default 8007 with
   `--network=host` (required here — this sandbox's rootless podman has no pasta/slirp4netns for
   `podman run`, so a bridge network can't reach `deb.debian.org`, same constraint
   `port-conflict.sh` already documents). Failed with a confusing "systemd says active(running)
   but nothing is listening" symptom. Root-caused by the orchestrator: a concurrent Playwright run
   verifying T-2001 had its own `webServer` fleet holding `127.0.0.1:8007` at that exact moment.
   Fixed properly, not worked around: `TEST_PORT` is now `61007`, chosen outside the *entire*
   "N8006/N8007" family `web/e2e`'s own eight-fixture-pair port scheme already occupies
   (8006-8008, 18006-18008, 28006-28007, 38006-38007, 48006-48007, 58006-58007 — grepped
   `web/playwright.config.ts`/`web/e2e/*.spec.ts`), not just a different member of it (an
   intermediate draft picked 28017, close enough to the fleet's own 28006/28007 to be worth
   catching even though it wasn't an actual collision). Added an explicit preflight check
   (`ss -tln | grep ":${TEST_PORT}"`) that fails immediately with a clear message rather than
   reproducing the confusing failure a second time.
2. **`vnprox.service` is `Type=simple`** (`packaging/systemd/vnprox.service`), so `systemctl
   is-active` goes true the instant the process forks — well before vnproxd finishes its own
   startup (migrations, cluster-secret generation) and binds the HTTPS listener. Found this
   *after* fixing the port collision, on a completely clean host: `systemctl status` showed
   `active (running)` with a real PID 110ms after start, journal had only the very first startup
   log line, and `ss` genuinely found nothing on the port yet. Fixed by giving the `ss` checks
   their own poll loop (up to 15×1s), separate from the `is-active` poll loop.

Final foreground run, clean host, both fixes in place:
```
--- start the REAL systemd service ... --- 
--- upgrade to 1.0.0 (real dpkg upgrade action, not a reinstall) ---
vnprox: session encryption key already present at /etc/vnprox/keys/session.key, leaving it untouched
--- the service comes back up on its own (postinst restarts it because it was running) ---
--- app-owned data + /etc/vnprox/keys survived, byte-for-byte and permission-for-permission ---
--- vnproxctl (daemon-independent, T-206) opens the store post-upgrade cleanly ---
No snapshots.
ALL CHECKS PASSED
```
Confirmed no leftover containers/images after (`trap cleanup EXIT` runs on both success and
failure paths — verified by killing an earlier run mid-flight too).
