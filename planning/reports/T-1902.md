## 1. What was built

### The hole, precisely

vnprox had no way to be diagnosed by anyone who could not SSH into it. `vnproxctl status` needs a
live daemon and an operator's terminal; `journalctl -u vnprox` needs a shell; nothing produced a
single artefact you could attach to a message. That is the gate on Phase 21: you cannot ship this to
strangers if a stranger's broken install is only diagnosable by logging into it.

The card's hazard is the reason it is 🔒: **the artefact this card produces is going to be posted in
public.** A backup archive is something an operator stores and might lose; a support bundle is
something an operator *publishes on purpose*, trusting that the credentials were removed. A PVE API
token or a WireGuard private key in a forum thread is strictly worse than having no support bundle.

### `vnproxctl support-bundle`

```
vnproxctl support-bundle --dry-run     # print exactly what would be collected; write nothing
vnproxctl support-bundle               # -> /var/lib/vnprox/support/vnprox-support-<node>-<UTC>.tar.gz
vnproxctl support-bundle --no-probe    # make no outbound connection at all
vnproxctl support-bundle -o json
```

Eleven entries, ~4.5 KiB on an empty install (measured, §4). It joins the **daemon-independent**
command family (`status`/`snapshots`/`rollback-now`/`backup`/`restore`) — deliberately, because a
bundle is most needed when vnproxd will not start.

### What was reused from T-1901, and what was deliberately not duplicated

T-1901's handoff was followed point by point. **No second archive format, no second secret
inventory, no second collection seam.**

| T-1901 gave me | How it is used |
|---|---|
| `KindSupportBundle` in the manifest | The bundle writes it, so `Restore` already refuses a bundle (`ErrWrongKind`) — now asserted against a **real** bundle rather than a hand-made one (`TestBundle_IsRefusedByRestore`). |
| The `Collector` seam and `Staging` | Every entry goes through `Staging`, so nothing reaches an archive without a recorded digest and a manifest entry describing it. |
| `SecretClasses()` (20 classes) | Drives AC1's table, the key-file probe, and the generated "what is NOT in here" list. **Extended, not replaced** — no new inventory was created. |
| `seed_test.go`'s fixture + `secretMarkers` + the unsealed-value control idea | AC1 lifts the shape wholesale; see §2 Claim 1 for how the control had to change (a bundle contains no store, so T-1901's control would have proved nothing here). |
| `Write`/`Inspect`/`Extract`, `Limits`, `validEntryName` | Untouched. A bundle validates and is parsed by exactly the same reader. |
| `store.InspectSchemaVersion` | Reports the store's version without migrating it — which is the whole of AC3 scenario 3. |

**Why this lives in `internal/backup` rather than a new package:** the card's author note says the
bundle is "structurally a backup with a harsher redaction policy and a narrower scope", and the
abstraction did not fight me. Putting it elsewhere would have meant exporting `Staging`'s internals,
duplicating T-1901's seeded fixture (the thing the dispatch explicitly ruled out for T-1901), and
splitting the secret inventory's consumers across packages.

### New files

**`internal/backup/bundle.go`** — `BundleOptions`, `BundlePlan`, `Bundle()`, the collector list, the
generated readme.

**`internal/backup/bundlecollect.go`** — nine collectors, the two open-format allowlists
(`configKeyAllowlist`, `ifaceOptionAllowlist`), and `bundleCollector`/`sealedCollector` (below).

**`internal/backup/bundledocs.go`** — every structured document a bundle emits, gathered in one file
because the AC2 enforcement point has to be able to enumerate them.

**`internal/backup/bundleschema.go`** — the declared inventories (`bundleFieldSchema`,
`bundleEntrySchema`) and `checkSchema`, the reflection walk that enforces them.

**`internal/backup/redact.go`** — `Scrub` (shape-matching value redactor), `redactJSON` (key-name
JSON walk), `redactedOptionValue`, and `Redacted`.

**`cmd/vnproxctl/bundlecmd.go`** — the command. **No `--include-keys` and no equivalent**; see
Claim 2.

**`internal/store/backup.go`** — one new primitive, `InspectReadOnly(ctx, path, fn)`: the
generalisation of what `InspectSchemaVersion` already did internally (`query_only(1)`, no
migration). `InspectSchemaVersion` was refactored onto it, so there is one read-only opener rather
than two. This is the primitive that makes "diagnose a failed migration without migrating it"
possible at all.

**Docs** — `docs/deployment.md` gains a "Support bundles (T-1902)" section (what's in it, what
isn't, how to decide before producing one); `docs/security.md` gains a "Support bundles (T-1902)"
threat model and a new threat-model-summary row.

**No new dependency**, Go or npm. **No frontend change** — a bundle is produced when the daemon (and
therefore the UI it serves) may be the broken thing.

### The three collectors that carry the real risk

1. **`configBundleCollector`** — the **sibling** collector T-1901 asked for, not a mode on
   `configCollector`. It renders `vnprox.toml` key by key through `configKeyAllowlist`. A key not on
   the list keeps its *name* (knowing `[oidc]` is configured is diagnostic) and loses its value —
   so `[pve] dev_ticket_password`, a genuine credential the config format permits, is redacted
   whether or not anyone remembers it exists. The walk enumerates the **operator's file**, not
   vnprox's config struct, so a key this build does not recognise still appears (name only) rather
   than being silently dropped.
2. **`hostNetCollector`** — `/etc/network/interfaces` parsed with `internal/host`'s existing AST and
   re-emitted option by option through `ifaceOptionAllowlist`. Emitting that file verbatim would be
   the single most damaging thing this card could do: an operator's interfaces(5) file can carry
   `wireguard-private-key` in the clear.
3. **`changesetsCollector`** — the last N changesets. `changesets.revert_ticket_enc` is **not in the
   SELECT**, so the ciphertext is never read rather than read-and-dropped; ops/plan/apply-log/
   findings go through `redactJSON`.

## 2. Safety analysis — every claim mapped to the test that proves it

### Claim 1 — "A bundle contains no secret class." (AC1)

| Test | What it proves |
|---|---|
| `TestBundle_AC1_ContainsNoSecretClass` | **20 subtests, one per inventory class.** A real bundle is produced from a fully seeded installation and the **decompressed** archive — every entry concatenated, not the `.tar.gz` bytes — is scanned for each class's marker. |
| ” (the **four controls**, asserted before any class) | This is where T-1901's control could not be lifted verbatim, and the difference matters. T-1901's control is an unsealed *store* column that must be findable — but a bundle **does not contain the store**, so that control would fail for a correct implementation and, worse, an equivalent one would be vacuous. So there is one control per collection *path*: a changeset title (the store-derived collectors), an allowlisted interfaces(5) option (the host collector), an allowlisted config value (the config collector), and an ordinary log line (the log collector). Each **must** be found; if any is not, the test `t.Fatalf`s with "so every 'secret not found' assertion below proves nothing". |
| `TestBundle_AC1_PlantingsReachWhatTheBundleReads` | **The guard that makes AC1 mean anything.** Seeding the markers only into the store — which is what T-1901's fixture does, correctly, for a backup — would make all 20 subtests pass trivially, because a bundle never reads the store's sealed columns. So eleven markers are additionally planted **in the inputs a bundle actually reads**: the WireGuard private and preshared keys into `/etc/network/interfaces`, the PVE token / session key / PVE ticket into the daemon log, an OIDC secret into `[pve] dev_ticket_password`, the revert ticket and federation credential into a changeset's `ops_json`, the switch credential into `plan_json`, the kubeconfig into `apply_log_json`, and the webhook secret into a changeset **title**. This test reads each input back and fails if a declared planting is not actually there, and fails outright if fewer than 8 plantings are declared. |
| ” (final assertions) | The manifest is `kind: support-bundle`, `includesKeyMaterial: false`, `secretClasses: []`, and the archive has ≥ 8 entries and non-zero size — so "no secrets found" is not the trivial consequence of an empty archive. |
| `TestBundle_HostNetworkNeverEmitsAWireGuardKey` | Called out on its own so a reviewer can find the most dangerous path: the wg0 stanza **is** collected (asserted as a control — "if it were not, asserting its key is absent says nothing"), its `wireguard-private-key` and `wireguard-preshared-key` options keep their *names* and lose their values, and `address 10.9.0.1/24` **survives** — so the collector is diagnostic rather than empty. |
| `TestBundle_ConfigCollectorIsASiblingNotAMode` | `pve.dev_ticket_password` is listed by name and redacted; `peer.ca_file` survives; and — the control — the **backup's** config entry for the same file *does* contain the credential verbatim, so "the bundle redacted it" is a fact about the bundle rather than about the fixture. It also asserts the two collectors are different Go types. |
| `TestScrub` (11 rows) / `TestRedactJSON` (6 rows) / `TestRedactedOptionValue` (9 rows) | Each row asserts three things, not one: the secret is gone, **the surrounding diagnostic survives**, and `Redacted` appears. The middle assertion is the one that stops "redact everything" from passing. Each row also has its own fixture control (`if !strings.Contains(tc.in, tc.gone) { CONTROL FAILED }`), so a typo in a fixture cannot make "gone" trivially true. |
| `TestScrub_LeavesOrdinaryDiagnosticsAlone` | Seven real log lines — including a 64-char SHA-256 blob hash and `bind: address already in use` — must pass through **byte-identical**. |

**A bug this test found while being written.** `secretTerms` and the keyed-assignment pattern were
two separate lists in the first draft. `TestBundle_AC1_ContainsNoSecretClass/session_key` failed:
`session_key=…` in a log line was not redacted, because only one of the two lists knew the term.
They are now one shared constant, and the comment records why.

### Claim 2 — "A bundle's collectors cannot declare a secret class, structurally." (safety analysis)

The card asks for `Emits()` to be the enforcement point and for the empty set to be *structural*
rather than reviewed. The strongest available form of that in Go is not "every collector returns
nil" — it is **removing the method**:

```go
// bundleCollector has no Emits method. There is consequently no way to write
// a bundle collector that declares it emits a secret class.
type bundleCollector interface {
    Name() string
    Collect(ctx context.Context, st *Staging) error
}

type sealedCollector struct{ bundleCollector }
func (sealedCollector) Emits() []SecretClass { return nil }
```

`sealedCollector` is the only adapter and has no field or option that could change what `Emits()`
returns. So `declaredSecretClasses()` over the bundle's collectors is empty *by type*, and the
manifest's `secretClasses: []` / `includesKeyMaterial: false` follow — they are not a default
anyone could flip.

| Test | What it proves |
|---|---|
| `TestBundleCollectors_CannotDeclareASecretClass` | Every collector in the real list yields an empty `Emits()`, and their union is empty. **With a control**: `declaredSecretClasses` over T-1901's `keyCollector` is *not* empty, so "empty" is a fact about bundle collectors rather than about the function always returning nothing. |
| `TestSupportBundleCommand_HasNoIncludeKeysEquivalent` (CLI) | `support-bundle --include-keys` exits `ExitUsage` — the flag does not exist. **With a control**: `backup` does know the flag, so the refusal is about this command rather than about the parser rejecting everything. |
| `TestBundle_AC1_…`'s manifest assertions | The structural claim is also *honest*: the empty declaration is backed by the byte scan. |

### Claim 3 — "Adding a field to a collected structure without declaring it fails a test." (AC2)

This is the claim that stops redaction rotting, and it is enforced in **two dimensions**, because a
new *file* changes no Go type and a new *field* changes no file list.

**Dimension 1 — fields, by reflection.** `bundleFieldSchema` declares every exported field of every
type reachable from `bundleDocTypes()`, each with a `disposition` (`emit` / `scrub` / `redact-json`
/ `allowlist`) and a **non-empty written reason it is safe to publish**. `checkSchema` walks the
real Go types and reports:

- a field with no declaration → *"field is emitted but not declared … add a fieldDecl saying how it
  is made safe and why"*;
- a declaration with no field → *"the schema has stopped describing the code"*;
- a type reachable but undeclared, an anonymous struct, a duplicate declaration, an unknown
  disposition, an empty reason;
- **and the rule that does the real work**: a field whose type reflection cannot see through
  (`json.RawMessage`, `any`, any map, any `[]byte`) **may not be declared `emit` at all** — it must
  name a redactor. That is the card's "an explicit allowlist or a redactor", made mechanical rather
  than reviewed.

**Dimension 2 — entries, at runtime and in the schema.** `bundleEntrySchema` declares every file a
bundle may contain. `Bundle()` **refuses to write** an archive containing an entry nothing declares
— a hard error, because the card says a collector that cannot describe its output does not ship.

| Test | What it proves |
|---|---|
| `TestBundleSchema_AC2_EveryEmittedFieldIsDeclared` | The real schema is clean, in both directions. Plus non-vacuity floors: ≥ 15 declared types, ≥ 80 declared fields, exactly 9 roots. (The "declared but not reachable" check means a walker that found *nothing* would report every one of the 18 types rather than passing.) |
| `TestBundleSchema_TheEnforcementIsNotVacuous` | **The control, and the reason the test above means anything.** A correct fixture must produce **zero** problems (asserted first — otherwise the rows below could pass because `checkSchema` rejects everything), then **7 rows** each break one rule and require `checkSchema` to name it: an undeclared field, an opaque field declared `emit`, an empty reason, an undeclared nested type, a stale declaration, an orphan declaration, an unknown disposition. |
| `TestBundleSchema_OpaqueClassification` | 13 rows pinning `opaque()`, the single predicate the whole "allowlist or redactor" rule rests on. If it ever returned false for `json.RawMessage`, every AC2 assertion above would still pass while the bundle emitted unredacted JSON. |
| `TestBundleEntrySchema_IsInternallyConsistent` | Every declared entry has a legal archive name, a description (readme.txt is generated from these), a stated redaction, and a role that is `meta` or `config`. **`RoleStore` and `RoleKey` are explicit errors** with the reason spelled out. |
| `TestBundle_AC2_EveryProducedEntryIsDeclared` | A real bundle's entries and `bundleEntrySchema` match **in both directions** — the reverse direction (a declaration with no entry) is one nothing else would notice, and it is what stops readme.txt describing a file that is not there. |
| `TestBundle_AC2_AnUndeclaredEntryIsRefused` | Asserts, with controls in both directions, that `entryDeclFor` distinguishes a declared entry from an undeclared one — the predicate `Bundle()`'s runtime refusal is built on. |
| `TestBundle_ReadmeDescribesThisBundle` | readme.txt is **generated** from the declaration and from what was actually collected, so it cannot describe an absent file or omit a present one. Asserted per entry, plus that it names `store/vnprox.db` as excluded, names `vnproxctl restore`'s refusal, prints the redaction marker, and names sealed and external classes. |

### Claim 4 — "The store is never in a bundle." (safety analysis / card deliverable)

`store/vnprox.db` carries the entire audit trail, every rollback snapshot, and the ciphertext of
every sealed credential. It is the one entry whose presence would defeat the card outright.

| Test | What it proves |
|---|---|
| `TestBundle_NeverCarriesTheStore` | No entry has `RoleStore`, no entry is named `store/vnprox.db` or contains `vnprox.db`, nothing is under `keys/`. **With a control**: a *backup* of the same fixture **does** carry a store entry, so the assertions are about the bundle rather than about the fixture having no store. |
| `TestBundleEntrySchema_IsInternallyConsistent` | The second, independent barrier: even a declared store entry is rejected by the schema check. |
| `TestBundle_IsRefusedByRestore` | A real bundle handed to `Restore` returns `ErrWrongKind` and the target store is byte-identical afterwards. |

### Claim 5 — "A bundle can diagnose a broken install without shell access." (AC3)

Three scenarios, each obeying two rules: **every assertion reads the archive** (never the fixture),
and **every scenario has a healthy control**, because a diagnosis also present in a working install
is not a diagnosis.

| Scenario | Test | What the reader can conclude, and the control |
|---|---|---|
| **Wrong PVE credential** | `TestBundle_AC3_Scenario1_WrongPVECredential/"the credential is rejected"` | The log carries `status=401` and PVE's own reason; the key-file probe says the token file **exists, mode 0600**; the config reports `pve.api_url` and `pve.token_file`. Together those say "rotate the token", not "fix the path". `logs/summary.json`'s `scrubbed` count is non-zero, so redaction demonstrably ran over the same log. **Control:** a healthy install's bundle contains no 401 and reports the same token file present. |
| ” (the other half) | `…/"the credential file is missing"` | The token file is deleted and the probe says so — **computed**, with no log line mentioning it. **Control:** every *other* key file is still reported present, so "missing" is a fact about that file rather than about the probe. |
| **Port conflict** | `TestBundle_AC3_Scenario2_PortConflict` | Entirely computed: the probe binds `[server] listen` itself and reports `in-use` with the bind error, and the daemon probe reports not-reachable. That matters because a crash-looping daemon's journal is mostly noise and a fresh install may have no journal at all. **Two controls:** an unbound address probes `free` **first** (so a probe that always said `in-use` fails before the interesting assertion), and after the conflicting listener is closed the *same address* flips back to `free` — so the verdict tracks reality rather than the config. |
| **Failed migration** | `TestBundle_AC3_Scenario3_FailedMigration` | Both directions, because they need opposite remedies: a store at `latest+5` reports "store is NEWER than this build … will refuse to start"; a store at `latest-3` reports "forward migration pending". Schema and binary versions are both reported. **Control:** a healthy store reports "up to date" at exactly `LatestSchemaVersion()`, with `integrity_check: ok` and ≥ 25 tables — asserted **first**. **And the assertion that matters most:** producing the bundle leaves the store **byte-identical** (SHA-256 of the raw file). A diagnostic tool that migrated the store it was asked to diagnose would have destroyed the evidence. |
| umbrella | `TestBundle_AC3_ReadingABundleNeverNeedsTheHost` | Every document a diagnosis needs decodes from the archive alone; the key-file probe covers exactly `len(SecretClassesBy(StorageKeyFile))` classes; and the archive validates through `Inspect` on its own terms, which is what a reader on a different machine will do to it. |

### Claim 6 — "`--dry-run` matches what a real run collects." (AC4)

The property is **structural, not coincidental**. T-1901's handoff warned against building two code
paths and comparing them, so a dry run performs the *identical* collection into an identical `0700`
staging directory, builds its plan from what `Staging` actually recorded, and then removes the
staging area without writing an archive. The plan cannot disagree with the run because it *is* the
run. (The trade: a dry run does touch a temp directory. It is `0700` and removed, and
`docs/deployment.md` says so.)

| Test | What it proves |
|---|---|
| `TestBundle_AC4_DryRunMatchesARealRun` | The two plans are `reflect.DeepEqual` ignoring only `DryRun` itself; the plan's entry set is exactly the archive's entry set, **checked both ways**; the dry run reports no path and **did not create the output directory**; and the plan is non-trivial (≥ 8 collectors, ≥ 10 omissions, non-empty entries — so comparing them is not comparing two empty lists). |
| `TestBundle_NoStagingResidue` | Staging holds the collected material in the clear while the archive is written. Asserted gone on the success path (no directory, no `.partial` in the output dir) and after a dry run (no `vnprox-collect-*` left in `os.TempDir()`). |
| `TestSupportBundleCommand_DryRunWritesNothing` (CLI) | The flag writes nothing, says "Nothing was written (--dry-run)", **and still describes the contents** — which is the entire point of the flag. |

### Claim 7 — "A bundle cannot be mistaken for a backup, in either direction."

| Test | What it proves |
|---|---|
| `TestBundleName_IsNotABackupName` | A bundle's filename does not match `archiveNamePattern`, so `backup.Prune`'s retention can neither delete a bundle nor keep one instead of a real backup. **With a control**: a real backup name *does* match, so the assertion is about the bundle name rather than about the pattern matching nothing. |

### What is deliberately *not* claimed

Stated in `docs/security.md` rather than left implicit:

1. **A bundle is neither signed nor encrypted.** It is *meant* to be published, so confidentiality
   is not its property — but that also means a bundle you receive is not proof of anything about the
   machine it claims to come from.
2. **A bundle still exposes metadata**: node names, interface names, IP addressing, VLAN ids,
   changeset titles and authors. That is a map of the network and it is the price of being
   diagnosable. The generated readme.txt says so inside the file.
3. **The local `/api/v1/health` read and the peer handshake do not verify TLS.** Neither sends any
   credential — the peer probe closes the connection after the handshake and issues no request at
   all — and both exist to *report* the certificate they were shown. But a machine-in-the-middle on
   the management network could influence the reported health status and certificate metadata.
   `--no-probe` produces a bundle from local files only.
4. **The redactors over-redact by design.** A redacted MTU is an annoyance; a WireGuard key in a
   forum thread is the failure this card exists to prevent.

## 4. Redaction inventory

Every emitted field, by disposition. `bundleFieldSchema` is the machine-readable form; this is the
same data with the reasoning collapsed.

| Document | `emit` (bounded, vnprox-generated) | `scrub` (free-form text → `Scrub`) | `redact-json` (opaque → `redactJSON`) | `allowlist` (key-gated) |
|---|---|---|---|---|
| `environment.json` | tool, version, Go/OS/arch, node, timestamp, TZ + UTC offset, euid, config path, `/etc/pve` present, `[]PathFact` | kernel, OS pretty name | — | — |
| `PathFact` (shared) | path, exists, isDir, **mode**, size, mtime | stat error | — | — |
| `config/vnprox.redacted.json` | path, parsed, key **names**, redacted flag, reason | parse error | — | **every value** (`configKeyAllowlist`) |
| `store/summary.json` | path, exists, sizes, schema versions, migration state, lock held, table names + row counts | integrity_check, error | — | — |
| `changesets/recent.json` | id, status, origin, cluster id, timestamps, revert-ticket **existence + expiry**, op count | title, author | **ops, plan, applyLog, findings** | — |
| `findings/events.json` | limit, total, transition, timestamp | finding id, error | — | — |
| `host/network.json` | path, parsed, option **names**, redacted flag | iface names, auto list, sources, inherits, parse error | — | **every option value** (`ifaceOptionAllowlist`) |
| `peers.json` | port, state, latency, notAfter, probed | node, addr, TLS subject/issuer, errors | — | — |
| `probes.json` | listen address + state, daemon URL/reachable/status, collector names, failure counts, timestamps, key-file class ids + `PathFact` | daemon version, TLS subject/issuer, collector node + **last error**, bind error | — | — |
| `logs/summary.json` | source, collected, line/byte counts, truncated, **scrubbed count** | note | — | — |
| `logs/daemon.log` | — | **every line** | — | — |

**Not present at any disposition:** the store file, any key file's contents, any `*_enc` or `*_hash`
column (`revert_ticket_enc` is not even in the SELECT), `vnprox.toml` verbatim,
`/etc/network/interfaces` verbatim, the peer cluster secret.

**How AC2 enforces it:** the table above is generated by the same declarations `checkSchema` walks.
Adding a field to any of those Go types without adding a `fieldDecl` — with a disposition *and* a
written reason — fails `TestBundleSchema_AC2_EveryEmittedFieldIsDeclared`. Adding a field whose type
reflection cannot see through and declaring it `emit` fails too, by a separate rule. Adding a whole
new file fails `TestBundle_AC2_EveryProducedEntryIsDeclared` and is refused at runtime by `Bundle()`
before the archive is written.

## 7. Deviations from the task card, with reasons

**D1 — The bundle lives in `internal/backup`, not a new package.** The card's author note asks the
executor to say so if the shared abstraction fights them. It did not. Reusing T-1901's `Staging`,
`Write`/`Inspect`, `Kind`, secret inventory **and seeded fixture** from inside the package was
strictly cheaper than exporting internals and duplicating the corpus, which is exactly what the
T-1901 dispatch ruled out for that card. `internal/backup` now means "vnprox's archive family".

**D2 — `--dry-run` runs the collectors and throws the result away, rather than predicting.** The
card says dry-run must "print exactly what would be collected"; T-1901's handoff says not to build
two code paths. Running the real collection and discarding the staging area is the only
implementation where the two *cannot* diverge. The cost is that a dry run creates (and removes) a
`0700` temp directory; documented in `docs/deployment.md`.

**D3 — Live findings and drift are reported only when the daemon is up.** The card lists "recent
findings and drift". Both are computed live by `internal/drift`/`internal/findings` against a
running collector — there is no stored table for either. What *is* stored is `finding_events`, the
transition history, and that is collected offline (`findings/events.json`). The live half comes from
`/api/v1/health` (unauthenticated, so no credential is needed) when the daemon answers. This is the
right trade for a card whose whole point is working when the daemon does not: an offline bundle that
carries finding *history* beats an online-only one that carries the current list.

**D4 — Collector health and poll history come from `/api/v1/health`, not from the store.**
`collect.Collector.Status()` is in-memory; there is no persisted poll history to collect. The health
endpoint's `collectors` array is exactly the shape the card names, and it is the only route vnproxd
serves without authentication — so the bundle needs no token. When the daemon is down,
`probes.json`'s `daemon.reachable: false` plus the log tail is the diagnosis.

**D5 — The daemon's own metrics (T-1903) are not scraped.** T-1903 landed, but `/metrics` is gated
by a scrape token, and reading `[metrics] key_file` to authenticate a scrape would mean this command
opens a key file — which is exactly the property "the bundle never opens a key file" that makes
Claim 1 easy to state and easy to check. The diagnostic content overlaps heavily with what
`store/summary.json` and `probes.json` already report offline. Flagged as a follow-up rather than
built: if it is wanted, it should be an explicit opt-in flag with its own reasoning, not a silent
key read.

**D6 — `internal/api`'s `redactOpSecrets` is not reused for changeset ops.** The card names it as
the rule to follow. It strips one known field (`WgPeerAddParams.PresharedKey`/`…Enc`) from one known
op type, which is right for a `[]change.Op` API response — the ops there are already typed — and
wrong for an archive that must be safe against the op type that lands next phase. The bundle reads
`ops_json` as JSON (it must: it uses a read-only connection and does not decode into `change.Op`)
and walks it by key name, so a sealed field invented later is covered on arrival. `redactOpSecrets`
remains the right tool where it is; this is a strictly wider rule for a strictly more hostile
destination. `TestRedactJSON`'s first row asserts the wg preshared key is stripped in **both** its
forms, so the narrower rule's guarantee is preserved.

**D7 — Bundle entries use `RoleMeta`, not a new `RoleDiagnostic`.** `RoleMeta` is already documented
as "human-readable notes, never restored anywhere", which is exactly right. Adding a role would have
meant touching `manifest.validate` and reasoning about format compatibility for no behavioural gain.

**D8 — No retention (`--keep`) for bundles.** T-1901's `Prune` is for archives a timer produces
repeatedly. A bundle is produced by hand, once, and mailed. `BundleName` deliberately does not match
`archiveNamePattern`, so the two families can share a directory without retention confusing them
(`TestBundleName_IsNotABackupName`).

**D9 — `store.InspectReadOnly` was added to `internal/store`.** Following T-1901's D8: read-only
inspection is a property of the store (its journal mode, its migration scheme), and `query_only(1)`
plus "never call `Open`" is the store's own invariant to keep. It is the generalisation of what
`InspectSchemaVersion` already did privately; that function is now built on it, so there is one
opener rather than two. T-1905 can use it.

**D10 — Peer reachability uses corosync.conf + a bare TLS handshake, not `peer.Client.TrustReport()`.**
T-1901's handoff flagged `TrustReport()` as bundle-ready, and it is — but it requires a live
`peer.Client`, i.e. a running daemon, which is the one thing a support bundle must not require. The
collector reproduces T-1906's `ok`/`unreachable`/`untrusted` trichotomy from a handshake that sends
nothing. When the daemon *is* up, `probes.json`'s health read carries its own view.

**D11 — No new dependency**, Go or npm, and **no frontend change**.

## 8. Needs hardware validation

Four items added to `planning/reports/needs-hardware-validation.md`; none blocks the card. All four
are about what a *real* node's inputs look like, and each is a place where an allowlist could turn
out too narrow (a useless bundle) or too wide (a leak):

1. **A real `/etc/network/interfaces`, especially an SDN/OVS one**, read back out of a bundle to
   check both that you could still draw the network and that nothing credential-shaped survived.
2. **`journalctl -u vnprox` on a real node** — the tail's readability across a Go panic, the
   byte-budget truncation, and whether `logs/summary.json`'s `scrubbed` count is non-zero (a zero on
   a node that talks to PVE would mean the patterns do not match vnproxd's real log format).
3. **Peer reachability against real peer daemons** — all three of T-1906's states actually occurring.
4. **Archive size on a busy node**, recorded in `docs/deployment.md` if it is materially more than a
   few hundred kilobytes.

## 9. For the next agents

### Phase 21 (distribution) — the gate is open, with three things to know

1. **The bundle is the support channel's front door. Point at it from wherever you point users to
   report bugs.** The command to give them is `vnproxctl support-bundle --dry-run` first, then
   `vnproxctl support-bundle`. The `--dry-run` step matters: it is what lets a cautious operator
   decide before producing anything, and telling people to run it first is the difference between
   "attach this" and "attach this, I promise it's fine".
2. **Every bundle carries its own `readme.txt`, generated from the code.** Distribution material
   should not restate what a bundle contains — it will go stale, and the file will not. Link to
   `docs/deployment.md`'s "Support bundles" section for the operator-facing version.
3. **The one thing to say out loud in user-facing docs**: a bundle contains no credential but *does*
   describe the network (node names, addressing, VLAN ids, changeset titles). Every user-facing
   "send us a bundle" prompt should carry that sentence. It is in readme.txt and in
   `docs/deployment.md`; do not drop it on the way to a README.

### T-1904 (`vnproxctl doctor`)

- Your AC3 says `doctor -o json` is "consumed by T-1902's bundle". **The seam is ready and it is one
  file**: add a `doctorCollector` implementing `bundleCollector` (in `internal/backup/bundlecollect.go`),
  a `BundleDoctor` document type in `bundledocs.go`, its `fieldDecl` list in `bundleFieldSchema`, its
  roots entry in `bundleDocTypes()`, and an `entryDecl` in `bundleEntrySchema`. The tests will tell
  you if you miss any of those — that is the whole point of them. Then bump the root count in
  `TestBundleSchema_AC2_EveryEmittedFieldIsDeclared`.
- **Do not duplicate the probes.** `probes.json` already computes: is `[server] listen` bindable, is
  the daemon answering `/api/v1/health` (with collector staleness), and do the declared key files
  exist and with what mode. Your card names port conflicts, key file existence and permissions, and
  PVE reachability among its checks — build `doctor` on the same helpers (`pathFact`,
  `probesCollector`'s methods) or lift them into a shared spot, rather than writing a second
  implementation that can disagree with the first.
- `store.InspectReadOnly` gives you "schema version vs. binary" without migrating anything, which is
  your "schema version vs. binary" check.

### T-1905 (retention)

- `store.InspectReadOnly` is available for any read-only accounting you need.
- `store/summary.json`'s per-table row counts are exactly the shape a `store_near_capacity` finding
  wants to report; consider whether the finding should read the same numbers rather than a second
  query.

### Everyone adding anything to a bundle

- **A new field** on a collected type: add a `fieldDecl` in `bundleFieldSchema` with a disposition
  and a written reason it is safe to attach to a public thread. `TestBundleSchema_AC2_…` will fail
  with that instruction if you don't. If the field's type is a `json.RawMessage`, an `any` or a map,
  you *cannot* declare it `emit` — name a redactor.
- **A new document type**: add it to `bundleFieldSchema`, to `bundleDocTypes()`, and to
  `bundleEntrySchema`, and bump the root count assertion.
- **A new file**: add an `entryDecl`. `Bundle()` refuses to write an undeclared entry at runtime, so
  you will find out immediately.
- **A new secret class** anywhere in vnprox: add it to `internal/backup/secrets.go` (T-1901's
  instruction still stands) and add a marker in `seed_test.go`. If it can plausibly appear in
  something a *bundle* reads — a log line, an interfaces(5) option, a config key, a changeset op —
  also add a row to `bundlePlantings` in `bundlefixture_test.go`, or AC1's assertion for that class
  will be true but vacuous.
- **Never** add `--include-keys` or anything like it to `support-bundle`. The absence is the feature,
  and `TestSupportBundleCommand_HasNoIncludeKeysEquivalent` says so.
