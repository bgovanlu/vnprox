## What was built

### 1. Log format grounding (a deviation flagged up front)

Before writing the parser I checked pve-firewall's actual upstream source (`proxmox/pve-firewall`, `src/pvefw-logger.c` and `src/PVE/Firewall.pm`) rather than guessing the format. Two things worth flagging:

- The real line format is `<VMID> <LOGLEVEL> <CHAIN> <TIME> <TIMEZONE> <MSG>` (pvefw-logger.c's own documented example: `117 6 tap117i0-IN 14/Mar/2014:12:47:07 +0100 policy REJECT: IN=vmbr1 ...`), where the message is either `"policy $policy: "` (a default-policy fallthrough) or `"$action: "` (a specific rule match) followed by standard netfilter `KEY=VALUE` fields.
- **Real pve-firewall log lines do not embed a rule position or index at all** — `get_log_rule_base()` builds the NFLOG prefix as `:$vmid:$loglevel:$chain: $msg`, nothing more. This contradicts docs/features/firewall.md §4's premise ("PVE logs include rule references in most drop/reject cases"). I did not change the spec unilaterally; instead `internal/fwlog`'s rule correlator is an honest best-effort heuristic (direction+action match against the guest's resolved evaluation order, narrowed by protocol/port when available) that never claims a correlation it can't support — ambiguous/unmatched cases are reported as such, not guessed. See `internal/fwlog/doc.go` for the full writeup and citations. **Flagging this for hardware validation** and for whoever revisits this feature: if a future PVE version's log format changes to include rule positions, `Correlate` should be updated to use them directly.
- Node/cluster-scope (host chain) log correlation is explicitly out of scope this task: I could not confidently ground the real host-chain naming convention (no live cluster to check against), so non-guest chains are labeled `unknown_chain` honestly rather than guessed. Guest chains (`tap<vmid>i<nic>-IN`/`-OUT`, `veth...` for containers) are the one convention pvefw-logger.c's own example confirms, so that's what's implemented.

### 2. Backend (`internal/fwlog`, new package)

- **Parser** (`parse.go`): `ParseLine`/`ParseAll` — lenient, never-crashing line parsing per the format above, plus a documented second timestamp variant (a single RFC3339 token, in case of journald-forwarded lines). Garbage detection is narrow and explicit: fewer than 3 fields, a non-integer/negative VMID, or a log level outside pve-firewall's documented 0–7 range. Anything else (bad timestamp, unrecognized chain, message with no action word) still yields a best-effort `Entry` rather than being discarded — "never crash, never silently drop recoverable data."
- **Correlator** (`correlate.go`): `Correlate(entry, resolvedView)` against `internal/fw.ResolvedView` (T-501's resolver, reused directly, not duplicated). Six honest outcomes: `rule` (a single unambiguous match — deep-link target), `default_policy`, `ambiguous` (with candidate positions, never guessed), `unmatched`, `unknown_chain`, `no_guest_data`.
- **Bounded buffer** (`buffer.go`): `RingBuffer` — fixed-capacity, oldest-evicted, sequence-numbered.
- **Source seam** (`source.go`): `Source` interface (`Tail(ctx, node, cursor, maxLines) (lines, nextCursor, reset, err)`), with `FileSource` (real `/var/log/pve-firewall.log`, byte-offset cursor) and `MemorySource` (in-memory, used for both the dev fixture corpus and every test, including the storm test's synthetic line injection). Deliberately **not** added to `host.Reader`/`peer.HostReader` — those exist for interfaces/netlink/LLDP/stats, and folding a sixth capability in would ripple into every implementer (`host.Real`, `FixtureReader`, `pvemock.FixtureHostReader`, `peer.HostReader`) for one new, unrelated capability. Instead it's its own small interface, mirroring the `AuditReader`/`SnapshotReader` precedent T-303 already established for the same reason.
- **Service** (`service.go`): the orchestrator — `Tick` (fetch new lines from local + every peer, parse, correlate, rate-cap, push, broadcast) is factored out of `Run`'s ticker loop specifically so tests (including the storm test) can call it directly, back-to-back, with no real wall-clock wait. `TailPage` serves REST reads directly from the same buffer `Tick` fills — one merged history, not two independently-fetched views that could disagree.
- **Rate cap / drop indicator (AC3):** `MaxBroadcastPerTick` (default 200) bounds how many newly-parsed entries one tick pushes/broadcasts; excess is dropped-and-counted (`droppedTotal`), never silently discarded from the count. This is deliberately distinct from `RingBuffer`'s own eviction (ordinary history rotation at `BufferCapacity`, default 5000) — the drop indicator only reflects genuine storm-induced rate-limiting, not normal buffer aging.
- **Wire DTOs** (`view.go`): `EntryView`/`CorrelationView` shared verbatim by both the REST response and the `firewall.log.batch` WS event, so the two never drift apart.

### 3. Peer transport (`internal/peer`)

Added `GET /api/peer/firewall/log?node=&cursor=&maxLines=` (new `FirewallLogReader` interface, `ServerOptions.FirewallLog`, `Client.FirewallLog`) — the peer-server-side seam a remote node's own `fwlog.Service.Tick` calls, mirroring the existing `HostReader`/`AuditReader` transport pattern exactly. A dedicated, higher line-count ceiling (`maxPeerLogLines` = 5000, vs. the audit/snapshot routes' 200) was added since a single peer fetch needs to be able to catch up on a real storm burst, not trickle in.

### 4. API + WS (`internal/api/fwlog.go`, `internal/api/router.go`)

- `GET /firewall/log?node=&vmid=&direction=&action=&limit=` — netRead-gated, served from `fwlog.Service.TailPage`. Filters mirror `GET /audit`'s "every param optional, ANDed" convention.
- The `firewall.log.batch` WS event is pushed directly by `fwlog.Service` over the shared hub (the same `Broadcaster` seam `internal/metrics.Sampler`/`internal/drift.Service` already use) — no separate WS mounting needed; `docs/api.md`'s WS section and events table are updated, including the new `firewall.log` subscribe topic.
- `docs/api.md` was updated in this same change (definition-of-done #4): the `GET /firewall/log` response shape, `FwLogEntry`/`Correlation`/`RuleRef` shapes, the WS event, and the new peer route are all documented, including an explicit note that log-format-embedded rule references don't actually exist in real pve-firewall (see §1 above).

### 5. cmd/vnproxd wiring

- `setupFwlog` (`cmd/vnproxd/fwlog.go`) builds the `Service`: a real `FileSource` in production, or — when `[firewalllog] dev_fixture_dir` is set (dev-only, mirrors `dev_interfaces_dir`'s precedent) — a `MemorySource` seeded from `testdata/firewall-logs/*.log`. The same local `Source` backs both this daemon's own polling and what it serves to peers (`fwLogPeerReaderAdapter`), so there's one reader of "this node's own log," not two.
- `fwlogSvc.Run` is registered in the daemon's run group unconditionally once initialized (same treatment `driftSvc.RunLoop` gets) — it's always on, not gated behind a WS subscriber.
- `internal/config` gained a `[firewalllog]` section (`path`, `dev_fixture_dir`) with a `DefaultFirewallLogPath` constant pinned equal to `fwlog.DefaultLogPath` by a cross-package test (mirrors `DefaultProtectedPath`'s existing precedent).
- A nil `*fwlog.Service` (the dev-fixture-load-failure path) is explicitly guarded before being handed to `api.Options.FwLog` — assigning a nil concrete pointer directly to an interface field would produce a non-nil interface wrapping nil (the classic Go footgun this codebase's own docs call out elsewhere), so it goes through an explicit `if svc != nil` first, same as the existing `peerAudit`/`peerSnapshots` pattern.

### 6. Fixture corpus (`testdata/firewall-logs/pve1.log`, `pve2.log`)

Hand-written to exercise: normal guest ACCEPT/DROP/REJECT lines with full netfilter KV fields, a default-policy fallthrough line, a container (`veth`) chain, an RFC3339 timestamp-variant line, a non-guest (`PVEFW-HOST-IN`) line, a message with no action word, and six distinct garbage-line shapes (blank lines, JSON noise, prose, a bare number, a negative VMID, an out-of-range log level). Used by both the Go parser tests and the dev-mode `MemorySource` seed.

### 7. Frontend (`web/src/fwlog/`, `web/src/api/fwlog.ts`, `web/src/api/types.ts` additions)

- `reducer.ts` — the pure state machine: a bounded client-side buffer (`CLIENT_BUFFER_CAP` = 1000, independent of the server's own buffer), pause/resume (pauses *freeze the view*, not the capture — incoming batches are buffered into `pending` and flushed on resume, also bounded), filter composition (`matchesFilter`/`selectVisibleEntries`), and both drop counters (client eviction + mirrored server `droppedTotal`).
- `deeplink.ts` — `ruleDeepLinkPath(rule)`: builds `/firewall?scope=guest&ref=...&pos=...&origin=...` by stable identity (guest ref + resolved-order position + origin), not DOM position or route state — **deliberately not wired into `web/src/firewall/`'s pages**, since T-502 is concurrently restructuring that directory in another worktree. The firewall pages don't currently read these query params (T-501's `FirewallPage.tsx` manages scope/selection as local state), so the link today navigates to the Firewall page but doesn't yet auto-select/highlight the rule — **flagging this as follow-up work** for whoever next touches `FirewallPage.tsx`: read `scope`/`ref`/`pos`/`origin`/`group` from the URL and focus the matching row. The contract is documented in `docs/api.md` and `deeplink.ts` so that wiring is a small, well-specified addition, not a redesign.
- `FwLogViewer.tsx` — filter bar, pause/resume/clear controls, the drop indicator, a render cap (`RENDER_CAP` = 300, independent of the buffer cap) so the DOM never mounts more rows than that regardless of how much history is buffered, and per-line correlation badges (a clickable "view rule" link only for `status: "rule"`).
- Wired into `web/src/pages/ToolsPage.tsx` as a new section (same placement convention as T-306's `MacFdbBrowser`) rather than into the Firewall page, per the orchestrator's brief (avoids touching files T-502 is concurrently editing).

## Deviations from the task card (with reasons)

1. **Rule correlation is a heuristic, not a literal "parse the embedded rule reference"** — because real pve-firewall logs don't contain one (see §1 above). This is the most important deviation and is documented in three places (`internal/fwlog/doc.go`, `docs/api.md`, this report) so it isn't missed. AC2 ("correlated lines deep-link to the right rule; uncorrelatable lines labeled as such") is still met: the fixture corpus and tests are constructed so unambiguous cases correlate correctly and ambiguous/unmatched/unknown cases are labeled honestly, never guessed.
2. **Node/cluster-scope log lines are not correlated to rules** — flagged as "needs hardware validation" (no live cluster to confirm the real host-chain naming convention against). They still appear in the stream, labeled `unknown_chain`.
3. **The rule-editor deep-link doesn't yet auto-focus the target rule** — `web/src/firewall/`'s pages don't read URL query params today, and T-502 is concurrently restructuring that directory in a separate worktree. The link is built by stable identity (ref/pos/origin) specifically so a follow-up wiring task in that page is additive, not a rework of this task's output.
4. **`internal/fwlog.Source` is its own interface, not an addition to `host.Reader`/`peer.HostReader`** — avoids rippling a firewall-log-specific capability into every existing Reader implementer; mirrors the `AuditReader`/`SnapshotReader` precedent T-303 already set for the identical reason.
5. **No new third-party dependency** — everything uses the stdlib plus already-approved deps (chi, nhooyr websocket via the existing hub, TanStack Query, react-router).
