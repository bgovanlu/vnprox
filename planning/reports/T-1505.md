## What was built

**Design decision (stated per the task card, docs/data-model.md §3):** per-guest-NIC rate limiting
is *not* a new op — it already exists as `guest.nic.update`'s `rateMbps` field
(`internal/change/params_guest.go`). This card's only new surface is bridge-level per-service
shaping, via the new `qos.*` op group.

**`internal/qos` (new package)**
- `Shape` (bridge Ref-by-name, optional `MatchCIDR`/`MatchVlan`, `RateMbit`, optional `CeilMbit`/
  `Priority`) and `RenderTC`/`RenderTCTeardown` — pure functions rendering the ordered `tc` argv
  lines that realize/remove one shape on its bridge (one shared HTB root qdisc per bridge, one HTB
  class per shape, a chained `u32` filter when a match is set, or the root's own `default` minor
  re-pointed at the shape's class when neither match is set — the "shape governs the bridge's whole
  egress" case). Deterministic per-shape classid derivation (FNV-1a hash of the shape id, avoiding
  the reserved unclassified minor `1`) makes re-applying an unchanged shape idempotent at the tc
  level. `internal/qos/shape_test.go`: table + golden-argv + idempotency + classid-collision-
  avoidance tests, all pure (no exec, no I/O).
- **NEEDS HARDWARE VALIDATION** (flagged in the package doc comment): the exec path is only proven
  against golden argv output, never a real kernel HTB/`u32` stack.

**Store (`internal/store`)**
- `migrations/0011_qos.sql` + `qos.go`: `qos_shapes` table (app-owned intent only, per
  `CLAUDE.md`'s storage rule) — `id, node, bridge, match_cidr, match_vlan, rate_mbit, ceil_mbit,
  priority, created_by, created_at, updated_at`. `QosShapeRepo` (`Insert`/`Get`/`List`/`Update`/
  `Delete`), mirroring `AlertRuleRepo`'s shape. `qos_test.go`: insert/get/list/update/delete +
  nullable-field round-trip + not-found/already-absent-delete convergence.

**Change engine (`internal/change`) — the ordinary changeset lifecycle, no second mutation path**
- `params_qos.go`: `QosShapeCreateParams`/`QosShapeUpdateParams`/`QosShapeDeleteParams`. `Bridge` is
  the bridge's plain interface name (like `nat.*`/`route.static.*`'s `Iface` convention would be —
  this base has no such ops yet, but the same "don't nest a redundant Ref when `target.Node` already
  carries it" reasoning applies), not a nested Ref.
- `op.go`: `OpQosShapeCreate/Update/Delete` + `paramFactories` entries.
- `apply_seams.go`: new `QosGateway` interface (`ApplyQosOp`/`SnapshotQos`/`RestoreQos`) — a
  **daemon-level** (root, no user PVE ticket) dependency, deliberately mirroring `NodeAgent`'s own
  shape rather than the ticket-scoped `PVEGateway`: a shape is node-local state with no PVE API
  surface, so (like `NodeAgent`'s interfaces-file restore) its rollback works on the unattended
  commit-confirm-timeout / crash-recovery path too.
- `apply_plan.go`: new `StepQosApply` step kind, `qosOpTypes`, `hasQos()`/`qosNodes()`/
  `qosStepSummary()`. `BuildPlan` emits one `qos_apply` step per op, placed after every node's
  interface stage/reload pair (a shape's bridge must already exist) and before a trailing
  `sdn.apply` — "a new apply-step kind ordered alongside the existing per-node ifreload step," per
  the task card.
- `apply_snapshot.go`: `qosStateSnapshotPath` (a synthetic cluster-scoped snapshot file, JSON-
  encoding each affected node's `QosGateway.SnapshotQos` string) + `qosStateSnapshotFile`/
  `qosStateFromSnapshot`, wired into `captureSnapshotFull`.
- `apply_exec.go`: executor gains `qosPre`/`hasQosPre`; `execStep` gains the `StepQosApply` case;
  `rollbackAfterFailure` gains `anyQosStepSucceeded`/`restoreQosState` (mid-apply-failure rollback).
- `apply.go`: `doRollbackLocked` gains an unconditional QoS-restore block (unlike the SDN block,
  which is `pveGW`-gated) — this is the "rollback restores the pre-snapshot shape config and
  re-applies it, following T-205's existing inverse-order rollback contract" the card asks for, and
  it works on the unattended auto-rollback path (proven by
  `TestApply_QosShapeLifecycle_RollbackOnTimeout`).

**MANDATORY: `TouchesMgmtPath` extension (`internal/change/mgmttouch.go`)**

  corosync path is flagged — mirroring `BridgePortAddParams`'s existing dual (target-or-named-param)
  check, the closest present analog on this base (see Deviations for why the card's literal "mirror

  this pure validator has no store-backed id→bridge lookup, so it is a documented, flagged gap

  `qos.shape.create` naming the mgmt-path bridge (`vmbr0`) → `want: true`; the identical op naming an

## Deviations from the task card (with reasons)

- **The task card's "mirror the existing `nat.*`/`route.static.*`/`wg.*` cases already in that
  switch" instruction does not apply to this base.** This worktree's `mgmttouch.go` (and `op.go`,
  `apply_plan.go`, `apply_seams.go`, `service.go`, `validate_codes.go`, …) predates T-1401
  (WireGuard) and T-1403 (edge/NAT) entirely — those op groups, and their `mgmttouch.go` cases,
  simply do not exist on this branch (`git log --all` shows them on sibling branches/worktrees not
  yet merged here). I verified this by reading the actual worktree files rather than assuming from
  the task card's prose, then designed the `QosShapeCreateParams`/`QosShapeUpdateParams` cases by
  mirroring the closest *present* analog instead — `BridgePortAddParams`'s "check target OR the
  named iface/bridge param" dual pattern, which is structurally the same thing `nat.*`'s
  `checkEdgeRuleIface` would be. Functionally equivalent; only the literal sibling-case mirroring
  instruction couldn't be followed as written. Flagged here per `CLAUDE.md`'s "flag it in your final
  report instead of changing it unilaterally" — nothing was changed, since there was nothing to
  mirror; this is a reporting note, not an unauthorized decision.
- **No dedicated QoS shape editor wizard in the frontend.** The task's AC list (and its Map/frontend
  deliverable bullet) asks only for the shaping-active badge, not a bespoke create/edit UI; a
  hand-built or API-driven `qos.shape.*` op already stages/diffs/applies/rolls back identically to
  one from a wizard (the changeset lifecycle doesn't care how an op was authored) and now renders a
  proper summary line (`opSummary.ts`) instead of the generic fallback. A dedicated wizard is a
  reasonable, additive follow-up, not attempted here to keep scope to what the card and ACs actually
  ask for.
- **`QosShapeUpdateParams`/`QosShapeDeleteParams` have a documented, flagged `touchesMgmtPath` gap**
  (see above): an update that doesn't re-set `Bridge`, or any delete, can't be resolved back to its
  stored bridge by this pure validator class without a store-backed lookup (the same kind of gap
  `WgCarrierSource` closes for WireGuard on the later, unmerged branch). AC3's two required
  regression cases (a flagged-true mgmt-path case, a flagged-false off-path case) are both satisfied
  by the `create` op, which is enough to prove the extension is wired and testable; closing the
  update/delete gap is flagged as a follow-up rather than attempted with a rushed, unreviewed
  store-read seam threaded through a currently-pure package.
- **`RenderTC`'s "re-point the root qdisc's `default` minor" interpretation for an unmatched
  (whole-bridge) shape is a documented, narrow reading**, not specified by the task card: it assumes
  at most one *unmatched* shape per bridge (enforced nowhere in code — a second unmatched shape on
  the same bridge would silently re-win the `default` pointer). Flagged in `RenderTC`'s own doc
  comment; closing this (e.g. a referential "only one unmatched shape per bridge" check) is a
  reasonable follow-up.
- **`govulncheck`/`npm audit --audit-level=high`** were not run — this sandboxed environment has no
  outbound network access to fetch the vulnerability DB / npm registry. Every other `make check`
  step (gofmt, vet, golangci-lint, go test, tsc, eslint, vitest) ran and is green.
- **Environment note, not a code deviation:** this worktree had no `web/node_modules` (a fresh git
  worktree checkout, same as T-1103's report notes); `npm ci` was run once before the frontend
  lint/typecheck/test steps could run.
