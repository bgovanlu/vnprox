# T-203 · Safety interlocks & protected interfaces — completion report

## What was built

### `internal/host` — corosync.conf reader (new)

- **`corosync.go`**: `ParseCorosyncConf([]byte) (*CorosyncConfig, error)` — a
  deliberately narrow, tolerant parser of corosync.conf's brace-delimited
  `block { key: value }` syntax, extracting only `nodelist { node { name,
  nodeid, ring*_addr } }` stanzas (every other section — totem, quorum,
  logging — and every other key is silently skipped, so an unrelated
  corosync feature this package doesn't understand never breaks
  safety-interlock detection). `ReadCorosyncConf(path string)` reads
  `DefaultCorosyncConfPath` (`/etc/pve/corosync.conf`) by default; a missing
  file wraps the underlying `os.PathError` (checkable via
  `errors.Is(err, os.ErrNotExist)`) so callers can distinguish "not
  clustered yet" from a real read failure. `CorosyncNode.RingAddrs` holds
  every configured ring (ring0_addr primary, ring1_addr+ redundant).
  Unlike every other `internal/host` reader, this one takes no node
  parameter and needs no per-node routing: `/etc/pve` is pmxcfs, the
  cluster's distributed filesystem, so corosync.conf is byte-identical on
  every node's local disk.

### `internal/change` — protected-interface set + safety-interlock validator (new)

- **`protected.go`**: `ProtectedConfig` (protected.json's on-disk shape:
  `{nodes: {<node>: [<ref>...]}, version, updatedAt, updatedBy}`) and
  `ProtectedSet` (`map[string][]inventory.Ref]`, the resolved shape the
  validator consumes). `LoadProtectedConfig`/`SaveProtectedConfig` do
  atomic-write (temp file + rename) file I/O against
  `DefaultProtectedPath` (`/etc/pve/vnprox/protected.json` — also under
  pmxcfs, so the onboarding-confirmed set is inherently cluster-wide the
  moment it's saved). `DetectProtected(snap, corosyncConfig)` computes the
  onboarding-suggestion set: for each node, every bridge/VLAN-sub-interface
  (the only inventory kinds with a declared `Addresses` field) whose
  address matches that node's management IP (`inventory.Node.IP`) or one of
  its corosync ring addresses.
- **`validate_safety.go`**: `safetyValidate(ops, snap, SafetyOptions)` —
  validator class 3 (docs/features/change-management.md §2 / docs/security.md
  "Safety interlocks"). Two checks:
  - **Protected-interface connectivity + bridge-path**: for every protected
    ref, folds all ops into `validate_projection.go`'s `projection` (reused
    as T-202's report suggested) and checks whether the exact host IP the
    ref carried in the base snapshot is still assigned to *any* interface
    on that node afterward (mask-insensitive — a mask change alone isn't a
    connectivity loss). Separately, if the protected ref is a bridge that
    still exists and still carries the address but has had every port
    removed, that's flagged too (docs/security.md's "...or deletes/detaches
    its bridge path" clause — a bridge can keep its configured IP while
    losing all physical connectivity).
  - **Guest-bearing bridge deletion**: a `bridge.delete` op targeting a
    bridge with running guests still attached (via `GuestNic.BridgeOrVnet`
    + `Guest.Status == "running"`) errors, listing every attached guest by
    name/VMID/NIC key, unless the same changeset also reattaches all of
    them (any `guest.nic.update` touching that NIC's `BridgeOrVnet`
    counts — partial reattachment leaves the error naming only the
    still-attached guests).
  - `SafetyOptions.AllowDangerousOps` downgrades every finding this class
    produces from `SeverityError` to `SeverityWarning` (code unchanged) —
    docs/security.md: "override only via config flag allow_dangerous_ops".
- **`validate_codes.go`**: added `safety.protected_interface` and
  `safety.guest_bearing_bridge` (dotted `<class>.<check>` convention,
  matching every other code in this file).
- **`validate.go`**: `Validate(ops, snap)` is now a thin wrapper around the
  new `ValidateWithSafety(ops, snap, SafetyOptions)`, which slots the safety
  class in at T-202's marked insertion point (between referential and
  advisory), short-circuiting on an error-severity safety finding exactly
  like every other class — but a downgraded warning does **not**
  short-circuit, so advisory still runs (verified by a dedicated test).
  Every existing call site/test using the old `Validate` signature is
  unaffected.
- **`validate_projection.go`**: extended `addrEntry` with a `hostIP net.IP`
  field (alongside the existing `ipnet *net.IPNet`, which only preserves
  the *masked network* address — insufficient for "is this exact IP still
  present" identity checks) and three new projection methods: `hasHostIP`,
  `hasHostIPOnRef`, `portCount`. No existing behavior changed; this is a
  pure addition T-202's own report anticipated ("it already tracks
  addresses per-op in order").
- **`errors.go`**: added `ErrInvalidProtectedRef` (mirrors `OpDecodeError`'s
  treatment of a malformed op target, for a malformed ref string in a
  `SetProtected` call).
- **`service.go`**: `Config` gained `ProtectedPath` (defaults to
  `DefaultProtectedPath`) and `AllowDangerousOps` (captured once at
  construction from `config.Config.Safety.AllowDangerousOps` — there is no
  daemon config hot-reload, matching every other `Config` field's
  static-at-startup convention). `Create`/`UpdateDraft`/`Validate` now call
  `ValidateWithSafety` with a `SafetyOptions` built fresh on **every**
  call via `safetyOptions()` — protected.json is read from disk each time,
  not cached, so an onboarding correction saved via `SetProtected` takes
  effect on the very next validation without a daemon restart (verified by
  `TestService_SafetyOptions_ReadsFreshEachValidation`). New methods:
  `GetProtected`/`SetProtected` (the onboarding read/update flow, audited as
  `protected.update`); `auditSafetyOverride` appends a
  `changeset.safety_override` audit entry whenever `AllowDangerousOps` is
  true **and** a safety-class finding is actually present (i.e. the
  override materially mattered), listing the affected refs.

### `internal/api` — minimal protected-interfaces API (new)

- **`protected.go`**: `ProtectedService` seam (`GetProtected`/`SetProtected`,
  satisfied directly by `*change.Service`). `GET /api/v1/protected-interfaces`
  (netRead) / `PUT /api/v1/protected-interfaces` (netWrite + CSRF, same
  gating pattern as `mountChangesetsRoutes`). A malformed ref in the PUT
  body maps to `400 validation_failed` with the offending refs in
  `details.refs`.
- **`router.go`**: added `Options.Protected` and wired
  `mountProtectedRoutes`.
- **`cmd/vnproxd/server.go`**: wires `change.Config.ProtectedPath =
  change.DefaultProtectedPath`, `AllowDangerousOps = cfg.Safety.AllowDangerousOps`,
  and `api.Options.Protected = changeSvc`.

## Deviations from the task card (flagged, not silent)

- **`docs/api.md` has no documented route for this.** The card asks for "a
  minimal API to read/update it" but the frozen API contract doc doesn't
  list a protected-interfaces route the way changesets/layouts are listed.
  I added `GET/PUT /api/v1/protected-interfaces` following this codebase's
  existing conventions exactly (Ref-string encoding, netRead/netWrite
  gating, CSRF on the write, the same error envelope) rather than inventing
  something inconsistent, but **`docs/api.md` itself was not touched**
  (out of scope per CLAUDE.md: "follow docs/api.md exactly" implies I
  shouldn't unilaterally edit the frozen contract other tasks depend on).
  The orchestrator should get this route added to docs/api.md's "Blueprints"
  or a new "Onboarding" section before T-207 (which will need to call it
  from the onboarding UI) starts.
- **Finding code spelling.** The card's prose says error `protected_interface`;
  I emitted `safety.protected_interface` (and `safety.guest_bearing_bridge`)
  to match `validate_codes.go`'s own documented convention ("every code is a
  stable, dotted identifier `<class>.<check>`"), consistent with every other
  class in this pipeline. Flagging in case a consumer expects the bare
  string.
- **PhysNic/Bond addresses are not modeled.** `inventory.PhysNic` and
  `inventory.Bond` have no `Addresses` field at all (only `Bridge` and
  `VlanIface` do — see `entity.go`); a protected.json entry naming a raw
  physnic/bond therefore contributes no connectivity check today (it would
  still be tracked for existence, but there's no address for it to lose).
  This matches real-world PVE practice closely (management IPs are almost
  always on a bridge, since PVE requires one for guest attachment) but is a
  genuine, not-invented, data-model gap. I did not add the fields myself —
  doing so would touch a shared entity type many other tasks/tests depend
  on with no test coverage demonstrating the need; flagging for whoever
  owns `internal/inventory` next.
- **Bridge-path-detachment check is bridge-only.** Docs/security.md's
  "deletes/detaches its bridge path" clause is checked for Linux/OVS
  bridges (port-count-drops-to-zero-while-address-unchanged). Bonds don't
  carry addresses in this model (see above), so there's no analogous "bond
  loses all its slaves while still carrying the mgmt IP" case to check —
  it's structurally the same gap, not a separate oversight.
- **`ProtectedConfig.Version`/onboarding-detection API endpoint not built.**
  `DetectProtected` (the onboarding "suggest" computation) and
  `ProtectedSet.ToConfig` exist and are tested, but there's no
  `GET /protected-interfaces/suggest`-shaped route exposing them — the
  card's deliverable list only asked for "read/update" of the *confirmed*
  set, not the detection endpoint itself, which reads more like T-207/the
  onboarding wizard's job (it needs the live snapshot + corosync config
  wired together with whatever UI flow presents the confirm/correct step).
  Flagging so whichever task builds onboarding knows `change.DetectProtected`
  already exists and just needs a thin handler.
- **No new third-party dependencies.** Everything here is standard library
  (`encoding/json`, `os`, `bufio`, `net`) plus this repo's own packages.

## What was tested and how

All new logic is covered by table-driven Go tests, no PVE/network access
needed:

- **`internal/host/corosync_test.go`**: `ParseCorosyncConf` against a
  representative multi-node corosync.conf fixture (two rings on one node,
  one on the other) plus a case proving an unrelated section's same-named
  key (`totem`'s own `ring0_addr`) is never captured; nil-config
  `NodeByName` safety; `ReadCorosyncConf` round-trip and its
  `errors.Is(err, os.ErrNotExist)` contract on a missing file.
- **`internal/change/protected_test.go`**: `LoadProtectedConfig` on a
  missing file; `SaveProtectedConfig`/`LoadProtectedConfig` round-trip
  including a nested-directory creation and "no leftover temp file"
  assertion; `Resolve`'s bad-ref reporting; `DetectProtected` against a
  snapshot with a management-IP bridge, a corosync-ring-only VLAN
  sub-interface, and an unrelated bridge (asserting exactly the first two
  are detected); the nil-corosync-config fallback path.
- **`internal/change/validate_safety_test.go`** (the acceptance-criteria
  suite):
  - **Criterion 1** (`TestSafetyValidate_ProtectedInterface`): deleting
    vmbr0 (carries mgmt IP) errors; re-addressing it to a different IP
    errors; re-addressing to the same IP with a different mask does
    *not* error (mask-insensitive identity); deleting an unrelated bridge
    has no interlock finding.
  - **Bridge-path clause** (`TestSafetyValidate_BridgePathDetachment`):
    removing every port from a two-port protected bridge (address
    untouched) errors; removing only one of two leaves connectivity
    intact.
  - **Criterion 2** (`TestSafetyValidate_ChainAnalysis`): creating a new
    bridge with the mgmt IP *and* deleting the old one in the same
    changeset validates clean.
  - **Criterion 3** (`TestSafetyValidate_GuestBearingBridgeDeletion`):
    deleting a bridge with two running guests + one stopped guest attached
    errors listing exactly the two running ones; reattaching both clears
    the error entirely; reattaching only one leaves the error naming only
    the other.
  - **Criterion 4** (`TestSafetyValidate_AllowDangerousOps_Downgrades`,
    `TestValidateWithSafety_WarningDoesNotShortCircuitAdvisory`):
    `AllowDangerousOps=true` downgrades the protected-interface finding to
    `SeverityWarning` (code unchanged); the downgraded warning does not
    short-circuit the advisory class (a single-slave-bond advisory warning
    in the same changeset still appears).
- **`internal/change/service_protected_test.go`** (Service-level, real
  SQLite-backed audit repo): a protected-interface error blocks
  `Validate` from promoting `draft -> validated`; with
  `AllowDangerousOps=true` the same case is a warning, promotes fine, *and*
  writes a `changeset.safety_override` audit entry (username +

- **`internal/api/protected_test.go`**: route-not-mounted without a

## Anything T-205 (apply engine) must know

1. **`change.ValidateWithSafety` is the pipeline's real entry point now**;
   `change.Validate` still exists and behaves exactly as before (zero-value
   `SafetyOptions`) for any caller that doesn't need protected-interface
   checks. `Service.Create`/`UpdateDraft`/`Validate` all now call
   `ValidateWithSafety` with `safetyOptions()` — T-205's apply path should
   do the same (revalidate immediately before apply, per
   docs/features/change-management.md §2: "Runs on every draft change and
   again immediately before apply") rather than calling the bare
   `Validate`, or a changeset with `allow_dangerous_ops`-downgraded warnings
   would silently lose that context.
2. **`Service.protectedPath`/`allowDangerousOps` and `safetyOptions()` are
   unexported** — if T-205's apply engine lives in a different file within
   `internal/change` (likely, per the task list — `internal/change/apply.go`
   or similar), it can call `s.safetyOptions()` directly since it's the
   same package and the same `*Service` receiver. If T-205 needs this from
   a *different* package instead, that method will need exporting — flag it
   rather than reimplementing the protected.json-loading logic separately.
3. **`SafetyOptions.AllowDangerousOps` downgrades to warning, it never
   suppresses the finding.** T-205's apply path must still treat a
   `SeverityWarning`-with-safety-code changeset as "has warnings the user
   must have acknowledged" (docs/features/change-management.md §2:
   "Warnings require an explicit 'apply with warnings' checkbox") — this
   task does not implement any apply-time gating itself, only the
   validation-time severity and the audit trail.
4. **Guest reattachment ops must be in the *same* changeset** as the
   `bridge.delete` for the interlock to clear — T-205's planner should be
   aware the safety class only looks at `ops` passed to `Validate`, not any
   notion of "this is a multi-step wizard flow"; if the UI ever splits
   guest-reattach into a separate changeset applied first, the bridge
   deletion changeset would still show the guest-bearing-bridge error
   (correctly, per current semantics) until PVE state actually reflects the
   reattachment.
5. **No apply/confirm/rollback code was touched** — `internal/change/ifaces`
   (T-204) and the 501-stub apply/confirm/rollback routes are exactly as
   T-204 left them.
