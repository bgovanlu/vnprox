# T-909 — Responsive triage layout

## What I built

A narrow-viewport ("phone/small-tablet") triage mode, gated below a JS-detected
768px breakpoint (`web/src/lib/useNarrowViewport.ts`, mirroring `useReducedMotion.ts`'s
`matchMedia` pattern — deliberately JS, not just a Tailwind `md:` variant, since
route-level decisions are about *which component tree renders*, not just how an
already-rendered one is styled).

### Reachable surface at narrow width
- **Dashboard** (`/`) — already responsive (Tailwind `grid-cols-1` base), untouched.
- **Findings** (`/tools`) — `ToolsPage.tsx` now renders a restricted view at narrow
  width: only the findings stream (read-only — see below), with the simulator, raw
  interfaces editor, MAC/FDB browser, firewall log viewer, and doc export replaced
  by one explicit `EmptyState` naming what's hidden and why.
- **Changeset confirm/rollback/apply-an-existing-draft ceremony** — the globally
  mounted `ChangesetDrawer`/`ReviewApplyScreen`/`CountdownBanner` (not a route, so
  no gate needed) stays fully usable: the typed management-path acknowledgement
  block, Apply, Confirm, and Roll back all work at phone width.
- **Every other route** (`/topology`, `/management`, `/guests`, `/sdn`, `/firewall`,
  `/ipam`, `/ports`, `/blueprints`, `/history`, `/audit`, `/settings`) is wrapped in
  a new `DesktopOnlyRoute` guard (`web/src/routes/DesktopOnlyRoute.tsx` +
  `DesktopOnlyNotice.tsx`): at narrow width it renders an explicit "needs a larger
  screen" panel with actionable copy (links back to Dashboard/Findings, a note that
  confirm/rollback still works) instead of the real page — including on a direct
  link, since the guard runs at the route element, not just via nav-click gating.
- `NavRail.tsx` filters its item list to the reachable set (Home, Tools) at narrow
  width, so the nav itself doesn't dangle a link into a page that just bounces to
  the notice.

### An interpretive decision I made (flagging per CLAUDE.md)
The card's "confirm/rollback actions only" framing, read literally, would exclude
Apply (`POST .../apply`) from the narrow-reachable surface. But the deliverables
section explicitly lists "the typed-acknowledgement block ... Apply ... confirm/
rollback buttons" together as the one ceremony that must work at narrow width, and
AC2 requires the ack block itself to be exercised at phone width — which only
renders pre-apply. I resolved this as: **applying an already-fully-formed existing
draft** (whether staged via a desktop wizard/editor, or an API-seeded draft) stays
reachable at narrow width, since it's not "staging new ops" or "editing entities"
— but reordering/removing ops, discarding a draft, creating a new draft (raw
editor, wizards, entity editors, "Create fixing changeset" from a finding) all stay
desktop-only. This is implemented in `ChangesetDrawer.tsx` (`editUiEnabled = editable
&& !narrow` gates reorder/remove/discard/fix-in-drawer) and `FindingsStreamPanel.tsx`
(fix button disabled with a tooltip reason at narrow; the wizard-launch/simulator
deep-link actions redirect to an explanatory toast instead of navigating).

### Two real bugs found and fixed along the way
1. **`ChangesetDrawer`'s floating panel overflowed off-screen at phone width.**
   `fixed bottom-4 right-4 w-full max-w-sm` — with `left` auto and `width` resolving
   to the viewport width, the browser solves `left` to a negative value (right
   offset + width > viewport width below ~400px), clipping content. Fixed with
   `inset-x-4` at narrow, restoring the original `right-4 max-w-sm` anchoring via
   `sm:` — a real, pre-existing bug, not narrow-viewport-restriction-specific.
2. **`CountdownBanner` (`fixed inset-x-0 top-0 z-40`) painted over `NavRail`**
   (`position: static`, no z-index) wherever they overlapped — found via this task's
   own e2e run: clicking "Tools" while a countdown banner was showing timed out
   because the banner intercepted the click. Pre-existing at *any* viewport (nothing
   in the existing suite combined "banner showing" + "click a nav link"), but only
   surfaced now because narrow width's 2-item nav clusters right under the banner's
   height where the old 13-item desktop list mostly didn't reach. Fixed with
   `relative z-50` on `NavRail`'s `<nav>` (matches the app's dialog/drawer z-tier;
   portaled modals render after NavRail in the DOM so they still paint on top).
3. Also found, **not fixed** (out of scope — flagging per CLAUDE.md rather than
   re-litigating or silently patching an unrelated pre-existing bug in a
   zero-backend-changes card): the guided management-redundancy wizard's Flow C
   ("move management to a dedicated VLAN interface") never enables "Create draft".
   `internal/inventory/entity.go`'s `Bridge` struct has no `json` tags, so
   `GET /inventory/{ref}`'s reflection-based `Fields` map keys are capitalized
   (`Addresses`, `Gateway`), but `MgmtRedundancyWizard.tsx`'s Flow C reads
   `fieldStr(carrierDetail?.fields, "addresses")`/`"gateway"` (lowercase) — always
   empty, so `configValid` never becomes true. This blocked my first attempt at a
   second wizard-driven narrow-viewport mgmt test (both tests in
   `mgmt-redundancy.spec.ts` share one webServer/interfaces sandbox not reset
   between them, and Flow A — the only other viable flow, since the single-node
   fixture has just 2 NICs, already consumed by the file's first test — would
   conflict). I worked around it by seeding the second test's draft via a direct
   `bridge.update` API call (a comments-only change, never touching `Ports`) rather
   than through the wizard, which sidesteps the bug and the sandbox-state
   collision. **Needs its own fix** (a T-703-era bug, not T-909's to touch).

## Hard invariant: no new write capability at narrow width

Grepped every new/narrow-aware file for mutating call sites:
- `useNarrowViewport.ts`, `DesktopOnlyNotice.tsx`, `DesktopOnlyRoute.tsx`,
  `NavRail.tsx`, `AppShell.tsx`, `ToolsPage.tsx`'s narrow branch — **zero**
  `Mutation`/`apiFetch`/`mutateAsync` call sites.
- `FindingsStreamPanel.tsx`: `useFixFindingMutation` (`POST /findings/{id}/fix`) is
  only invoked from a `Button` whose `disabled` prop is `fixDisabledReason !==
  undefined` — set at narrow, so the click never fires. The mgmt-wizard-launch and
  "View in simulator" actions have their `onClick` swapped to a toast at narrow —
  never call `openMgmtWizard`/`navigate`.
- `ChangesetDrawer.tsx`: `useDiscardChangesetMutation` only fires from the Discard
  button, `disabled={!editable || narrow}`. Move-up/move-down/remove buttons and
  the in-drawer `FixButton` (each backed by `PUT /changesets/{id}` via
  `useDrawerActions`) are gated behind `editUiEnabled = editable && !narrow` and
  don't render in the DOM at all when narrow.
- The remaining reachable mutations — `useApplyChangesetMutation` (apply),
  `useConfirmChangesetMutation`, `useRollbackChangesetMutation` (in
  `ReviewApplyScreen.tsx`/`CountdownBanner.tsx`, unmodified by this task) — are the
  explicitly sanctioned "review/apply-an-existing-draft/confirm/rollback" ceremony,
  not new: they were reachable at every viewport before this task (no gating
  existed at all), so nothing new is exposed by going narrow — if anything the net
  write surface at narrow width is now strictly *smaller* than before this task
  (draft editing/discarding is newly gated off).
