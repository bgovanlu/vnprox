# T-1407 · Tunnel-aware federation transport

## Summary

Implemented the deferred T-1407 card: an optional `clusters.wg_tunnel_id` linkage
(migration `0032_cluster_wg_tunnel.sql`, schema version 31 → 32) marks an attached
federation cluster as reachable only via a specific T-1401-managed WireGuard tunnel.
`internal/federation.Aggregator` gained a `TunnelHealth` seam (`WithTunnelHealth`
option); when a linked tunnel's live handshake state has gone stale, the Aggregator
excludes that cluster from `ClusterNodesAll`, `Audit`, and `IPAMSubnets` — the three
surfaces the card's Objective names (topology/audit/IPAM-conflict reads) — **without**
adding it to those calls' `partial`/`failedClusters` envelope. In its place,
`internal/findings` gained one new producer (`health_federation_tunnel.go`,
`source: "federation"`, check `tunnel_down_peer_unreachable`) that fires the single
named finding a human actually sees, hysteresis-debounced identically to
`wg_handshake_stale` (2-cycle rise/fall). Both consumers key off the same exported
`findings.WgTunnelHasFreshHandshake` staleness definition, so they can never disagree
about which tunnels are down.

`cmd/vnproxd/federationtunnel.go`'s `federationTunnelAdapter` is the composition-root
bridge: it resolves `clusters.wg_tunnel_id` → `wireguard_tunnels` row (node, ifName) via
the existing WireGuard store repo, and answers both `internal/federation.TunnelHealth`
and `internal/findings.FederationProvider` from the identical live WireGuard state
`wg_handshake_stale` already reads (`wgReadSvc`). It's wired in with the same
lazily-set-after-construction pattern `fwAnalyticsAdapter`/`baselineSvcVal` already use
in this codebase, since `federation.NewService`/`NewAggregator` are built after the
findings engine in `server.go`.

`PUT /federation/clusters/{id}` accepts an optional `wgTunnelId` field to set/clear the
linkage, following the exact "absent leaves unchanged, explicit value replaces"
convention `credential` already uses.

## Why this card was picked up now

An unrelated docs/plans-vs-implementation audit found T-1407 was the one phase-14 card
with no report and no code — every one of its six siblings shipped (folded into the
`v2.0.0` tag, per that tag's own timing — see `CHANGELOG.md`), but T-1407 itself was
never executed. `planning/tasks/phase-14.md`'s card header, `docs/roadmap-universal.md`,
and the CHANGELOG have all been updated to reflect that this is now implemented,
post-v3.0.2, not part of the original v2.0.0/v3.0.0 cuts.

## Deviation from the card: no new API routes, `clusters` gained the field via `PUT`

The card's deliverables didn't specify how an operator sets the linkage; I extended the
existing `PUT /federation/clusters/{id}` (additive optional field) rather than adding a
dedicated route, since it's the same class of edit `credential` already is and needs no
new capability gate.

## Deviation considered and rejected: reusing `wireguard_peers.cluster_id` instead

`docs/data-model.md`'s pre-T-1407 text on `wireguard_peers.cluster_id` describes it as
"links a federation-managed internal peer (the T-1201 seam ... until federation lands)" —
i.e. a *tunnel → cluster* linkage already exists in the schema, the mirror image of what
this card asks for (*cluster → tunnel*, on `clusters.wg_tunnel_id`). I confirmed
`wireguard_peers.cluster_id` is fully plumbed through the store and the `wg.peer.add`
changeset op (`internal/change/params_wg.go`'s `WgPeerAddParams.ClusterID`) but is
**never actually set** by any UI flow — the "connect two clusters" wizard (T-1402) never
populates it (`grep -rn "clusterId" web/src` under any wireguard/tunnel file: zero hits).

I implemented the card as written (`clusters.wg_tunnel_id`) rather than wiring up the
dormant `wireguard_peers.cluster_id` field instead, for three reasons: (1) it's the
literal, unambiguous spec — the card's AC5 explicitly names `clusters` gaining
`wgTunnelId`; (2) populating `wireguard_peers.cluster_id` would mean also fixing the
frontend wizard to set it, which is scope well beyond this card and touches working,
released UI code; (3) a `clusters`-side flag is a clean 1:1 "the tunnel to use for this
cluster" declaration an operator sets once, versus inferring it from possibly-multiple
peer rows. **Flagging for a future task:** `wireguard_peers.cluster_id` remains dormant
and unset by any code path — worth either wiring it up (T-1402's wizard should set it
when pairing two federated clusters) or removing the now-redundant field/comment if
`clusters.wg_tunnel_id` is judged sufficient going forward.

## Acceptance criteria

1. **A federated cluster linked to a healthy WireGuard tunnel aggregates normally — no
   synthetic finding, ordinary behavior.** Pass.
   `TestAggregator_TunnelHealthy_AggregatesNormally` (`internal/federation/tunnel_test.go`),
   `TestFederationTunnelFindings_HealthyNoFinding` (`internal/findings/health_federation_tunnel_test.go`).
2. **The linked tunnel's fixture-driven handshake goes stale past threshold → the
   aggregator reports the cluster unreachable via exactly one
   `tunnel_down_peer_unreachable` finding, and the per-surface `partial`/`failedClusters`
   noise across topology/audit/IPAM-conflict reads is collapsed into that one finding.**
   Pass. `TestAggregator_TunnelDown_ClusterNodesAll` and
   `TestAggregator_TunnelDown_IPAMAndAudit` prove all three surfaces (`ClusterNodesAll`,
   `Audit`, `IPAMSubnets`) exclude the tunnel-down cluster with `partial: false`,
   `failedClusters` empty; `TestFederationTunnelFindings_StaleRaisesAndClears` proves the
   one finding fires with 2-cycle hysteresis and clears when healthy again.
3. **A federation peer not linked to a vnprox-managed tunnel gets T-1201's ordinary
   unreachable-peer handling unchanged — regression test.** Pass.
   `TestAggregator_NotTunnelLinked_OrdinaryHandlingUnchanged` — an unlinked cluster killed
   mid-aggregation still produces the ordinary `partial: true`/`failedClusters` signal,
   even with a `TunnelHealth` wired in. All pre-existing `TestAggregator_*` tests
   (`ClusterNodesAll`, `FailureIsolation`, `Audit`, `IPAMSubnets`, etc.) still pass
   unmodified, proving no regression for the `nil`-`TunnelHealth` default case either.
4. **No auto-remediation exists: the finding carries no fix and no code path re-applies
   or restarts the tunnel automatically.** Pass by construction —
   `federationTunnelFindings` never sets `Finding.Fixable` (stays the zero value `false`)
   and no `FixOps`-style method exists on `FederationProvider`;
   `TestFederationTunnelFindings_StaleRaisesAndClears` asserts `Fixable == false`
   explicitly. `federationTunnelAdapter`/`internal/federation.Aggregator` only ever
   *read* WireGuard/cluster state — grep-verifiable: neither file imports
   `internal/change` or calls anything WireGuard-apply-shaped.
5. **`docs/data-model.md`'s `clusters` table entry gains the `wgTunnelId` field;
   `docs/api.md` updated for the new finding code; `make check` green.** Pass. Both docs
   updated (see below); `make check` green (see above).

## Notes for the next agent

- **`wireguard_peers.cluster_id` is still dormant** — see the rejected-deviation section
  above. If a future task wires up the "connect two clusters" wizard to actually set it,
  reconcile it with `clusters.wg_tunnel_id` rather than letting the two drift (either
  make one derive from the other, or clearly document why both need to exist
  independently).
- **Schema is now version 32.** `CHANGELOG.md`'s `[3.0.2]` entry's "schema stays 31" claim
  is historically correct (it described that release, not this change) and was not
  edited. This change has not been cut into a release/tag — that's a separate action the
  orchestrator should take deliberately (a new patch/minor version, updated `CHANGELOG.md`
  entry, tag + release + deploy), not assumed as part of this report.
- **No frontend surface exists for setting `wgTunnelId` yet.** An operator can set it via
  `PUT /federation/clusters/{id}` today, but there's no UI control for it — a natural
  follow-up alongside the `wireguard_peers.cluster_id` wiring noted above, both living in
  the T-1402 "connect two clusters" wizard's territory.
