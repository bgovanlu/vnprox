# T-1402 · WireGuard map edges & "connect two clusters" wizard

## What was built

This card's shipped surface from T-1401 (`wg.*` op group, `GET /wireguard/tunnels`,
`wg_handshake_stale`/`wg_endpoint_drift` findings) needed no backend changes — everything below is
frontend, built on that already-merged surface.

**Live map layer — WireGuard tunnel edges** (the "Frontend: a new edge kind (`wg-tunnel`)"
deliverable):
- `web/src/api/wireguard.ts` + new types in `web/src/api/types.ts` (`WireGuardTunnel`,
  `WireGuardPeer`, `WireGuardTunnelStatus`): the `GET /wireguard/tunnels` client.
- `web/src/wireguard/wgEdgeStatus.ts`: a pure function (`wgPeerEdgePaint`) resolving one peer's live
  fields to the map's paint — `status: "ok"|"degraded"` for healthy/stale-handshake (mirrors
  `internal/findings/health_wireguard.go`'s `WgHandshakeStaleThreshold` = 5m and its "never
  handshaked ⇒ not stale" rule exactly), plus the existing `"drift"` badge (already wired to dashed
  rendering in `EntityEdge.tsx`/`canvasDraw.ts`/`EntityNode.tsx` for every other drift finding) for
  `wg_endpoint_drift`. Status and the drift badge are independent axes, not exclusive states.
- `web/src/wireguard/wgTunnelEdges.ts`: `computeWgTunnelOverlay` turns `WireGuardTunnel[]` into
  synthetic `{nodes, edges}` — one `wg-tunnel` edge per (tunnel, peer), anchored on the real
  `node:<name>:<name>` map entity (the same anchor the Latency/MTU overlays already use) and a
  synthetic `wg-external-endpoint` node per peer (WireGuard tunnels are app-owned intent, not part
  of the PVE-inventory-derived `internal/topology.Project`, so the far side has no existing map
  entity to anchor to — this mirrors how the mgmt-path badge overlay is "a second, independent
  decoration," docs/features/topology.md §3).
- `web/src/wireguard/wgTunnelsQuery.ts`: 30s poll, only while the new "WireGuard" layer toggle is on
  (mirrors `mtuProbeQueries.ts`'s exact pattern).
- Wired into `web/src/topology/store.ts` (`wgLayerActive`/`toggleWGLayer`),
  `web/src/topology/LayerToggleBar.tsx` (8th toggle chip), and `web/src/topology/TopologyPage.tsx`
  (merges the overlay into the existing `extraNodes`/`extraEdges` seam T-1003's expanded guest-group
  pills already use — moved earlier in the component to avoid a circular dependency on
  `canvasNodeIds`, which is itself derived from `elements`).

**Pre-existing bug found and fixed: the node-to-node overlay anchor was structurally broken.**
While wiring the WG overlay's "from" endpoint (a tunnel's owning cluster node), I copied
`TopologyPage.tsx`'s existing `nodeIdForName` helper (already used by the Latency/T-1303 and MTU/
T-1306 overlay layers), which resolves a PVE node name to `"node:<name>:<name>"` and looks it up in
the rendered canvas node set. `internal/topology/project.go`'s `layerOf` function, however,
**deliberately never renders a `KindNode` entity** ("Kinds with no entry (KindNode, KindFwRuleset)
are never rendered directly as topology nodes ... cluster membership ... surfaced by other routes
... not the topology map") — confirmed independently by `internal/inventory/ingest.go`'s literal
`Ref{Kind: KindNode, Node: e.Name, ID: e.Name}` construction (so the id shape is right, it's just
never a *rendered* entity). That means `"node:<name>:<name>"` **never appears in a real `GET
/topology` response**, so `nodeIdForName` always returned `undefined`, and
`computeLatencyOverlayEdges`/`computeMTUOverlayEdges` always produced **zero edges** against any real
backend — silently, because neither overlay has ever had a component/e2e test exercising it against
real (or even fixture-shaped) topology data; their existing unit tests inject their own
`nodeIdForName` stub directly, which never exposed the mismatch. Fixed with a new shared resolver,
`web/src/wireguard/../topology/nodeAnchor.ts`'s `buildNodeAnchorResolver`: it anchors to the first
*actually-rendered* entity in that node's own band (`TopologyNode.nodeGroup`) instead, which always
resolves for any node with at least one physical/L2 entity (every real cluster node).
`TopologyPage.tsx` now computes this **once**, early (from `topology.nodes` directly, before
`extraNodes`/`extraEdges`/`elements` exist — avoiding the circular dependency `canvasNodeIds` would
otherwise create), and all three overlays (Latency, MTU, WireGuard) consume the same fixed resolver.
New unit tests: `web/src/topology/nodeAnchor.test.ts`.

**This fix was verified live, end to end, against the real stack** — not just at the unit level.
Since applying a `wg.tunnel.create` op isn't possible on this host (see the Playwright section
below), I seeded a tunnel+peer directly into a fresh dev SQLite store via `internal/store`'s own
`WireGuardRepo.InsertTunnel`/`AddPeer` (the exact same repo methods the real apply path uses — this
only bypasses the exec-dependent keygen/`wg-quick` step, not any read/render logic), started
`vnproxd`+`pvemock` for real, logged in as `root` in a real headless Chromium session, switched to
the v2 canvas renderer, clicked the new "WireGuard" layer toggle, and confirmed via the map's
accessibility bridge (`TopologyA11yLayer.tsx`, `data-entity-id`/`aria-label` proxies — the same
descriptors the canvas itself draws from) that exactly one `wg-endpoint:...` node rendered, with
`aria-label: "wg-external-endpoint 203.0.113.10:51820, status ok, badges: wg, external"` — the
correct healthy (no drift, `ok` status) rendering for a peer with no live handshake data, exactly as
`wgEdgeStatus.ts` and T-1401's own findings semantics predict. This one-off manual verification (not
committed as an automated spec — see "Notes for the next agent" below for why) is the strongest
evidence in this report that the live map layer genuinely works against the real backend, not merely
against injected test fixtures.

**"Connect two clusters" wizard** (`web/src/wireguard/ConnectClustersWizard.tsx`, launched from the
topology page's "New ▾" menu → per-node submenu):
- Built on the exact same infrastructure every SDN zone wizard uses: `WizardShell` +
  `WizardPreviewPane` (`web/src/sdn/wizards/`) for the step engine/live preview, and
  `useDrawerActions().addOps` for the single `POST`/`PUT /changesets` mutation path every wizard in
  this codebase shares.
- `web/src/wireguard/wizardOps.ts` (`buildConnectClustersOps`) stages exactly `wg.tunnel.create` +
  `wg.peer.add` (this node's side) + `fw.rule.create` (opening the tunnel's UDP listen port,
  appended after the target ruleset's current rules) — three existing op types, one changeset, in
  that order.
- `web/src/wireguard/previewGraph.ts` (`buildConnectClustersPreview`) builds the live preview graph.
  Both functions take the exact same `(params, tunnelId)` pair — `tunnelId` is generated once
  (`crypto.randomUUID()`) in the wizard component's state and threaded unchanged into both, which is
  the entire mechanism behind AC2 ("no drift between preview and submitted ops"): they cannot
  disagree because they're pure functions of the same inputs.
- `web/src/wireguard/wgWizardStore.ts` + `ConnectClustersWizardHost.tsx`: the same
  one-shared-instance-mounted-in-`AppShell` pattern `mgmt/MgmtWizardHost.tsx` established for T-703's
  wizard.
- `web/src/wireguard/strings.ts`: wizard copy, including the federation-seam explanation shown
  in-wizard on the "Other side" step (see below).

**Regression fix found and repaired along the way**: `web/src/changesets/planPreview.ts` (the
client-side Plan-tab preview) and `web/src/changesets/opSummary.ts` (the drawer/Summary-tab op
labels) had never been updated for T-1401's `wg.*` op family — before this fix, staging a `wg.*` op
would have shown the user a **false** "Not yet executable by the apply engine: wg.tunnel.create ...
Applying a changeset containing these ops will be refused" warning, even though
`internal/change/apply_plan.go`'s `BuildPlan` has executed `wg.*` as `StepWgApply` since T-1401
shipped. Fixed both files to classify `wg.*` correctly (mirroring `BuildPlan`'s exact step
kind/ordering: after per-node stage/reload, before firewall/`sdn.apply`) and added
human-readable summaries matching `apply_plan.go`'s `wgStepSummary` wording. This is the same class
of bug `planPreview.test.ts` already had a named regression test for (SDN-write ops, T-402) — this
task adds the equivalent for WireGuard.

## Federation seam (for T-1201/T-1202/T-1407)

The card's original brief (written before this repo's dependency graph was pinned down) assumed
T-1202's cluster-capsule primitive and a "pick a target cluster" step. Per this task's dispatch
instructions, T-1201 (federation core) and T-1202 (global topology) are **not implemented in this
repo**, and the wizard is built accordingly — not blocked on them, and not faked:

- **Both "standalone endpoint" and "this cluster's own nodes" collapse to the same mechanism.**
  T-1401's key-custody design generates a tunnel's keypair *on the owning node, at apply time*
  (`internal/change/params_wg.go`'s own doc comment) — never at stage time. That means a
  same-changeset op can never reference a not-yet-applied peer's future public key, for *any* peer,
  whether it's a genuinely external WireGuard install or another node in this very cluster. There is
  no op-output-binding mechanism in the change engine to make this otherwise. So the wizard has
  exactly one buildable shape: this node's own tunnel + an externally-modeled peer
  (`wg.peer.add {external: true}`) whose public key the operator already has and pastes in — whether
  that key came from a truly external system, or from another vnprox node/cluster's own
  `GET /wireguard/tunnels/{id}/pubkey`, copied manually. The in-wizard copy on the "Other side" step
  says this explicitly.
- **When T-1201 lands**: a "pick a target cluster" step (using T-1202's capsule picker) is the
  natural extension — it would auto-fill the peer public key/endpoint fields this wizard already has
  by querying the target cluster's `GET /wireguard/tunnels/{id}/pubkey` via the federation
  aggregator, instead of requiring manual paste. No structural change to `wizardOps.ts`'s op-building
  needed.
- **When T-1407 lands** (tunnel-aware federation transport): automatic key exchange between two
  vnprox-managed clusters removes the manual-paste step entirely; the wizard's three-op shape (tunnel
  + peer + firewall, one changeset) stays the contract T-1407 builds on.
- Cluster wg routing itself (a `wg.*` op targeting a non-local node) is rejected by
  `hostWGGateway.ensureLocal` — an existing T-1401 single-node-scope limitation, unrelated to
  federation, documented in T-1401's own report as a flagged follow-up.

    intended production behavior *is* correctly implemented either way: a freshly-applied tunnel's
    peer has never handshaked, and `wgEdgeStatus.ts` (mirroring T-1401's own `checkWgHandshakeStale`

    `wg-quick`, the AC's "renders healthy on the next poll" outcome should hold by construction; this

## Deviations from the task card (with reasons)

1. **No backend changes.** The card's deliverables list was frontend-only; T-1401 already shipped
   every backend surface needed (`wg.*` ops, `GET /wireguard/tunnels`, the two findings). Confirmed
   by reading `internal/change/apply_plan.go`'s `wgOpTypes`/`BuildPlan` before starting.
2. **"Two attached mock clusters" (AC1/AC3's literal wording) → one cluster + a modeled external
   endpoint.** Federation isn't in this repo; adapted per this task's explicit dispatch instructions
   and documented extensively (see "Federation seam" above and inline doc comments in `wizardOps.ts`,
   `ConnectClustersWizard.tsx`, and `docs/features/topology.md` §7).
3. **AC3's apply-and-see-healthy leg not exercised via the *wizard's own apply path*** — environment
   gap (missing `wg-quick`), not a wiring defect; see the Playwright section above for the full
   reasoning. The "renders healthy" *rendering* half of this is, however, independently proven true
   by the live manual verification described above (a real tunnel, read via the real backend, renders
   correctly on the real map) — the only unverified piece is `wg-quick`'s own exec success, identical
   in kind to T-1401's own already-flagged gap.
4. **Fixed two pre-existing bugs outside this card's file list**, both necessary for this feature to
   actually work/not mislead the user, both scoped narrowly and fully covered by new tests:
   - `planPreview.ts`/`opSummary.ts` didn't know about `wg.*`, so the wizard's own Review screen would
     have shown a false "not yet executable" warning for its own ops.
   - `TopologyPage.tsx`'s `nodeIdForName` (shared by Latency/MTU/WireGuard overlays) resolved against
     an id `internal/topology.Project` never emits — silently zero-rendering all three overlay layers
     against any real backend. See "What was built" above for the full diagnosis and fix
     (`nodeAnchor.ts`).

## Notes for the next agent

- `docs/features/topology.md` §7 is the canonical doc for this task's rendering contract and wizard
  shape — read it before touching WireGuard map rendering or the wizard again.
- The WireGuard map layer is v2-canvas-renderer-only, same scope cut as Flows/Latency/MTU (T-1003/
  T-1303/T-1306) — not a new constraint, an existing one this task follows.
- **The Latency (T-1303) and MTU (T-1306) overlay layers were silently non-functional against a real
  backend until this task's `nodeAnchor.ts` fix** (see "What was built" above) — worth a follow-up
  regression check on those two tasks' own original acceptance criteria if anyone revisits them, since
  their shipped Vitest coverage never caught it (pure-function tests with an injected resolver, no
  component/e2e test against real topology shape). Both now share the fixed resolver with WireGuard,
  so no further action is needed unless a *fourth* overlay repeats the same mistake — if so, reuse
  `nodeAnchor.ts`'s `buildNodeAnchorResolver`, don't reinvent the `"node:<name>:<name>"` lookup.
- `wgTunnelEdges.ts`'s doc comment names the exact seam T-1407/cluster-wg-routing would need to
  close to ever correlate two separate tunnels (one per node) into a single node-to-node edge instead
  of two standalone-endpoint edges — today `GET /wireguard/tunnels` has no peer fan-out
  (T-1401's own documented single-node scope), so this repo cannot do that correlation yet regardless
  of the frontend.
- **No committed automated test seeds a WireGuard tunnel for live map-rendering e2e coverage**, even
  though this report's manual verification proves the rendering pipeline works: T-1401 never added a
  dev/CI seeding mechanism for `wireguard_tunnels` (unlike every PVE-config feature, which seeds via
  `internal/pvemock` fixture YAML — WireGuard tunnels are app-owned SQLite data, a fundamentally
  different seeding problem). A future task wanting permanent e2e coverage of the live WG map layer
  needs either (a) a dev-only seed/bootstrap step for `wireguard_tunnels`/`wireguard_peers`, or (b) a
  host with real `wg-quick` + kernel WireGuard support so the wizard's own apply path can populate it
  for real. Once either exists, `wireguard-wizard.spec.ts` is already positioned to extend with the
  apply → confirm → "edge renders healthy" assertions AC3 originally asked for.
