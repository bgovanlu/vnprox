# T-202 · Validation framework + schema/referential validators — completion report

## What was built

### `internal/change` — the layered validator pipeline (new files)

- **`validate.go`** — `Validate(ops []Op, snap inventory.Snapshot) []Finding`, the pure
  entry point (no store/service dependency, directly table-testable). Runs validator
  classes in `docs/features/change-management.md` §2's documented order —
  **schema → referential → [safety, T-203's slot] → [cross-node, unassigned] → advisory**
  — short-circuiting immediately after any class that produces an error-severity
  finding (generalizes the card's "short-circuit on schema errors" to every class
  boundary: referential/safety checks over a schema-broken op, or advisory checks
  over a referentially-broken graph, would be operating on nonsense). `hasError`,
  `errorf`/`warnf` are the small shared helpers every class file uses.
- **`validate_schema.go`** — class 1: per-op types/ranges/enums/syntax, independent
  of the snapshot. Covers every one of the 39 documented op types: MTU 576–9216,
  VID/VLAN-tag 1–4094, bond mode/LACP-rate/xmit-hash-policy enums, CIDR/IP/MAC
  syntax (`net.ParseCIDR`/`ParseIP`/`ParseMAC`), fw direction/action/policy/log
  enums, required-field checks, duplicate-slave/duplicate-port detection within a
  single op's list, and DHCP-range (`start-end`) syntax.
- **`validate_projection.go`** — the "as of this point in the ops list" view every
  referential check runs against: an inventory.Snapshot folded forward through
  every earlier op in the same changeset (in order). Tracks the flat per-node
  iface namespace (physnic/bond/bridge/vlan share one namespace, matching
  interfaces(5)), current enslavement ownership, VLAN sub-interface (parent, vid)
  pairs, declared addresses per node (for overlap), and cluster-scoped SDN
  zone/vnet/subnet name indexes. `fold(op)` applies one op's effect after its
  checks run, *unconditionally* (even if the op itself had an error) — see the
  "design notes" section below for why.
- **`validate_referential.go`** — class 2: existence, duplicate enslavement, name
  collisions, VID overlap, address overlap — evaluated against the projection
  above, so `bond.create bond0` followed by `bridge.port.add ... bond0` in one
  changeset validates clean, while the reverse order correctly errors (acceptance
  criterion 2, covered by `TestValidate_IntraChangesetOrdering`).
- **`validate_advisory.go`** — class 5 (spec item 5): 802.3ad bonds without
  `xmitHashPolicy=layer3+4`, bridges without a description, single-slave bonds.
  For `*.update` ops, the existing entity's snapshot state is merged with the op's
  partial override before evaluating, so e.g. a `bond.update` that only touches
  `xmitHashPolicy` still correctly reads the bond's already-declared `mode`.
- **`validate_fix.go`** — machine-applicable `fix` patches: MTU clamp (every op
  with an MTU field), VID/tag clamp (`vlan.create`, `sdn.vnet.create/update`), and
  bridge-VLAN-trunk-range clamp (`bridge.create/update`'s `Vids`). Every fix is a
  one-op patch sharing the offending op's exact `Type`/`Target`.
- **`validate_codes.go`** — the stable `Finding.Code` string constants the golden
  suite and (eventually) the frontend key off.

### Wiring

- **`service.go`**: added `InventorySource` (satisfied by `*inventory.Graph` via its
  existing `Snapshot()` method) and `Config.Inventory` (optional; nil falls back to
  an empty graph snapshot, so T-201's existing tests that never set it keep
  working unchanged). `Create`/`UpdateDraft` now compute `Findings` immediately
  against the current snapshot on every mutation (docs/features/change-management.md
  §2: "runs on every draft change") — but, importantly, **neither auto-promotes
  Status**: they always leave a draft at `StatusDraft` regardless of what the
  findings say. The new exported `Validate` method is the only thing that moves
  `StatusDraft → StatusValidated` (when clean) or `StatusValidated → StatusDraft`
  (when a re-check now finds an error, e.g. the snapshot moved) — it's audited
  (`changeset.validate`, result `clean`/`errors`) and broadcasts `changeset.status`
  only on an actual transition, mirroring `UpdateDraft`'s existing behavior.
- **`internal/api/changesets.go`**: `ChangesetService` gained `Validate`;
  `POST /changesets/{id}/validate` is wired to a real handler
  (`handleValidateChangeset`) instead of the 501 stub. `diff`/`apply`/`confirm`/
  `rollback` are untouched (still 501, still T-205's).
- **`cmd/vnproxd/server.go`**: passes the daemon's live `*inventory.Graph` as
  `change.Config.Inventory` so validation runs against real collected state, not
  an empty snapshot, in production.

## Design notes / things T-203 needs to know

- **Class ordering and insertion points are explicit in `validate.go`**: there are
  two clearly-commented gaps in the class sequence — one between referential and
  advisory for T-203's safety-interlock class, one after it for an (unassigned)
  cross-node class. T-203 adds its class function call at the first marked spot;
  no restructuring of the pipeline, the projection, or the short-circuit logic is
  needed. T-203's class should follow the same shape as `referentialValidate`/
  `advisoryValidate`: `func safetyValidate(ops []Op, snap inventory.Snapshot) []Finding`,
  and if it needs the "what does this changeset's ops-so-far state look like"
  view (likely, for "does this chain of ops still leave the mgmt IP reachable"),
  it can reuse `validate_projection.go`'s `projection` type directly (it's already
  exported-within-package and walks ops in the same order).
- **`fold()` applies every op's effect even when that op itself errored.** E.g. if
  `bond.create bond0` already-exists-errors, `bond0` is still marked as existing
  in the projection afterward. This means a later op referencing it does not
  cascade a second, redundant "not found" on top of the first op's own error. This
  was a deliberate call the report is flagging: an alternative design (only fold
  in a clean op's effect) would make later-op findings noisier without adding
  information, but it's worth T-203 being aware of the choice since interlock
  chain-analysis logic (its acceptance criterion 2: "moving the mgmt IP ... and
  deleting the old [bridge] in one changeset validates clean") depends on the
  same folding behavior.
- **Severity and short-circuiting**: every referential finding in this task is
  `SeverityError` (never a warning) — so any single referential finding
  short-circuits advisory for that `Validate` call. T-203's safety-interlock
  findings are documented as hard errors too (`docs/security.md`), so the same
  short-circuit-before-advisory behavior will apply to them without any change.

## Known scope gaps (flagged, not silently dropped)

- **fw.alias/ipset/group referential checks are intra-changeset only.** These
  three object kinds have no dedicated `inventory.Kind` in the current data model
  (see `params_fw.go`'s own doc comment) — there is no snapshot-backed way to know
  whether an alias/ipset/group already exists on the real cluster, or whether an
  `update`/`delete` op's `Name` refers to something real. `create` ops are checked
  against duplicates created earlier in the *same* changeset only. If a future
  task adds these as inventory entities, `validate_projection.go`'s `fwNames` map
  and the corresponding referential cases should be extended to a real
  existence/collision check.
- **fw ruleset existence for `fw.rule.update/delete/move`** is checked against the
  snapshot (`checkFwPos`'s `requireRuleset=true`); `fw.rule.create` and
  `fw.options.update` do not require a pre-existing `FwRuleset` entity, since
  cluster/node rulesets always exist in real PVE even before any rule has ever
  been added, and the test fixtures/mock may not always model an empty one.
- **VID overlap on a bridge trunk is evaluated per-op, not merged with prior
  state**: since `bridge.update`'s `Vids` fully replaces the declared list (per
  `params_bridge.go`'s doc comment — no partial-add semantics), there's no need to
  track a bridge's VID history across ops; each create/update's own list is
  checked for internal pairwise overlap. This is correct for the documented
  semantics but worth double-checking against T-203/T-207 if that assumption ever
  changes.
- **Address-overlap is checked at CIDR-containment granularity** (`net.IPNet.Contains`
  on either endpoint), not full interval math — sufficient for the documented
  check ("address overlaps with existing subnets") but a report flag in case a
  future task needs exact partial-overlap detection for oddly-aligned prefixes.

## What was tested and how

All tests are table-driven Go tests in `internal/change`; no PVE/network access
needed (pure functions over an in-memory `inventory.Snapshot`, built via
`buildSnapshot()` — one `inventory.Graph.ApplyPoll` call per test, same pattern
`internal/inventory`'s own tests use).

- **`validate_test.go`**: `TestValidate_Golden` — **49 cases** (card asked for
  ≥40), each isolating exactly one schema/referential/advisory check via a
  minimal op + snapshot, asserting an exact `(severity, code, ref)` match (plus
  5 "clean" happy-path cases). `TestValidate_IntraChangesetOrdering` — acceptance
  criterion 2, both directions (forward validates clean, reversed errors).
  `TestValidate_EveryOpTypeHasAPassingCase` — a coverage sweep proving every
  documented op type (not just the ones the golden/fix corpora exercise via an
  error case) has at least one passing case against a populated snapshot.
- **`validate_fix_test.go`**: `TestValidate_FixProperty` — acceptance criterion 3,
  an 11-entry fix corpus (MTU clamps across bond/bridge/vlan/iface/sdn-zone
  create+update, VID clamps for vlan/sdn-vnet create+update, bridge-VLAN-range
  clamp) where each snapshot is built so that *only* the one clamped field could
  possibly be wrong; asserts the fix shares the original op's Type/Target and
  that substituting it revalidates with zero error-severity findings.
  `TestValidate_100OpsUnder200ms` + `BenchmarkValidate_100Ops` — acceptance
  criterion 4; measured **~172µs** for 100 independent `bridge.create` ops
  (`go test -bench=BenchmarkValidate_100Ops -benchtime=200x`), comfortably under
  the 200ms budget.
- **`service_test.go`** (additions): `Service.Validate` promotes a clean draft to
  `validated` and broadcasts; demotes a `validated` changeset whose ops no longer
  validate clean back to `draft`; returns `*ErrIllegalTransition` for a non-editable
  changeset; 404s via `store.ErrNotFound` for a missing id; audits exactly one
  `changeset.validate` entry. A new `TestService_Create_ValidatesAgainstInjectedInventory`
  proves the `Config.Inventory` seam is actually wired (a bond referencing a slave
  that only exists via the injected fake inventory validates clean; against the
  default empty snapshot it would error).
- **`internal/api/changesets_test.go`** (additions): `TestChangesetsValidate_Route`
  (real 200 + findings + promoted status) and `TestChangesetsValidate_NotFound`;
  `TestChangesetsStubRoutes_501` trimmed to just diff/apply/confirm/rollback.
- **Coverage**: `internal/change` package coverage went from ~62% (T-201 baseline)
  to **80.2%** (`go test ./internal/change/... -race -cover`); the whole package
  tree (`internal/change/...`) is at 84.2%. Remaining gaps are mostly rare

## Anything the next agent (T-203) must know

1. **Where to add your class**: `validate.go`'s `Validate` function has two
   comment-marked insertion points; add your `safetyValidate(ops, snap)` call at
   the first one (between referential and advisory).
2. **Reuse `validate_projection.go`'s `projection` type** if you need an
   ops-so-far view (e.g. to detect a chain that moves the mgmt IP to a new bridge
   and deletes the old one in the same changeset per your acceptance criterion 2)
   — it already tracks bridge/bond/vlan existence, enslavement, and addresses
   per-op in order.
3. **All findings you emit should be `SeverityError`** (matching `docs/security.md`:
   "hard error, no override ... except via `allow_dangerous_ops`") for the default
   path; implement the `allow_dangerous_ops`-downgrade-to-warning behavior your
   card describes as a parameter your class function takes (e.g. a `bool` or a
   small config struct), not a change to the pipeline's short-circuit logic itself
   — a *warning* from your class should NOT short-circuit advisory, matching how
   every other class here already behaves (only `SeverityError` findings trigger
   `hasError`/short-circuit).
4. Protected-interface detection (management IP, corosync links) needs data this
   task's projection doesn't carry (host config, `/etc/pve/corosync.conf`,
   `/etc/pve/vnprox/protected.json`) — that's your card's own deliverable, not
   something layered into the projection here.
