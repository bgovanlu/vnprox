## 1. What was built

**`internal/metrics` (new package).** Built from scratch per the task card;
`internal/store/metrics.go` (the `metric_samples` table repo, 24h
`PruneRetention`/`RunPruneLoop`) and its daemon wiring already existed from
an earlier audit-remediation commit (`03d8b22`) — reused as-is, no new
migration.

- `rate.go`: `Counters`/`Rates` domain types, `ComputeRates(prev, cur
  Counters, dt) Rates` (bps is bits/sec), and `UtilizationPct(bps,
  speedMbps) float64`. Counter-wrap handling: `deltaCounter` uses Go's
  native `uint64` wraparound subtraction for a genuine 64-bit rollover, and
  a 32-bit-rollover heuristic (both operands `<= 2^32-1`) for the far more
  common truncated-counter case — table-tested for increase/equal/32-bit
  wrap/64-bit wrap (AC1).
- `linkmeta.go`: `refMetasFromLinks(node, links []host.LinkState)
  []refMeta` derives each sampleable interface's `inventory.Ref` + link
  speed + (for a Bond) slave list by reusing `inventory.FromNetlinkLinks`
  and type-switching its output — no duplicated Kind-classification logic.
  A Bond's own capacity (no ethtool speed of its own) is approximated as
  the sum of its *active* slaves' speeds, falling back to summing every
  declared slave if none is marked active.
- `sampler.go`: `Sampler.Ingest(ctx, node, at, links, stats)` — the single
  entry point `collect.Config.OnStats` calls every host-loop tick. Per ref:
  computes a live rate (once a second sample exists), broadcasts
  `metrics.sample` over the shared WS hub (`Broadcaster` interface,
  `*topology.Hub`/`*topology.Service` satisfy it — same seam pattern as
  `internal/change.Broadcaster`), and persists a downsampled counter row to
  `MetricStore` (an interface over `*store.MetricSampleRepo`) — the
  timestamp is truncated to the 30s wall-clock bucket and only the first
  tick observed in each new bucket actually writes, so ~6x fewer SQLite
  writes than a naive "insert every 5s tick" would produce, without
  changing the stored row count/resolution at all (upsert-on-conflict was
  available but intentionally not relied on for this — skipping redundant
  writes outright is strictly better).
- `sampler.go` also exposes `Live(refs []string) []LiveMetric` (bond refs
  carry a `Slaves []SlaveRate` breakdown, each slave's ref resolved back
  into the same live cache) and `History(ctx, ref, fromTs, toTs)
  []HistoryPoint` (rate between consecutive stored 30s samples).
- `store.go`: `Counters` <-> `store.MetricSample` conversion helpers.

**`internal/collect`.** `Config.OnStats func(ctx, node, at, links, stats)`
added; `hostPollStateFor` now hands its already-fetched `Links()` result and
`Stats()` result to it instead of discarding the counters (its old doc
comment literally said "modeling them is internal/metrics' future job").
Fires identically for the local node and every peer-fanned-out node
(`peerHostReader`) — no new peer transport, reusing T-303's existing
`peer.Client.Stats`.

**`internal/api`.** `metrics.go`: `MetricsService` interface,
`GET /metrics/live?refs=`, `GET /metrics/history?ref=&fromTs=&toTs=`, both
netRead-gated like every other read route. `docs/api.md`'s Metrics section
was a one-line-per-route stub; filled in the exact `Rates`/`LiveMetric`/
`SlaveRate`/`HistoryPoint` shapes there (definition-of-done #4).

**`cmd/vnproxd`.** `metricsSampler := metrics.New(...)` constructed once
(before `setupCollect`, reusing the same `*store.MetricSampleRepo` the
existing hourly prune loop uses), `Ingest` passed into `setupCollect` as
`collect.Config.OnStats`, `Metrics: metricsSampler` added to
`api.Options`.

**`web/`.**
- `api/metrics.ts` + `api/types.ts`: typed clients + wire shapes.
- `topology/trafficMode.ts`: pure, fully-unit-tested utilization-%-to-
  color/stroke-width heat mapping (5-stop scale, slate→blue→green→amber→
  red) and `resolveEdgeUtilizationRef` (prefers a Bond/PhysNic endpoint
  over Bridge/VLAN when both have live data) — this is the "logic-bearing"
  client code the task card calls out for Vitest coverage.
- `topology/metricsQueries.ts`: `useLiveMetrics(refs, enabled, client?)`
  seeds from `GET /metrics/live` then keeps every ref fresh via one
  `metrics:<ref>` WS subscription each (per docs/api.md: only subscribed
  refs stream); a `metrics.sample` push carries only `{ref, at, rates}` (no
  speed/utilization), so utilization is recomputed client-side
  (`computeUtilizationPct`, a direct TS port of the Go
  `UtilizationPct`) from the link speed the last full fetch reported.
  `useMetricsHistoryQuery` backs the inspector sparkline (last 1h,
  refetched every 30s — there's no WS push for history).
- `topology/store.ts`/`TopologyPage.tsx`/`toFlowElements.ts`/
  `EntityEdge.tsx`: a "Traffic" toggle button; when on, every edge's
  stroke color/width come from its resolved endpoint's utilization instead
  of status, and only refs of metrics-bearing kinds
  (`physnic`/`bond`/`bridge`/`vlan`) are ever subscribed to.
- `InspectorPanel.tsx`/`MetricsTab.tsx`: a "Metrics" tab (same kind gate)
  with rx/tx bps/pps/errors/drops stat tiles, a recharts rate-over-time
  sparkline, and — for a Bond — the per-slave balance list (ref, active/
  inactive dot, rx/tx). `recharts` was already an approved dependency
  (`docs/development.md`); no new dependency added anywhere in this task.

## 3. Deviations from the task card

1. **Guest netin/netout top-talkers (P1, spec §3)** — not implemented.
   Explicitly marked P1 in both the task card and the feature spec; the
   card's P0 acceptance criteria (1-5) are all about the sampler/history/
   traffic-mode/WS-load/DB-growth axis, none of which need per-guest PVE
   counters. Flagging as deferred rather than silently dropped.
2. **`docs/architecture.md`'s component diagram doesn't show a
   `MON -> STORE` edge**, but the Sampler genuinely needs to persist
   through `internal/store` (there is no other owner for the
   `metric_samples` table). Same situation T-303's report already flagged
   for `API -> PEER`; noting here rather than silently diverging. Not a
   design decision this task should be re-litigating — the store package
   already existed with exactly this table for exactly this purpose.
3. **Bond "link speed" is a derived approximation** (sum of active slaves'
   negotiated speeds, or all slaves if none report active) since the
   kernel bonding master has no ethtool speed of its own. Documented in
   `linkmeta.go`'s doc comment; reasonable given no better signal exists,
   but worth knowing if a future task wants a more authoritative source
   (e.g. cross-checking against PVE's own bond reporting, if it ever
   exposes one).
4. **Traffic mode subscribes to every metrics-bearing ref in the current
   topology response, not just on-screen/visible edges.** At the tested
   200-entity scale this is fine (AC4's own load test proves 200 is no
   problem); if a future performance pass (T-607) finds larger clusters
   pushing past a comfortable WS-subscription count, scoping this down to
   viewport-visible edges (progressive disclosure is already a topology.md
   §4 concept) would be the natural next optimization — flagging so T-607
   doesn't have to rediscover it from scratch.
5. **Inspector sparkline defaults to a 1h lookback**, not the full 24h
   ring (`docs/features/monitoring.md` §2's storage ceiling is 24h; the
   sparkline itself is a separate, narrower UX choice for a readable
   recent-activity view). `fetchMetricsHistory` supports any window; widening
   the default (or adding a lookback selector) is a small, isolated future
   change if wanted.
6. **Needs hardware validation:** `host.Real.Stats` (reading
   `/sys/class/net/*/statistics`) is exercised only through
   `internal/pvemock`'s fixture-backed `Stats()` in this task's tests, per
   CLAUDE.md ("you do NOT have a live Proxmox cluster"). The counter-wrap
   logic itself is fixture/table-tested directly (not dependent on real
   hardware), but real NIC driver behavior (which counters actually wrap at
   32 vs 64 bits, whether virtio-net/OVS interfaces report consistently)
   is unverified against a live cluster.

No new third-party dependencies were added on either side (`recharts` was
already approved and present in `web/package.json`; `nhooyr.io/websocket`
was already the locked WS dependency — its module-wide `SA1019` deprecation
notice needed the same golangci-lint exclusion the existing
`internal/topology/hub(_test)?.go` rule already carries, extended to cover
`internal/metrics/loadtest_test.go`).

  thresholds", "bond slave down") should read off `Sampler.Live()`'s

  should treat `internal/metrics` purely as a read dependency (construct
  its own polling/evaluation loop against `Sampler.Live`, or extend
  `Sampler` with an `OnSample`-style hook if a push model is preferred —
  there isn't one today, only the WS broadcast path).
- The `metric_samples` table's 30s-bucket persistence means a threshold
  check driven off *stored* history (rather than the in-memory live cache)
  has at most 30s latency to reflect a new counter delta — fine for the
  documented threshold-check cadence, but worth knowing if T-602 wants
  tighter hysteresis timing than that.
- `internal/metrics.LiveMetric`/`Rates`/`SlaveRate` are all in
  `internal/metrics` (not `internal/api`), so T-602 can import them
  directly without going through the HTTP layer.
