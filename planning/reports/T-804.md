# T-804 · LACP actor/partner state in the bond inspector

## Summary

Implemented in full: `/proc/net/bonding/<name>`'s per-slave 802.3ad "details actor/partner lacp
pdu" block is now decoded into `host.BondSlave` (parser) and `inventory.BondSlaveState` (flowed

partner system ID and key remain `/proc`-only since `github.com/vishvananda/netlink` v1.3.1's
bond-level `IFLA_BOND_AD_INFO` parsing is an explicit upstream TODO stub (not something this task
can work around without a netlink library upgrade — flagged, not silently worked around).

## Deviations from the task card (with reasons)

1. **Netlink AD-info is narrower than "prefer netlink, fall back to /proc" might suggest at face
   value.** Investigated `github.com/vishvananda/netlink` v1.3.1 (the pinned version,
   `docs/development.md`): the bond-level `IFLA_BOND_AD_INFO` nested attribute — which would carry
   the aggregate actor/partner system MAC and key — is parsed as an explicit `// TODO: implement`
   stub in that library version (`link_linux.go`'s `parseBondData`), so it is **never** populated
   on a real `LinkList()`/`LinkByName()` call today. Only the **per-slave** port-state bitmask
   (`IFLA_BOND_SLAVE_AD_ACTOR_OPER_PORT_STATE`/`...PARTNER_OPER_PORT_STATE`, on the enslaved link's
   own `Attrs().Slave`) is genuinely parsed. So this task's netlink path (`applyBondADState`)
   overlays only the synchronized/collecting/distributing bits; actor/partner system ID/priority/
   key come from `/proc` exclusively, regardless of kernel version. This is exactly the kind of
   "best-effort, not a hard requirement" gap the task card anticipated — noted here rather than
   silently pretending netlink covers more than it does, and **not** treated as grounds to bump the
   netlink dependency (that would be a new-dependency-version decision outside this task's scope;
   flagging instead per `CLAUDE.md`).
2. **`golangci-lint`'s `fieldalignment` check required reordering both new structs** (`host.
   BondSlave`, `inventory.BondSlaveState`) from topic-grouped to size-grouped field order (144 → 128
   bytes). Doc comments were moved to the struct-level comment so the conceptual (topic) grouping
   is still documented, just not reflected in physical field order. Mechanical, no behavior change.
3. **The inventory golden test (AC2) does not extend `internal/host/fixture.go` or
   `testdata/clusters/three-node-vlan.yaml`.** `FixtureReader`'s own doc comment already documents
   that fixtures model declared intent and simple runtime facts, not full kernel state (bond slave
   MII/active status is already only *approximated*, not per-slave-authentic) — extending that
   subsystem to fabricate LACP PDU detail would be new scope invented on top of the task card, not
   requested by it. Followed the codebase's existing precedent instead (`TestIngestNetlink`,
   `ports_test.go`'s "ApplyPoll entities onto several nodes directly" pattern, documented in
   `fdb_test.go`'s header comment) — hand-construct the `host.LinkState`/`BondDetail` overlay
   directly in the test, applied on top of the real three-node-vlan pipeline run so the bond ref
   itself is still the fixture's own.
4. **The e2e spec asserts one of several known-good LACP tab states rather than a specific
   negotiated/mismatched one**, because — as `web/e2e/topology.spec.ts`'s own doc comment already
   establishes — this suite's host collector reads the real dev machine, which has no actual bond0
   device, so host-netlink contributes no LACP detail for the fixture's declared bond0 in this
   environment. The state-specific rendering (negotiated vs. split-brain, AC4's actual ask) is
   covered by the Vitest suite against hand-built fixture data instead; the e2e spec's job is
   "the tab exists, renders without a page error, and shows one of its defined states" — this is
   consistent with how other e2e specs in this repo (`evpn-tab.spec.ts`) handle a no-real-data
   environment.
