## How the "no mutation verb via MCP" invariant is enforced STRUCTURALLY

Two independent structural facts, each with a regression test — it is not a documented convention:

1. **Fixed, enumerable tool allowlist (not a route bridge).** The registry is a static nine-tool slice; there is no generic "call any route/method" path. `validateRegistry()` (run at package load, `init()`) **panics** any tool whose name matches `apply|confirm|rollback|discard`, and `TestRegistryIsStageOnlyAllowlist` / `TestNoMutatingToolByName` pin the exact set and the forbidden vocabulary. `TestValidateRegistryPanicsOnMutatingTool` proves the guard actually fires.

2. **A change-engine seam with no mutation method.** The only change-engine capability the MCP server holds is `ChangesetStager`, whose method set is exactly `CreateWithOrigin` / `Validate` / `Diff`. It has **no** `Apply`/`Confirm`/`Rollback`/`Discard` method at all, so no MCP code path can call a live-mutating verb even if a tool tried — the type it is handed does not have one. `TestChangesetStagerHasNoMutationVerb` asserts the omission by reflection over the interface's method set (the same interface-surface style T-1702's plugin seam will use). `cmd/vnproxd` wires `*change.Service` (which does have those methods) into this narrow interface, so the concrete apply machinery is unreachable through the MCP handle.

Supporting guarantees: the automation-scope gate lives only in `Server.Authenticate`; per-tool exposure is derived from the token's scopes at connect time (`Session.exposedTools`) and re-checked per call; a revoked token force-closes the session within one `RevocationInterval` tick; every MCP-staged changeset carries `origin: "mcp"` + `originTokenId` and every invocation writes an `mcp.tool.invoke` audit row with actor `mcp:<token-name>`.

## Deviations from the task card (with reasons)
- **Tool set = the Deliverables allowlist exactly (nine tools), not the objective's prose list.** The card's objective prose mentions "microseg propose/dry-run" among read surfaces, but the Deliverables section and AC1 name an exact nine-tool set ("and nothing else") that excludes microseg/failsim tools. I implemented exactly the Deliverables/AC1 set, since AC1 tests it verbatim. Microseg/failsim remain reachable only through their existing HTTP routes.
- **`diagnose.run` never escalates to packet capture over MCP.** The ladder's capture rung is its only side effect; `NewDiagnoseRunner` forces `EscalateToCapture=false`, keeping the MCP surface free of side effects. Capture stays a human/HTTP-gated action.
- **`[mcp]` config is a single `enabled` flag** (mount path fixed at `/api/v1/mcp`), rather than a configurable path — simpler and avoids a chi mount-conflict; `DefaultMCPPath` is pinned equal across `internal/config` and `internal/api` by a test.
- **MCP changeset views omit `ops`** (return metadata + findings only) to avoid ever echoing a sealed op secret (e.g. a wg PSK) back over MCP.
