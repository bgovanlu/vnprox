## 1. What was built

### The hole, precisely

`internal/peer.Client` built its HTTP client as `&http.Client{Timeout: opts.RequestTimeout}` —
no `TLSClientConfig` at all, so peer TLS inherited `net/http`'s default system trust store. Every
production call site (`cmd/vnproxd/collect.go`'s collector fan-out, `cmd/vnproxd/server.go`'s
`coordPeerClient`, both `vnproxctl status` probes) left `ClientOptions.HTTPClient` nil and got
that. Real peer daemons serve the node's PVE certificate (`docs/architecture.md` §9), issued by
`/etc/pve/pve-root-ca.pem`, which was never consulted.

The consequence: an attacker holding a certificate from **any** publicly-trusted CA, plus a
position on the management network, satisfied the TLS half of peer authentication for a surface
that carries cross-node changeset application, distributed rollback timers, and host-writer calls.
Flagged in `planning/reports/T-301.md` §5 and `planning/reports/needs-hardware-validation.md`; no
card owned it until now.

### Backend

**`internal/peer/trust.go` (new)** — `Trust`, an `http.RoundTripper` that is the daemon's single
peer-TLS trust decision:

| Piece | Behaviour |
|---|---|
| `DefaultClusterCAPath` | `/etc/pve/pve-root-ca.pem`; `TrustOptions.CAFile` / `[peer] ca_file` overrides |
| `TrustMode` | `cluster-ca` (zero value), `system`, `insecure`; `TrustExternal` is report-only and `ParseTrustMode` rejects it |
| `AckSystem` / `AckInsecure` | `i-accept-unpinned-peer-tls` / `i-accept-unverified-peer-tls` — per-mode literals |
| `NewTrust` | validates mode + ack, emits the startup banner (`WARN` for either escape hatch, `Info` for the pin) |
| `RoundTrip` | https → the pinned transport; plain http → `http.DefaultTransport` (no anchor needed, and reported as a degraded posture) |
| `refreshLocked` | re-reads the anchor when `ReloadInterval` (30 s) has elapsed; SHA-256 fingerprint diff decides whether to rebuild |
| `swapTransportLocked` | installs the new transport and **closes the old one's idle connections**, so a keep-alive verified under the old anchor cannot outlive a rotation |
| `logOnceLocked` | state-transition logging, so a steady state does not reprint every cadence and a real transition is never swallowed |
| `isTrustFailure` | `*tls.CertificateVerificationError`, `x509.UnknownAuthorityError` / `HostnameError` / `CertificateInvalidError`, and this package's own `ErrTrustAnchorUnavailable`. Deliberately **not** `tls.RecordHeaderError`, handshake timeouts, or version-negotiation failures — calling those "untrusted" would cry wolf |

**`internal/peer/trustreport.go` (new)** — `PeerTrustState` (`ok`/`unreachable`/`untrusted`), a
per-node `peerStatusStore` on the `Client`, `Client.PeerStatuses()`, and `Client.TrustReport()`
(mode, anchor error, dialled scheme, per-peer verdicts). Only peers actually attempted appear;
nothing is invented.

**`internal/peer/client.go`** — `ClientOptions.Trust`; `NewClient` now defaults a nil `Trust` to
`newPinnedTrust(...)` rather than to a bare `http.Client`, so *forgetting to configure* yields the
pinned posture instead of the vulnerability. `do()` classifies transport failures and records the
verdict, and the circuit-breaker fast-fail path replays a sticky untrusted verdict instead of
flattening it back to "unreachable". Both failure wraps changed from `%v` to `%w` so callers can
reach the underlying `x509` cause.

**`internal/peer/errors.go`** — `ErrPeerUntrusted` (`peer_untrusted`).

**`internal/config`** — `[peer] ca_file` / `tls_trust` / `tls_trust_ack`, resolved and validated by
`resolvePeerConfig`. Validation delegates to `peer.NewTrust` so the *library* is the enforcement
point; config load just moves the failure to startup.

**`internal/findings/health_peertrust.go` (new)** — `SourcePeer` and three checks
(`peer_untrusted`, `peer_unreachable`, `peer_trust_degraded`), wired through `findings.Config`,
`Engine`, and `Engine.Findings()`.

**`cmd/vnproxd/peertrust.go` (new)** — `newPeerTrust` (one `*peer.Trust` per daemon, forced first
evaluation so a missing anchor is a startup `ERROR`) and `peerTrustAdapter` (the lazily-set
findings seam, mirroring `federationTunnelAdapter`). Both peer clients in `runDaemon` and both
`vnproxctl status` probes now share that anchor; `vnproxctl status` prints the posture line.

## 2. Safety analysis — every claim, mapped to the test that proves it

### Claim 1 — "The pin is real: a certificate the *system* trusts is still rejected." (AC1)

The headline. `TestTrust_AC1_RejectsAPeerWhoseCAIsInTheSystemTrustStore` runs in a **child
`go test` process** — `crypto/x509` honours `SSL_CERT_FILE`/`SSL_CERT_DIR` on Linux but caches the
resulting pool behind a `sync.Once`, so a fresh process is the only way to be certain the injection
actually took rather than silently no-opping and leaving a vacuous test. The parent generates two
CAs, starts an HTTPS peer whose certificate is issued by the **rogue** one, and re-execs itself
with `SSL_CERT_FILE` pointing at the rogue CA. The child asserts, in order:

| Step | Assertion | Why it is there |
|---|---|---|
| 1 | `x509.SystemCertPool()` is non-empty | the injection took |
| 2 | a client built **verbatim** the way `NewClient` built one before this card (`&http.Client{Timeout: …}`) **accepts** the rogue peer | reproduces the vulnerability in-process, against this very server. This is what stops the test rotting into a tautology: if the rogue CA were ever not really trusted, step 2 fails loudly instead of step 3 passing for the wrong reason |
| 3 | the cluster-CA-pinned client rejects the same peer with `ErrPeerUntrusted` | the pin |
| 4 | a pinned client whose CA file **does not exist** also rejects, with `ErrPeerUntrusted` + `ErrTrustAnchorUnavailable` | **no silent fallback** — the system pool that step 2 just proved would have accepted is not consulted |

**Counterfactual check performed:** I temporarily changed `newTLSTransport` to pass
`RootCAs: nil` (i.e. reinstated the inherited-trust-store behaviour) and re-ran. The test failed
with `AC1 child: pinned client ACCEPTED a peer signed by a system-trusted CA — the pin is not in
effect`, and the in-process companion failed too. Change reverted. The test genuinely fails against
today's code.

`TestTrust_AC1_SystemModeAcceptsWhatPinningRejects` is the deterministic in-process companion: the
same rogue peer, with "the trust store the client would otherwise inherit" injected through the
package-private `TrustOptions.systemPool` seam. It asserts `system` mode accepts and `cluster-ca`
rejects, and that the server's request counter is `1` — the rejected request never reached the
handler.

### Claim 2 — "A legitimate peer still works, and hostname verification was not sacrificed to make that true." (AC2)

| Test | What it proves |
|---|---|
| `TestTrust_AC2_AcceptsAPeerSignedByThePinnedClusterCA` | a peer serving a cluster-CA-issued certificate is accepted, `Version` decodes a real body over that connection (so it is a working connection, not a suppressed error), and the recorded verdict is `PeerTrustOK` |
| `TestTrust_AC2_StillVerifiesTheHostname` | the obvious way to fake AC2 — pin the CA but turn off name checking — is closed: a certificate the cluster CA genuinely issued, for a *different* host, is still `ErrPeerUntrusted`. Without this, any node in the cluster could impersonate any other |

### Claim 3 — "The escape hatch cannot be enabled by accident." (AC3)

The design is a two-key interlock, mirroring `[switches]`' daemon-flag-AND-per-switch-flag
precedent: the mode *and* its own exact acknowledgement literal, with **different literals per
mode** so copying a `system` config and editing only the mode line yields a refusal to start rather
than an unverified daemon.

| Test | What it proves |
|---|---|
| `TestTrust_AC3_EscapeHatchNeedsItsOwnExactAcknowledgement` | 14 rows. Zero value → pinned. `cluster-ca` needs no ack and ignores a stray one. `system`/`insecure` without an ack, with `"true"`, with the *other* mode's ack, or with a trailing-space near-miss → `ErrTrustNotAcknowledged` **and a nil `Trust`**. Unknown modes (`off`, `clusterca`, `false`) → `ErrUnknownTrustMode`. Only the exact pair is allowed |
| `TestTrust_AC3_EscapeHatchWarnsOnEveryStartup` | three successive constructions produce three `WARN` records (not one), for both hatches, each naming "escape hatch". There is no ack, state file, or counter that silences it |
| `TestTrust_AC3_DefaultConstructionIsPinnedNotSystem` | `NewTrust(TrustOptions{})` is pinned at `DefaultClusterCAPath`; and a `Client` handed **neither** a `Trust` nor an `HTTPClient` — the exact shape every pre-T-1906 call site had — reports pinned cluster-ca. Forgetting to wire cannot reintroduce the hole |
| `TestTrust_AC3_ParseTrustModeNeverFallsBack` | `""` is the secure default and nothing else is coerced: `off`, `none`, `no`, `disabled`, `System`, `INSECURE`, `cluster_ca`, `" "` all error. `TrustExternal` is not configurable |
| `TestLoad_PeerTLSTrustDefaultsToPinned` | three real config files that say nothing about peer TLS (including one with no sections at all) all load pinned — i.e. every production config in existence |
| `TestLoad_PeerTLSTrustEscapeHatchInterlock` | the same interlock at the config layer: every malformed attempt is a fatal `ErrInvalidConfig`, never resolved to *either* the requested or the safe mode |
| `TestLoad_PeerTLSTrustErrorNamesTheRequiredAcknowledgement` | the error names the literal to write, so a blocked operator does not reach for something worse |
| `TestNewPeerTrust_RefusesAnUnacknowledgedEscapeHatch` | a hand-built `config.Config` that bypassed `Load` still cannot produce an unpinned daemon — the library, not the config layer, is the enforcement point |
| `TestNewPeerTrust_LogsTheEscapeHatchWarningEveryStartup` | three `level=WARN` lines across three startups, asserted on the real `slog` text output the operator's journal receives |

### Claim 4 — "A rotated CA is followed without a restart." (AC4)

| Test | What it proves |
|---|---|
| `TestTrust_AC4_RotatedClusterCAIsPickedUpWithoutARestart` | one `Trust` and one `Client`, never reconstructed, across a rotation. Before: old-CA peer accepted, new-CA peer untrusted. The file is rewritten; **within** the reload interval the old anchor still applies (proving the reload is cadence-driven, not a per-request read); after the cadence elapses the verdicts swap. Critically, the old-CA peer is rejected **even though a verified keep-alive connection to it is already pooled** — that is what `swapTransportLocked`'s `CloseIdleConnections` buys, and without it the rotation would be cosmetic |
| `TestTrust_AC4_RotationIsLogged` | five reload cadences in a steady state produce exactly two `INFO` records (banner + "anchor loaded") — no per-cadence spam — and the rotation itself logs "rotated" |

### Claim 5 — "Untrusted and unreachable are different facts, all the way to the operator." (AC5)

| Test | What it proves |
|---|---|
| `TestTrust_AC5_UntrustedAndUnreachableAreDistinguishable` | a live impostor and a genuinely dead peer (listener bound then closed) in the same client: the impostor is `ErrPeerUntrusted`, the dead peer is `ErrPeerUnreachable` and is **not** untrusted, and the recorded states are `untrusted`/`unreachable` respectively |
| ” (same test, last assertion) | the untrusted error **also** satisfies `errors.Is(err, ErrPeerUnreachable)` — the card's "an unverifiable peer is unreachable, never trusted". This is what keeps every existing degrade-around-a-dead-peer path (`partial`/`failedNodes` fan-outs, T-304's "the peer's own local timer is the safety net" rollback tolerance, collector staleness) behaving exactly as before instead of newly hard-failing |
| `TestTrust_AC5_UntrustedSurvivesTheCircuitBreaker` | with `BreakerFailureThreshold: 1`, the second call fast-fails without touching the network and **still** reports `ErrPeerUntrusted` ("circuit open after a certificate verification failure"), not a generic unreachable. | `TestPeerTrustFindings_AC5_UntrustedAndUnreachableAreDifferentFindings` | two peers differing *only* in why they could not be reached produce different checks, ids, severities (`error` vs `warning`), and wording — the details are asserted to contain "did not verify against the pinned cluster CA"/"not a connectivity problem" and "nothing responded"/"certificate was never in question" respectively. ### Claim 7 — "Every weakening of the posture is visible, including the ones that are not config."

`peer_trust_degraded` has four independent causes, each with its own stable id so two simultaneous
problems cannot hide one another (`TestPeerTrustFindings_TwoPostureProblemsAreTwoFindings`):

- `unpinned` — `tls_trust = "system"`, **or** a caller-supplied `ClientOptions.HTTPClient` whose
  trust decision this package cannot inspect. That second case is the pre-T-1906 shape itself, and
  it is reported as `TrustExternal`/unpinned rather than quietly vouched for
  (`TestClient_TrustReportFlagsACallerSuppliedHTTPClient`).
- `unverified` — `tls_trust = "insecure"`, severity `error`.
- `anchor_unavailable` — fail-closed, severity `error`.
- `plaintext` — the client dials `http`. The plain-http bypass exists so the test harness and
  `make dev` do not need `/etc/pve`, and it is *reported* rather than hidden
  (`TestTrust_PlainHTTPBypassesTheAnchorButIsReported`).

Table-driven over all five shapes, with the default pinned posture asserted to raise nothing
(`TestPeerTrustFindings_PostureIsReported`, `…HealthyClusterIsSilent`).

### The one place this deliberately does **not** fail closed, and why

If the anchor has **never** loaded, `Trust` fails closed. If a **previously loaded** anchor
becomes momentarily unreadable (a pmxcfs blip, `/etc/pve` unmounted during a `pve-cluster`
restart), it keeps serving the last known-good pool and logs a `WARN`.

This trusts nothing that was not already verified against a real cluster CA — the security property
("never accept an unverified peer") is identical either way. What it avoids is converting a
transient filesystem error into a cluster-wide peer outage. A CA file is an anchor, not a
revocation list; dropping it on a read error would buy no security and cost availability, on
exactly the surface an operator needs during an incident. Proved by
`TestTrust_KeepsTheLastKnownGoodAnchorOnATransientReadFailure`, which after deleting the file
asserts (a) the good peer still verifies, (b) a foreign-CA peer is **still rejected** — the old
anchor is still doing real work, not being bypassed — and (c) the degraded re-read is logged at
`WARN`. Stated in the code's doc comment, not just here.

## 6. Deviations from the task card, with reasons

**D1 — `ErrPeerUntrusted` also wraps `ErrPeerUnreachable`.** The card asks for a distinction, and
also states the rule "an unverifiable peer is unreachable, never trusted". Making the untrusted
error satisfy *both* `errors.Is` checks honours both: the operator-facing distinction lives in the
findings stream (AC5's actual requirement), while every existing `errors.Is(err,
ErrPeerUnreachable)` degradation path in the daemon — cluster fan-out `partial`, T-304's rollback
tolerance, collector staleness — keeps behaving exactly as it does for a dead node. The
alternative (untrusted matching neither) would have silently converted graceful degradation into
hard failures across a dozen unrelated call sites. Documented on the sentinel and asserted.

**D2 — Three finding checks, not two.** AC5 requires two. I added `peer_trust_degraded` because
the card's other requirement — that degradation be an explicit, loud choice — is only half met by a
log line an operator has to go looking for. It also gives the fail-closed condition and the
plain-http bypass somewhere to be visible. Each cause is its own id so they cannot mask each other.

**D3 — A two-key interlock (mode + per-mode ack literal), not a single config value.** The card
says "explicit config value"; AC3 says "impossible to enable by accident". A single string value
is explicit but one careless edit away, so I used the `[switches]` two-key precedent and made the
literals differ per mode, which additionally prevents sliding from `system` to `insecure` with a
one-line change. The cost is a slightly noisier config for the rare dev host; the escape hatch is
supposed to be uncomfortable.

**D4 — Reload cadence rather than per-request re-read.** Reading a 2 KiB file on every peer request
would make rotation instantaneous but adds a syscall to a hot path. 30 s is far shorter than any
CA's lifetime and is injectable for tests. The cadence is itself asserted (the AC4 test proves the
old anchor still applies within the interval).

**D5 — A previously-good anchor survives a transient read failure.** See §2's closing subsection.
This is the single deliberate non-fail-closed behaviour, documented in code and tested from both
sides.

**D6 — No frontend change.** `FindingSource` in `web/src/api/types.ts` is already missing eight
existing sources; the UI does not branch on it. Adding only `peer` would be arbitrary. Flagged for
whoever reconciles that union.

**D7 — `vnproxctl status` gained a posture line.** Not asked for, but `vnproxctl status` builds its
own peer client, and one that made a *different* trust decision from the daemon would report peers
as reachable that vnproxd itself refuses. Sharing the anchor was mandatory; printing which anchor
was one line and prevents a confusing "vnproxctl says it's fine" support loop.

**D8 — The peer *server* is unchanged.** No mTLS, no client-certificate requirement. Peer request
authenticity still rests on the cluster-secret HMAC. Pinning protects the client's view of who it
is talking to, which is the direction that carries the mutation. Stated as a residual in
`docs/security.md` rather than silently scoped out.

**D9 — No new dependency**, Go or npm.

## 7. Needs hardware validation

`planning/reports/needs-hardware-validation.md`'s "Peer TLS trust" item is rewritten: the original
text ("`internal/peer.Client` does not yet pin that CA") is now wrong and is replaced with what was
built plus six concrete checks. **T-1801's harness (`planning/validation/`) does not exist yet**,
so they live in the ledger phrased as harness steps ready to be lifted verbatim.

Every CA and certificate in this card's tests is synthetic. What genuinely cannot be known from
here is the **real chain's shape**:

1. **The leaf's SANs — the top risk.** Peers are dialled by **IP**
   (`Client.Peers` builds `https://<node-ip>:8007` from `GET /cluster/status`). If PVE's generated
   `pve-ssl.pem` carries only the hostname/FQDN and not the management IP in its SAN list,
   hostname verification fails on **every** peer. Because pinning fails closed, that would present
   as every peer flipping to `peer_untrusted` at once on upgrade. It is loud, diagnosable (the
   finding detail names the "not valid for the address it was reached at" cause and quotes the
   `x509` error verbatim), and recoverable via `[peer] ca_file` or the acknowledged escape hatch —
   but it must be checked on iron before this ships widely. I deliberately did **not** invent a
   node-name/`ServerName` fallback: the card says not to assume a chain shape beyond what
   `docs/architecture.md` §9 documents, and guessing here would trade a loud, correct failure for
   a quiet, wrong success.
2. **The served chain**: is the leaf issued directly by `pve-root-ca.pem` or via an intermediate,
   and does `pveproxy` send the issuer? Capture with `openssl s_client -showcerts` and keep as a
   fixture.
3. **Custom certificates** (`pveproxy-ssl.pem`, e.g. Let's Encrypt): such a node's peer certificate
   is not issued by the cluster CA, so pinning rejects it. `[peer] ca_file` is the designed answer;
   confirm and document.
4. **Rotation on iron**: `pvecm updatecerts -f`, then confirm recovery within one reload interval
   with no restart.
5. **`/etc/pve` availability during a `pve-cluster` restart**: confirm the last-known-good path
   (§2's closing subsection) is what actually happens rather than a fail-closed blip.
6. **Mixed-version rollout**: a pre-T-1906 node serving a pinned peer. The pinned side is the
   client, so this should be unaffected — confirm no asymmetry.

## 8. For the next agents

- **Anyone constructing a `peer.Client`**: pass the daemon's shared `*peer.Trust`. Passing
  `ClientOptions.HTTPClient` instead is now a *reported* degraded posture (`peer_trust_degraded`,
  cause `unpinned`), deliberately — that field is for tests.
- **Anyone catching peer errors**: check `ErrPeerUntrusted` **before** `ErrPeerUnreachable`; the
  former implies the latter (D1).
- **T-1801 (validation harness)**: §7's six items are written as harness steps. Item 1 is the one
  that could break a real cluster and is worth doing first.
- **T-1902 (support bundle)**: `peer.Trust.Status()` and `Client.TrustReport()` are exactly the
  right shape for a collector — mode, anchor path, anchor error, per-peer verdicts — and contain
  no secrets by construction (no key material, no secret, no ticket; the only free text is a
  path and an `x509` error string).
- **Whoever reconciles `web/src/api/types.ts`'s `FindingSource`**: it is now missing nine sources,
  `peer` included (D6).
- **T-1806 / the allowlist owner**: `npm audit` is the only red gate on this branch and is
  reproducible on a pristine tree (§5).
