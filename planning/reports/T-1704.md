## The single-writer / fencing guarantee (the 🔒 checkpoint)

- **Durable lease, not "probably one active."** `ha_lease {holder, term, expiresAt}` is the sole
  authority. `term` is a monotonic fencing token — a promotion always writes `strictly-higher`
  (`promoteFrom` uses `max(local, observed)+1`); a heartbeat/action older than the observed term is
  rejected (`Manager.Receive` stale-sender path) and no data is applied.
- **No double-drive.** `change.Service`'s `autoRollback`/`TickSchedules` fire as logged no-ops off
  the leader (`mayLead`). An isolated active that cannot confirm its lease with the peer for a whole
  TTL **self-demotes** (`handlePushFailure`), so the standby's promotion (at observed-expiry +
  margin ≥ TTL) lands *after* the old active has stepped down — no overlap window. A demoted
  former-active adopts the newer term and drives nothing (`demote` → `Coordinator.Quiesce`).
- **Same absolute deadline on failover.** `confirm_deadline` / schedule windows replicate verbatim
  (absolute unix seconds). On promotion the new active calls `Coordinator.ReArm` →
  `change.Service.ArmPendingRollbacks` + `TickSchedules` — the **existing** T-205/T-1103 re-arm code
  path, reproducing the same deadline, never a fresh one.
- **Fail safe.** Ambiguity withholds: the guard's non-leader answer withholds the rollback (a missed
  confirm just leaves the changeset awaiting the leader's own re-armed, absolute-deadline timer),
  never a double-apply that could cut connectivity.

## Failover reconciliation with node-local timers

The card's requirement that a failover *reconcile with* T-304's node-local timers (not fight them)
is honored two ways: (1) the LeaderGuard is applied only to the coordinator-side unattended timers,
never to `LocalTimerAgent` (each node's self-restore on its own absolute deadline stays
authoritative); (2) on promotion the new coordinator re-arms its own view to the *same* persisted
absolute deadline, so the coordinator-side and node-local safety nets agree rather than race.

## Deviations from the card

1. **Snapshot pre-state is replicated too.** The card enumerates changesets / `changeset_schedules`
   / `api_tokens` / audit. A promoted standby that must *complete* an in-flight rollback needs the
   byte-exact pre-apply files, which live in `snapshots`+`snapshot_files`+`blobs` — the enumerated
   set alone would leave a promoted standby unable to roll back, defeating the P0 requirement. I
   replicate the pre-apply snapshots of in-flight changesets (awaiting_confirm/applying/committed)
   idempotently; only metrics rings stay excluded, exactly as the card says. Flagged here as a
   deliberate, necessary extension.
2. **Peer wire-protocol version left at 2.** I added `POST /api/peer/ha/replicate` without bumping
   `peer.ProtocolVersion` (an HA pair runs the same build; the route is 503-nil-safe otherwise), to
   avoid destabilizing the existing peer-compat gate/tests. Noted for T-1707's freeze pass.
3. No new third-party dependency (std-lib only for the VIP command / DNS webhook announcers).
