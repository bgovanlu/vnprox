# T-1705 · Blueprint & plugin hub — completion report

## What I built

An opt-in browse/install client over a public registry of T-1107 signed blueprint
bundles and T-1702 SDK plugins. **This repo ships the client and the
registry-index contract, not the registry service** — the registry (its
`index.json` and hosted artifacts) lives in a separate repo. This mirrors
T-1106's "the provider/collection source lives in a separate repo" boundary
(cited per the task card; T-1204's docs-boundary precedent was explicitly *not*
applicable). The hub is a catalog/install-orchestration layer, not a new trust
boundary.

### Backend

- **`internal/hub`** (`hub.go`): the registry-index contract types (`Index`,
  `Entry`, `PluginManifest`, `PluginArtifact`), an HTTP `Client` that fetches and
  briefly caches `GET <registry>/index.json` and downloads artifacts, and
  `VettedSet` (the `[hub] vetted_signers` allowlist). The client does **no**
  signature/trust decision of its own — it fetches and parses bytes only. An
  off-origin `artifactUrl` is refused (`ErrForeignArtifact`): the fetched index
  is not signed as a whole, so it can never redirect an install off-host.
- **`internal/api/hub.go`**: `GET /hub/index?type=` (netRead, annotates each
  entry with the informational `vetted` badge) and `POST /hub/install` (netWrite +
  CSRF). Seams: `HubClient`, `HubVetting`, `PluginInstaller`.
- **`internal/api/blueprint_bundle.go`**: extracted `importBundleCore` from
  `handleImportBundle` — the single verify → trust-decision → save + audit
  implementation. The direct `POST /blueprints/import` handler and the hub
  blueprint-install path both call it (AC2's "no duplicated verification logic").
- **`internal/blueprint/bundle.go`**: extracted `VerifySignature(sig, msg)` from
  `VerifyBundle` so the plugin manifest path reuses the *exact same* Ed25519
  primitive rather than reimplementing the crypto. `VerifyBundle` now delegates to
  it (behaviour unchanged; all T-1107 tests still green).
- **`cmd/vnproxd/hubinstall.go`**: `hubPluginInstaller` — the concrete
  `PluginInstaller`. It turns a hub-verified `plugin.Manifest` into a live
  `plugin.Registration` (spawning the out-of-process subprocess via
  `internal/plugin/procshim`) and installs it through T-1702's `Registry.Install`,
  which independently re-validates the capability scope. Only `grpc`
  (out-of-process) plugins are installable from the hub.
- **`internal/config`**: `[hub]` section (`registry_url`, `vetted_signers`).
- Wired into `cmd/vnproxd/server.go` and `internal/api/router.go` (all deps
  nil-safe; no registry URL → hub routes not mounted).

## How the signature + capability gates are preserved (inherited, not weakened)

- **Blueprint installs** run the downloaded bundle through `importBundleCore` —
  literally T-1107's import path (verify → trust-store decision → save). Unsigned
  or untrusted-signer bundles return the exact same `unsigned`/
  `untrustedSignature` status and require the same `trustUnsigned`/`trustNewKey`
  step; audited as `blueprint.import` with the identical shape (AC3 test asserts a
  single denied `blueprint.import` entry).
- **Plugin installs** verify the manifest's Ed25519 signature with
  `blueprint.VerifySignature` against the *same* trust store, apply the identical
  gate, then install only through `plugin.Registry.Install` (via the
  `PluginInstaller` seam), which re-runs `ValidateScope`. No hub path reaches
  `Registry.Install` around the scope check. Test confirms an unsigned plugin
  never reaches the installer.
- **Vetted tier** (`VettedSet`) is display-only. AC5 regression test:
  a vetted-but-not-trusted signer still returns `untrustedSignature` on install —
  the badge never bypasses the trust decision.

## Deviations / notes for the next agent

- **No migration / no new table.** The hub caches the index in memory and owns no
  durable state (plugins persist via T-1702's `PluginRepo`, blueprints via the
  blueprint service, trust via T-1107's filesystem trust store). `migrations/` and
  `kv_test.go` are untouched (no `0033`).
- **`BundleSignature.PublicKey` reuse for plugin manifests.** Plugin artifacts are
  signed with the same `blueprint.BundleSignature` shape over the canonical
  manifest bytes, verified by the shared `blueprint.VerifySignature`. This keeps a
  single Ed25519 scheme + single trust store across both artifact kinds.
- **Out-of-process only + subprocess launch needs hardware validation.** The hub
  installs only `grpc` plugins (an in-process plugin is build-time Go code that
  cannot be materialized from a downloaded manifest). The actual subprocess launch
  in `hubPluginInstaller` (`procshim.Start(exec.Command(endpoint))`) is exercised
  only against a test double in CI; delivering a real plugin binary to
  `manifest.endpoint` is the registry service's responsibility (separate repo), so
  the end-to-end launch of a downloaded binary **needs hardware validation**.
- **Ingress plugin Kind.** A hub-installed ingress-discoverer plugin's discoverer
  `Kind` is derived from its manifest `id` (the manifest carries no separate Kind
  field); a built-in Kind is never overridden (`Registry.IngressRegistry`).
