## `ConntrackEntry` shape (docs/api.md, this task's own contract)

```go
// internal/host — one node's live read
type ConntrackEntry struct {
    SrcIP, DstIP, State string
    NatSrc, NatDst       *NatAddr // nil = untranslated
    Proto, SrcPort, DstPort, TimeoutSec int
}
type NatAddr struct { IP string; Port int }
```

`GET /conntrack`'s wire shape adds `node` (which cluster node observed the connection — not on
`host.ConntrackEntry` itself, since a single `Reader.Conntrack` call is already scoped to one
node): `{node, proto, srcIp, srcPort?, dstIp, dstPort?, state?, timeoutSec?, natSrc?, natDst?}`.

## `GET /conntrack` and `GET /api/peer/host/conntrack` contracts

- **`GET /conntrack?node=&guest=&srcIp=&dstIp=&port=&state=`** (`internal/api/conntrack.go`,
  netRead-gated): every filter optional and ANDed; unrecognized/unresolvable values (including an
  unknown `guest=` ref) match nothing, never a `400`, except a non-integer `?port=` (`400
  validation_failed`, matching `GET /flows`' own `?port=` convention — a caller bug, not a
  legitimate empty-result value). `state` matches case-insensitively. No pagination (a live kernel
  snapshot has no cursor to resume — unlike `GET /flows`, this route has no retention window at
  all). Response: `{items: [ConntrackEntry], partial?, failedNodes?}`.
- **`GET /api/peer/host/conntrack?node=`** (`internal/peer`, HMAC-authenticated, internal only):
  one node's own local live table, `{entries: [ConntrackEntry]}`, no `partial`/`failedNodes` (a
  peer only ever reports its own node — the fan-out/merge happens on the calling daemon).

## Design notes / deviations worth flagging

- **`guest=` resolves through `internal/ipam.Service.GuestIPs`, a new method, not through
  `internal/inventory`.** The inventory graph carries no guest IP addresses at all (the same
  documented gap `GET /flows`' own `srcRef`/`dstRef` resolution and `POST /simulate/path`'s
  `guest-ip-unknown` caveat already disclose) — `GuestIPs` collects the two enrichment sources
  `internal/ipam` already reads for its own subnet merge (guest-agent-reported addresses; PVE-IPAM
  allocations matched by the guest's known NIC MACs) directly, rather than going through the full
  per-subnet `Cell` merge (which renders IPAM's own confidence/state labels this task doesn't
  need). Same "observed, never authoritative" posture every other enrichment source in this
  codebase carries.
- **The map's right-click "View live connections" and `FlowPairPanel`'s own drill-down link are
  node-scoped (`?node=<node>`), not exact IP/guest-pair-scoped.** A flow conversation's resolved
  endpoints (`FlowEdge.from`/`to`) are always Bridge or SdnVnet refs — never a conntrack-matchable
  raw IP, never a Guest ref — per `GET /flows`' own documented "never guessed" limitation. Rather
  than fabricate a false-precision filter, both entry points extract the ref's own node segment
  (`bridge:pve1:vmbr0` → `pve1`) and scope the explorer to that node, which is the honest link this
  codebase's own data can build today. Documented in `conntrack/urlState.ts`'s own doc comment and
  in the new `docs/api.md` Conntrack section.
- **`GET /conntrack` has no pagination, unlike `GET /flows`/`GET /audit`.** A live conntrack table
  is a point-in-time kernel read, bounded by the kernel's own table size, not an accumulating log —
  there is nothing to page through or resume a cursor against. The explorer instead polls
  (`CONNTRACK_REFETCH_MS = 5s`) rather than subscribing to a WS event, since a snapshot read has no
  natural incremental-delta shape to push (unlike `flow.batch`).
- **`node=` is an ANDed post-fetch filter, not a fan-out-scoping optimization** — `GET /conntrack`
  always queries every reachable node (local + every peer) regardless of `?node=`, then filters the
  merged result. This mirrors every other filter's ANDed convention exactly and keeps the fan-out
  logic uniform; a future optimization to skip querying nodes the filter would exclude is possible
  but not attempted here (correctness-neutral, and the current per-request 3-node dev-fixture cost
  is negligible — see the "peer timeouts add up serially" note below for the one real cost this
  surfaced).
- **web/e2e/conntrack.spec.ts does not assert fixture-declared conntrack rows appear in the
  browser** — the single most significant deviation from a literal reading of AC5's "seeded fixture
  set" for the e2e half specifically (the Vitest half, `ConntrackExplorer.test.tsx`, does use a
  seeded fixture set exactly as written). Root cause, confirmed by direct `curl` + log inspection
  against this dev machine's real running `vnproxd`: `internal/host.Real.Conntrack` reads
  `/proc/net/nf_conntrack` directly off the kernel (`Real` — as documented, "reads the actual
  netlink/procfs state," per `docs/architecture.md` §1's "there is no PVE host here" caveat every
  other host-level e2e spec in this suite already discloses for interfaces/links/LLDP/stats); that
  file is `0440 root:root` on this sandboxed dev machine, and `web/playwright.config.ts`'s shared
  webServer commands run vnproxd unprivileged (never as root, for good reason on a shared dev box).
  The read fails with `EPERM`, `GET /conntrack` correctly reports `partial: true` with every node in
  `failedNodes` and empty `items` — the exact fail-safe behavior the design calls for, never
  fabricated data. In production `docs/security.md` states vnproxd runs as root, so this specific
  failure mode should not occur there (flagged in `needs-hardware-validation.md` regardless, since
  it was never observed against an actual node). The e2e test was rewritten to assert this real,
  honest degradation end-to-end instead — a meaningful proof in its own right — while the
  fixture-row-rendering half of AC5 is fully covered without needing root by
  `internal/pvemock/conntrack_test.go`, `internal/host/fixture_test.go`,
  `internal/api/conntrack_test.go` (all three go through `FixtureReader`, never the real kernel
  path) and `ConntrackExplorer.test.tsx` (a seeded fixture set, no network at all — satisfies AC5's
  Vitest half literally).
- **Peer conntrack fetches are sequential, not concurrent**, inherited from
  `fetchClusterConntrack`'s straightforward per-peer loop (unlike `mergeClusterPage`'s more
  elaborate cursor-aware fan-out `GET /flows`/`GET /audit` share, which this route doesn't need
  since it has no pagination). Observed cost on this 3-node dev fixture with 2 unreachable peers:
  ~10s (2 × the peer client's 5s `DefaultRequestTimeout`). Correctness-neutral (the response is
  still correct, just slower than it could be) but worth flagging as a straightforward follow-up
  optimization (parallel `goroutine`+`sync.WaitGroup` fan-out) if a real cluster's peer-timeout
  cost in the common case (an unreachable peer, not a slow one) turns out to matter in practice.
- **`golangci-lint`'s `fieldalignment`/`package-comments` findings were fixed via
  `golangci-lint run --fix`** (struct field reordering for pointer-byte packing; a blank line
  inserted before four `package X` declarations whose leading file comment was otherwise being
  read as an undocumented package doc comment). No behavior change — struct literals in this
  codebase are always field-named, so declaration-order changes are invisible at every call site;
  confirmed by a full `go build ./... && go test ./...` pass after the fix.

## Bugs found and fixed (development-time, not part of the shipped defect surface)

- **`golangci-lint` findings** (see above) — caught and fixed via `--fix` before this report; `make
  check`'s lint stage is green.
- **The e2e test's original design assumed fixture-declared conntrack data would reach the
  browser** — see "Deviations" above. Not a code bug (the backend's `partial`/`failedNodes`
  behavior is exactly correct), but a genuine test-design error caught only by directly `curl`-ing
  the real running backend and reading `vnproxd`'s own request log during debugging, after several
  Playwright runs failed in ways that looked at first like a client-side navigation race. The
  actual navigation mechanism (`TopologyPage.tsx`'s `conntrackItemFor` → `navigate(path)`, the same
  pattern the pre-existing "Trace path" context-menu entry already uses) was never at fault; the
  test's own resilience additions (a same-URL reload fallback if the client-side route swap lags
  under load, and a retry-scoped canvas pan to clear the minimap-occlusion class of flake
  `simulator.spec.ts` already documents) are left in place as legitimate hardening against a
  genuinely loaded shared CI/dev machine, not as a workaround for a real product defect.
