## 1. What was built

### Go: mixed-version apply refusal (a gap this task's own deliverable surfaced)

`docs/architecture.md` §5 documents "a daemon refuses to coordinate changes
involving a peer with an incompatible schema version (upgrade prompt in
UI)", and `docs/api.md`'s stable error-code list already reserved
`peer_incompatible` — but nothing in `internal/change` actually called
`peer.Client.CheckCompatible` before dispatching apply steps to a peer.
Investigating T-606's "mixed-version refusal behavior verified in the
multi-daemon harness" deliverable surfaced this as a real, unfinished gap
(not a documentation nit), so it's fixed here rather than deferred:

- `internal/change/cluster_agent.go`: `PeerCompatibilityChecker` — an
  optional `NodeAgent` capability (`ClusterNodeAgent.CheckNodeCompatible`);
  local node always compatible, a peer is checked via
  `peer.Client.CheckCompatible`.
- `internal/change/apply.go`'s `beginApply`: a pre-flight gate, after
  `BuildPlan` and before any snapshot/mutation, refusing (new
  `ErrIncompatiblePeer`) only on a confirmed `peer.ErrPeerIncompatible` —
  deliberately **not** on a merely-unreachable peer, which is a different,
  already-handled failure mode (existing per-step apply/rollback machinery
  tolerates transient partitions; treating "down" the same as
  "incompatible" would make ordinary applies fragile against network
  blips, and broke an existing T-304 test on first attempt — see §3).
- `internal/api/changesets.go`: `writeApplyError` maps `ErrIncompatiblePeer`
  to the reserved `peer_incompatible` code, 409.
- Tests: `TestClusterNodeAgent_CheckNodeCompatible` (unit, three branches);
  `TestApply_RefusesWhenPeerProtocolIncompatible` /
  `TestApply_SucceedsWhenAllPeersCompatible` (new
  `internal/change/mixedversion_test.go`, reusing T-304's real three-daemon
  distributed harness — real `peer.Server`/`peer.Client` over loopback
  HTTP — with one peer swapped for a stub reporting a mismatched
  `protocolVersion`, the same technique `internal/peer`'s own
  `TestClient_CheckCompatible_VersionMismatch` uses).

### Go: migration tests from each prior schema version

`internal/store/migrate_fromeach_test.go`. This repo has cut no git tags
yet (`git tag -l` is empty), so "each prior *tagged* schema" is realized as
"each prior `schema_version` that has ever shipped" (0, 1, 2, against
latest 3 today) — tag-agnostic by construction, so it keeps working
unmodified as new migrations/tags are added. Each case freezes a database
at version V (applying only migrations 1..V — exactly what an older
`vnproxd` build left on disk), seeds representative rows in that version's
shape, runs the current build's full `migrate()` (what `apt install` does
on upgrade), and asserts: the DB lands on latest, every pre-existing row
survived untouched, and tables/columns only later migrations add are
present and usable. Also covers re-running `migrate()` on an
already-latest DB (idempotent — every subsequent `apt install`/daemon
restart).

### Go: `vnproxctl status` rich output

`docs/deployment.md`'s "Troubleshooting quick refs" documents `vnproxctl
status` reporting "local daemon, peer reachability, PVE API health,
collector ages" — the prior skeleton only implemented the local-daemon
check, with placeholder "available after T-301"/"T-104" lines (stale:
those tasks had since landed). `cmd/vnproxctl/status.go` now:

- Renders `GET /api/v1/health`'s existing `collectors` field (sorted,
  age/failure-count/last-error) instead of dropping it.
- `printPVEHealth`: probes the PVE API directly via `buildStatusPVEClient`
  (mirrors `cmd/vnproxd/collect.go`'s `buildCollectorPVEClient` exactly,
  including its documented dev/test ticket-auth escape hatch), reports
  reachability/latency/node count.
- `printPeerReachability`/`printPeerStatuses`: discovers cluster peers via
  PVE's own `/cluster/status` and probes each with `GET /api/peer/health` +
  `GET /api/peer/version`, flagging a protocol-version mismatch as
  `INCOMPATIBLE` — the same signal the change-engine gate above acts on.

None of the three additions fail the command on their own — an operator
running `status` to diagnose a broken node needs to see "PVE API
unreachable" as a line, not have the whole command abort.

`vnproxctl snapshots list/restore` and `rollback-now` were already fully
implemented (T-206's daemon-independent disaster-recovery path — direct
SQLite + file write + `ifreload` exec, no HTTP dependency) with existing

### Packaging: `vnprox-setup` — real PVE API token provisioning

Replaced the `TODO(T-606)` stub with real, idempotent `pveum`-driven
provisioning (docs/security.md's "one privileged internal identity ...
used exclusively for read polling"):

- Role `VnproxAuditor` (`Sys.Audit,VM.Audit,SDN.Audit` — read-only;
  created only if `pveum role list` doesn't already show it).
- User `vnprox@pve` + its `/`-scoped ACL grant (created/re-applied
  unconditionally — `pveum`'s own add/modify are themselves idempotent).
- Token `vnprox@pve!daemon`, created only if the local token file
  (`/etc/vnprox/keys/pve-token`) doesn't already exist *and* `pveum` itself
  doesn't already list one — a token's secret is returned by `pveum`
  exactly once at creation time, so a second creation attempt on an
  existing token is refused with clear operator guidance rather than
  silently invalidating it.
- `pve_try_create`: runs a `pveum ... add` command and treats "already
  exists" (pveum's own error text) as success — chosen over pre-parsing
  `pveum <resource> list`'s human-oriented table output, whose exact
  column layout isn't a contract this script should assume.
- Skips cleanly (clear log line, no error, no `set -e` abort) when `pveum`
  isn't on `PATH` — only a real PVE node has it.

### Packaging: `install.sh` — real multi-node SSH rollout + apt repo install

- **Step 3 (install the package):** now really installs from an apt repo
  (fetch+import the signing key, write
  `/etc/apt/sources.list.d/vnprox.list` with `signed-by`, `apt-get
  update && apt-get install vnprox`) when `--offline` isn't given, instead
  of unconditionally dying. `--apt-repo <url>` overrides the default
  (`https://get.vnprox.io/apt`).
- **Step 8 (remaining cluster nodes):** real SSH rollout, evaluated
  *per node* rather than all-or-nothing. A reachable node (`ssh
  -o BatchMode=yes root@<node> true` succeeds) gets scp+`apt-get install`
  (`--offline`) or the apt-repo flow, then a remote `vnprox-setup` run with
  this node's resolved port/lldp choice; an unreachable node falls back to
  printed per-node manual instructions — exactly matching
  `docs/deployment.md`'s documented "via SSH root ... or prints per-node
  instructions if SSH between nodes is unavailable."
- Fixed a latent bug in the existing `pvecm nodes` output parser (present
  since T-006, exposed by this task's own more-faithful test fixture): the
  original `awk 'NR>2 && NF{print $NF}'` took the coordinating node's own
  row's last field, which is the literal string `(local)` (pvecm suffixes
  the local node's row with it), not the node name. Rewritten to match
  data rows by shape (`$1`/`$2` both integers — nodeid, votes) rather than
  a fixed header-line count, and to strip the `(local)` suffix before
  taking the last field.

### Packaging: `postrm` — last-node cluster-shared-state purge prompt

`docs/deployment.md`: "The PVE token and `/etc/pve/vnprox/` are removed on
purge of the last node (prompted)." Both are cluster-shared (pmxcfs-
replicated / PVE user.cfg), not this-node-only data, so removing them
unconditionally on *any* node's purge would break every other
still-installed node the moment the first one is purged. `postrm` now
prompts interactively against `/dev/tty` (no debconf dependency for one
yes/no question) on `purge`, only when there's something cluster-shared to
consider removing at all (`/etc/pve/vnprox` exists or `pveum` is present);
with no controlling tty (unattended/scripted purge, CI), the safe default
is to leave cluster-wide state untouched.

### Packaging: apt repository tooling

- `packaging/build-apt-repo.sh`: assembles a signed flat apt repo
  (`pool/`, `dists/stable/{Release,Release.gpg,InRelease,Packages(.gz)}`,
  exported keyring) from built `.deb`s via `dpkg-scanpackages` + `gpg`.
  Production signing key via `VNPROX_SIGNING_KEY_FILE`; transparent
  ephemeral-key fallback for dev/test when unset.
- `packaging/apt-repo.md`: repo layout, signing-key story (production
  secret vs. ephemeral dev key), client configuration.
- `.github/workflows/release.yml`: on a `vX.Y.Z` tag (or manual dispatch),
  builds `.deb` for amd64+arm64 (`make build` once for the real frontend,
  then `make -C packaging deb ARCH=<arch>` per arch), signs the apt repo
  (`APT_SIGNING_KEY` secret, or the ephemeral fallback), uploads both as
  artifacts, and cuts a GitHub release with an auto-generated
  since-previous-tag changelog. The "publish to get.vnprox.io" step is a
  documented, gated placeholder (no such host exists — see §4).

Fix: removed the four fragile log-line assertions (and the analogous "cluster secret already present" line-grep after the sha256 comparison, same reasoning) in favor of the authoritative checks already present — a strictly stronger proof the rollout ran and completed than any log line, and immune to this multiplexing flake. `packaging/test/cluster-ssh.sh`'s own comments now document this precedent for both boundaries it was observed at.

## 3. Deviations from the task card (with reasons)

1. **Mixed-version refusal fix scoped narrowly to confirmed incompatibility.**
   The first implementation treated any `CheckNodeCompatible` error
   (including a merely-unreachable peer) as grounds to refuse the whole
   apply pre-flight. This broke an existing T-304 test
   (`TestThreeDaemon_Property_EveryNodeConvergesNeverMixed/mid_apply_failure/pve3_unreachable_at_reload`,
   which models a peer going unreachable *during* apply and expects the
   existing per-step rollback machinery to handle it) — correctly, because
   "peer down right now" and "peer running an incompatible protocol
   version" are different failure modes with different documented handling.
   Narrowed to `errors.Is(err, peer.ErrPeerIncompatible)` specifically;
   full suite green afterward.
2. **"Previous tagged schema" / "upgrade from previous tag" realized without
   real tags.** This repo has cut no release tags (`git tag -l` empty).
   Both the migration test harness and `packaging/test/upgrade.sh` are
   built to be meaningful today (parameterized over schema_version /
   built from two synthetic version strings of the current tree,
   respectively) and to keep working unmodified once real tags exist —
   documented explicitly in both files' headers rather than silently
   assumed.
3. **PBS-present port-conflict trigger not literally reproduced in
   `cluster-ssh.sh`.** AC3 says "PBS package present → prompt → alternate
   port". `proxmox-backup-server` isn't installable outside PVE's own
   repos, and faking `dpkg-query`'s output system-wide (shadowing it for
   every caller, including apt's own internal use) was judged too invasive
   for a throwaway test container. `cluster-ssh.sh` reuses the same
   occupied-port trigger `port-conflict.sh` already uses (which exercises
   the identical downstream conflict-handling branch `pbs_installed()`
   would) to prove the *cluster-wide consistency* half of AC3 (every node
   ends up on the same fallback port); the PBS-detection code path itself
   (`pbs_installed()`, a two-line `dpkg-query` wrapper) is exercised
   nowhere new by this task — it was already correct and untouched.
4. **Container networking uses `--network=host` + per-node SSH ports, not
   per-container addresses.** This sandbox's rootless podman has no
   `pasta` binary, so a user-defined bridge network (real per-container
   IPs/hostnames) isn't available. `cluster-ssh.sh` instead runs all three
   containers with `--network=host`, one sshd per simulated node on a
   distinct port (2201/2202/2203), with SSH client host-aliases on the
   coordinator. This is an environment constraint (documented in the
   script's header), not a design choice — nothing under test (cluster
   detection, SSH rollout, `vnprox-setup`) depends on which addressing
   scheme reaches a "node", and a CI runner with normal bridge networking
   would exercise the identical script unmodified with real container
   networking instead.

  columns, `acl modify --delete` syntax, `user token add --output-format
  json` field names) against a real PVE node's `user.cfg`. `vnprox-setup`'s
  `pve_try_create` was written defensively (matches on pveum's own
  "already exists" error text rather than parsing list-table columns) to
  minimize this risk, and `postrm`'s cleanup calls are all best-effort
  (`|| true`), but the exact commands have only been exercised against
  `packaging/test/fakepveum`, a deliberately narrow stand-in — not a real
  `pveum` binary.
- **Real inter-node root SSH the way `pvecm` cluster joins establish it.**
  `cluster-ssh.sh` proves the *installer's* SSH-rollout logic against real
  sshd/ssh binaries and real keys; it does not (cannot, in this sandbox)
  prove that a real multi-node PVE cluster's pre-existing root-SSH trust
  matches what `install.sh` assumes.
- **Real pmxcfs replication of `/etc/pve/vnprox/cluster.secret`.**
  `cluster-ssh.sh`'s shared-podman-volume stand-in proves the *daemon-side*
  logic (generate once, treat an existing file as already-replicated) is
  correct; it does not exercise real pmxcfs.
- **A real production `APT_SIGNING_KEY` secret and an actual
  `get.vnprox.io` host.** `release.yml`'s signing/publish steps are real
  code, gated to a documented no-op (ephemeral key; a `TODO(infra)`
  placeholder step for the publish-to-host leg) when those secrets aren't
  configured — which they aren't, in this repository, today.
- **A live PVE cluster's actual `/cluster/status`/`/access/ticket` shapes**
  for `vnproxctl status`'s new PVE-health/peer-reachability checks beyond
  what `internal/pvemock` fixtures already cover (pvemock's own
  documented gap: no PVE API-token auth support, only ticket auth — see
  `buildStatusPVEClient`'s dev/test escape hatch, the same one the
  collectors already use for this exact reason).

  (`cluster_agent.go`) is the pattern to extend if a future task needs

  migration `0004_*.sql` needs a new `seedAtVersion3`/`assertVersion3Seeded`

  building its `.deb` as "old" — the script's header says exactly this.

  two real secrets exist: `APT_SIGNING_KEY` (repo secret, ASCII-armored
