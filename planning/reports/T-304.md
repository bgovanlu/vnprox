## 1. What was built

This extends T-205's single-coordinator commit-confirm safety guarantee to
multi-node applies, per `docs/architecture.md` §4 and
`docs/features/change-management.md` §4 ("each node arms its own local timer
at step start — no cross-node dependency for safety"). All new code builds
on T-301 (`internal/peer`'s client/server) and T-205 (`internal/change`'s
apply engine); nothing from either is duplicated.

### `internal/store` (new)

| File | Purpose |
|---|---|
| `migrations/0003_node_timers.sql` | `node_timers` table: a node's own record of a rollback deadline it was asked to arm for a changeset it may know nothing else about (deliberately independent of `changesets` — a peer node has no `changesets` row for another daemon's coordinated changeset). |
| `nodetimers.go` | `NodeTimerRepo`: `Arm` (insert-or-replace), `Resolve` (move to a terminal status, idempotent on a missing row), `Get`, `ListByStatus` (startup re-arm + reconciliation scans). |

### `internal/peer` (extends T-301's surface)

| File | Purpose |
|---|---|
| `timer.go` | `TimerAgent` interface (`ArmTimer`/`CancelTimer`/`TimerStatus`), `TimerRecord`/`TimerStatus` wire types, `ErrTimerNotFound`. |
| `server.go` | Three new routes: `POST /api/peer/timer/{arm,cancel}`, `GET /api/peer/timer/status`; `HostWriter` gained `DiscardStaged` (see §3.1) and `POST /api/peer/host/discard-staged`. `ServerOptions.Timers` (nil-safe, 503 when unconfigured, mirroring `Reader`/`Writer`). |
| `client.go` | `Client.{ArmTimer,CancelTimer,TimerStatus,DiscardStaged}`. |
| `version.go` | `ProtocolVersion` bumped 1→2 (see §3.2). |

### `internal/change` (T-304's core)

| File | Purpose |
|---|---|
| `localtimer.go` | `LocalTimerAgent`: the node-side protocol implementation — persists an armed timer to `node_timers`, arms a real `TimerFunc`, and on fire (uncancelled) restores the node via `NodeAgent.StageInterfaces`+`ReloadInterfaces` and records the outcome. `ArmPendingOnStartup` (restart survival, mirroring T-205's `ArmPendingRollbacks`) and `StopTimers`. Implements `peer.TimerAgent` structurally — has no dependency on `Service`, so it keeps working on a node that isn't coordinating anything. |
| `cluster_agent.go` | `ClusterNodeAgent` (implements `NodeAgent`) and `ClusterTimerAgent` (implements the new `NodeTimerAgent`): both route a call to the local implementation when `node == localNode()`, or through `*peer.Client` otherwise — the "single value abstracting local and peer nodes" `apply_seams.go` had documented as T-304's scope. `PeerLocator` (`DiscoveringPeerLocator`, backed by `peer.Client.Peers`/PVE cluster-status; `StaticPeerLocator` for tests) resolves node→`peer.Peer`. |
| `apply_seams.go` | New `NodeTimerAgent` interface (`Config.Timers`, optional — nil falls back to T-205's original single coordinator-side timer only, so every existing T-205 test is untouched). |
| `apply_log.go` | `ApplyLog.NodeTimers []NodeTimerLog`, `NodeTimerStatus` (`armed\|cancelled\|rolled_back\|rollback_failed\|unknown`). |
| `apply.go` | `Apply` computes the commit-confirm deadline once, up front, and threads it through the executor and into `finishAwaitingConfirm` (which records a `NodeTimerLog` entry per node when `Timers` is configured); `Confirm` fans out `CancelTimer` to every affected node (concurrently, best-effort — see §4); `doRollbackLocked`/`autoRollback` use the new distributed-aware restore when `Timers` is configured. |
| `apply_exec.go` | `execStep`'s `StepReload` case arms the node's local timer (via `NodeTimerAgent`) *before* the reload call — an arm failure fails the step (and thus never reloads), which is the "peer dies before its steps start" abort path. |
| `apply_distributed.go` | `cancelNodeTimers` (concurrent fan-out), `restoreAllDistributed` (peer-aware: `peer.ErrPeerUnreachable` doesn't count as a hard rollback failure — that node's own timer is the safety net — vs. a genuine reachable-but-failed restore, which still routes to `StatusFailed` exactly as T-205 defined), `mergeNodeTimerLogs`, `updateApplyLog`, and `Service.Reconcile` (coordinator-side reconciliation on reconnect: resolves `unknown` entries by querying each such node's `TimerStatus` directly; never retroactively changes a changeset's own terminal `Status` — only completes the per-node detail in `ApplyLog.NodeTimers`, audited as `changeset.reconcile`). |

### `cmd/vnproxd/server.go`

Wires `store.NewNodeTimerRepo` + `change.NewLocalTimerAgent` (armed on
startup, stopped on shutdown, same pattern as `changeSvc`'s own timers); a
dedicated peer-discovery `*pve.Client` (via the existing

`hostNodeAgent`; `peer.ServerOptions.Timers: localTimers`.

## 2. What was tested and how

A three-daemon harness (`internal/change/distributed_test.go`): pve1
coordinates via a real `change.Service`; pve2/pve3 are independent daemons —
each with its own SQLite `node_timers` DB, its own `LocalTimerAgent` with an
independently-fireable `TimerFunc`, and its own `peer.Server` reached over a
real `httptest.Server` + HMAC-signed `peer.Client`, sharing one
`pvemock` three-node cluster for the PVE-facing reload calls. A
`partitionableTransport` (custom `http.RoundTripper`) simulates and heals a
coordinator↔node partition deterministically; every daemon shares one
auto-ticking fake clock (see §4's replay-cache finding for why it ticks
rather than stays frozen).

**All five acceptance criteria, independently verified:**

1. `TestThreeDaemon_ApplyConfirm_CancelsAllLocalTimers` — apply → confirm
   cancels all three nodes' timers, asserted against each node's own
   `node_timers` DB row *and* the coordinator's persisted `ApplyLog.NodeTimers`.
2. `TestThreeDaemon_Partition_IndependentLocalRollback_ThenReconcile` — cut
   coordinator↔pve3 after all three committed, no confirm: pve1/pve2 roll
   back via the coordinator's deadline; pve3 is left `unknown` in the log
   and independently self-restores at its own deadline; `Reconcile` (after
   healing) resolves pve3's entry to `rolled_back` without altering the
   changeset's own `StatusRolledBack`.
3. `TestThreeDaemon_PeerDiesBeforeSteps_AbortRollsBackCompleted` — pve3's
   stage step fails outright: pve1/pve2 (completed) roll back, changeset
   `failed`, pve3 stays byte-identical to its pre-apply content and never
   even armed a timer.
4. `TestThreeDaemon_CoordinatorDies_PeersStillRollBackLocally` +
   `TestThreeDaemon_PeerRestart_ReArmsFromDB` — pve2/pve3 self-restore with
   zero further coordinator involvement after apply; a peer's own restart
   (`ArmPendingOnStartup` over a fresh `LocalTimerAgent`/fresh in-process
   timer map, deadline already past) self-heals immediately.
5. `TestThreeDaemon_Property_EveryNodeConvergesNeverMixed` — a property
   checked across 11 injected failure points: mid-apply (each of the 6
   stage/reload steps failing, plus a true `peer.ErrPeerUnreachable` at
   reload) and post-apply (confirm, timeout, partition-then-self-restore,
   and the "confirm succeeds but one node's cancel can't be delivered"
   edge case). For every case, every node's final committed content is
   asserted to be *exactly* its pre-apply or its new content — never
   anything else.

Additional unit coverage: `LocalTimerAgent` in isolation (arm/fire/cancel/
re-arm/restart-survival/reload-failure→`rollback_failed`, no peer/pvemock
dependency — `localtimer_test.go`), `ClusterNodeAgent`/`ClusterTimerAgent`'s
local-vs-remote-vs-unknown-node routing (`cluster_agent_test.go`),
`DiscoveringPeerLocator` against a fake PVE cluster-status source, the new
peer routes' 503/404/replay/idempotency behavior
(`internal/peer/timer_test.go`), and the `node_timers` repo
(`internal/store/nodetimers_test.go`).

## 3. Deviations from the task card (with reasons)

1. **`peer.HostWriter` gained a fourth method, `DiscardStaged`, and a new
   route `POST /api/peer/host/discard-staged`.** The card names arm/cancel/
   reconcile-style endpoints as the expected new peer surface; this one is
   different but necessary: a remote node whose *stage* step succeeded but
   whose reload step is the one that fails needs its staged-but-unapplied
   file discarded during mid-apply rollback, the exact same "not committed"
   branch T-205's `undoNode` already has for the local case. CLAUDE.md's
   "everything is cluster-aware" rule applies to `NodeAgent`'s fourth method
   same as the other three. Small, additive, mirrors the existing
   stage/reload/restore pattern exactly.
2. **Peer `ProtocolVersion` bumped 1→2.** A v1 peer cannot serve
   `discard-staged` or `timer/*` — `Client.CheckCompatible`'s existing
   version-skew refusal (`docs/architecture.md` §5) needs this bump so a
   coordinator refuses to route multi-node steps to a stale peer rather than
   discovering the gap as a 404 mid-apply.
3. **`computeStagedFile` no longer re-reads a node's interfaces file itself**
   — it now takes the pre-apply content the executor already captured for
   that node. It was previously a second `ReadInterfaces` call per node
   within the same `Apply()`. That was harmless when `NodeAgent` was always
   local (T-205); routed over the peer wire, two identical signed GETs to
   the same node within the same second collide in `internal/peer`'s
   replay cache (see the residual-risk item below), and it was simply a
   redundant read regardless. This is a small, self-contained fix inside
   `internal/change`; nothing in `internal/peer` was touched.
4. **`Service.Config.Timers` is optional (nil-safe).** Every existing T-205
   test, and any Service that doesn't wire the new local-timer protocol,
   is completely unaffected — `Apply`/`Confirm`/`Rollback` fall back to
   exactly T-205's original single-coordinator-timer behavior. This was a
   deliberate design choice to keep the large existing T-205 suite as a
   regression guard with zero modification (confirmed: it still passes
   unchanged).
5. **`ClusterNodeAgent`/`ClusterTimerAgent`'s `localNode` parameter is a
   `func() string`, not a fixed string.** Production wiring only learns its
   own node name from the collector's first successful PVE cluster-status
   poll (`internal/collect.Collector.Status().LocalNode`), which is empty
   for a window after daemon startup; a value captured once at construction
   would stay wrong forever.

No new third-party dependencies were added.

## 4. Residual risk / honesty contract (READ BEFORE DEPENDENT WORK)

**Proven (three-daemon harness, high confidence):** the full arm→reload,
confirm→cancel, timeout→self-restore, and abort→rollback-completed flows;
restart survival of a *peer's* own timer (not just the coordinator's, which
T-205 already proved); the never-a-mixed-state property across 11 injected
failure points including a genuine `peer.ErrPeerUnreachable` path (not just
seam-level fault injection).

**Known, documented gaps — not fixed here, flagged for the next reviewer:**

1. **A confirmed changeset can still have a node roll itself back.** If
   `Confirm`'s cancellation fan-out can't reach a node (that node is
   partitioned at the exact moment of confirm), that node's timer is still
   armed and will self-restore at its deadline even though the changeset
   reads `committed`. This is inherent to a local-timer safety design under
   partition (there is no way to guarantee both "confirm always wins" and
   "no node's safety depends on connectivity" simultaneously) and is
   exercised directly by the property test's
   `confirm_but_one_node_uncancellable` case, which proves the per-node
   property still holds (that node cleanly reaches one of its two valid
   states) even though the changeset-level label and that one node's actual
   state can disagree. `Reconcile` would surface this disagreement (the
   node's `TimerStatus` would read `rolled_back` against a `committed`
   changeset) but does not attempt to resolve or alert on it — a natural
   T-305/audit-surface follow-up.
2. **Whole-second HMAC replay-cache collisions** — see
   `planning/reports/needs-hardware-validation.md`'s new T-304 section.
   Discovered via this task's own testing; worked around in the test harness
   with an auto-ticking clock (which real wall-clock time also provides);
   unverified how often two genuinely back-to-back peer calls to the same
   node land in the same second on real hardware. The proper fix, if needed,
   is in `internal/peer`'s signing/replay scheme, explicitly out of this
   task's scope.
3. **`Reconcile` is not wired into a background loop.** It's a plain
   `Service` method, exercised directly by tests and ready to call from
   `cmd/vnproxd` on a periodic loop (mirroring the existing snapshot-retention
   loop pattern) or an explicit API trigger — neither wiring was added since
   the card doesn't specify a cadence and no API route was requested; flagged
   for whichever task owns the audit/reconciliation UI surface.
4. **Everything T-205's own residual-risk list already flagged still
   applies** (hostNodeAgent never touched a real ifupdown2, SDN-apply
   rollback not implemented, guest/SDN-write/fw/ipam ops still
   unexecutable) — T-304 does not touch or change any of that.

## 5. Anything the next agent must know

- `internal/change`'s `NodeAgent`/`NodeTimerAgent` seams are now genuinely
  cluster-aware in production (`cmd/vnproxd`'s `clusterNodes`/`clusterTimers`);
  a single-node deployment (zero PVE peers) behaves identically to before —
  `ClusterNodeAgent`'s local branch is exactly T-205's `hostNodeAgent` path.
- `ApplyLog.NodeTimers` is new, additive JSON on `apply_log_json` — any UI
  or audit surface consuming that field should treat a missing/empty array
  as "single-node coordinator timer only, T-304's protocol wasn't in play"
  rather than an error.
- `docs/api.md`'s Peer API section and `planning/reports/needs-hardware-validation.md`
  were updated; `docs/features/change-management.md` §4 needed no changes —
  the delivered protocol matches its existing wording.
