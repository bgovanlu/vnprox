# T-401 · SDN read: cockpit tree, map overlay, pending diff

## 1. What was built

Full read-only visibility into the SDN stack, per docs/features/sdn.md §1.

**Backend**

- **`internal/pvemock`**: a `?running=1` last-applied view alongside the
  existing default (staged, pending-merged) view on
  `GET /cluster/sdn/{zones,vnets,vnets/{v}/subnets}`, mirroring real PVE's
  own running-vs-pending query convention. Derived automatically per
  object from its `Pending` marker (`new` → absent from the running view,
  `deleted` → still present until an actual apply, `""` → identical) except
  for `changed`, where a fixture author can declare an explicit `running:`
  override (the pre-edit value) — otherwise a `changed` object has no
  meaningful diff to show. `PUT /cluster/sdn` (apply) now re-syncs the
  running maps from the just-applied staged maps.
- **`internal/pve`**: `ListSDNZonesRunning` / `ListSDNVnetsRunning` /
  `ListSDNSubnetsRunning` wrap the same query param.
- **`internal/inventory`**: `SdnZone`/`SdnVnet`/`SdnSubnet` gain a
  `Pending` field (same pattern T-305 gave `PhysNic`/`Bond`/`Bridge`/
  `VlanIface`), wired through `FromPVESDN`, surfaced as a topology badge.
- **`internal/inventory/link.go`**: new `EdgeVtepPeer` edges — for
  vxlan/evpn zones, every pair of the zone's peer addresses that resolves
  to an underlay bridge gets a full-mesh edge, badged with the zone id and
  VNI MTU (docs/features/sdn.md §1: "EVPN/VXLAN zones draw the VTEP mesh
  with tunnel endpoints and MTU annotations"). The existing `EdgeRealizes`
  (VNet plane → realizing bridges) needed no changes — it already worked
  for simple/vlan/qinq zones (`zone.Bridge` set); vxlan/evpn zones don't
  use a shared zone-wide bridge in real PVE, so their map presence is the
  VTEP mesh instead, matching the feature spec's own wording.
- **`internal/topology/project.go`**: `sdnZoneStatus` now distinguishes a
  node reporting `error` (paints the zone `down`/red) from `pending`
  (`degraded`/amber) instead of collapsing every non-ok status to the same
  amber — acceptance criterion 4.
- **New `internal/sdn` package**: `Service.Tree(ctx)` builds
  `GET /sdn`'s zone → vnet → subnet tree with per-node status and, for any
  staged-but-unapplied edit, a `PendingDiff` (`state` + exactly the changed
  top-level fields for `changed`, staged-only for `new`, running-still-
  present for `deleted`; nothing at all — the field is omitted — for an
  in-sync object). It reads PVE directly and live on every request rather
  than the poll-cached inventory graph, on the same "exact live state"
  precedent T-208's raw-interfaces editor set — a diff view must never be
  stale relative to what an apply would actually do.
- **`internal/api/sdn.go`**: mounts `GET /sdn` behind the `sdnRead`
  capability (not `netRead` — SDN has its own PVE privilege, `SDN.Audit`).
- **`cmd/vnproxd`**: wires `internal/sdn.Service` to the collectors' own
  read-only PVE client; `setupCollect` now also returns that client
  (mirroring `peerClient`'s established "returned for reuse" pattern).
- **`testdata/clusters/evpn-lab.yaml`**: extended from one EVPN zone to
  all five real PVE zone types (simple, vlan, qinq, vxlan, evpn), with a
  deliberately mixed per-node status (`simplez`'s bridge exists on pve1/
  pve2 but not pve3 → `error` there) and a staged-but-unapplied `changed`
  zone (`vlanz`, mtu 1600 staged vs 1500 running) plus a staged `new` vnet
  (`qinqz`'s `vnet-qinq1`).

**Frontend** — new `web/src/sdn` feature module:

- `SdnPage.tsx`: zone → vnet → subnet tree (status dot + pending badge per
  row) with a detail panel — fields, per-node status list, and either
  `PendingDiffView` (staged/running side-by-side for each changed field)
  or an "In sync" badge.
- `status.ts` / `tree.ts`: pure, Vitest-covered logic split out of the
  component — status-vocabulary mapping (mirrors the backend's
  `sdnZoneStatus` exactly, so tree and map never disagree) and
  selection/diff-value formatting.
- `web/src/api/sdn.ts` + `web/src/sdn/queries.ts`: the fetch wrapper and
  TanStack Query hook, following the existing per-feature module
  convention (`web/src/fdb`-style, `web/src/api/types.ts` extended with
  the full `SdnTree`/`SdnZone`/`SdnVnet`/`SdnSubnet`/`PendingDiff` shapes).
- `mapOverlay.test.ts`: verifies the topology map's SDN overlay against a
  **captured real fixture** — `evpn-lab.yaml` run through the actual
  pvemock → collect → `inventory.Graph` → `topology.Project` pipeline (the
  same capture process `topology/threeNodeVlan.render.test.tsx`'s own
  fixture used; captured via a one-off temporary Go test, deleted after
  the JSON was written).

## 3. Deviations / scope notes (flagged, not silent)

- **`GET /sdn`'s exact response shape and the `?running=1` query param are
  additions beyond docs/api.md's one-line contract** (`"zones → vnets →
  subnets tree + per-node apply/health status"`). Both are documented in
  docs/api.md and docs/data-model.md in this same change, per
  docs/development.md's definition-of-done #4 — this is the smallest
  reasonable extension consistent with the pattern T-302/T-303/T-306
  already established for undocumented-but-necessary route/field
  additions.
- **`internal/sdn.Service` bypasses the poll-cached inventory graph and
  reads PVE live, per request.** Every other GET route in this codebase
  (topology, drift, fdb, lldp) renders the collector's already-polled
  inventory snapshot. SDN's pending diff is different: it's fundamentally
  a "compare two live PVE views" operation, and rendering it against a
  snapshot that might be one poll interval stale risks showing a diff that
  no longer matches what an actual apply would do. I judged this
  correctness concern more important than avoiding the extra PVE round
  trips (2 zone-tree fetches + 2 vnet-tree fetches + one zone-status call
  per zone + one subnet-pair fetch per vnet, on each `GET /sdn` request) —
  acceptable for a cockpit page that isn't hit every second, but flagging
  it as a design call in case a future task wants to move this onto the
  poll cycle instead (would need the inventory model extended with a
  parallel "running" state, a bigger change).
- **VNet planes vs. VTEP mesh is an either/or per zone type, not both.**
  Re-reading docs/features/sdn.md §1 closely: "the topology map's overlay
  layer shows each VNet as a colored plane connecting the bridges that
  realize it across nodes; EVPN/VXLAN zones draw the VTEP mesh ... "
  reads as two distinct renderings for two distinct zone families, not a
  VNet plane *plus* a VTEP mesh for every zone. `EdgeRealizes` (already
  existed, unmodified) covers the plane for simple/vlan/qinq zones (which
  have a real, shared `zone.Bridge`); the new `EdgeVtepPeer` mesh covers
  vxlan/evpn zones, which in real PVE realize each VNet as a per-node
  bridge with no shared zone-wide bridge name for `EdgeRealizes` to match
  against. I did not fabricate synthetic per-VNet bridges in the fixture
  to force a `realizes` edge for vxlan/evpn zones — that would mean
  inventing network state `pve-network`/`host-netlink` never actually
  reported, contradicting "Proxmox is the source of truth."
- **`internal/sdn`'s `PendingDiff.ChangedFields` is a plain top-level JSON
  field diff** (marshal both objects, compare keys), not a structural/
  semantic diff (no special handling for e.g. a reordered-but-equal
  `nodes` list, though field order stability isn't a concern here since
  both sides come from the same PVE object shape). Good enough for the
  small, flat objects zones/vnets/subnets are; would need revisiting if a
  future SDN entity grows deeply nested fields.
- **No cluster peer fan-out for `GET /sdn`.** SDN config is cluster-scoped
  PVE data (replicated via pmxcfs) — the local node's PVE API already has
  the complete view regardless of which node's vnproxd the browser hit, so
  (unlike `GET /audit`/`GET /snapshots`) there's nothing to fan out to.
  Documented explicitly in the package doc comment so it doesn't read as
  an oversight.
- **Zone-type-specific fields not otherwise used by pvemock/PVE's zone
  shape** (e.g. QinQ's inner/outer VLAN range, distinct from the plain
  `tag` field `SDNVnetSpec` already had) were not added — out of scope for
  a read-only task; the existing `SDNZoneSpec`/`SDNVnetSpec` field set
  (already present before this task, from the op-vocabulary work) was
  sufficient to model all five zone types for tree/status/diff purposes.

## 4. Notes for the next agent

- **T-402 (SDN ops & apply)**: the `sdn.*` op params (`SdnZoneCreateParams`
  etc.) already existed in `internal/change/params_sdn.go` before this
  task — not touched here, this task is read-only. `internal/sdn.Service`
  is a pure read view; T-402's apply orchestration should NOT route
  through it for writes (writes stay in `internal/change` exclusively per
  the change-engine safety guarantee) — `internal/sdn` exists only to
  render `GET /sdn`.
- **`internal/pvemock`'s new `Running` override field** on
  `SDNZoneSpec`/`SDNVnetSpec`/`SDNSubnetSpec` is fixture-authoring-only
  (`json:"-"`, never serialized) — a future fixture that wants a
  meaningful "changed" pending diff needs to declare it explicitly (see
  `evpn-lab.yaml`'s `vlanz` zone for the pattern); without it, a `changed`
  object's diff still renders (`state: "changed"`) but with an empty
  `changedFields` (running defaults to identical-to-staged).
- **T-403 (EVPN/BGP observability, `GET /sdn/evpn/status`)** is a
  distinct route this task does not implement (FRR/`vtysh` reads,
  peering matrix) — `internal/sdn` only covers the zone/vnet/subnet tree.
- **Zone wizards (docs/features/sdn.md §2)** and the SDN editors UI are
  T-402/T-403's job; `SdnPage` is read-only by design (no create/edit
  affordances) for this task.
- **Needs hardware validation**: the `?running=1` query param convention
  is my own design (documented as such in docs/api.md), matching real
  PVE's actual running-vs-pending distinction in spirit but not verified
  against a live cluster's exact query-param semantics — worth a hardware
  check before this ships, in case real PVE's parameter name/semantics
  differ from what I assumed.
