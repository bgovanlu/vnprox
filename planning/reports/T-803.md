## What was built

Five new health checks in `internal/findings` (docs/features/monitoring.md §5, all
`source: "health"`, all `fixable: false`, all with a `docsLink`):

- **`vxlan_underlay_mtu`** (`health_vxlanmtu.go`) — a vxlan/evpn `SdnZone`'s configured MTU vs. the
  *observed* underlay path MTU (minimum effective MTU among the member node's `PhysNic`s), reusing
  `internal/change.VxlanOverhead` (newly exported alias for the existing unexported
  `vxlanOverhead` constant in `validate_sdn.go` — same math, no duplicated literal). Standard
  hysteresis (2 cycles each way). Does **not** re-implement plain L2 NIC→bond→bridge MTU
  asymmetry — that stays `drift.CheckMTUConsistency`'s job, unchanged, per the card's explicit
  scoping note.
- **`orphan_vnet`** (`health_orphanvnet.go`) — an `SdnVnet` whose `Zone` names no known `SdnZone`.
  Hysteresis-exempt (structural).
- **`evpn_gw_inconsistency`** (`health_evpngw.go`) — an EVPN zone's anycast subnet gateway present
  on some member nodes' realized VNet bridge (matched by bridge name == vnet ID, mirroring how
  guest NICs attach to VNets by name in the existing fixtures) and absent on others. Reuses T-801's
  `internal/xnode.BridgesByName` cross-node fold for the same-named-bridge grouping — no second
  grouping helper written. Hysteresis-exempt (structural). **Needs hardware validation.**
- **`corosync_link_degraded`** (`health_corosync.go`) — a corosync ring reporting faulty via the
  new `host.Reader.CorosyncStatus` capability. Fed through an explicit `CorosyncProvider` seam
  (mirrors `health_service.go`'s `OnServices`-style ingestion, since a ring's live status has no
  inventory.Ref/map-entity slot). Standard hysteresis (2 cycles each way). **Needs hardware
  validation; scope-limited, see below.**
- **`trunk_unused_vlans`** (`health_trunkvlans.go`, informational, `severity: info`) — a VLAN-aware
  bridge's trunked `Vids` containing a VID no `GuestNic.EffectiveVid` on it currently uses. Never
  auto-narrows the trunk. Hysteresis-exempt (structural).

New `internal/host.Reader` capability (real + fixture, per the card):

- `CorosyncStatus(ctx, node) ([]byte, error)` — real implementation shells out to
  `corosync-cfgtool -s` (`netlink_linux.go`), non-Linux stub in `netlink_other.go`.
- `host.ParseCorosyncStatus` (`corosync.go`) — tolerant text parser for `corosync-cfgtool -s`'s
  "RING ID n / id / status" shape; a ring is `Faulty` unless its status text contains "no faults"
  (case-insensitive). `host.RingStatus` type, `host.ErrCorosyncUnavailable` sentinel (mirrors
  `ErrFRRUnavailable`'s graceful-degradation convention for a node with no corosync at all).
- `internal/pvemock`: `HostReader.CorosyncStatus`, `NodeSpec.Corosync`/`CorosyncSpec`/`RingSpec`
  fixture fields, `corosync_render.go` (renders fixture data through the real parser's shape),
  `ErrCorosyncUnavailable` sentinel.
- `internal/host/fixture.go`: `FixtureReader.CorosyncStatus` delegates to pvemock, mapping its
  sentinel onto `host.ErrCorosyncUnavailable`.

Adding a method to `host.Reader` is a structural-interface change, so every existing implementer
needed a `CorosyncStatus` stub to keep compiling: `internal/change/apply.go`'s `nodeAgentReader`,
and test fakes in `internal/change/distributed_test.go`, `internal/collect/clusterharness_test.go`,
`internal/peer/testhelpers_test.go`.

Wiring: `findings.Engine.Config.Corosync` (new field) → `cmd/vnproxd/findings.go`'s new
`corosyncStatusAdapter` (reuses the existing `realHost`/`localNode` closures already built for
`dhcpSvc`/`neighborSvc`) → `setupFindings`'s new parameter → `server.go`'s call site.

**Deliberate scope decision, flagged per CLAUDE.md's "if blocked, flag it" and the "everything is
cluster-aware" ground rule**: `corosyncStatusAdapter` reports only the *local* node's ring status
today — `host.Real.CorosyncStatus`, like every other `Real` method, only ever serves its own node,
and fanning this out across peers the way `Services`/`Links` already do would need a new peer API
route (`internal/peer.Client`/`Server` method) that T-803's card deliverables did not list (only
"a new `internal/host.Reader` capability ... real + fixture implementations"). Rather than either
skip cluster-awareness silently or unilaterally expand into `internal/peer` under time pressure,
I built the check itself fully cluster-shaped and well-tested (`CorosyncProvider` returns
`map[string][]host.RingStatus` for arbitrary node sets) and left the production adapter
local-node-only with the gap documented in three places: this report, the adapter's own doc
comment, and docs/features/monitoring.md §5's new "Scope note". A multi-node cluster today only
ever sees the daemon's own node's corosync health through this check.

  healthy, pve3's ring 1 deliberately `faulty: true` (`corosync_link_degraded`'s firing case).

  the healthy case (9166 mtu over a 9216 underlay, exact fit).

**`orphan_vnet` could not be fixture-extended the same way**: `pvemock.LoadFixture` enforces
zone-reference integrity for `sdn.vnets` at load time (confirmed by trying — it rejected a vnet
naming a nonexistent zone with `ErrFixtureInvalid`), so the check's own scenario (a vnet whose
zone was deleted out from under it — a raw-API/race shape, not something a validated static
fixture can represent) is only exercisable via a synthetic graph, which is exactly what
`health_orphanvnet_test.go` does. Noted in a comment in `evpn-lab.yaml` at the point I'd
originally tried to add it.

**Primary test coverage is synthetic-graph-based** (`inventory.Graph.ApplyPoll` built directly in
`internal/findings/health_*_test.go`), matching every sibling `health_*.go` check's own existing
test convention in this package (`health_bondslave_test.go`/`health_carrier_test.go`/
`health_mgmtpath_test.go` etc. — none of them load a YAML fixture through the full pvemock
pipeline either; `internal/findings/mtupath_test.go`'s doc comment confirms this is the
established pattern, not a shortcut I introduced). The YAML fixture extensions above satisfy the
card's literal fixture-naming instruction and give future integration-level tests real scenario
data; the actual golden/table-driven assertions live in the synthetic tests.
