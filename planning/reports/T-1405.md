# T-1405 · WAN & upstream health

## Summary

Implemented per-uplink availability/latency/loss monitoring against operator-configured *external*
reference targets, a `wan_degraded` finding routed through the existing T-1005 alert-rule webhook
pipeline, and a `GET /wan/status` dashboard-tile verdict that answers "it's the ISP, not the
cluster." Visibility and findings only — **no WAN failover automation**: no changeset op type or
write route exists anywhere for uplink switching (`internal/change.TestNoWanFailoverOpType` pins
this structurally, mirroring T-1404's `TestNoDHCPv6PDOpType`).

Per the card's explicit instruction ("reuse the existing probe/mesh scheduler rather than building
a second one, following T-1306's precedent"), the probe loop is literally `internal/latmesh.Service`
itself, reused (not forked): `internal/wan.Service` wraps a `*latmesh.Service` configured with a new
`Discoverer` (`wan.TargetDiscoverer`, emitting one `Pair` per configured node/uplink/reference-
target triple) and a new `Ring` (`store.WanProbeSampleRepo`, backing its own `wan_probe_samples`
table and `[wan]` retention config rather than sharing `latency_samples`/`[latmesh]` — a WAN link's
jitter/loss profile and retention needs aren't the LAN mesh's). The wire-level probe mechanism
(`latmesh.RealProber`, execing `ping`) is reused completely unmodified — it works identically against
an external hostname/IP as it does a cluster node name.

## What was built

- **`internal/wan`** (new package): `TargetDiscoverer` (implements `latmesh.Discoverer` over
  `store.WanTargetRepo`'s configured targets, re-read fresh every tick — the same convention
  `latmesh.GraphDiscoverer` uses for corosync.conf), `Service` (wraps `*latmesh.Service` as its
  scheduler; `Status` aggregates per-`(node, uplink)` readings for T-1405 AC2's independent multi-WAN
  view; `Export` surfaces the bounded ring for AC4).
- **`internal/store`**: migration `0017_wan.sql` — `wan_targets` (id, node, uplink, host,
  created_at, `UNIQUE(node, uplink, host)`) and `wan_probe_samples` (mirrors `latency_samples`
  field-for-field plus an `uplink` column, derived from the sample's own `LinkID` at insert time).
  `WanProbeSampleRepo` satisfies `internal/latmesh.Ring` structurally (its five methods use the
  identical `LatencySample` currency type) — the literal mechanism that lets `wan.Service` reuse
  `*latmesh.Service` without an adapter. `WanTargetRepo.ReplaceForNode` is a full-set
  delete-then-insert replace (mirrors `PUT /protected-interfaces`' own semantics).
- **`internal/findings`**: new `SourceWan`, `CheckWanDegraded` = `wan_degraded`,
  `HealthThresholds.WanLossWarnPct` (default 20%), `checkWanDegraded` (`health_wan.go`) — one
  finding per link whose rolling loss crosses the threshold and holds, 3-cycle-rise/2-cycle-fall
  hysteresis (AC1), wired into `Engine.Findings()` via a new `Wan WanProvider` `Config` field.
- **`internal/config`**: `[wan]` section (`probe_interval_sec`/`retention_minutes`/`max_rows`/
  `loss_warn_pct`), same defaults as `[latmesh]` (10s/60min/500,000 rows); `loss_warn_pct` is
  threaded into *both* `wan.Service`'s own per-uplink status aggregation and
  `findings.HealthThresholds.WanLossWarnPct` (via `cmd/vnproxd/server.go`) so the "degraded" label
  `GET /wan/status` shows and the threshold `wan_degraded` actually fires at never silently drift
  apart.
- **`internal/api`**: `GET /wan/status` (per-uplink status + `verdict`/`summary` dashboard-tile
  fields — `"likely_isp"` when a degraded uplink coincides with an otherwise-quiet `GET /findings`
  stream, `"wan_degraded"` otherwise, computed here since `internal/wan` never imports
  `internal/findings`), `GET /wan/targets`, `PUT /wan/targets` (netWrite+CSRF, audited
  `wan.targets_update`). No other write route in this file.
- **`cmd/vnproxd`**: `setupWan` builds the Service + its two run-group actors (probe loop, prune
  loop); wired into `findings.Config.Wan` and `api.Options.Wan`/`WanAudit`.
- **`internal/change`**: `TestNoWanFailoverOpType` — AC5's structural regression, mirroring T-1404's
  `TestNoDHCPv6PDOpType`.
- **Docs**: `docs/api.md` (new "WAN & upstream health" section; `source` vocabulary additions in the
  `GET /findings` shape and Alert Rules `sourceFilter` docs), `docs/data-model.md` (`wan_targets`/
  `wan_probe_samples` table definitions + prose), `docs/features/monitoring.md` (§5 `wan_degraded`
  entry, new §8), `docs/security.md` (extends the `ping`/`ping -M do` Host-footprint entry to name
  the WAN probe and its operator-configured, not inventory-resolved, target argument).

No new third-party dependency — everything above builds on already-approved stdlib +
`internal/latmesh`/`internal/store`/`internal/findings`/`internal/edge`(docs cross-reference only,

## Deviations from the card (flagged, with reasons)

1. **No `internal/edge` code dependency at runtime.** The card's context doc says "T-1403's
   `GET /edge/routes` uplink model" — I read this as the *conceptual* uplink model (a node's
   default-route-carrying interfaces), not a runtime data dependency: `wan.TargetDiscoverer` builds
   `Pair`s straight from `store.WanTargetRepo`'s already-configured `(node, uplink, host)` rows, never
   consulting `GET /edge/routes` at probe time. The web client is expected to populate a target-add
   form's `uplink` dropdown from `GET /edge/routes`' `DefaultRoute.Iface` list (documented in
   `docs/api.md`), but `PUT /wan/targets` itself does not validate `uplink` against that list — it's
   an operator-chosen label, schema-checked non-empty only. This card carries no explicit AC
   requiring that validation, and the T-1405 card lists no frontend deliverable at all (unlike
   T-1402/T-1403's explicit "Frontend: ..." bullets) — the wiring point for a future target-management
   UI is `GET/PUT /wan/targets`, left for a future card.
2. **Node-local scope**, the same documented gap T-1303/T-1306 already carry (their own context docs
   named no Peer API section, and neither does this card's): a node only probes its own configured
   targets; `GET/PUT /wan/targets` likewise only ever reach the requesting node's local store, no
   `{node}` path param. A cluster-wide merged view is a documented follow-up.
3. **`UplinkUnknown` status value declared but currently unreachable**: `Service.Status` only reports
   uplinks that `Heatmap` has at least one reading for (an uplink with a configured-but-never-probed
   target simply has no entry yet, rather than an explicit "unknown" placeholder row) — the same
   "no result yet → no entry, never a stale placeholder" stance `internal/mtuprobe`'s own map-edge
   annotation doc comment already establishes. `UplinkUnknown` is kept in the wire vocabulary for a
   future caller that wants that distinction, documented as reserved.
4. **`GET /wan/status`'s "likely_isp" correlation lives in `internal/api`, not `internal/wan`** — a
   deliberate dependency-direction choice (`internal/wan` never imports `internal/findings`, the same
   one-way rule every findings *producer* in this codebase keeps) rather than a card gap; noted for
   the next agent touching this area since it's the one place both seams are wired together.

## Acceptance criteria

1. **Hysteresis: a single missed probe doesn't fire.** `internal/findings/health_wan_test.go`'s
   `TestWanDegraded_DegradingSeries` drives a 9-cycle synthetic loss series (3 clean, 4 above-
   threshold, 2 clean again) through `checkWanDegraded` directly — no finding until cycle 6 (after
   3 consecutive breaches), clears after cycle 9 (after 2 consecutive clean cycles); `
   TestWanDegraded_CleanSeries_NeverFires` proves a never-breaching series never fires.
2. **Multi-WAN: two uplinks, one degraded, reported independently.**
   `internal/wan/service_test.go`'s `TestService_Status_MultiUplinkIndependent` drives two configured
   uplinks through a real `Tick()`, asserts `Status.Uplinks` reports `vmbr0` healthy and `vmbr1`
   unreachable independently (never blended). `internal/findings/health_wan_test.go`'s
   `TestWanDegraded_MultiUplink_Independent` proves the same independence one layer up, at the
   findings level. `internal/api/wan_test.go` exercises the same shape through the HTTP layer.
3. **Webhook delivery via an alert_rules entry.** `internal/findings/health_wan_webhook_test.go`'s
   `TestWanDegraded_DeliversViaAlertRule` reuses `webhook_test.go`'s own `fakeRuleProvider`/
   `fakeRecorder`/`WebhookNotifier.Notify` verbatim (T-1104's own delivery-test pattern), asserting
   one delivered webhook carrying the `wan_degraded` finding.
4. **Ring bound + export path.** `internal/store/wan_test.go`'s
   `TestWanProbeSampleRepo_PruneOlderThan`/`PruneToCap` assert the age/row-cap bound is honored
   (mirrors `TestLatencySampleRepo_PruneOlderThan`/`PruneToCap` exactly); `TestWanProbeSampleRepo_
   QueryAll` asserts the export path returns the expected bounded, newest-first set and defaults a
   non-positive limit rather than dumping unbounded.
5. **No WAN failover write surface.** `internal/change/wan_zerowrite_test.go`'s
   `TestNoWanFailoverOpType` structurally scans every registered `OpType` for `wan`/`failover`/
   `uplink` substrings — none exist. `internal/api/wan_test.go` pins the mounted route set (`GET
   /wan/status`, `GET /wan/targets`, `PUT /wan/targets` only — the PUT is target-list config, not
   failover) and that `PUT /wan/targets` requires `netWrite`+CSRF like every other write route.
6. **Docs + `make check` green.** See above.
