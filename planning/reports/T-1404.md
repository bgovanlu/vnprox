# T-1404 · IPv6 enablement suite — completion report

## What was built

**Per-family path simulator (`internal/sim`, T-503).** `Request` gains a `Family` field
(`FamilyV4`/`FamilyV6`, default v4, backward compatible). `bestGuestIP` now filters
`Input.GuestIPs` candidates by family instead of picking the highest-confidence address
regardless of family; a dual-stack VNet's subnet-disambiguation fallback (used when a guest-nic's
IP isn't known at all, for hop/L3 reasoning) is also filtered by family via a new
`familySubnets` helper. Firewall address matching already worked correctly cross-family for free
(`netip.Prefix.Contains` returns `false`, not a match, when the prefix and address are different
families) — no change needed there.

**`internal/host.Reader.IPv6RA`** (new interface method): bounded, host-local IPv6 Router
Advertisement / DHCPv6 observation per bridge/VLAN interface. Real Linux implementation
(`netlink_linux.go`) execs `rdisc6 -1 -w <timeoutMs> <iface>` (fixed argv) per interface from
`Links()`, parses the plain-text report defensively; `rdisc6` (ndisc6 package) not being installed
degrades to `(nil, nil)`, not an error — **needs hardware validation**, ndisc6 is not on a stock
Debian/PVE host by default. `DHCPv6ServerPresent` is *inferred* from the RA's M-flag (documented
limitation, `DHCPv6InferredFromRA` always true alongside it) — there is no way to confirm a real
DHCPv6 server without completing a SOLICIT/ADVERTISE exchange as a client, out of scope for a
bounded read-only observation. pvemock fixture support (`IPv6RASpec`), peer route
(`GET /api/peer/host/ipv6-ra`, protocol-version-2-additive) and client method added following the
existing `Conntrack`/`Neighbors` precedent exactly.

**New `internal/ipv6` package.** `Service.Segments` fans `IPv6RA` out across the cluster (local +
peer, the identical local-vs-peer adapter shape `internal/evpn.Service.Status` already
establishes for FRR/BGP), correlating each raw observation to its owning `Bridge`/`SdnVnet` by
interface name (PVE realizes an SDN VNet as a same-named bridge on every node it's deployed to).
Backs `GET /ipv6/segments` (`internal/api/ipv6.go`), gated on `netRead` per the card's own
explicit wording (not `sdnRead`, which `GET /sdn`/`GET /ipam/*` use — RA/DHCPv6 observation is
host-local diagnostic data, the same category `GET /conntrack`/`GET /latmesh/heatmap` are gated
on). Wired into `cmd/vnproxd` the same way `evpnSvc` is.

**`dualstack_drift` finding** (`internal/findings/health_dualstack.go`, source `health`,
hysteresis-exempt — structural, like `orphan_vnet`). For every SDN VNet carrying both a v4 and a
v6 subnet, each with a configured gateway, it runs `internal/sim` once per family from that
subnet's own gateway address to `external` and flags the case where the v4 simulation is `allow`
and the v6 simulation is `deny`/`unreachable`/`indeterminate` — the classic "v4 works, v6 is
silently broken" case, driven entirely by SNAT/exit-node config (no guest IP resolution needed).
Both verdicts are named in `detail`; `refs` names both subnets.

**Per-family latency mesh** (`internal/latmesh`). `Pair` gains a `Family` field;
`discoverGuestPairs` now emits one `Pair` per address family a shared bridge carries on *both*
nodes, not one `Pair` per bridge regardless of family — a dual-stack bridge gets two independently
probed, independently retained `LinkID`s (family suffixed into `Label`, e.g.
`"guest:vmbr0-v4|pve1->pve2"` / `"guest:vmbr0-v6|pve1->pve2"`). A single-family bridge keeps the
pre-T-1404 bare-label `LinkID` unchanged (no breaking change); a bridge with no address data at
all, or mismatched families across the two nodes, keeps the pre-existing address-less fallback
pair (dial-by-name). `discoverCorosyncPairs` also tags `Family` from the ring address's own
parsed type. **No schema/migration change**: `LinkID` already uniquely keys a family via the
`Label` suffix, so the existing bounded ring, `Heatmap`, and `History` all keep two families'
samples independent for free.

**IPv6 planning grid** (`internal/ipam/v6plan.go`, `GET /ipam/subnets/{prefix}/v6-plan`). Given a
delegated prefix (`≤ /64`, capped at 65536 enumerated `/64` blocks — a defensive bound against an
absurd delegation), enumerates its `/64`-aligned blocks, marks ones an already-configured SDN v6
subnet occupies `allocated`, and proposes free blocks in ascending order to every currently
v4-only VNet (sorted by ID for a deterministic, reviewable proposal) `proposed`; everything else
is `free`. Purely read-only.

**Guided dual-stack rollout wizard** (`web/src/ipv6/DualStackWizard.tsx`), built on T-603's
`blueprint.Instantiate` pattern exactly as the card specifies: picks an existing VLAN/VNet, fills
a v6 subnet CIDR/gateway/SNAT via the *existing* `ParamForm` component, and submits through the
same save-blueprint-if-missing → instantiate flow `BlueprintsPage` already uses (a fixed,
well-known blueprint id, upserted once via `POST /blueprints` and reused on every subsequent run —
remembered client-side in the wizard's own local state as well, so a second submit in the same
session never re-saves). Every mutation is the ordinary `sdn.subnet.create` op inside one
reviewable changeset draft — no new op type. Idempotent by construction (T-603's own contract):
re-running against an already-converged VNet yields a zero-op changeset, rendered as "already up
to date."

**Fixed a real, pre-existing bug this task's own wizard immediately hit**: the blueprint
param-form's `cidr`/`ip` validators (`web/src/blueprints/paramValidation.ts`) were hard-coded to
dotted-decimal IPv4 regexes, silently rejecting every legitimate IPv6 address/CIDR at the form
layer. Added a segment-based IPv6 validator alongside the existing IPv4 one (dispatched on whether
the input contains `:`); IPv4 behavior is unchanged (16 pre-existing + new tests all pass).

**New `testdata/clusters/ipv6-dualstack.yaml` fixture** (single node, three SDN VNets on one
`simple` zone): `vnet20` (healthy dual-stack — both families SNAT'd, full RA with M=1),
`vnet21` (the v6-broken silent-failure case — v4 SNAT'd, v6 not, zone has no exit node, and
deliberately no RA observed on the segment at all), `vnet22` (DHCPv6-PD-from-an-upstream-device
visibility scenario — RA present with M=1, same shape as a vnprox-managed segment, since vnprox
has no way to distinguish "whose DHCPv6 server" at this layer and never claims to).

## Deviations from the task card (with reasons)

- **Dependency correction already reflected in the card** (`T-503`, not `T-501`) — followed as
  written, no further action needed.
- **T-1303 (`internal/latmesh`) was not actually present in this worktree at task start**, despite
  the card's "now merged" framing — the worktree branched before another parallel agent's Phase-13
  work landed on `main`. Fast-forward-merged this worktree's branch onto `main` (`a731c2d`) before
  starting; the merge was a clean fast-forward (no divergent commits on this branch), verified with
  a full `go build`/`go test` pass before any T-1404 code was written.
- **RA/DHCPv6 parameter control stays P1, deliberately** — PVE SDN's own subnet model
  (`SdnSubnetCreateParams`) has no M/O-flag or DHCPv6-range fields at all; the dual-stack wizard
  therefore only ever stages *addressing* (CIDR/gateway/SNAT) via the existing `sdn.subnet.create`
  op. Once addressing exists on an SDN zone, the zone's own dnsmasq/radvd instance is what actually
  emits the RA `GET /ipv6/segments` then observes — this is the same "display real, config P1"
  split the card's own context doc (`docs/features/sdn.md` §6) already drew; T-1404 promotes
  *display* to real and adds *addressing* config, not full RA/DHCPv6 parameter control.
  Documented explicitly in `docs/features/ipam.md` §5 and `docs/features/sdn.md` §6.
- **Live-probe (`POST /simulate/verify`) v6 support needs hardware validation.** `family` threads
  through to the `observed` half's destination-address resolution (`bestAgentIP`, generalized from
  the pre-existing v4-only `bestAgentIPv4`, with an IPv6-link-local fallback exclusion), but the
  actual in-guest probe command's IPv6 behavior across guest OS/toolchains is unverified against a
  live cluster — flagged in `docs/api.md` and `planning/reports/needs-hardware-validation.md`
  alongside this route's pre-existing v4 needs-hardware-validation note.
- **Guest-IP wiring into `POST /simulate/path`/`verify`** was not explicitly listed as a T-1404
  deliverable, but was necessary to make AC3 (family produces a distinct, firewall-rule-driven
  verdict) meaningful at all: firewall enforcement only ever applies at guest-nic endpoints
  (`internal/sim/firewall.go`), and `Input.GuestIPs` was previously never populated by the API
  route. Reused the existing `GuestInteriorIPAMSource` seam (T-1304's `AllAllocations` read,
  already wired in `cmd/vnproxd`) rather than adding a second IPAM adapter — one `*ipam.Service`
  instance now backs both T-1304's guest-interior IPAM cross-check and this route's guest-IP
  resolution. Documented in `docs/api.md`'s Path simulator section as an additive capability, not a
  breaking change (nil-safe, degrades to the pre-existing "IP unknown" behavior with no IPAM
  wired).

  tag-derived offset alignment as an opt-in mode without breaking this one.

  flagging that as a small doc-completeness gap for whichever task next touches that section (it
