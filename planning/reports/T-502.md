## What was built

### 1. Change engine: the full `fw.*` op family (`internal/change`)

T-501/earlier scaffolding had already added `fw.*`'s `Op`/`Params` types, `paramFactories`, and basic schema/position/collision validators (see "Building on existing scaffolding" below) — but no execution path existed: `BuildPlan` rejected every `fw.*` op with `ErrUnsupportedOp`. This task closes that gap end to end:

- **`apply_plan.go`**: two new step kinds, `StepFwApply` (executes every op targeting one firewall ruleset, grouped by target in first-appearance order, mirroring the existing per-node stage/reload grouping) and `StepFwVerify` (post-apply compile-status check, spec §3 — only emitted for node-/guest-scope targets, since a cluster-scope target has no single node to check against; see "Deviations" #3).
- **`apply_seams.go`**: `PVEGateway` gains `FirewallRuleFields`, `ApplyFwOp`, `SnapshotFirewallScope`, `RestoreFirewallScope`, `FirewallCompileStatus`. Its doc comment carries a load-bearing flagged limitation — see "Deviations" #1.
- **`apply_exec.go`**: `execFwApply` snapshots the target's live content before its first mutating call (`e.fwPre`), executes each op via `pveGW.ApplyFwOp`, and — for `fw.rule.move` ops carrying a non-nil `Expect` — re-fetches the live rule at `FromPos` via `FirewallRuleFields` and fails with `*ErrFwPositionChanged` on any mismatch **before** calling the move (acceptance criterion 3). `execFwVerify` calls `FirewallCompileStatus` and fails the step if not clean. `rollbackAfterFailure`/`undoFwTargets` reverts any fw target whose pre-mutation snapshot was captured, restoring it via `RestoreFirewallScope` — same-request rollback (see Deviations #1 for its scope).
- **`params_fw.go`**: added `FwRuleFields` (a rule's content-identity, everything but `Pos`) and `FwRuleMoveParams.Expect *FwRuleFields` — the client-observed-at-draft-time fingerprint the executor revalidates against.
- **Validators**:
  - `validate_schema.go`: macro-existence check (`schemaFwMacro`, against `internal/fw.MacroExpansion`); `"group"` added to `validFwDirections` with a carve-out (`schemaFwActionForDirection`) so a group-reference rule's `Action` (the group's name) isn't checked against the ACCEPT/DROP/REJECT enum.
  - `validate_referential.go`: `checkFwObjectDeletable` — **acceptance criterion 2**: `fw.alias/ipset/group.delete` now builds `fw.Snapshot`/`fw.UsageCounts` from the validation snapshot and blocks the delete (with the exact reference count in the finding message) when `count > 0`; also closes the pre-existing "no existence check for delete" gap.
  - `validate_projection.go`: new `fwRuleDelta` tracking — **without this, acceptance criterion 1's "create rules then reorder one, all in the same changeset" workflow could never validate**, since the position-bounds check (`checkFwPos`) only had the (poll-cached, out of date) inventory snapshot to check against, which knows nothing about rules this same draft is about to create. `fwRuleDelta` folds the net rule-count effect of earlier `fw.rule.create`/`delete` ops in the same changeset into the bounds check.
- **`cmd/vnproxd/changeagent.go`**: `pveGateway` (renamed from `pveSDNGateway`, now also the firewall gateway) implements every new `PVEGateway` method — rule create-then-move-if-needed (real PVE's create always appends), rule/alias partial-update via read-merge-write, ipset membership diffing (add/remove, no "replace all" PVE call exists), group rule replace via clear-then-recreate, and scope snapshot/restore via list-everything / delete-all-then-recreate (the CRUD-API equivalent of the interfaces-file "replace the whole file" restore model).
- **`internal/fw/effects.go`** (new, pure): `MatchingGuests(snap, group)` — **acceptance criterion 4**'s rule-effects preview, reusing `Resolve` rather than duplicating resolution logic. Honestly reflects the documented cluster-cascade simplification (a group referenced by the *cluster* ruleset matches every guest, not just guests that reference it themselves).
- **`internal/api/firewall.go`**: new `GET /firewall/effects?group=` route + `handleFirewallEffects`, documented in `docs/api.md`.

## Building on existing scaffolding

An earlier task (evidently done alongside T-201/T-205's op-vocabulary work, before T-501/T-502's spec details existed) had already added `fw.*`'s `Op`/`Params` types, `paramFactories` wiring, and *some* schema/referential validators (position bounds, intra-changeset name-collision detection for creates). This task built directly on that rather than duplicating it — the gaps it left (explicitly documented in its own code comments) were exactly this task's job: no execution path (`BuildPlan` rejected every `fw.*` op), no usage-guarded delete, no macro check, no move-position revalidation, and (undocumented, discovered while making acceptance criterion 1 pass) no way to validate a changeset that creates and reorders rules in the same draft.

## Deviations from the task card (all flagged, none silent)

1. **fw.\* ops are not covered by the unattended (session-less) commit-confirm-timeout / crash-recovery rollback path** — only same-request rollback (a later step's failure reverts an earlier `fw.*` step within the same `Apply()` call, while the user's PVE ticket is still live). PVE firewall writes require the user's own ticket (docs/architecture.md §6, D3); unlike `NodeAgent` (root-level host access, callable by the daemon unattended), there is no ticket available once the HTTP request that started an apply has ended. **This is not a new gap** — I found the *exact same* limitation already exists, unaddressed, for `sdn.apply` (its own step is excluded from `rollbackAfterFailure`'s node iteration, and the confirm-timeout path only ever restores node-file state). This is a real, product-relevant architectural question — a fw.\*-only changeset that reaches `awaiting_confirm` and then times out, or whose daemon crashes mid-window, is not automatically reverted — that both this task and SDN's task/future tasks share, and I did not consider it appropriately in-scope for one task to unilaterally invent an architecture-wide fix (e.g. a narrowly-scoped daemon-level PVE token) for. Flagging for the orchestrator to decide whether it's worth a dedicated follow-up task spanning both op families.
2. **`GET /nodes/{node}/firewall/status` is a mock-only extension**, not real PVE's own REST surface — real PVE exposes no API for `pve-firewall`'s own compile-loop result; an administrator (or a real vnproxd) checks it via `pve-firewall status` locally on the node, the same access pattern `internal/host`'s LLDP/netlink readers already use (root-level, proxied through the peer API for a non-local node). This task's mock endpoint stands in so the change engine's post-apply verification step (spec §3) has something to call in tests; a real implementation needs a new `internal/host` reader. **Needs hardware validation.**
3. **`StepFwVerify` (post-apply compile-status check) is only emitted for node-/guest-scope targets**, not cluster-scope ones: `BuildPlan` is a pure function over `ops []Op` with no cluster-node-list dependency to enumerate every node a cluster-scope ruleset change would need verifying against. A cluster-scope `fw.*` changeset still applies and snapshots/restores correctly; it just doesn't get an automatic post-apply compile check across the whole cluster in this increment.
4. **ObjectsPanel's delete button only appears for cluster-scope objects.** `GET /firewall/objects`' response (T-501's shape, `ObjectUsageView`) carries `scope` (cluster/node/guest) but not *which* node/guest a node-/guest-scope object belongs to (multiple nodes/guests can each have a same-named local alias) — deleting one unambiguously requires that identity, which the current read contract doesn't expose. Rather than guess, or expand a T-501-owned response shape without strong reason, node-/guest-scope object deletion is left to that scope's own rule table context (not built in this pass) — flagged rather than silently guessed at.
5. **`fw.group.update`'s `Comment` field is not wired** to any PVE call: neither `pvemock` nor the real PVE security-group surface this task's client uses exposes a "rename the group's comment" endpoint distinct from its member-rule CRUD (only `POST` create, `DELETE`, and per-rule sub-resource calls exist). Rules replacement (the field this op family primarily exists for) is fully implemented.
6. **The move-position-race failure (acceptance criterion 3) surfaces through the existing generic apply-failure banner** (`CountdownBanner.tsx`'s `"...failed to apply at step N ... check the apply log"`), not a bespoke "the ruleset changed — refresh and retry" prompt. The backend's `ErrFwPositionChanged` message *is* that exact sentence, but no apply-log step-detail viewer exists anywhere in the frontend yet (a broader, pre-existing gap affecting every op family, not fw.\*-specific) for that message to actually reach the screen. Building one was out of this task's bounded scope; the safety guarantee itself (no silent misplacement, apply fails cleanly) is fully enforced and tested at the backend.
7. **Builder-row autocomplete covers aliases and ipsets only**, not guest IPs/subnets (the task card's "autocomplete ... from aliases/ipsets/guest IPs/subnets from inventory") — there's no existing API surface returning guest-IP/subnet candidates scoped for this use, and adding one felt like a second task's worth of scope creep against an already-large card. Flagged as a deferred enhancement.
8. **`internal/fw` purity preserved**: `effects.go`'s `MatchingGuests` is pure (calls only `Resolve`/`Snapshot`, no I/O); depguard's lint rule for `internal/fw` was not touched.
