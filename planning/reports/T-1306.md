# T-1306 · Path MTU prober — completion report

## What was built

**New `internal/mtuprobe` package**, built directly on T-1303's `internal/latmesh` infrastructure
(reused, not duplicated — see the package doc comment for the full reasoning):

- `BinarySearchMTU(probe, lo, hi)` (`binarysearch.go`) — the core algorithm: integer binary
  search for the largest packet size a `ProbeFunc` reports `ok` for, always probing the floor
  first (a fast reject when even `MinMTU`, 552, fails). Bounded at `ceil(log2(hi-lo+1))+1` probes
  over the default 552–9216 range (at most 15). Returns `mtu=0` (not an error) when even the floor
  fails, mirroring `internal/latmesh.parsePingSummary`'s "can't confirm, report the pessimistic
  reading" stance.
- `Prober` interface + `RealProber` (`prober.go`) — issues real DF-set (`ping -M do -s <n>`)
  probes per candidate size via `dfProbe`, defensively parsing iputils-ping's fragmentation-drop
  output (`"Frag needed"`/`"Message too long"`/`"100% packet loss"`) the same honesty-first way
  `internal/latmesh.RealProber` parses its own summary line.
- `Service` (`service.go`) — `Tick`/`RunLoop`/`Results`/`Result`/`MeasuredUnderlayMTU`.
  `Config.Discoverer` is typed as `internal/latmesh.Discoverer` itself (not a new interface); in
  production it is **the same `*latmesh.GraphDiscoverer` instance** `latmesh.Service` uses
  (`setupLatMesh` now returns it so `setupMTUProbe` can share it — see "Composition root" below),
  so this prober reaches exactly the paths the mesh already knows about — never a second,
  parallel path-discovery mechanism. `RunLoop` calls `latmesh.RunTicker` (see "Scheduler reuse"
  below), never a hand-rolled ticker loop. Unlike `latmesh.Service`, this is **current-state
  only** — `Results()`/`Result(linkID)` hold each link's most recent verified MTU in memory, no
  SQLite ring (no history/rolling-stats use case a rarely-changing value needs; a daemon restart
  loses the last reading until the next tick re-establishes it). A probe attempt that fails to
  even run (transport error) leaves the prior good reading in place rather than clearing it — MTU
  has no meaningful "loss" analog, so `latmesh.Service.Tick`'s "record as full loss" stance
  doesn't apply here.
- `MeasuredUnderlayMTU(node) (mtu, ok)` — the minimum verified MTU across every link this node
  has successfully probed outbound, mirroring `health_vxlanmtu.go`'s `observedUnderlayMTU`'s
  per-node min-across-NICs shape but sourced from a live, measured, end-to-end DF-probe reading.
  Satisfies `internal/findings.MTUProvider` structurally (no adapter).
- `ProbeWireGuardLink(ctx, tunnelRef)` + `WireGuardCapability` (`wireguard.go`) — the
  capability-gated, declared-not-blocking seam the card asks for. `WireGuardCapability` is a
  package-level `var` defaulting to `func() bool { return false }`; `ProbeWireGuardLink` always
  returns `ErrWireGuardNotAvailable` today, checked against that capability var so the seam stays
  dark even if a future caller flips it before a real implementation lands. **This is the exact
  hook Phase 14's T-1401 should replace/extend**: swap `WireGuardCapability` for a real capability
  check (once a WireGuard capability flag exists) and give `ProbeWireGuardLink` a real body (once
  a WireGuard tunnel entity kind exists in `internal/inventory` to resolve `tunnelRef` against) —
  the method signature and its callers (none yet) don't need to change.

**Scheduler reuse (T-1303 integration, AC5)**: `internal/latmesh/scheduler.go` is new — `RunTicker
(ctx, interval, fn)` extracts the exact ticker-loop shape `latmesh.Service.RunLoop`/`RunPruneLoop`
already hand-rolled identically twice. Both of those methods were refactored to call it (behavior
unchanged, `internal/latmesh`'s existing test suite passes unmodified); `mtuprobe.Service.RunLoop`
calls the same function on its own coarser interval. This is real, single-implementation reuse —
not two schedulers that merely look alike — and is what `cmd/vnproxd` registers as a **second**
owned goroutine (`mtuprobe.Service.RunLoop`, on `[mtuprobe] probe_interval_sec`) alongside
latmesh's own two (`RunLoop`, `RunPruneLoop`), per `docs/development.md`'s "every goroutine has an
owner and a shutdown path" convention — one shared scheduler function, three goroutines that call
it (latmesh probe loop, latmesh prune loop, mtuprobe probe loop; mtuprobe has no prune-loop
goroutine, since it holds no SQLite ring to prune).

**Findings upgrade (AC3)**: `internal/findings/health_vxlanmtu.go`'s `checkVxlanUnderlayMTU`
gained a third parameter, `mtuProv MTUProvider` (new interface, this file), and a new
`underlayMTUFor(mtuProv, snap, node)` helper: when `mtuProv` has a fresh `MeasuredUnderlayMTU`
reading for a zone member node, the check compares against that (tighter, measured) figure
instead of `observedUnderlayMTU`'s local-NIC read; falls back to the original T-803 behavior
(`observed`) wherever no fresh reading exists — never a regression for paths the prober hasn't
reached. The finding's `detail` text now names which source it used (`"measured"` vs
`"observed"`), so a reader can tell at a glance whether a given finding is backed by a live probe
or just a local NIC read. `findings.Engine` gained `Config.MTU MTUProvider` / `Engine.mtuSvc`,
threaded into `healthFindings()`'s existing `checkVxlanUnderlayMTU` call.

**API**: `internal/api/mtuprobe.go` — `GET /mtuprobe/results`, netRead-gated, node-local only
(same documented scope `GET /latmesh/heatmap` carries — no peer fan-out; this task's context docs
named no Peer API section either). Mounted via `router.go`'s new `Options.MTUProbe` field.

**Config**: `[mtuprobe]` section (`probe_interval_sec`, default 300 — 30x coarser than
`[latmesh]`'s 10s default) — `internal/config.MTUProbeConfig`, documented in
`docs/deployment.md`.

**Composition root**: `cmd/vnproxd/latmesh.go`'s `setupLatMesh` now additionally returns its
`*latmesh.GraphDiscoverer` (so it can be shared, not rebuilt); `cmd/vnproxd/mtuprobe.go`'s new
`setupMTUProbe(cfg, discoverer, logger)` builds the `Service` (real `RealProber`, the shared
discoverer) and its one run-group actor. `server.go` wires `mtuProbeSvc` into
`findings.Config.MTU` and `api.Options.MTUProbe`, and registers `mtuProbeActors` with the run
group alongside every other owned goroutine. `setupFindings`'s signature grew one parameter
(`mtuSvc findings.MTUProvider`) for this.

**Frontend**: `web/src/topology/mtuOverlay.ts` (`computeMTUOverlayEdges` — pure mapping from
`GET /mtuprobe/results` items to on-canvas badges, mirroring `latencyMode.ts`'s
`computeLatencyOverlayEdges` precedent exactly; `formatMTUBadgeLabel` formats `"MTU <value>"`, so
the badge is always visually distinct from a bare configured-MTU number shown elsewhere), a new
`drawMTUOverlay` pass in `canvasDraw.ts` (drawn last, on top of every other overlay, since a text
badge needs to stay legible), a "MTU" toggle in `LayerToggleBar.tsx` +
`useTopologyStore` (`mtuLayerActive`/`toggleMTULayer`, mirroring the T-1303 Latency-layer pattern),
`web/src/api/mtuprobe.ts` + `mtuProbeQueries.ts` (a plain 60s poll — no WS event exists for this
data, matching `latMeshQueries.ts`'s own "no push, just poll" convention, at a coarser interval
matching the server's own coarser cadence), and `MTUProbeResult`/`MTUProbeResults` types in
`web/src/api/types.ts`. Wired end-to-end into `TopologyPage.tsx`/`TopologyCanvasV2.tsx`
(`mtuPaintable` gate: v2-canvas-only, same as Latency).

**Docs**: `docs/api.md` gained a "Path MTU prober (T-1306)" section (mirroring "Latency mesh"'s
shape) and an update to `vxlan_underlay_mtu`'s finding-shape entry describing the measured-vs-
observed upgrade; `docs/features/monitoring.md` gained §6 (same content, product-doc framing) and
an update to its own `vxlan_underlay_mtu` bullet; `docs/deployment.md` gained the `[mtuprobe]`
example-config block.

## Deviations from the task card (with reasons)

1. **"Along each bridge/bond/VXLAN-EVPN path" narrowed to exactly the paths
   `internal/latmesh.Discoverer` already knows about (corosync + shared-bridge "guest" fabric)** —
   the same fabric-scope narrowing T-1303 itself already documented and flagged (this package's
   doc comment explains why in detail: a bond is node-local link aggregation with no node-to-node
   IP path of its own to path-MTU-discover in isolation; "guest" fabric *is* the VXLAN/EVPN
   underlay path when the shared bridge is an SDN zone's own bridge). Building a third,
   bond-specific pair-discovery mechanism with no existing substrate in this codebase would have
   been exactly the kind of unverified-shape guess T-801 exists to prevent. Flagged in
   `planning/reports/needs-hardware-validation.md`'s new "Path MTU prober (T-1306)" section for a
   real-cluster call on whether this is a genuine, actionable gap.
2. **Current-state store instead of a SQLite ring** — the card's deliverables describe "producing
   a verified path MTU per link," not a history/time-series requirement, and MTU rarely changes
   (unlike latency/loss), so there's no rolling-stats consumer to serve. No `docs/data-model.md`
   table was added; `Service.Results()` is the only durable-enough-for-purpose store. If a future
   task needs MTU history, this is a documented, deliberate gap, not an oversight.
3. **Map-edge annotation implemented as a client-side canvas overlay (mirroring T-1303's Latency
   layer), not server-side `internal/topology` edge badges** — `internal/topology.Project` is a
   pure function of an inventory snapshot with no external-provider injection seam (its own doc
   comment: even staleness is decorated *after* `Project` by the API handler, not inside it), and
   `internal/topology`'s existing `Edge`/badge model is entity-to-entity graph edges (NIC→bond,
   bond→bridge, ...), not node-to-node mesh links — there is no existing `topology.Edge` a
   `latmesh.Pair`/mtuprobe `Result` could attach a badge to even if the seam existed. T-1303 hit
   the identical shape mismatch and solved it with a dedicated client-side overlay
   (`latencyMode.ts`/`drawLatencyOverlay`), not a `topology.Project` change; this task follows that
   exact precedent rather than inventing a second approach or touching a package another task
   (T-901/T-902/T-908) owns.
4. **WireGuard hook signature is `ProbeWireGuardLink(ctx context.Context, tunnelRef string) (mtu
   int, err error)`**, a plain method on `*mtuprobe.Service` rather than a new interface — the
   card only asks for a declared, no-op'd seam; T-1401 is free to change this signature when it
   lands a real implementation (nothing in this task's code calls it yet, so there's no call site
   to break).
