# T-1005 · Alert routing

## Summary

Implemented in full. Routes findings/drift transitions to arbitrary webhook targets (generic
JSON, Gotify, ntfy, Slack incoming-webhook), independent of PVE's own notification-target system
— closing `pvenotify.go`'s documented gap (PVE's API has no way to carry vnprox's own finding
text). `WebhookNotifier` (`internal/findings/webhook.go`) is a new implementation of the
**existing** `findings.Notifier` interface, composed alongside the existing `PVENotifier` via a
small `multiNotifier` fan-out added to `cmd/vnproxd/findings.go` (composition-root wiring only).

**Engine's notification-firing/once-per-transition logic (`notify.go`/`engine.go`) was NOT
changed** — confirmed by `git diff` on those two files: zero hunks. `WebhookNotifier` is just a
second `Notifier` value the composition root hands to the same `Config.Notifier` field, exactly
the shape `PVENotifier` already used.

## Backend (`internal/findings/webhook.go`, `internal/store/alertrules.go`, `internal/store/alertdeliveries.go`, `internal/api/alertrules.go`)

- `findings.WebhookNotifier` implements `findings.Notifier`. `Notify` fans a transition out
  concurrently to every enabled `alert_rules` row whose optional/ANDed `sourceFilter`/
  `severityFilter` match, each with its own bounded exponential-backoff retry sequence
  (`DefaultMaxAttempts = 5`, `1s → 2s → 4s → 8s → 30s cap`, mirroring
  `internal/collect/loop.go`'s `backoffFor` shape). Every attempt (success or failure) is recorded
  via a `DeliveryRecorder` seam before `Notify` returns for that rule.
- `findings.PayloadFor`/`findings.Deliver` are the pure/testable primitives: `PayloadFor` builds
  the documented per-`targetKind` shape (generic = `Finding` verbatim; Gotify = `{title, message,
  priority}` + `X-Gotify-Key`; ntfy = plain-text body + `Title`/`Priority`/`Tags` headers +
  `Authorization: Bearer`; Slack = `{"text": "..."}`, secret unused); `Deliver` is a single-shot
  HTTP attempt reused by both the retry loop and `POST /alert-rules/{id}/test` (which deliberately
  bypasses retry — a single attempt, synchronous response).
- `internal/findings` still does **not** import `internal/store` — `AlertRuleProvider`/
  `DeliveryRecorder` are small seams; `cmd/vnproxd/findings.go`'s new
  `alertRuleProviderAdapter`/`alertDeliveryRecorderAdapter` do the store<->findings conversion
  (decrypting `TargetSecretEnc` via the session cipher), the same decoupling pattern
  `ipamFindingsAdapter`/`probeFindingsAdapter` already established for other producers.
- `store.AlertRuleRepo`/`store.AlertDeliveryRepo`: plain CRUD/List repos over the two new tables.
  Filter columns are `NULL`-means-"no filter" JSON arrays; `TargetSecretEnc` is opaque
  `[]byte` ciphertext the store package never decrypts itself.
- `internal/api/alertrules.go`: `GET/POST /alert-rules`, `GET/PUT/DELETE /alert-rules/{id}`,
  `POST /alert-rules/{id}/test`, `GET /alert-deliveries?ruleId=&status=`. Reads gated `netRead`;
  writes (including `test`, since it performs a real outbound call and writes a delivery-log row)
  gated `netWrite` + CSRF. Secrets are **never** returned by any route (`hasSecret bool` only,
  matching `GET /config`'s "excludes every secret" contract); `PUT`'s `targetSecret` is a
  three-way-nullable `*string` (absent = unchanged, `""` = clear, non-empty = replace).

## Secrets at rest

`target_secret_enc` uses `store.SessionCipher` (AES-256-GCM) — the **same instance/key** as
`sessions.pve_ticket_enc`, not a second cipher/key pair. This required widening `setupAuth`'s
return signature (`cmd/vnproxd/auth.go`) from `(*auth.Service, *store.DB, error)` to
`(*auth.Service, *store.DB, *store.SessionCipher, error)` — its one call site
(`cmd/vnproxd/server.go`) updated; no other caller exists (grepped `_test.go` files for
`setupAuth(` — none).

## Deviations / judgment calls (flagged, not silent)

1. **Capability choice**: the task card doesn't name a capability; alert-rule reads/writes reuse
   the existing `netRead`/`netWrite` vocabulary (no new capability added) rather than inventing an
   unused-elsewhere "settings" capability, per CLAUDE.md's "no new dependency/decision without a
   note."
2. **`alert_deliveries` row-per-attempt, not row-per-logical-delivery**: chosen so the delivery log
   UI shows the full retry history, not just the terminal outcome — documented in both the
   migration and `docs/api.md`.
3. **`POST /alert-rules/{id}/test` skips retry entirely** (single attempt, synchronous response) —
   the task card says "returns the delivery outcome synchronously"; a 5-attempt/up-to-~45s retry
   loop behind a manual "Test" button would be a poor UX for an explicit user action, so this calls
   `Deliver` once directly rather than `WebhookNotifier`'s retry wrapper.
4. **e2e stack**: added a fifth dedicated pvemock+vnproxd pair (ports 48006/48007,
   `testdata/dev-alert.toml`, `web/playwright.config.ts`) reusing the existing `sim-lab.yaml`
   fixture's scripted `vm-a -> vm-c tcp/2222` live-probe divergence (T-806's own mechanism,
   `simulator.spec.ts`) rather than sharing that spec's stack — a finding only re-notifies on a
   *fresh* transition (Engine's own once-per-transition contract), so sharing state with
   `simulator.spec.ts` (which also probes that exact tuple) would make the alert-rules e2e
   non-deterministic depending on file execution order across the shared `workers: 1` Playwright
   run.
5. **Unrelated pre-existing e2e ambiguity found, not fixed**: `web/e2e/simulator.spec.ts`'s
   `page.getByLabel("Port")` (lines 99, 178) is ambiguous against `AppShell`'s "Ports" nav link
   (`getByLabel` substring-matches accessible names) under the current nav — reproduced live while
   building this task's own e2e spec. `alert-rules.spec.ts` avoids it with
   `getByRole("spinbutton", { name: "Port" })`; `simulator.spec.ts` itself is untouched (out of
   this task's scope, and e2e isn't part of `make check` so this wasn't caught by CI).
