  on `WHERE status = pending` so a row only ever resolves once.
- `errors.go`: new `ErrIllegalState` sentinel (a row exists but isn't in the state a mutation

- `kv_test.go`: `TestKVRepo_SchemaVersionIsPresentAfterOpen` updated `9` → `10` (mechanical, tracks
  the new migration).

**Change engine (`internal/change/schedule.go`, `schedule_errors.go`)**
- `Clock` interface (`Now() time.Time`) — the task card's required injected-clock seam.
  `Config.Clock` defaults to a thin adapter over the existing `Config.Now func() time.Time` (the
  package's established fake-clock convention, e.g. `apply.go`/`localtimer.go`), so production
  wiring needs nothing new and schedule-specific tests can hand in a fake `Clock` directly.
- `Service.Schedule`: validates window (`windowStart < windowEnd`), `missedWindowPolicy` enum,
  rejects a changeset that already has a pending schedule, **recomputes `touchesMgmtPath` fresh**
  via `Service.MgmtStatus` (never a cached/client value) and rejects unconditionally
  (`*ErrMgmtPathUnattendedForbidden`) with no downgrade path, then re-validates
  (`*ErrValidationBlocked` on any error finding). On success: mints the callback token, persists the
  row, audits `changeset.schedule_create`.
- `Service.CancelSchedule` / `Service.GetSchedule` / `Service.AckSchedule`.
- `Service.TickSchedules(ctx)`: scans every pending row against `s.clockNow()`; fires rows whose
  window has opened, hands elapsed-window rows to `handleMissedWindow`. Exported specifically so
  tests drive it directly (no goroutine, no ticker, no sleep).
- `Service.RunScheduler(ctx, interval)`: the production supervised-goroutine wrapper around
  `TickSchedules` (owned, shuts down on `ctx.Done()` — `cmd/vnproxd`'s `runGroup` actor shape).
- `fireSchedule`: reloads the changeset, recomputes `touchesMgmtPath` fresh, fails fast on a plan
  needing a `PVEGateway` (the scheduler never has a live user session — mirrors
  `internal/api/changesets.go`'s own `planRequiresPVEGateway` pre-check), then calls the existing
  `Service.Apply` (which itself revalidates from scratch) with `confirmTimeout =
  min(confirmTimeoutSec, windowEnd-effectiveStart)`. Resolves the row `fired`/`blocked`/`failed`
  and audits `changeset.schedule_fire` / `changeset.schedule_fire_blocked` accordingly.
- `handleMissedWindow`: `skip` (default) → row `missed`, audits `changeset.schedule_missed`;
  `applyImmediately` → calls `fireSchedule` with `effectiveStart = now` (a freshly computed
  window), still fully `touchesMgmtPath`/validation-checked.
- Callback token (`mintCallbackToken`/`verifyCallbackToken`/`hashCallbackToken`): HMAC-SHA256 over
  `changesetID + 0x00 + windowEnd`, same construction style as `internal/peer/sign.go`. Only
  `sha256(token)` is ever persisted (`callback_token_hash`); the process-lifetime-only signing
  secret (`newScheduleSecret`, `crypto/rand`, never persisted) is needed only at mint time —
  verification is a stored-hash comparison, so a daemon restart (fresh secret) never invalidates an
  already-minted, not-yet-used token. Single-use falls out of `Confirm`'s own state machine
  (`AckSchedule` **is** `Confirm`): a replay after commit/rollback fails `*ErrNotConfirmable`
  exactly like a stale UI confirm click would — no separate "used" bookkeeping needed.
- New errors: `ErrInvalidScheduleWindow`, `ErrInvalidMissedWindowPolicy`,
  `ErrMgmtPathUnattendedForbidden`, `ErrScheduleAlreadyExists`, `ErrInvalidCallbackToken`.
- `service.go`: `Config.Schedules *store.ChangeScheduleRepo`, `Config.Clock`; `Service.schedules`/
  `clock`/`scheduleSecret` fields; `scheduleConfigured()` (mirrors `applyConfigured()`).

## Required safety-analysis section (task-card scenarios → tests)

1. **Daemon down mid-window** — no partial apply is possible: `Service.Apply` only ever starts at
   `windowStart` (`fireSchedule` is the only caller), never resumes mid-flight. A crash before
   firing leaves the row `pending`; `cmd/vnproxd/server.go` calls `changeSvc.TickSchedules(ctx)`
   once, eagerly, immediately after `ArmPendingRollbacks` at startup — a schedule whose window (or,
   for `missedWindowPolicy: skip`, whose `windowEnd`) already passed while the daemon was down is
   resolved right away rather than waiting for `RunScheduler`'s first real tick.
   **Test:** `TestSchedule_RestartSafety_FiresFromPersistedRow` (reconstructs the scheduler from
   the same store, advances the clock past `windowStart`, proves the apply still fires from the
   persisted row) and `TestSchedule_MissedWindow/skip` +
   `TestSchedule_MissedWindow/applyImmediately` (the elapsed-while-down case for both policies).
2. **Peer unreachable at deadline** — unchanged from T-304: `Service.Apply` arms every affected
   node's own local rollback timer (`LocalTimerAgent`) with one shared absolute deadline, and each
   node rolls back independently on its own clock with no cross-node dependency. This task adds
   nothing to that path — it only decides *when* `Apply` starts (`fireSchedule`'s doc comment says
   so explicitly).
   **Test:** `TestSchedule_FireThenNoAck_RollsBack` (no ack before the deadline → the *existing*
   commit-confirm timer fires via `fakeTimers.fireLatest`, with zero scheduler involvement in the
   rollback itself — pre-state byte-identical afterward, proving the rollback path is exactly
   T-304's, untouched).
3. **Clock skew** — `fireSchedule` computes one absolute unix deadline
   (`min(windowStart+confirmTimeoutSec, windowEnd)`) and passes it to `Service.Apply` as a duration
   relative to this daemon's own clock at fire time; from there it is the *exact same* "coordinator
   computes one absolute instant, every node's local timer is armed with it before any apply step
   begins" flow T-304 already implements — each node's own clock governs its own rollback,
   unchanged.
   **Test:** `TestSchedule_FireThenAck_Commits` asserts the exact computed `ConfirmDeadline`
   (`scheduleEpoch+40` for a `windowStart+10`/`confirmTimeoutSec=30` schedule), proving the deadline
   math is deterministic and identical to a manually-triggered apply's.
4. **Spec/state changed between schedule and fire time** — `touchesMgmtPath` and full validation
   are recomputed at fire time, never trusted from schedule time. `fireSchedule` calls
   `Service.MgmtStatus` fresh (not the value `Schedule` computed) and then `Service.Apply`, which
   itself revalidates the changeset's ops against current live state before doing anything else
   (`beginApply`) — a newly introduced blocking finding aborts with zero steps executed.
   **Test:** `TestSchedule_RevalidationAtFireTime_Aborts` (mutates a live `*inventory.Graph` between
   schedule and fire time to introduce a `referential.already_exists` error via a fresh
   `bridge.create` name collision; asserts the fire aborts, no file is touched
   (`agent.committedFile` unchanged), and `changeset.schedule_fire_blocked` is audited).

## No mgmt-path override path anywhere — confirmed

`ScheduleParams` (the entire `POST /changesets/{id}/schedule` request schema) has no field capable
of bypassing the `touchesMgmtPath` gate — there is no `force`/`override`/`allowDangerousOps`-style
parameter documented in `docs/api.md` or accepted by `internal/api/schedules.go`'s decoder
(`DisallowUnknownFields` rejects anything not in the documented shape). At the service layer,
`Service.Schedule` checks `TouchesMgmtPath` unconditionally and returns
`*ErrMgmtPathUnattendedForbidden` with **no** reference to `s.allowDangerousOps` anywhere in that
code path — `allowDangerousOps` is consulted later in the same function only by `s.validate` (via
`safetyOptions()`), and only for the *unrelated* T-203 safety-interlock validation class,
independent of the mgmt-path check that already returned by that point. `TestSchedule_
MgmtPathForbidden_NoOverride` runs the exact same forbidden-schedule scenario with
`AllowDangerousOps` both `false` and `true` and asserts identical rejection either way — proving,
not just asserting, that the one config flag which *does* affect T-203's own interlock has zero
effect on this gate. `docs/security.md`'s Safety interlocks section now states this explicitly as a
"stricter, separate gate" from `allow_dangerous_ops`, not an application of it.

## Deviations from the task card (with reasons)

- **No `GET /changesets/{id}/schedule` route.** The card's deliverable list didn't ask for one, and
  none of the acceptance criteria need it; `Service.GetSchedule` exists and is exercised directly by
  tests, so adding the route later (T-1105/vnproxctl, or a UI status panel) is a small, additive
  change. Flagged here per the reporting convention rather than silently omitted.
- **`changeset_schedules` gained two columns beyond the card's literal list** (`status`, `fired_at`)
  — the card's parenthetical list read as illustrative rather than exhaustive (every comparable
  table in this codebase, e.g. `node_timers`, also carries its own status/resolved-at bookkeeping
  beyond what its owning task's prose enumerated). Without `status`, "resolve exactly once" can't be
  enforced at the SQL layer (`Resolve`/`Cancel`'s `WHERE status = pending` guard).
- **Single-use ack enforcement has no dedicated column.** The card doesn't specify the mechanism;
  reusing `Confirm`'s existing `awaiting_confirm`-only state check (rather than adding a `used_at`
  column) means `AckSchedule` is *by construction* just `Confirm` with a different auth check —
  smaller surface, and provably no route to a double-apply.
- **`missedWindowPolicy` "applyImmediately" uses the effective *fire* time, not the original
  `windowStart`, as the new window's start** — the card says "applies on restart with a fresh
  window"; anchoring the fresh window at "now" (when it's actually noticed) rather than the stale
  original `windowStart` is the only reading that produces a sensible `confirmTimeoutSec` countdown
  going forward instead of one that may already be in the past.
- **No `internal/pvemock` fixture changes** — every scheduling test needs only `single-node.yaml`
  (already required baseline) plus, for AC6, a hand-built in-memory `*inventory.Graph` (the same
  `inventorySource` seam `drift_closedloop_test.go` already established) rather than a live PVE
  state mutation, since the safety property under test (fresh revalidation) doesn't depend on which
  validator class fires.
- **Environment note, not a code deviation:** this worktree had no `web/node_modules` (a fresh git
  worktree checkout); `npm ci` was run once before `make check` could reach the frontend lint/test
  stages. Not part of this task's diff.
