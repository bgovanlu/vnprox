# T-907 · Saved views & annotations

## Summary

Implemented in full. Two additive, app-owned features on the topology page:

- **Named saved views**: reuses the existing per-user `layouts` table/route mechanism
  (`internal/api/layouts.go`, `internal/store/layouts.go`) rather than forking it — a saved view is
  just another `(username, name)` row whose opaque JSON blob happens to carry
  `{kind:"view", layers, vlanFilter?, zoom, viewport, selection?, view}` instead of the
  pre-existing `{positions, activeLayers, vlanFilter}` auto-layout shape. Added the two routes the
  original GET/PUT-only contract was missing for this to work as a picker: `GET /layouts` (list)
  and `DELETE /layouts/{name}`.
- **Shareable URLs**: the same view state round-trips through flat `/topology?svLayers=...` query
  params (`web/src/topology/savedViews.ts`), independent of any server-side row — a link opens
  correctly even for a viewer with no saved-view row at all, matching this codebase's existing
  `web/src/simulator/urlState.ts` convention rather than a new opaque-blob-in-URL scheme.
- **Annotations**: entity-pinned sticky notes in a **new** `annotations` table (not a `layouts`
  extension — see "Deviations" below), shared across every user, rendered in `InspectorPanel`'s new
  "Notes" tab.

## New/changed API surface (docs/api.md, docs/data-model.md updated in this same change)

**Saved views** (`internal/api/layouts.go`, extends the T-107 contract):
- `GET /layouts` (new) — `{items: [{name, layout, updatedAt}]}`, the caller's own saved
  layouts/views, `netRead`-gated, no CSRF (matches the existing PUT/GET precedent's own
  documented reasoning — a personal UI preference, not a network mutation).
- `GET /layouts/{name}` (existing since T-107, **retroactively documented** — had no `docs/api.md`
  entry before this task at all) — unchanged.
- `PUT /layouts/{name}` (existing) — unchanged wire shape; `layout` may now additionally be a
  `SavedViewPayload` (`{kind:"view", ...}`), still fully opaque to the backend either way.
- `DELETE /layouts/{name}` (new) — `204`, idempotent, `netRead`-gated, no CSRF.

**Annotations** (`internal/api/annotations.go`, brand new file):
- `GET /annotations` — `{items: [Annotation]}`, cluster/topology-wide (not user-scoped).
- `POST /annotations` — `{ref, content}` → `201` + created `Annotation`; `createdBy` server-stamped.
- `DELETE /annotations/{id}` — `204`, idempotent.
- All three `netRead`-gated, no CSRF — same precedent/reasoning as layouts, documented explicitly
  in `docs/api.md`'s new "Saved views & annotations" section (placed between "Blueprints" and
  "WebSocket").

`Annotation`: `{id, ref, content, createdBy, createdAt, updatedAt}`.

## Deviation flagged: annotations is a new table, not a `layouts` extension

The task explicitly asked me to flag this rather than fork silently. Reasoning (also in
`docs/api.md`/`docs/data-model.md` §2 and the migration's own doc comment): `layouts` is one opaque
blob per `(username, name)`, entirely overwritten on each `PUT` — a natural fit for "one named
preset." An annotation is structurally different on two axes: (1) **many rows per entity** (and
per user) rather than one blob per name, so individual create/delete needs row-level CRUD, not a
read-modify-write-the-whole-blob cycle; (2) **shared across every user** (a team scratchpad on the
map), not private per-user state like every existing `layouts` row. Cramming that into `layouts`
would mean synthesizing a fake per-note "name" and accepting lost-update races on concurrent
pin/unpin from two users. A dedicated table with normal `id`-keyed rows avoids both problems at
the cost of one more migration file — which the card explicitly permitted ("new store table or an
extension of `layouts` — document the choice").

## Bugs found and fixed along the way

Building the real e2e coverage (not just mocked Vitest) surfaced one genuine pre-existing bug this
task's own feature exposed, fixed in scope:

- **`VlanFilterInput.tsx`** kept its own local `draft` string initialized once at mount from the
  `value` prop, with no effect re-syncing it when `value` changed externally later. Loading a saved
  view (or a shareable-URL view) updates the store's `vlanFilter`, but the input kept showing
  whatever the user last typed/cleared — a real, user-visible bug for this feature (and latent for
  any other future programmatic vlanFilter setter). Fixed with a `useEffect` syncing `draft` from
  `value` (a no-op for the component's own Apply/Clear paths, since `draft` already matches by the
  time `value` updates from those). Added `VlanFilterInput.test.tsx` (4 cases, including "does not
  clobber an in-progress keystroke") since no test existed for this component before.
