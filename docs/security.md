# Security design

vnprox runs as root on hypervisor hosts and can reconfigure the network of an entire cluster. Security posture is therefore conservative by design.

## Authentication

- **No vnprox-local accounts.** Users authenticate with Proxmox credentials; vnproxd forwards to PVE `POST /access/ticket` (supports any PVE realm: PAM, PVE, LDAP/AD, OIDC, and TOTP/second factor passthrough via `otp`).
- On success vnproxd creates a server-side session: random 256-bit id in an `HttpOnly; Secure; SameSite=Strict` cookie. The PVE ticket + CSRF token are stored encrypted at rest (AES-256-GCM; key in `/etc/vnprox/keys/session.key`, root:root 0600, generated at install).
- PVE tickets expire at 2h; vnproxd renews at ~1h30 while the session is active. vnprox sessions idle out at 2h, hard cap 12h.
- CSRF: double-submit — mutating requests require `X-VNPROX-CSRF` matching the session record.
- Login rate limiting: per-IP and per-username token bucket; lockout events audited.

**Metrics scrape token (T-1001, addition).** `GET /metrics` (docs/api.md's Metrics-exporter subsection) is the **one documented exception** to this section's session-cookie model: a Prometheus scraper cannot carry a browser session cookie or a CSRF header, so it authenticates with its own bearer token instead of a PVE-derived session.

- A random 256-bit token, hex-encoded, generated on first daemon start (the same "generate if absent" convention the session key above uses) and stored at `/etc/vnprox/keys/metrics.key`, `root:root 0600`.
- Checked via `Authorization: Bearer <token>`, compared with `crypto/subtle.ConstantTimeCompare` — never a plain `==` (which would leak timing information about how much of the token matched).
- No PVE ticket is involved anywhere in this path: the token identifies "an authorized scraper," not a PVE user, and this route performs no PVE API calls of its own.
- A missing or invalid token is `401 not_authenticated`, using the same `{"error":...}` envelope every other route in this doc uses.
- Additive, optional **source-CIDR allowlist**: `[metrics] allow_from` in `vnprox.toml` (a list of CIDRs, nginx-`allow`-directive-shaped), checked *before* the token — a request from outside every listed CIDR is `403 forbidden` regardless of whether it carries a valid token. Unset (the default) allows any source, matching this route's own scrape-token gate being the sole required control in that case.
- `[metrics] enabled = false` disables the route entirely (not mounted; `cmd/vnproxd` never even loads/generates the token file) — surfaced read-only via `GET /config`'s `metricsEnabled` field.

This does not weaken the model above: every other route in this document still requires the full session-cookie/CSRF/PVE-ACL chain. `GET /metrics` is read-only, exports no secret, and its own separate token is the *sole* new credential this addition introduces.

**Automation tokens (T-1104, addition).** `docs/api.md`'s Tokens section (`POST/GET/DELETE /tokens`) lets a logged-in user mint a vnprox-local, capability-scoped bearer token for automation callers (CI, `vnproxctl`, Terraform/Ansible — T-1105/T-1106). This is explicitly **not** a second login/authentication path, and it is a different mechanism from both the credentials this section otherwise documents and from the T-1001 metrics scrape token above:

- **Distinguished from the PVE ticket bridge.** A cookie session's identity and capabilities come from *forwarding the user's own credentials to PVE* (`POST /access/ticket`) — the session doesn't exist until PVE has authenticated the user. A token never touches PVE at all: it is minted by an *already-authenticated* session (cookie **or** an existing bearer token) and is vnprox's own delegated credential, checked entirely against vnprox's local `api_tokens` table. Presenting a token never creates a PVE ticket, never calls `POST /access/ticket`, and is invisible to PVE's own audit log — only vnprox's.
- **Distinguished from the metrics scrape token.** That token identifies "an authorized scraper" (a fixed, single, unscoped, install-time-generated credential with no user attached). An automation token identifies a *specific minting user* (`created_by`), is *dynamically mintable* any number of times, and is *capability-scoped per token* — the two are unrelated bearer schemes serving different purposes, both layered onto the same `Authorization: Bearer <token>` header convention rather than each inventing its own.
- **Minting, not a second privilege source.** `POST /tokens` validates every requested scope against the minting session's *own, currently-derived* capabilities (`internal/auth.Identity.ValidateScopeGrant`) — a token's scopes can never exceed what the creating user could already do at mint time. The one addition to the capability vocabulary, `automation` (gating the WS `"events"` topic and the webhook routes, `docs/api.md`'s WebSocket/Tokens & Webhooks sections), is never derived from a PVE privilege at all — it exists purely as a token scope, so a browser session alone can never reach those routes, only a minted token can.
- **Storage.** The raw token value is never persisted — only its hex-SHA-256 hash (`api_tokens.token_hash`), the same one-way-hash convention GitHub/GitLab personal access tokens use; `POST /tokens` reveals the raw value exactly once, at creation.
- **Revocation is immediate.** `DELETE /tokens/{id}` sets `revoked_at` (rejecting the token's next request with `401`) and force-closes any live WS connection that token authenticated in the same request (`internal/topology.Hub.CloseByTokenID`, using an immediate `CloseNow` teardown rather than a graceful close handshake, which could otherwise block the revoking request for several seconds waiting on an uncooperative peer).
- **Rate-limited and audited like every other credential in this document:** a per-token token-bucket (burst 60, refill 1/s by default) bounds a single token's request rate independent of the per-IP/per-username login limiter above; every authenticated use is audited (`token.use`), alongside `token.create`/`token.revoke` on the lifecycle routes themselves.
- CSRF is skipped for bearer-authenticated requests (there is no cookie to double-submit), the same precedent the metrics scrape token already sets for a non-cookie credential — every other control (rate limiting, audit, capability enforcement) still applies in full.

**Embed tokens (T-1706, addition).** `docs/api.md`'s Embeds section (`POST /embed/tokens`, `GET /embed/{map,dashboard,posture}`) lets a logged-in user mint a **read-only, token-scoped** embed of the map / home dashboard / posture report for a wiki, NOC screen, or status page. An embed token is a special case of the automation token above — an ordinary `api_tokens` row, same storage/revocation/rate-limit/audit machinery — with two extra, security-defining constraints:

- **A hard read-only ceiling, enforced server-side at mint.** `POST /embed/tokens` restricts scopes to the read-only subset `{netRead, sdnRead, fwRead, audit}` and rejects **any** other scope (`netWrite`, `sdnWrite`, `fwWrite`, `guestNet`, `capture`, `automation`) with a `400`, *before* the ordinary per-user ceiling check and **regardless of the minting user's own capabilities** — even a full-privilege admin cannot mint a write-capable embed token. Combined with the inherited `ValidateScopeGrant` ceiling, an embed token can never exceed its minting user's own scope and never carries a write surface. There is deliberately **no persisted `embed` column** (no schema change / forward-only-migration cost): "embed" is defined structurally by the read-only scope set, which the view-route auth re-checks on every request (a token carrying any write scope is refused at an embed route, `403`).
- **A distinct authentication path — never a session cookie.** The `GET /embed/{view}` shell routes have their own middleware that reads the token from the `?token=` query parameter **only** (an `<iframe>` cannot set an `Authorization` header) and **never inspects the session cookie** — a first-party browser session is never accepted in place of an embed token, so an embed pane cannot be silently authenticated by a logged-in operator's ambient cookie. The embedded view then reaches the ordinary `netRead`/… -gated read routes with the same token as a bearer credential, so no parallel, less-guarded read path is introduced. On the frontend the mirror holds: in embed mode the shared fetch wrapper sends the bearer token and sets `credentials: "omit"`, never falling back to the cookie.

**WireGuard tunnel keys (T-1401, addition).** A site-to-site WireGuard tunnel's private key is a new class of at-rest secret, stored under the **identical** AES-256-GCM primitive this section already documents for `sessions.pve_ticket_enc` — `internal/store.SessionCipher`, keyed from `/etc/vnprox/keys/session.key`, **not a second cipher or key pair** — in the `wireguard_tunnels.private_key_enc` column (docs/data-model.md §9, docs/api.md's WireGuard section).

- **Key custody.** The keypair is generated *on the owning node* via stdlib `crypto/ecdh`'s X25519 curve (`internal/wireguard.GenerateKeypair` — no new third-party crypto dependency) as part of applying a `wg.tunnel.create` changeset op, sealed once, and **never returned by any API response, log line, or audit-log detail**. Only the derived public key is exportable (`GET /wireguard/tunnels/{id}/pubkey`); `internal/wireguard.ParseDump` deliberately discards the interface's private-key column when polling live state. A tunnel's key is never regenerated in place — rotation is delete-and-recreate, always two ordinary audited changeset ops, never a silent overwrite. An optional per-peer preshared key uses the same sealed column shape (`wireguard_peers.preshared_key_enc`).
- **No new mutation path.** Every WireGuard change flows through the ordinary change engine (`internal/change`'s `wg.*` op family) — stage→validate→diff→apply→confirm/rollback — exactly like every other mutation; there is no dedicated WireGuard write route. The on-node apply step writes the wg-quick config and execs `wg`/`wg-quick` with a **fixed argv array** (no dynamic shell interpolation), mirroring the `ifreload`/`lldpctl` subprocess convention in the Host footprint section below.
- **Management-path interlock (no override).** A `wg.*` op on a tunnel whose carrier interface is itself part of a node's resolved management or corosync path is `touchesMgmtPath: true`, inheriting T-703's ceremony (typed node-name acknowledgement, 180s confirm-window floor) with **no override** — the "no override in UI" rule in the Safety interlocks section is unamended by this addition.
- **Residual risk, stated plainly.** An *external* peer's key material is never vnprox's to protect — peers outside vnprox's control are modeled read-only with config export only, and their own key hygiene is explicitly out of scope (surfaced in the operator-facing peer-config export copy, not papered over).

**Apply-time revert ticket (T-1805, addition; `docs/roadmap-proven.md` decision **D1**).** The commit-confirm safety net — "if the change locks you out, it reverts itself" — held for everything the daemon can undo as root, and **did not hold** for PVE firewall and SDN changes, because those are written with the *user's own* ticket (Authorization below) and no such credential survives the request that applied them. A `fw.*`-only changeset that reached `awaiting_confirm` and then timed out was simply never reverted (`planning/reports/T-502.md`). D1 closes that hole by introducing a new, deliberately short-lived at-rest credential class: `changesets.revert_ticket_enc` (docs/data-model.md §2, migration 0033).

- **Sealed with the one key, like every other credential class in this document.** AES-256-GCM via `internal/store.SessionCipher`, keyed from `/etc/vnprox/keys/session.key` — the **identical** primitive and key `sessions.pve_ticket_enc`, `clusters.credential_enc`, `oidc_pve_links.credential_enc`, `switches.credentials_enc` and `wireguard_tunnels.private_key_enc` use, **never** a second cipher or key pair. It is never returned by any API response, never logged, never in an audit detail (the audit trail records only *that* a sealed credential was used — `sealedRevertTicketUsed` — and the coverage decision, never anything about its value); regression-tested by `TestChangesetRepo_RevertTicketEncryptedAtRest` (ciphertext + raw-DB-file bytes) and `TestRevertTicket_AC3_NeverLeaksToAnySurface` (one case per surface: apply response, changeset read, list, audit log, daemon log, WS broadcasts, raw DB file).
- **Bounded from both ends, unconditionally.** Captured immediately before the apply's first mutating step (so a daemon killed mid-apply can still use it, not only one killed mid-window), and wiped on confirm, on manual rollback, on the commit-confirm timeout's own rollback, on a failed or crash-interrupted apply, on discard, and by a ticket-expiry sweep at daemon startup — whichever comes first. The wipe is not best-effort: it runs inside the same lock hold as the terminal status transition and even when that transition's own persist failed.
- **It authorizes exactly one thing.** The sealed bytes have no field on any read model (`store.Changeset`, `change.Changeset`, or any API response type), so nothing that renders a changeset *could* carry them. The single reader, `store.ChangesetRepo.RevertTicket`, is reached only from that one changeset's revert path. Verified by enumeration over the real registries — every route the production router registers (`chi.Walk` + drive), every tool in the frozen MCP allowlist, and every plugin extension point — not by convention.
- **It cannot outlive, or extend, the user's own session.** The revert acts through a *non-renewing* sealed-ticket PVE client (`pve.Config.Ticket`/`CSRFToken`): it never calls `POST /access/ticket`, so the daemon can never mint itself a fresh credential from a sealed one. When the ticket expires, PVE answers 401 and the revert reports the scopes it could not restore, landing the changeset in the distinguishable "rollback incomplete" state rather than a silent `rolled_back`.
- **Expiry is surfaced, never swallowed.** A PVE ticket lives ~2h. `POST /changesets/{id}/apply` returns `unattendedRevert` (docs/api.md) stating whether unattended revert is available and until when; a confirm window that would outlive the ticket reports reduced coverage **at apply time**, and the review dialog says plainly, before apply, which parts of the changeset depend on the sealed session.
- **Not replicated.** T-1704's HA state push deliberately does not carry this column: the sealed ticket stays on the daemon that armed the timer rather than being copied to a second host. An HA failover mid-window therefore leaves the firewall/SDN portion where it was before T-1805 (node files still revert unattended) — a stated residual, not a regression.
- **Not a second mutation path.** The revert runs the existing rollback machinery with a credential it previously lacked. No new op type, no new route, and nothing about this addition applies anything.

**OIDC SSO (T-1207, addition).** For federated deployments where per-cluster PVE credentials stop scaling, vnproxd offers OIDC login alongside the PVE ticket bridge — an OpenID Connect authorization-code + PKCE flow (`GET /auth/oidc/login`, `POST /auth/oidc/callback`, docs/api.md's Auth section), configured in `vnprox.toml`'s `[oidc]` section (`issuer`, `client_id`, `client_secret_file`, `redirect_url`, `scopes`, `groups_claim`, and a group→role mapping table). The precise split it draws is the load-bearing point:

- **OIDC authenticates the human to vnprox; PVE authorization still gates every cluster-scoped action per cluster.** An OIDC identity holds no PVE ticket by itself. A cluster-scoped action therefore still needs a resolved PVE authorization for that cluster: an admin-configured OIDC-group→PVE-identity mapping (the encrypted `oidc_pve_links` store table, docs/data-model.md §2), or — where no mapping exists — a first-use PVE-credential prompt. There is **no third path**: an OIDC login with no PVE linkage for a cluster is authenticated but holds **zero** cluster-scoped capability there (proven by T-1207's AC2 table/integration tests), never the OIDC bundle alone.
- **OIDC-derived capabilities are never additive beyond the linked PVE identity's own ACLs.** The group→role mapping maps OIDC group claims to a vnprox capability bundle (the same `internal/auth/caps.go` vocabulary the PVE-privilege mapping uses); that bundle is then **intersected** with the linked PVE identity's live-derived PVE ACLs (`internal/auth.IntersectCaps`, applied at the same `deriveCapabilities` point `forceReadOnly` uses, on both login and hourly re-derivation). The intersection can only ever *narrow* the PVE side — an OIDC bundle can never grant a capability the user's real PVE ACLs don't (T-1207 AC3), mirroring this section's "vnprox cannot exceed the user's PVE ACLs" invariant exactly.
- **Session lifecycle is the existing one.** An OIDC session is an ordinary server-side session — the identical HttpOnly/Secure/SameSite=Strict cookie, encrypted-at-rest session store, idle (2h) and hard-cap (12h) timeouts, and CSRF double-submit as a ticket-bridge session (T-1207 AC1/AC4). The one difference is renewal: where the ticket bridge renews the PVE ticket at ~half-life, an OIDC session renews via the IdP's **refresh token** (rotated and re-verified on each refresh); the OIDC ID/refresh tokens are never persisted in the app store, only the derived capabilities and (encrypted) an empty PVE-ticket placeholder.
- **Secrets at rest.** The OIDC **client secret** lives in `client_secret_file` (a `root:root 0600` file, the same on-disk-secret convention the session/metrics keys use), never inlined in the config in the clear. The mapped **PVE credentials** in `oidc_pve_links.credential_enc` are sealed with the **identical** AES-256-GCM `internal/store.SessionCipher` primitive `sessions.pve_ticket_enc`/`clusters.credential_enc` use — not a second cipher or key pair. **ID-token verification** is RS256-only against the IdP's published JWKS (issuer/audience/expiry/nonce all checked); `alg: none`/HS* are rejected outright, closing the classic alg-confusion downgrade rather than trusting the token's own header.

**Cluster-registry credentials (T-1201, addition).** Federation attaches N PVE clusters as app-owned registry rows (`clusters` table, docs/data-model.md §2); each cluster's own PVE API credential (a token or a ticket-bridge username/password used only for that cluster's `internal/pve.Client`) is sealed in `clusters.credential_enc` with the **identical** AES-256-GCM `internal/store.SessionCipher` primitive `sessions.pve_ticket_enc` uses — **not a new cipher, key, or on-disk secret**: one key (`/etc/vnprox/keys/session.key`) still seals every at-rest credential class in this document. The plaintext credential is never returned by any `/federation/clusters` response, log line, or audit detail (`internal/federation.Service` unseals only to construct a per-cluster client, and `TestService_CredentialCiphertextNeverContainsPlaintext` asserts the stored bytes never contain the plaintext token). Federation federates *reads*; it introduces **no** cross-cluster mutation primitive — `internal/change` rejects at validation any op whose target Ref belongs to a different cluster than the changeset's `clusterId`, so an attached cluster's credential can never be used to write to another cluster's config.

**Switch-driver credentials (T-1205, addition).** The guarded switch-config-push surface stores each registered switch's driver credential (gNMI/OpenConfig auth) in `switches.credentials_enc`, sealed with the **same** `internal/store.SessionCipher` primitive as every credential class above — not a second cipher or key pair (`TestSwitchRepo_CredentialsEncryptedAtRest` asserts the stored bytes never contain the plaintext credential and only the cipher recovers it). The plaintext is never returned by any API response, log line, or audit detail. Switch push **ships dark by construction**: no push is possible unless both the daemon-level `[switches] enabled` flag *and* the specific switch's `enabled` row are true, and every push is an ordinary change-engine changeset (`switch.port.update`, VLAN-membership/description/LACP only) — the mgmt-path interlocks extend one LLDP hop onto the uplink port carrying a node's management path, hard-blocked (`safety.protected_switch_port`, no override) if a push's net effect would strip that port's management VLAN. A switch that becomes unreachable after a push cannot be remotely reverted (there is no recovery agent living on the switch): that residual risk is stated plainly to the operator, and such a changeset lands in a distinguishable "rollback incomplete — needs manual intervention" state rather than being silently marked `rolled_back`.

**Git spec-sync credential (T-2701, addition).** The git-backed spec sync (`internal/gitsync`, `[gitsync]`, docs/api.md's "Git spec sync") reads one file from one ref over plain HTTPS. Its host credential is a **file-based secret, never a config value**: `[gitsync] token_file` names a `root:root 0600` file — the identical on-disk-secret convention `[oidc] client_secret_file`, `[pve] token_file` and the session/metrics keys already use. Four properties bound it:

- **It exists only as a request header.** The credential is read once at startup and sent as `Authorization: Bearer` (GitHub/raw) or `PRIVATE-TOKEN` (GitLab). It is never placed in a URL — a URL that *embeds* credentials is refused at construction with a message that does not echo them — and it is not formatted into any error this package produces. A non-2xx answer is reported as "GET <url>: status N"; the **response body is deliberately never echoed**, because a hosting provider's 401 body routinely quotes the request (and therefore the credential) back.
- **Four surfaces, one assertion each.** `TestAC6_CredentialNeverAppearsOnAnySurface` drives the real HTTP source with a real token through a successful cycle and a 401 cycle, then scans the daemon log, the findings stream, the audit rows and `gitsync status` output. It runs two controls first — the mock host must actually have been presented with the token, and each surface must contain a known non-secret marker — so a scan looking in the wrong place, or a credential that was never in flight, fails loudly instead of passing vacuously.
- **No new at-rest credential class.** Nothing about this feature is stored in SQLite: the token stays in the file the operator wrote it to. There is no `gitsync_*` sealed column, and the backup/support-bundle secret-class inventories are unchanged.
- **It authorizes a read, and only a read.** The sync never pushes, never opens a branch, and never authenticates a write on this path (that is T-2702, explicit and operator-initiated). A leaked sync token is a read of a spec repository, not a route into the cluster: the sync's only effect on vnprox is a **draft changeset a human still reviews and applies**.

**Commit-signature verification is local, and fails closed (T-2701).** With `[gitsync] require_signed_commits`, a commit proceeds only if vnprox itself verifies its signature against the operator's own `allowed_signers_file`. The host's own "verified: true" boolean is never the deciding fact — it is not consulted at all. Verification covers git's SSH-format signatures (`gpg.format = ssh`) with ed25519 and `rsa-sha2-256/512` keys, implemented against OpenSSH's PROTOCOL.sshsig with the **standard library only** (SHA-1 `ssh-rsa` signatures are refused). Every other case is a refusal, not a pass: an unsigned commit, an OpenPGP signature (unverifiable without adding a deprecated third-party dependency — the decision is recorded in `internal/gitsync`'s doc comment), a malformed armor block, a signature made under a different SSHSIG namespace, a key absent from the allowed-signers list, and a host that cannot supply the signed commit object at all (GitLab and plain raw hosts). Each refusal raises a finding naming the reason and stages nothing.

**Residual risk, stated rather than papered over (T-2701).** Because the sync fetches over the host's HTTPS read API rather than the git object protocol, vnprox has no local object graph. Verifying a signature therefore proves that *the commit object the host reported for this ref* was signed by a trusted key; it does not, by itself, prove that the separately fetched file bytes are the blob under that commit's tree. Establishing that binding needs pack negotiation and object-graph traversal, which this card deliberately did not take on (see the git-access decision in `internal/gitsync/doc.go`). A hostile *host* is therefore inside the trust boundary for file content — the same position `git clone` over HTTPS puts an operator in — while a hostile *network position* is not, since the fetch is TLS-verified and the signature check is local. And in every case the blast radius is bounded by the invariant the whole feature rests on: the worst a compromised spec can produce is a **draft changeset**, which a human reviews and applies through the ordinary commit-confirm path.

**Web push subscriptions and VAPID identity (T-2005, addition).** `docs/api.md`'s Web push family (`GET /push/vapid-public-key`, `POST/GET/DELETE /push/subscriptions`) lets a logged-in session register this browser to receive web-push notifications for critical findings, changesets awaiting confirm, and drift — `docs/features/monitoring.md` §11 has the full feature writeup; this entry is the credential/at-rest half.

- **This daemon's own VAPID identity.** An ECDSA P-256 keypair (RFC 8292), generated on first daemon start — the identical "generate if absent, `root:root 0600`" convention the session/metrics/blueprint-signing keys above already establish, via `internal/push.GenerateVAPIDKeyFile`. Ship no default key. Only the public half is ever exposed (`GET /push/vapid-public-key`, and as RFC 8292's `Authorization: vapid ... k=` header parameter on every delivery); the private half signs an RFC 8292 JWT per push and never leaves the daemon.
- **A subscription's endpoint and keys are a credential, sealed like every other class in this document.** `push_subscriptions.endpoint_enc`/`p256dh_enc`/`auth_enc` (migration `0046_push_subscriptions.sql`) are AES-256-GCM ciphertext under the **identical** `internal/store.SessionCipher` primitive `sessions.pve_ticket_enc` and every credential class above use — not a second cipher or key. Anyone holding a subscription's raw endpoint+keys can push arbitrary payloads to that browser until it unsubscribes, which is why `GET /push/subscriptions` returns only display metadata (id, categories, device label, timestamps) and never decrypts them for a read. `endpoint_hash` (unencrypted, one-way SHA-256 of the same endpoint) exists purely so a resubscribe to the same push-service endpoint can be recognized without decrypting an existing row — the identical hash-for-lookup/encrypt-for-storage split `api_tokens.token_hash` uses for a different reason.
- **Subscriptions are per-session and die with it, structurally.** `push_subscriptions.session_id REFERENCES sessions(id) ON DELETE CASCADE` — the database already opens with `_pragma=foreign_keys(1)`, so a logout or session-expiry sweep removes every subscription that session created in the same transaction. No cross-package cleanup hook to keep in sync; `TestPushSubscriptionRepo_DiesWithItsSession` (`internal/store`) proves it and, as a control, that an unrelated still-live session's own subscription survives the same delete untouched.
- **A push notification is a deep link, never an action token — this is a hard invariant, not an implementation detail.** `web/public/sw.js`'s `notificationclick` handler only ever navigates an open (or newly opened) tab to an app-relative URL; it holds no session of its own and cannot call any API. Confirming a changeset from a lock-screen notification still goes through the confirm route's ordinary authenticated-session + capability check on whatever page the click lands on, exactly as if the operator had typed the URL in by hand — the notification shortens the path to the right screen, it does not shorten the authorization chain.
- **The payload itself carries no cluster-identifying content.** `internal/push.Notification` (`payload.go`) is a closed, four-field shape built from Go string literals at the call site plus at most one caller-supplied value (an opaque changeset ULID, `internal/store.NewULID` — no embedded identity). No `Finding` field (id, detail, nodes, refs — all of which routinely embed a node or guest name) is ever threaded through, even for the notifier that is invoked with a full `findings.Finding` on every qualifying transition. This is the enumerated-outbound-payload discipline the Compatibility-telemetry section below documents for `internal/telemetry.Guard`, applied to web push: `TestCriticalFindingNotification_NeverContainsInjectedIdentity` seeds a finding whose id/detail/nodes/refs are deliberately hostname/IP-shaped and asserts none of it reaches the marshaled payload, with a positive control proving the search itself would have found it.
- **The service worker never caches an authenticated response.** `web/public/sw.js`'s fetch handler explicitly bypasses `/api/*` for both reading and writing its cache — a shared device (a kiosk, a family member's laptop) where a second vnprox session logs in after this one must never be able to read the first session's cached API data back out of the offline shell.

## Backup archives (T-1901)

`vnproxctl backup` produces a file that leaves the hypervisor — to a NAS, an object store, a
colleague's laptop, a support ticket. That makes the archive its own trust boundary, and this
section is its threat model. The deployment-facing description is in `docs/deployment.md`,
"Backup and disaster recovery".

**The archive's contents are exactly two things**: a consistent copy of vnprox's own SQLite store
(`VACUUM INTO`, not a file copy — WAL mode means `cp vnprox.db` silently drops committed
transactions) and `vnprox.toml`. It contains **no** Proxmox configuration: `/etc/network/interfaces`
and `/etc/pve` are PVE's, and vnprox never shadows them.

- **A default backup carries no secret in the clear, and that is a structural property, not a
  policy.** Every credential class in this document is either a `*_enc` column (AES-256-GCM
  ciphertext under `internal/store.SessionCipher`) or a `*_hash` column (one-way SHA-256) — there is
  no plaintext secret column anywhere in the schema. The session key that opens the sealed columns
  lives in `/etc/vnprox/keys/session.key` and is **not collected**. So an attacker holding a default
  archive holds ciphertext and hashes: the store's whole history, and nothing they can authenticate
  with. `internal/backup`'s declared secret-class inventory is checked against the real migrations
  by a test, so a new sealed column landing without an inventory entry fails the build rather than
  silently escaping this claim.
- **`--include-keys` is a categorically different artifact, and is marked as one.** It adds the
  session key, the PVE API token, the metrics scrape token, the blueprint signing key and the OIDC
  client secret in the clear — which, because the session key is among them, makes every sealed
  column readable too: PVE tickets, federation credentials, OIDC-mapped PVE credentials, switch
  credentials, WireGuard private and preshared keys, Kubernetes kubeconfigs, webhook and alert
  secrets, ingress credentials, and T-1805's sealed revert tickets. It therefore prints a warning
  naming each of those classes before writing anything, requires an interactive confirmation (or an
  explicit `--yes`, which still prints the warning), sets `includesKeyMaterial: true` in the archive
  manifest, and suffixes the filename `-with-keys` so the marking survives an `ls`, an rsync log, or
  a filename pasted into a chat window. Such an archive is equivalent to `/etc/vnprox/keys` and must
  be stored the same way. Every archive is written `0600` regardless.
- **The peer cluster secret is never collected**, under any flag. It is cluster-shared state on
  pmxcfs (`/etc/pve/priv/vnprox/`), replicated by Proxmox itself — not this node's to hand out.
- **On restore, the archive is hostile input.** It is whatever file an operator was handed, and the
  extraction target is a root-owned directory on a hypervisor. The reader enforces, in a pass that
  writes nothing to disk at all: an allowlisted entry-name vocabulary (traversal, absolute paths and
  backslashes are not *expressible*, rather than filtered); regular files only (a symlink or hardlink
  entry — the standard way to redirect a later "safe" write — is refused outright); absolute,
  streamed budgets on manifest size, per-entry size, total size and entry count, so a decompression
  bomb is stopped at the tar header that declares it rather than after it has filled the disk; and
  an exact match between every entry and the manifest's declared name, order, size and SHA-256, with
  the gzip checksum verified at the end. Undeclared, duplicate and trailing entries are all
  refusals.
- **A restore is a mutation of the daemon's own authoritative state.** It refuses to run against a
  live daemon — detected both by an advisory lock vnproxd holds on `<db>.lock` for its lifetime and
  by probing `[server] listen`, so a pre-v3.2 daemon that takes no lock is still caught — and it
  refuses a store from a **newer** schema than the running binary understands (forward migration is
  supported and automatic; downgrade is not). That version check is made against the manifest *and*
  re-made against the store actually inside the archive, so an edited manifest cannot smuggle a
  newer store past it. The swap itself is atomic: extract and migrate in a private directory beside
  the target, then two renames within one directory, with the previous store put back if the second
  fails and **kept** at `<db>.pre-restore-<UTC>` on success.
- **Residual risks, stated rather than papered over.** (1) The archive is not encrypted and not
  signed: integrity is per-entry SHA-256 against a manifest that travels inside the same file, which
  detects corruption and casual tampering but is not an authenticity control — an attacker who can
  rewrite the archive can rewrite the manifest with it. Use the transport and storage you would use
  for any other root-owned artifact, and note that the store it installs is app-owned history, not a
  mutation path: restoring a forged archive cannot by itself change the cluster's network, because
  every mutation still flows through the change engine. (2) A default archive still exposes
  *metadata* — node names, interface names, IP addressing, changeset titles, the audit trail's
  usernames and actions. That is not a secret class, but it is a map of the network, and it should
  be treated as sensitive even though it carries no credential. (3) `--restore-keys` overwrites this
  node's key material with another node's; existing files are moved aside rather than deleted, but
  the operator owns that decision.

## Support bundles (T-1902)

A backup archive is something an operator stores. **A support bundle is something an operator
posts.** It is going to be attached to a forum thread, a GitHub issue, or a mail to a stranger who
offered to help — so its threat model is not "someone steals it", it is "it was published on
purpose, by someone who trusted us to have removed the credentials". The deployment-facing
description is in `docs/deployment.md`, "Support bundles".

The design rule is **redacted by construction, not by review**:

- **A bundle's collectors cannot declare a secret class, structurally.** `internal/backup`'s
  `Collector` interface (which a *backup*'s collectors implement) has an `Emits() []SecretClass`
  method precisely so `--include-keys` can print an honest warning. A bundle's collectors implement
  a different, narrower interface with **no `Emits` method at all**, adapted by a single wrapper
  whose `Emits()` returns nil unconditionally. There is therefore nowhere for a bundle collector to
  declare an emitted secret, and consequently no flag, environment variable or config value that
  makes `secretClasses` in a bundle's manifest non-empty or `includesKeyMaterial` true. That the
  empty declaration is also *honest* is a separate claim, proved by a table-driven scan (below).
- **Every emitted field is declared, and the declaration is enforced by reflection.** Each
  structured document a bundle emits is a Go type whose every exported field is declared with a
  disposition (`emit` / `scrub` / `redact-json` / `allowlist`) and a written reason it is safe to
  publish. A test walks the real types and fails in both directions: an undeclared field is a value
  nobody decided was publishable, and a declaration with no field behind it means the inventory has
  stopped describing the code. Critically, a field whose type reflection cannot see through — a
  `json.RawMessage`, an `any`, a map — **may not be declared as plainly emitted at all**; it has to
  name a redactor. That is "an explicit allowlist or a redactor" made mechanical.
- **The store is not in a bundle.** `store/vnprox.db` holds the full audit trail, every rollback
  snapshot, and the ciphertext of every sealed credential. A bundle carries derived facts instead —
  schema version, migration state, `integrity_check`, per-table row counts, and the last N redacted
  changesets — read through a `query_only` connection so that inspecting a store whose migration
  failed cannot become the thing that migrates it.
- **Two open-ended file formats are re-emitted through allowlists rather than copied.**
  `vnprox.toml` is rendered key by key (a key not on the allowlist keeps its *name* — knowing
  `[oidc]` is configured is diagnostic — and loses its value, so `[pve] dev_ticket_password` is
  redacted whether or not anyone remembers it exists). `/etc/network/interfaces` is parsed with
  vnprox's existing AST and re-emitted option by option: an operator's interfaces(5) file can
  legitimately carry `wireguard-private-key`, and emitting that file verbatim would be the single
  most damaging thing this feature could do.
- **Free-form text passes a value redactor.** Log lines, changeset titles, apply-log output,
  certificate subjects and validation errors have no finite field set to allowlist against, so they
  are matched against credential *shapes* rather than known values: PVE tickets, `PVEAPIToken=`
  headers, `Authorization:` headers of any scheme, URL userinfo, `<named-key> = <value>`
  assignments, bare 43-character base64 (the wire form of a WireGuard private key, a preshared key,
  and vnprox's own session key), and PEM private-key blocks. Everything removed is replaced with a
  single fixed marker, so a reader can grep for what is missing. The redactor is idempotent and is
  tested in both directions — it must remove the credential *and* leave the surrounding diagnostic
  intact, because a bundle that redacts everything is useless and would pass a naive leak test.
- **Changeset ops are walked by key name, not by known field.** `internal/api`'s `redactOpSecrets`
  strips one known field from one known op type, which is right for a `[]change.Op` response and
  wrong for an archive that must be safe against the op type that lands next phase. The bundle walks
  the stored JSON and redacts any value under a key matching the credential vocabulary, plus
  `*_enc` / `*_hash` suffixes, so a sealed field invented later is covered the day it appears.
  Unparsable JSON is replaced wholesale: "I could not parse it" and "I know it is safe" are not the
  same statement.
- **The leak test is the one that matters, and it has controls.** A bundle is produced from an
  installation seeded with one marker per declared secret class — and, crucially, with those markers
  planted in the places a bundle *actually reads* (the interfaces file, the log, `vnprox.toml`, a
  changeset's four JSON columns), because seeding them only into the store would make every
  assertion pass trivially. The whole decompressed archive is then scanned, one case per class.
  Four controls run first — a changeset title, an allowlisted interfaces option, an allowlisted
  config value and an ordinary log line, each of which **must** be found — so that a scan looking in
  the wrong place, a collector that did not run, or a redactor that ate everything fails loudly
  instead of producing green subtests that assert nothing.
- **Residual risks.** (1) A bundle is not encrypted or signed; it is meant to be published, so
  confidentiality is not its property — but note that means a bundle you receive is not proof of
  anything about the machine it claims to come from. (2) A bundle still exposes *metadata*: node
  names, interface names, IP addressing, VLAN ids, changeset titles and authors. That is a map of
  the network, it is the price of being diagnosable, and the generated `readme.txt` says so in the
  file itself. (3) The local `/api/v1/health` read and the peer reachability probe do not verify
  TLS — they send nothing and no credential, and exist to *report* the certificate they were shown,
  but a machine-in-the-middle on the management network could therefore influence the reported
  health status and certificate metadata in a bundle. `--no-probe` makes a bundle from local files
  only.

## Compatibility telemetry (T-2503)

A support bundle is something an operator posts once, deliberately, about a problem. **Compatibility
telemetry is something an operator opts into repeatedly, about a machine that is working fine** — so
it gets a stricter rule than "redacted by construction": it is *enumerated* by construction. There
is a fixed list of fields, it is below, and a field that is not on it does not exist in the code.

**It is off, and off is structural.** `[telemetry] enabled` defaults to `false` and the shipped
`/etc/vnprox/vnprox.toml` ships the section commented out entirely. There is also **no default
endpoint**: vnprox runs no telemetry service, so opting in means naming an `https://` collector
yourself. With either half missing, `internal/telemetry.Submit` returns before an HTTP client is
constructed — the "nothing was sent" claim is asserted in tests by a transport that fails the test
if it is called at all, with a control case proving that same transport *does* record a call when
something genuinely reaches the network.

**What you see is what is sent.** `vnproxctl telemetry preview` prints the exact bytes. Not an
equivalent rendering: the payload is marshalled exactly once into a buffer, and preview writes that
buffer while send posts that same buffer. A test captures the output of the preview command and the
body observed by the transport and compares them byte for byte.

**What is collected — the complete list.** Every field below is compared against the payload struct
on every `make check` (`internal/telemetry.TestDocSectionMatchesPayload`), in both directions: a
field added to the code without a row here fails the build, and a row here with no field behind it
fails too.

| Field | Type | What it is | Why it carries no identity |
|---|---|---|---|
| `payloadVersion` | number | The reduction's schema version, currently `1`. | A constant compiled into the build. |
| `installId` | string | A ULID generated locally on first send; the only correlator. | Random (crypto/rand), never derived from the machine, resettable with `vnproxctl telemetry reset-id`. |
| `vnproxVersion` | string | The `vnproxctl` build that ran the suite, e.g. `3.0.3`. | The same string for everyone running that release. |

| `nicPciIds` | string list | PCI `vendor:device` ids of the NICs seen, e.g. `0x8086:0x1521`. | Hardware model ids. The interface names and modalias strings that sit beside them in the report are dropped, because `tap101i0` names a guest. |

**What is deliberately absent**, all of which the report being reduced *does* contain: node names,
the PVE endpoint URL, any IP address, any MAC, any guest name, the cluster name, every check's
`detail`/`skipReason` free text, and every `evidence` body (which routinely quotes command output,
API responses and addresses). No timestamp of ours is sent either — the collector's receipt time is
enough, and a local clock is a fingerprint.

**The payload is checked, not trusted.** Immediately before any send, and again before any preview,
the marshalled bytes are scanned by `internal/telemetry.Guard`, which runs on the *payload* rather
than on the *type* — a `string` field named `kernel` can hold a hostname, and the requirement is
that such a payload fails rather than ships. Three layers:

- **Shape rules**: anything that parses as an IPv4/IPv6 address, anything MAC-shaped, and any dotted
  FQDN-shaped name, wherever in the document it appears — object keys included.
- **Known-value rules**: hostnames and guest/cluster names have no recognisable shape, so the node
  names and endpoint host of the report being reduced are searched for as literal substrings. This
  over-matches on purpose: a node genuinely named `pve` matches the `-pve` in a Proxmox kernel
  string and that install refuses to send until it is renamed. A refusal costs a data point; a miss
  costs somebody their hostname.
- **A closed schema**: every key must be one of the documented fields and every value must match its
  documented shape (`installId` must be a ULID, `checks[].status` must be one of three words,
  `nicPciIds` entries must be `0xVVVV:0xDDDD`). There is no pass-through branch, so an
  undocumented field cannot be sent even if it were added to the struct.

There is one exemption, stated rather than hidden: the FQDN shape rule does not run on
`checks[].id`, because `drift.config_vs_live` is shape-identical to a hostname and the rule would
refuse every payload ever built. That field is instead bounded by the closed schema, is populated
only from the compiled-in check registry, and is still scanned by the MAC, address and known-value
rules.

**Reset.** `vnproxctl telemetry reset-id` deletes the stored id and inserts a fresh ULID; no query
returns the old value afterwards, and nothing records what it was — no audit row, no log line, no
"previous" column. The honest residual: SQLite may retain the freed page holding the old string in
the database file until that page is reused or the store is compacted, so a reset is a promise about
what the store *returns*, not about raw bytes on the disk.

**Failure is never fatal.** A send from `vnproxctl verify` runs in the background and is never
waited on: a collector that hangs cannot delay or block a verify run, and the run's verdicts, output
and exit code do not depend on it. The consequence is stated rather than hidden — a send still in
flight when the command exits is abandoned, which is why the reliable path is the operator's own
foreground `vnproxctl telemetry send`.

## Authorization

Two enforcement layers, both required:

1. **PVE-enforced (primary):** all PVE API writes use the *user's own ticket* — vnprox cannot exceed the user's PVE ACLs, and PVE remains the audit point of record for those calls.
2. **vnprox-enforced (for host-level ops):** operations that bypass the PVE API (reading LLDP, staging `/etc/network/interfaces`, ifreload, snapshot restore) are gated on capability flags derived from the user's PVE ACLs at login (and re-derived hourly): `Sys.Audit` on `/nodes/{node}` → read; `Sys.Modify` on `/nodes/{node}` → node network write; `SDN.Allocate` → SDN write; `VM.Config.Network` → guest NIC edits; firewall caps from `Sys.Modify`/relevant paths. The mapping table lives in `internal/auth/caps.go` and is the single source of truth.

   **Packet capture — `capture` capability (T-1301).** The distributed packet-capture surface (`POST /captures` and the peer routes it fans out to) is gated on a **dedicated** `capture` capability, distinct from `netRead`/`netWrite`. It is deliberately **at least as strict as `netWrite`'s** gate: `capture` is derived only from `Sys.Modify` **and** `Sys.Console` held together on `/nodes/{node}` (the same root-shell-equivalent access class needed to run `tcpdump` on the host by hand). Holding `netRead`/`netWrite` alone — even every read/write privilege short of `Sys.Console` — therefore **never** grants capture; a session must hold `capture` explicitly. Rationale: capture exposes raw payload bytes, a materially stronger read than any config counter, so a wrong permission decision here is a data-exposure incident that cannot be retrofitted. Every `/captures` route requires both `netRead` and `capture`. When `[server] read_only = true` (docs/features/blueprints.md §3's "observe-only until you trust it" toggle), the four **config-write** capabilities — `netWrite`, `sdnWrite`, `fwWrite`, `guestNet` — are forced false regardless of the user's PVE ACLs (`internal/auth.forceReadOnly`, applied inside `deriveCapabilities` and, since T-2903, on the bearer-token path too). Every `RequireCap`-gated route that mutates *network configuration* gates on those four flags, so for network configuration `read_only` is a real, server-enforced restriction and not merely a UI affordance the frontend is trusted to hide.

> **Correction, 2026-08-16 (`T-3003`). This paragraph previously said `read_only` forces "every derived capability's write flags" false and that "every `RequireCap`-gated mutating route in `internal/api` gates on these same flags". Both halves overstated it, and the overstatement lived in the paragraph arguing that `capture` is the strictest gate in the product.** `forceReadOnly` clears exactly the four flags named above. **`capture` and `automation` survive it**, and each gates a mutating route family: `POST /captures` and `POST /captures/{id}/stop` start and stop real packet captures on hosts (`internal/api/captures.go:94-95`), and `POST /webhooks` registers an outbound destination the daemon will then POST to (`internal/api/webhooks.go:167`). So a `read_only` deployment today permits starting a packet capture while refusing a bridge rename.
>
> Whether that is *wrong* is a product question rather than an obvious bug, which is why it is recorded rather than silently changed: `automation` also gates the read-only WS `events` topic, and a capture is arguably observation — the very argument this paragraph makes for it being a stronger *read*. It is tracked as `T-3003-followup-01` in `planning/tasks/phase-30.md`, and `internal/auth`'s `TestForceReadOnly_PinsExactlyWhichFlagsItClears` pins today's behaviour so that whichever way it is decided, the change is deliberate and this paragraph moves with it.
>
> Note also that on a cookie session `automation` is always false anyway — it is never derived from a PVE privilege. The gap is reachable only with an `automation`-scoped **bearer token**, which is exactly the surface T-2903 brought under `read_only` in the first place.

   **Plugin capability scope (T-1702).** An installed extension plugin (`internal/plugin`)
   declares a **capability scope** drawn entirely from the `internal/auth/caps.go` vocabulary
   above — the SDK introduces **no new privilege** of its own. The scope is a **ceiling, not a
   grant**, enforced server-side and structurally:

   - **Stage-only, never apply.** The only change-engine surface handed to plugin code is
     `plugin.Stager` (Create/Validate). No Apply/Confirm/Rollback method is reachable from a
     plugin — in-process or over the out-of-process transport — so a plugin can stage a draft
     changeset for a human to apply but is never itself a mutation path. This is the same
     apply-only-through-the-change-engine guarantee every mutation has had since T-205, and it
     is verified by an interface-surface test, not by convention.
   - **The scope caps what a plugin can construct.** Every op a plugin tries to stage is mapped
     (`plugin.RequiredCap`) to the capability that op class already requires (`fw.*`→`fwWrite`,
     `sdn.*`→`sdnWrite`, `guest.nic.update`→`guestNet`, everything else→`netWrite`, fail-safe
     default `netWrite` for any unmapped op). If the plugin's declared scope does not cover an
     op's required capability, the op is rejected **before it ever reaches `internal/change`** —
     a plugin whose scope excludes `netWrite` cannot construct a `netWrite`-class op. A plugin
     also cannot *register* an extension point whose entry ceiling its scope does not meet (the
     write-adjacent `switchDriver` point requires `netWrite`; the four read-only points require
     `netRead`).
   - **Audited and bounded.** Install/enable/disable/uninstall each write an audit row recording
     the plugin's capability scope, so `GET /audit` always shows what a plugin may touch and who
     installed it. An out-of-process plugin runs as a supervised subprocess (`procshim`) with no
     DB/file access; its only channel back into vnprox is the capability-scoped `Stager`. Residual
     risk: the subprocess can make unconstrained OS-level network calls from its own process — a
     stated-not-hidden risk (mirroring T-1205's switch-rollback residual-risk stance), to be
     bounded operationally (systemd sandboxing / netns) rather than by the SDK.
   - **What gets executed is pinned, not manifest-chosen (T-2904).** A hub-installed plugin's
     `endpoint` is registry-supplied data; before anything runs, it must be an absolute path that
     resolves — symlinks included, on both sides of the comparison — to a regular file inside the
     vnprox-owned install root (`/var/lib/vnprox/plugins`). A bare name is never resolved via
     `$PATH`; a relative path, a `..` segment, a path outside the root, or a symlink escaping it
     is refused with the constraint named. And trusting an *unsigned* hub artifact is double-gated:
     the request's `trustUnsigned` flag is honored only when the server config also says
     `[hub] trust_unsigned = true` (a startup-`WARN` escape hatch in the `[peer] tls_trust`
     mold); otherwise the request gets a `403` naming the key. Signature verification of signed
     artifacts is unconditional either way.
**MCP stage-only boundary (T-1701, extended by T-2705) — the central invariant of the AI-operator surface.** The Model Context Protocol server (`internal/mcp`, docs/api.md's "MCP server" section) lets an AI operator reach vnprox's read surfaces and *stage* a draft changeset — and nothing else. T-2705 added four **typed** staging tools (`changesets.stage.bridge`/`.iface`/`.fwrule`/`.ipam`) so an AI operator can propose a concrete change rather than dictate one to a human; they stage, and they change nothing about this boundary. **No apply/confirm/rollback/discard verb is reachable through MCP, by any tool, parameter, or combination of tools.** A human (or T-1103's confirm machinery) remains the sole apply/confirm authority; an MCP-staged changeset is an ordinary draft a person still reviews and applies through the change engine. This boundary is enforced **structurally**, not by convention, on two independent axes:

1. **A fixed, enumerable tool allowlist.** The MCP surface is exactly thirteen tools (docs/api.md's tool table), not a generic "call any route" bridge. A package-load check rejects any tool whose name matches an apply/confirm/rollback/discard/approve/delete/destroy/remove/revert/commit/execute verb, and registry-enumeration tests pin the exact set so a future edit that adds an apply-shaped tool fails the build — including a guard over the *wired handler map*, so a tool smuggled in by wiring rather than by declaration is caught too.
2. **A change-engine seam with no mutation verb.** The only change-engine capability handed to the MCP server is a narrow interface exposing `CreateWithOrigin`/`CreateWithProvenance`/`UpdateDraft`/`Validate`/`Diff`/`List` — it has no `Apply`/`Confirm`/`Approve`/`Rollback`/`Discard` method at all, so no MCP code path can call a live-mutating verb even if a tool tried. **T-2705 made this a compile-time guarantee** (`internal/mcp/stageonly.go`): a placeholder type implementing exactly those stage-only verbs and nothing else is asserted to satisfy the interface, so adding a mutating method to it stops the package *building*, naming the offending method — not merely failing a test. The reflection-based interface-surface test (T-1701's, the same style T-1702's plugin seam uses) is retained alongside it.
3. **Policy is evaluated before a draft exists (T-2705).** Every op a typed staging tool would stage is run through T-2601's policy engine *first* — the same `EvaluatePolicySet` `POST /policies/test` uses, which writes nothing. A denied op is refused with the denying rule's **id and description**, and no changeset row is created; an unevaluable or unwired policy set fails **closed** (the tool refuses to stage rather than staging unchecked).
4. **Budgeted (T-2705).** Staging is rate-limited per session (keyed on the session's token, so reconnecting does not refill the budget — default 12 per minute) and the number of simultaneously *open* MCP-staged drafts is capped (default 10); exceeding either refuses further staging with a message naming the limit. This bounds how much unreviewed work a looping AI operator can leave behind.

MCP auth reuses T-1104's bearer tokens unchanged: a session must present a token carrying the `automation` scope, and each tool is exposed only if the token's scopes cover it — a `{netRead, automation}` token can never reach the `netWrite`-gated staging tools. Exposure is derived from the token at connect time, never from a client assertion; revoking the token force-closes the session within one tick. **Every AI-originated changeset is unerasably labelled** `origin: "mcp"` with the staging token's id — and, since T-2705, with the staging **tool's** name (`originTool`), so a reviewer sees not just "an AI staged this" but which action it took. All three are set once at create and never rewritten (the changeset repo's `UPDATE` does not name those columns), they survive to the review API on every changeset response, and every MCP tool invocation writes its own audit row with actor `mcp:<token-name>`, so an operator reading `GET /audit` can always tell an AI-originated action from a human one.

**In-app assistant (T-2808) — the same tools, the caller's own authority, and no daemon data path.** The MCP surface above is reachable only by an external MCP client, so most operators never see the capability it was built for. The in-app assistant (`web/src/assistant/`) is a panel that runs the **same read tools** against the local daemon: it adds no backend capability, no route, and no second authorisation model. Four properties make that more than a claim. (1) **Authorisation is the caller's own** — each tool calls the `/api/v1` route its MCP counterpart wraps, over the session cookie, so the server's existing capability gate is the only gate; the panel's client-side capability filter merely avoids a call that would 403. (2) **A refused surface yields nothing citable**, so no answer can lean on data the caller could not reach directly. (3) **An uncited answer is never rendered**: a citation resolves only against this turn's own tool results, and a reply with none left is discarded — the withheld value does not carry the answer text, so refusing is structural rather than a branch a renderer must remember. (4) **No apply path**, inherited unchanged from T-2705's compile-time guarantee; the panel's only write is staging a draft through `POST /changesets`, and a source scan fails the suite if any assistant module so much as names an apply/confirm/rollback call. The **model backend is absent by default** — vnprox ships none and no credential for one — and is configured per browser; prompts and answers travel from the browser to the operator's own backend and never through vnproxd, which is why no daemon route accepts prompt content and no support-bundle entry declares any. A cross-language test parses the panel's tool catalogue out of its source and fails if it names a tool the frozen MCP allowlist does not have, or one whose name contains a mutating verb. **Two limits recorded rather than hidden:** an assistant-staged draft carries `origin: "ui"` (the API has no client-settable origin), tagged instead by an `[assistant]` title prefix; and what the operator's chosen model backend does with the question and the tool evidence it is sent is outside vnprox's control.

There is **one privileged internal identity**: a PVE API token `vnprox@pve!daemon` (created at install, stored root-only) used exclusively for *read* polling by collectors — never for writes. Writes without a user context do not exist, with one exception: automatic rollback of an unconfirmed changeset, which restores from snapshot using host-level file operations and is attributed in the audit log to `system:rollback` with the originating user recorded. **Amended by T-1805:** that exception now also covers the firewall/SDN portion of such a rollback, which cannot be done with host-level file operations — but it is emphatically *not* a widening of the daemon token's privilege. The daemon token is still read-only and still never used for a write; the unattended firewall/SDN revert acts as the **applying user**, through their own PVE ticket sealed for that changeset's confirm window (see "Apply-time revert ticket" above), so PVE enforces the same ACLs it did on the apply and remains the audit point of record. The audit row is still `system:rollback` — that names *what triggered* the revert (the daemon's own timer), while the credential on the wire is the user's.

**Tenant authorization (T-1703, addition).** Multi-tenancy layers delegated, server-side-scoped views on top of the two enforcement layers above — it only ever **narrows** what a principal may see and do, never widens it, and it never adds a mutation path around the change engine. The load-bearing points:

- **Scoping is enforced server-side, at the data-access layer — never only in the UI.** The authority for "what may this principal see" is the tenant store (`tenants`/`tenant_scopes`/`tenant_members`, docs/data-model.md §2), resolved fresh on every request from the *authenticated* identity (`internal/tenant.Service.ScopeFor`), never from any client-supplied value. The `internal/api` scoping middleware attaches the resolved `Scope` to the request context; every tenant-scoped read handler (`/topology`, `/findings`, `/ipam/*`, `/flows`, plus inventory detail and search) filters its in-memory projection through that `Scope` **before serialization** — the same enforcement-point pattern `internal/auth.forceReadOnly` uses, not a response-shaping filter a client could bypass. A caller who is not a tenant member gets no `Scope` and reads unscoped, exactly as before.
- **No cross-tenant leakage — list, search, error, or count.** A tenant sees only its own delegated view: list endpoints drop out-of-scope items, search filters to visible Refs, the scoped dashboard counts only in-scope resources, and a **direct out-of-scope Ref lookup returns `404`, not `403`** (existence is never confirmed). A hostile client crafting IDs from another tenant learns nothing — the same "not-found, not-forbidden" stance the metrics/token paths already take for a wrong credential.
- **Requests still flow through the change engine.** A tenant member does not write; they **request** via a request-changeset (`POST /changesets {tenantId}` → an ordinary changeset in the additive `requested` status), which is validated exactly like a draft but blocked from apply until an **approver** of that tenant calls `POST /changesets/{id}/approve` (converting it to a `draft`). A member can never approve, and even an approver can never approve their own request (separation of duties — server-side role check). Every op in a request is verified server-side to target a Ref within the tenant's scope; an op with a zero or out-of-scope target is rejected. Approval is **not** apply — the approver still drives the ordinary draft → validate → apply → confirm/rollback flow afterward, so multi-tenancy narrows *who may touch what*, never *how* a change is applied.
- **Identity supply.** Tenant membership is keyed on the authenticated principal (a PVE-ticket-bridge or OIDC username). OIDC group claims map to tenant memberships (`internal/tenant.MapGroupsToTenants`) the same way T-1207 maps groups to capability bundles — and, like that mapping, this grants no capability by itself (OIDC caps are still intersected with the linked PVE identity's ACLs); it only selects which tenant's scoped view an authenticated user lands in.

**Change review approval (T-2003, addition).** Generalizes the request-changeset approval gate above from tenant requests to every changeset. `[changesets] approval_required` (docs/deployment.md) is the deployment-wide policy switch; when on, `POST /changesets/{id}/apply` refuses (`422 approval_required`) any changeset that does not currently carry a stored `approved` decision in `changeset_approvals`. This is decided **server-side, from stored state, on every apply attempt** — `internal/change.Service`'s `beginApply` reads the approval store fresh before any revalidation/snapshot/mutation, regardless of the caller (the SPA, a direct API call, or `vnproxctl`). Three properties make it a genuine authorization surface rather than a UI convenience:

- **Fail-closed.** A missing approval store, a read error, or any status other than `"approved"` (including `"none"` and `"rejected"`) all refuse apply identically — there is no code path where "couldn't determine approval state" is treated as "approved."
- **Editing invalidates a stale decision.** `PUT /changesets/{id}` unconditionally clears any recorded approval — a decision made against one set of ops must never silently authorize a materially different one (an attacker, or an innocent later edit, swapping in different ops after approval cannot ride on the earlier sign-off).
- **Self-approval and who may decide are both server-configured, not client-asserted.** `[changesets] allow_self_approval` (default `true`) and `[changesets] approvers` (default: anyone with `netWrite`) are read from the daemon's own config at decision time (`POST /changesets/{id}/review/approve`/`review/reject`), never from anything the request body supplies.

The frontend renders an Apply button disabled when it locally computes that approval is required and missing (`web/src/changesets/approvalGate.ts`) — purely an affordance; the server's own refusal above is the actual enforcement, and a build that skipped rendering the disabled state (or a raw API/`vnproxctl` call bypassing the SPA entirely) would still be refused identically. `planning/reports/T-402.md` flagged a prior instance of capability enforcement (`sdnWrite`) that lived only in the frontend, disabled-affordance-only with no server-side per-op check — deliberately not repeated here: this gate's enforcement is server-side first, the disabled button second.

**Proposing a changeset to git (T-2702, addition).** `POST /changesets/{id}/propose` is the daemon's only outbound *write* to a third-party host. Three properties bound it:

- **Its own credential, of its own scope.** The push token is a separate config key (`[gitsync] push_token_file`) held by a separate object from T-2701's read-only sync token. A deployment that has not set it never reads a write credential off disk and the route answers `501`; the sync path's credential is never widened to cover pushing. The two are separate *types* as well as separate keys — `gitsync.Source` (read) has no write verb and `gitsync.Host` (write) has no fetch verb, so "vnprox never pushes on the sync path" is enforced by the compiler rather than by review.
- **It is `netWrite` + CSRF, but it is not an apply.** Nothing about the cluster changes and the changeset itself is not mutated (the propose path's change-engine seam has exactly one method, `Get`). It requires `netWrite` because it publishes the operator's intent to a shared repository under the daemon's credential, which is a mutation of something — just not of the network.
- **It opens a pull request and stops.** There is no merge, approve, gate or poll — not as a route, not as a method on the host client. What happens to the request comes back through the ordinary git spec sync, which stages a draft a human applies through the change engine. The credential appears in none of what it writes: not the branch name, the commit message, the pull-request body, the audit row, the log, or any error.

## Transport

- TLS everywhere; no plaintext listener. Reuses the node's PVE certificate by default (see architecture §9), so admins keep one cert story.
- HSTS, `X-Content-Type-Options`, `X-Frame-Options: DENY`, and a strict CSP (self-only; no inline script; WS to self). `worker-src`/`manifest-src` are `'self'` — the exact grant T-2005's installable PWA needs to register `sw.js` and serve the manifest, and nothing wider (T-2901; before it they were `'none'`, which silently broke the PWA in production). The app is never framed: `frame-ancestors 'none'` everywhere **except** the three `/embed/*` views, which exist to be iframed and carry a per-route relaxation instead — `frame-ancestors 'self'` plus whatever origins the operator lists in `[server] embed_frame_ancestors` (validated as `scheme://host[:port]` origins at startup; empty means same-origin embedding only), with `X-Frame-Options` removed on those routes because that header cannot express an origin list. Every other CSP directive on the embed routes is byte-identical to the app's, by construction (one shared policy builder).
- Peer API: TLS + HMAC-SHA256 over (method, path, body hash, timestamp) with the cluster secret; ±30s replay window; constant-time compare.
- **Peer-API CA pinning (T-1906).** The TLS half of the line above is pinned, not inherited. `internal/peer.Client` verifies every peer daemon's certificate against the cluster's own root CA — `/etc/pve/pve-root-ca.pem` by default (`[peer] ca_file`) — and never consults the host system certificate pool. This closes a real hole: until v3.1 the peer client used `net/http`'s default trust store, so an attacker holding a certificate from *any* publicly-trusted CA and sitting on the management network could impersonate a peer daemon, and the peer API carries cluster-wide network mutations (cross-node changeset application, distributed rollback timers, host-writer calls). The HMAC still bounds what such an attacker could *do* — they would also need `/etc/pve/priv/vnprox/cluster.secret` to have a request accepted — but pinning removes the position entirely rather than relying on one layer.
  - **Fail closed:** no readable anchor ⇒ every peer is unverifiable and unreachable; nothing is sent, nothing is trusted, and there is no silent fallback to the system pool. Logged at `ERROR` and surfaced as a `peer_trust_degraded` finding.
  - **Escape hatches are two-key and loud:** `[peer] tls_trust = "system"` (host trust store) and `= "insecure"` (no verification) each require their own exact `[peer] tls_trust_ack` literal — `i-accept-unpinned-peer-tls` and `i-accept-unverified-peer-tls` respectively. Different literals per mode, so a config cannot slide from one to the other with a one-line edit. Either one logs a `WARN` naming exactly what was given up on **every** startup (there is no acknowledgement, state file, or counter that silences it) and raises a standing `peer_trust_degraded` finding. Anything else — an unknown mode, a missing ack, the wrong mode's ack — is a fatal config error, not a fallback in either direction.
  - **Rotation:** the anchor is re-read on a 30 s cadence and idle connections verified under the old anchor are dropped when it changes, so a rotated cluster CA is followed without restarting the daemon.
  - **Attack legibility:** a certificate that does not verify raises `peer_untrusted` (severity `error`); a peer that simply does not answer raises `peer_unreachable` (severity `warning`). Telling those apart is the point — an operator must be able to distinguish a down node from a machine answering in its place.
  - **Residual:** the peer *server* does not require client certificates; peer request authenticity still rests on the cluster-secret HMAC. Pinning protects the client's view of who it is talking to, which is the direction that carries the mutation.
- **HA replication transport (T-1704, addition):** the active/standby state-replication push (`POST /api/peer/ha/replicate`, docs/architecture.md §12) rides this **same** peer channel — TLS + cluster-secret HMAC + replay window — introducing no new transport credential or listener. The push is directed only at the operator-configured standby and is fenced by the lease `term` on receipt (a stale-term batch applies nothing); replicated sealed columns stay ciphertext, decrypting on the standby only under the identical `[storage] session_key_file` (see the threat-model row).
- **Metrics exporter transport (T-1001, addition):** `GET /metrics` is served over the same TLS listener as every other route (no separate plaintext metrics port) — a Prometheus scrape target must be configured `scheme: https` and to trust the node's certificate (or `tls_config.insecure_skip_verify` for a lab/dev target), same as any other HTTPS scrape. The bearer token above travels only over this TLS connection, never in a query string or a redirect.

## Certificates

Peer-API CA pinning above makes the cluster's certificates load-bearing: pinning fails closed, so a certificate that cannot authenticate a node removes that node from the peer mesh entirely. Phase 23 makes that state visible, checks it continuously, and fixes the one case where correct components still failed.

- **Inventory without fan-out.** `/etc/pve` is pmxcfs, so `/etc/pve/nodes/<node>/pve-ssl.pem` and `/etc/pve/pve-root-ca.pem` are present on every node's local disk. `internal/certs` therefore builds a **cluster-wide** inventory from a local directory walk — deliberately, because a certificate problem is precisely what makes peers unreachable, and an inventory that needed the peer API to diagnose a peer-API failure would be useless at the only moment it mattered. Surfaced at `GET /certs`, in **Settings → Certificates**, and via `vnproxctl certs` (which reads pmxcfs directly and works with the daemon down).
- **Private keys are structurally out of reach.** `pve-ssl.key` sits in the same pmxcfs directory as the certificate. The scanner only ever constructs paths from a three-entry filename allowlist rather than listing a directory and filtering — a filter is one loosened predicate away from reading a key, a fixed list is not. `certs.Certificate` carries no raw-bytes field at all (no PEM, no DER), so "this type cannot leak key material" is a property of the type, not of care taken at each call site. Regression-tested by planting a marked key beside a certificate and asserting no byte of it reaches any output field.
- **Checks (`source: "cert"`, all detection-only, all hysteresis-exempt).** `cert_expired`/`cert_expiring` (default 30 days), `cert_san_mismatch`, `cert_not_chained`, `cert_ca_mismatch`, `cert_weak_key` (below RSA-2048, or a SHA-1/MD5 signature), `cert_missing`, `cert_unreadable`. Hysteresis-exempt because an expiry date and a SAN list are facts read from a file, not sampled measurements — there is no noise to debounce, so a rise window would only delay a real signal. Nothing is `fixable`: every finding names the PVE command that fixes it instead.
- **A leaf's chain is checked; a custom certificate's is not.** `pve-ssl.pem` must verify against the cluster CA. `pveproxy-ssl.pem` is normally issued by a public CA or ACME, so chain-checking it against the cluster CA would flag every correctly configured Let's Encrypt deployment — which is how a check trains operators to ignore it.

### Peer verification names (fixes `T-1906-bug-01`)

Peers are dialled by IP. On real hardware (`pve-manager/9.2.4`), the node's `pve-ssl.pem` carried an IP SAN — but a **stale** one (`192.168.100.99`) for a node now at `192.168.1.9`. Pinned verification against the dial address therefore fails closed on a correctly configured cluster: correct components, no operator error, every peer down at once on upgrade. PVE generates `pve-ssl.pem` at cert-creation time and does not necessarily regenerate it when a node's management address changes.

The fix keeps the pin and changes only the *identity* checked. `internal/certs.ResolveVerifyName` picks a verification name per peer and `internal/peer.Trust` sets it as `ServerName`; the connection still goes to the IP. This is what `curl --resolve` does, and it needs no network round trip because pmxcfs already holds every node's certificate locally.

Three properties, each with an adversarial test:

1. **The CA pin is untouched.** A certificate that does not chain to the cluster CA is still rejected, whatever name it claims.
2. **Candidate names come from PVE's authoritative node name**, never from the presented certificate. Reading a name out of a peer's certificate and then verifying that certificate against that name would verify nothing.
3. **An FQDN candidate must be rooted at the node name** (first label equals it), and a wildcard SAN can never *originate* a candidate. So node A's certificate cannot authenticate node B even though the same cluster CA issued both.

Where no candidate identity is covered, the handshake still fails closed with crypto/tls's own hostname error — and `cert_san_mismatch` is raised at **startup**, before the first peer call, so the operator learns it from a named finding rather than an opaque handshake error under load later.

### Renewal is deliberately out of scope

vnprox does not renew, reissue, or replace certificates. PVE already owns this — `pvecm updatecerts -f` regenerates a node's leaf from the cluster CA, `pvenode acme cert order` drives ACME — and both restart `pveproxy`. Wrapping them would put a hypervisor-restarting action behind a vnprox button while adding nothing PVE does not already do better. A certificate is also not network config: there is no `/etc/network/interfaces` to diff and no pre-change snapshot to roll back to, so it could not go through the change engine either (the same category argument `docs/features/ipam.md` §7 makes for external-IPAM writes). Every finding names the exact command instead, so the operator runs it knowing precisely why.

## Host footprint

- Systemd unit hardening: `ProtectSystem=strict` with explicit `ReadWritePaths` (`/var/lib/vnprox`, `/etc/vnprox/keys`, `/etc/wireguard`, `/etc/network`, `/run`), `ProtectHome=yes`, `PrivateTmp=yes`, `NoNewPrivileges=yes`. (`/etc/vnprox/keys` is writable because the daemon generates first-run secrets there — session key, metrics scrape token, blueprint signing key — `0600 root:root`; the rest of `/etc` stays read-only. **v3.0.1** added this path after a real-hardware upgrade from a pre-metrics release crash-looped writing `metrics.key`/`blueprint-signing.key` into then-read-only `/etc/vnprox`. **v3.0.2** added `/etc/wireguard` — applying a WireGuard changeset op writes each tunnel's wg-quick config there (`cmd/vnproxd/wireguard.go`), which `ProtectSystem=strict` was also blocking; the same crash class the v3.0.1 keys fix missed. `postinst` creates `/etc/wireguard` `0700 root:root` so the bind target always exists. The cluster secret's fallback generate-if-absent write to `/etc/pve/priv/vnprox/` is deliberately *not* in `ReadWritePaths`: `/etc/pve` is a pmxcfs FUSE mount that `vnprox-setup` pre-seeds, and whether `ProtectSystem=strict` even makes it read-only is pending hardware validation — see `planning/reports/needs-hardware-validation.md`.) **Updated (T-604, completed):** the process still runs as root (no `User=`/`Group=` — netlink/ifreload/file-ownership operations require it), but `CapabilityBoundingSet` is now scoped to exactly six capabilities (`CAP_NET_ADMIN`, `CAP_NET_RAW`, `CAP_NET_BIND_SERVICE`, `CAP_DAC_OVERRIDE`, `CAP_DAC_READ_SEARCH`, `CAP_CHOWN`, `CAP_FOWNER`) rather than the full root set, plus `ProtectKernelModules=yes`, `ProtectKernelTunables=yes`, `ProtectKernelLogs=yes`, `RestrictAddressFamilies=AF_INET AF_INET6 AF_NETLINK AF_UNIX`, and a `SystemCallFilter=@system-service` allowlist (`packaging/systemd/vnprox.service`, `docs/security-verification.md`'s Host footprint section has the full evidence). **Correction (T-608, hardware validation):** `AF_UNIX` is required, not excludable — this seccomp filter is inherited across exec by every subprocess vnproxd spawns, including `lldpctl`, which talks to lldpd over a Unix domain socket (`/run/lldpd.socket`); omitting it silently broke every LLDP poll on a real node. **Correction (2026-08-18, T-3201 follow-up — real-hardware finding, `planning/reports/blocked-validation.md` §2.6):** a SEVENTH capability, `CAP_SETPCAP`, is required too — not for vnproxd itself, but for the `ping` child process every DF-probe (`internal/mtuprobe`) and latency-mesh (`internal/latmesh`) tick execs. Modern iputils-ping opens its raw ICMP socket (`CAP_NET_RAW`, already covered), then calls `cap_set_proc()` as its own defense-in-depth privilege drop, and **aborts hard (exit 255) if that call itself fails** — even though the socket it needed was already open. Without `CAP_SETPCAP` in the bounding set every `ping` this daemon ever execs failed this way, confirmed on a real two-node PVE 9.2.10 cluster (a debug capture caught `ping: cap_set_proc: Operation not permitted`, while an identical manual ping outside `vnprox.service`'s systemd scope succeeded against the same target) — and because both probers' own defensive "did not confirm success" fallback cannot distinguish a hard exec failure from a genuine timeout, this was silently producing false `path_loss`/`path_latency_degraded`/path-MTU findings on every correctly-hardened install, not merely missing an optimization. Per `capabilities(7)`, granting `CAP_SETPCAP` here only lets a child process (`ping`) manipulate its *own* process capability sets — here, specifically to narrow them further, per `ping`'s own design — never to raise vnproxd's; on a modern kernel with file capabilities, it does not by itself let `ping` hand capabilities beyond the bounding set's own ceiling to anything else, so this does not widen the process tree's effective privilege, only unblocks `ping`'s own already-benign self-restriction. **`CAP_SETPCAP` alone was not sufficient, confirmed the hard way on the same live cluster**: this unit's `SystemCallFilter` already denies `@privileged` (line above), and `systemd-analyze syscall-filter @privileged` shows `capset` — the syscall `cap_set_proc()` actually makes — is a member of that denied group, seccomp-blocking it outright regardless of which capabilities the calling thread holds. A `systemd-run` reproduction matching this unit's directives one at a time confirmed it: `CAP_SETPCAP` with `capset` still seccomp-denied reproduced the identical `cap_set_proc: Operation not permitted` failure; allowlisting `capset` specifically (`SystemCallFilter=capset setuid` in the unit, added alongside the deny line) changed the failure to `ping: setuid: Operation not permitted` — iputils-ping's privilege-drop sequence calls `capset()` and then `setuid()` as a second, UID-level defense-in-depth step — and allowlisting both let `ping` complete cleanly. Both individually justified narrow exceptions to the `@privileged` denial, not a re-opening of the group: `capset` only rearranges bits within a process's own already-granted capability sets (never gains beyond the `CapabilityBoundingSet` ceiling), and `setuid` without `CAP_SETUID` in the bounding set (deliberately absent) can only set a process's UID to one it already holds — a no-op for every vnproxd child, which stays at UID 0 throughout. Full non-root operation remains out of scope for v1 (tracked post-1.0).
- vnproxd never shells out with user-supplied strings; the external commands it does exec (`lldpctl -f json`, `vtysh` for FRR, `ifreload -a`, the lldpd install/enable commands, and the read-only diagnostic probes added across Phases 13–14 — `wg`/`wg-quick` for WireGuard config apply, `ping`/`ping -M do` for the latency mesh, path-MTU prober, and WAN & upstream health probe (T-1405), `conntrack -L` for the conntrack explorer, `nsenter`+`ip`/`ss` for the lxc guest-interior reads, and `rdisc6` for the IPv6 RA reader) use fixed argv arrays; the few that take a dynamic argument only ever pass a validated, non-shell-interpolated value (a node/vmid/target resolved from inventory, an operator-configured WAN reference target — schema-validated non-empty on `PUT /wan/targets`, still just one fixed argv element, never shell-interpolated — or an operator-chosen BPF filter that is server-validated before it reaches a capture process). `ifreload -a` reloads the whole file — per-interface commands don't exist. **Correction (T-607 docs audit):** `ethtool` is not invoked as a subprocess at all — link speed/duplex is read via the `SIOCETHTOOL` ioctl directly (`internal/host/ethtool_linux.go`), a stronger property (zero shell-out surface) than the "fixed argv" claim above implies; see `docs/security-verification.md`'s Host footprint section for the full evidence and citations.
- SQLite DB and key files are `root:root 0600`; snapshots contain network configs (not secrets) but are treated as sensitive.
- **Host-local flow sampling capability footprint (T-1004, addition):** `internal/flow/hostsample`'s conntrack sampler (periodic `/proc/net/nf_conntrack` poll, `[flows] conntrack_sampling_enabled`) needs no capability beyond the six already in `CapabilityBoundingSet` above (`CAP_DAC_READ_SEARCH` already covers reading the procfs table). Its eBPF sampler (`[flows] ebpf_sampling_enabled`), when enabled, needs **`CAP_BPF` and `CAP_PERFMON`** — capabilities beyond those six, not previously required by anything else vnproxd does, and not present in the shipped unit's bounding set. These two capabilities are **flagged, never granted unconditionally**: `packaging/debian/postinst` only writes a systemd drop-in (`/etc/systemd/system/vnprox.service.d/10-ebpf-caps.conf`, adding `CapabilityBoundingSet=CAP_BPF CAP_PERFMON` — systemd unions repeated `CapabilityBoundingSet=` assignments rather than replacing them) when it finds `ebpf_sampling_enabled = true` in `/etc/vnprox/vnprox.toml` at install/upgrade time, and removes that drop-in when the value is absent/false; a node that never opts in never has its capability bounding set widened. Even with both capabilities granted, `internal/flow/hostsample`'s runtime kernel-feature probe (Linux 5.8+, both capabilities present in this process's effective set, and BTF/CO-RE support at `/sys/kernel/btf/vmlinux`) must also pass before the eBPF sampler is considered active; a probe failure is logged (naming the missing capability/feature) and the daemon falls back to conntrack-only (or fully disabled) sampling — never fatal. As of this task, actual per-packet BPF program attachment is not implemented (no third-party eBPF loader dependency has been added, per CLAUDE.md's dependency rule) — only the kernel-feature probe and the capability-grant scaffolding are real; see `planning/reports/T-1004.md` and `planning/reports/needs-hardware-validation.md`.

- **Packet-capture file footprint (T-1301, addition):** `internal/capture` writes captured packets to one bounded `.pcap` file per session under `[capture] root` (default `/var/lib/vnprox/captures/`, already an app-owned, `root:root` `ReadWritePath` in the systemd unit — no new writable path). Reading raw packets off a live interface needs `CAP_NET_RAW`, already in the shipped unit's `CapabilityBoundingSet` (host footprint above) — no capability widening. Every capture file is **hard-bounded** at write time by server-enforced, un-overridable caps (a time cap, a byte cap, and a packet cap — whichever is hit first stops the capture; no API parameter, admin flag, or filter construction can raise these past their configured `vnprox.toml` `[capture]` ceilings, and each capturing node re-clamps independently), and **auto-purged** past `[capture] retention_hours` by an owned sweep goroutine (`internal/capture.Coordinator.Sweep`, on the same tick-cadence pattern `internal/metrics`' ring pruning uses) — including files orphaned by a daemon restart mid-capture. **Captured payload bytes never leave that file:** nothing is copied into SQLite, the audit log, WS events, or any other store — `capture_sessions` and the `capture.start`/`capture.stop` audit rows carry app-owned intent + byte/packet *counts* only, never packet contents (regression-tested, grep-verifiable across the store/audit code paths). The submitted BPF filter is server-validated (shell-unsafe characters and over-ceiling instruction counts rejected) before any capture process is invoked. As of T-1301 the on-hardware capture backend (a real `tcpdump`/AF_PACKET binding) is a **needs-hardware-validation** item — development/tests run against `internal/capturemock`'s scripted agent; every surrounding safety property (capability gate, caps, filter validation, audit, retention, peer fan-out) is real and agent-agnostic.

## Safety interlocks (availability is security here)

- The change engine refuses (hard error, no override in UI; override only via config flag `allow_dangerous_ops`) any changeset that would: remove/re-address the interface carrying the node's management IP, take down the interface used by corosync links, or delete a bridge with running guests attached (must first present guest reattachment ops).
- **The interlocks hold on the receiving side of the peer API too (T-2902).** `POST /api/peer/host/{stage-interfaces,restore}` runs the receiving node's *own* change-engine validation (the exact raw-content pipeline the coordinator runs — `change.Service.ValidatePeerHostWrite`) before anything reaches the host writer, so holding the cluster secret is not a shortcut past the interlocks: a peer-delivered write that would strand the management path is refused with the findings on the wire, and every `/api/peer/host/*` write — allowed, refused, or failed — is audited on the receiving node with the coordinator's attribution (actor, origin node, origin IP, content digest). A restore whose content matches a snapshot this node itself recorded is exempted **by provenance** (a distributed rollback legitimately re-arms the management path), never by skipping validation wholesale.
- Commit-confirm auto-rollback (architecture §4) bounds the blast radius of every applied change.
- Cluster-wide apply lock prevents concurrent conflicting changesets.
- **Scheduled/unattended apply (T-1103, addition):** a changeset whose ops touch a node's resolved management path (`touchesMgmtPath`) can never be scheduled for unattended apply (docs/api.md's `POST /changesets/{id}/schedule`: `422 mgmt_path_unattended_forbidden`). This is a **stricter, separate gate** from the `allow_dangerous_ops` line above, not an application of it: `allow_dangerous_ops` only ever downgrades a T-203 safety-interlock *validation finding* from error to warning for an ordinary, interactively-confirmed apply — it has no bearing on, and no effect over, the scheduling gate, which checks `touchesMgmtPath` directly and unconditionally before any validation pass even runs. There is no config flag, request field, or combination of the two that schedules a management-path change for unattended apply; the only path to changing a node's management path stays the interactive one (T-703's guided wizard, reviewed and confirmed by a human at apply time).

## Blueprint & plugin hub (T-1705, T-2104)

The hub (`internal/hub`, opt-in via `[hub] registry_url`) is a browse/install **client** over a public registry of signed blueprint bundles (T-1107) and SDK plugins (T-1702). There is no registry *service*: the registry is a static, signed `index.json` plus an artifact tree on ordinary hosting (`docs/hub-registry.md`, T-2803). It is **not a new trust boundary** — it inherits, and never weakens, the existing gates:

- **Signature + trust gate (inherited).** A downloaded blueprint bundle goes through T-1107's exact `POST /blueprints/import` path (the same `importBundleCore`); a downloaded plugin manifest is verified with the same Ed25519 primitive (`blueprint.VerifySignature`) against the same trust store. An unsigned or untrusted-signer artifact is never installed without the explicit `trustUnsigned`/`trustNewKey` decision, identical to a direct import.
- **Capability scope (inherited).** A plugin install is completed only through T-1702's `Registry.Install`, which re-validates the declared capability scope against `internal/auth`'s vocabulary. The hub reaches no path that installs a plugin without that check; only out-of-process (`grpc`) plugins are installable this way.
- **Catalog/artifact capability agreement (T-2104).** `GET /hub/index` is what an operator reviews *before* clicking install (T-1705 AC4); the artifact's own manifest — downloaded and, when signed, cryptographically verified — is what `plugin.Registry.Install` actually grants a scope from. Those are two separate pieces of registry-served data, and nothing served by a registry is trusted merely because the registry served it: `POST /hub/install` (`installPluginCore`, `hub.CapabilityMismatch`) compares the catalog entry's `capabilities`/`extensionPoints` against the downloaded artifact's manifest as sets before any signature/trust decision is even considered, and refuses the install outright — status `capabilityMismatch`, audited `hub.install`/`denied` — on any disagreement, signed or unsigned, trusted signer or not. No trust flag can override this: it is not a trust decision, it is a check that the operator's consent was to the thing actually being installed. (Belt-and-suspenders: `internal/hubreg`'s publish/index tooling already *derives* a plugin entry's catalog fields from the artifact's own manifest at submission time, so a submission built through `vnproxctl hub publish` cannot disagree with itself in the first place — this gate is what still refuses an install if a registry serves an index that disagrees anyway, whether from a hand-edited submission, a compromised registry, or a future publishing bug.)
- **Vetted tier is informational only.** `[hub] vetted_signers` is the hub's own recognized-signer allowlist, **distinct** from the per-admin trust store. A "vetted" badge is display metadata; it never substitutes for the per-installation trust decision — a vetted-but-untrusted signer still requires an explicit trust step. This is a deliberate non-authority: the vetted list can add reassurance but can never grant trust an admin hasn't.
- **Off-origin fetch guard.** An entry's `artifactUrl` is required to resolve to the registry's own host — the index can never redirect an install to an arbitrary third-party host (the artifact's own signature remains the authoritative gate; this is defence in depth).
- **Signed catalog and offline revocation (T-2803).** With `[hub] index_signers` set to the registry's index-key fingerprint(s), the index must verify against one of them before the client sees a single entry: an unsigned, corrupted, truncated, or foreign-signed index yields an error and **zero** entries, so a catalog can never partially load. Revocations are carried *inside* that signed document, which means a revoked artifact is refused — both hidden from the catalog and blocked at download — using only the index already fetched, with no live revocation call to be blocked, spoofed or unreachable. The gate lives in `internal/hubreg` on the client's existing HTTP seam; `internal/hub` makes no trust decision, as before. **What this is not:** the index signature is an authority over the *catalog*, never over an artifact. A signed entry for an untrusted-signer artifact still stops at the operator's explicit trust step, and `index_signers` can no more grant trust than the vetted badge can. Leaving `index_signers` empty preserves the pre-T-2803 behaviour (unauthenticated catalog, revocations unenforced) and logs a warning naming exactly that at startup. Index-key handling and rotation: `docs/hub-registry.md`.

## Audit

Every mutation attempt (including denied and rolled-back) is written to the audit log with user, source IP, changeset id, op summaries, and result. Audit entries are append-only at the API layer; there is no delete endpoint. Hub installs are audited as `blueprint.import` (blueprint installs, reusing T-1107's exact audit) or `hub.install` (plugin installs, recording the trust decision and signer fingerprint).

## Threat model summary

| Threat | Mitigation |
|---|---|
| Credential stuffing on 8007 | rate limits, PVE lockout semantics, TOTP passthrough |
| Session theft | HttpOnly+Secure+SameSite cookies, short idle timeout, encrypted server-side tickets |
| Privilege escalation via vnprox | user-ticket writes (PVE enforces), read-only daemon token, cap mapping for host ops |
| Rogue peer / lateral movement | cluster-secret HMAC + TLS, pmxcfs-distributed root-only secret, replay window |
| Peer-daemon impersonation with a publicly-trusted certificate (T-1906) | peer TLS is pinned to the cluster's own root CA (`/etc/pve/pve-root-ca.pem`, `[peer] ca_file`) and the system trust store is never consulted, so a certificate from any public CA plus a management-network position is no longer sufficient; unpinning is a two-key, per-mode-acknowledged config change that `WARN`s on every startup and raises a standing `peer_trust_degraded` finding; a missing anchor fails **closed** (no peer reachable, never a silent fallback); a rotated cluster CA is picked up within 30 s without a restart, including dropping keep-alive connections verified under the old anchor; a peer that fails verification raises `peer_untrusted` (error) rather than being flattened into the ordinary `peer_unreachable` (warning), so an impersonation attempt is legible as one |
| Malicious/buggy change bricks cluster | validators + safety interlocks + commit-confirm rollback + time machine |
| Sealed apply-time revert ticket theft / misuse (T-1805) | the applying user's PVE ticket is sealed in `changesets.revert_ticket_enc` with the **one** AES-256-GCM session key — not a second cipher or key pair — only while that changeset is mid-apply or awaiting confirmation, and wiped on confirm/rollback/timeout/failed-apply/discard/expiry, whichever comes first (wipe asserted directly against the stored row in every case); it has **no field on any read model**, so no API response, MCP tool result, or plugin-visible value can carry it (verified by enumeration over the real route/tool/extension-point registries, plus per-surface and raw-DB-bytes non-leak tests); it is reachable only from that one changeset's own revert path, acts through a **non-renewing** sealed-ticket PVE client so the daemon can never mint a longer-lived credential from it, is bounded by the ticket's own ~2h life with reduced coverage reported to the operator **at apply time**, and is never replicated to an HA standby |
| Backup archive theft (T-1901) | a default `vnproxctl backup` archive contains **no key material**: every credential class in the store is a `*_enc` (AES-256-GCM) or `*_hash` (one-way) column and the session key that opens them is not collected, so a stolen archive yields ciphertext and hashes, not credentials (table-driven, one case per secret class, scanning the whole decompressed archive, with an unsealed-value control proving the scan works); `--include-keys` is the only way to include key material and it warns naming every class, requires an interactive confirmation, sets `includesKeyMaterial` in the manifest, and suffixes the filename `-with-keys`; every archive is `0600`; the peer cluster secret is never collected under any flag; residual: the archive is unencrypted and unsigned and still exposes network *metadata* — see "Backup archives" above |
| Credential published in a support bundle (T-1902) | a bundle is *designed* to be posted publicly, so it is redacted by construction: its collectors implement an interface with **no `Emits` method**, so no flag or config can make it declare or carry a secret class (`includesKeyMaterial` is structurally false); the SQLite store is never included (derived facts only, read `query_only` so diagnosing a failed migration cannot migrate it); `vnprox.toml` and `/etc/network/interfaces` are re-emitted through per-key/per-option allowlists rather than copied (an interfaces(5) file can carry `wireguard-private-key`); every structured field is declared with a disposition and a written justification, enforced by a reflection walk that **refuses** to let a `json.RawMessage`/`any`/map field be declared plainly emitted; free-form text (logs, changeset titles, apply output, cert subjects) passes a shape-matching redactor covering PVE tickets, `PVEAPIToken=`, `Authorization:`, URL userinfo, named-key assignments, bare 43-char base64 and PEM private keys; changeset ops are walked by key name (not by known field) so a sealed field invented next phase is covered on arrival; proved by a table-driven scan of the whole decompressed archive, one case per secret class, with the markers planted in the inputs a bundle actually reads and **four** must-be-found controls so the scan cannot pass vacuously; `vnproxctl restore` refuses a bundle outright; residual: a bundle still exposes network *metadata* and is neither signed nor encrypted — see "Support bundles" above |
| Malicious restore archive (T-1901) | the archive is parsed as hostile input in a pass that writes **nothing** to disk: allowlisted entry-name vocabulary (traversal/absolute/backslash names inexpressible), regular files only (symlink/hardlink/device entries refused), absolute streamed budgets on manifest/entry/total bytes and entry count (a decompression bomb is stopped at the header declaring it), and an exact match to the manifest's declared name, order, size and SHA-256 with the gzip checksum verified; undeclared, duplicate and trailing entries are refusals; table-driven with a benign-archive control proving the reader is not simply rejecting everything |
| Restore against a live daemon / schema downgrade (T-1901) | `vnproxctl restore` refuses while a daemon owns the store — an advisory `flock` vnproxd holds for its lifetime on `<db>.lock`, **plus** a probe of `[server] listen` so a pre-v3.2 daemon that takes no lock is caught too — and refuses a store from a newer schema than the running binary understands, checked against the manifest *and* re-checked against the store inside the archive so a forged manifest cannot smuggle one past; the swap is atomic (stage + forward-migrate beside the target, then two renames in one directory, with the previous store put back on failure and kept at `<db>.pre-restore-<UTC>` on success), proved by injecting a failure at each of three points and asserting the original store is byte-identical afterwards |
| Supply chain | pinned deps; `make check` includes `govulncheck` + `npm audit` gates. **Where that gate runs, stated plainly:** the GitHub Actions workflows have been `disabled_manually` since 2026-08-13 (Actions billing exhausted), so nothing runs on push. The full seven-job gate is run on the dev host via `scripts/ci-local.sh`, and `make check` before every commit. Treat "in CI" throughout this document as "in the gate", not as "on GitHub" |
| XSS → config change | strict CSP, no inline script, CSRF header, framework-escaped rendering only |
| Metrics scrape token theft (T-1001) | token is separate from the session cookie (theft of one doesn't grant the other), constant-time compare, optional source-CIDR allowlist, route is read-only and exports no secret |
| Automation token theft/overreach (T-1104) | scopes bounded to the minting user's own capabilities at mint time, raw value stored only as a one-way hash, immediate revocation force-closes live WS use, per-token rate limit, every use audited (`token.use`) |
| Webhook target compromise/tampering (T-1104) | delivery signed per-body (`X-VNPROX-SIGNATURE`, HMAC-SHA256, constant-time verify), retried with bounded backoff, `webhook_unhealthy` finding surfaces N consecutive delivery failures |
| Webhook as blind-SSRF primitive (T-2905) | destination policy: public **https** targets only by default — loopback/RFC1918/link-local (incl. cloud metadata addresses) and plain http are refused at registration AND re-checked against the **resolved** address at every dial (DNS rebinding does not slip past the URL check); `[webhooks] allow_private_targets` / `allow_insecure_targets` opt out per class, each WARNing at every startup |
| Embed token overreach / write via an embed (T-1706) | scopes hard-restricted to read-only at mint (`400` for any write scope, before the per-user ceiling, regardless of the minting user's caps), re-checked on every embed request; embed view routes authenticate the `?token=` query token only and never a session cookie (distinct middleware path); the embedded view reaches only the existing read-only gated routes — no parallel read path, no persisted privilege beyond the read-only scope set |
| OIDC token forgery / IdP-response tampering (T-1207) | RS256-only ID-token verification against the IdP's published JWKS (issuer/audience/expiry/nonce checked; `alg:none`/HS* rejected — no alg-confusion downgrade), PKCE (S256) + single-use state/nonce on every auth request, mapped-PVE credentials encrypted at rest (`oidc_pve_links.credential_enc`), OIDC caps intersected with (never additive to) the linked PVE identity's real ACLs |

| Cluster-registry credential theft (T-1201) | per-cluster PVE credential sealed in `clusters.credential_enc` with the one AES-256-GCM session key (never a new secret), never returned by any API/log/audit, ciphertext-vs-plaintext regression-tested; no cross-cluster mutation primitive exists, so a leaked credential cannot be used to write another cluster |
| Malicious/over-reaching extension plugin (T-1702) | plugin capability scope is a server-enforced ceiling drawn from the existing `caps.go` vocabulary (no new privilege); the only change-engine seam a plugin holds is stage-only `Stager` (no Apply/Confirm/Rollback reachable, verified by an interface-surface test); an op whose required capability the scope excludes is rejected before reaching `internal/change`; out-of-process plugins run as supervised subprocesses with no DB/file access and degrade gracefully when killed; install/enable/disable/uninstall are audited with the recorded scope |
| Rogue / compromised attached cluster (T-1201) | config ownership stays strictly per-cluster; a changeset's ops are validated to belong to its own `clusterId` (cross-cluster op rejected); an unreachable/misbehaving cluster is failure-isolated (`partial`/`failedClusters`) and never blanks or errors the aggregate response for the healthy clusters — a hostile cluster degrades only its own capsule, not the federation |
| Cross-tenant data disclosure (T-1703) | tenant scoping enforced server-side at the data-access layer (`internal/tenant.Service` + the `internal/api` scoping middleware) — every scoped read filters the projection by the authenticated principal's `tenant_scopes` before serialization; an out-of-scope direct Ref lookup is `404` (existence not confirmed), and list/search/dashboard-count paths never emit another tenant's data; a request-changeset's ops are server-verified to target only in-scope Refs |
| Tenant privilege escalation / rogue approval (T-1703) | a request-changeset is blocked from apply until an approver of the owning tenant converts it to a draft (change-engine `requested`→`draft` transition, no path to `applying`); a plain member can never approve, and an approver can never approve their own request (server-side role check); approval is not apply — the ordinary confirm/rollback flow still gates the real mutation |
| Switch-driver credential theft / errant push (T-1205) | `switches.credentials_enc` sealed with the same session cipher, never returned, ciphertext-vs-plaintext regression-tested; push ships dark (daemon flag **and** per-switch `enabled` both required); every push is a change-engine changeset scoped to PVE-facing ports only, with a mandatory pre-write LLDP-neighbor identity re-check (hard abort on mismatch) and mgmt-path interlock (`safety.protected_switch_port`, no override); unrevertable-after-push risk surfaced as a distinguishable "rollback incomplete" state |
| Captured packet-payload exposure (T-1301) | capture is gated on the dedicated `capture` capability (derived only from `Sys.Modify`+`Sys.Console`, ≥ `netWrite`'s strictness — Authorization above); each `.pcap` is hard-bounded at write time by server-enforced, un-overridable time/byte/packet caps (re-clamped independently on every capturing node) and auto-purged past `[capture] retention_hours`; **payload bytes never leave the capture file** — nothing is copied into SQLite, the audit log, or WS events (only byte/packet counts), regression-tested by `TestNoPayloadBytesPersistedOutsideCaptureFile`; the submitted BPF filter is server-validated before any capture process runs |
| WireGuard tunnel key theft (T-1401) | the X25519 tunnel private key is sealed in `wireguard_tunnels.private_key_enc` (and any per-peer PSK in `wireguard_peers.preshared_key_enc`) with the **one** AES-256-GCM session key — not a second cipher or key pair — generated on the owning node, sealed once, and **never returned** by any API/log/audit (only the derived public key is exportable); no-plaintext-at-rest is regression-tested (`TestWireGuardRepo_PrivateKeyEncryptedAtRest` for the tunnel key at the store layer, `TestSealOpSecrets_NoPlaintextPSKAtRest` + the API non-leak tests for the PSK in staged ops); rotation is delete-and-recreate (two audited changeset ops), never a silent overwrite; an external peer's own key hygiene is out of scope, stated plainly |
| MCP AI-operator surface abuse (T-1701, T-2705) | the AI-operator surface is **read + stage only** — a fixed thirteen-tool allowlist with no apply/confirm/approve/delete tool reachable by any tool/parameter/combination (package-load verb check + registry- and handler-enumeration tests + a change-engine seam with no mutation method, asserted at **compile time**); every staged op is policy-checked (T-2601) before any draft exists, and a denial names the refusing rule; staging is rate-limited per session and the open-draft backlog is capped; MCP reuses T-1104 bearer tokens (must carry `automation`; each tool exposed only if the token's scopes cover it, derived at connect time, revocation force-closes within one tick); every AI-staged changeset is unerasably labelled `origin: "mcp"`+`originTokenId` and every tool call is audited with actor `mcp:<token-name>`, so an operator can always distinguish an AI action from a human one; a human remains the sole apply/confirm authority |
| In-app assistant used to reach data, or to act, beyond the operator (T-2808) | the panel mirrors the MCP **read** tools and runs them over the ordinary `/api/v1` routes with the caller's **own session cookie** — no bearer token, no service identity, no second authorisation model, so a capability the user lacks 403s exactly as it does when they click (asserted per surface, each with a capable-caller control leg); the client-side capability filter is a courtesy, and a refused surface contributes **no citable entity**, so nothing sourced from it can appear in an answer; an answer whose citations do not resolve to this turn's own tool results **is not rendered at all** (the withheld result type does not carry the answer text, so no renderer can show it); the one write is staging a draft through `POST /changesets`, which is the ordinary change-engine path — the module cannot even reference `applyChangeset`/`confirmChangeset`/`rollbackChangeset` (source-scan test with a non-vacuity guard), and the stage-only guarantee it inherits from T-2705 is the compile-time one above; the model backend is **absent by default**, configured per browser, and the prompt/answer path is browser → the operator's own backend, so vnproxd never receives prompt content (no route accepts it — enumerated over the daemon's own route table) and a support bundle declares no entry that could carry it; the API key is held in memory for the tab and never written to storage. **Residual risk, stated:** whatever the operator points the panel at receives their question and the tool evidence behind it — vnprox cannot constrain a third-party model backend's own retention, and the tool evidence is real cluster data. That is the operator's choice to make, which is why the default is no backend at all. |
| Git spec-sync credential theft / a hostile spec repository (T-2701) | the host credential lives in a `root:root 0600` `[gitsync] token_file` (never in `vnprox.toml`, never in a URL — a URL embedding one is refused at startup without echoing it), exists only as a request header, and is absent from the daemon log, the findings stream, the audit rows and `gitsync status` — asserted once per surface with two must-fail controls (the token really was in flight; each surface really was populated); no response body is ever echoed into an error, so a 401 that quotes the request back cannot leak it; it authorizes a **read of one file** and no write path exists on this transport; with `require_signed_commits`, commits are verified **locally** against the operator's own allowed-signers file (the host's own "verified" flag is never consulted) and every unverifiable case — unsigned, OpenPGP, unsupported algorithm, unlisted signer, wrong SSHSIG namespace, or a host that cannot supply the signed commit object — is a refusal with a finding; and above all the blast radius of a compromised spec is a **draft changeset a human reviews**, because the sync's change-engine seam has no apply/confirm/rollback method at all (interface-surface test) |
| A public read-only demo instance is written to, or used to reach a real cluster (T-2801, T-2802) | a demo daemon cannot be started against a configured `[pve]` endpoint (`config.LoadDemo` refuses at load, before a collector is built or a port is bound), and the two routes that attach an external cluster (`/federation/clusters`, `/k8s/clusters`) are refused `403 demo_real_endpoint_refused` rather than answered with the ordinary demo would-have — "I would have attached your production cluster" is not a sentence a demo may say; `--public-demo` requires `--demo` and is refused without it. Per-visitor state (`HttpOnly`+`Secure`+`SameSite=Strict` cookie) is held in memory at the edge, outside the daemon's own store, so one visitor's data is invisible to another; every cap (requests, scratch-state size) is per-visitor, so a hostile visitor degrades only their own session, and the one cluster-wide cap (visitor count) refuses arriving visitors rather than evicting seated ones. **Residual, stated:** there is no hosted instance of this today (`docs/features/demo-mode.md`'s "Known gaps") — everything above is built and tested, but nothing runs at a public URL |
| A map annotation carries a script or breaks a rendered document (T-2806) | annotation and region text is operator-supplied free text with no vnprox-side interpretation, escaped independently at every place it is rendered rather than once centrally: the API's ordinary JSON encoding, `docexport`'s HTML renderer, `docexport`'s Markdown renderer (whose hazards are different from HTML's — raw-HTML passthrough, table-breaking pipes and newlines rather than tag injection), the embedded SVG legend, and the frontend's map canvas and entity-inspector layers — each with its own escape and its own test, so a regression in one path cannot hide behind another's coverage |
| HA replication-channel compromise / rogue standby (T-1704) | HA replication rides `internal/peer`'s existing TLS + HMAC-SHA256(cluster-secret) channel with the ±30s replay window — **no new transport credential**; the `POST /api/peer/ha/replicate` push targets only the operator-configured standby, never an arbitrary cluster peer, and is fenced by the lease `term` (a stale-term or out-of-band batch is rejected by `internal/ha.Manager.Receive`, no data applied); it introduces **no new at-rest credential class** — `api_tokens` replicate as one-way hashes and any sealed column (WireGuard keys, webhook secrets) replicates as ciphertext that decrypts on the standby only under the **same** `[storage] session_key_file`, so a standby with the wrong key holds unreadable ciphertext, not plaintext |
