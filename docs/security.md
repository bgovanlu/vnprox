# Security design

vnprox runs as root on hypervisor hosts and can reconfigure the network of an entire cluster. Security posture is therefore conservative by design.

## Authentication

- **No vnprox-local accounts.** Users authenticate with Proxmox credentials; vnproxd forwards to PVE `POST /access/ticket` (supports any PVE realm: PAM, PVE, LDAP/AD, OIDC, and TOTP/second factor passthrough via `otp`).
- On success vnproxd creates a server-side session: random 256-bit id in an `HttpOnly; Secure; SameSite=Strict` cookie. The PVE ticket + CSRF token are stored encrypted at rest (AES-256-GCM; key in `/etc/vnprox/keys/session.key`, root:root 0600, generated at install).
- PVE tickets expire at 2h; vnproxd renews at ~1h30 while the session is active. vnprox sessions idle out at 2h, hard cap 12h.
- CSRF: double-submit — mutating requests require `X-VNPROX-CSRF` matching the session record.
- Login rate limiting: per-IP and per-username token bucket; lockout events audited.

**Metrics scrape token (T-1001, addition).** `GET /metrics` (docs/api.md's Metrics-exporter subsection) is the **one documented exception** to this section's session-cookie model: a Prometheus scraper cannot carry a browser session cookie or a CSRF header, so it authenticates with its own bearer token instead of a PVE-derived session.

- A random 256-bit token, hex-encoded, generated on first daemon start (the same "generate if absent" convention the session key above uses) and stored at `/etc/vnprox/keys/metrics.key`, `root:root 0600`.
- Checked via `Authorization: Bearer <token>`, compared with `crypto/subtle.ConstantTimeCompare` — never a plain `==` (which would leak timing information about how much of the token matched).
- No PVE ticket is involved anywhere in this path: the token identifies "an authorized scraper," not a PVE user, and this route performs no PVE API calls of its own.
- A missing or invalid token is `401 not_authenticated`, using the same `{"error":...}` envelope every other route in this doc uses.
- Additive, optional **source-CIDR allowlist**: `[metrics] allow_from` in `vnprox.toml` (a list of CIDRs, nginx-`allow`-directive-shaped), checked *before* the token — a request from outside every listed CIDR is `403 forbidden` regardless of whether it carries a valid token. Unset (the default) allows any source, matching this route's own scrape-token gate being the sole required control in that case.
- `[metrics] enabled = false` disables the route entirely (not mounted; `cmd/vnproxd` never even loads/generates the token file) — surfaced read-only via `GET /config`'s `metricsEnabled` field.

This does not weaken the model above: every other route in this document still requires the full session-cookie/CSRF/PVE-ACL chain. `GET /metrics` is read-only, exports no secret, and its own separate token is the *sole* new credential this addition introduces.

**Automation tokens (T-1104, addition).** `docs/api.md`'s Tokens section (`POST/GET/DELETE /tokens`) lets a logged-in user mint a vnprox-local, capability-scoped bearer token for automation callers (CI, `vnproxctl`, Terraform/Ansible — T-1105/T-1106). This is explicitly **not** a second login/authentication path, and it is a different mechanism from both the credentials this section otherwise documents and from the T-1001 metrics scrape token above:

- **Distinguished from the PVE ticket bridge.** A cookie session's identity and capabilities come from *forwarding the user's own credentials to PVE* (`POST /access/ticket`) — the session doesn't exist until PVE has authenticated the user. A token never touches PVE at all: it is minted by an *already-authenticated* session (cookie **or** an existing bearer token) and is vnprox's own delegated credential, checked entirely against vnprox's local `api_tokens` table. Presenting a token never creates a PVE ticket, never calls `POST /access/ticket`, and is invisible to PVE's own audit log — only vnprox's.
- **Distinguished from the metrics scrape token.** That token identifies "an authorized scraper" (a fixed, single, unscoped, install-time-generated credential with no user attached). An automation token identifies a *specific minting user* (`created_by`), is *dynamically mintable* any number of times, and is *capability-scoped per token* — the two are unrelated bearer schemes serving different purposes, both layered onto the same `Authorization: Bearer <token>` header convention rather than each inventing its own.
- **Minting, not a second privilege source.** `POST /tokens` validates every requested scope against the minting session's *own, currently-derived* capabilities (`internal/auth.Identity.ValidateScopeGrant`) — a token's scopes can never exceed what the creating user could already do at mint time. The one addition to the capability vocabulary, `automation` (gating the WS `"events"` topic and the webhook routes, `docs/api.md`'s WebSocket/Tokens & Webhooks sections), is never derived from a PVE privilege at all — it exists purely as a token scope, so a browser session alone can never reach those routes, only a minted token can.
- **Storage.** The raw token value is never persisted — only its hex-SHA-256 hash (`api_tokens.token_hash`), the same one-way-hash convention GitHub/GitLab personal access tokens use; `POST /tokens` reveals the raw value exactly once, at creation.
- **Revocation is immediate.** `DELETE /tokens/{id}` sets `revoked_at` (rejecting the token's next request with `401`) and force-closes any live WS connection that token authenticated in the same request (`internal/topology.Hub.CloseByTokenID`, using an immediate `CloseNow` teardown rather than a graceful close handshake, which could otherwise block the revoking request for several seconds waiting on an uncooperative peer).
- **Rate-limited and audited like every other credential in this document:** a per-token token-bucket (burst 60, refill 1/s by default) bounds a single token's request rate independent of the per-IP/per-username login limiter above; every authenticated use is audited (`token.use`), alongside `token.create`/`token.revoke` on the lifecycle routes themselves.
- CSRF is skipped for bearer-authenticated requests (there is no cookie to double-submit), the same precedent the metrics scrape token already sets for a non-cookie credential — every other control (rate limiting, audit, capability enforcement) still applies in full.

**Embed tokens (T-1706, addition).** `docs/api.md`'s Embeds section (`POST /embed/tokens`, `GET /embed/{map,dashboard,posture}`) lets a logged-in user mint a **read-only, token-scoped** embed of the map / home dashboard / posture report for a wiki, NOC screen, or status page. An embed token is a special case of the automation token above — an ordinary `api_tokens` row, same storage/revocation/rate-limit/audit machinery — with two extra, security-defining constraints:

- **A hard read-only ceiling, enforced server-side at mint.** `POST /embed/tokens` restricts scopes to the read-only subset `{netRead, sdnRead, fwRead, audit}` and rejects **any** other scope (`netWrite`, `sdnWrite`, `fwWrite`, `guestNet`, `capture`, `automation`) with a `400`, *before* the ordinary per-user ceiling check and **regardless of the minting user's own capabilities** — even a full-privilege admin cannot mint a write-capable embed token. Combined with the inherited `ValidateScopeGrant` ceiling, an embed token can never exceed its minting user's own scope and never carries a write surface. There is deliberately **no persisted `embed` column** (no schema change / forward-only-migration cost): "embed" is defined structurally by the read-only scope set, which the view-route auth re-checks on every request (a token carrying any write scope is refused at an embed route, `403`).
- **A distinct authentication path — never a session cookie.** The `GET /embed/{view}` shell routes have their own middleware that reads the token from the `?token=` query parameter **only** (an `<iframe>` cannot set an `Authorization` header) and **never inspects the session cookie** — a first-party browser session is never accepted in place of an embed token, so an embed pane cannot be silently authenticated by a logged-in operator's ambient cookie. The embedded view then reaches the ordinary `netRead`/… -gated read routes with the same token as a bearer credential, so no parallel, less-guarded read path is introduced. On the frontend the mirror holds: in embed mode the shared fetch wrapper sends the bearer token and sets `credentials: "omit"`, never falling back to the cookie.

**WireGuard tunnel keys (T-1401, addition).** A site-to-site WireGuard tunnel's private key is a new class of at-rest secret, stored under the **identical** AES-256-GCM primitive this section already documents for `sessions.pve_ticket_enc` — `internal/store.SessionCipher`, keyed from `/etc/vnprox/keys/session.key`, **not a second cipher or key pair** — in the `wireguard_tunnels.private_key_enc` column (docs/data-model.md §9, docs/api.md's WireGuard section).

- **Key custody.** The keypair is generated *on the owning node* via stdlib `crypto/ecdh`'s X25519 curve (`internal/wireguard.GenerateKeypair` — no new third-party crypto dependency) as part of applying a `wg.tunnel.create` changeset op, sealed once, and **never returned by any API response, log line, or audit-log detail**. Only the derived public key is exportable (`GET /wireguard/tunnels/{id}/pubkey`); `internal/wireguard.ParseDump` deliberately discards the interface's private-key column when polling live state. A tunnel's key is never regenerated in place — rotation is delete-and-recreate, always two ordinary audited changeset ops, never a silent overwrite. An optional per-peer preshared key uses the same sealed column shape (`wireguard_peers.preshared_key_enc`).
- **No new mutation path.** Every WireGuard change flows through the ordinary change engine (`internal/change`'s `wg.*` op family) — stage→validate→diff→apply→confirm/rollback — exactly like every other mutation; there is no dedicated WireGuard write route. The on-node apply step writes the wg-quick config and execs `wg`/`wg-quick` with a **fixed argv array** (no dynamic shell interpolation), mirroring the `ifreload`/`lldpctl` subprocess convention in the Host footprint section below.
- **Management-path interlock (no override).** A `wg.*` op on a tunnel whose carrier interface is itself part of a node's resolved management or corosync path is `touchesMgmtPath: true`, inheriting T-703's ceremony (typed node-name acknowledgement, 180s confirm-window floor) with **no override** — the "no override in UI" rule in the Safety interlocks section is unamended by this addition.
- **Residual risk, stated plainly.** An *external* peer's key material is never vnprox's to protect — peers outside vnprox's control are modeled read-only with config export only, and their own key hygiene is explicitly out of scope (surfaced in the operator-facing peer-config export copy, not papered over).

**OIDC SSO (T-1207, addition).** For federated deployments where per-cluster PVE credentials stop scaling, vnproxd offers OIDC login alongside the PVE ticket bridge — an OpenID Connect authorization-code + PKCE flow (`GET /auth/oidc/login`, `POST /auth/oidc/callback`, docs/api.md's Auth section), configured in `vnprox.toml`'s `[oidc]` section (`issuer`, `client_id`, `client_secret_file`, `redirect_url`, `scopes`, `groups_claim`, and a group→role mapping table). The precise split it draws is the load-bearing point:

- **OIDC authenticates the human to vnprox; PVE authorization still gates every cluster-scoped action per cluster.** An OIDC identity holds no PVE ticket by itself. A cluster-scoped action therefore still needs a resolved PVE authorization for that cluster: an admin-configured OIDC-group→PVE-identity mapping (the encrypted `oidc_pve_links` store table, docs/data-model.md §2), or — where no mapping exists — a first-use PVE-credential prompt. There is **no third path**: an OIDC login with no PVE linkage for a cluster is authenticated but holds **zero** cluster-scoped capability there (proven by T-1207's AC2 table/integration tests), never the OIDC bundle alone.
- **OIDC-derived capabilities are never additive beyond the linked PVE identity's own ACLs.** The group→role mapping maps OIDC group claims to a vnprox capability bundle (the same `internal/auth/caps.go` vocabulary the PVE-privilege mapping uses); that bundle is then **intersected** with the linked PVE identity's live-derived PVE ACLs (`internal/auth.IntersectCaps`, applied at the same `deriveCapabilities` point `forceReadOnly` uses, on both login and hourly re-derivation). The intersection can only ever *narrow* the PVE side — an OIDC bundle can never grant a capability the user's real PVE ACLs don't (T-1207 AC3), mirroring this section's "vnprox cannot exceed the user's PVE ACLs" invariant exactly.
- **Session lifecycle is the existing one.** An OIDC session is an ordinary server-side session — the identical HttpOnly/Secure/SameSite=Strict cookie, encrypted-at-rest session store, idle (2h) and hard-cap (12h) timeouts, and CSRF double-submit as a ticket-bridge session (T-1207 AC1/AC4). The one difference is renewal: where the ticket bridge renews the PVE ticket at ~half-life, an OIDC session renews via the IdP's **refresh token** (rotated and re-verified on each refresh); the OIDC ID/refresh tokens are never persisted in the app store, only the derived capabilities and (encrypted) an empty PVE-ticket placeholder.
- **Secrets at rest.** The OIDC **client secret** lives in `client_secret_file` (a `root:root 0600` file, the same on-disk-secret convention the session/metrics keys use), never inlined in the config in the clear. The mapped **PVE credentials** in `oidc_pve_links.credential_enc` are sealed with the **identical** AES-256-GCM `internal/store.SessionCipher` primitive `sessions.pve_ticket_enc`/`clusters.credential_enc` use — not a second cipher or key pair. **ID-token verification** is RS256-only against the IdP's published JWKS (issuer/audience/expiry/nonce all checked); `alg: none`/HS* are rejected outright, closing the classic alg-confusion downgrade rather than trusting the token's own header.

**Cluster-registry credentials (T-1201, addition).** Federation attaches N PVE clusters as app-owned registry rows (`clusters` table, docs/data-model.md §2); each cluster's own PVE API credential (a token or a ticket-bridge username/password used only for that cluster's `internal/pve.Client`) is sealed in `clusters.credential_enc` with the **identical** AES-256-GCM `internal/store.SessionCipher` primitive `sessions.pve_ticket_enc` uses — **not a new cipher, key, or on-disk secret**: one key (`/etc/vnprox/keys/session.key`) still seals every at-rest credential class in this document. The plaintext credential is never returned by any `/federation/clusters` response, log line, or audit detail (`internal/federation.Service` unseals only to construct a per-cluster client, and `TestService_CredentialCiphertextNeverContainsPlaintext` asserts the stored bytes never contain the plaintext token). Federation federates *reads*; it introduces **no** cross-cluster mutation primitive — `internal/change` rejects at validation any op whose target Ref belongs to a different cluster than the changeset's `clusterId`, so an attached cluster's credential can never be used to write to another cluster's config.

**Switch-driver credentials (T-1205, addition).** The guarded switch-config-push surface stores each registered switch's driver credential (gNMI/OpenConfig auth) in `switches.credentials_enc`, sealed with the **same** `internal/store.SessionCipher` primitive as every credential class above — not a second cipher or key pair (`TestSwitchRepo_CredentialsEncryptedAtRest` asserts the stored bytes never contain the plaintext credential and only the cipher recovers it). The plaintext is never returned by any API response, log line, or audit detail. Switch push **ships dark by construction**: no push is possible unless both the daemon-level `[switches] enabled` flag *and* the specific switch's `enabled` row are true, and every push is an ordinary change-engine changeset (`switch.port.update`, VLAN-membership/description/LACP only) — the mgmt-path interlocks extend one LLDP hop onto the uplink port carrying a node's management path, hard-blocked (`safety.protected_switch_port`, no override) if a push's net effect would strip that port's management VLAN. A switch that becomes unreachable after a push cannot be remotely reverted (there is no recovery agent living on the switch): that residual risk is stated plainly to the operator, and such a changeset lands in a distinguishable "rollback incomplete — needs manual intervention" state rather than being silently marked `rolled_back`.

## Authorization

Two enforcement layers, both required:

1. **PVE-enforced (primary):** all PVE API writes use the *user's own ticket* — vnprox cannot exceed the user's PVE ACLs, and PVE remains the audit point of record for those calls.
2. **vnprox-enforced (for host-level ops):** operations that bypass the PVE API (reading LLDP, staging `/etc/network/interfaces`, ifreload, snapshot restore) are gated on capability flags derived from the user's PVE ACLs at login (and re-derived hourly): `Sys.Audit` on `/nodes/{node}` → read; `Sys.Modify` on `/nodes/{node}` → node network write; `SDN.Allocate` → SDN write; `VM.Config.Network` → guest NIC edits; firewall caps from `Sys.Modify`/relevant paths. The mapping table lives in `internal/auth/caps.go` and is the single source of truth.

   **Packet capture — `capture` capability (T-1301).** The distributed packet-capture surface (`POST /captures` and the peer routes it fans out to) is gated on a **dedicated** `capture` capability, distinct from `netRead`/`netWrite`. It is deliberately **at least as strict as `netWrite`'s** gate: `capture` is derived only from `Sys.Modify` **and** `Sys.Console` held together on `/nodes/{node}` (the same root-shell-equivalent access class needed to run `tcpdump` on the host by hand). Holding `netRead`/`netWrite` alone — even every read/write privilege short of `Sys.Console` — therefore **never** grants capture; a session must hold `capture` explicitly. Rationale: capture exposes raw payload bytes, a materially stronger read than any config counter, so a wrong permission decision here is a data-exposure incident that cannot be retrofitted. Every `/captures` route requires both `netRead` and `capture`. When `[server] read_only = true` (docs/features/blueprints.md §3's "observe-only until you trust it" toggle), every derived capability's write flags are additionally forced false regardless of the user's PVE ACLs (`internal/auth.forceReadOnly`, applied inside `deriveCapabilities`) — since every `RequireCap`-gated mutating route in `internal/api` gates on these same flags, this makes `read_only` a real, server-enforced restriction, not merely a UI affordance the frontend is trusted to hide.

   **Plugin capability scope (T-1702).** An installed extension plugin (`internal/plugin`)
   declares a **capability scope** drawn entirely from the `internal/auth/caps.go` vocabulary
   above — the SDK introduces **no new privilege** of its own. The scope is a **ceiling, not a
   grant**, enforced server-side and structurally:

   - **Stage-only, never apply.** The only change-engine surface handed to plugin code is
     `plugin.Stager` (Create/Validate). No Apply/Confirm/Rollback method is reachable from a
     plugin — in-process or over the out-of-process transport — so a plugin can stage a draft
     changeset for a human to apply but is never itself a mutation path. This is the same
     apply-only-through-the-change-engine guarantee every mutation has had since T-205, and it
     is verified by an interface-surface test, not by convention.
   - **The scope caps what a plugin can construct.** Every op a plugin tries to stage is mapped
     (`plugin.RequiredCap`) to the capability that op class already requires (`fw.*`→`fwWrite`,
     `sdn.*`→`sdnWrite`, `guest.nic.update`→`guestNet`, everything else→`netWrite`, fail-safe
     default `netWrite` for any unmapped op). If the plugin's declared scope does not cover an
     op's required capability, the op is rejected **before it ever reaches `internal/change`** —
     a plugin whose scope excludes `netWrite` cannot construct a `netWrite`-class op. A plugin
     also cannot *register* an extension point whose entry ceiling its scope does not meet (the
     write-adjacent `switchDriver` point requires `netWrite`; the four read-only points require
     `netRead`).
   - **Audited and bounded.** Install/enable/disable/uninstall each write an audit row recording
     the plugin's capability scope, so `GET /audit` always shows what a plugin may touch and who
     installed it. An out-of-process plugin runs as a supervised subprocess (`procshim`) with no
     DB/file access; its only channel back into vnprox is the capability-scoped `Stager`. Residual
     risk: the subprocess can make unconstrained OS-level network calls from its own process — a
     stated-not-hidden risk (mirroring T-1205's switch-rollback residual-risk stance), to be
     bounded operationally (systemd sandboxing / netns) rather than by the SDK.
**MCP stage-only boundary (T-1701) — the central invariant of the AI-operator surface.** The Model Context Protocol server (`internal/mcp`, docs/api.md's "MCP server" section) lets an AI operator reach vnprox's read surfaces and *stage* a draft changeset — and nothing else. **No apply/confirm/rollback/discard verb is reachable through MCP, by any tool, parameter, or combination of tools.** A human (or T-1103's confirm machinery) remains the sole apply/confirm authority; an MCP-staged changeset is an ordinary draft a person still reviews and applies through the change engine. This boundary is enforced **structurally**, not by convention, on two independent axes:

1. **A fixed, enumerable tool allowlist.** The MCP surface is exactly nine tools (docs/api.md's tool table), not a generic "call any route" bridge. A package-load check rejects any tool whose name matches an apply/confirm/rollback/discard verb, and a registry-enumeration test pins the exact set so a future edit that adds an apply-shaped tool fails the build.
2. **A change-engine seam with no mutation verb.** The only change-engine capability handed to the MCP server is a narrow interface exposing `CreateWithOrigin`/`Validate`/`Diff` — it has no `Apply`/`Confirm`/`Rollback`/`Discard` method at all, so no MCP code path can call a live-mutating verb even if a tool tried (an interface-surface test asserts the omission, the same style T-1702's plugin seam uses).

MCP auth reuses T-1104's bearer tokens unchanged: a session must present a token carrying the `automation` scope, and each tool is exposed only if the token's scopes cover it — a `{netRead, automation}` token can never reach the `netWrite`-gated staging tools. Exposure is derived from the token at connect time, never from a client assertion; revoking the token force-closes the session within one tick. **Every AI-originated changeset is unerasably labelled** `origin: "mcp"` with the staging token's id, and every MCP tool invocation writes its own audit row with actor `mcp:<token-name>`, so an operator reading `GET /audit` can always tell an AI-originated action from a human one.

There is **one privileged internal identity**: a PVE API token `vnprox@pve!daemon` (created at install, stored root-only) used exclusively for *read* polling by collectors — never for writes. Writes without a user context do not exist, with one exception: automatic rollback of an unconfirmed changeset, which restores from snapshot using host-level file operations and is attributed in the audit log to `system:rollback` with the originating user recorded.

**Tenant authorization (T-1703, addition).** Multi-tenancy layers delegated, server-side-scoped views on top of the two enforcement layers above — it only ever **narrows** what a principal may see and do, never widens it, and it never adds a mutation path around the change engine. The load-bearing points:

- **Scoping is enforced server-side, at the data-access layer — never only in the UI.** The authority for "what may this principal see" is the tenant store (`tenants`/`tenant_scopes`/`tenant_members`, docs/data-model.md §2), resolved fresh on every request from the *authenticated* identity (`internal/tenant.Service.ScopeFor`), never from any client-supplied value. The `internal/api` scoping middleware attaches the resolved `Scope` to the request context; every tenant-scoped read handler (`/topology`, `/findings`, `/ipam/*`, `/flows`, plus inventory detail and search) filters its in-memory projection through that `Scope` **before serialization** — the same enforcement-point pattern `internal/auth.forceReadOnly` uses, not a response-shaping filter a client could bypass. A caller who is not a tenant member gets no `Scope` and reads unscoped, exactly as before.
- **No cross-tenant leakage — list, search, error, or count.** A tenant sees only its own delegated view: list endpoints drop out-of-scope items, search filters to visible Refs, the scoped dashboard counts only in-scope resources, and a **direct out-of-scope Ref lookup returns `404`, not `403`** (existence is never confirmed). A hostile client crafting IDs from another tenant learns nothing — the same "not-found, not-forbidden" stance the metrics/token paths already take for a wrong credential.
- **Requests still flow through the change engine.** A tenant member does not write; they **request** via a request-changeset (`POST /changesets {tenantId}` → an ordinary changeset in the additive `requested` status), which is validated exactly like a draft but blocked from apply until an **approver** of that tenant calls `POST /changesets/{id}/approve` (converting it to a `draft`). A member can never approve, and even an approver can never approve their own request (separation of duties — server-side role check). Every op in a request is verified server-side to target a Ref within the tenant's scope; an op with a zero or out-of-scope target is rejected. Approval is **not** apply — the approver still drives the ordinary draft → validate → apply → confirm/rollback flow afterward, so multi-tenancy narrows *who may touch what*, never *how* a change is applied.
- **Identity supply.** Tenant membership is keyed on the authenticated principal (a PVE-ticket-bridge or OIDC username). OIDC group claims map to tenant memberships (`internal/tenant.MapGroupsToTenants`) the same way T-1207 maps groups to capability bundles — and, like that mapping, this grants no capability by itself (OIDC caps are still intersected with the linked PVE identity's ACLs); it only selects which tenant's scoped view an authenticated user lands in.

## Transport

- TLS everywhere; no plaintext listener. Reuses the node's PVE certificate by default (see architecture §9), so admins keep one cert story.
- HSTS, `X-Content-Type-Options`, `X-Frame-Options: DENY`, and a strict CSP (self-only; no inline script; WS to self).
- Peer API: TLS + HMAC-SHA256 over (method, path, body hash, timestamp) with the cluster secret; ±30s replay window; constant-time compare.
- **HA replication transport (T-1704, addition):** the active/standby state-replication push (`POST /api/peer/ha/replicate`, docs/architecture.md §12) rides this **same** peer channel — TLS + cluster-secret HMAC + replay window — introducing no new transport credential or listener. The push is directed only at the operator-configured standby and is fenced by the lease `term` on receipt (a stale-term batch applies nothing); replicated sealed columns stay ciphertext, decrypting on the standby only under the identical `[storage] session_key_file` (see the threat-model row).
- **Metrics exporter transport (T-1001, addition):** `GET /metrics` is served over the same TLS listener as every other route (no separate plaintext metrics port) — a Prometheus scrape target must be configured `scheme: https` and to trust the node's certificate (or `tls_config.insecure_skip_verify` for a lab/dev target), same as any other HTTPS scrape. The bearer token above travels only over this TLS connection, never in a query string or a redirect.

## Host footprint

- Systemd unit hardening: `ProtectSystem=strict` with explicit `ReadWritePaths` (`/var/lib/vnprox`, `/etc/vnprox/keys`, `/etc/wireguard`, `/etc/network`, `/run`), `ProtectHome=yes`, `PrivateTmp=yes`, `NoNewPrivileges=yes`. (`/etc/vnprox/keys` is writable because the daemon generates first-run secrets there — session key, metrics scrape token, blueprint signing key — `0600 root:root`; the rest of `/etc` stays read-only. **v3.0.1** added this path after a real-hardware upgrade from a pre-metrics release crash-looped writing `metrics.key`/`blueprint-signing.key` into then-read-only `/etc/vnprox`. **v3.0.2** added `/etc/wireguard` — applying a WireGuard changeset op writes each tunnel's wg-quick config there (`cmd/vnproxd/wireguard.go`), which `ProtectSystem=strict` was also blocking; the same crash class the v3.0.1 keys fix missed. `postinst` creates `/etc/wireguard` `0700 root:root` so the bind target always exists. The cluster secret's fallback generate-if-absent write to `/etc/pve/priv/vnprox/` is deliberately *not* in `ReadWritePaths`: `/etc/pve` is a pmxcfs FUSE mount that `vnprox-setup` pre-seeds, and whether `ProtectSystem=strict` even makes it read-only is pending hardware validation — see `planning/reports/needs-hardware-validation.md`.) **Updated (T-604, completed):** the process still runs as root (no `User=`/`Group=` — netlink/ifreload/file-ownership operations require it), but `CapabilityBoundingSet` is now scoped to exactly six capabilities (`CAP_NET_ADMIN`, `CAP_NET_RAW`, `CAP_NET_BIND_SERVICE`, `CAP_DAC_OVERRIDE`, `CAP_DAC_READ_SEARCH`, `CAP_CHOWN`, `CAP_FOWNER`) rather than the full root set, plus `ProtectKernelModules=yes`, `ProtectKernelTunables=yes`, `ProtectKernelLogs=yes`, `RestrictAddressFamilies=AF_INET AF_INET6 AF_NETLINK AF_UNIX`, and a `SystemCallFilter=@system-service` allowlist (`packaging/systemd/vnprox.service`, `docs/security-verification.md`'s Host footprint section has the full evidence). **Correction (T-608, hardware validation):** `AF_UNIX` is required, not excludable — this seccomp filter is inherited across exec by every subprocess vnproxd spawns, including `lldpctl`, which talks to lldpd over a Unix domain socket (`/run/lldpd.socket`); omitting it silently broke every LLDP poll on a real node. Full non-root operation remains out of scope for v1 (tracked post-1.0).
- vnproxd never shells out with user-supplied strings; the external commands it does exec (`lldpctl -f json`, `vtysh` for FRR, `ifreload -a`, the lldpd install/enable commands, and the read-only diagnostic probes added across Phases 13–14 — `wg`/`wg-quick` for WireGuard config apply, `ping`/`ping -M do` for the latency mesh, path-MTU prober, and WAN & upstream health probe (T-1405), `conntrack -L` for the conntrack explorer, `nsenter`+`ip`/`ss` for the lxc guest-interior reads, and `rdisc6` for the IPv6 RA reader) use fixed argv arrays; the few that take a dynamic argument only ever pass a validated, non-shell-interpolated value (a node/vmid/target resolved from inventory, an operator-configured WAN reference target — schema-validated non-empty on `PUT /wan/targets`, still just one fixed argv element, never shell-interpolated — or an operator-chosen BPF filter that is server-validated before it reaches a capture process). `ifreload -a` reloads the whole file — per-interface commands don't exist. **Correction (T-607 docs audit):** `ethtool` is not invoked as a subprocess at all — link speed/duplex is read via the `SIOCETHTOOL` ioctl directly (`internal/host/ethtool_linux.go`), a stronger property (zero shell-out surface) than the "fixed argv" claim above implies; see `docs/security-verification.md`'s Host footprint section for the full evidence and citations.
- SQLite DB and key files are `root:root 0600`; snapshots contain network configs (not secrets) but are treated as sensitive.
- **Host-local flow sampling capability footprint (T-1004, addition):** `internal/flow/hostsample`'s conntrack sampler (periodic `/proc/net/nf_conntrack` poll, `[flows] conntrack_sampling_enabled`) needs no capability beyond the six already in `CapabilityBoundingSet` above (`CAP_DAC_READ_SEARCH` already covers reading the procfs table). Its eBPF sampler (`[flows] ebpf_sampling_enabled`), when enabled, needs **`CAP_BPF` and `CAP_PERFMON`** — capabilities beyond those six, not previously required by anything else vnproxd does, and not present in the shipped unit's bounding set. These two capabilities are **flagged, never granted unconditionally**: `packaging/debian/postinst` only writes a systemd drop-in (`/etc/systemd/system/vnprox.service.d/10-ebpf-caps.conf`, adding `CapabilityBoundingSet=CAP_BPF CAP_PERFMON` — systemd unions repeated `CapabilityBoundingSet=` assignments rather than replacing them) when it finds `ebpf_sampling_enabled = true` in `/etc/vnprox/vnprox.toml` at install/upgrade time, and removes that drop-in when the value is absent/false; a node that never opts in never has its capability bounding set widened. Even with both capabilities granted, `internal/flow/hostsample`'s runtime kernel-feature probe (Linux 5.8+, both capabilities present in this process's effective set, and BTF/CO-RE support at `/sys/kernel/btf/vmlinux`) must also pass before the eBPF sampler is considered active; a probe failure is logged (naming the missing capability/feature) and the daemon falls back to conntrack-only (or fully disabled) sampling — never fatal. As of this task, actual per-packet BPF program attachment is not implemented (no third-party eBPF loader dependency has been added, per CLAUDE.md's dependency rule) — only the kernel-feature probe and the capability-grant scaffolding are real; see `planning/reports/T-1004.md` and `planning/reports/needs-hardware-validation.md`.

- **Packet-capture file footprint (T-1301, addition):** `internal/capture` writes captured packets to one bounded `.pcap` file per session under `[capture] root` (default `/var/lib/vnprox/captures/`, already an app-owned, `root:root` `ReadWritePath` in the systemd unit — no new writable path). Reading raw packets off a live interface needs `CAP_NET_RAW`, already in the shipped unit's `CapabilityBoundingSet` (host footprint above) — no capability widening. Every capture file is **hard-bounded** at write time by server-enforced, un-overridable caps (a time cap, a byte cap, and a packet cap — whichever is hit first stops the capture; no API parameter, admin flag, or filter construction can raise these past their configured `vnprox.toml` `[capture]` ceilings, and each capturing node re-clamps independently), and **auto-purged** past `[capture] retention_hours` by an owned sweep goroutine (`internal/capture.Coordinator.Sweep`, on the same tick-cadence pattern `internal/metrics`' ring pruning uses) — including files orphaned by a daemon restart mid-capture. **Captured payload bytes never leave that file:** nothing is copied into SQLite, the audit log, WS events, or any other store — `capture_sessions` and the `capture.start`/`capture.stop` audit rows carry app-owned intent + byte/packet *counts* only, never packet contents (regression-tested, grep-verifiable across the store/audit code paths). The submitted BPF filter is server-validated (shell-unsafe characters and over-ceiling instruction counts rejected) before any capture process is invoked. As of T-1301 the on-hardware capture backend (a real `tcpdump`/AF_PACKET binding) is a **needs-hardware-validation** item — development/tests run against `internal/capturemock`'s scripted agent; every surrounding safety property (capability gate, caps, filter validation, audit, retention, peer fan-out) is real and agent-agnostic.

## Safety interlocks (availability is security here)

- The change engine refuses (hard error, no override in UI; override only via config flag `allow_dangerous_ops`) any changeset that would: remove/re-address the interface carrying the node's management IP, take down the interface used by corosync links, or delete a bridge with running guests attached (must first present guest reattachment ops).
- Commit-confirm auto-rollback (architecture §4) bounds the blast radius of every applied change.
- Cluster-wide apply lock prevents concurrent conflicting changesets.
- **Scheduled/unattended apply (T-1103, addition):** a changeset whose ops touch a node's resolved management path (`touchesMgmtPath`) can never be scheduled for unattended apply (docs/api.md's `POST /changesets/{id}/schedule`: `422 mgmt_path_unattended_forbidden`). This is a **stricter, separate gate** from the `allow_dangerous_ops` line above, not an application of it: `allow_dangerous_ops` only ever downgrades a T-203 safety-interlock *validation finding* from error to warning for an ordinary, interactively-confirmed apply — it has no bearing on, and no effect over, the scheduling gate, which checks `touchesMgmtPath` directly and unconditionally before any validation pass even runs. There is no config flag, request field, or combination of the two that schedules a management-path change for unattended apply; the only path to changing a node's management path stays the interactive one (T-703's guided wizard, reviewed and confirmed by a human at apply time).

## Blueprint & plugin hub (T-1705)

The hub (`internal/hub`, opt-in via `[hub] registry_url`) is a browse/install **client** over a public registry of signed blueprint bundles (T-1107) and SDK plugins (T-1702); the registry service lives in a separate repo. It is **not a new trust boundary** — it inherits, and never weakens, the existing gates:

- **Signature + trust gate (inherited).** A downloaded blueprint bundle goes through T-1107's exact `POST /blueprints/import` path (the same `importBundleCore`); a downloaded plugin manifest is verified with the same Ed25519 primitive (`blueprint.VerifySignature`) against the same trust store. An unsigned or untrusted-signer artifact is never installed without the explicit `trustUnsigned`/`trustNewKey` decision, identical to a direct import.
- **Capability scope (inherited).** A plugin install is completed only through T-1702's `Registry.Install`, which re-validates the declared capability scope against `internal/auth`'s vocabulary. The hub reaches no path that installs a plugin without that check; only out-of-process (`grpc`) plugins are installable this way.
- **Vetted tier is informational only.** `[hub] vetted_signers` is the hub's own recognized-signer allowlist, **distinct** from the per-admin trust store. A "vetted" badge is display metadata; it never substitutes for the per-installation trust decision — a vetted-but-untrusted signer still requires an explicit trust step. This is a deliberate non-authority: the vetted list can add reassurance but can never grant trust an admin hasn't.
- **Off-origin fetch guard.** The fetched `index.json` is not signed as a whole, so an entry's `artifactUrl` is required to resolve to the registry's own host — the index can never redirect an install to an arbitrary third-party host (the artifact's own signature remains the authoritative gate; this is defence in depth).

## Audit

Every mutation attempt (including denied and rolled-back) is written to the audit log with user, source IP, changeset id, op summaries, and result. Audit entries are append-only at the API layer; there is no delete endpoint. Hub installs are audited as `blueprint.import` (blueprint installs, reusing T-1107's exact audit) or `hub.install` (plugin installs, recording the trust decision and signer fingerprint).

## Threat model summary

| Threat | Mitigation |
|---|---|
| Credential stuffing on 8007 | rate limits, PVE lockout semantics, TOTP passthrough |
| Session theft | HttpOnly+Secure+SameSite cookies, short idle timeout, encrypted server-side tickets |
| Privilege escalation via vnprox | user-ticket writes (PVE enforces), read-only daemon token, cap mapping for host ops |
| Rogue peer / lateral movement | cluster-secret HMAC + TLS, pmxcfs-distributed root-only secret, replay window |
| Malicious/buggy change bricks cluster | validators + safety interlocks + commit-confirm rollback + time machine |
| Supply chain | pinned deps, `make check` includes `govulncheck` + `npm audit` gates in CI |
| XSS → config change | strict CSP, no inline script, CSRF header, framework-escaped rendering only |
| Metrics scrape token theft (T-1001) | token is separate from the session cookie (theft of one doesn't grant the other), constant-time compare, optional source-CIDR allowlist, route is read-only and exports no secret |
| Automation token theft/overreach (T-1104) | scopes bounded to the minting user's own capabilities at mint time, raw value stored only as a one-way hash, immediate revocation force-closes live WS use, per-token rate limit, every use audited (`token.use`) |
| Webhook target compromise/tampering (T-1104) | delivery signed per-body (`X-VNPROX-SIGNATURE`, HMAC-SHA256, constant-time verify), retried with bounded backoff, `webhook_unhealthy` finding surfaces N consecutive delivery failures |
| Embed token overreach / write via an embed (T-1706) | scopes hard-restricted to read-only at mint (`400` for any write scope, before the per-user ceiling, regardless of the minting user's caps), re-checked on every embed request; embed view routes authenticate the `?token=` query token only and never a session cookie (distinct middleware path); the embedded view reaches only the existing read-only gated routes — no parallel read path, no persisted privilege beyond the read-only scope set |
| OIDC token forgery / IdP-response tampering (T-1207) | RS256-only ID-token verification against the IdP's published JWKS (issuer/audience/expiry/nonce checked; `alg:none`/HS* rejected — no alg-confusion downgrade), PKCE (S256) + single-use state/nonce on every auth request, mapped-PVE credentials encrypted at rest (`oidc_pve_links.credential_enc`), OIDC caps intersected with (never additive to) the linked PVE identity's real ACLs |
| Over-privileged OIDC group mapping (T-1207) | group→role bundle is always intersected with the linked PVE identity's live-derived ACLs (`IntersectCaps`); no PVE linkage → zero cluster-scoped capability; `[server] read_only` still forces every OIDC session read-only server-side |
| Cluster-registry credential theft (T-1201) | per-cluster PVE credential sealed in `clusters.credential_enc` with the one AES-256-GCM session key (never a new secret), never returned by any API/log/audit, ciphertext-vs-plaintext regression-tested; no cross-cluster mutation primitive exists, so a leaked credential cannot be used to write another cluster |
| Malicious/over-reaching extension plugin (T-1702) | plugin capability scope is a server-enforced ceiling drawn from the existing `caps.go` vocabulary (no new privilege); the only change-engine seam a plugin holds is stage-only `Stager` (no Apply/Confirm/Rollback reachable, verified by an interface-surface test); an op whose required capability the scope excludes is rejected before reaching `internal/change`; out-of-process plugins run as supervised subprocesses with no DB/file access and degrade gracefully when killed; install/enable/disable/uninstall are audited with the recorded scope |
| Rogue / compromised attached cluster (T-1201) | config ownership stays strictly per-cluster; a changeset's ops are validated to belong to its own `clusterId` (cross-cluster op rejected); an unreachable/misbehaving cluster is failure-isolated (`partial`/`failedClusters`) and never blanks or errors the aggregate response for the healthy clusters — a hostile cluster degrades only its own capsule, not the federation |
| Cross-tenant data disclosure (T-1703) | tenant scoping enforced server-side at the data-access layer (`internal/tenant.Service` + the `internal/api` scoping middleware) — every scoped read filters the projection by the authenticated principal's `tenant_scopes` before serialization; an out-of-scope direct Ref lookup is `404` (existence not confirmed), and list/search/dashboard-count paths never emit another tenant's data; a request-changeset's ops are server-verified to target only in-scope Refs |
| Tenant privilege escalation / rogue approval (T-1703) | a request-changeset is blocked from apply until an approver of the owning tenant converts it to a draft (change-engine `requested`→`draft` transition, no path to `applying`); a plain member can never approve, and an approver can never approve their own request (server-side role check); approval is not apply — the ordinary confirm/rollback flow still gates the real mutation |
| Switch-driver credential theft / errant push (T-1205) | `switches.credentials_enc` sealed with the same session cipher, never returned, ciphertext-vs-plaintext regression-tested; push ships dark (daemon flag **and** per-switch `enabled` both required); every push is a change-engine changeset scoped to PVE-facing ports only, with a mandatory pre-write LLDP-neighbor identity re-check (hard abort on mismatch) and mgmt-path interlock (`safety.protected_switch_port`, no override); unrevertable-after-push risk surfaced as a distinguishable "rollback incomplete" state |
| Captured packet-payload exposure (T-1301) | capture is gated on the dedicated `capture` capability (derived only from `Sys.Modify`+`Sys.Console`, ≥ `netWrite`'s strictness — Authorization above); each `.pcap` is hard-bounded at write time by server-enforced, un-overridable time/byte/packet caps (re-clamped independently on every capturing node) and auto-purged past `[capture] retention_hours`; **payload bytes never leave the capture file** — nothing is copied into SQLite, the audit log, or WS events (only byte/packet counts), regression-tested by `TestNoPayloadBytesPersistedOutsideCaptureFile`; the submitted BPF filter is server-validated before any capture process runs |
| WireGuard tunnel key theft (T-1401) | the X25519 tunnel private key is sealed in `wireguard_tunnels.private_key_enc` (and any per-peer PSK in `wireguard_peers.preshared_key_enc`) with the **one** AES-256-GCM session key — not a second cipher or key pair — generated on the owning node, sealed once, and **never returned** by any API/log/audit (only the derived public key is exportable); no-plaintext-at-rest is regression-tested (`TestWireGuardRepo_PrivateKeyEncryptedAtRest` for the tunnel key at the store layer, `TestSealOpSecrets_NoPlaintextPSKAtRest` + the API non-leak tests for the PSK in staged ops); rotation is delete-and-recreate (two audited changeset ops), never a silent overwrite; an external peer's own key hygiene is out of scope, stated plainly |
| MCP AI-operator surface abuse (T-1701) | the AI-operator surface is **read + stage only** — a fixed nine-tool allowlist with no apply/confirm/rollback/discard tool reachable by any tool/parameter/combination (package-load verb check + registry-enumeration test + a change-engine seam with no mutation method); MCP reuses T-1104 bearer tokens (must carry `automation`; each tool exposed only if the token's scopes cover it, derived at connect time, revocation force-closes within one tick); every AI-staged changeset is unerasably labelled `origin: "mcp"`+`originTokenId` and every tool call is audited with actor `mcp:<token-name>`, so an operator can always distinguish an AI action from a human one; a human remains the sole apply/confirm authority |
| HA replication-channel compromise / rogue standby (T-1704) | HA replication rides `internal/peer`'s existing TLS + HMAC-SHA256(cluster-secret) channel with the ±30s replay window — **no new transport credential**; the `POST /api/peer/ha/replicate` push targets only the operator-configured standby, never an arbitrary cluster peer, and is fenced by the lease `term` (a stale-term or out-of-band batch is rejected by `internal/ha.Manager.Receive`, no data applied); it introduces **no new at-rest credential class** — `api_tokens` replicate as one-way hashes and any sealed column (WireGuard keys, webhook secrets) replicates as ciphertext that decrypts on the standby only under the **same** `[storage] session_key_file`, so a standby with the wrong key holds unreadable ciphertext, not plaintext |
