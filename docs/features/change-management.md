# Feature spec — Change management

The change engine is vnprox's safety core. Architecture §4 defines the lifecycle; this spec defines behavior and UX.

## 1. Changeset drawer (UX)

A persistent drawer (bottom-right) accumulates draft ops as the user edits anywhere in the UI — map drag-drops, form edits, firewall rule changes all land here. The drawer shows: op list (human-readable summaries, reorderable, individually removable), live validation status, and buttons **Review & apply** / **Discard**. Multiple named drafts can be parked and resumed. Editing never mutates anything until apply.

## 2. Validation

Runs on every draft change and again immediately before apply (state may have moved). Validator classes, executed in order:

1. **Schema** — types, ranges (VID 1–4094, MTU 576–9216, bond mode enums, CIDR syntax).
2. **Referential** — targets exist; no duplicate enslavement; name collisions; VID overlaps on a trunk; address overlaps with existing subnets.
3. **Policy (T-2601)** — the cluster's declarative policy-as-code rule set, below. `deny` rules are hard errors; `warn` rules annotate.
4. **Safety (interlocks)** — see `docs/security.md`: management-IP interface, corosync links, bridges with running guests. Hard errors.
5. **Cross-node consistency** — the changeset's *projected* effect, folded across **every** cluster node (not just the node(s) an op targets), compared for same-named bridge divergence, MTU asymmetry, and SDN zone realization gaps. Hard errors that block apply.
6. **Advisory** — style/health warnings (bond without `xmit_hash_policy layer3+4` on 802.3ad, bridge without description, single-slave bond).

The numbers shifted by one when the policy class was inserted at 3 (T-2601): code comments predating it that say "class 3" (safety), "class 4" (cross-node) or "class 5" (advisory) name the same classes. Two further blocking classes run inside this sequence without numbers of their own — T-402's SDN pre-apply checks and T-1205's switch-push authorization, both between referential and policy. Every class short-circuits the rest on any error-severity finding.

**Cross-node consistency (T-801).** The same shape of comparison the async drift checker (`docs/features/topology.md` §6, 30s interval) runs against *live* state, run instead against *what the state would become* — so cross-node breakage a changeset would introduce or leave uncorrected is caught at **review time**, not only on the next drift cycle. The comparison logic is genuinely shared with `internal/drift` (both call the same functions in `internal/xnode` — one implementation, not the same problem under two names), but severity is this class's own: every finding here is a blocking **error** (the drift checker's own equivalents warn), because a changeset that would leave the cluster inconsistent should not apply without the operator seeing it. Runs after Safety and before Advisory (`validate.go`), short-circuiting Advisory on any error like the earlier classes; scoped to same-named bridge groups the changeset actually touches (a bridge the changeset leaves entirely alone stays the drift checker's job). The three codes:
- `crossnode.bridge_divergence` (`severity: "error"`): a same-named bridge whose presence, VLAN-awareness, or VID set diverges across the projected cluster. The VLAN-awareness/VID-set forms carry a `fix` restoring parity; the presence form does not (creating a missing bridge needs a physical-port decision), mirroring drift's own fixable/not-fixable split.
- `crossnode.mtu_consistency` (`severity: "error"`): a same-named bridge whose MTU diverges across the projected cluster, with a `fix` aligning outliers to the majority MTU.
- `crossnode.sdn_realization` (`severity: "error"`, detection-only, no `fix`): an SDN zone that, in the projected cluster, lists a member node whose realizing bridge does not exist there — closing the gap `sdnValidate` leaves, where a plain `bridge.delete`/`iface.rename` op (no `sdn.*` op) silently breaks an *untouched* zone's realization on one node.

**Policy-as-code guardrails (T-2601).** `protected.go` encodes exactly one organisational rule — don't cut the management path — and it is hard-coded. Every other rule an organisation has ("no guest on VLAN 1", "every bridge carrying guests needs two uplinks", "never touch `vmbr9` on the storage nodes") used to live in a wiki, enforced by whoever happened to review. This class evaluates them as **data**, at the validate stage, so a violating changeset never reaches diff.

A rule is `{id, description, severity, match, assert, tags?, zone?}`, where `match` and `assert` are lists of `{field, op, value}` conditions over the same op and inventory shapes the change engine already uses. It is deliberately **not a scripting language**: there is no expression interpreter and no policy-engine dependency, and a rule that genuinely cannot be expressed this way is a decision to record, not a language feature to add. `field` names either the op's own params (`params.<jsonField>`, exactly the shape docs/data-model.md §3 documents) or one of a small closed set of derived facts — `op`, `target.kind|node|id|ref|exists|protected|guestCount|uplinkCount|vlanAware`, `changeset.opCount`, and (T-4006) `time.now|weekday|minuteOfDay|date|dayOfMonth|month` — every non-`time.*` one evaluated against the changeset's **net effect** on live inventory, because an organisational rule is about the state the cluster is left in. An empty `assert` means the match itself is the violation.

**Freeze windows (T-4006)** are the clearest instance of that last sentence: "no changes during the Friday afternoon freeze" is an ordinary `PolicyRule` — an op-type wildcard match plus `time.*` conditions, empty `assert` — not a second rule type. `time.now` is a zone-free absolute instant (for a one-off date range, bounded once at authoring time); `time.weekday`/`time.minuteOfDay`/`time.date`/`time.dayOfMonth`/`time.month` are local-wall-clock facts resolved in the rule's own `zone` (an IANA name), which `PolicySet.Validate` **requires explicitly** whenever one of them is used — there is no fallback to UTC or the daemon's own local zone, because a silently-wrong zone is precisely the failure this card exists to prevent. `severity: deny` blocks staging outright; `severity: warn` annotates without blocking, the same distinction every other rule makes. Both the validate-time refusal and T-1103's scheduler fire-time re-validation evaluate the SAME installed policy set fresh each time, so a freeze declared after a changeset was already scheduled still catches it at fire time. `GET /calendar` (a best-effort READER, never a second evaluation path) renders declared freeze windows alongside pending schedules. The escape hatch — `POST /changesets/{id}/freeze-override`, `{reason}` required — follows T-2604 break-glass's audited shape (reasoned, recorded, its own `change.freeze_override` audit action, pinned to the ops it was taken for) but, because a freeze is a validate-time finding rather than an apply-time authorization gate, it downgrades the freeze rule's finding to a visible `[overridden: ...]` warning instead of satisfying a separate check. See docs/api.md's "Freeze windows & the change calendar" section for the full contract.

`severity: deny` produces a blocking `policy.violation` finding naming the rule id and its description; `severity: warn` produces a non-blocking one that rides the changeset's findings to the review surface. A rule that matches nothing is not a silent pass: the statically-decidable cases (an op type or params field no matchable op has) are **load errors**, and a rule that has gone through enough evaluations over a long enough window without ever matching is reported as `probablyMisconfigured` on `GET /policies`.

Rule sets are cluster-scoped and versioned in the store, and every change is audited `policy.update` with the full rule-set diff. A daemon can also be pointed at a policy file (`[changesets] policy_file`); one it cannot parse is fatal at startup. `vnproxctl policy test --policy=f.yaml --changeset=<id>` evaluates a candidate rule set against a real changeset without staging anything, and `vnproxctl policy lint` validates a document with no daemon at all. The default policy set is **empty**, and an empty set changes nothing. See docs/api.md's "Policy set (T-2601)" section for the route/error contract.

Findings carry optional machine-applicable `fix` patches (API doc). Errors block apply; warnings require an explicit "apply with warnings" checkbox.

## 3. Diff & plan review

The review screen shows four tabs: **Summary** (op cards), **File diff** (unified diffs of every file the change touches — `/etc/network/interfaces` per node, and, since T-2003, SDN config, cluster-scoped), **Plan** (the exact ordered steps: which PVE API calls, which nodes reload, in what order), and **Discussion** (T-2003, below). Nothing applies until the user has seen this screen. The config (File diff) tab is deliberately literal — operators reason in `/etc/network/interfaces` terms even where the Summary tab's semantic op cards are more precise — and it renders exactly what apply would write: the same parse → mutate → unified-diff pipeline apply's own staging step uses for node files, and the same net-effect projection over live inventory for SDN config.

### 3.0 Post-apply topology preview (T-2605)

The blast radius (T-2404) answers *what breaks* and the diff answers *what fields change*. Neither
answers the question an operator forms before clicking apply: **what will the map look like**.
`GET /changesets/{id}/preview` answers it — the live inventory graph with the changeset's ops folded
in **in memory**, rendered through the same projection `GET /topology` uses, plus a per-entity
`added`/`removed`/`modified` marking. The map renders it as a distinct mode (`/topology?previewChangeset=<id>`),
with removed entities drawn back onto the scene and struck rather than quietly absent — a deletion
shown as an absence is a deletion nobody notices.

Three properties are the whole point:

- **It is best-effort and says so.** `bestEffort` is always true, and every op whose effect cannot be
  expressed as a change to the inventory graph — a raw `/etc/network/interfaces` edit, or a
  firewall/QoS/NAT/WireGuard/switch op that has no graph entity at all — is listed **by name with a
  reason** in `unprojectable`. Nothing is silently dropped, and the reason describes the op rather
  than vnprox's completeness.
- **A changeset that cannot apply gets no preview.** Blocking validation findings mean there is no
  post-apply state; the route refuses with `422 validation_failed` rather than rendering a map no
  sequence of events can produce.
- **It is read-only.** The projection touches neither the store nor PVE, and never writes through to
  the live graph.

### 3.1 Review, comments, and approval (T-2003)

The changeset is this product's unit of work, and review is where a *team*, not just a single admin, actually lives — generalizing T-1703's tenant self-service request-changeset approval queue (docs/api.md's "Tenants & self-service" section) into a mechanism every changeset can use, not only tenant requests.

- **Comments.** Any changeset (not only a tenant request) can carry review comments, either attached to one op or to the changeset as a whole, each attributed and timestamped. Comments survive validate/diff (neither ever touches the ops a comment is keyed to). Deleting an op deletes its comment explicitly — audited, never silently orphaned — while an edit that leaves an op untouched keeps its comments attached.
- **Approval.** A deployment can require an explicit approval before a changeset applies ([changesets] section, docs/deployment.md), with self-approval permitted or forbidden and an optional named-approvers list, all admin-configured. **This is an authorization surface, not a UI affordance**: whether apply is permitted is decided server-side from the stored approval decision on every apply attempt, never inferred from a client request field and never merely by the frontend declining to render an Apply button — an unapproved apply attempt is refused with a documented error regardless of caller (UI, direct API call, or `vnproxctl`). Editing a changeset's ops clears any prior approval decision, the same way it demotes a stale `validated` status back to `draft` — a decision made against one set of ops must never silently authorize a different one.
- **Shareable review link.** Every changeset has a stable URL (`/changesets/{id}/review` in the SPA) that opens it directly in the review screen — the exit demo's "a colleague reviews and comments on the resulting changeset from a phone." Opening it still requires an authenticated session with the ordinary read capability; the link carries no credential of its own.

## 4. Apply, confirm, rollback

- Apply executes the plan; each step's outcome streams to the UI (`changeset.status` WS events).
- Default confirm window **120s** (configurable 30–600). The countdown renders as a full-width banner. Confirmation requires an authenticated API round-trip — if connectivity broke, rollback happens server-side at the deadline.
- Rollback restores pre-snapshot files on affected nodes and re-runs ifreload + SDN apply as needed; result is audited and the changeset marked `rolled_back` with the failure step preserved for diagnosis.
- Manual rollback of a `committed` changeset is offered for 7 days (creates a new restoring changeset via the normal flow).
- **Management-path changes (T-703):** a changeset whose ops intersect a node's resolved management path (the server-computed `touchesMgmtPath` flag — docs/api.md's changesets section) gets an *additive* apply-time ceremony on top of the normal flow, never an interlock override: the review screen requires a typed node-name acknowledgement (audited as `changeset.mgmt_ack`) before Apply enables, and the commit-confirm window defaults to and cannot be set below **180s** (rejected server-side with `confirm_window_too_short`). The T-203 safety interlock (`safety.protected_interface`) remains the enforcement backstop behind the guided management-redundancy wizard, which is interlock-clean by construction (it preserves the management IP value and its physical connectivity in every changeset's net effect). Re-addressing the management IP stays out of scope (docs/security.md's "no override in UI" is unamended).
- If a node becomes unreachable mid-apply: remaining steps abort, completed nodes roll back, the unreachable node's daemon rolls back locally at its deadline (each node arms its own local timer at step start — no cross-node dependency for safety).
- **Canary / staged multi-node apply (T-2602).** An apply reaches every affected node in one pass, so a wrong change is wrong everywhere at once and commit-confirm catches it only after the damage is cluster-wide. An apply can instead be *staged*: `applyStrategy: {mode: all|canary, canaryNodes, holdFor, gate: manual|auto}` on `POST /changesets/{id}/apply`. **The default is `all`, which is the behaviour above, unchanged** — staging happens only when someone asks for it. A canary apply runs the named nodes' steps, then **pauses in a resumable state**: the changeset is neither applied nor rolled back, and the store records exactly which nodes are in which state (`changeset_apply_stages`, docs/data-model.md §2) so a daemon restarted mid-hold resumes or rolls back *per the recorded strategy* rather than leaving a half-applied cluster with nothing describing it. `gate: manual` waits for `POST /changesets/{id}/continue`; `gate: auto` promotes at the hold deadline only when the canary nodes are healthy and no new `error` finding attributable to them appeared during the hold — an unassessable canary never promotes. **Aborting restores exactly the stages that ran**: a node that was never touched is never contacted, let alone restored. The commit-confirm window covers the **whole** staged sequence rather than each stage, so a stalled canary cannot hold the cluster open past it — every hold deadline is clamped to the window's, and a hold still pending when it elapses rolls back everything applied so far. See docs/api.md's changesets section for the full route/field/refusal contract.
- **Finding-triggered auto-rollback inside the window (T-2603).** Commit-confirm's rollback fires when nobody confirms — which handles a lost connection well, and "the change was wrong and the operator is still watching" not at all, even though the findings engine detects the breakage within a cycle. An apply can opt in with `autoRollbackOnError: true` (or cluster-wide with `[changesets] auto_rollback_on_error`, off by default): a **new** `error` finding attributable to an entity the changeset touched — its T-2404 `Impact` set of nodes, carriers and guests — rolls it back at once rather than at the deadline. Three things never trigger it, by construction: a finding that was already firing before the apply (the findings-stream ID set is recorded as a baseline at apply time, so this is a property rather than a race), a finding outside the changeset's `Impact` however severe, and anything below `error`. The rollback names the finding that caused it, in the audit trail (`changeset.auto_rollback`) and on the changeset (`applyLog.autoRollback`) — never just "something went wrong". During a canary hold it aborts the staged sequence instead, restoring only the stages that ran. Arming it is audited too, so an operator can always tell why a changeset was being watched.
- **Enforced two-person rule on protected op classes (T-2604).** The approval above answers "has anyone approved this?"; it cannot answer "have two *different people* approved this?" A deployment can declare classes of change that require **N distinct principals** to have approved before apply — an op-type glob (`fw.*`, `sdn.*`), the reserved `mgmtPath` (anything touching a node's resolved management path), or `tag:<tag>` naming a T-2601 policy rule's tag, so an organisation's own "this needs three people" rule is written as policy data rather than as new vocabulary. **Declaring no classes is the default and changes nothing.** Enforcement is server-side at apply — refused `422 two_person_required`, naming the class and the shortfall, before the plan is built and before any mutation — and never in the UI: a request crafted directly against the API meets exactly the same gate. Approvers are counted as *people*: one person approving through two API tokens is one approver, and a later rejection withdraws their sign-off. **Emergency break-glass** (`POST /changesets/{id}/break-glass`) exists for the 3am case with nobody else awake: it requires a written reason, is audited under its own action `change.breakglass`, overrides only the approver count (every other gate still applies), does not survive an edit of the ops, and raises an `error` finding (`change_break_glass`) that **cannot be acknowledged for 24 hours** — so the override is reviewed by someone who was not in the room. See docs/api.md's changesets section for the full route/field/refusal contract.
- **What the automatic rollback covers, and when it doesn't (T-1805).** Interface-file, WireGuard, QoS and switch-port changes are undone by the daemon itself and always revert unattended. Firewall (`fw.*`) and SDN (`sdn.*`) changes are written to PVE under *your* login, so undoing them without a session needs a copy of it: at apply time vnprox seals your PVE ticket into the changeset for the confirm window, uses it only to undo that one changeset, and deletes it the moment you confirm or it rolls back (docs/security.md's "Apply-time revert ticket"). The review screen states this before you apply, and the apply response reports exactly how much of the window is covered (`unattendedRevert`, docs/api.md) — a PVE session lasts about 2 hours, so a long confirm window opened late in a session can be only partly covered, and you are told which. Before this, a firewall-only changeset that timed out was never reverted at all.
- **Scheduled apply / maintenance windows (T-1103):** a draft/validated changeset can be scheduled (`POST /changesets/{id}/schedule`) to apply automatically inside a future window instead of immediately — stage now, apply later, with this section's apply/confirm/rollback machinery running completely unchanged at fire time. A supervised scheduler goroutine re-validates and recomputes `touchesMgmtPath` fresh at `windowStart` (never trusting the value from schedule time), then applies with a commit-confirm deadline of `min(windowStart + confirmTimeoutSec, windowEnd)`. `touchesMgmtPath` changesets are excluded from scheduling entirely, unconditionally, server-side — see docs/security.md's Safety interlocks section for why this is a stricter, separate gate from `allow_dangerous_ops` rather than an application of it. Ack (confirming a fired, awaiting-confirm scheduled changeset) works two ways: the normal UI session-cookie `POST .../confirm`, or a single-use, changeset-scoped signed callback token delivered once at schedule time (`POST .../schedule/ack`) — the webhook path, for automation that has no browser session. See docs/api.md's "Scheduled changesets & maintenance windows" section for the full route/error/token contract.

## 5. Editors: bridges, bonds, VLANs, interfaces

Form-based editors open from the map or list views; every field has inline help written for non-networking-experts (e.g. bond modes explained with "use this when..."). Specific requirements:

- **Bridge**: kind (Linux/OVS), ports multi-select with conflict hints, VLAN-aware toggle with VID range editor, addresses, MTU, STP, comment. Deleting a bridge with attached guests requires choosing a reattachment target (generates the guest ops in the same changeset).
- **Bond**: mode selector with live guidance, slave picker showing current link state/speed of candidates, LACP options (rate, hash policy), MII monitor interval. Post-apply, the inspector shows live bond state (mode, MII status, active slave, per-slave link/failure-count) parsed from `/proc/net/bonding/*` (`internal/host/bonding.go`). **T-804 (closes the T-607-flagged gap):** LACP actor/partner system ID/priority/key and per-slave 802.3ad port-state (synchronized/collecting/distributing) are now parsed from the same `/proc/net/bonding/<name>` file's "details actor/partner lacp pdu" block, opportunistically refined by netlink AD-info attributes where the running kernel exposes them (best-effort — see `docs/data-model.md`'s `BondSlave` row and `planning/reports/needs-hardware-validation.md` for the cross-kernel-version caveat), and flow through inventory to a dedicated live LACP section in the bond inspector (`web/src/topology/BondLacpSection.tsx`), visually distinct for a mismatched vs. negotiated-correctly bond. A new `lacp_partner_mismatch` health check (`internal/findings/health_lacpmismatch.go`) raises a hysteresis-debounced finding when slaves disagree on the partner system/key or aren't fully negotiated.
- **VLAN**: parent picker, VID, addresses, MTU (warn when exceeding parent).
- **Interface**: MTU, addresses/gateway, autostart, comment. Renaming NICs is out of scope v1 (link files are a hardware-specific minefield) — document the manual procedure instead.

## 6. Guest NIC operations

List + map views support: reattach to another bridge/VNet, change VLAN tag, rate limit, toggle firewall flag, disconnect/connect (`link_down`). **Bulk mode**: select N guests (filter by current bridge/VLAN/node) → one changeset moving all, with per-guest hotplug attempted and per-guest results reported. Ops use the user's ticket via PVE API (`PUT /nodes/{n}/qemu/{vmid}/config` etc.).

## 7. Raw editor escape hatch

A Monaco-based editor for `/etc/network/interfaces` per node with interfaces(5) syntax linting and the same validators run against the parsed result. Saving creates a changeset whose single op is `iface.raw.replace` — still diffed, still commit-confirmed. This keeps power users inside the safety envelope instead of SSHing around it.

## 8. Audit UI

Filterable table (user, date range, target, result) over the merged cluster audit log; each row expands to op summaries and links to the changeset and its snapshots.
