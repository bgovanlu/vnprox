# Feature spec — Monitoring & health

Scope discipline: vnprox shows *network-shaped, short-horizon* operational data on the map where it's uniquely useful. It is not a metrics platform.

## 1. Live rates

- Collector samples `/sys/class/net/*/statistics` (via peer API for remote nodes) every 5s; rates computed daemon-side; pushed over WS (`metrics.sample`) for subscribed refs.
- **Map integration**: optional "traffic" paint mode — edge thickness/heat by current utilization %, per-entity sparklines in the inspector, live counters (rx/tx bps, pps, errors, drops) on selection.
- Bond member balance shown per-slave (spot the LACP hash imbalance instantly).

**Added by T-1303:** a second, independent map overlay — a "latency" heatmap paint mode, distinct from "traffic" above (edge color/legend never shares a value with traffic mode's own scale, so the two read as clearly separate layers when either is active) — color-scales every node-to-node link this node's own `internal/latmesh` scheduler probes by its current rolling RTT/loss (`GET /latmesh/heatmap`, docs/api.md's Latency mesh section). Continuous, low-rate ICMP probes (`[latmesh] probe_interval_sec`, default 10 — "a mesh, not a flood") across every shared corosync/guest fabric this node can identify; see that section for the exact fabric-discovery scope.

**Extended by T-1404:** on the guest fabric, a bridge shared by two nodes that carries both an IPv4 and an IPv6 address gets probed on **each family independently** — two distinct links, two distinct rolling RTT/loss series, painted as two distinct heatmap edges — rather than one merged reading that could hide a v6-only degradation behind a healthy v4 number. A single-family bridge is unaffected. See docs/api.md's Latency mesh section for the exact link-id scheme.

## 2. History

24h ring in SQLite (`metric_samples`, 30s resolution after downsampling). Inspector charts: rate over time, errors/drops over time. Nothing longer — export to real observability instead.

**Added by T-1303:** a second, independently-bounded ring, `latency_samples` (docs/data-model.md §2) — one row per node-to-node probe tick, pruned to `[latmesh] retention_minutes` (default 60) **and** a hard row cap (`[latmesh] max_rows`, default 500,000), whichever is smaller prunes first, the identical bound-shape `flow_samples` already established. `GET /latmesh/history?linkId=&fromTs=&toTs=` (docs/api.md's Latency mesh section) backs the inspector's per-link latency/loss sparkline, same pattern as `GET /metrics/history`.

## 3. Top talkers (P1)

Per-bridge approximation from guest NIC counters (PVE exposes per-guest netin/netout): rank guests by throughput on a selected bridge, 5m/1h windows. No packet capture, no flow sampling in v1.

**Updated by T-1002 (Phase 10):** "no flow sampling in v1" no longer holds — `internal/flow` adds opt-in (off by default, per node) sFlow v5/NetFlow v5/v9/IPFIX ingestion into a bounded ring (`GET /flows`, docs/api.md's Flows section; docs/data-model.md §2's `flow_samples`), which T-1003 (flow explorer + map flow painting) and T-1004 (host-local conntrack/eBPF sampling, closing the "no packet capture" half too) build on. The v1 scope note above is left as-is for its historical context; the roadmap-next carried-forward invariant it was protecting — vnprox never becomes a long-term flow/metric warehouse — is unchanged and is exactly what `internal/flow`'s bounded-ring design (window + hard row cap, whichever prunes first) still honors.

## 4. Prometheus exporter

**Shipped (T-1001)**, not just a "P2" aspiration as previously labeled here: `GET /metrics` (Prometheus/OpenMetrics-compatible text exposition, docs/api.md's Metrics-exporter subsection) exports the sampler's per-ref counters, `GET /findings`'s open count by severity, `GET /drift`'s open count, and changeset counts by status. **Correction:** this section previously said the route would be "gated to `Sys.Audit`" — a Prometheus scraper cannot carry a PVE-derived session at all, so it is instead gated on its own bearer scrape token (`crypto/subtle.ConstantTimeCompare`, generated alongside the session key) plus an optional source-CIDR allowlist; see docs/security.md's Authentication section for the full story. Node-local only (no peer fan-out) — a cluster-wide view is a Prometheus federation/multi-target-scrape concern, not something vnproxd computes itself.

## 5. Health checks

Continuous checks feeding one findings stream (shared with drift, LLDP mismatch, IPAM conflicts): interface error/drop rate thresholds, bond slave down, LACP partner mismatch (T-804), MTU path mismatch, STP topology change bursts, bridge with no carrier uplink, dnsmasq/frr service down on a node, `interfaces.new` pending >1h, (T-702) a node's management path carrying no redundancy (`mgmt_single_path`), and T-803's "health-check pack 2": a VXLAN/EVPN zone's configured MTU against the *observed* underlay path MTU (`vxlan_underlay_mtu`), an orphaned SDN VNet (`orphan_vnet`), an EVPN zone's anycast gateway realized inconsistently across member nodes (`evpn_gw_inconsistency`), a degraded corosync ring (`corosync_link_degraded`), and an unused trunked VLAN (`trunk_unused_vlans`, informational). Findings: severity, plain-English explanation, affected refs (map-linked), and remediation (a fixing changeset where computable, docs link otherwise). Notification hooks (webhook/email via PVE notification system) — shipped (`internal/findings/notify.go`, `pvenotify.go`), not just a "P1" aspiration as previously labeled here.

**`lacp_partner_mismatch` (T-804).** Source `health`, severity `warning`, one finding per 802.3ad bond that netlink reports MII-up whose slaves either disagree on the LACP partner's system ID/key (split-brain aggregation — each slave is really talking to a different partner) or aren't fully negotiated (missing synchronized/collecting/distributing on the actor's decoded port-state bits), among the slaves that reported LACP PDU detail at all (`internal/host/bonding.go`'s `/proc/net/bonding` actor/partner parser). A bond not running 802.3ad, or whose kernel/driver never emits that detail, is silently skipped — this check has nothing to say about a bond it never observed negotiating. Standard hysteresis debounce (2 consecutive cycles each way, `internal/findings/health_lacpmismatch.go`) — unlike `mgmt_single_path`, this is live negotiation state, not a structural fact. Detection-only (`docsLink` always set, never `fixable` — no changeset op can fix a switch-side LACP misconfiguration).

**`mgmt_single_path` (T-702).** Source `health`, severity `warning`, one finding per node whose resolved management path (`internal/topology.ResolveMgmtPaths`, the same shared resolver `GET /protected-interfaces/status` and `GET /topology`'s mgmt badges use — see docs/features/topology.md §3) has fewer than two confirmed link-up physical NICs behind a ref carrying the `mgmt` role. Unlike every other check in this section, it is **hysteresis-exempt** (no debounce window): whether a bridge/bond has one NIC or two behind it is a structural property of the current network configuration, not a noisy live counter to debounce — it fires the instant the path stops being redundant and clears the instant a second NIC comes up, with a stable id across polls (`health:mgmt_single_path|<carrier ref>`). Detection-only (`docsLink` always set, never `fixable` in this task) — this is also T-703's entry point: its guided "bond the management uplink" / "add a slave to an existing mgmt-path bond" wizards launch from this exact finding.

**Health-check pack 2 (T-803).** Five checks, `internal/findings/health_*.go`, all source `health`, all detection-only (`docsLink` always set, never `fixable` — none of the five has a computable fix):

- **`vxlan_underlay_mtu`** — severity `warning`, standard hysteresis (2 cycles each way, `internal/findings/health_vxlanmtu.go`). A vxlan/evpn `SdnZone` with an explicit MTU whose value plus VXLAN's encapsulation overhead (`change.VxlanOverhead`, the exact constant §2's guided VXLAN wizard and `checkVxlanMTU`'s changeset-validate-time check already use) leaves no headroom over the underlay path MTU — the minimum effective MTU among the zone's member node's physical NICs, from live inventory rather than the assumed 1500-byte default `checkVxlanMTU` uses at validate time. Promotes the one genuinely uncovered MTU gap this task's card identified: a physical underlay MTU that degrades *after* apply (no changeset involved) previously went undetected. Plain L2 NIC→bond→bridge MTU mismatches remain `drift.CheckMTUConsistency`'s job (both within-node and, since T-801, cross-node pre-apply) — not reimplemented here. **Upgraded by T-1306** (§7 below): when `internal/mtuprobe.Service` has a fresh *measured* (DF-probe-verified, end-to-end) MTU reading for a zone member node's outbound path, the check compares against that tighter, live-measured figure instead of the local-NIC-read `observed` figure — the `observed` reading remains the fallback for any node/path the prober hasn't reached yet, never a regression. The finding's `detail` text names which source (`measured` or `observed`) it evaluated against.
- **`orphan_vnet`** — severity `warning`, **hysteresis-exempt** (structural: whether a vnet's zone exists is a config fact, not a noisy counter). An `SdnVnet` whose `Zone` no longer names any known `SdnZone`.
- **`evpn_gw_inconsistency`** — severity `warning`, **hysteresis-exempt**. An EVPN zone's anycast subnet gateway (§2: "the gateway becomes the anycast address realized on every zone member node") present on some member nodes' realized VNet bridge and absent (or missing entirely) on others — a real split, not "not realized anywhere yet" (that's `sdn.evpn_gateway_missing`'s job at validate time). Reuses T-801's `internal/xnode.BridgesByName` cross-node fold for the same-named-bridge grouping rather than writing a second one. **Needs hardware validation**: exact per-node anycast-gateway realization in `/etc/network/interfaces` is unverified (`planning/reports/needs-hardware-validation.md`).
- **`corosync_link_degraded`** — severity `warning`, standard hysteresis (2 cycles each way). A corosync ring reporting faulty/no-link status via `corosync-cfgtool -s` (`internal/host.Reader.CorosyncStatus`, new in this task — distinct from corosync.conf's static ring *addresses*, which every safety-interlock check already reads). Fed through an explicit `CorosyncProvider` seam (mirroring `service_down`'s `OnServices`-style ingestion) rather than the inventory graph, since a ring's live status is not a map entity. **Scope note**: the production wiring (`cmd/vnproxd`) reports only this daemon's own local node's ring status today — cluster-wide peer fan-out needs a new peer API route this task's card did not include; see this task's completion report. **Needs hardware validation**: exact `corosync-cfgtool` output format/version (`planning/reports/needs-hardware-validation.md`).
- **`trunk_unused_vlans`** (informational, severity `info`) — **hysteresis-exempt**. A VLAN-aware bridge's trunked VID set (`Bridge.Vids`) contains a VID no guest NIC attached to it currently uses (`GuestNic.EffectiveVid`). Never auto-narrows the trunk — a "you might be able to tidy this up" signal, not a correctness problem.

**`path_latency_degraded` / `path_loss` (T-1303).** Source `health`, severity `warning`, `internal/findings/health_latmesh.go`, fed by `internal/latmesh.Service` (§1/§2 above) via the `LatMeshProvider` seam (mirroring `corosync_link_degraded`'s own explicit-provider shape — a probed link has no `inventory.Ref`, so it can't be fed through the graph like every other health check). One finding per directed node-to-node link whose *rolling* (window-averaged, not a single noisy tick) RTT/loss crosses a threshold (`internal/findings.HealthThresholds.LatRttWarnMs`/`LatLossWarnPct`, defaults 80ms/2%) and holds — standard hysteresis (3 cycles rise / 2 cycles fall, the same window `error_drop_rate` uses for a comparable live-runtime-derived signal, one layer on top of the rolling window's own smoothing). Detection-only (`docsLink` always set, never `fixable` — no changeset op can fix a physically degraded path); `id` is `"health:<check>|<linkId>"`, keyed by the link id (not just the node pair, since two different fabrics can share the same two endpoints). Routes through the existing T-1005 alert-rule webhook delivery unmodified, same as every other producer's findings.

## 6. Guest network interior inspector (T-1304)

An opt-in, read-only inspector tab on a guest's own map entity (InspectorPanel's "Interior" tab, guest-kind entities only): the guest's own inside view of its network — interfaces, addresses, routing table, DNS config, listening sockets, default-gateway reachability — plus an IPAM cross-check annotation. Off by default (docs/api.md's Guest interior section: `GET/PUT /guests/{ref}/interior-toggle`); turning it on reads inside the guest itself every time the tab is open, via the QEMU guest agent for a qemu guest (`source: "qemu-ga"`, reusing §"Live path probe"'s existing `AgentExec` seam) or directly from the host side for an lxc container, which has no guest agent (`source: "lxc-host"`, `internal/host.Reader.ContainerInterior`/`ContainerPing` — locally, or peer-routed per docs/architecture.md §1/§5's cluster-awareness invariant when the container's node is not this daemon's own).

This is deliberately not a trust boundary vnprox treats as authoritative: a guest's self-report is exactly that, a claim, so every claimed address is cross-checked against `internal/ipam`'s resolved allocation set (docs/features/ipam.md §1's confidence-labeling contract) rather than taken at face value — an address the guest claims but IPAM has no record of surfaces as an unmatched entry, never silently accepted. Strictly read-only: there is no write path from this inspector into the guest or into IPAM.

**Needs hardware validation**: the exact in-guest/in-container command set and the lxc pid-resolution mechanism — see docs/api.md's Guest interior section and `planning/reports/needs-hardware-validation.md`.

## 7. Path MTU prober (T-1306)

`internal/mtuprobe.Service` performs active per-path MTU discovery: a binary-search sweep of DF-set (Don't Fragment) ICMP probes, converging on the largest packet size a path actually carries end-to-end — built directly on T-1303's latency-mesh infrastructure (§1/§2), not a second scheduler or a second path-discovery mechanism. Its `Discoverer` is the exact same `internal/latmesh.GraphDiscoverer` instance the latency mesh itself uses, so it probes exactly the corosync/guest-fabric paths the mesh already knows about (see `internal/latmesh`'s own package doc comment for why those two fabrics — corosync ring addresses and bridges shared by two or more nodes, which is the VXLAN/EVPN underlay path itself when that shared bridge is an SDN vxlan/evpn zone's own bridge); its `RunLoop` calls `internal/latmesh.RunTicker`, the identical shared scheduler primitive `latmesh.Service.RunLoop`/`RunPruneLoop` use. Runs on its own, much coarser cadence (`[mtuprobe] probe_interval_sec`, default 300s — MTU rarely changes, unlike latency/loss) than latency probing's default 10s.

Unlike the latency mesh, this is a **current-state seam, not a SQLite-backed ring**: `Service.Results`/`Result` hold only each link's most recently verified MTU in memory (no `mtu_probes` table, no history/rolling stats — there is no history use case a rarely-changing value needs). A link this node has never successfully probed simply has no entry; a probe attempt that fails to even run (transport error) leaves the prior good reading in place rather than clearing it to a stale zero.

| Method | Path | Purpose |
|---|---|---|
| GET | `/mtuprobe/results` | every currently-known verified per-link MTU reading this node has probed |

**`GET /mtuprobe/results`** response: `{items: [MTUProbeResult]}`. `MTUProbeResult`: `{linkId, fabric, fromNode, toNode, mtu, at, probeCount}` — `linkId`/`fabric`/`fromNode`/`toNode` are the exact same `internal/latmesh.Pair.LinkID`-keyed identity `GET /latmesh/heatmap` uses for the same path, so a UI can correlate a link's latency reading and its verified MTU reading by `linkId`. `mtu` is the binary search's converged result; `probeCount` is how many DF-probes that convergence took (bounded — see `internal/mtuprobe.BinarySearchMTU`'s doc comment). Node-local only, no peer fan-out, the same documented scope `GET /latmesh/heatmap` carries.

**Map-edge annotation**: the web client's "verified MTU" overlay (`web/src/topology/mtuOverlay.ts`'s `computeMTUOverlayEdges`) renders each probed link's measured MTU as its own badge, distinct from wherever that link's *configured* MTU is already shown (the zone/bridge editor's own MTU field) — a link with no probe result yet renders no badge at all, never a stale or zero placeholder. This is a second, independent overlay from the "Latency" heatmap layer (T-1303), the same "two independent overlays, one toggle each" pattern that layer established.

**Findings**: see §5 above — `vxlan_underlay_mtu` consumes `Service.MeasuredUnderlayMTU` (the minimum verified MTU across a node's successfully-probed outbound links) as an optional, tighter input, falling back to the pre-existing observed-NIC-MTU evaluation wherever no fresh probe reading exists.

**WireGuard hook (declared, not wired)**: `Service.ProbeWireGuardLink(ctx, tunnelRef)` is a capability-gated seam that always returns `mtuprobe.ErrWireGuardNotAvailable` today (`mtuprobe.WireGuardCapability` defaults false — there is no WireGuard tunnel entity kind in `internal/inventory` yet). Phase 14's T-1401 is the task expected to introduce that capability flag and wire a real implementation into this exact method; see `planning/reports/T-1306.md`.
