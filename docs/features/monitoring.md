# Feature spec — Monitoring & health

Scope discipline: vnprox shows *network-shaped, short-horizon* operational data on the map where it's uniquely useful. It is not a metrics platform.

## 1. Live rates

- Collector samples `/sys/class/net/*/statistics` (via peer API for remote nodes) every 5s; rates computed daemon-side; pushed over WS (`metrics.sample`) for subscribed refs.
- **Map integration**: optional "traffic" paint mode — edge thickness/heat by current utilization %, per-entity sparklines in the inspector, live counters (rx/tx bps, pps, errors, drops) on selection.
- Bond member balance shown per-slave (spot the LACP hash imbalance instantly).

**Added by T-4110 (LACP hash visualizer, hardware-flagged per CLAUDE.md's "needs real NICs / physical switch" category):** the bond inspector's "LACP" tab (alongside T-804's live actor/partner state) additionally predicts which slave the kernel's `xmit_hash_policy` (`layer2`\|`layer2+3`\|`layer3+4`\|`encap2+3`\|`encap3+4`) would route each recently-observed flow to, and shows it beside the actual per-slave rate above where a live sample exists — predicted-vs-actual divergence is the useful signal, since it can reveal a hash policy that isn't distributing traffic the way it's assumed to. `internal/lacphash` implements the five policies as pure, tested functions sourced from `Documentation/networking/bonding.rst`'s documented formulas (no kernel source tree or hardware available to write it against — see that package's own doc comment); `layer2`/`layer2+3`/`encap2+3` can never be predicted from vnprox's own flow records specifically, since none of sFlow/NetFlow/IPFIX/conntrack carry Ethernet MAC addresses — reported as an explicit unclassified reason, not silently guessed. See `planning/reports/needs-hardware-validation.md`'s T-4110 entry for exactly what remains unverified without a real switch.

**Added by T-1303:** a second, independent map overlay — a "latency" heatmap paint mode, distinct from "traffic" above (edge color/legend never shares a value with traffic mode's own scale, so the two read as clearly separate layers when either is active) — color-scales every node-to-node link this node's own `internal/latmesh` scheduler probes by its current rolling RTT/loss (`GET /latmesh/heatmap`, docs/api.md's Latency mesh section). Continuous, low-rate ICMP probes (`[latmesh] probe_interval_sec`, default 10 — "a mesh, not a flood") across every shared corosync/guest fabric this node can identify; see that section for the exact fabric-discovery scope.

**Extended by T-1404:** on the guest fabric, a bridge shared by two nodes that carries both an IPv4 and an IPv6 address gets probed on **each family independently** — two distinct links, two distinct rolling RTT/loss series, painted as two distinct heatmap edges — rather than one merged reading that could hide a v6-only degradation behind a healthy v4 number. A single-family bridge is unaffected. See docs/api.md's Latency mesh section for the exact link-id scheme.

## 2. History

24h ring in SQLite (`metric_samples`, 30s resolution after downsampling). Inspector charts: rate over time, errors/drops over time. Nothing longer — export to real observability instead.

**Added by T-1303:** a second, independently-bounded ring, `latency_samples` (docs/data-model.md §2) — one row per node-to-node probe tick, pruned to `[latmesh] retention_minutes` (default 60) **and** a hard row cap (`[latmesh] max_rows`, default 500,000), whichever is smaller prunes first, the identical bound-shape `flow_samples` already established. `GET /latmesh/history?linkId=&fromTs=&toTs=` (docs/api.md's Latency mesh section) backs the inspector's per-link latency/loss sparkline, same pattern as `GET /metrics/history`.

## 3. Top talkers (P1)

Per-bridge approximation from guest NIC counters (PVE exposes per-guest netin/netout): rank guests by throughput on a selected bridge, 5m/1h windows. No packet capture, no flow sampling in v1.

**Updated by T-1002 (Phase 10):** "no flow sampling in v1" no longer holds — `internal/flow` adds opt-in (off by default, per node) sFlow v5/NetFlow v5/v9/IPFIX ingestion into a bounded ring (`GET /flows`, docs/api.md's Flows section; docs/data-model.md §2's `flow_samples`), which T-1003 (flow explorer + map flow painting) and T-1004 (host-local conntrack/eBPF sampling, closing the "no packet capture" half too) build on. The v1 scope note above is left as-is for its historical context; the roadmap-next carried-forward invariant it was protecting — vnprox never becomes a long-term flow/metric warehouse — is unchanged and is exactly what `internal/flow`'s bounded-ring design (window + hard row cap, whichever prunes first) still honors.

**Added by T-1504: service-network attribution.** `internal/flow.Classifier` tags each flow record with a `serviceClass` (`"migration"`\|`"backup"`\|`"ceph-public"`\|`"ceph-cluster"`\|`"corosync"`\|`"unclassified"`) using only the record's own metadata (IP/CIDR containment against a registered network declaration, an exact known address, VLAN) — **never payload inspection**, this is not an IDS; `internal/flow/classify.go` has no import of any capture/payload package. Additive to `GET /flows`' `flow.Record` (docs/api.md's Flows section has the full field/registration-source writeup) and, transitively, to the Flow Explorer and history playback's scrubber, since both render straight off `GET /flows`. `RegisterNetworkSource(kind, source)` is the classifier's explicit extension point: this task wires corosync's configured ring addresses (`cmd/vnproxd`, real production data); T-1503 (Ceph awareness) registers Ceph's public/cluster CIDRs the same way; a migration-network CIDR and a PBS backup-path address set (T-1206, Phase 12, not yet landed) are each a working, independently-tested `NetworkSource` constructor with no live production data source wired yet — see `internal/flow/classify.go`'s doc comment. The Home dashboard gains a matching tile (`ServiceClassTile.tsx`): per-`serviceClass` bytes/sec breakdown over the recent `GET /flows` window, client-side computation, no new backend aggregation (mirrors the Top-talkers tile's own convention, §3 above). See §5 below for the companion `service_traffic_on_wrong_network` finding.

**Added by T-1502: Kubernetes service-flow attribution.** The Flow Explorer gains a `k8sService` column alongside `serviceClass`, attributing a row's `srcIp`/`dstIp` against every currently-registered T-1501 k8s cluster's live `GET /k8s/{clusterId}/overlay` — unlike `serviceClass` above, this is **not** a wire field on `flow.Record`: it's computed entirely client-side (`web/src/topology/layers/k8sFlowAttribution.ts`), a TypeScript port of `internal/k8s.K8sResolver`'s own match precedence (exact Service ClusterIP, then exact Pod IP, then pod-CIDR containment — never a wrong guess), the same "kept in sync by hand" convention this codebase's other client-side overlay algorithms (e.g. `wgEdgeStatus.ts`'s mirrored handshake-staleness threshold) already use rather than a second backend round trip. Attribution is display-only: an address matching nothing shows "—", never hides the row. Independent of `docs/features/topology.md` §1's Kubernetes map layer toggle — the column populates whenever at least one cluster is registered, regardless of whether that layer happens to be on.

## 4. Prometheus exporter

**Shipped (T-1001)**, not just a "P2" aspiration as previously labeled here: `GET /metrics` (Prometheus/OpenMetrics-compatible text exposition, docs/api.md's Metrics-exporter subsection) exports the sampler's per-ref counters, `GET /findings`'s open count by severity, `GET /drift`'s open count, and changeset counts by status. **Correction:** this section previously said the route would be "gated to `Sys.Audit`" — a Prometheus scraper cannot carry a PVE-derived session at all, so it is instead gated on its own bearer scrape token (`crypto/subtle.ConstantTimeCompare`, generated alongside the session key) plus an optional source-CIDR allowlist; see docs/security.md's Authentication section for the full story. Node-local only (no peer fan-out) — a cluster-wide view is a Prometheus federation/multi-target-scrape concern, not something vnproxd computes itself.

## 5. Health checks

Continuous checks feeding one findings stream (shared with drift, LLDP mismatch, IPAM conflicts): interface error/drop rate thresholds, bond slave down, LACP partner mismatch (T-804), MTU path mismatch, STP topology change bursts, bridge with no carrier uplink, dnsmasq/frr service down on a node, `interfaces.new` pending >1h, (T-702) a node's management path carrying no redundancy (`mgmt_single_path`), and T-803's "health-check pack 2": a VXLAN/EVPN zone's configured MTU against the *observed* underlay path MTU (`vxlan_underlay_mtu`), an orphaned SDN VNet (`orphan_vnet`), an EVPN zone's anycast gateway realized inconsistently across member nodes (`evpn_gw_inconsistency`), a degraded corosync ring (`corosync_link_degraded`), and an unused trunked VLAN (`trunk_unused_vlans`, informational). Findings: severity, plain-English explanation, affected refs (map-linked), and remediation (a fixing changeset where computable, docs link otherwise). Notification hooks (webhook/email via PVE notification system) — shipped (`internal/findings/notify.go`, `pvenotify.go`), not just a "P1" aspiration as previously labeled here.

**`lacp_partner_mismatch` (T-804).** Source `health`, severity `warning`, one finding per 802.3ad bond that netlink reports MII-up whose slaves either disagree on the LACP partner's system ID/key (split-brain aggregation — each slave is really talking to a different partner) or aren't fully negotiated (missing synchronized/collecting/distributing on the actor's decoded port-state bits), among the slaves that reported LACP PDU detail at all (`internal/host/bonding.go`'s `/proc/net/bonding` actor/partner parser). A bond not running 802.3ad, or whose kernel/driver never emits that detail, is silently skipped — this check has nothing to say about a bond it never observed negotiating. Standard hysteresis debounce (2 consecutive cycles each way, `internal/findings/health_lacpmismatch.go`) — unlike `mgmt_single_path`, this is live negotiation state, not a structural fact. Detection-only (`docsLink` always set, never `fixable` — no changeset op can fix a switch-side LACP misconfiguration).

**`mgmt_single_path` (T-702).** Source `health`, severity `warning`, one finding per node whose resolved management path (`internal/topology.ResolveMgmtPaths`, the same shared resolver `GET /protected-interfaces/status` and `GET /topology`'s mgmt badges use — see docs/features/topology.md §3) has fewer than two confirmed link-up physical NICs behind a ref carrying the `mgmt` role. Unlike every other check in this section, it is **hysteresis-exempt** (no debounce window): whether a bridge/bond has one NIC or two behind it is a structural property of the current network configuration, not a noisy live counter to debounce — it fires the instant the path stops being redundant and clears the instant a second NIC comes up, with a stable id across polls (`health:mgmt_single_path|<carrier ref>`). Detection-only (`docsLink` always set, never `fixable` in this task) — this is also T-703's entry point: its guided "bond the management uplink" / "add a slave to an existing mgmt-path bond" wizards launch from this exact finding.

**`neighbor_binding_flap` (T-3905).** Source `health`, severity `warning`, `internal/findings/health_neighborflap.go`, fed by `internal/neighbor.HistoryRecorder.Flaps` (§ "Neighbor binding history" in docs/api.md) via the `NeighborFlapProvider` seam — computed live each findings cycle over the persisted, restart-durable `neighbor_bindings` ring, not a per-process in-memory tracker. Two independent flap directions, either of which fires this check: one IP resolving to 3+ different MACs within a trailing 2-minute window (`ip_churn`), or one MAC recorded as the owner of 5+ distinct IPs within a trailing 2-minute window (`mac_claim`) — see `internal/neighbor/history.go`'s doc comment for the full threshold rationale. **Hysteresis-exempt**, the same way `mgmt_single_path`/T-803's structural checks are: a flap reading is already a windowed aggregate over several ticks' worth of persisted history, not a single noisy instantaneous reading, so it needs no further debounce. Detection-only (`docsLink` always set, never `fixable`). **Relationship to `arp_spoof_suspected`** (source `rogue`, docs/features/ipam.md's "Rogue-service / L2-anomaly detection" bullet): the two checks deliberately overlap on the `ip_churn` direction — `arp_spoof_suspected` is the live, in-memory, error-severity security alarm (resets on daemon restart); `neighbor_binding_flap` is the persisted, warning-severity, node-attributed operational complement, and the sole detector of the `mac_claim` direction, which `arp_spoof_suspected` does not track at all. Silencing one must never silence the other — see `internal/findings/health_neighborflap.go`'s doc comment.

**Health-check pack 2 (T-803).** Five checks, `internal/findings/health_*.go`, all source `health`, all detection-only (`docsLink` always set, never `fixable` — none of the five has a computable fix):

- **`vxlan_underlay_mtu`** — severity `warning`, standard hysteresis (2 cycles each way, `internal/findings/health_vxlanmtu.go`). A vxlan/evpn `SdnZone` with an explicit MTU whose value plus VXLAN's encapsulation overhead (`change.VxlanOverhead`, the exact constant §2's guided VXLAN wizard and `checkVxlanMTU`'s changeset-validate-time check already use) leaves no headroom over the underlay path MTU — the minimum effective MTU among the zone's member node's physical NICs, from live inventory rather than the assumed 1500-byte default `checkVxlanMTU` uses at validate time. Promotes the one genuinely uncovered MTU gap this task's card identified: a physical underlay MTU that degrades *after* apply (no changeset involved) previously went undetected. Plain L2 NIC→bond→bridge MTU mismatches remain `drift.CheckMTUConsistency`'s job (both within-node and, since T-801, cross-node pre-apply) — not reimplemented here. **Upgraded by T-1306** (§7 below): when `internal/mtuprobe.Service` has a fresh *measured* (DF-probe-verified, end-to-end) MTU reading for a zone member node's outbound path, the check compares against that tighter, live-measured figure instead of the local-NIC-read `observed` figure — the `observed` reading remains the fallback for any node/path the prober hasn't reached yet, never a regression. The finding's `detail` text names which source (`measured` or `observed`) it evaluated against.
- **`orphan_vnet`** — severity `warning`, **hysteresis-exempt** (structural: whether a vnet's zone exists is a config fact, not a noisy counter). An `SdnVnet` whose `Zone` no longer names any known `SdnZone`.
- **`evpn_gw_inconsistency`** — severity `warning`, **hysteresis-exempt**. An EVPN zone's anycast subnet gateway (§2: "the gateway becomes the anycast address realized on every zone member node") present on some member nodes' realized VNet bridge and absent (or missing entirely) on others — a real split, not "not realized anywhere yet" (that's `sdn.evpn_gateway_missing`'s job at validate time). Reuses T-801's `internal/xnode.BridgesByName` cross-node fold for the same-named-bridge grouping rather than writing a second one. **Needs hardware validation**: exact per-node anycast-gateway realization in `/etc/network/interfaces` is unverified (`planning/reports/needs-hardware-validation.md`).
- **`corosync_link_degraded`** — severity `warning`, standard hysteresis (2 cycles each way). A corosync ring reporting faulty/no-link status via `corosync-cfgtool -s` (`internal/host.Reader.CorosyncStatus`, new in this task — distinct from corosync.conf's static ring *addresses*, which every safety-interlock check already reads). Fed through an explicit `CorosyncProvider` seam (mirroring `service_down`'s `OnServices`-style ingestion) rather than the inventory graph, since a ring's live status is not a map entity. **Scope note**: the production wiring (`cmd/vnproxd`) reports only this daemon's own local node's ring status today — cluster-wide peer fan-out needs a new peer API route this task's card did not include; see this task's completion report. **Needs hardware validation**: exact `corosync-cfgtool` output format/version (`planning/reports/needs-hardware-validation.md`).
- **`trunk_unused_vlans`** (informational, severity `info`) — **hysteresis-exempt**. A VLAN-aware bridge's trunked VID set (`Bridge.Vids`) contains a VID no guest NIC attached to it currently uses (`GuestNic.EffectiveVid`). Never auto-narrows the trunk — a "you might be able to tidy this up" signal, not a correctness problem.

**`path_latency_degraded` / `path_loss` (T-1303).** Source `health`, severity `warning`, `internal/findings/health_latmesh.go`, fed by `internal/latmesh.Service` (§1/§2 above) via the `LatMeshProvider` seam (mirroring `corosync_link_degraded`'s own explicit-provider shape — a probed link has no `inventory.Ref`, so it can't be fed through the graph like every other health check). One finding per directed node-to-node link whose *rolling* (window-averaged, not a single noisy tick) RTT/loss crosses a threshold (`internal/findings.HealthThresholds.LatRttWarnMs`/`LatLossWarnPct`, defaults 80ms/2%) and holds — standard hysteresis (3 cycles rise / 2 cycles fall, the same window `error_drop_rate` uses for a comparable live-runtime-derived signal, one layer on top of the rolling window's own smoothing). Detection-only (`docsLink` always set, never `fixable` — no changeset op can fix a physically degraded path); `id` is `"health:<check>|<linkId>"`, keyed by the link id (not just the node pair, since two different fabrics can share the same two endpoints). Routes through the existing T-1005 alert-rule webhook delivery unmodified, same as every other producer's findings.

**`wan_degraded` (T-1405).** Source `wan` (its own top-level source, not `health` — a WAN reading is external to the cluster, unlike every check above), severity `warning`, `internal/findings/health_wan.go`, fed by `internal/wan.Service` via the `WanProvider` seam (the same explicit-provider shape `path_latency_degraded`/`path_loss` use, one layer reused verbatim). One finding per (node, uplink, external reference target) whose *rolling* loss crosses `internal/findings.HealthThresholds.WanLossWarnPct` (default 20% — deliberately looser than the LAN mesh's 2%, since an ordinary WAN path's baseline jitter/loss is inherently higher) and holds — the identical 3-cycle-rise/2-cycle-fall hysteresis window. Detection-only, never `fixable`; `id` is `"wan:wan_degraded|<linkId>"`. See §8 below.

**PTR completeness audit (T-4109).** Source `health`, `internal/findings/health_ptrcoverage.go`, hysteresis-exempt (same reasoning as `orphan_vnet`/`mgmt_single_path`: PTR coverage is a structural fact about current DNS config, not a noisy live counter). Three checks over `internal/inventory`'s already-collected SDN DNS zone/record entities (the same `internal/sdndns` read path `internal/sdn/dns.go` uses — no second DNS client). **T-4112:** until 2026-08-30 that read path called PVE routes that do not exist, so on any real cluster it received zero records for every zone and this audit reported `ptr_zone_unreadable` for all of them, permanently and correctly given what it was told; records now come from the PowerDNS server PVE writes them into, and a forward record's *every* address is audited rather than only the first (a PowerDNS rrset can hold several, and a PTR rrset naming this record among its targets is a match, not a mismatch). The checks themselves: for every forward A/AAAA record, does a matching PTR exist in the reverse (`*.in-addr.arpa`/`*.ip6.arpa`) zone vnprox has a config entry for? **`ptr_missing`** (severity `warning`) — no PTR at all in a reverse zone vnprox manages and can currently read. **`ptr_mismatch`** (severity `warning`) — a PTR exists but its target doesn't match the forward record (stale/dangling). **`ptr_zone_unreadable`** (severity `info`, once per affected zone, not once per address) — a reverse zone vnprox has a config entry for, and that at least one known forward record's address falls inside, contributed zero records on the last poll; `internal/collect/pve.go`'s SDN DNS poll skips a zone's entire record set on any per-zone read error rather than partially populating it, so this state is genuinely indistinguishable from "the zone has no records yet" — reported as unknown rather than folded into `ptr_missing`, per this task's "collapsing missing and unknown is how a product lies" mandate. An address whose reverse domain matches no zone entry in inventory at all raises nothing — that reverse zone is not delegated to this PowerDNS instance, so it's the operator's wider DNS estate, not vnprox's business. Detection-only (`docsLink` always set, never `fixable` — no changeset op can create or fix a PTR record safely from this check alone).

## 6. Guest network interior inspector (T-1304)

An opt-in, read-only inspector tab on a guest's own map entity (InspectorPanel's "Interior" tab, guest-kind entities only): the guest's own inside view of its network — interfaces, addresses, routing table, DNS config, listening sockets, default-gateway reachability — plus an IPAM cross-check annotation. Off by default (docs/api.md's Guest interior section: `GET/PUT /guests/{ref}/interior-toggle`); turning it on reads inside the guest itself every time the tab is open, via the QEMU guest agent for a qemu guest (`source: "qemu-ga"`, reusing §"Live path probe"'s existing `AgentExec` seam) or directly from the host side for an lxc container, which has no guest agent (`source: "lxc-host"`, `internal/host.Reader.ContainerInterior`/`ContainerPing` — locally, or peer-routed per docs/architecture.md §1/§5's cluster-awareness invariant when the container's node is not this daemon's own).

This is deliberately not a trust boundary vnprox treats as authoritative: a guest's self-report is exactly that, a claim, so every claimed address is cross-checked against `internal/ipam`'s resolved allocation set (docs/features/ipam.md §1's confidence-labeling contract) rather than taken at face value — an address the guest claims but IPAM has no record of surfaces as an unmatched entry, never silently accepted. Strictly read-only: there is no write path from this inspector into the guest or into IPAM.

**Needs hardware validation**: the exact in-guest/in-container command set and the lxc pid-resolution mechanism — see docs/api.md's Guest interior section and `planning/reports/needs-hardware-validation.md`.

## 7. Path MTU prober (T-1306)

`internal/mtuprobe.Service` performs active per-path MTU discovery: a binary-search sweep of DF-set (Don't Fragment) ICMP probes, converging on the largest packet size a path actually carries end-to-end — built directly on T-1303's latency-mesh infrastructure (§1/§2), not a second scheduler or a second path-discovery mechanism. Its `Discoverer` is the exact same `internal/latmesh.GraphDiscoverer` instance the latency mesh itself uses, so it probes exactly the corosync/guest-fabric paths the mesh already knows about (see `internal/latmesh`'s own package doc comment for why those two fabrics — corosync ring addresses and bridges shared by two or more nodes, which is the VXLAN/EVPN underlay path itself when that shared bridge is an SDN vxlan/evpn zone's own bridge); its `RunLoop` calls `internal/latmesh.RunTicker`, the identical shared scheduler primitive `latmesh.Service.RunLoop`/`RunPruneLoop` use. Runs on its own, much coarser cadence (`[mtuprobe] probe_interval_sec`, default 300s — MTU rarely changes, unlike latency/loss) than latency probing's default 10s.

Unlike the latency mesh, this is a **current-state seam, not a SQLite-backed ring**: `Service.Results`/`Result` hold only each link's most recently verified MTU in memory (no `mtu_probes` table, no history/rolling stats — there is no history use case a rarely-changing value needs). A link this node has never successfully probed simply has no entry; a probe attempt that fails to even run (transport error) leaves the prior good reading in place rather than clearing it to a stale zero.

| Method | Path | Purpose |
|---|---|---|
| GET | `/mtuprobe/results` | every currently-known verified per-link MTU reading this node has probed |

**`GET /mtuprobe/results`** response: `{items: [MTUProbeResult]}`. `MTUProbeResult`: `{linkId, fabric, fromNode, toNode, mtu, at, probeCount}` — `linkId`/`fabric`/`fromNode`/`toNode` are the exact same `internal/latmesh.Pair.LinkID`-keyed identity `GET /latmesh/heatmap` uses for the same path, so a UI can correlate a link's latency reading and its verified MTU reading by `linkId`. `mtu` is the binary search's converged result; `probeCount` is how many DF-probes that convergence took (bounded — see `internal/mtuprobe.BinarySearchMTU`'s doc comment). Node-local only, no peer fan-out, the same documented scope `GET /latmesh/heatmap` carries.

**Map-edge annotation**: the web client's "verified MTU" overlay (`web/src/topology/mtuOverlay.ts`'s `computeMTUOverlayEdges`) renders each probed link's measured MTU as its own badge, distinct from wherever that link's *configured* MTU is already shown (the zone/bridge editor's own MTU field) — a link with no probe result yet renders no badge at all, never a stale or zero placeholder. This is a second, independent overlay from the "Latency" heatmap layer (T-1303), the same "two independent overlays, one toggle each" pattern that layer established.

**Findings**: see §5 above — `vxlan_underlay_mtu` consumes `Service.MeasuredUnderlayMTU` (the minimum verified MTU across a node's successfully-probed outbound links) as an optional, tighter input, falling back to the pre-existing observed-NIC-MTU evaluation wherever no fresh probe reading exists.

## 8. WAN & upstream health (T-1405)

`internal/wan.Service` answers "is this the ISP, not the cluster?" — per-uplink availability/latency/loss to operator-configured *external* reference targets (a public resolver, an upstream gateway, ...), the dashboard-tile verdict that separates "the cluster is fine, your uplink isn't" from an in-cluster problem. **Visibility and the `wan_degraded` finding only — no WAN failover automation** (no changeset op type or write route exists anywhere for uplink switching).

Its probe loop is literally `internal/latmesh.Service` reused (§7's own precedent for reusing T-1303's infrastructure rather than forking it): `Service.Config.Discoverer` is `internal/wan.TargetDiscoverer` (emitting one `Pair` per configured node/uplink/reference-target triple, re-read fresh from the store every tick) and `Service.Config.Store` is `store.WanProbeSampleRepo`, backing a new `wan_probe_samples` ring rather than `latency_samples` — a WAN link's own jitter/loss profile and retention needs are not the LAN mesh's, so `[wan]`'s own `probe_interval_sec`/`retention_minutes`/`max_rows` (`vnprox.toml`, same 10s/60min/500,000-row defaults as `[latmesh]`) apply to their own bounded ring. The wire-level probe mechanism (`latmesh.RealProber`, execing `ping`) is reused unmodified — it works identically against an external hostname/IP as it does a cluster node name.

**Node-local scope**, the same documented gap §7's `GET /mtuprobe/results` carries: a node only probes its own configured targets; `GET /wan/status`'s cluster-wide picture is the union of every node's own view. `GET/PUT /wan/targets` (docs/api.md's WAN & upstream health section) likewise operate on the requesting node's own local store.

**`GET /wan/status`** reports every currently-probed uplink independently (multi-WAN: two uplinks on one node, one degraded, are never blended into one reading) plus a dashboard-tile `verdict`: `"likely_isp"` when at least one uplink is degraded/unreachable **and** every other (non-`wan`) finding in `GET /findings` is below `warning` severity — computed in `internal/api` (the one place both the WAN and findings seams are already wired; `internal/wan` itself never imports `internal/findings`, the same one-way dependency direction every other findings *producer* in this codebase keeps) — falling back to the less specific `"wan_degraded"` verdict when that "otherwise clean" confirmation isn't available or doesn't hold, never a confident "it's the ISP" claim the daemon can't actually back up.

**Findings**: see §5 above — `wan_degraded`, routed through the existing T-1005 alert-rule webhook delivery unmodified, same as every other producer's findings.

**WireGuard hook (declared, not wired)**: `Service.ProbeWireGuardLink(ctx, tunnelRef)` is a capability-gated seam that always returns `mtuprobe.ErrWireGuardNotAvailable` today (`mtuprobe.WireGuardCapability` defaults false — there is no WireGuard tunnel entity kind in `internal/inventory` yet). Phase 14's T-1401 is the task expected to introduce that capability flag and wire a real implementation into this exact method; see `planning/reports/T-1306.md`.
**`service_traffic_on_wrong_network` (T-1504).** Source `flow` — its own top-level source, not `health` (fed by `internal/flow.Classifier`-classified flow-sample metadata rather than the inventory graph or a polled host/PVE seam). Severity `warning`, standard hysteresis (2 cycles each way, the same window `corosync_link_degraded` uses). One finding per `(serviceClass, vlan)` pair with at least one currently-observed flow record whose own VLAN falls outside its matching `NetworkSource`'s declared VLAN set — e.g. Ceph-classified traffic observed riding the guest VLAN instead of Ceph's own declared public/cluster network ("storage traffic is eating the guest VLAN"). Detection-only (`docsLink` always set, never `fixable` — moving traffic onto the right network is an administrative/config decision, not a computable patch; no `flow.*` changeset op exists or ever will). Silent whenever a classified record's VLAN matches its declared network, or the matching `NetworkSource` declares no VLANs to compare against at all (nothing to judge — see §3's `serviceClass` note above for exactly which sources are wired with a declared VLAN set in production today). See docs/api.md's `GET /findings` section for the full shape/id scheme.

## 9. Daemon self-observability (T-1903)

§4's exporter reports the *cluster* vnprox observes; this section is the daemon observing *itself* — the same `GET /metrics` response, a second family of series alongside §4's. Scope discipline still applies: this is RED-shaped operational telemetry for an operator's own Prometheus/Grafana, not a second findings/audit surface — a change-engine outcome is a counter here and a full record in `GET /audit` there, and the two are not meant to answer the same question.

**Cardinality discipline (the hazard this section exists to prevent).** A metric label populated from a raw request path, a changeset ULID, or a guest name turns one series into an unbounded number of series — the single most common way to melt a self-hosted Prometheus. Every series below is labeled only from a small, compile-time-fixed vocabulary; each entry states its bound explicitly. Two backstops enforce this even if a future change gets it wrong: `internal/api/redmetrics.go`'s HTTP middleware sources its `route` label exclusively from chi's own matched route *pattern* (`chi.RouteContext(r.Context()).RoutePattern()`) — which is built by joining each matched sub-router's literal pattern string, never a URL parameter's resolved value, so there is no code path that could leak a raw ID even by mistake (a request no route matches collapses to the single label `"unmatched"`, not the raw path) — and, belt-and-suspenders, every series in `internal/metrics/self.go`'s registry caps its own distinct label-combination count (4,000) and folds anything beyond that into one `cardinality_overflow` bucket, logging once at `WARN` rather than growing unboundedly. `internal/api/redmetrics_test.go`'s `TestHTTPRED_RouteLabelNeverLeaksRawID` drives a real request through the real router with a concrete changeset ULID in the URL and asserts that ID string appears nowhere in the scrape body — the regression test a future author who reintroduces `r.URL.Path` here would trip.

**Push vs. pull.** Most series below are *push*-model: `internal/metrics.Registry` (a small hand-rolled counter/histogram implementation — see its own doc comment for why this doesn't pull in a Prometheus client library dependency) is updated in-process as HTTP requests/collector polls/change-engine operations/store queries/peer RPCs happen, and rendered verbatim at scrape time. A handful are *pull*-model: collector consecutive-failure counts, store size/schema version, and the live WebSocket connection count are read fresh from their existing source of truth at scrape time rather than shadow-tracked — collector consecutive-failures in particular deliberately **mirrors** `GET /health`'s existing `collect.Collector.Status()` bookkeeping rather than inventing a second notion of collector staleness (this task's card, verbatim).

## 10. Incident mode (T-2804)

When a network breaks, the operator needs the diagnosis ladder (§6/§7 and `docs/api.md`'s Diagnosis section), a capture, the current findings (§5), recent flows, and what changed — and before this, that meant five screens correlated by hand, under time pressure, which is exactly when hand-correlation fails.

An **incident** (`internal/incident`, `web/src/incidents/`, `docs/api.md`'s Incidents section) is one window and one merged timeline over all of it, plus the operator's own annotations, plus T-2704's point-in-time diff across the window.

**It is a view, not a mode.** Opening one starts no collector, subscribes to no stream and copies no event. Every timeline is assembled at read time from history vnprox already records — `finding_events`, `audit_log` (both the changeset-lifecycle actions and `diagnose.run`), `capture_sessions`, `flow_samples` — the same tables `GET /history/events` (§2), `GET /audit`, `GET /captures` and `GET /flows` already serve. Two consequences are contractual:

- An incident can be opened **retroactively** over a window that closed hours ago and contains exactly what a live one opened at that moment would have contained. Nobody has to press "start incident" before the network breaks.
- **Closing deletes nothing**, and reopening shows the same timeline — there is no `incident_events` table to delete from (see `docs/data-model.md` §2 and migration `0041_incidents.sql`).

**What it refuses to imply.** A source that is not collecting on this node reports `unavailable` rather than looking empty; a failed source degrades only its own events; the flow list is capped and says when the cap bound. The point-in-time diff's scope caveat is *derived from the diff's own `coverage`* (today `/etc/network/interfaces` only — SDN entities are not diffed), as is the warning about a node captured at only one end of the range, whose absent entities are not deletions. A range the change engine cannot cover surfaces its typed refusal — which names the snapshots that do exist — never an empty diff, because an empty diff reads as "nothing changed" and an operator acts on that.

**Export** produces one artifact: T-1902's support bundle with one additional declared entry, `incident/timeline.json`, through the same staging, manifest, declared-field schema and redactor — which is why T-1902's own secret scan runs over it as a second producer rather than being reimplemented. A diff entry travels as the *names* of the changed interfaces(5) options and never their values, since an option value is exactly where a `wireguard-private-key` lives.

## 11. Mobile PWA with web push (T-2005)

Phase 17's exit demo (`docs/roadmap-universal.md`) describes an on-call human confirming a changeset from their phone. T-909 shipped the phone-usable triage layout that makes the destination real; this task makes the *arrival* real — an installable PWA (`web/public/manifest.webmanifest`, `web/public/sw.js`) that can push a notification for the three things worth waking someone up for.

**Categories are closed and per-subscription.** `internal/push.Category` is exactly `critical` \| `awaitingConfirm` \| `drift` — a subscription (`POST /push/subscriptions`) opts into a non-empty subset, chosen in Settings → Notifications (`web/src/push/PushSettingsSection.tsx`). "Critical" reuses this document's own severity vocabulary (§5): it is `findings.SeverityError`, this codebase's highest defined severity — there is no separate "critical" level, only the highest one this section already describes.

**Delivery paths, one per category:**

- **`critical`** — `internal/push`'s `FindingNotifier` (`cmd/vnproxd/push.go`) is composed into the same `multiNotifier` §5's "Notification hooks" paragraph describes, alongside the PVE notification hook and the T-1005 webhook notifier: on a finding transitioning to `new` or `escalated` at error severity, it fires. Unlike the other two notifiers, it never receives the `findings.Finding` value's identity-bearing fields — see the safety note below.
- **`awaitingConfirm`** — fans off the existing `changeset.status` WS event (docs/api.md's WebSocket section) the moment a changeset's status is `awaiting_confirm`, via the same event fan-in T-1104's webhook Dispatcher already taps (`internal/topology.Hub.SetEventSink`, one combined sink installed in `cmd/vnproxd/server.go` so both consumers see every event).
- **`drift`** — the same fan-in's `drift.changed {count}` event, gated on `count > 0` (nothing to say when drift resolves to zero).

**Safety note: a push payload carries no cluster-identifying content.** `internal/push.Notification` (`payload.go`) is a closed, four-field shape (`category`, `event`, `title`, `body`, `url`) built entirely from Go string literals at the call site, plus at most one caller-supplied value: a changeset ULID (`internal/store.NewULID`, no embedded identity) for the `awaitingConfirm` deep link. The `critical` category's notification is generic — `"New critical finding"`, deep-linking to `/tools?pushCategory=critical` (a pre-filtered view of §5's findings stream) rather than to one specific finding — because a `Finding.ID`/`Detail`/`Nodes`/`Refs` routinely embeds a node or guest name (e.g. `health_peertrust.go`'s `peerFindingID(check, p.Node)`), and this task's card requires the payload not leak the network's shape to a phone lock screen. This is the same enumerated-payload discipline docs/security.md's Compatibility-telemetry section documents for `internal/telemetry.Guard`, applied to a second outbound channel.

**Confirming still requires a real session.** A notification's `notificationclick` handler (`web/public/sw.js`) only ever posts a URL to an open tab or opens a new one — it is a deep link, never an action token. Whatever page it lands on enforces its own `RequireAuth`/capability gate exactly as if the operator had typed the URL in by hand.

**Subscriptions are credentials, encrypted at rest, and die with their session.** `push_subscriptions` (`0046_push_subscriptions.sql`) stores a browser's endpoint/keys as AES-256-GCM ciphertext under the same session-secret cipher `sessions.pve_ticket_enc` uses; `session_id` is a foreign key `ON DELETE CASCADE`, so a logout or session expiry removes the row structurally, not via a handler that has to remember to. Listable/revocable per device at Settings → Notifications → "Your devices" (`GET`/`DELETE /push/subscriptions`).

## 12. SIEM export (T-4012)

vnprox is explicitly not a long-horizon warehouse (`docs/features.md`): `audit_log` and the findings stream are both bounded and pruned (`store.AuditRepo.RunPruneLoop`, `[retention] audit_keep_days`). An operator who wants ninety days of audit history is expected to keep it in a SIEM they already run, not in vnprox's own SQLite — `internal/siemexport` is the "ship it out" half of that contract: a bounded, best-effort streaming export of every audit row and every finding transition, in RFC 5424 syslog or newline-delimited JSON. Full design rationale lives in `internal/siemexport/doc.go`; this section is the operator-facing summary.

**Off by default, config-gated, `[siemexport]`.** The zero value is a complete no-op. An *enabled* section is validated strictly at startup (`internal/config.resolveSIEMExportConfig`) — a half-configured destination (a `format` with no `address`, both `path` and `network`/`address` set for `jsonl`, an out-of-range `facility`, ...) refuses to start rather than silently exporting nothing:

```toml
[siemexport]
enabled = true
format = "syslog"          # "syslog" (RFC 5424) | "jsonl" (newline-delimited JSON)
network = "tcp"             # "tcp" | "udp" (syslog); "tcp" | "udp" | "unix" (jsonl socket mode)
address = "siem.example:6514"
# path = "/var/log/vnprox/audit.jsonl"   # jsonl-to-file, mutually exclusive with network/address
buffer_size = 4096           # bounded ring buffer capacity (default 4096)
facility = 16                # RFC 5424 facility 0-23 (default 16, local0; syslog only)
```

**Fed from the existing fan-in, not a new capture path.** Audit rows: `store.AuditRepo`'s existing `SetOnAppend` hook (`cmd/vnproxd/events.go`'s `wireAuditAppendedEvents`, already feeding the `audit.appended` WS event) is extended to additionally call `Exporter.ExportAudit`, once per committed row, same as the WS event. Findings: rather than `internal/findings.Engine`'s `Notifier` interface (which only fires above the operator's own `NotifyThreshold` — an alerting knob a SIEM export must not be silently gated by), `cmd/vnproxd`'s `siemFindingsTracker` diffs the full findings list `Config.OnCycle` already hands it every cycle against its own previous-cycle snapshot, exporting every finding that newly appears, changes severity, or resolves (`transition`: `new`\|`changed`\|`resolved`) — regardless of alert threshold, and without re-sending an unchanged finding every cycle forever.

**Delivery is at-most-once, deliberately.** Every event is attempted exactly one time: on success it is done; on failure (far end down, connection reset, write timeout) it is dropped and counted, never retried — retrying would risk a duplicate row in the SIEM if the original send actually succeeded but its ACK was lost, and a security team debugging a duplicate is a worse failure than a security team seeing a drop counter move. The buffer itself (`Exporter`'s bounded ring, capacity `buffer_size`) evicts the OLDEST not-yet-attempted event when full, favoring recency — the same bounded-ring shape `internal/capture`'s retention sweep and `internal/metrics`'s self-observability ring already use elsewhere in this codebase. Neither failure mode is silent: every drop increments `vnprox_siemexport_events_total{outcome="dropped_buffer_full"|"dropped_send_error"}` (§9 above) and calls a `DropObserver` hook, and `internal/siemexport.Exporter.Stats()` exposes the running counts directly. Export failure never touches the primary record — `audit_log`/the findings stream are written exactly as they were before this section existed, regardless of whether the configured sink is reachable.

**Redaction is mandatory, not opt-in.** Every audit `detail_json` and finding `detail` passes through `internal/redact` (`redact.JSON`/`redact.Scrub` — the same vocabulary support-bundle export already uses) inside `Exporter`'s own event constructors, so there is no code path that can export an unredacted event. See `internal/redact/redact.go`'s doc comment for exactly what it catches (keyed secrets by name, PVE tickets/API tokens, `Authorization` headers, URL userinfo, base64-shaped keys, PEM blocks) and what it does not (a secret with no recognizable key name or wire shape).

**Field mapping.** Every exported event carries `kind` (`"audit"`\|`"finding"`), `at` (UTC), and `severity` (`"error"`\|`"warning"`\|`"info"`), plus either the audit fields (`auditId`, `username`, `action`, `target`, `changesetId`, `result`, `ip`, `detail`) or the finding fields (`findingId`, `source`, `check`, `transition`, `nodes`, `refs`, `findingDetail`). JSONL uses these exact field names; syslog carries the same fields as RFC 5424 SD-PARAMs inside one `vnproxAudit@32473`/`vnproxFinding@32473` SD-ELEMENT (32473 is RFC 5424 §7.2.2's reserved example enterprise number — vnprox has no IANA-registered PEN), plus a human-readable `MSG` for a parser that only reads that field. `internal/siemexport/doc.go`'s "Field mapping" section is the source of truth this paragraph summarizes.

**Offline shell.** The service worker precaches the app shell and opportunistically caches static assets, but never `/api/*` — a cached authenticated response on a shared device would leak the previous session's data to whoever logs in next. `OfflineShellBanner` (`web/src/layout/OfflineShellBanner.tsx`) is the honesty half: while `navigator.onLine` is false it says so explicitly and states the age of whatever data is on screen (via the shared `QueryClient`'s own cache timestamps), so a stale topology is never presented as current.
