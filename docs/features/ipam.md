# Feature spec — Visual IPAM

Proxmox has IPAM plugins (built-in `pve`, NetBox, phpIPAM) but no usable view of them. vnprox provides the view and the workflow.

## 1. Data sources

- Primary: PVE IPAM API (allocations per SDN subnet).
- Enrichment: guest agent-reported IPs, DHCP leases (dnsmasq zones), and ARP/IPv6-neighbor tables via peer API (`internal/neighbor.Service`, T-805) — merged with confidence labels (`allocated`, `observed`, `both`, `conflict`). The neighbor source reads `internal/host.Reader.Neighbors` (real: `/proc/net/arp` for IPv4, the IPv6 neighbor table via netlink) locally and fans it out cluster-wide via `GET /api/peer/host/neighbors`, exactly like the guest-agent and DHCP-lease sources — never authoritative, filtered to resolved neighbor-cache states (`REACHABLE`/`STALE`/`PERMANENT`). All three enrichment sources are wired today; no known gap remains here.
- External IPAM (NetBox/phpIPAM) is configured in PVE, not vnprox; vnprox reads through PVE's plugin transparently and deep-links to the external tool for records it doesn't own.
- **Rogue-service / L2-anomaly detection (T-1605).** The same neighbor/ARP enrichment above, the DHCP lease/reservation views, and (once it ships) T-1404's IPv6 RA visibility feed also power four detection-only findings in the unified stream under `source: "rogue"` — all `severity: "error"`, never `fixable`, and hysteresis-exempt (a rogue/spoof signal is a security event, not a noisy counter): `rogue_dhcp_server` (a DHCP-offering source whose MAC is not the subnet's configured PVE-SDN DHCP range owner, `GET /sdn/dhcp`'s config-truth view), `unexpected_ra` (an IPv6 RA from a source that is not a known PVE-configured RA source — a documented no-op until T-1404's feed lands), `arp_spoof_suspected` (the same IP flapping between MACs across a short trailing churn window, distinguished from a single DHCP-renewal reassignment), and `unknown_mac_protected_segment` (a MAC learned on a bridge listed in the `[security] protected_segments` config that matches no known guest/PhysNic/LLDP-neighbor MAC in the inventory graph). This is detection only — vnprox never auto-blocks a suspected rogue; mitigation stays a human-confirmed firewall change through the ordinary change engine, like every other detection-only producer. See `docs/api.md`'s `source: "rogue"` paragraph for the per-check `id`/`refs` contract.

## 2. Views

- **Subnet list**: all SDN subnets + (read-only) detected non-SDN subnets from bridge addresses; utilization bars, gateway, zone/VNet, DHCP on/off.
- **Address list** (NetBox-style): the selected subnet's occupied addresses as rows — IP, state (allocated / reserved / observed-unallocated / gateway / conflict), hostname, VMID, MAC, source — with the contiguous free space between them collapsed into "N addresses free" range rows. Because the response is sparse (proportional to actual usage, not the address space), the same view serves a /30 and a /16 with no paging. A segmented utilization strip and the conflict callouts sit above the list; a search box and per-state filter chips narrow it; clicking a row opens its detail + reserve/release. This replaced the earlier colored-square allocation grid (which didn't scale past a /24 and hid per-address detail behind a click).
- **Conflict surfacing** (P0 value): duplicate IPs (two guests reporting the same address), observed-but-unallocated (squatters), allocated-but-dark (stale records). Each conflict is a health finding with suggested resolution.

## 3. Workflow

- Reserve/release addresses (`ipam.alloc.*` ops through the change engine).
- "Next free address" picker (`web/src/ipam/NextFreePicker.tsx`) exposed on the bridge editor's address field today; wiring it into every other IP-entry field in the UI (VLAN editor, interface editor, SDN subnet gateway) is a known follow-up (flagged, T-607), not yet done for all of them.
- CSV export per subnet.

## 4. IPv6 planning grid (T-1404)

Given a delegated IPv6 prefix (e.g. a `/56` from an upstream ISP/RIR), `GET /ipam/subnets/{prefix}/v6-plan` (`docs/api.md`) enumerates its `/64`-aligned blocks — PVE SDN's (and nearly every real-world v6 addressing plan's) atomic per-subnet unit — and proposes one block per currently v4-only VLAN/VNet, aligned in ascending order against VNet ID for a deterministic, reviewable proposal. A block an already-configured SDN v6 subnet occupies renders `allocated`; everything else not proposed to a target renders `free`. Read-only: the grid is a planning aid, not a write path — turning a `proposed` block into a real subnet goes through the ordinary `sdn.subnet.create` changeset op (directly, or via the dual-stack rollout wizard below).

DHCPv6-PD from an upstream device vnprox doesn't manage is visibility-only, surfaced through `GET /ipv6/segments`'s RA observation (`docs/api.md`'s IPv6 section) — never fetched, requested, or configured by vnprox itself.

## 5. Dual-stack rollout wizard (T-1404)

`web/src/ipv6/DualStackWizard.tsx`, built on `docs/features/blueprints.md`'s `blueprint.Instantiate` pattern: picks an existing VLAN/VNet, collects a v6 subnet CIDR/gateway/SNAT choice, and stages an `sdn.subnet.create` op as one reviewable changeset — the ordinary stage→validate→diff→apply→confirm/rollback lifecycle, no new op type. Idempotent by construction (the same "entities that already match are skipped" contract every blueprint instantiation gets): re-running the wizard against a VNet that already has the requested v6 subnet yields a zero-op changeset, rendered as "already up to date" rather than a duplicate or conflicting draft. RA/DHCPv6 *parameter* control beyond addressing (M/O flags, DHCPv6 ranges) remains P1 — PVE SDN's own subnet model has no such fields yet (§6 of `docs/features/sdn.md`); once addressing exists on an SDN zone, the zone's own dnsmasq/radvd instance is what actually emits the RA the segments view (§4 above's sibling, `GET /ipv6/segments`) then observes.

## 7. External subnets & external-IPAM bidirectional sync (T-1203)

vnprox v1 could only *view* the IP space Proxmox itself knows about (SDN subnets, bridge-derived subnets). Two gaps closed here:

**External subnets as first-class records.** IP space Proxmox has no knowledge of — a physical office LAN, an upstream transit range, a prefix that lives in NetBox/phpIPAM — is now a first-class IPAM record (the app-owned `external_subnets` table, docs/data-model.md §2). It renders in the subnet list as a `source: "external"` row (read-only — it carries no PVE-IPAM allocation set), alongside the `sdn` and `bridge` rows. External subnets are app-owned *intent*, **not** a shadow copy of any PVE SDN subnet: they are read/written only through the dedicated `/ipam/external-subnets` CRUD routes (docs/api.md), never through `ipam.alloc.*` (or any) changeset op — they are not PVE SDN subnets, so there is nothing in PVE to stage/apply.

**Cross-cluster IPAM view.** With more than one PVE cluster attached (T-1201 federation), the same or an overlapping CIDR allocated in two different clusters is a latent addressing hazard invisible to any single cluster's own view. `GET /federation/ipam/conflicts` (backed by T-1201's aggregator, fanning each attached cluster's configured SDN subnets out) surfaces it as a `Conflict` of the new type `cross_cluster_duplicate_subnet`, reusing the existing `Conflict` shape with an added `clusters` cluster-pair field naming the two clusters. One cluster being unreachable is isolated the same way every other fan-out isolates a down peer (`partial`/`failedClusters`); the reachable clusters' conflicts are unaffected.

**Bidirectional NetBox/phpIPAM sync.** The v1 NetBox/phpIPAM integration was read-merge only (vnprox read through PVE's plugin transparently). T-1203 upgrades the bridge to bidirectional sync: a diff engine compares vnprox's own PVE-IPAM allocations against the external system's own records and classifies each difference as an **add** (vnprox has it, external doesn't), a **remove** (external has it, vnprox no longer allocates it), or a **conflict** (both hold the address but disagree on its hostname — never auto-written). `POST /ipam/external-sync/preview` is a pure dry-run that never writes; `POST /ipam/external-sync/apply {confirm:true}` applies the adds/removes and audit-logs every write (`ipam.external_sync`, before/after per record). Conflicts and pending drift also flow into the unified findings stream as `source: "ipam"` checks `external_ipam_conflict` / `external_ipam_drift`.

**Design note — why external-IPAM writes sit outside `internal/change` yet mirror its contract.** The change engine (`internal/change`) owns *Proxmox network config* mutations: stage → validate → diff → apply → confirm/rollback, with a pre-apply snapshot to roll back to. An external IPAM system is **not** Proxmox network config — there is no PVE object to diff, no `/etc/network/interfaces` or SDN config to snapshot, and no node-local daemon that could roll a remote NetBox/phpIPAM write back. Routing external-IPAM writes through `internal/change` would therefore be a category error (and is structurally prevented: no `ipam.external_sync.*` op type exists, and a regression test asserts the sync write path never imports `internal/change`). But *"outside the change engine" must never mean "unstaged and unaudited."* The sync path deliberately mirrors the change engine's stage/review/confirm/audit **ceremony**: `preview` is the stage/diff step (a dry-run that shows exactly what would change and writes nothing), `apply {confirm:true}` is the explicit confirm step (mirroring `POST /lldp/install`'s confirm ceremony — `confirm` false/omitted is a `400` with no write), and every applied write lands an `ipam.external_sync` audit row with before/after. An external-IPAM write is thus exactly as reviewable and auditable as an in-cluster change, without pretending to be one.

**Status.** The diff engine, preview/apply/confirm/audit flow, cross-cluster conflict detection, and external-subnet records are complete and tested (`internal/ipam` against an HTTP test double of a NetBox/phpIPAM address API). The concrete production write client keyed to real NetBox/phpIPAM API shapes is **needs hardware validation** — see `planning/reports/needs-hardware-validation.md`. Until such a client is configured, the sync routes report "not configured".
