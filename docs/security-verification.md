# Security verification (T-604)

This document maps every claim in `docs/security.md` to its evidence: an automated test (name + file), a structural/code-inspection fact (for claims that are true by construction rather than by runtime behavior), or an explicitly documented manual-verification procedure for anything that cannot be automated in this environment. It is organized section-by-section, mirroring `docs/security.md`.

Legend: **T** = automated test, **S** = structural/code-inspection verification, **M** = manual verification procedure, **H** = needs hardware validation (real PVE cluster/systemd host).

## Host footprint

| Claim | Evidence |
|---|---|
| Systemd unit hardening: `ProtectSystem=strict` + `ReadWritePaths`, `ProtectHome=yes`, `PrivateTmp=yes`, `NoNewPrivileges=yes`, capability bounding | **S** `packaging/systemd/vnprox.service` — all directives present. **v3.0.1 (hardware validation, upgrade 1.3.6→3.0.0):** `ReadWritePaths` gained `/etc/vnprox/keys` — the daemon generates first-run secrets there (`metrics.key` T-1001, `blueprint-signing.key` T-1705) that `ProtectSystem=strict` was blocking, crash-looping the service on first boot after an upgrade from a release predating those keys; a smoke test on a freshly-`vnprox-setup`'d node never hit it because setup had already created the keys. **T-604 additions**: `RestrictAddressFamilies=AF_INET AF_INET6 AF_NETLINK AF_UNIX` and `SystemCallFilter=@system-service` plus an explicit re-deny of `@mount @reboot @swap @privileged @resources @raw-io @debug @module @cpu-emulation @obsolete @clock`. **M** `systemd-analyze verify` reports zero warnings against this unit file (manually run, this task). **M** a functional smoke test running the real `vnproxd` binary under a `systemd-run --user` transient unit carrying this exact directive set (plus the pre-existing `Protect*`/`Restrict*` set) confirmed: the daemon starts, serves HTTPS, discovers the local node via a real netlink read, and polls a mock PVE server over plain HTTP — i.e. the syscall/address-family restrictions do not break any real I/O path exercised in this environment (procedure and result documented in this task's report). **H → S (T-608, hardware validation)**: full production parity — running as root with the unit's `CapabilityBoundingSet`, under a real systemd PID 1 — is now verified against a real PVE 9.2.4 node, and it found a real gap the smoke test above missed: the original `RestrictAddressFamilies` omitted `AF_UNIX` on the (wrong) assumption that vnproxd's own no-cgo I/O never needs it — but the filter is inherited across exec by `lldpctl`, a subprocess vnproxd spawns, which talks to lldpd over a Unix domain socket. Every LLDP poll failed outright under the original directive set; fixed by adding `AF_UNIX`. |
| Never shells out with user-supplied strings; fixed argv arrays for `lldpctl -f json`/ethtool | **S** Every `exec.Command(Context)` call site in `internal/host` and `cmd/vnproxd` uses a fixed or config-supplied (never per-request/user-supplied) argv: `internal/host/netlink_linux.go:121` (`r.LLDPCommand`, config-supplied, defaults to `lldpctl -f json`), `internal/host/netlink_linux.go:164` (`runFRRCommand`, config-supplied `vtysh` invocations), `cmd/vnproxd/changeagent.go:125` (`exec.CommandContext(ctx, "ifreload", "-a")` — literally zero arguments), `internal/host/lldp_install_linux.go:29,32` (fixed `InstallLLDPDCommand`/`EnableLLDPDCommand` argv constants). **Note (doc correction opportunity, flagged for the T-607 docs freeze):** ethtool is *not* invoked as a subprocess at all — `internal/host/ethtool_linux.go` uses the `SIOCETHTOOL` ioctl directly via `golang.org/x/sys/unix` (a documented T-102 deviation, see `ethtool.go`'s doc comment), which is a *stronger* property than the documented "fixed argv" claim (zero shell-out surface for ethtool specifically). **None of the current exec call sites accept a dynamic interface name as an argv element at all** (`ifreload -a` takes no arguments; `lldpctl`/`vtysh` invocations are whole-node, not per-interface) — so the "interface names validated against the kernel's interface list" half of the claim is vacuously satisfied: there is no such argument to inject in the first place. Interface names from user-submitted changesets only ever reach the `interfaces(5)` file *content* (via the AST writer, `internal/change/ifaces`), never a shell argv. |
| SQLite DB and key files are `root:root 0600` | **T** `TestOpen_EnforcesFilePermissions`, `TestOpen_CorrectsPreExistingLoosePermissions` (`internal/store/store_test.go`, **added by this task** — this task found and fixed a real gap: the sqlite driver created the DB file, and its `-wal`/`-shm` sidecars, at the ambient-umask mode (0644 under a typical 022 umask), not 0600; `Open` now enforces 0600 explicitly, including correcting a pre-existing looser-mode file on reopen). **T** `TestKeyFile_GenerateAndLoad` (`internal/store/sessions_test.go`) for the session key file. **H** the `root:root` *ownership* half (as opposed to the 0600 *mode*, which is unit-tested) depends on the daemon actually running as root, per the installer — needs hardware validation. |

The closest analogous untrusted-input parsing this package does is JSON request-body decoding (`encoding/json`, part of the Go standard library's own fuzzed corpus) and PVE permission-path handling (`internal/auth/caps.go`), which operates on a small closed set of privilege-name strings rather than free-form untrusted text. No additional fuzz target is warranted here beyond the peer-HMAC fuzzing already in place for the one auth-adjacent wire format (peer signatures) that does need it.

## Ancillary finding (out of this task's docs/security.md scope, noted for follow-up) — fixed by T-607

`web/src/firewall/ObjectsPanel.tsx`'s cluster-scope object "Delete" button (shared by the Firewall and SDN pages) had no `disabled` binding wired to the read-only/capability state at all — a read-only or `fwWrite`-lacking user saw an enabled Delete control. This was never a docs/security.md violation (the backend's `RequireCap`/PVE-ACL enforcement, see Authorization section, always blocked the actual mutation server-side regardless of the button's `disabled` state — no privilege escalation was possible), only a T-605 UX-completeness gap. T-604 flagged it rather than fixing it (out of that task's scope); **T-607's own E2E read-only crawl independently re-caught this same gap** (plus two more of the same shape: `SdnPage.tsx`'s zone/vnet/subnet edit/delete/create triggers, and `RuleEditor.tsx`'s per-rule delete/enable-toggle/drag-reorder/add-rule) and fixed all of them, using the same `capsForNode`/`missingCapTooltip` pattern this doc's Authorization section already cites for `internal/auth/caps.go`'s mapping — plus fixing a second, more severe bug the fix surfaced along the way: five pre-existing SDN editor dialogs' cluster-scope capability checks (`capsForNode(session, "")`) were resolving against a caps-map key (`""`) that `internal/auth.BuildCapabilities` never actually populates for a non-empty node list, silently disabling the entire SDN write UI for every real multi-node cluster; corrected to `hasAnyCap(session, cap)`. See `planning/reports/T-607.md` for detail.
