# API design

Base: `https://<node>:8007/api/v1`. JSON everywhere. This document is a **contract** — implementation tasks in different phases depend on these routes and shapes matching exactly.

## Conventions

- Auth: session cookie `vnprox_session` (HttpOnly, Secure, SameSite=Strict) + `X-VNPROX-CSRF` header on mutating requests. **Exception (T-1001):** `GET /metrics` (the Metrics-exporter subsection below) uses a separate bearer-token scheme instead — see that subsection and docs/security.md's Authentication section for the full auth story and why a Prometheus scraper can't carry a session cookie or CSRF header. **Addition (T-1104):** `Authorization: Bearer <token>` is accepted on *every* route in this document (not just `GET /metrics`), converging on the exact same session-derived request context a cookie does — see the Tokens section below and docs/security.md's Authentication section for the full model. A bearer-authenticated request skips CSRF (there is no cookie to double-submit) but is still rate-limited and audited (`token.use`) per use.
- Errors: `{"error": {"code": "string", "message": "human readable", "details": {}}}` with proper HTTP status. Codes are stable identifiers (`validation_failed`, `pve_denied`, `changeset_locked`, `peer_unreachable`, `peer_untrusted`, `peer_incompatible`, ...). `peer_untrusted` (T-1906) is deliberately distinct from `peer_unreachable`: the peer answered but its TLS certificate did not verify against the pinned cluster CA — a possible impersonation, not a network fault. See the Peer API section.
- IDs: entities use `Ref` triplets `kind:node:id` in URLs, URL-encoded (cluster-scoped: empty node, `sdn-vnet::zone1/vnet1`).
- Pagination: `?limit=&cursor=` on list endpoints that can grow (audit, snapshots).
- All timestamps are unix seconds UTC.

## Auth

| Method | Path | Purpose |
|---|---|---|
| POST | `/auth/login` | `{username, password, realm, otp?}` → sets cookie, returns `{user, caps}` |
| GET | `/auth/oidc/login` | (T-1207) start an OIDC SSO login: returns `{authorizationUrl, state}` for the SPA to navigate the browser to; PKCE verifier + nonce are held server-side. `404 not_found` when `[oidc]` is not configured. Public (no session yet). |
| POST | `/auth/oidc/callback` | (T-1207) complete the OIDC flow: `{code, state}` (from the IdP's redirect back to `[oidc] redirect_url`) → verifies the ID token, maps groups to a capability bundle capped at the linked PVE identity's ACLs, and on success sets the **same** session cookie `/auth/login` does, returning `{user, caps}` (`user.realm` = `"oidc"`). Public + CSRF-exempt (no cookie exists yet, exactly like `/auth/login`). `400 invalid_state` (unknown/expired state), `401 invalid_oidc_token` (token verification failed), `502 oidc_unreachable` (IdP/token-endpoint failure). |
| POST | `/auth/logout` | destroy session |
| GET | `/auth/me` | current user + capability flags `{caps: {netRead, netWrite, sdnRead, sdnWrite, fwRead, fwWrite, guestNet, audit, automation}}` per node — `automation` (T-1104) is always `false` here: it is never derived from a PVE privilege, only ever present on a bearer token's own minted scopes (see the Tokens section below) |
| GET | `/config` | (added by the Settings page; documented per docs/development.md's definition-of-done #4) the daemon's **non-secret** operational configuration for the Settings page's Instance section: `{version, listen, pveApiUrl, protectedPath, pveInterval, hostInterval, lldpInterval, confirmTimeoutDefaultSec, snapshotKeepDays, snapshotPinDays, readOnly, allowDangerousOps, metricsEnabled, hostSampler?}` — a read-only snapshot of `/etc/vnprox/vnprox.toml` values captured at daemon start. Session-gated (`netRead`). Deliberately excludes every secret/secret-bearing value (PVE token, session key, peer secret, TLS private key, dev ticket credentials, metrics scrape token) — see `internal/api/config.go`. Not runtime-editable (vnprox.toml is a per-node, restart-time file). `metricsEnabled` is T-1001's addition: whether `GET /metrics` is mounted on this node (`[metrics] enabled`, default true). `hostSampler` is T-1004's addition: which host-local flow sampler (`internal/flow/hostsample`) is active on this node — `"conntrack"`, `"ebpf"`, or omitted/empty when neither is configured (or eBPF was configured but its kernel-feature probe failed at startup with no conntrack fallback also enabled). |

## Inventory & topology

| Method | Path | Purpose |
|---|---|---|

| GET | `/inventory/{ref}` | full detail for one entity, including raw source (interfaces stanza / PVE API object) — see shape below |
| GET | `/inventory/search?q=` | fuzzy search across names, MACs, IPs, VMIDs, comments |
| GET | `/lldp` | all LLDP neighbors cluster-wide (fanned out to peers): `{items: [{ref, node, localIface, protocol, chassisName, chassisId, chassisIdType?, portId, portIdType?, portDescr?, mgmtIps?, pvid?, taggedVlans?, speedMbps?, speedDescr?, ttl?, lastSeen?}]}`. | GET | `/lldp/vlan-check` | VLAN cross-check findings (docs/features/lldp-discovery.md §2): `{items: [{bridgeRef, neighborRef, code, severity, message, expected: [string], advertised: [string], missing?: [int], extra?: [int]}]}`. `code` is one of `vlan_cross_check_ok`\|`vlan_cross_check_missing_on_switch`\|`vlan_cross_check_missing_on_bridge`. Added by T-302 (not in the original contract; documented here per docs/development.md's definition-of-done #4). |
| GET | `/ports` | flat ports table (docs/features/lldp-discovery.md §2): `{items: [{node, nic, switch, port, speedMbps?, speedDescr?, pvid?, taggedVlans?, lastSeen?, stale}]}`; `?format=csv` returns the same rows as `text/csv` (`Content-Disposition: attachment`) with columns `node,nic,switch,port,speedMbps,pvid,taggedVlans,lastSeen,stale`. `stale` is true once a neighbor has greyed (2×TTL) or aged past 10 minutes — dropped-from-map entries (docs/features/lldp-discovery.md §3) still appear here, tagged stale, for troubleshooting unplugged links. Added by T-302 (not in the original contract; documented here per docs/development.md's definition-of-done #4). |
| GET | `/fdb` | MAC/FDB browser (docs/features/lldp-discovery.md §4): `{items: [{node, bridge, bridgeRef, mac, port?, vlan?, master?, permanent?, stale, owner, ownerRef?, ownerLabel?, score?}]}`, cluster-wide. With no `?mac=`, every learned entry (sorted node/bridge/mac); with `?mac=<query>` (full or partial, separators optional), ranked partial-match results (`score` populated, exact > prefix > substring > fuzzy — same scoring as `/inventory/search`), capped at 50. `owner` is `guest` (`ownerRef` is the owning Guest's ref), `vnprox-known` (`ownerRef` is a PhysNic elsewhere in the cluster — a recognized infra MAC, not a guest), or `unknown` (no match — typically an external device on an uplink/trunk port). Added by T-306 (not in the original contract; documented here per docs/development.md's definition-of-done #4). |
| GET | `/drift` | cross-node consistency report: `[{check, severity, nodes, detail}]` |
| POST | `/drift/{id}/fix` | create a fixing changeset draft from a fixable finding's computed op patch → returns the changeset (same shape as `POST /changesets`); `404 not_found` if `id` no longer names a current, fixable finding |
| GET | `/findings` | T-602's unified findings stream, spanning drift + LLDP mismatch + IPAM conflicts + health checks: `{items: [Finding]}`. Optional `?source=&severity=&node=` filters, each independently optional and AND-combined (never a 400 for an unrecognized value — it just matches nothing for that filter). |
| POST | `/findings/{id}/fix` | same contract as `POST /drift/{id}/fix`, generalized across every producer: creates a fixing changeset draft from a fixable unified finding's computed op patch; `404 not_found` if `id` no longer names a current, fixable finding. Only drift-sourced findings have a computable fix today (bridge-property harmonization, MTU alignment); every other producer's findings are detection-only. |

**`GET /drift` finding shape** (added by T-305; documented here per docs/development.md's definition-of-done #4 — the base `{check, severity, nodes, detail}` fields are the original contract, `id`/`refs`/`fixable` are additive): `{id, check, severity, detail, nodes: [string], refs?: [string], fixable}`. `check` is one of `bridge_divergence`\|`mtu_consistency`\|`sdn_realization`\|`pending_interfaces`\|`file_runtime_divergence` (docs/features/topology.md §6's five original families) **or** `spec_drift` (T-1102's sixth, additional family — see below); `severity` is `error`\|`warning`\|`info`, reusing the changeset finding vocabulary. `id` is a stable key (derived from `check` plus the finding's affected refs/nodes, never random or time-based) — the same finding on an unchanged cluster keeps the same `id` across drift cycles. `fixable` is true iff `POST /drift/{id}/fix` will succeed for `id` right now (bridge-property harmonization, MTU alignment, and `spec_drift` are the check families with a computable fix as of T-1102; presence/SDN-realization/pending/file-vs-runtime findings are detection-only). Cluster-wide fan-out (peer nodes' own drift findings, mirroring `GET /audit`/`GET /snapshots`) is not yet implemented — today's response covers only this daemon's own view of the cluster-wide inventory graph, which is already complete for every node the PVE API and this daemon's own host poller can see (see `GET /topology`'s staleness note for the same host-poller-locality caveat).

**`spec_drift` (T-1102, docs/features/topology.md §6's "Pinned-spec drift mode").** A sixth check family, distinct from and additive to the five cross-node-consistency families above: it diffs live state against a **pinned** declarative spec (`GET/POST/DELETE /spec/pin` below) using T-1101's own `spec.Import(Spec, live)` diff engine, unchanged. One finding per diverging entity (`refs` names it, `nodes` its node) — never one finding for the whole spec — so the same entity can independently trigger a cross-node family (e.g. `mtu_consistency`) and `spec_drift` at once; they are always distinct `check` values, letting a consumer filter GitOps-vs-cluster drift independently. Since T-1101's spec covers only bond/bridge/vlan/sdn-zone/sdn-vnet/sdn-subnet (incl. DHCP ranges), `spec_drift` only ever fires for those six kinds — **firewall configuration has no spec-drift detection** in specVersion 1, matching T-1101's own scope (docs/data-model.md §6). `fixable: true`, computed the same way every other fixable family is: `POST /drift/{id}/fix` returns a **draft** changeset (`spec.Import`'s own op patch for that entity) reconciling it to the pinned spec — never auto-applied. No pin at all (nothing ever pinned, or unpinned via `DELETE /spec/pin`) means zero `spec_drift` findings; a stale/absent pin never blocks or alters any of the other five families.

**`GET /findings` finding shape** (T-602, docs/features/monitoring.md §5 — internal/findings.Finding): `{id, source, check, severity, detail, nodes: [string], refs?: [string], fixable, docsLink?}`. `source` is one of `drift`\|`lldp`\|`ipam`\|`health`\|`probe`\|`wireguard`\|`wan`\|`baseline` — which producer emitted the finding; `source: "wan"`'s own check is `wan_degraded` (T-1405, see the "WAN & upstream health" section below: one finding per node/uplink/external-reference-target whose rolling loss crosses `HealthThresholds.WanLossWarnPct` and holds; `refs` is empty — a WAN link has no `inventory.Ref` — `nodes` names the probing node only; `id` is `"wan:wan_degraded|<linkId>"`), `fixable: false`. `check` is that producer's own check name (drift's six families unchanged — the original five plus T-1102's `spec_drift`; Health checks apply hysteresis (debounce) before firing/clearing, so a finding's presence lags a raw threshold breach/clear by a few cycles, **except `mgmt_single_path`** (T-702), T-803's `orphan_vnet`/`evpn_gw_inconsistency`/`trunk_unused_vlans`, and T-1006's `fw_rule_unused` (structural config facts / already-N-day-smoothed signals, not noisy counters — see each check's own doc comment for the hysteresis-exempt rationale), which are hysteresis-exempt — see docs/features/monitoring.md §5 and internal/findings' health_*.go doc comments for each check's specific window.

**`source: "baseline"` — `new_port`\|`volume_spike`\|`new_subnet` (T-1601)**. `internal/baseline`-fed: a learned per-guest/per-segment traffic baseline (`baseline_profiles`, docs/data-model.md §2) deviated from by recent flows. `internal/baseline.Learn` computes each Ref's baseline over a learning window (top talkers, observed service-port set, observed peer-subnet set, per-hour-of-day byte-volume mean/stddev), and `internal/baseline.Detect` raises three deviation classes: `new_port` (a service — destination — port never seen while learning; ephemeral source ports are deliberately excluded), `volume_spike` (a wall-clock hour whose byte volume is ≥ a configurable multiple, default 10×, of that hour-of-day's baseline mean+stddev), and `new_subnet` (a peer `/24`/`/64` CIDR never observed while learning). **`GET /topology` staleness.** The response carries an optional top-level `staleness` object (omitted when the daemon has no collector status, e.g. collectors failed to initialize) describing how fresh the data behind the map is, per collector source — the feature spec's greyed-band + staleness-banner state (docs/features/topology.md §5):

```json
"staleness": {
  "stale": false,
  "sources": [
    {"name": "pve", "stale": false, "lastSuccess": 1720512345},
    {"name": "host", "node": "pve1", "stale": false, "lastSuccess": 1720512345},
    {"name": "host", "node": "pve2", "stale": false, "lastSuccess": 1720512340},
    {"name": "host", "node": "pve3", "stale": true, "lastSuccess": 1720512200, "lastError": "peer_unreachable"},
    {"name": "lldp", "node": "pve1", "stale": false, "lastSuccess": 1720512345}
  ]
}
```

- `name` is the collector loop: `pve` (all PVE-derived data, cluster-wide), `host` (netlink + interfaces-file data), `lldp`.
- `node` scopes the source to one cluster node's band; absent = cluster-wide. Since T-303 (documented here retroactively per that task's report note), `host` carries one entry **per cluster node** this daemon can reach — itself directly, every peer through the peer API (docs/architecture.md §1, §5) — so a single unreachable peer's band degrades independently (docs/features/topology.md §5's "greyed from last-known data with a staleness banner and timestamp") without affecting any other node's; `lldp` is still local-node-only pending T-302's own cluster-wide collection.
- `stale` per source flips true after 3 consecutive poll failures (≈ data 3 poll intervals old); top-level `stale` is true iff any source is stale. `lastSuccess` (unix seconds, omitted if no poll has ever succeeded) is the "data as of" timestamp for the banner; `lastError` (string, present while a source is failing) is the most recent poll error.

**`GET /inventory/{ref}` response shape.** `{ref, kind, node, label, fields, provenance, rawSource?, related, generatedAt}`:

- `fields` — the resolved entity's canonical fields (JSON object).
- `provenance` — per resolved field: `{"<field>": {"owner": "<source>", "conflicts": [{"source", "value"}]}}` (which source won the merge, and any dissenting values).
- `rawSource` — the raw source text behind the entity, keyed by contributing source name; omitted when no source retained raw text. Every value is a **string**: for `host-interfaces` the verbatim interfaces(5) stanza (byte-identical to the file); for `pve-network`/`pve-sdn`/`pve-guest`/`pve-firewall`/`pve-cluster` the pretty-printed JSON of the PVE API object; for `host-netlink`/`host-lldp` compact JSON of the observed state. Example: `"rawSource": {"host-interfaces": "auto vmbr0\niface vmbr0 inet static\n...", "pve-network": "{\n  \"iface\": \"vmbr0\", ...\n}"}`.
- `related` — edges incident to the entity: `[{ref, edgeKind, direction: "from"|"to"}]`.

Validation finding shape: `{severity: "error"|"warning"|"info", code, message, ref?, fix?}` where `fix` is an optional machine-applicable amendment (an `[]Op` patch the UI can offer one-click).

**Changeset provenance: `origin` + `originTokenId` (added by T-1701).** Every changeset response carries `origin` (`"ui"` \| `"mcp"` \| `"cli"`) and, for a token-staged one, `originTokenId` (the staging `api_tokens.id`). `origin` records who/what staged the changeset — an ordinary human edit through the SPA (`"ui"`, the default for every pre-T-1701 changeset), an AI operator through the MCP server (`"mcp"`, see the MCP-server section below), or a CLI (`"cli"`). It is set once at create and never mutated; the change engine's apply path is identical regardless of origin (a changeset is a changeset), so this is a provenance label the review UI badges, not a control-flow switch. An MCP-staged changeset is also attributed in the audit trail to actor `mcp:<token-name>`, so an operator can always tell an AI-staged draft from a human one.

**Management-path ceremony: `touchesMgmtPath` + the confirm-window floor (added by T-703).** Every changeset response (`POST`/`PUT`/`GET`/validate/apply/confirm/rollback) carries a server-computed boolean `touchesMgmtPath`: whether the changeset's ops intersect any node's resolved management path — the carrier refs plus every entity in their physical paths from `GET /protected-interfaces/status` (`change.TouchesMgmtPath`). It is computed over the same `MgmtStatus` the badges are painted from, so it is true for *any* changeset touching the path (hand-built drafts included, wizard or not) and false otherwise — never a client assertion. The review screen turns it into a mandatory acknowledgement block (a typed node-name confirmation). `POST /changesets/{id}/apply`'s body gains an optional `mgmtAck: {node}` — the typed acknowledgement, recorded to the audit log as `changeset.mgmt_ack` (with the originating user and node) when present. For a `touchesMgmtPath` changeset the commit-confirm window (`confirmTimeoutSec`) **defaults to and cannot be set below 180s** (`change.MgmtConfirmTimeoutFloor`): a lower value is rejected before any apply work with `400` and the stable code `confirm_window_too_short`, leaving the changeset in its pre-apply status. This is an *additive ceremony*, not an interlock override — T-203's safety class (`safety.protected_interface`) remains the enforcement backstop, and re-addressing the management IP stays out of scope (docs/security.md's "no override in UI" is unamended).

**Unattended-revert coverage: `unattendedRevert` (added by T-1805).** PVE firewall and SDN writes are performed with the *user's own* ticket (docs/architecture.md §6), so reverting them with no live session needs a credential the daemon does not otherwise have. Per `docs/roadmap-proven.md`'s decision **D1**, `POST /changesets/{id}/apply` seals the applying user's PVE ticket into the changeset row for the duration of the commit-confirm window, reverts with it, and wipes it the moment the changeset leaves `awaiting_confirm` by any path. The apply response — and a `GET /changesets/{id}` read of an `awaiting_confirm` changeset — carries the resulting coverage report:

```json
"unattendedRevert": {
  "required": true,
  "available": true,
  "coversUntil": 1785446605,
  "fullWindow": false,
  "reason": "your PVE session expires before the confirm window closes; after that point firewall/SDN changes will no longer revert automatically"
}
```

- `required` — does anything in this changeset need the user's PVE ticket to revert (`fw.*`, `sdn.*`)? When false the other fields are moot and `available` is true: node-file, WireGuard, QoS and switch-port reverts all run through daemon-level gateways and have always covered the whole window.
- `available` — was a ticket sealed successfully? False means the firewall/SDN portion of this changeset **will not** revert itself; `reason` says why (no PVE session credential at apply time, the daemon not configured for unattended revert, or the seal failing).
- `coversUntil` — unix instant past which unattended revert of the ticket-scoped portion stops being possible: `min(confirm deadline, PVE ticket expiry)`. Omitted when `available` is false.
- `fullWindow` — does `coversUntil` reach the confirm deadline? A `false` here with `available: true` is the reduced-coverage case: a timeout after `coversUntil` reverts the node-file portion but not the firewall/SDN portion. PVE tickets live ~2h, so this only arises for a long confirm window opened late in a session.

The field is **omitted entirely** outside the commit-confirm window, and it never carries credential material: `coversUntil` is a bound, and the sealed ticket has no representation in any changeset read model at all (a stronger guarantee than the `presharedKey` stripping above — there is nothing to strip). No route, MCP tool, or plugin capability can reach it; it is unsealable only from that one changeset's own revert path.

**Scheduled changesets & maintenance windows (added by T-1103).** Stage now, apply inside a later window, reusing T-205's Apply/Confirm/Rollback and T-304's per-node local-timer machinery completely unchanged — this feature only decides *when* apply starts.

- `POST /changesets/{id}/schedule` (netWrite + CSRF) `{windowStart, windowEnd, confirmTimeoutSec?, missedWindowPolicy?}` (both timestamps unix seconds) → `201` with the created schedule, `{changesetId, windowStart, windowEnd, confirmTimeoutSec, missedWindowPolicy, status, createdBy, createdAt, firedAt?, cancelledAt?, callbackToken}`. `callbackToken` is delivered **exactly once, in this response** — it is never persisted in plaintext and no other route ever returns it again (see the callback-token paragraph below). `confirmTimeoutSec` defaults to the same 120s `change.DefaultConfirmTimeout` every other apply uses; `missedWindowPolicy` defaults to `"skip"`. Rejects, before any persistence:
  - `422 mgmt_path_unattended_forbidden` when the changeset's `touchesMgmtPath` (computed fresh, exactly like every other route in this section) is true. **This is an unconditional, server-side-only gate: there is no config flag, request field, or `allowDangerousOps`-style override anywhere in the API or schema that bypasses it** — unlike the T-203 safety-interlock class, which `[safety] allow_dangerous_ops` can downgrade for an ordinary interactive apply, this check has no such escape hatch at all, matching docs/security.md's "no override in UI" stance on the underlying interlock and going one step further (no override *at all*, not even a config-file one, for the unattended-apply path specifically).
  - `422 validation_failed` (`details.findings`) when the changeset carries any error-severity finding, freshly recomputed (not the changeset's possibly-stale cached findings).
  - `422 bad_window` when `windowStart >= windowEnd`.
  - `422 invalid_missed_window_policy` when `missedWindowPolicy` is set to anything other than `"skip"`/`"applyImmediately"`.
  - `409 schedule_already_exists` when the changeset already has a pending (not yet fired/missed/cancelled) schedule.
- `DELETE /changesets/{id}/schedule` (netWrite + CSRF): cancels a pending schedule (audited `changeset.schedule_cancel`) → `204`. `404 not_found` if the changeset never had a schedule; `409 schedule_not_cancelable` if it already resolved (fired/missed/blocked/failed/cancelled).
- `POST /changesets/{id}/schedule/ack` `{token}`: the webhook ack path — **deliberately not session/CSRF-gated** (a webhook caller carries no browser cookie); auth is the token itself. On a valid, matching token this is exactly `POST /changesets/{id}/confirm` (same status transition, same audit trail) — see the callback-token paragraph. `401 invalid_callback_token` on a mismatch.

At `windowStart`, the scheduler (a supervised goroutine driven by an injected clock, `change.Service.RunScheduler`/`TickSchedules`) re-validates the changeset against current live state, **recomputes `touchesMgmtPath` fresh** (never the value from schedule time — aborting if now true), and applies with a commit-confirm deadline of `min(windowStart + confirmTimeoutSec, windowEnd)`, using T-304's existing per-node local-timer machinery completely unchanged: this feature decides when to start, T-205/T-304 own everything after. Any abort at fire time (mgmt-path newly true, a new blocking validation finding, no PVE session for an sdn/fw/ipam-carrying changeset, or the apply call itself failing) leaves the changeset in its pre-fire status with zero steps executed, and is audited `changeset.schedule_fire_blocked`; a clean fire is audited `changeset.schedule_fire`. Daemon-restart-safe: schedules persist in the `changeset_schedules` table and the scheduler re-evaluates every pending row against the current clock immediately on startup (mirroring `ArmPendingRollbacks`' own restart re-arm), so a window that elapsed while the daemon was down is resolved the moment it comes back, not silently skipped.

`missedWindowPolicy` governs a schedule the scheduler discovers only after its own `windowEnd` has already passed (the daemon was down through the whole window): `"skip"` (default) marks the row `schedule_missed`, audits `changeset.schedule_missed`, and raises a `schedule_missed` health finding (`GET /findings`, `source: "health"`, detection-only) naming the changeset — the operator decides whether to reschedule or apply by hand. `"applyImmediately"` fires right away with a freshly computed window (`now .. now+confirmTimeoutSec`), still fully `touchesMgmtPath`/validation-checked exactly like an on-time fire.

The single-use, changeset-scoped signed **callback token** (`POST /changesets/{id}/schedule/ack`'s auth) is an HMAC-SHA256 over the changeset id and `windowEnd`, minted at schedule time — the same construction style as the peer API's own HMAC (`internal/peer/sign.go`), not a general-purpose credential. Only a sha256 hash of it is ever persisted (`callback_token_hash`); the plaintext token exists only in the one `POST /changesets/{id}/schedule` response body that created it. "Single-use" falls out of the underlying state machine rather than needing its own bookkeeping: `AckSchedule` is exactly `Confirm`, which only succeeds while the changeset is `awaiting_confirm` — a replayed token (before the window even opens, or after the changeset already committed/rolled back) fails on that same state check every UI confirm click would.

**SDN apply orchestration (added by T-402; documented here retroactively per docs/development.md's definition-of-done #4).** A changeset carrying `sdn.zone/vnet/subnet.*` ops and a trailing `sdn.apply` renders a plan whose cluster-scope SDN steps (`kind: "sdn_stage"`, one per op) come first and whose `sdn_apply` step is always last (docs/data-model.md §3). Each `apply_log` step gains an optional `taskUpid` field: for the `sdn_apply` step, the PVE task's UPID, populated as soon as the task starts (even on failure) so the UI can deep-link to that task's log on its node (`node` on the same step entry). If the underlying `PUT /cluster/sdn` task itself succeeds but T-402's post-apply per-zone health check (`GET /cluster/sdn/zones/{zone}/status`) finds a member node unhealthy, `POST /changesets/{id}/apply` fails with a `422` and the stable code `sdn_zone_unhealthy`, `details: {zone, node, status, detail, taskUpid, taskNode}`. `POST /changesets/{id}/rollback` on an SDN-carrying changeset additionally reverts the SDN portion (pre-apply zone/vnet/subnet config diffed against current and re-applied) — this needs the requesting user's own PVE ticket exactly like apply does. **Amended by T-1805:** a rollback with no live session (the auto commit-confirm-timeout path, and crash recovery) no longer skips that portion — it uses the ticket sealed at apply time (`unattendedRevert` above). It skips only when no usable sealed ticket exists (none was captured, or it has since expired), in which case the un-reverted scopes are recorded as failed `apply_log.rollback` entries and the changeset lands in the distinguishable "rollback incomplete" state (`failed`, result `rollback_incomplete`) rather than a silent `rolled_back`. The same now holds for the `fw.*` portion, which before T-1805 was never reverted on **any** path beyond same-request rollback.

**Subnet gateway validation and `pve_session_required` (added by T-701; documented here retroactively per docs/development.md's definition-of-done #4).** Three new validation finding codes on `sdn.subnet.create`/`sdn.subnet.update`, plus one new `POST /changesets/{id}/apply` rejection code:
- `schema.gateway_not_in_subnet` (`severity: "error"`, schema class): the op's `gateway` is a syntactically valid IP but falls outside the subnet's own CIDR (`cidr` on create, the target's id — which *is* the CIDR, docs/data-model.md §3 — on update). Carries a `fix` setting `gateway` to the CIDR's first usable address.
- `sdn.snat_requires_gateway` (`severity: "error"`, sdn class): the subnet's *effective* state (this changeset's own net effect, e.g. a `sdn.subnet.create` with no gateway followed by a `sdn.subnet.update` enabling `snat` later in the same changeset) has `snat: true` with no gateway — real PVE's SubnetPlugin rejects this at subnet stage time. Carries the same first-usable-address `fix`.
- `sdn.evpn_gateway_missing` / `sdn.snat_requires_exit_node` (`severity: "warning"`, advisory class): an EVPN-zone subnet with no gateway (its anycast gateway is never realized on any node) or with `snat: true` while its zone's effective `exitNodes` is empty (SNAT traffic has nowhere to leave through) — real PVE accepts both shapes, but traffic through the subnet is silently broken, so these warn rather than block. No `fix` (there's no single obviously-correct value to set).
- `POST /changesets/{id}/apply` additionally fails fast, before any snapshot/mutation, with a `422` and the stable code `pve_session_required` when the changeset's plan carries any step that needs a live PVE session (`sdn_stage`/`sdn_apply`/`fw_apply`/`fw_verify`/`ipam_alloc`) and none resolved for the requesting user (an expired/unrenewable PVE ticket) — previously this case fell through into the executor and failed mid-apply with an opaque low-level error string instead.

**Cross-node consistency validation (added by T-801; documented here per docs/development.md's definition-of-done #4).** Validator class 4 (docs/features/change-management.md §2) folds the changeset's *projected* effect across **every** cluster node and compares same-named entities across nodes — the same comparisons `GET /drift`'s `bridge_divergence`/`mtu_consistency`/`sdn_realization` families run against *live* state (one shared implementation, `internal/xnode`), run here against the changeset's would-be state and raised to blocking **errors**. Three finding codes, each on a changeset that touches a bridge (`bridge.create`/`update`/`delete`, `bridge.port.add`/`remove`):
- `crossnode.bridge_divergence` (`severity: "error"`, cross-node class): a same-named bridge whose presence, VLAN-awareness, or VID set diverges across the projected cluster. Carries a `fix` (a `bridge.update` per dissenting node aligning it to the cluster majority) for the VLAN-awareness/VID-set forms; the presence form has no `fix` (creating a missing bridge needs a physical-port decision), mirroring `GET /drift`'s own fixable/not-fixable split.
- `crossnode.mtu_consistency` (`severity: "error"`, cross-node class): a same-named bridge whose MTU diverges across the projected cluster, with a `fix` aligning outlier nodes to the majority MTU.
- `crossnode.sdn_realization` (`severity: "error"`, cross-node class, detection-only): an SDN zone that, in the projected cluster, lists a member node whose realizing bridge does not exist there — the gap `sdn.bridge_missing_on_node` leaves, where a plain `bridge.delete`/`iface.rename` (no `sdn.*` op) silently breaks an *untouched* zone. No `fix` (creating the bridge needs a physical-port decision).

**Interface rename validation (added by issue #2; documented here retroactively per docs/development.md's definition-of-done #4).** The `iface.rename` op (a logical bridge/bond/vlan rename) adds three finding codes:
- `schema.iface_name_invalid` (`severity: "error"`, schema class): the new name is empty, longer than 15 characters (IFNAMSIZ-1), or contains anything but a leading alphanumeric followed by alphanumerics and `.-_`.
- `referential.rename_target_exists` (`severity: "error"`, referential class): the new name already names another interface on the same node (net-effect-aware).
- `safety.rename_guests_attached` (`severity: "error"`, safety class): the interface still has running guests attached to its old name in the changeset's final state — a rename rewrites `/etc/network/interfaces` but not PVE guest config, so those `bridge=` bindings would be orphaned. Cleared by reattaching each guest (a `guest.nic.update` to the new name) in the same changeset; downgraded to a warning under `AllowDangerousOps` like the other safety-class checks.

**SDN name and VNI validation (added by issue #3; documented here retroactively per docs/development.md's definition-of-done #4).** Two new validation finding codes, both catching shapes real PVE rejects at `sdn_stage` time with a "Parameter verification failed" 400:
- `schema.sdn_name_invalid` (`severity: "error"`, schema class): a `sdn.zone.create`/`sdn.vnet.create` whose id contains characters outside PVE's SDN id charset (case-insensitively `[a-z][a-z0-9]*` — a leading letter, then letters/digits, no hyphens/underscores/dots/whitespace). Charset only — the length cap PVE also enforces is a non-blocking wizard warning (`web/src/sdn/wizards/validation.ts`), not a finding, since the exact cap is unverified against live PVE (`planning/reports/needs-hardware-validation.md`). No `fix` (there's no single correct id to substitute).
- `sdn.vni_required` (`severity: "error"`, sdn class): a `sdn.vnet.create` (or a `sdn.vnet.update` that explicitly sets `tag`) whose *effective* zone is `vxlan`/`evpn` but whose effective `tag` (the VNI, for those zone types) is 0 — real PVE requires a VNI for a vxlan/evpn vnet. Zone-type-aware and net-effect-folded (a vnet and the vxlan/evpn zone giving it its type, created in the same changeset, are resolved together). No `fix`.

**`sdn.zone.create`/`sdn.zone.update` gain `exitNodes`/`peers` (added by T-403; documented here retroactively per docs/development.md's definition-of-done #4).** `exitNodes: [string]` (member-node names, EVPN zones' egress path — docs/features/sdn.md §2's "exit nodes, primary exit") and `peers: [string]` (underlay IP addresses, VXLAN/EVPN zones' VTEP mesh peers — docs/features/sdn.md §2's "peer address list auto-suggested from cluster node IPs") were readable on `GET /sdn`'s `Zone` shape since T-401 but had no changeset-op way to set them until this task — a real write-path gap the zone wizards surfaced (internal/pve.SDNZone and internal/pvemock's `SDNZoneSpec` already carried both fields on the wire). `exitNodes` is validated against known cluster nodes exactly like `nodes`; `peers` (addresses, not node names) is not. The EVPN zone wizard's "primary exit" concept is UI-only (the first entry of `exitNodes` by convention) — there is no separate `primaryExit` wire field.

**QoS & traffic shaping (added by T-1505).** A new `qos.shape.create`/`qos.shape.update`/`qos.shape.delete` op group (docs/data-model.md §3): a bridge-level tc/HTB traffic shape, staged/validated/applied/rolled back through this same changeset lifecycle — no second mutation path. Target is a `qos-shape` Ref (node-scoped, caller-chosen id). Params: `bridge` (required, the bridge this shape governs), `matchCidr`/`matchVlan` (optional — both absent means the shape governs the bridge's whole, otherwise-unclassified egress), `rateMbit` (required, positive), `ceilMbit`/`priority` (optional; `ceilMbit`, when set, must be `>= rateMbit`). **Per-guest-NIC rate limiting is not part of this group** — it already exists as `guest.nic.update`'s `rateMbps` field; this group's only new surface is bridge-level per-service shaping.

New validation finding codes: `schema.qos_rate_invalid` (`severity: "error"`, schema class — non-positive `rateMbit`/`ceilMbit`, or `ceilMbit < rateMbit`), `schema.qos_vlan_out_of_range` (`severity: "error"`, schema class — `matchVlan` outside `[1,4094]`), `referential.qos_bridge_not_found` (`severity: "error"`, referential class — `bridge` does not name a currently known bridge on the target's node). A `qos.shape.*` op whose `bridge` param names a node's resolved management/corosync path is `touchesMgmtPath` (see that ceremony's paragraph above) — a shape on the management/uplink bridge can starve or deprioritize mgmt/corosync traffic exactly as disruptively as an `iface.update` there, so it inherits the same mandatory-acknowledgement + 180s confirm-window floor, with no override.

`GET /qos/shapes` (netRead) lists every currently-stored shape: `{shapes: [{id, node, bridge, matchCidr?, matchVlan?, rateMbit, ceilMbit?, priority?}]}` — a read view onto the app-owned `qos_shapes` table (docs/data-model.md §2), never a live tc read. `GET /topology`'s node badges (docs/features/topology.md §3's vocabulary) gain a new token, `qos-shaped`, painted on every bridge node currently carrying an applied shape, additive to whatever other badges that node already has.

It drives the post-commit "update the protected list?" prompt (pre-filled from `GET /protected-interfaces/suggest`) and the stale-set warning in the inspector's Management path section.

**`GET /topology` management-path badges** (added by T-702, docs/features/topology.md §3): node badges gain three additional values, painted the same way the `"drift"` badge already is (a handler-level decoration over the pure projection, driven by the exact same computation `GET /protected-interfaces/status` answers from) — `mgmt` and `corosync` on a resolved ref's carrier node (its `roles`), `mgmt-path` on every entity in its resolved `path`. ## Capacity forecasting (T-1606)

Capacity forecasting trends link/segment utilization and IPAM pool consumption against a **downsampled** long-term history (the `capacity_aggregates` table, docs/data-model.md §2 — the network-intelligence arc's one deliberate retention extension) and raises `source: "capacity"` findings (`capacity_link_forecast`/`capacity_ipam_forecast`, see the finding-shape section above) when a growth curve is projected to cross capacity within `[capacity] forecast_horizon_days` (default 90). A daily supervised rollup job (`internal/capacity.RollupJob`) computes each UTC day's per-link average/peak utilization (from that day's `metric_samples` counter deltas against the link speed) and per-pool allocation percentage (from `internal/ipam`'s live counts) *before* the raw `metric_samples` 24h ring prunes them, so a learned trend outlives the raw samples it was summarized from. The aggregate table is explicitly bounded by `[capacity] aggregate_retention_days` (default 400, ~13 months) and pruned on the same tick-based cadence every other bounded table uses — never a raw-data warehouse.

The **export** below is the retention extension's required exportable path (design §6 rule 4): the full aggregate history for one ref, bounded to the same retention window (rows older than `aggregate_retention_days` are absent even between prune ticks), never a live-data dump.

| Method | Path | Purpose |
|---|---|---|
| GET | `/capacity/export?ref=<ref>&kind=link\|ipam_pool&format=csv\|json` | netRead-gated. `ref` is required and `kind` must be `link` or `ipam_pool` (`400 validation_failed` otherwise); `format` defaults to `json`, `csv` supported. Returns that ref's daily aggregate history bounded to `[capacity] aggregate_retention_days`. CSV: header `ref,kind,bucket_at,avg_utilization,max_utilization,created_at` (`bucket_at`/`created_at` unix seconds), `Content-Disposition: attachment`. JSON: `{ref, kind, aggregates: [{bucketAt, avgUtilization, maxUtilization, createdAt}]}`. |

Paginated list response envelope (`/snapshots`, `/audit` below): `{items: [...], nextCursor?: "<opaque>", partial?: boolean, failedNodes?: [string]}` — `nextCursor` is present iff there is a further page; pass it back verbatim as `?cursor=` to fetch it. An empty `?cursor=` (or omitted) starts from the newest item. Added by T-303 (retroactive doc note per that task's report): `partial`/`failedNodes` are cluster-fan-out fields (docs/architecture.md §7 — both tables are node-local app data, so a cluster-wide list re-queries every peer and merges the pages) — `partial` is present and `true` iff one or more peers (or peer discovery itself) could not be reached for this page, and `failedNodes` names them; both are omitted entirely on a fully-successful page, including every single-node deployment (zero peers) and every pre-T-303 caller's exact original response shape.

Snapshot shape (list item and, with an added `files` array, the `/snapshots/{id}` detail response): `{id, kind: "pre"|"post"|"manual"|"scheduled", changesetId?, note?, takenAt, nodes: [string], files?: [{node, path, sha256}]}` — file *content* is never inlined (it lives in the content-addressed, zstd-compressed blob store, deduplicated by sha256); fetch it via `/snapshots/diff`.

`/snapshots/diff` response: `{files: [{node, path, unified, changed}]}` — only entries with `changed: true` carry a non-empty `unified` diff (mirrors the changeset diff's `FileDiff` shape, minus the op summaries, since a snapshot diff is raw file state, not changeset ops).

## Audit

| Method | Path | Purpose |
|---|---|---|
| GET | `/audit?user=&action=&target=&result=&changesetId=&from=&to=&limit=&cursor=` | filtered, paginated audit log (docs/features/change-management.md §8) |

Requires the `audit` capability (viewing vnprox's own audit log), not `netRead`. Every filter param is optional and ANDed together; `from`/`to` are unix seconds, inclusive. Response: `{items: [{id, at, username, action, target?, changesetId?, result, detail?}], nextCursor?, partial?, failedNodes?}` (the last two per the pagination envelope note above) — `detail` is the action-specific structured detail object (e.g. `{"stepCount":3}`), opaque JSON. Every T-205 apply-engine lifecycle action (`changeset.apply`, `changeset.confirm`, `changeset.rollback`, `changeset.timer_rearm`, `changeset.recover`, `changeset.safety_override`) and this task's `snapshot.create` / `snapshot.restore` appear here; each row's `changesetId` (when present) links to that changeset and, transitively, its snapshots.

T-1301 adds `capture.start` / `capture.stop` to the action vocabulary: `target` is the captured entity's `Ref`, and `detail` carries the resolved filter and the effective (server-clamped) caps — `{sessionId, groupId, node, iface, filter, maxDurationSec, maxBytes, maxPackets, retentionHours}` — but **never any captured payload byte** (docs/security.md's Audit section).

T-1307 adds `diagnose.run`: one row per `POST /diagnose` call (see the Diagnosis section below), regardless of how many of the ladder's five steps actually ran — `target` is the diagnosed `targetRef`; `detail` is `{steps: {<stepName>: "ran"|"skipped"|"error"}, verdictConfidence, escalatedToCapture}`. `result` is `"error"` iff any step ended `StatusError`, `"ok"` otherwise (a step's own honest "could not attempt this" outcome is still `StatusRan`, so it does not flip `result`). Unlike `probe.verify`/`guest.interior_read` above, the ladder's own live-probe/guest-interior/conntrack steps do **not** each additionally audit themselves — the whole ladder run is audited exactly once, as a deliberate simplification (see `planning/reports/T-1307.md`).

Cluster fan-out (T-303): each node's audit log is node-local (docs/architecture.md §7), so `GET /audit` re-queries every reachable peer (via `GET /api/peer/audit` below) with the same filter/cursor/limit and merges the pages with the local one, newest-first, filtered per peer before merging (not fetched-then-filtered) — see the pagination envelope note for the `partial`/`failedNodes` fields this produces. A peer-supplied row is not otherwise distinguished from a local one in the response shape.

**`GET /sdn` response shape** (added by T-401; documented here per docs/development.md's definition-of-done #4 — the original contract was the one-line purpose above): `{zones: [Zone], generatedAt}`. `Zone` is `{id, type, bridge?, controller?, nodes?, exitNodes?, peers?, mtu?, vrfVxlan?, pending?, nodeStatus: [NodeStatus], pendingDiff?: PendingDiff, vnets: [Vnet]}`; `Vnet` is `{id, zone, alias?, tag?, vlanAware?, pending?, pendingDiff?: PendingDiff, subnets: [Subnet]}`; `Subnet` is `{id, vnet, cidr, gateway?, dhcpRangeStart?, dhcpRangeEnd?, snat?, pending?, pendingDiff?: PendingDiff}` (`id` is the CIDR, per docs/data-model.md's `SdnSubnet.ID` doc comment). `pending` mirrors PVE's own staged-edit marker (`""`\|`"new"`\|`"changed"`\|`"deleted"`).

`NodeStatus` is `{node, status, detail?}` — `status` is `"ok"`\|`"pending"`\|`"error"` (docs/features/sdn.md §1: "every level shows per-node realization status").

`PendingDiff` renders docs/features/sdn.md §1's "staged-vs-running as a first-class diff": `{state, changedFields?: [string], running?: {...}, staged?: {...}}`. `state` is `"new"`\|`"changed"`\|`"deleted"`; an in-sync object (`pending` is empty) carries no `pendingDiff` field at all — omitted entirely, not present-but-empty. `changedFields`/`running` are only populated for `state: "changed"` (a "new" object has nothing to diff against; a "deleted" object's fields haven't changed, only its existence is about to). `running`/`staged` are the two full objects (JSON-shaped, `id`/`pending` stripped) the UI renders the delta from.

`GET /sdn` reads PVE directly and live on every request (not the poll-cached inventory graph `GET /topology` renders) via `?running=1` on the underlying `GET /cluster/sdn/{zones,vnets,vnets/{v}/subnets}` calls — a mock-server-only extension (`internal/pvemock`) mirroring real PVE's own running-vs-pending query convention, added alongside this route so the staged-vs-running diff is never stale relative to what an apply would actually do. SDN configuration is cluster-scoped PVE data (replicated via pmxcfs), so the local node's own PVE API always has the complete view regardless of which node's vnproxd the browser is talking to — no peer fan-out.

**`GET /ipam/subnets` / `GET /ipam/subnets/{cidr}/allocations` response shapes** (added by T-405; documented here per docs/development.md's definition-of-done #4 — the original contract was the one-line purposes above). Gated on the `sdnRead` capability (there is no dedicated `ipamRead` flag in the documented `/auth/me` capability set — IPAM is an SDN-adjacent read view, and vnprox reads through PVE's own configured IPAM plugin transparently per docs/features/ipam.md §1); flagged here as the smallest reasonable extension where the contract didn't fully specify one.

`GET /ipam/subnets` → `{items: [Subnet], generatedAt}`. `Subnet` is `{cidr, zone?, vnet?, gateway?, node?, source: "sdn"|"bridge"|"external", readOnly?, dhcpEnabled?, total, allocated, observed, conflicts, utilization}` — one row per currently-configured SDN subnet (`source: "sdn"`, live from PVE), one row per detected non-SDN subnet derived from a bridge address (`source: "bridge"`, `readOnly: true`, `node` set to the node the bridge was observed on — docs/features/ipam.md §2), plus (T-1203) one row per app-owned external subnet record (`source: "external"`, `readOnly: true` — they carry no PVE-IPAM allocation set, so `allocated`/`observed` are 0; they are reserved/released only via the dedicated `/ipam/external-subnets` CRUD routes, never `ipam.alloc.*` ops). `allocated`/`observed` each count every address `GET .../allocations` would render with that source contributing (not a mutually-exclusive partition — an address both allocated and observed, e.g. a "both"-confidence cell, counts toward both); `utilization` is `allocated/total`.

**External subnets & bidirectional sync** (T-1203, docs/features/ipam.md §7). External subnets are app-owned intent — IP space Proxmox has no knowledge of (a physical LAN, an upstream transit range, a NetBox/phpIPAM-sourced prefix) — never a shadow copy of a PVE SDN subnet. Read the external-subnet reads on `sdnRead`; the mutations are `netWrite`+CSRF like every other write family.

`GET /ipam/external-subnets` → `{items: [ExternalSubnet]}`. `ExternalSubnet` is `{id, cidr, label?, source: "manual"|"netbox"|"phpipam", description?, createdBy, createdAt, updatedAt}` — `source` is provenance (distinct from `GET /ipam/subnets`' row-level `source`, whose external rows all render as `"external"`). `POST /ipam/external-subnets {cidr, label?, source?, description?}` → `201` with the created record (`cidr` canonicalized to its network form; a duplicate CIDR or malformed CIDR/source → `400 validation_failed`); audited `ipam.external_subnet_add`. `GET /ipam/external-subnets/{id}` → the record (`404 not_found` if gone). `PUT /ipam/external-subnets/{id}` → the updated record; audited `ipam.external_subnet_update`. `DELETE /ipam/external-subnets/{id}` → `204` (idempotent); audited `ipam.external_subnet_remove`. These routes are the ONLY way to read/write external subnets — there is deliberately no `ipam.external_subnet.*` (or `ipam.external_sync.*`) changeset op, because an external subnet is not a PVE SDN subnet (nothing in PVE to stage/apply).

`POST /ipam/external-sync/preview` → `SyncPlan` `{changes: [SyncChange], generatedAt}`, a pure dry-run of the NetBox/phpIPAM bridge diff (vnprox's own PVE-IPAM allocations vs. the external system's records) that NEVER writes. `SyncChange` is `{kind: "add"|"remove"|"conflict", ip, before?: {ip, hostname?}, after?: {ip, hostname?}}` — `add` (vnprox has it, external doesn't → apply would create it externally), `remove` (external has it, vnprox no longer allocates it → apply would delete it), `conflict` (both hold the address but disagree on its hostname → never auto-written, surfaced as a finding). `POST /ipam/external-sync/apply {confirm: true}` → `SyncResult` `{applied: [SyncRecordResult], generatedAt}` — applies the plan's adds/removes to the external system; `confirm` false/omitted → `400 validation_failed`, no write (the same explicit-confirm ceremony `POST /lldp/install` uses). Every applied write is audit-logged `ipam.external_sync` with `before`/`after` per record. External-IPAM writes sit outside `internal/change` (external IPAM is not Proxmox config) but mirror its stage/review/confirm/audit contract — see docs/features/ipam.md §7's design note. Both routes return `404 not_found` when no external-IPAM bridge is configured. The sync diff also feeds two new `source: "ipam"` `GET /findings` check values: `external_ipam_drift` (a pending add/remove) and `external_ipam_conflict` (a hostname disagreement on one address; `fixable: false`, `docsLink` set), joining the existing `duplicate_ip`/`observed_unallocated`/`allocated_dark` IPAM checks.

`GET /federation/ipam/conflicts` → `{items: [Conflict], partial, failedClusters: [string]}` (T-1203, netRead, backed by T-1201's aggregator fanning each attached cluster's configured SDN subnets out). The same or an overlapping CIDR allocated in two different clusters surfaces as one `Conflict` of the new `type: "cross_cluster_duplicate_subnet"`, reusing the existing `Conflict` shape with an added `clusters: [string]` cluster-pair field (the two cluster names). No overlap anywhere → empty `items`. An unreachable cluster is isolated exactly like the peer/cluster fan-out elsewhere: `partial: true`, `failedClusters` names it, the reachable clusters' conflicts are unaffected.

`GET /ipam/subnets/{cidr}/allocations[?block=][&format=csv]` → `{cidr, prefix, total, paged, blocks?: [BlockSummary], block?, cells?: [Cell], conflicts: [Conflict], readOnly?, generatedAt}`. For a subnet with <=256 addresses (a /24 or smaller), `paged` is `false` and `cells` carries every address in the subnet. For a larger subnet, the default (no `?block=`) response has `paged: true` with `blocks` (one summary per /24-sized — or, for IPv6, /120-sized — block) and no `cells`; passing `?block=<cidr>` (one of `blocks`' own `cidr` values) returns that one block's full `cells` instead, with `block` echoing the requested block. `?format=csv` returns `text/csv` (`Content-Disposition: attachment`) instead of JSON: one row per non-free address across the *whole* subnet regardless of paging (columns `ip,state,confidence,hostname,mac,vmid,sources`), not a literal dump of the address space.

`Cell` is `{ip, state, confidence?, hostname?, mac?, vmid?, guestRef?, sources?: [string]}`. `state` (docs/features/ipam.md §2's grid legend) is `"free"`\|`"allocated"`\|`"reserved"`\|`"observed"`\|`"gateway"`\|`"conflict"` — the cell's render color. `confidence` (docs/features/ipam.md §1's multi-source-merge label) is `"allocated"`\|`"observed"`\|`"both"`\|`"conflict"`, omitted for a free or pure-gateway cell — a related but distinct axis from `state`: e.g. an allocated-but-dark address (docs/features/ipam.md §2) renders `state: "conflict"` (it needs attention) while `confidence` stays `"allocated"` (it genuinely is PVE-IPAM-sourced only). `sources` lists which collector(s) contributed: `"pve-ipam"`, `"guest-agent"`, `"dhcp-lease"` (T-406), and `"neighbor"` (T-805: the ARP/peer-API enrichment source, `internal/neighbor.Service` — the last of the three enrichment sources documented in docs/features/ipam.md §1, now implemented). `BlockSummary` is `{cidr, total, allocated, observed, conflicts, utilization}`.

`Conflict` (docs/features/ipam.md §2: "Each conflict is a health finding with suggested resolution") is `{type, severity, ips: [string], message, suggestion, clusters?: [string]}`. `type` is `"duplicate_ip"` (two+ guests, or an IPAM record and reality, disagree about who owns an address), `"observed_unallocated"` (an address is actively in use with no IPAM reservation — a squatter), `"allocated_dark"` (an IPAM reservation whose VMID/MAC corresponds to no currently-known guest — a stale record), or (T-1203, `GET /federation/ipam/conflicts` only) `"cross_cluster_duplicate_subnet"` (the same or an overlapping CIDR configured in two attached clusters); `severity` mirrors the changeset finding vocabulary (`error`\|`warning`\|`info`). `clusters` is populated only for the cross-cluster type — the pair of cluster names that share the overlap — and omitted entirely for every intra-cluster conflict.

**`GET /ipam/subnets/{prefix}/v6-plan` response shape** (added by T-1404; same `sdnRead` gate). `{prefix, prefixLen, blockPrefixLen, totalBlocks, blocks: [V6PlanBlock], generatedAt}` — `prefix` is a delegated IPv6 prefix no more specific than `/64` (e.g. a `/56` or `/48` from an upstream ISP/RIR PD), `400 validation_failed` for a malformed/non-v6/over-specific prefix, or one that would enumerate more than 65536 `/64` blocks (a defensive cap against an absurdly large delegation). `V6PlanBlock`: `{cidr, vnet?, zone?, alias?, state}` — `state` is `"allocated"` (an already-configured SDN v6 subnet occupies this exact `/64` block), `"proposed"` (this plan assigns the block to a currently v4-only VNet that has no v6 subnet yet — `vnet`/`zone`/`alias` name the target, one block per target in ascending-CIDR order, VNets picked in ID order for a deterministic, reviewable proposal), or `"free"`. Read-only — this route never writes anything, and never issues a DHCPv6-PD request to any upstream device (the delegated prefix is operator-supplied in the request, not fetched from anywhere).

Like `GET /sdn`, both `/ipam/*` routes read PVE directly and live on every request (every configured IPAM plugin's current allocation set, via PVE's `/cluster/sdn/vnets/{vnet}/ips` write route for reserve/release — mock-server-only, mirrors real PVE's own vnet-scoped IPAM plugin API) plus the cluster's own inventory graph (for guest-agent-reported IPs and bridge-derived subnet detection), so a reserve/release apply is reflected immediately, never waiting on the next poll cycle.

**`GET /sdn/evpn/status` response shape** (added by T-404; documented here per docs/development.md's definition-of-done #4 — the original contract was the one-line purpose above): `{nodes: [NodeStatus], exitNodes: [ExitNodeHealth], findings: [Finding], generatedAt, partial?, failedNodes?}`.

`NodeStatus` (reusing the name but *not* the shape of `GET /sdn`'s own `NodeStatus` above — these are two distinct route-local types) is `{node, frrInstalled, routerId?, asn?, peers: [Peer], vnis: [VNI], error?}`. `frrInstalled` is `false` (with `peers`/`vnis` empty and `error` unset) for a node running no FRR daemon at all — the documented clean "no EVPN" case (docs/features/sdn.md §3), distinct from `error` being set (a real read/parse failure on a node that *does* run FRR, e.g. an unreachable peer). `Peer` is `{peerAddr, peerNode?, addressFamily?, state, stateReason?, remoteAs?, pfxRcd?, pfxSnt?, uptimeSecs?, flapTransitions?}` — one entry per distinct BGP neighbor address, preferring the `l2VpnEvpn` address-family observation when a peer negotiates more than one (the underlying TCP session is the same; EVPN is what this view is about). `state` is FRR's own FSM vocabulary (`Idle`\|`Connect`\|`Active`\|`OpenSent`\|`OpenConfirm`\|`Established`) — the peering matrix's node×peer color (`Established`→green, `Connect`/`Active`/`OpenSent`/`OpenConfirm`→amber, `Idle`→red); `stateReason` is FRR's parenthetical qualifier for a down session when present (e.g. `Idle (Admin)` renders as `state:"Idle", stateReason:"Admin"`) — the closest FRR's summary JSON comes to a "last error", surfaced as such in the session detail panel. `VNI` is `{vni, type, vxlanIf?, tenantVrf?, numMacs?, numArpNd?}`, `type` is `"L2"`\|`"L3"`.

`ExitNodeHealth` is `{zone, node, healthy, detail?}` — one entry per (EVPN zone, exit node) pair from `GET /sdn`'s own zone tree (docs/features/sdn.md §2's exit-node model): `healthy` is true iff the node has FRR installed and every one of its observed peer sessions is `Established`.

`Finding` is `{id, code, severity, node, peerAddr, detail}`, reusing `GET /drift`'s `{id, severity, detail}` finding vocabulary (`severity` is currently always `"warning"` for this route). `code` is `"evpn_bgp_flapping"`: a session whose observed state has changed 3+ times within a trailing 10-minute window (docs/features/sdn.md §3: "Flapping sessions raise a health finding") — `Peer.flapTransitions` is the same session's live transition count, so a UI can render both the raised finding and its current count. Flap detection needs repeated observations over time, which a single live snapshot can never show by itself: the backing `internal/evpn.Service` is long-lived within one daemon process and accumulates a short rolling per-session state history across calls to this route (poll it regularly, e.g. via the same interval-based refetch `GET /sdn` itself would use, for the finding to become and stay accurate).

`partial`/`failedNodes` mirror `GET /audit`/`GET /snapshots`' cluster-fan-out convention: `partial` is true iff peer discovery or an individual peer's FRR read failed (as opposed to that node cleanly reporting no FRR, which is `frrInstalled:false` with no failure at all); `failedNodes` names them. `GET /sdn/evpn/status` fans out across the cluster via the peer API (`GET /api/peer/host/frr/{bgp-summary,evpn-vni}` below) exactly like `internal/collect`'s host poller does for netlink/LLDP data — unlike `GET /sdn`, EVPN/BGP state is node-local FRR daemon state, not cluster-scoped PVE config, so it cannot be read from any single node's PVE API and does need this fan-out.

**`GET /sdn/dhcp?zone=` response shape** (added by T-406; documented here per docs/development.md's definition-of-done #4 — the original contract was the one-line purpose in docs/features/sdn.md §5). Gated on the same `sdnRead` capability `GET /ipam/*` uses: `{reservations: [Reservation], leases: [Lease], generatedAt}`. `?zone=` scopes both arrays to one SDN zone; omitted (or unknown) means "cluster-wide"/"none", respectively — never a 400.

`Reservation` is `{cidr, zone, vnet, ip, mac, hostname?, vmid?, guestRef?}` — one entry per MAC-bound PVE-IPAM allocation on a DHCP-enabled subnet (a subnet with `GET /sdn`'s `dhcpRangeStart`/`dhcpRangeEnd` set). This is **the same underlying PVE-IPAM record** `GET /ipam/subnets/{cidr}/allocations`' `Cell` renders as an allocated/reserved grid cell — docs/features/sdn.md §5's "Reservations are IPAM allocations (`ipam.alloc.create`) so the IPAM grid and DHCP stay one dataset" — not a second, independently-stored reservation list: creating one via `ipam.alloc.create` with a `mac` (docs/data-model.md §3) makes it appear here and in the IPAM grid from the same write; releasing it via `ipam.alloc.delete` removes it from both. `guestRef` is populated when the reservation's `mac` matches a currently-known `GuestNic` in the inventory graph, the empty string otherwise (e.g. a stale reservation for a decommissioned guest).

`Lease` is `{cidr, zone, vnet, ip, mac, hostname?, guestRef?}` — one entry per currently-active dnsmasq lease observed on any cluster node's DHCP-enabled subnet, parsed defensively from each node's raw lease-file content (`GET /api/peer/host/dhcp-leases` below; `internal/host.ParseDHCPLeases` skips and counts any malformed line rather than erroring the whole read). `guestRef` uses the same known-guest MAC correlation `Reservation.guestRef` does. Leases are read fresh on every request (no daemon-side cache), fanned out across every reachable cluster node exactly like `GET /sdn/evpn/status`'s FRR fan-out — poll this route on an interval (the SPA's DHCP tab does, every 30s) for a lease that just appeared/expired to show up, since dnsmasq's lease file changes independently of any vnprox changeset apply.

**`GET /firewall/rulesets?scope=` response shapes** (added by T-501; documented here per docs/development.md's definition-of-done #4 — netRead-gated, read-only). `scope` is `cluster`\|`node`\|`guest`.

- `scope=cluster`: one `RulesetView` — `{ref, scope, node?, enabled, defaultIn?, defaultOut?, rules: [RuleView], banners?: [Banner]}`. 404 `not_found` if the cluster firewall config has not been observed yet.
- `scope=node`: with `?node=<name>`, that node's `RulesetView`; without it, `{items: [RulesetView]}` — every node this daemon has observed a ruleset for (hierarchy navigation).
- `scope=guest`: with `?ref=<guest ref>` (a `guest:<node>:<vmid>` Ref triplet, URL-encoded), `{ruleset: RulesetView, resolved: ResolvedView}` — the guest's own raw ruleset plus its full resolved evaluation order in one payload; without `ref`, `{items: [RulesetView]}` (raw rulesets only, one per observed guest).
- Any other `scope` value: 400 `validation_failed`.

`RuleView`: `{pos, enabled, direction, action, proto?, source?, dest?, sport?, dport?, iface?, macro?, macroExpansion?, log?, comment?}` — mirrors `internal/inventory.FwRule` field-for-field; `macroExpansion` (`[{proto?, dport?}]`) is populated whenever `macro` names a macro this build's built-in catalog knows (docs/features/firewall.md §2's "expansion preview").

`Banner`: `{scope, message}` — the "Datacenter firewall is OFF: none of these rules are active" footgun warning (docs/features/firewall.md §2) and its cascaded node/guest-scope variants, computed by `internal/fw.ScopeBanners`. Present on every `RulesetView` (and, for guest scope, additionally on `ResolvedView.gates`) whenever some scope's own toggle — or an ancestor scope's — means none of that ruleset's rules are actually enforced.

`ResolvedView`: `{guest, active, gates?: [Banner], rules: [ResolvedRuleView], defaultIn: DefaultPolicy, defaultOut: DefaultPolicy}` — a guest's full effective evaluation order per docs/features/firewall.md §1 ("cluster rules → security groups → guest rules → default policies"), computed by `internal/fw.Resolve`. `active` is false iff some gate in `gates` makes every rule inert; `rules` is still populated in that case (transparency — the UI shows what's configured even when it's not enforced). `ResolvedRuleView`: `{origin, groupName?, rule: RuleView, pos}` where `origin` is `cluster`\|`group`\|`guest` (`group` when this entry came from a security group's own rule list, spliced in at the position a `"type":"group"` reference rule named it — `groupName` names it either way). `DefaultPolicy`: `{direction, policy, origin}` where `origin` additionally allows `default` (pve-firewall's own hardcoded fallback, DROP in/ACCEPT out, when neither the guest's own ruleset nor the cluster's set an explicit policy).

**`GET /firewall/objects` response shape** (added by T-501): `{aliases: [ObjectUsage], ipsets: [ObjectUsage], groups: [ObjectUsage], macros: [Macro]}`. `ObjectUsage`: `{kind, scope, name, comment?, count, referencedBy?: [{scope, ref, pos}]}` — `kind` is `alias`\|`ipset`\|`group`; `scope` is the scope the object is *defined* in (cluster-scope objects are referenceable from any rule anywhere; node-/guest-scope objects only from their own ruleset's rules — real pve-firewall's alias/ipset visibility rule); `count`/`referencedBy` are docs/features/firewall.md §2's "referenced by N rules — view" usage tracking, computed by `internal/fw.UsageCounts`. `Macro`: `{name, comment?, ports: [{proto?, dport?}]}` — the built-in service-macro catalog's expansion preview (a representative subset of pve-firewall's own macros, not exhaustive; see `internal/fw`'s `KnownMacros`).

**`GET /firewall/log` response shape** (added by T-505, docs/features/firewall.md §4; documented here per docs/development.md's definition-of-done #4 — netRead-gated, read-only). Every filter param is optional and ANDed together, mirroring `GET /audit`'s convention: `node` (exact match), `vmid` (positive integer), `direction` (`in`\|`out`), `action` (case-insensitive, e.g. `DROP`); `limit` defaults to 500. Response: `{items: [FwLogEntry], droppedTotal, unavailableNodes?}`. `items` is oldest-first (so it reads top-to-bottom the same way subsequent `firewall.log.batch` WS pushes append). `droppedTotal` is the cumulative count of lines the server-side rate cap has dropped since this daemon started (the storm indicator — see the WS section below); `unavailableNodes` (omitted when empty) names any cluster node whose most recent log fetch attempt failed, so the UI can flag that node's contribution as possibly stale/incomplete rather than silently under-reporting it.

`FwLogEntry`: `{seq, node, vmid, guestRef?, direction?, action?, proto?, source?, dest?, sport?, dport?, at?, raw, correlation: Correlation}`. `seq` is a server-assigned, strictly increasing sequence number (stable React key / de-dup id). `guestRef` (a `guest:<node>:<vmid>` Ref triplet) is present iff the line's chain was a recognized guest tap/veth chain. `at` (unix seconds) is omitted when the line's own timestamp could not be parsed. `raw` is the original log line verbatim.

`Correlation`: `{status, rule?: RuleRef, candidatePositions?: [int], reason?}`. `status` is one of `rule` (correlated — `rule` names the deep-link target), `default_policy` (matched a default-policy fallthrough, not a specific rule — by design, not a parsing failure), `ambiguous` (2+ rules match; `candidatePositions` lists their positions, informational only), `unmatched` (no rule matches, e.g. the ruleset changed since the line was logged), `unknown_chain` (not a recognized guest chain — node/cluster-scope log correlation is not evaluated, see `internal/fwlog`'s package doc comment), or `no_guest_data` (this daemon hasn't observed any firewall data for that guest yet). `reason` is a human-readable explanation, always present except for `status: "rule"`. `RuleRef`: `{guestRef, origin, groupName?, pos}` — `origin` is `cluster`\|`group`\|`guest` (mirrors `ResolvedRuleView.origin` above); deep-linking is by `guestRef`+`pos`+`origin` (never DOM position), so it survives the firewall rule-table UI's independent evolution.

Rule correlation is a best-effort heuristic (direction+action match against the guest's resolved evaluation order, narrowed by protocol/port when available), not a re-simulation of pve-firewall's actual evaluation (that is `internal/sim`'s job, T-503): real pve-firewall log lines do not embed a rule position at all (checked against the upstream `pve-firewall` source — see `internal/fwlog`'s package doc comment), contradicting this feature's original premise that "PVE logs include rule references in most drop/reject cases". Ambiguous or unmatched lines are always labeled honestly, never guessed.

**`GET /firewall/analytics?scope=&ref=&windowHours=` response shape** (added by T-1006, docs/features/firewall.md §4; documented here per docs/development.md's definition-of-done #4). Read-only aggregation over the exact same shared, cluster-merged log buffer `GET /firewall/log` serves (`internal/fwlog.Analyze`) — no new log-collection path, no new unbounded storage. `windowHours` (a positive integer; 400 `validation_failed` otherwise) defaults to 24 and governs `hitCounts`/`topBlocked`/`unusedRules` uniformly (one window, not three independent ones): a rule is "unused" iff it has zero hits within that same window. `scope=guest` (requiring `?ref=<guest ref>`, 400 `validation_failed` if omitted) narrows `hitCounts`/`unusedRules` to that one guest; `topBlocked` stays cluster-wide regardless of scope (a blocked source/destination isn't a per-guest concept the same way a rule is). Response: `{hitCounts: [RuleHitCount], topBlocked: TopBlocked, unusedRules: [UnusedRule]}`.

`RuleHitCount`: `{rule: RuleRef, hits, lastSeenAt?}` — `rule` reuses `GET /firewall/log`'s own `RuleRef` shape above (`{guestRef, origin, groupName?, pos}`); `lastSeenAt` (unix seconds) is omitted iff `hits` is 0 (never present with a zero count). `TopBlocked`: `{sources: [EndpointCount], destinations: [EndpointCount]}`, `EndpointCount`: `{value, count}` — the top (capped, currently 10) most frequent source/destination addresses among DROP/REJECT-actioned lines within the window, counted regardless of whether the line itself correlated to a specific rule (an ambiguous/unmatched DROP line still names a real blocked address). `UnusedRule`: `{rule: RuleRef, daysSinceLastHit}` — one entry per enabled rule currently reachable in some known guest's resolved evaluation order (`internal/fw.Resolve`) with zero hits inside the window; `daysSinceLastHit` is `-1` when the rule has no observed hit anywhere in the currently-retained log buffer at all (an honest "don't know" — its true history, if any, may simply have rotated out of the bounded ring — never fabricated as `0` or the window length), otherwise the whole number of days since its most recent hit (which may itself predate the window).

Rule-identity tracking survives a `fw.rule.move`: hit counts are computed by re-running `Correlate` fresh against the *current* resolved ruleset for every buffered line (not by trusting each line's own ingestion-time-cached correlation), so a rule's hit history follows it to its new position — see `internal/fwlog.Analyze`'s doc comment.

**`GET /firewall/effects?group=<name>` response shape** (added by T-502; docs/features/firewall.md §2 P1's "rule effects preview" for a security-group reference): `{group, guests: [Ref]}` — every guest ref (`guest:<node>:<vmid>`) whose resolved evaluation order actually splices in `group`'s own rules, computed by `internal/fw.MatchingGuests` (which calls the same `fw.Resolve` the guest resolved view uses). Given this build's documented cluster-cascade simplification (`internal/fw`'s `Resolve` doc comment: cluster rules apply directly to every guest's resolved view), a group referenced by the *cluster* ruleset matches every observed guest, not just ones that reference it themselves. `group` naming zero, or a nonexistent, group returns `{group, guests: []}` (200), not a 404 — "no matches" is itself the answer a preview needs. `group` missing from the query is 400 `validation_failed`. For a *guest-scope* group reference, the matching set is trivially that one guest — the UI computes that locally without calling this route.

## Edge & NAT cockpit (T-1403)

| Method | Path | Purpose |
|---|---|---|
| GET | `/edge/routes` | per-node default route(s) + additional/policy static routes |
| GET | `/edge/nat` | PVE-host masquerade/port-forward rules + PVE SDN simple-zone NAT, with a port-forward's target guest correlated (and flagged when powered off) |

Both routes are netRead-gated, accept no request body, and mount no `netWrite`-capable route at all — every mutation to NAT/route state flows through the ordinary `nat.*`/`route.static.*` changeset ops below, never a dedicated write route (docs/roadmap-universal.md's phase-14 safety note: "surfacing inbound exposure must not itself become a write path"). Both are thin adapters over a pure projection (`internal/edge`) parsing each cluster node's *current* interfaces-file content (the same read `GET /nodes/{node}/interfaces/raw` uses, `ChangesetService.ReadRawInterfaces` — no second interfaces-file read path) for `nat.*`/`route.static.*` rules, each recovered from its own generated lines' trailing marker comment (see `nat.*`/`route.*` below) — there is no separate store of a rule's state anywhere in vnprox.

**`GET /edge/routes` response shape**: `{defaultRoutes: [DefaultRoute], staticRoutes: [StaticRoute], generatedAt}`. `DefaultRoute`: `{node, iface, gateway}` — one entry per iface stanza carrying a non-empty `gateway` option (the same field `iface.update`'s `gateway` param writes; this route never invents a second way to represent a default gateway). `StaticRoute`: `{id, node, iface, destCidr, gateway, metric?, comment?}` — one entry per `route.static.*` rule.

**`GET /edge/nat` response shape**: `{masquerade: [Masquerade], portForwards: [PortForward], sdnSimpleZoneNat: [SDNSimpleZoneNAT], generatedAt}`. `Masquerade`: `{id, node, iface, sourceCidr, comment?}`. `PortForward`: `{id, node, iface, proto, extPort, intIp, intPort, comment?, targetGuestRef?, targetGuestPoweredOff?}` — `targetGuestRef`/`targetGuestPoweredOff` are populated when `intIp` correlates to a currently-known guest (via live PVE-IPAM allocation data, `internal/ipam.Service.AllAllocations`, the same source T-406's DHCP-range-overlap check reads); omitted/false when it doesn't (an external/unmanaged target, or simply no IPAM data for it — never guessed). `targetGuestPoweredOff: true` is this card's own exit-demo scenario: "the Edge layer showing exactly which ports the lab exposes to the internet — with one of them flagged as forwarding to a powered-off guest." `SDNSimpleZoneNAT`: `{zone, vnet, subnet, gateway?}` — one entry per PVE SDN *simple*-zone subnet with `snat: true`, already surfaced read-only via `GET /sdn`'s own `Subnet.snat` (docs/features/sdn.md §2); this route only re-shapes it into the Edge layer's own view, never a second source of truth for it.

**New op groups (docs/data-model.md §3 addition), applied via `NodeAgent`'s existing interfaces-file write path** (the same "vnprox writes the file it will re-read" pattern `iface.raw.replace` established, docs/features/change-management.md §7) as a `post-up`/`post-down` shell-command stanza pair appended to an *existing* iface stanza — never a second mutation mechanism, and a node's *default* gateway stays owned by `iface.update`'s own `gateway` field (this group only adds additional/policy routes and NAT rules alongside it):

- `nat.masquerade.create` — target `nat-rule:<node>:<id>` (id is caller-chosen, schema-checked: letters/digits/`.-_`, max 64 chars); params `{iface, sourceCidr, comment?}`. `nat.masquerade.delete` — no `update` (rotating a masquerade rule's shape is delete-and-recreate, so it is always two visible ops, never a silent overwrite).
- `nat.portforward.create/update/delete` — target `nat-rule:<node>:<id>`; create params `{iface, proto: "tcp"|"udp", extPort, intIp, intPort, comment?}`; update params are the same fields, all optional (a partial patch — the rule's currently-stored fields, recovered from its own marker, fill in whichever the request omits).
- `route.static.create/update/delete` — target `static-route:<node>:<id>`; create params `{iface, destCidr, gateway, metric?, comment?}`; update is the same partial-patch shape as `nat.portforward.update`.

**Validation.** Schema class: `sourceCidr`/`destCidr` valid CIDR, `gateway`/`intIp` valid IP, `proto` one of `tcp`\|`udp`, `extPort`/`intPort` in `[1,65535]`, `metric` non-negative, and every create op's target id non-empty and charset-valid (codes `schema.cidr_invalid`, `schema.ip_invalid`, `schema.nat_proto_invalid`, `schema.port_number_invalid`, `schema.edge_rule_id_invalid`). Referential class: `iface` must name a currently-known interface on the op's node (`referential.iface_not_found`); `route.static.create/update`'s `gateway` must fall inside some already-configured address's subnet on that node (`referential.route_gateway_unreachable` — the same failure a real `ip route add ... via <gw>` hits when no directly-connected interface can reach the nexthop), net-effect-aware (a `bridge.create` earlier in the same changeset that gives the node a matching address satisfies it).

## Ingress visibility (T-1406)

Read-only discovery of the reverse-proxy layer sitting between a port-forward and its actual backend — HAProxy, nginx, Caddy, or Traefik — via each vendor's own status/admin endpoint, and **only** for targets the operator explicitly added below. `internal/ingress`'s `IngressDiscoverer` interface (`Discover(ctx, Target) (ProxyState, error)`) is the seam Phase 17's plugin SDK (T-1702) is expected to make pluggable — a plugin registers an additional vendor `Kind` against the same `Registry` map without any change to the routes below. **Every discoverer implementation issues only HTTP GET requests against a configured target — never a mutating call, and never a target this table doesn't already contain** (no network-range scan exists anywhere in this package).

| Method | Path | Purpose |
|---|---|---|
| GET | `/ingress/targets` | list every configured discovery target (credential never echoed back) |
| POST | `/ingress/targets` | add a target: `{kind, address, credential?}` → `201` with the created target |
| DELETE | `/ingress/targets/{id}` | remove a target; `204` whether or not it previously existed |
| GET | `/ingress/status` | discover every target fresh, correlate discovered backends to known guest refs, and render any WAN → port-forward → proxy guest → backend guest chain that lines up |

`GET`/`POST`/`DELETE /ingress/targets` are `netRead`/`netWrite`+CSRF respectively, matching every other read/write route family in this doc. **`GET /ingress/status` is itself `netRead`-gated and accepts no request body** — it only ever calls `IngressDiscoverer.Discover` (GET-only against the target, see above) fresh on every request; nothing it returns is ever persisted as authoritative (docs/architecture.md §7's new-domain invariant carried forward from T-1401/T-1403/T-1404).

**`IngressTarget`**: `{id, kind: "haproxy"|"nginx"|"caddy"|"traefik", address, addedBy, addedAt, hasCredential}`. `address` is the target's own status/admin endpoint base URL (e.g. `http://10.0.0.5:8404` for an HAProxy stats page); `credential` (create-only, never returned) is an optional bearer-token/basic-auth secret some deployments put in front of a status endpoint, sent as `Authorization: Bearer <credential>` on every discovery call — encrypted at rest with the identical `internal/store.SessionCipher` AES-256-GCM primitive `sessions.pve_ticket_enc`/`alert_rules.target_secret_enc`/`wireguard_tunnels.private_key_enc` all use (not a second cipher).

**Per-vendor discovery** (`internal/ingress`, each a plain HTTP GET, no admin/mutation endpoint of any vendor is ever called):
- **HAProxy** — the classic `;csv` stats-page export (`stats enable`/`stats uri` in haproxy.cfg); server rows carry a dial address (HAProxy ≥2.0's `addr` column) when the deployment's stats page reports one, else the bare server name.
- **nginx** — auto-detected per response: nginx Plus's JSON `/api/<ver>/http/upstreams` (per-backend `server`/`state`, used for guest correlation) or open-source nginx's plain-text `stub_status` block (aggregate connection counters only, no backend list — a target speaking only this format is reported reachable with zero backends).
- **Caddy** — the admin API's own `GET /reverse_proxy/upstreams` (currently active upstreams + live fail counters).
- **Traefik** — the API's own `GET /api/http/services` (every configured HTTP service's load-balancer servers + enabled/disabled status).

**`GET /ingress/status` response shape**: `{targets: [TargetStatus], chains: [Chain], generatedAt}`. `TargetStatus`: `{id, kind, address, reachable, error?, backends: [Backend]}` — `reachable: false` with a human-readable `error` is a normal, expected outcome (a down/misconfigured proxy), never an API error. `Backend`: `{route?, address, guestRef?, healthy}` — `guestRef` is populated when `address`'s host correlates to a currently-known guest via the same IPAM-allocation-based lookup `GET /edge/nat`'s `targetGuestRef` uses (T-1406 AC2); omitted when it doesn't (an external/unmanaged backend, or simply no IPAM data for it — never guessed). `Chain`: `{portForwardId, node, proto, extPort, proxyGuestRef?, targetId, targetKind, backends: [Backend]}` — one entry per `GET /edge/nat` port-forward whose `intIp` matches a configured `ingress_targets` row's own address, drawing the full WAN → port-forward → proxy guest (`proxyGuestRef`, from `GET /edge/nat`'s own port-forward → guest correlation) → backend guest (`backends[].guestRef`) chain; a port-forward with no matching `ingress_targets` entry produces no `Chain` — this route only ever draws a chain the operator's own configuration actually lines up, never an inferred one.

## Path simulator

| Method | Path | Purpose |
|---|---|---|
| POST | `/simulate/path` | `{src: EndpointSpec, dst: EndpointSpec, proto, port, family?}` → `SimulateResult` where `EndpointSpec` is a guest NIC ref, an IP literal, or "external" |

**Response shapes** (added by T-503; netRead-gated — a read-only static analysis over the poll-cached inventory snapshot, it mutates nothing). Documented here per docs/development.md's definition-of-done #4 (the route's one-line purpose above didn't pin a schema).

- `EndpointSpec`: `{kind, ref?, ip?}` — `kind` is `guest-nic`\|`ip`\|`external`. `ref` (a `guest-nic:<node>:<vmid>/<key>` Ref triplet) is required for `guest-nic`; `ip` (a literal address) is required for `ip`; `external` needs neither.
- `proto` is `tcp`\|`udp`\|`icmp`\|omitted (any); `port` is the destination port (omit/0 = any).
- `family` (T-1404, additive): `"v4"`\|`"v6"`, omitted defaults to `"v4"` — backward compatible, `SimulateResult`'s shape is unchanged. Governs which address family a `guest-nic` endpoint resolves to when more than one is known (see below), and which of a dual-stack VNet's subnets an IP-unknown `guest-nic` endpoint's L3/hop reasoning anchors to. A literal `ip` endpoint's family is self-evident from the address itself and ignores this field. A dual-stack check is two calls, one per family, compared by the caller — this route never itself compares them (see `dualstack_drift` below for the one continuously-computed comparison this task does add).
- `SimulateResult`: `{verdict, src, dst, proto?, port?, hops: [Hop], blockingRule?, missing?, caveats: [Caveat]}`.
  - **`verdict`** is `allow`\|`deny`\|`unreachable`\|**`indeterminate`**. *Flagged deviation from the original one-liner:* T-503 adds `indeterminate` because the spec's honesty contract (docs/features/firewall.md §6, AC5) forbids a confident allow/deny/unreachable when the engine could not fully evaluate the path — an unknown/unsupported entity kind, an unresolvable firewall alias/ipset/macro, or a firewall decision that would depend on a guest IP the inventory does not carry. An `indeterminate` result always carries at least one `blocker`-severity caveat explaining why, and the UI (T-504) must surface it as "could not determine", never as a pass/fail.
  - `src`/`dst` (`ResolvedEndpoint`): `{kind, ref?, guest?, node?, ip?, ipSource?, attachment?, vid?, zone?, vnet?, subnet?, description?}` — how the engine resolved each endpoint. `ipSource` is `literal`\|`static`\|`ipam`\|`guest-agent`\|omitted (unknown).
  - `Hop`: `{ref?, kind, node?, label, detail?}` — one step of the traced path (guest NIC → bridge/VNet → fabric/overlay/router/exit-node/gateway → …), for T-504's map rendering. `ref` is an inventory Ref string where the hop is a real entity, else a synthetic id (`external`, a fabric segment).
  - `blockingRule` (present only for `deny`): `{enforcementPoint, rulesetRef, origin, groupName?, direction, action, pos, rule}` — `enforcementPoint` is `source-guest-out`\|`dest-guest-in`; `origin` is `cluster`\|`group`\|`guest`; `rule` is a `RuleView` (same shape as `GET /firewall/rulesets`, macro expansion included) for the editor deep-link.
  - `missing` (present only for `unreachable`): `{code, message, atRef?, atNode?}` — `message` is the operator-facing break description (e.g. `"VLAN 30 is not trunked on bond0 of node pve2"`, `"no route between subnets … — different zones without exit node"`).
  - `Caveat`: `{code, severity, message, feature?}` — the honesty-contract disclosures (docs/features/firewall.md §5/§6), **always present** (every result carries at least the standing "simulated"/conntrack/guest-internal-firewall notes). `severity` is `info`\|`warning`\|`blocker`; `code` includes `simulated`, `conntrack`, `snat-asymmetry`, `guest-agent-ip`, `guest-ip-unknown`, `not-evaluated`, `fw-cluster-host-guest-simplification`, `node-firewall-not-on-path`, `ovs-l2`, `lldp-trunk-cross-check`, and (T-1505) `qos-shaped`. `feature` names the un-evaluated PVE/SDN feature for `code: not-evaluated`.

The engine is pure (`internal/sim`, no I/O) and reuses `internal/fw.Resolve` (T-501) as its firewall substrate; the API layer passes the live `*inventory.Graph`'s snapshot. Guest IPs (IPAM allocations) are supplied to the engine when a `GuestInteriorIPAMSource` is wired (T-1404, the same `AllAllocations` read T-1304's guest-interior IPAM cross-check already uses, correlated to guest NICs by MAC) — both a `guest-nic` endpoint's v4 and v6 known addresses are made available, and `family` (above) selects which one a given request resolves to; a daemon with no IPAM read wired (or a NIC whose MAC matches no allocation) still resolves that endpoint's IP unknown, the same honesty-contract degradation as before this task — any firewall rule that restricts by address then yields `indeterminate` with a `guest-ip-unknown` caveat. Guest-agent-reported IPs are still not carried into this route (a documented follow-up, unchanged by this task).

**Shape-awareness (added by T-1505).** The engine also gains an optional `ShapedRefs` input (`internal/sim.Input.ShapedRefs`, sourced by the API layer from the app-owned `qos_shapes` table via `GET /qos/shapes`' same read seam) naming every bridge Ref currently carrying an applied `qos.shape`. A hop crossing such a bridge adds an `info`-severity `qos-shaped` caveat — disclosed, not silently ignored, and never a blocker: a shape changes a path's *throughput*, not its *reachability*, so it never downgrades `allow` to anything else. A path that crosses the same shaped bridge at more than one hop still surfaces exactly one `qos-shaped` caveat (the existing caveat dedup-by-code+message behavior).

### Live path probe (T-802, T-806)

| Method | Path | Purpose |
|---|---|---|
| POST | `/simulate/verify` | `{src: EndpointSpec, dst: EndpointSpec, proto, port, family?}` (same request shape as `/simulate/path`, `src` restricted to `guest-nic`) → `{simulated: SimulateResult, observed: Observed, diverges}` |
| GET | `/simulate/verify/eligibility?ref=` | T-806: can `POST /simulate/verify` actually run for this `guest-nic` ref right now → `{eligible: bool, reason?}` |

docs/features/firewall.md §5's "verify live" P2 item: runs the identical `src→dst/proto/port` tuple through both the static path simulator (`simulated`, byte-identical to `/simulate/path`'s own result) and a real, explicit ICMP/TCP probe executed *inside* the source guest via the QEMU guest agent (`observed`) — a diagnostic action, never a network-config mutation, but one that reaches into a guest, so unlike `/simulate/path` it is audited. Gated on the same `netRead` capability as `/simulate/path` (both are read/diagnostic routes); nil `ProbeClientProvider` (no live PVE session support wired) simply omits this route, the same degraded-mode treatment every other optional dependency gets.

- `src` must be `kind: "guest-nic"` — only a guest can host a live probe (an `ip`/`external` src has nothing to exec inside); any other kind is `400 validation_failed`. The named guest NIC must resolve to a **qemu** guest (`AgentExec` is qemu-only, mirroring `GetGuestAgentInterfaces`' existing precedent — no LXC guest-agent equivalent); an LXC (or unresolvable) src is also `400 validation_failed`.
- `proto` must be `tcp`\|`icmp` (unlike `/simulate/path`'s `tcp`\|`udp`\|`icmp`\|omitted-any — a live probe needs one concrete, executable action); `port` is required (>0) for `tcp`. Anything else is `400 validation_failed`.
- `family` (T-1404) governs the `simulated` half exactly like `/simulate/path`'s own `family` field. The `observed` half's live probe follows whichever address the resolved `family` picks (guest-agent-reported interfaces are filtered to the matching family, falling back the same way `bestAgentIPv4` already did for v4); **needs hardware validation** for v6 (`planning/reports/needs-hardware-validation.md`) — the in-guest probe command's IPv6 behavior across guest OS/toolchains is not verified against a live cluster, mirroring this route's existing v4-only needs-hardware-validation note.
- `dst` accepts the same three kinds as `/simulate/path`. An `ip` endpoint's literal address is probed directly. A `guest-nic` endpoint's target address is resolved **live** (never from the inventory graph, which does not carry guest IPs) via that destination guest's own QEMU guest-agent-reported interfaces — the same source `GetGuestAgentInterfaces`/T-405's enrichment already reads — preferring the address on the interface whose hardware address matches the named NIC, falling back to the first reported IPv4 address. `external` has no concrete host to probe; like an unresolvable `guest-nic` dst, it yields `observed.outcome: "error"` rather than a 400 (the request itself was valid — the probe just couldn't be attempted, see below).
- No live PVE session available for the request → `422 pve_session_required` (mirrors T-701's `changeset.apply` code for the same underlying condition).
- `Observed`: `{outcome, detail?, execError?}`. `outcome` is `reachable`\|`unreachable`\|`timeout`\|`error` (`internal/probe.Outcome`) — `reachable`/`unreachable` are a completed probe's genuine result (ICMP reply/no-reply, TCP connect succeeded/refused); `timeout` means the probe did not complete within the bounded poll deadline (`internal/probe.DefaultTimeout`, 5s); `error` means the probe could not be attempted or classified at all (guest agent unreachable, exec transport failure, unresolvable dst) — the honesty-contract "no claim" bucket, never conflated with a genuine `unreachable`. `execError` is set (non-empty) iff `outcome: "error"`; `detail` is a human-readable context string, populated for every other outcome. A guest whose QEMU guest agent isn't reachable answers `200` with `outcome: "error"` and `execError` set — never a `5xx` — "the attempt itself is the answer" (docs/features/firewall.md §6's honesty contract applied to a live probe).
- `diverges` is `true` iff `simulated.verdict` makes a confident reachability claim (`allow`\|`deny`\|`unreachable`) that disagrees with `observed.outcome`: `allow` disagrees with anything but `reachable`; `deny`/`unreachable` disagree with `reachable`. An `indeterminate` `simulated.verdict` or an `observed.outcome: "error"` never diverges — neither one makes a claim to contradict.
- Audited as `probe.verify` (target: the src guest NIC ref; `detail`: `{proto, port, simulatedVerdict, observedOutcome, diverges}`) — every request that passes input validation produces exactly one `audit_log` row, `result: "ok"` unless `observed.outcome: "error"` (`result: "error"`); a malformed/invalid request (400/422) is not audited, matching every other route in this package.
- The probe engine (`internal/probe`, not pure — unlike `internal/sim`, it performs real PVE API I/O) wraps `internal/pve`'s `AgentExec`/`AgentExecStatus` (`POST`/`GET .../agent/exec[-status]`). The exact in-guest command per guest OS/toolchain is **needs hardware validation** (`planning/reports/needs-hardware-validation.md`) — the engine implements one deliberately narrow target profile (a Linux guest with iputils-ping/netcat-openbsd) rather than guessing a "portable" command.
- `POST /simulate/verify` with `diverges: true` persists one `sim_divergence` finding (`source: "probe"`, see the `GET /findings` section above and docs/data-model.md §5) — upserted by the exact tuple's content-derived id (re-verifying the identical tuple never accumulates duplicates), cleared automatically when the identical tuple is re-verified and no longer diverges. Persisted (survives a daemon restart), unlike every other producer's findings, which are recomputed fresh from polled state on each `GET /findings` call.

**`GET /simulate/verify/eligibility?ref=`** (T-806, additive to T-802's contract — not itself a probe, no audit row): backs the "Verify live" button's grey-out gating (docs/features/firewall.md §5) without running the honesty-contract-laden ICMP/TCP probe just to answer "could this even be attempted". `ref` must be a valid `guest-nic` Ref (`kind:node:id`); malformed/missing → `400 validation_failed`. No live PVE session available → `422 pve_session_required` (same code as `/simulate/verify` for the identical underlying condition). Response: `{eligible: bool, reason?}` — `reason` (omitted when `eligible: true`) is `not-qemu` (the ref resolves, but not to a qemu guest — mirrors `/simulate/verify`'s own 400 for this case, but this route answers 200 since the *ref itself* was valid) or `agent-unreachable` (a qemu guest whose QEMU guest agent doesn't answer a transport-level ping — `internal/pve.Client.AgentPing`, `POST /nodes/{node}/qemu/{vmid}/agent/ping`, deliberately independent of `GetGuestAgentInterfaces`, which can legitimately report zero interfaces for a guest with a perfectly reachable agent but no configured network). Mounted only when `ProbeClients` is wired, same nil-safety as `/simulate/verify`.

## Microsegmentation (T-1602)

| Method | Path | Body → Result |
|---|---|---|
| POST | `/microseg/propose` | `{guestRef}` → `Proposal` |
| POST | `/microseg/dry-run` | `{guestRef, heldOut?}` → `DryRunReport` |

The microsegmentation planner (`internal/microseg`) computes, from a guest's observed flows, the **minimal** firewall policy that preserves observed-good traffic ("these N rules cover 30 days of traffic; everything else was noise"), and dry-runs that policy to report which observed-good flows a would-be enforcement would have blocked. Both routes are **`netRead`-gated** and read-only: they only READ flows + firewall state and COMPUTE a proposal — nothing here mutates or stages. The proposal PROPOSES; a human reviews and applies it through the ordinary changeset flow (T-1603's review UX). No new op type: staging emits ordinary `fw.rule.create` ops (docs/data-model.md §3's existing `fw.*` group).

**`Proposal`** (`POST /microseg/propose`): `{guestRef, rulesetRef, directions: ["in"|"out"], rules: [FwRule], stagedOps: [Op], coveragePct, observedGoodBytes, coveredBytes, observedGoodFlowCount, uncoveredFlowCount, excludedAnomalyFlows, alreadyCoveredGroups}`. `rules` is the ordered minimal policy — the ACCEPT allow-list followed by one trailing match-all deny (`DROP`) per governed direction, so the whole default-deny policy is expressible as `fw.rule.create` ops alone (`stagedOps`, ready to hand into the ChangesetDrawer). `coveragePct`/`uncoveredFlowCount` are the honesty fields: the exact fraction of observed-good **bytes** the rules cover (default threshold 99.5%) and how many observed-good flows fall in the deliberately-uncovered long tail — **never rounded up to "covers everything"**. `excludedAnomalyFlows` counts flows dropped from observed-good because T-1601's baseline detector flagged them (a transient compromise inside the training window can never legitimize itself into an allow rule). `alreadyCoveredGroups` counts groups suppressed because the guest's current firewall already accepts them.

**`DryRunReport`** (`POST /microseg/dry-run`): `{guestRef, wouldAllow: [FlowRef], wouldBlock: [FlowRef], cannotDetermine: [FlowRef], ungoverned: [FlowRef], coveragePct}`, where `FlowRef` is `{direction, proto, port, peerIp, peerSubnet, at, bytes, reason?}`. Each replayed flow lands in exactly one bucket, decided by `internal/sim`'s **own** firewall evaluator (the same rule-walk `POST /simulate/path` uses — never a second, divergent evaluator). A `wouldBlock` flow that was observed-good is the **would-have-blocked** signal the review UI surfaces before anyone enforces. Upholding the simulator's honesty contract (docs/features/firewall.md §5/§6, "no silent approximation"), a flow the evaluator cannot prove permitted is reported in `cannotDetermine` (with `reason`), **never** folded into `wouldAllow`. `ungoverned` holds flows in a direction the proposal does not govern (the policy changes nothing for them). `heldOut: true` replays a trailing held-out window (excluded from the training window the proposal was learned over) rather than the training corpus itself — an independent soundness proof point. All buckets serialize as `[]`, never `null`.

## IPv6 (T-1404)

Promotes IPv6 from "addresses render correctly" to a managed capability (docs/features/sdn.md §6): RA/SLAAC/DHCPv6 visibility per segment, a `dualstack_drift` finding catching the classic silent failure (v4 works, v6 is broken), and an IPv6 planning grid in IPAM (documented in the Firewall/SDN/IPAM section above, `GET /ipam/subnets/{prefix}/v6-plan`). The path simulator's `family` field and the latency mesh's per-family probing are documented in their own sections above/below — this section covers only the new `GET /ipv6/segments` read view.

| Method | Path | Purpose |
|---|---|---|
| GET | `/ipv6/segments` | per-VLAN/VNet RA/SLAAC/DHCPv6 visibility, cluster-wide |

**`GET /ipv6/segments`** (`netRead`-gated, not `sdnRead` — RA/DHCPv6 observation is host-local diagnostic data, the same gate `GET /conntrack`/`GET /latmesh/heatmap` use, not SDN config itself). Response: `{items: [Segment], generatedAt, partial?, failedNodes?}` — the same `partial`/`failedNodes` cluster-fan-out convention `GET /sdn/evpn/status` uses (one node's RA read failing never blanks every other node's).

`Segment`: `{ref?, node, iface, kind?, vnet?, zone?, vid?, raPresent, managedFlag?, otherFlag?, prefixes?: [string], routerLifetimeSec?, dhcpv6ServerPresent?, dhcpv6InferredFromRA?}`. `kind` is `"bridge"`\|`"vnet"`\|omitted (the interface doesn't currently correlate to a known Bridge/SdnVnet entity — still rendered, since the RA observation itself is real regardless); `ref` is that entity's inventory Ref when `kind` is set. `raPresent` is always `true` for an entry in `items` — an interface with **no** RA observed at all (the v6-broken symptom) simply produces no entry, never a fabricated `raPresent: false` row. `managedFlag`/`otherFlag` are the RA's M/O flags (RFC 4861 §4.2); `prefixes` are the RA's advertised on-link prefixes (CIDR form); `routerLifetimeSec` is the RA's own lifetime field.

`dhcpv6ServerPresent`/`dhcpv6InferredFromRA`: **documented inference limitation** — vnprox has no independent way to confirm a DHCPv6 server actually answers on a segment without completing a real DHCPv6 SOLICIT/ADVERTISE exchange as a client (out of scope for a bounded, read-only observation, the same "read, never write/probe-as-a-client" boundary this phase's WAN/upstream and reverse-proxy surfaces draw). `dhcpv6ServerPresent` is therefore *inferred* from `managedFlag` (M=1 implies a DHCPv6 server is expected); `dhcpv6InferredFromRA` is always `true` when `dhcpv6ServerPresent` is `true`, so the UI renders "expected (from RA M-flag)" rather than a bare confirmed/not-confirmed boolean. **Needs hardware validation** (`planning/reports/needs-hardware-validation.md`): a real cluster could legitimately advertise M=1 while transiently having no DHCPv6 server reachable.

Sourced the same way LLDP is: a bounded, host-local observation (`internal/host.Reader.IPv6RA`, real implementation solicits one RA per bridge/VLAN interface via `rdisc6 -1 -w <timeoutMs> <iface>`, fixed argv, never shell-interpolated — **needs hardware validation**, `ndisc6` is not installed on a stock Debian/PVE host by default) fanned out cluster-wide via the peer API (`GET /api/peer/host/ipv6-ra`, documented in the Peer API section below), correlated to each node's own Bridge/SdnVnet entities by interface name (PVE realizes an SDN VNet as a same-named bridge on every node it's deployed to).

DHCPv6-PD from an upstream device vnprox doesn't manage is surfaced through this exact same route (a segment's RA simply looks the same whether the answering DHCPv6 server is vnprox-managed or upstream) — read-only, visibility only; no route or op anywhere lets vnprox write a DHCPv6-PD request to an upstream device (regression-tested, see this task's completion report).

**`dualstack_drift` finding** (`source: "health"`, see the `GET /findings` finding shape section above): for every SDN VNet that carries both a v4 and a v6 subnet each with a configured gateway (a dual-stack VNet), `internal/sim` simulates that VNet's own path to external once per family from the subnet's gateway address; a finding fires when the v4 simulation is `allow` and the v6 simulation is `deny`\|`unreachable`\|`indeterminate` — the identical-tuple, per-family comparison the classic silent dual-stack failure needs, with both verdicts named in `detail`. Never `fixable` (a routing/SNAT gap on one family is a config decision, not a computable patch); `refs` names both subnets' Refs; structural, hysteresis-exempt like `orphan_vnet` (re-derived fresh from current SDN config every cycle, nothing to debounce). A healthy dual-stack VNet, or a v4-only one, raises nothing.

## Guest interior (T-1304)

| Method | Path | Purpose |
|---|---|---|
| GET | `/guests/{ref}/interior-toggle` | current opt-in state for this guest's interior inspector → `{ref, enabled}` |
| PUT | `/guests/{ref}/interior-toggle` | `{enabled}` → flips the opt-in → `{ref, enabled}` |
| GET | `/guests/{ref}/interior` | the guest's own inside network view (opt-in, off by default) |

`ref` is a `guest:<node>:<vmid>` Ref triplet (`internal/inventory.KindGuest`) — not a `guest-nic` ref; the map's own presence for a guest is its NIC entity (docs/features/topology.md), so the frontend's InteriorTab resolves the owning guest ref from the selected NIC's `Guest` field, or from a direct guest-kind search/inventory result.

All three routes are `netRead`-gated with no CSRF requirement, the same "personal/team UI preference, not a network-config mutation" precedent the Saved views & annotations section above documents — flipping the toggle itself never reaches into a guest. `GET /guests/{ref}/interior` does reach into a guest (or a peer node, for an lxc container), so it is additionally gated on `AuthService` implementing `UsernameLookup` (mounted only then, mirroring `POST /simulate/verify`'s own requirement) and audited as `guest.interior_read` (target: the guest ref; no `detail` — see below); the toggle routes are not audited (matching `annotations`'/`layouts`' own convention).

**The opt-in toggle** (`internal/store`'s `guest_interior_toggles` table, docs/data-model.md §2): one row per guest that has ever been toggled, off by default for a guest with no row at all. A `GET /guests/{ref}/interior` while the toggle is off answers `404 interior_not_enabled` — the read is never silently attempted just because a client asked for it.

**`GET /guests/{ref}/interior` response**: `{interfaces, addresses, routes, dns, listeningSockets, defaultGatewayReachable, source, ipamDiff}`.

- `source` is `"qemu-ga"` (read via the QEMU guest agent, reusing T-802's `AgentExec`/`AgentExecStatus`/`GetGuestAgentInterfaces` seam — qemu-only, same precedent as the live path probe above) or `"lxc-host"` (a container has no guest agent, so the read happens directly from the host side — locally via `internal/host.Reader.ContainerInterior`/`ContainerPing`, or via the peer routes above when the guest's node is not this daemon's own).
- `interfaces`: `[{name, mac?, mtu?, up}]`.
- `addresses`: `[{interface, ip, family: "ipv4"|"ipv6", prefix?}]`.
- `routes`: `[{destination, gateway?, dev?, metric?}]` — `destination` is `"default"` or a CIDR.
- `dns`: `{nameservers?: [string], searchDomains?: [string]}`, parsed from `/etc/resolv.conf`.
- `listeningSockets`: `[{proto: "tcp"|"udp", localAddr, localPort}]`.
- `defaultGatewayReachable`: a best-effort ping from inside the guest (qemu: `internal/probe.Run`, the same icmp probe the live path probe uses; lxc: a single ping issued inside the container's netns) toward the routing table's own default gateway — `false` both when there is no default route to test and when the ping itself did not succeed; unlike `internal/probe.Outcome`, this route does not distinguish "no reply" from "could not attempt" for this one field, since the response has no error-detail slot for it (a deliberate simplification over the live path probe's own honesty-contract-modeled `Observed`, noted in T-1304's completion report).
- `ipamDiff`: `[{ip, claimed, allocated, matches}]`, one entry per guest-claimed address (`addresses` above), cross-checked against `internal/ipam`'s resolved allocation set (the same "observed, never authoritative" confidence-labeling contract docs/features/ipam.md §1 already applies to guest-agent-reported IPs) — `claimed` is always `true` (this list only ever holds addresses the guest itself claimed); `allocated` is whether IPAM has a matching allocation record for that exact address; `matches` is `claimed && allocated`. Never a write to IPAM — the seam this route reads through (`AllAllocations`) has no write method at all.

A qemu guest whose read could not even be attempted (no live PVE session, guest agent unreachable) or an lxc guest whose node is unreachable (locally or via every peer route) answers `503 interior_unavailable` — the request itself was valid, the dependency needed to answer it isn't available right now.

**Needs hardware validation** (`planning/reports/needs-hardware-validation.md`): the exact in-guest/in-container command set (`ip -j addr show`, `ip -j route show`, `cat /etc/resolv.conf`, `ss -H -tuln`) per guest OS/toolchain, and the lxc pid-resolution mechanism (`/sys/fs/cgroup/lxc/<vmid>/cgroup.procs`) — both follow T-802's own "one deliberately narrow target profile, not a portable guess" precedent (`internal/probe/command.go`).

### Metrics exporter (T-1001)

`GET /metrics` — a Prometheus/OpenMetrics-compatible **text exposition** endpoint (`Content-Type: text/plain; version=0.0.4; charset=utf-8`), promoted from docs/features/monitoring.md §4's P2 note. This is an export surface only: it renders data `internal/metrics.Sampler` and `internal/findings.Engine` already compute, with no new collection logic. Unlike `GET /metrics/live`/`GET /metrics/history` above, this route:

- is **not** session/CSRF-gated — see "Auth" below, the one documented exception to this doc's Conventions section;
- exports the sampler's **raw, cumulative per-ref counters**, not pre-computed rates (Prometheus does its own `rate()`/`increase()` across scrapes);
- is node-local only (no peer fan-out) — a cluster-wide view is a Prometheus federation/multi-target-scrape concern, not something vnproxd computes itself.

**Auth.** Two gates, both required, checked in this order (a request failing the first never reaches the second):

1. **Source-CIDR allowlist** (optional): `[metrics] allow_from` in `vnprox.toml`, a list of CIDRs. Unset (default) allows any source. A source outside every listed CIDR gets `403 forbidden` — checked *before* the token, so a misconfigured-network case reads as "wrong network," not "bad token."
2. **Scrape token**: `Authorization: Bearer <token>` compared against the daemon's own token file with `crypto/subtle.ConstantTimeCompare`. A missing or invalid token is `401 not_authenticated` with the standard `{"error":...}` envelope — the same envelope every other route in this doc uses, so a scraper's failure still parses like every other API error.

See docs/security.md's Authentication section for where the token comes from and its on-disk format.

## Flows

Added by T-1002 (`internal/flow`): sFlow v5, NetFlow v5/v9, and IPFIX ingestion into a bounded, per-node SQLite ring (`flow_samples`, docs/data-model.md §2) — **not a long-term warehouse**; see that table's own doc comment for the enforced bound (a retention-window prune and a hard row cap, whichever is smaller, prunes first). Every protocol listener is off by default and enabled per node via `vnprox.toml`'s `[flows]` section (`sflow_enabled`/`netflow_enabled`/`ipfix_enabled`), matching T-1004's own opt-in convention.

T-1004 (`internal/flow/hostsample`) adds two more, equally opt-in, `[flows]`-configured sources for nodes with no external sFlow/NetFlow/IPFIX exporter pointed at them — both feed the exact same `flow_samples` ring above, tagged `source: "conntrack"` (no second storage path): `conntrack_sampling_enabled` (periodic `/proc/net/nf_conntrack` poll-and-diff, works with the capabilities `vnproxd` already holds) and `ebpf_sampling_enabled` (higher-fidelity per-bridge eBPF sampling, gated by a runtime kernel-feature probe — CAP_BPF/CAP_PERFMON + a BTF-capable kernel — that logs why and falls back to conntrack-only when it fails; docs/security.md's Host footprint section documents the extra capability this flag grants the systemd unit at install/upgrade time, never unconditionally). Both share `host_sample_interval_sec` (default 10 — coarser than the live UDP listeners above by design). `GET /config`'s Settings payload surfaces which sampler (if any) is active as `hostSampler`.

| Method | Path | Purpose |
|---|---|---|
| GET | `/flows?guest=&vlan=&subnet=&port=&protocol=&fromTs=&toTs=&limit=&cursor=` | paginated, cluster-wide flow record query |

**`flow.Record`** (the shape both `GET /flows`' `items` and the `flow.batch` WS event's `entries` carry): `{at, node, srcIp, dstIp, srcPort?, dstPort?, proto, bytes, packets, vlan?, srcRef?, dstRef?, ingressIfIndex?, egressIfIndex?, source, serviceClass?}`. `at` is unix seconds (the datagram's own reported timestamp for NetFlow/IPFIX; the listener's receive time for sFlow, which carries no wall-clock timestamp of its own). `proto` is the IP protocol number (6=tcp, 17=udp, 1=icmp, ...). `source` is `"sflow"`\|`"netflow5"`\|`"netflow9"`\|`"ipfix"`\|`"conntrack"` (the last reserved for T-1004's host-local sampler). `srcRef`/`dstRef` are inventory `Ref` strings, populated only when `srcIp`/`dstIp` resolves against a known bridge address CIDR or SDN subnet in the live inventory graph (`internal/flow.GraphResolver`) — left unset otherwise, **never guessed**. Guest-NIC-level resolution is a known, documented gap: `internal/inventory.Graph` does not carry guest IP addresses at all (the same limitation `POST /simulate/path`'s `guest-ip-unknown` caveat already discloses), so a resolved ref is always a Bridge or SdnVnet ref, never a GuestNic ref, however precisely an address matches a known subnet.

**`serviceClass`** (T-1504, `internal/flow.Classifier`): `"migration"`\|`"backup"`\|`"ceph-public"`\|`"ceph-cluster"`\|`"corosync"`\|`"unclassified"` — service-network attribution computed from a record's own metadata only (IP/CIDR containment against a registered network declaration, an exact known address, VLAN — **never payload inspection**, this is not an IDS). Omitted entirely (not `"unclassified"`) when the daemon has no `internal/flow.Classifier` wired at all (no `RegisterNetworkSource` call has ever registered anything); present as `"unclassified"` when a classifier is wired but no registered `NetworkSource` matched this record. `RegisterNetworkSource(kind, source)` is the classifier's own extension point: this task registers corosync's configured ring addresses (`internal/host.CorosyncConfig`); T-1503 (Ceph awareness) registers Ceph's public/cluster CIDRs the same way, tagging `"ceph-public"`/`"ceph-cluster"`; a declared PVE migration-network CIDR classifies `"migration"` once one is registered (no live reader of PVE's own `datacenter.cfg` `migration: network=` exists in this codebase yet — a repeatedly-documented gap, see `planning/reports/needs-hardware-validation.md`); a PBS backup-path address set classifies `"backup"` (`internal/flow.NewBackupPathSource`) — a declared-but-inert seam until T-1206 (PBS network awareness, Phase 12, not yet landed) discovers real PBS host addresses to register. T-1507 (migration planner) consumes `"migration"`-classified volume directly (headroom = link capacity minus current migration traffic) — no second migration-traffic detector. History playback (`web/src/topology/history/HistoryTimeline.tsx`'s scrubber, see the History section below) replays this exact field: it re-queries `GET /flows` with a `fromTs`/`toTs` window, so a classified flow's `serviceClass` is visible identically whether viewed live or scrubbed into the past.

Every filter param is optional and ANDed together, mirroring `GET /audit`'s convention (an unrecognized/unparsable filter value — e.g. a malformed `subnet` CIDR, or a `protocol` naming neither a known name like `"tcp"` nor a valid number — matches nothing, never a `400`). `guest` matches either `srcRef` or `dstRef` exactly; `subnet` (CIDR) matches either `srcIp` or `dstIp` within it; `port` matches either `srcPort` or `dstPort`; `protocol` accepts either a name (`tcp`, `udp`, `icmp`, `icmpv6`, `sctp`) or a raw IP protocol number; `vlan`/`fromTs`/`toTs` match `vlan`/`at` exactly/inclusively. `limit` defaults to 100, capped at 500.

`GET /flows` fans out to every reachable cluster peer via `GET /api/peer/flows` (below) and merges, following the `GET /audit`/`GET /snapshots` `partial`/`failedNodes` pagination envelope exactly (docs/architecture.md §7: `flow_samples` is node-local app data, so a cluster-wide view re-queries every peer and merges the pages) — response: `{items: [flow.Record], nextCursor?, partial?, failedNodes?}`.

## Latency mesh

Added by T-1303 (`internal/latmesh`): continuous, low-rate ICMP probes between every pair of cluster nodes this daemon's own node shares a fabric with, persisted into a bounded, per-node SQLite ring (`latency_samples`, docs/data-model.md §2) — **not a long-term warehouse**, same retention-window-AND-hard-row-cap bound `flow_samples` uses (`[latmesh]` in `vnprox.toml`: `probe_interval_sec` default 10, `retention_minutes` default 60, `max_rows` default 500,000). Unlike `[flows]`'s per-protocol opt-in listeners, latency-mesh probing is always on — a low-rate outbound probe carries no listening-port attack surface to gate behind an opt-in flag.

**Fabric scope** (flagged deviation from `docs/features/monitoring.md` §5's "corosync, migration, storage, guest" wish list): this task concretely identifies exactly two of those four fabrics — `corosync` (from `internal/host.CorosyncConfig`'s existing ring-address reader, the same substrate T-803's `corosync_link_degraded` check already reads) and `guest` (every bridge name shared by two or more cluster nodes, `internal/xnode.BridgesByName`'s existing cross-node grouping, labeled per bridge name). Neither a migration network nor a distinct storage network is modeled anywhere in `internal/inventory`/`internal/pve` yet (no `datacenter.cfg` `migration: network=` reader exists) — adding readers for either is a documented follow-up, not guessed at here; see `internal/latmesh`'s package doc comment and this task's completion report.

**Per-family probing on the guest fabric** (T-1404, docs/features/monitoring.md §1's "Extended by T-1404" note — "v4 and v6 probes run independently on any dual-stack-capable segment"): `discoverGuestPairs` emits one `Pair` per address family a shared bridge carries on both nodes, not one `Pair` per bridge regardless of family — a dual-stack bridge's two families get two distinct `LinkID`s (family suffixed into the label, `"guest:vmbr0-v4|pve1->pve2"`/`"guest:vmbr0-v6|pve1->pve2"`), each with its own independently-retained, independently-probed bounded-ring history. A single-family bridge keeps the pre-T-1404 bare-label `LinkID` unchanged (no breaking change for an existing v4-only deployment); a bridge with no address data at all (or mismatched families across the two nodes) keeps the pre-existing address-less fallback pair. The corosync fabric is unaffected — a ring carries one address, never split. No schema change: `latency_samples` already keys uniquely by `LinkID`, which is what makes two families' samples independent for free.

**Cluster scope (node-local only)**: a link's probe always originates at *this* node (`internal/latmesh.DiscoverPairs`'s `localNode` parameter) — the full cluster mesh is the union of every node's own outbound pairs (node A probes A→B, node B separately and independently probes B→A), not one node coordinating every other over the peer API. `GET /latmesh/heatmap`/`GET /latmesh/history` below are therefore **node-local only, no peer fan-out** — the same documented scope `GET /metrics` (the Prometheus exporter) and T-803's `corosync_link_degraded` check already carry; a cluster-wide merged view needs a new peer route, left as a follow-up (this task's card context docs named no Peer API section).

| Method | Path | Purpose |
|---|---|---|
| GET | `/latmesh/heatmap` | current + rolling per-link latency/loss status for every link this node originates |
| GET | `/latmesh/history?linkId=&fromTs=&toTs=` | one link's raw sample history (the inspector sparkline's data source, T-908 pattern) |

**`GET /latmesh/heatmap`** response: `{items: [LatMeshLink]}`. `LatMeshLink`: `{linkId, fabric, fromNode, toNode, at, rttMs, lossPct, rollingRttMs, rollingLossPct, sampleCount}`. `linkId` is `internal/latmesh.Pair.LinkID`'s stable, content-derived key (`"<fabric>[:<label>]|<fromNode>-><toNode>"`, e.g. `"corosync:ring0|pve1->pve2"` or `"guest:vmbr0|pve1->pve3"`) — globally unique per directed link, never random. `fabric` is `"corosync"`\|`"guest"`. `at`/`rttMs`/`lossPct` are the single most recent probe tick's own values; `rollingRttMs`/`rollingLossPct`/`sampleCount` are the mean over the configured rolling window (`internal/latmesh.DefaultRollingWindow`, 5 minutes) — what the `path_latency_degraded`/`path_loss` health checks below actually key on, since a single noisy tick is never enough to fire a finding. A node this daemon has never successfully discovered a pair for (no shared fabric, or not yet clustered) simply has no entries — never an error.

**`GET /latmesh/history`** response: `{linkId, items: [{at, rttMs, lossPct}]}`, ascending by `at`. `linkId` is required (`400 validation_failed` if omitted); `fromTs`/`toTs` default to "no bound on that side" when omitted/unparsable, matching `GET /metrics/history`'s convention.

**`Baseline(linkId) (p50, p95 RttMs, LossPct)`** (`internal/latmesh.Service.Baseline`, not a route — a Go function T-806's verify-live UX can call to caption an observed live-probe result against the mesh's own rolling baseline for the same path): p50/p95 round-trip time and mean loss% over every retained sample for `linkId`, computed with the nearest-rank percentile method (hand-verifiable, never interpolated). Wiring this into `POST /simulate/verify`'s response is a documented follow-up, not this task's own work (no `POST /simulate/verify` shape change ships with this task).

**Findings**: `path_latency_degraded`/`path_loss` (source `health`, see the `GET /findings` finding shape section above and `docs/features/monitoring.md` §5) — one finding per link whose *rolling* RTT/loss crosses a threshold (80ms / 2%, `internal/findings.HealthThresholds`' `LatRttWarnMs`/`LatLossWarnPct`) and holds for 3 consecutive Engine cycles (clearing after 2 consecutive cycles back under threshold — the same hysteresis window `error_drop_rate` uses). Never `fixable` (no changeset op can fix a physically degraded path); `id` is `"health:<check>|<linkId>"`.

## Path MTU prober (T-1306)

Added by T-1306 (`internal/mtuprobe`): active per-path MTU discovery — a binary-search sweep of DF-set (Don't Fragment) ICMP probes converging on the largest packet size a path actually carries end-to-end — built directly on T-1303's latency-mesh infrastructure above, not a second scheduler or a second path-discovery mechanism: `Service.Config.Discoverer` is the exact same `internal/latmesh.GraphDiscoverer` instance the latency mesh itself uses (so this prober reaches exactly the paths the mesh already knows about), and `Service.RunLoop` calls `internal/latmesh.RunTicker`, the identical shared scheduler primitive `latmesh.Service.RunLoop`/`RunPruneLoop` themselves call. Runs on its own, much coarser cadence (`[mtuprobe] probe_interval_sec` in `vnprox.toml`, default 300 — MTU rarely changes, unlike latency/loss) than latency probing's default 10s. Always on, same as `[latmesh]` (a low-rate outbound DF-probe carries no listening-port attack surface to gate behind an opt-in flag).

**Current-state only, not a ring**: unlike `latency_samples`, there is no new SQLite table here — `Service.Results`/`Result` hold only each link's most recently verified MTU in memory (no history/rolling-stats use case a rarely-changing value needs). A daemon restart loses the last reading until the next probe tick re-establishes it; a probe attempt that fails to even run (transport error, not "too big for this path") leaves the prior good reading in place rather than clearing it to a stale zero — a link this node has never successfully probed simply has no entry at all.

| Method | Path | Purpose |
|---|---|---|
| GET | `/mtuprobe/results` | every currently-known verified per-link MTU reading this node has probed |

**`GET /mtuprobe/results`** response: `{items: [MTUProbeResult]}`. `MTUProbeResult`: `{linkId, fabric, fromNode, toNode, mtu, at, probeCount}` — `linkId`/`fabric`/`fromNode`/`toNode` are the exact same `internal/latmesh.Pair.LinkID`-keyed identity `GET /latmesh/heatmap` uses for the same path, so a caller can correlate a link's latency reading and its verified MTU reading by `linkId`. `mtu` is the binary search's converged path MTU; `at` is the unix-seconds timestamp of the probe that produced it; `probeCount` is how many DF-probes that convergence took (bounded — `internal/mtuprobe.BinarySearchMTU`'s doc comment documents the exact bound: at most `ceil(log2(hi-lo+1))+1` probes over the default 552–9216 range). Node-local only, no peer fan-out — the same documented scope `GET /latmesh/heatmap` carries; netRead-gated, matching every other read-only monitoring route.

**Map-edge annotation**: the web client's "verified MTU" overlay (`web/src/topology/mtuOverlay.ts`'s `computeMTUOverlayEdges`, a second, independent overlay from the "Latency" heatmap layer, T-1303) renders each probed link's measured MTU as its own badge, distinct from wherever that link's *configured* MTU is already shown (the zone/bridge editor's own MTU field) — a link with no probe result yet renders no badge at all, never a stale/zero placeholder.

**Findings**: see the `GET /findings` finding shape section above — `vxlan_underlay_mtu` (T-803, upgraded by this task) consumes `Service.MeasuredUnderlayMTU(node)` (the minimum verified MTU across every link that node has successfully probed outbound) as an optional, tighter input, falling back to the pre-existing observed-NIC-MTU evaluation wherever no fresh probe reading exists for that node yet — never a regression.

**WireGuard hook (declared, not wired)**: `Service.ProbeWireGuardLink(ctx, tunnelRef)` is a capability-gated seam that always returns `mtuprobe.ErrWireGuardNotAvailable` today (`mtuprobe.WireGuardCapability` defaults `false` — there is no WireGuard tunnel entity kind in `internal/inventory` yet, and no capability flag exists to check). Phase 14's T-1401 is the task expected to introduce that capability flag and a WireGuard tunnel entity, then wire a real implementation into this exact method — see `planning/reports/T-1306.md` for the precise call-site this task leaves for it. This card's own work stops at the declared, tested, dark seam. (T-1401 note: T-1401 adds the `wg-tunnel`/`wg-peer` Ref kinds and the `wireguard_tunnels` store table, but leaves this MTU-prober hook still dark — wiring a real per-tunnel MTU probe is out of T-1401's scope and remains a follow-up.)

## WAN & upstream health (T-1405)

Added by T-1405 (`internal/wan`): per-uplink availability/latency/loss to operator-configured *external* reference targets (a public DNS resolver, an upstream gateway, ...), answering "is this the ISP, not the cluster?" — visibility and a `wan_degraded` finding only, **no WAN failover automation** (no changeset op type or write route exists anywhere for uplink switching; `internal/change`'s `TestNoWanFailoverOpType` pins this structurally, mirroring T-1404 AC7's own `TestNoDHCPv6PDOpType`).

**Reuses T-1303's scheduler, not a second one** (following T-1306's own precedent for reusing `internal/latmesh` infrastructure): `internal/wan.Service` wraps *`internal/latmesh.Service` itself*, configured with this task's own `Discoverer` (`wan.TargetDiscoverer`, emitting one `Pair` per configured node/uplink/reference-target triple instead of latmesh's cluster-node-pair discovery) and its own `Ring` (`store.WanProbeSampleRepo`, backing a new `wan_probe_samples` table rather than `latency_samples` — a WAN link's own jitter/loss profile and retention needs are not the LAN mesh's, so `[wan]`'s own `probe_interval_sec`/`retention_minutes`/`max_rows` tunables (`vnprox.toml`, defaults 10s/60min/500,000 rows — the same numbers `[latmesh]` uses) apply to their own ring). The wire-level probe mechanism is reused verbatim too: `latmesh.RealProber` execs `ping` against `Pair.ToAddr`, which works identically against an external hostname/IP as it does a cluster node name.

**Node-local scope** (the same documented gap `GET /latmesh/heatmap`/`GET /mtuprobe/results` already carry): a node only ever probes its own configured targets; the cluster-wide picture is the union of every node's own `GET /wan/status`. `GET/PUT /wan/targets` likewise operate on the *requesting* node's own local store, with no `{node}` path param — configuring a different node's targets from this node's API is a documented follow-up, not implemented here.

| Method | Path | Purpose |
|---|---|---|
| GET | `/wan/status` | per-uplink current availability/latency/loss plus a dashboard-tile verdict — netRead-gated |
| GET | `/wan/targets` | this node's own configured reference targets — netRead-gated |
| PUT | `/wan/targets` | replace this node's configured reference targets (full-set replace) — netWrite + CSRF, audited `wan.targets_update` |

**`GET /wan/status`** response: `{uplinks: [WanUplinkStatus], generatedAt, verdict, summary}`. `WanUplinkStatus`: `{node, uplink, status, targets: [WanTargetStatus], availabilityPct, rttMs, lossPct}` — `status` is `"healthy"`\|`"degraded"`\|`"unreachable"` (every configured target's rolling loss under threshold / at least one over threshold / every target at 100% loss); `availabilityPct`/`rttMs`/`lossPct` are the mean across the uplink's own configured targets' rolling figures. `WanTargetStatus`: `{host, at, rttMs, lossPct, rollingRttMs, rollingLossPct, reachable}`. Multiple uplinks on one node are always reported independently — never merged or blended (multi-WAN visibility). An uplink with a configured target that has no probe reading yet simply has no entry at all, the same "no result yet → no entry, never a stale placeholder" stance `GET /mtuprobe/results`' map-edge annotation already establishes. `verdict` is `"healthy"`\|`"wan_degraded"`\|`"likely_isp"`\|`"no_targets"` — `"likely_isp"` fires when at least one uplink is degraded/unreachable **and** every other (non-`wan`-sourced) finding in `GET /findings` is below `warning` severity (`internal/wan` itself never imports `internal/findings` — this correlation is computed in `internal/api`, the one place both seams are already wired); `"wan_degraded"` is the same WAN-side signal without that "otherwise clean" confirmation (either no `FindingsService` is wired, or another cluster issue is active too — never a confident "it's the ISP" claim this package can't back up). `summary` is the operator-facing sentence for the dashboard tile.

**`GET/PUT /wan/targets`** response/request body: `{node, targets: [{uplink, host}]}` (`node` is response-only — a computed field, GET/PUT both use the requesting session's own node). `uplink` is a caller-chosen label — in practice the web client populates it from `GET /edge/routes`' `DefaultRoute.Iface` list for the node being configured (T-1403's uplink model), though this route does not itself validate `uplink` against that list. PUT is always a full-set replace (never a partial patch), schema-validated (`uplink`/`host` both non-empty, capped at 100 targets per node — `400 validation_failed` otherwise).

**Findings**: `wan_degraded` (`source: "wan"`, see the `GET /findings` finding shape section above) — one finding per (node, uplink, target) whose *rolling* loss crosses `HealthThresholds.WanLossWarnPct` (default 20% — deliberately looser than the LAN mesh's 2%, since an ordinary WAN path's baseline jitter/loss to an external host is inherently higher) and holds for 3 consecutive Engine cycles (clearing after 2 consecutive cycles back under threshold — the same hysteresis window `path_loss` uses). Routed through the existing `alert_rules`/webhook delivery pipeline (T-1005) exactly like every other finding, no new delivery mechanism. Never `fixable` (a degraded WAN path is a fact to investigate, not a computable config patch).

**Regression** (AC5): `/wan/*` routes accept no request body except `PUT /wan/targets`' own target-list replace, and no changeset op type exists for WAN failover/uplink switching — `GET /wan/status` and the probe loop never call any mutating route.

## WireGuard (T-1401)

Added by T-1401 (`internal/wireguard`): site-to-site WireGuard tunnels as a first-class, changeset-managed capability. **Every WireGuard mutation is an ordinary `wg.*` changeset op** (docs/data-model.md §3) through the normal stage→validate→diff→apply→confirm/rollback lifecycle — there is **no write route here and no second mutation path.** The routes below are all read-only and `netRead`-gated. WireGuard's own on-node state (the live interface, handshake ages, transfer counters, the endpoint a peer is actually reaching us from) stays authoritative and is polled fresh (`wg show <if> dump`-equivalent), never persisted as truth.

| Method | Path | Purpose |
|---|---|---|
| GET | `/wireguard/tunnels` | every tunnel's app-owned config merged with its live on-node status (mirrors `GET /sdn`'s running-vs-config-truth pattern) |
| GET | `/wireguard/tunnels/{id}/pubkey` | the tunnel's derived **public** key only — no route can retrieve the private key |
| GET | `/wireguard/tunnels/{id}/peer-config` | an exportable wg-quick config block for an external peer's own side |

**`GET /wireguard/tunnels`** response: `{items: [WireGuardTunnel]}`. `WireGuardTunnel`: `{id, node, ifName, publicKey, listenPort, addresses: [string], mtu, carrier?, peers: [WireGuardPeer], status: {interfaceUp, peerCount}}`. It **never** carries a private key — the private key is generated on the owning node, sealed with the same AES-256-GCM `SessionCipher` `sessions.pve_ticket_enc` uses, and is never returned by any response, log line, or audit-log detail (docs/security.md's WireGuard credential-storage note). `WireGuardPeer`: `{publicKey, endpoint?, allowedIps: [string], keepaliveSec?, external, observedEndpoint?, lastHandshakeUnix?, rxBytes, txBytes, endpointDrifted}` — the config fields plus the live-polled status half; `external` marks a read-only, config-export-only peer vnprox does not own.

**`GET /wireguard/tunnels/{id}/pubkey`** response: `{id, publicKey}`. **`GET /wireguard/tunnels/{id}/peer-config`** response: `{id, peerConfig}` — a complete `[Interface]`/`[Peer]` block naming this tunnel's public key and endpoint, with the peer's own private key left a placeholder (vnprox never holds an external peer's key — its own key hygiene is out of vnprox's control).

**Findings** (`source: "wireguard"`, see the `GET /findings` finding shape section above): `wg_handshake_stale` (a peer whose last handshake is past the `WgHandshakeStaleThreshold`, hysteresis-debounced so a single missed poll doesn't fire) and `wg_endpoint_drift` (a peer whose live observed endpoint disagrees with its configured one — the NAT-rebind case, also debounced). Both are computed fresh from the live poll, never persisted, and both `fixable: false` (a stale handshake or a rebind is a fact to investigate, not a computable config patch). A `wg.*` op on a tunnel whose carrier interface is on a node's resolved management/corosync path is `touchesMgmtPath` (the changesets section's flag), inheriting T-703's typed-ack / 180s-confirm-window ceremony with no override.

## Captures (T-1301, T-1302)

Added by T-1301 (`internal/capture`): server-orchestrated packet capture on the local node or any peer, behind a **dedicated `capture` capability** and **server-enforced, un-overridable caps**. This is a security-sensitive trust boundary — see docs/security.md's Authorization / Host footprint / Audit sections. The captured packets live **only** in one bounded per-session `.pcap` file on the capturing node (`[capture] root`, default `/var/lib/vnprox/captures/<sessionId>.pcap`), auto-purged past `retention_hours`; **no payload byte is ever copied into SQLite, the audit log, or any other store** — `capture_sessions` (docs/data-model.md §2) holds app-owned intent + byte/packet accounting only.

| Method | Path | Purpose |
|---|---|---|
| POST | `/captures` | start a (possibly multi-point) capture |
| POST | `/captures/{id}/stop` | stop every session in the capture group |
| GET | `/captures/{id}` | one capture group |
| GET | `/captures` | list capture groups |
| GET | `/captures/{id}/download?sessionId=` | per-session pcap download (T-1302) |

Every route requires **both** `netRead` **and** the dedicated `capture` capability (holding `netRead`/`netWrite` alone is never sufficient — docs/security.md's Authorization section documents the `capture` gate as at least as strict as `netWrite`'s). The two mutating routes additionally require CSRF. A missing `capture` capability is a `403`.

**`POST /captures`** body: `{targetRef, filter?, durationSec?, maxBytes?, maxPackets?, peerTargets?}`. `targetRef` is the inventory `Ref` of a bridge/bond/guest-NIC/SDN-VNet to capture on; `peerTargets` is an optional list of additional target `Ref`s (typically on other nodes) to capture the same logical flow at, correlated into one group. `filter` is a pcap/BPF filter expression, **server-validated** before any capture starts (rejected — `400 validation_failed` — if it contains shell-unsafe characters, exceeds the configured instruction ceiling, or names a target that cannot be scoped to a concrete interface; a rejected filter never reaches a capture process). `durationSec`/`maxBytes`/`maxPackets` are **cap requests only**: the server clamps each down to its configured, un-overridable ceiling (`[capture]` in `vnprox.toml`) — a request may ask for a *lower* value, never a *higher* one, and each capturing node re-clamps independently. The T-1302 UI never renders the requested value back — every cap field it shows after a session starts is read from the response's `caps`/`session.caps`, i.e. what the server actually granted. Response (`201`): a **capture group** `{id, status, startedBy, startedAt, caps: {maxDurationSec, maxBytes, maxPackets, retentionHours}, sessions: [captureSession]}`.

**`captureSession`**: `{id, groupId, targetRef, node, filter, caps, status, startedBy, startedAt, stoppedAt, fileBytes, packets, nodes?}`. `status` is `"running"`\|`"completed"` (a server cap was hit)\|`"stopped"` (operator-stopped)\|`"error"`\|`"purged"` (its file was auto-deleted past retention). The on-disk file path is **never serialized to API clients**. A multi-point capture is a set of `sessions` sharing one `groupId` (the correlation key T-1302 aligns the two nodes' decoded streams by).

**`POST /captures/{id}/stop`** stops every non-terminal session in the group (local via its live process, remote via the peer). **`GET /captures/{id}`** / **`GET /captures`** (`{items: [group]}`) reconcile each member's live byte/packet accounting before returning.

**`GET /captures/{id}/download?sessionId=`** (T-1302): downloads one session's raw `.pcap` file — `Content-Type: application/vnd.tcpdump.pcap`, `Content-Disposition: attachment`, opens directly in Wireshark. `{id}` is the capture **group** id, matching every other `/captures/{id}` route; `sessionId` picks which node's session within the group (defaults to the group's first/primary session — the common single-node case needs no query param). Resolves local-vs-peer transparently: a session captured on this node is read straight from `[capture] root`; a session captured on a peer node is fetched over a new additive, HMAC-gated `GET /api/peer/capture/download?sessionId=` route (Peer API table below) — the same cluster-aware contract every other host-state read in this codebase honors, never a local-only shortcut. An unknown group/session id is `404 not_found`; a session whose file has already been auto-purged past `retention_hours` is also `404 not_found` (distinct reason string: "file is no longer available"), never a stale/empty download.

Every start/stop writes an audit row — see the Audit section's `capture.start`/`capture.stop` action vocabulary.
## Conntrack

Added by T-1305 (`internal/api/conntrack.go`, docs/features/monitoring.md's "instead of SSH" toolkit): a **live**, per-node conntrack/NAT table read, cluster-fanned-out and filtered — the "what is this connection doing right now" complement to `GET /flows`' sampled/historical view. Read-only this arc: **no mutation route exists for a conntrack entry anywhere in this API surface** — no flush, no delete, no changeset op. Nothing here is persisted: every request re-reads each node's live kernel conntrack table fresh (`internal/host.Reader.Conntrack`, `/proc/net/nf_conntrack` on the real implementation), so unlike `GET /flows` this route has no retention window and no pagination — a live snapshot has no cursor to resume.

| Method | Path | Purpose |
|---|---|---|
| GET | `/conntrack?node=&guest=&srcIp=&dstIp=&port=&state=` | live, cluster-wide conntrack/NAT table query |

Requires the `netRead` capability, the same gate every other live-network-observability read route (`GET /flows`, `GET /metrics/live`, `GET /firewall/log`) uses.

**Response**: `{items: [ConntrackEntry], partial?, failedNodes?}` — the same cluster-fan-out envelope `GET /audit`/`GET /flows` document, minus their pagination fields. `partial`/`failedNodes` name any node (local or peer) whose live table couldn't be read this request; every other node's contribution is still returned — a single unreachable node degrades only its own entries, never the whole response, mirroring `GET /flows`' `partial`/`failedNodes` contract exactly.

**`ConntrackEntry`**: `{node, proto, srcIp, srcPort?, dstIp, dstPort?, state?, timeoutSec?, natSrc?, natDst?}`. `node` is which cluster node this connection was observed on. `proto` is the raw IP protocol number (6=tcp, 17=udp, 1=icmp, ...). `state` is the kernel's own connection-tracking state (e.g. `ESTABLISHED`, `TIME_WAIT` for TCP; UDP/ICMP carry no formal state, so a once-replied flow surfaces the kernel's own `ASSURED`/`UNREPLIED` flag here instead, and an entry with neither leaves `state` empty rather than fabricating one). `timeoutSec` is the connection's remaining conntrack-table timeout in seconds. `natSrc`/`natDst` (each `{ip, port?}`) are present only when that side of the connection is NAT-translated — recovered by comparing the conntrack line's original and reply direction tuples (`internal/host.ParseConntrackTable`'s doc comment has the exact detection logic) — absent for a plain, untranslated connection.

Every filter param is optional and ANDed together, mirroring `GET /flows`'/`GET /audit`'s convention (an unrecognized/unparsable filter value matches nothing, never a `400` — except a genuinely non-integer `port`, which `400`s the same way `GET /flows`' own `?port=` does, since that's a caller bug rather than a legitimate value with no matches). `node` matches the entry's own `node` field exactly. `srcIp`/`dstIp` match exactly (no CIDR/subnet matching — unlike `GET /flows`' `subnet=`, since a conntrack entry has no resolved ref to widen a match against). `port` matches either `srcPort` or `dstPort`. `state` matches case-insensitively. `guest` resolves against every enrichment source this daemon currently has evidence from for that guest (`internal/ipam.Service.GuestIPs`: the guest's own live guest-agent-reported addresses, plus any PVE-IPAM allocation whose MAC matches one of the guest's known NICs — the same "observed, never authoritative" sources `docs/features/ipam.md` §1 already documents) to a set of IP addresses, then matches an entry whose `srcIp` or `dstIp` is in that set; an unresolvable/never-observed guest ref matches nothing, not an error.

`GET /conntrack` fans out to every reachable cluster peer via `GET /api/peer/host/conntrack` (below) and merges, following the `GET /audit`/`GET /flows` `partial`/`failedNodes` convention (docs/architecture.md §7: this is a live, node-local kernel read, so a cluster-wide view re-queries every peer and merges).

### Conntrack explorer (`web/src/conntrack/ConntrackExplorer.tsx`, T-1305)

A live (polling-refreshed, no dedicated WS event — a point-in-time kernel read has no natural delta shape to push) table with the same filter-control shape `web/src/flows/FlowExplorer.tsx` established, showing state/timeout/NAT-translation columns. Reachable from the map's right-click menu (on a bridge/bond/guest-NIC/SDN-VNet entity — node-scoped via that entity's own node, since a flow conversation's resolved endpoints are never conntrack-matchable IPs or guest refs, `GET /flows`' own documented "never guessed" gap) and from the Flow Explorer's guest-pair drill-down panel (`topology/FlowPairPanel.tsx`'s "View live connections" link, alongside its existing "View in Flow Explorer" link — also node-scoped, for the same reason).

## Diagnosis (T-1307)

Added by T-1307 (`internal/diagnose`, `internal/api/diagnose.go`): a "Diagnose" action on any guest/edge that composes this phase's already-shipped surfaces — the path simulator (T-503), the live path probe (T-802/T-806), the guest interior inspector (T-1304), the conntrack explorer (T-1305), and packet capture (T-1301) — into one ordered ladder and one readable verdict. **Advisory only**: the ladder never auto-remediates; a verdict's `suggestedFixRef`, when present, always names an *existing* fixable finding's own `POST /findings/{id}/fix` link (the Findings section above) — this route never computes a fix itself. **This is scaffolding**: the response shape below is the stable, machine-consumable contract Phase 17's T-1701 MCP AI operator drives — treat field names/the `status` vocabulary as a versioned contract, not an internal detail.

| Method | Path | Purpose |
|---|---|---|
| POST | `/diagnose` | `{targetRef, escalateToCapture?}` → one ladder `Result` |

Requires `netRead`, gated on `AuthService` additionally implementing `UsernameLookup` (audit attribution) — mounted only then, mirroring `POST /simulate/verify`'s own requirement. `targetRef` is any inventory `Ref` string (`kind:node:id`) — typically a guest NIC, a bare guest, or an edge (bridge/bond/vlan/SDN VNet); malformed/missing → `400 validation_failed`. `escalateToCapture` (default `false`) opts into the capture step's real side effect — see below.

**`Result`**: `{target, steps: [Step], verdict: Verdict}`.

- `Step`: `{name, status, summary, detail?, ranAt}`. `name` is one of the five registered steps, always present and in this fixed order: `"config-check"` (T-503's `sim.Simulate`, a static path simulation from the target's guest source to its own network's configured default gateway), `"live-probe"` (T-802/T-806's real ICMP probe to the same gateway via the QEMU guest agent, upgrading/persisting a `sim_divergence` finding exactly as `POST /simulate/verify` itself would if it diverges), `"guest-interior"` (T-1304's opt-in guest interior read), `"conntrack"` (T-1305's live conntrack read, scoped to the target's owning guest's known IPs, or to the target's own node for a non-guest edge target), `"capture"` (T-1301's packet capture, escalation-gated — see below). `status` is `"ran"`\|`"skipped"`\|`"error"`: `"ran"` covers both a genuine result *and* an honest "could not attempt this" outcome (e.g. a live probe against an unreachable guest agent, docs/features/firewall.md §6's honesty contract carried through); `"skipped"` means the step does not apply to this target at all (e.g. no `"guest-interior"` step for a bare bridge target, or `"config-check"`/`"live-probe"` for any target with no resolvable guest source or no configured gateway to check) — `summary` always states why; `"error"` is reserved for a genuine ladder-level failure, never for an honest "could not attempt" result. `detail` is that step's own underlying response shape verbatim — a `SimulateResult` (config-check), `{simulated, observed, diverges}` (live-probe, `POST /simulate/verify`'s own shape), a Guest interior response (guest-interior), a Conntrack response (conntrack), or a capture group (capture) — never re-summarized or lossy. It is omitted for `skipped`/`error` steps, and also for a `ran` step whose honest "could not attempt this" outcome produced no underlying response (e.g. an unreachable guest agent on `guest-interior`, or a capture that failed to start) — `status`/`summary` carry the outcome in that case. So `detail` is present for a `ran` step that obtained a real response, not for every `ran` step. `ranAt` is unix seconds.
- `Verdict`: `{summary, confidence, linkedFindingIds: [string], suggestedFixRef?}`. `confidence` is `"high"`\|`"medium"`\|`"low"`\|`"none"` — a deliberately simple, disclosed heuristic (`"none"`: no step ran at all; `"low"`: at least one step errored; `"high"`: every step ran clean and at least one related finding was surfaced; `"medium"`: every step ran clean, no related findings) — a human reads `steps` for the real detail, `verdict` is a one-line orientation, not a scored diagnosis. `linkedFindingIds` merges two sources: any finding the live-probe step itself persisted this run (a fresh `sim_divergence`, by its exact deterministic id — the same id `POST /simulate/verify` would compute for the identical tuple) and every current finding (`GET /findings`) whose `refs` overlap the target itself, its owning guest, or its attached bridge/VNet — e.g. a `bondslave`/LACP/STP finding on the exact bridge a diagnosed guest sits on. Always `[]`, never `null`. `suggestedFixRef` (omitted when none) is the first `Fixable` finding among those matches, by id — resolves through the *same* `POST /findings/{id}/fix` route that finding's own fix link would use directly; this route never has its own fix-computation path.

**Capture escalation** (T-1301's own trust boundary, never weakened here): the `"capture"` step only calls `capture.Coordinator.Start` when **both** `escalateToCapture: true` **and** the requesting session holds the dedicated `capture` capability — checked in-step (`DiagnoseCapabilityChecker`, mirroring `AuthService`'s own capability derivation), never at the route level. `escalateToCapture: false` (the default) never starts a capture session at all, regardless of capability — the step returns `"skipped"` before ever calling `Coordinator.Start`. A caller lacking `capture` gets the capture step `"skipped"` (a stated capability-not-held reason) while every other eligible step still runs and the ladder still returns a verdict — never a `403` for the whole call, unlike every other `capture`-gated route (`POST /captures` itself 403s). A started capture is audited `capture.start` exactly as T-1301 already requires (in addition to this call's own single `diagnose.run` row — see the Audit section above).

**Extensibility**: the ladder is a registration table (`internal/diagnose.Ladder`), not a hardcoded sequence — a future phase (e.g. Phase 14's WireGuard/edge diagnostics) appends a `Step` at its own construction call site without touching `internal/diagnose`'s own code or this route's five-step contract above.

## History

Added by T-1007 ("History playback", docs/features/topology.md §2 §3, docs/features/monitoring.md §2): a single merged event-marker feed for `web/src/topology/history/HistoryTimeline.tsx`'s scrubber, which replays the map's traffic-paint (`GET /metrics/history` above) and flow-painted edges (`GET /flows` above) back through their already-retained windows. This route adds no new retention — it is strictly read-only over data those two routes and `GET /audit` already serve, plus one small new table (`finding_events`, docs/data-model.md §2) that closes the one real gap: `GET /findings` has no history of its own.

| Method | Path | Purpose |
|---|---|---|
| GET | `/history/events?fromTs=&toTs=` | merged changeset-lifecycle + finding-transition timeline markers |

Requires the `audit` capability (the same gate `GET /audit` uses — this route's changeset half re-exposes real `audit_log` rows, so it is never gated more loosely than the route that already serves them).

**Response**: `{items: [HistoryEvent]}`, ascending by `at` (oldest first — a scrubbable timeline reads left-to-right in time order, unlike `GET /audit`'s own newest-first activity-feed convention). `HistoryEvent` is `{at, kind, action?, target?, changesetId?, result?, findingId?, transition?, serviceClass?}`:

- `kind: "changeset"` — one entry per `audit_log` row whose `action` is in the T-205 apply-engine lifecycle set `GET /audit` already documents (`changeset.apply`, `changeset.confirm`, `changeset.rollback`, `changeset.timer_rearm`, `changeset.recover`, `changeset.safety_override`); `action`/`target`/`changesetId`/`result` mirror `GET /audit`'s own fields for the same row (username/detail are omitted — this is a timeline-marker feed, not a second audit browser). Clicking this marker in the UI deep-links to that `changesetId`'s existing changeset detail/diff view (`useChangesetDrawerStore.setActiveId`) — it never re-triggers apply/confirm/rollback; the timeline has no mutation affordance anywhere.
- `kind: "finding"` — one entry per `finding_events` row (`findingId`, `transition`: `"new"`\|`"escalated"`\|`"resolved"`), populated from `internal/findings.Notifier`'s existing transition detection (`notify.go`'s `evaluateNotifications`/`fireNotification`) via a new `Notifier` implementation (`internal/findings/findingevents.go`'s `FindingEventsNotifier`) composed alongside `PVENotifier`/`WebhookNotifier` at the `cmd/vnproxd` composition root — the exact same "once per transition" firing `docs/features/monitoring.md` §5's AC5 already guarantees, reused rather than re-derived from polled `GET /findings` snapshots. **`serviceClass`** (T-1504) is additionally present on a `kind: "finding"` entry only when `findingId` is a `service_traffic_on_wrong_network` finding (source `flow`, see `GET /findings` below) — parsed server-side from that finding's own content-derived id (`internal/findings.ServiceClassFromFindingID`), not a new `finding_events` column: the id already carries the serviceClass, so this route recomputes it at render time rather than duplicating storage. Every other finding's entry omits the field.

`fromTs`/`toTs` are unix seconds, inclusive; both default to "no bound on that side" when omitted/unparsable, matching `GET /metrics/history`'s convention. Node-local only (no peer fan-out): `finding_events` is app-owned, per-node data like `metric_samples`, and the changeset-lifecycle half already comes from this node's own `audit_log` (a cluster-wide *changeset* audit view is `GET /audit`'s own job, with its documented peer fan-out — this route deliberately does not duplicate that fan-out for a timeline-marker feed).

**Bounds** (docs/features/topology.md §2's scrubber, per this task's card): the UI clamps its playback range to the shorter of the metrics window (24h, `store.MetricRetention`) and the flows window (`[flows] retention_minutes`, default 60m, T-1002) — scrubbing earlier than the flow window's own retention disables/greys the Flows layer with an explicit disclosure ("flow history available for the last N minutes only") rather than silently showing an empty overlay. `finding_events` is bounded and pruned to the same `store.MetricRetention` window as `metric_samples` (`internal/store/migrations/0009_finding_events.sql`'s doc comment) — never a longer horizon, matching every other bounded ring this codebase keeps.

## Blueprints

| Method | Path | Purpose |
|---|---|---|
| GET/POST | `/blueprints` | list / save (parameterized topology template JSON) |
| POST | `/blueprints/{id}/instantiate` | `{params}` → changeset draft |

**Blueprint shape** (T-603): `{blueprintVersion: 1, id, name, description?, readOnly?, nodeSelector: {mode: "all"|"single"}, params: [ParamDef], entities: [EntityTemplate], createdBy?, createdAt?, updatedAt?}`. `ParamDef`: `{name, type: "string"|"int"|"bool"|"cidr"|"ip"|"vid"|"vidList"|"iface"|"nodeList", label?, description?, default?, required?, addressSuggest?, subnet?}` — `addressSuggest` (only valid on `cidr`/`ip` params) marks it eligible for `GET /blueprints/{id}/suggest` below; `subnet` is the CIDR pool searched (falls back to the containing network of `default` for a `cidr` param). `EntityTemplate`: `{kind: "bridge"|"bond"|"vlan"|"sdn-zone"|"sdn-vnet"|"sdn-subnet", idTemplate, nodeSelector?, fields: {...}}` — `fields` keys are exactly the corresponding `change.*CreateParams` JSON field names; values may be literal, a `"{{param}}"` placeholder (whole-value substitution preserves the param's JSON type), or the builtin `"{{__nodes__}}"` token (the instantiate request's target node list). `readOnly: true` marks the five bundled starters (`GET /blueprints` always includes them; they cannot be saved-over or deleted — `403 blueprint_read_only`).

**`POST /blueprints/{id}/instantiate` body** is additive to the documented `{params}` shape (per docs/development.md's definition-of-done #4): `{params: {...}, nodes?: [string], title?: string}`. `nodes` is the target cluster node list for `nodeSelector.mode: "all"` expansion and for entities' `"{{__nodes__}}"` substitution; omitted/empty defaults to every node currently in inventory. `title` overrides the default changeset title (`"blueprint: <name>"`). The response is the same shape `POST /changesets` returns (a draft changeset) — instantiation only ever produces a draft; nothing is applied.

Additive routes (T-603, not in the original contract; documented here per docs/development.md's definition-of-done #4):

| Method | Path | Purpose |
|---|---|---|
| GET | `/blueprints/{id}` | single blueprint detail (starter or saved) — also the export/download source |
| DELETE | `/blueprints/{id}` | remove a saved blueprint; `403 blueprint_read_only` for a starter id |
| POST | `/blueprints/capture` | `{node}` → an unsaved Blueprint captured from that node's live bonds/bridges/VLAN interfaces (addresses turned into named, address-suggest-eligible params); save it via `POST /blueprints` to persist |
| GET | `/blueprints/{id}/suggest?param=` | next-free-address suggestion for one of the blueprint's `addressSuggest` params: `{address}` |

Import/export is file-level, not a dedicated route: export is `GET /blueprints/{id}`'s JSON body saved to a file; import is that same JSON re-posted to `POST /blueprints` (with `id` cleared so a new blueprint is created, or set to overwrite an existing saved one — never a starter id).

### Blueprint sharing bundles (T-1107)

Signed, cross-installation bundles on top of the plain-file import/export above — full schema/trust-model writeup: `docs/features/blueprints.md` §5.

| Method | Path | Cap | Purpose |
|---|---|---|---|
| GET | `/blueprints/{id}/bundle?sign=` | `netRead` | export a Bundle; signed iff `?sign=` is present and not `""`/`"0"`/`"false"` |
| GET | `/blueprints/signing-key` | `netRead` | this installation's own bundle-signing public key (for a receiving admin to pin) |
| POST | `/blueprints/import` | `netWrite` + CSRF | verify a Bundle's signature, apply the trust decision, save |
| GET/POST | `/blueprint-signers` | `netRead` / `netWrite` + CSRF | list / pin a trusted signer |
| DELETE | `/blueprint-signers/{fingerprint}` | `netWrite` + CSRF | un-pin a trusted signer |

**Bundle shape**: `{bundleVersion: 1, blueprint: Blueprint, signature?: {alg: "ed25519", publicKeyFingerprint, publicKey, sig}}` — `publicKey`/`sig`/`publicKeyFingerprint` are all base64/hex strings; see `docs/features/blueprints.md` §5 for exactly what bytes `sig` covers and why `publicKey` travels alongside the fingerprint.

**`GET /blueprints/{id}/bundle?sign=`** response is the Bundle itself (not wrapped in a `content` envelope the way `GET /spec` is) — `application/json`, suitable for saving straight to a file. Omitting `?sign=` (or `?sign=false`/`?sign=0`) produces an unsigned bundle (no `signature` field at all).

**`GET /blueprints/signing-key`** response: `{alg: "ed25519", publicKey, fingerprint}` — not mounted at all if this daemon has no signing key configured.

**`POST /blueprints/import`** body: the Bundle plus two optional trust flags: `{...bundle fields, trustUnsigned?: boolean, trustNewKey?: boolean}`. Response: `{status: "imported"|"unsigned"|"untrustedSignature"|"invalidSignature", blueprint?, signer?}` — `blueprint` is set only when `status: "imported"` (the newly saved blueprint, always a fresh `id`); `signer` (`{fingerprint, publicKey}`) is set only for `"untrustedSignature"`, so a caller can offer "trust this signer" without a second fetch. None of the three non-`"imported"` statuses is an HTTP error — each is a normal `200` the caller inspects `status` on; only a malformed request body or an unsupported `bundleVersion` is `400 validation_failed`. Every import attempt (both explicit-trust paths and every rejection) is audited as `blueprint.import` with the trust decision recorded.

**`GET/POST/DELETE /blueprint-signers`**: `TrustedSigner` shape `{fingerprint, publicKey, label?, addedBy?, addedAt}`. `POST` body: `{publicKey: "<base64>", label?: string}` (the fingerprint is derived server-side, never client-supplied). Both write routes are audited as `blueprint.signer.add`/`blueprint.signer.delete`.

## Declarative cluster network spec (T-1101)

Blueprints v2: one versionable YAML document capturing cluster-wide L2/SDN intent (bonds, bridges, VLANs, SDN zones/vnets/subnets), rendered from live state and reconciled back against it. Full schema and semantics: `docs/data-model.md` §6 (`internal/spec`).

| Method | Path | Cap | Purpose |
|---|---|---|---|
| GET | `/spec` | `netRead` | export the live cluster network as `specVersion: 1` YAML |
| POST | `/spec/import` | `netWrite` + CSRF | diff a spec against live → **draft** changeset + `notInSpec` |

**`GET /spec`** response: `{specVersion: 1, content: "<yaml>"}` — `content` is the exact YAML document (byte-stable: two exports of an unchanged cluster are byte-identical, the property that makes a GitOps `git diff` empty). `specVersion` is surfaced as a first-class field so a caller need not parse the body to branch on it.

**`POST /spec/import`** body: `{content: "<yaml>"}`. The handler parses the document (rejecting any `specVersion` ≠ 1 with `400 validation_failed`), diffs it against the live inventory snapshot, and calls the same `change.Service.Create` every programmatic op-drafting path uses. The response is the **draft changeset** — the same shape `POST /changesets` returns (`{id, title, status, ops, findings, …}`, `status` is always `draft`/`validated`, never `applying`/`committed`) — with one added field:

```jsonc
{ ...changeset fields...,
  "notInSpec": ["bridge:pve1:vmbr0", "sdn-zone::evpnz"] }  // Ref strings
```

`notInSpec` lists managed-kind entities present **live** but absent from the document. They are **reported, never deleted** — `POST /spec/import` has no prune path and emits no delete ops (docs/data-model.md §6). Apply/confirm the returned draft through the normal `POST /changesets/{id}/apply` + `.../confirm` lifecycle; import itself never applies.

### Spec pin (T-1102)

The GitOps reconciler's declared desired state: an operator pins one spec document, and `internal/drift`'s `spec_drift` check family (`GET /drift`'s sixth check value, documented in "Inventory & topology" above) diffs live state against it every drift cycle via the exact same `spec.Import` diff engine `POST /spec/import` uses. Pinning is app-owned data (`pinned_spec` table, `docs/data-model.md` §7), never a shadow copy of PVE config, and never applies anything by itself — reconciling a `spec_drift` finding still goes through the normal `POST /drift/{id}/fix` → review → apply/confirm lifecycle.

| Method | Path | Cap | Purpose |
|---|---|---|---|
| GET | `/spec/pin` | `netRead` | current pin + metadata, or `{pinned: false}` if nothing is pinned |
| POST | `/spec/pin` | `netWrite` + CSRF | `{content}` → validates (`specVersion` must parse) and pins it, audited `spec.pin` |
| DELETE | `/spec/pin` | `netWrite` + CSRF | clears the pin, audited `spec.unpin`; `204` |

**`GET`/`POST` response shape**: `{pinned: bool, content?, pinnedBy?, pinnedAt?}` — every field but `pinned` is omitted when nothing is pinned. `content` is the exact YAML document as pinned (byte-for-byte, the same document `spec_drift` reconciles against); `pinnedBy`/`pinnedAt` are the acting user and unix-seconds timestamp `POST /spec/pin` recorded. `POST` re-pins in place (no explicit unpin required first) and returns the same shape as `GET` immediately after. A `POST` whose `content` fails `spec.Parse` (e.g. `specVersion` ≠ 1) is rejected with `400 validation_failed` and nothing is stored or audited — the existing pin, if any, is unchanged.

## Saved views & annotations

Added by T-907 (Phase 9's only card permitted to touch the backend — docs/roadmap-next.md; `planning/tasks/phase-9.md`'s T-907 card). Both routes below are strictly app-owned UI state: named presets of the topology page's own layer/filter/zoom/selection state, and free-text sticky notes pinned to a map entity — **never** a shadow copy of any PVE-authoritative network config (CLAUDE.md's storage rule). Gated identically to the pre-existing `layouts` routes below: session + `netRead`, no CSRF requirement — the reasoning is unchanged from T-107's original layouts routes ("saving a canvas layout is a personal UI preference, not a network-mutating action"), extended here to naming/deleting a saved view and to pinning/unpinning a shared sticky note, neither of which mutates network state either.

### Saved layouts / named views (`internal/api/layouts.go`, `internal/store/layouts.go`)

The `GET/PUT /layouts/{name}` routes existed since T-107 (undocumented until this task — retroactively documented here per docs/development.md's definition-of-done #4) as the mechanism the topology page's auto-persisted canvas positions/filters (reserved name `"topology"`) and the onboarding walkthrough's progress (reserved name `"onboarding"`) both already used. T-907 adds `GET /layouts` (list) and `DELETE /layouts/{name}`, and reuses the exact same per-user `(username, name)` mechanism for **named saved views** — no new table, no forked mechanism (see docs/data-model.md §2's note on why `layouts` was reused for views but not for annotations).

| Method | Path | Purpose |
|---|---|---|
| GET | `/layouts` | list every layout/saved-view the requesting user has saved: `{items: [{name, layout, updatedAt}]}` — same per-item shape as `GET /layouts/{name}` below, ordered by name ascending. Includes the reserved `"topology"`/`"onboarding"` blobs alongside any named views; see the `kind` discriminator below for how a client tells them apart. |
| GET | `/layouts/{name}` | `{name, layout, updatedAt}` — `layout` is caller-defined opaque JSON, stored and returned verbatim; `404 not_found` if `name` has never been saved by this user |
| PUT | `/layouts/{name}` | upsert `{layout: {...}}` → the same shape GET returns, with a fresh `updatedAt` |
| DELETE | `/layouts/{name}` | remove a saved layout/view; `204` whether or not it previously existed (idempotent, mirrors `store.LayoutRepo.Delete`) |

**Named saved view shape** (frontend-owned; `internal/api` never inspects `layout`'s contents — it is opaque JSON on every route above, exactly as it always was for the `"topology"` auto-layout). A saved view's `layout` is:

```json
{
  "kind": "view",
  "layers": ["phys", "l2", "sdn", "guest"],
  "vlanFilter": 100,
  "zoom": 1.4,
  "viewport": {"x": -120, "y": 40},
  "selection": "bridge:pve1:vmbr0",
  "view": "graph"
}
```

`layers` is the active-layer subset (docs/features/topology.md §2's layer ids); `vlanFilter` (omitted when unset) is the active VLAN dim filter; `zoom`/`viewport` are the v2 canvas's pan/zoom transform (`web/src/topology/canvasScene.ts`'s `Viewport`, split into a bare `zoom` scalar plus an `{x, y}` pan offset here for readability — same transform, different field grouping); `selection` (omitted when nothing is selected) is the selected entity's Ref; `view` is `"graph"` or `"switch"` (`store.ts`'s `TopologyViewMode`). The `"kind": "view"` tag is what lets the frontend's saved-views picker filter `GET /layouts`' items down to actual named views, excluding the reserved `"topology"`/`"onboarding"` auto-layout blobs (whose shape has no `kind` field at all) — a purely client-side distinction; the backend treats every name identically.

**Shareable URLs.** A saved view's state additionally round-trips through the topology page's own URL query string, independent of any server-side row — flat per-field params (not an opaque blob), the same "state lives in the URL" convention `web/src/simulator/urlState.ts` already established for the path simulator's shareable links (see the `sim_divergence` finding's `docsLink` note above): `/topology?svLayers=phys,l2&svVlan=100&svZoom=1.4&svX=-120&svY=40&svSel=bridge:pve1:vmbr0&svView=graph`. `svLayers` is comma-separated layer ids; `svVlan`/`svSel` are omitted when unset (mirroring `layout`'s optional `vlanFilter`/`selection` above); `svZoom`/`svX`/`svY` are the canvas pan/zoom transform; `svView` is `graph`\|`switch`. This is what makes a saved view's "Share link" work for a viewer with no `layouts` row of their own — opening the link applies the URL's state directly (`web/src/topology/savedViews.ts`'s `decodeViewFromSearch`) without ever calling `GET /layouts/{name}`; saving the view under a name (so it also appears in the viewer's own `GET /layouts` list) is a separate, optional action. No new route: this is pure client-side URL state.

### Annotations (`internal/api/annotations.go`, `internal/store/annotations.go`)

Entity-pinned sticky notes, persisted additively in a **new** table (`annotations`, docs/data-model.md §2) rather than folded into `layouts`: an annotation is naturally many-rows-per-entity and shared across every user (a team scratchpad, not private per-user state), which doesn't fit `layouts`' single-opaque-blob-per-`(username, name)` shape — see docs/data-model.md §2's note and `internal/store/migrations/0006_annotations.sql`'s doc comment for the full reasoning this task's card asked to be flagged explicitly.

| Method | Path | Purpose |
|---|---|---|
| GET | `/annotations` | list every pinned note, cluster/topology-wide (not scoped to the requesting user — see below): `{items: [Annotation]}`, ordered oldest-first |
| POST | `/annotations` | pin a new note: `{ref, content}` → `201` with the created `Annotation`; `400 validation_failed` if `ref` or `content` is empty, or `content` exceeds 4000 characters |
| DELETE | `/annotations/{id}` | unpin a note; `204` whether or not it previously existed (idempotent) |

`Annotation` is `{id, ref, content, createdBy, createdAt, updatedAt}` — `id` is a server-assigned ULID; `ref` is the pinned entity's `Ref` string; `content` is free text, never interpreted by vnproxd; `createdBy` is the authenticated username that pinned it (server-stamped from the session, never client-supplied) and `createdAt`/`updatedAt` are unix seconds. Unlike `layouts`, annotations carry **no per-note ownership ACL** — any authenticated `netRead`-capable user can list, create, or delete any annotation (a deliberate product choice: a sticky note on the shared map is visible and manageable by the whole team, the same way the map itself is; `createdBy` is display/audit metadata only, not an access-control field). The frontend renders an entity's pinned notes wherever that entity's own detail is shown (the inspector panel), keyed by matching `ref` — there is no separate per-entity route; a client filters the one `GET /annotations` list.

## Alert Rules

Added by T-1005 (`internal/api/alertrules.go`, `internal/store/alertrules.go`, `internal/store/alertdeliveries.go`, `internal/findings/webhook.go`). Routes findings/drift transitions to arbitrary webhook targets (generic JSON, Gotify, ntfy, or a Slack incoming webhook), independent of PVE's own notification-target system (`internal/findings/pvenotify.go`'s documented gap: PVE's API has no way to carry vnprox's own finding text). | POST | `/alert-rules/{id}/test` | deliver a synthetic test finding through the rule's target right now; `200 {status: "delivered"\|"failed", error?}` — the HTTP status is always 200 once the rule is found (a failed delivery is a normal, reportable outcome, not an API error); `404 not_found` if `id` doesn't name a rule |
| GET | `/alert-deliveries?ruleId=&status=` | delivery log: `{items: [AlertDelivery]}`, newest first; both filters independently optional and ANDed (an unrecognized value simply matches nothing, mirrors every other filter contract in this doc, e.g. `GET /findings`'s `?source=&severity=`) |

**`AlertRule`**: `{id, name, enabled, sourceFilter?: [string], severityFilter?: [string], targetKind: "generic"|"gotify"|"ntfy"|"slack", targetUrl, hasSecret, createdAt, updatedAt}`. `sourceFilter`/`severityFilter` are optional/ANDed like every other filter in this codebase — empty/omitted means "matches every value on that dimension"; when both are set, a finding must match at least one value in *each* list (AND across dimensions, OR within a dimension) to fire the rule. `sourceFilter` values are `GET /findings`'s own `source` vocabulary (`drift`\|`lldp`\|`ipam`\|`health`\|`probe`\|`wireguard`\|`wan`); `severityFilter` values are `error`\|`warning`\|`info`. A rule's target secret (a Gotify app token or an ntfy access token) is **never** returned by any route in this section, plaintext or encrypted — `hasSecret` is the only signal a client gets that one is configured, matching `GET /config`'s "deliberately excludes every secret" contract.
**`AlertRule`**: `{id, name, enabled, sourceFilter?: [string], severityFilter?: [string], targetKind: "generic"|"gotify"|"ntfy"|"slack", targetUrl, hasSecret, createdAt, updatedAt}`. `sourceFilter`/`severityFilter` are optional/ANDed like every other filter in this codebase — empty/omitted means "matches every value on that dimension"; when both are set, a finding must match at least one value in *each* list (AND across dimensions, OR within a dimension) to fire the rule. `sourceFilter` values are `GET /findings`'s own `source` vocabulary (`drift`\|`lldp`\|`ipam`\|`health`\|`probe`\|`k8s`); `severityFilter` values are `error`\|`warning`\|`info`. A rule's target secret (a Gotify app token or an ntfy access token) is **never** returned by any route in this section, plaintext or encrypted — `hasSecret` is the only signal a client gets that one is configured, matching `GET /config`'s "deliberately excludes every secret" contract.

**Create/update request body**: `{name, enabled, sourceFilter?, severityFilter?, targetKind, targetUrl, targetSecret?}`. `targetUrl` must be an absolute `http`/`https` URL (`400 validation_failed` otherwise); `targetKind` must be one of the four documented values. `targetSecret` is a plain string on create (omitted/empty means no secret); on **update** its absence leaves the existing secret untouched, `""` clears it, and a non-empty value replaces it — this three-way distinction is why the field is a nullable string rather than always-present. A secret, once set, is encrypted at rest with AES-256-GCM (`internal/store/cipher.go`'s `SessionCipher` — the exact same cipher/key `sessions.pve_ticket_enc` uses, docs/security.md's Authentication section) before it ever reaches SQLite.

**Delivery shapes per `targetKind`** (`internal/findings/webhook.go`'s `PayloadFor`): `generic` sends the `GET /findings` `Finding` shape verbatim as the JSON body (no wrapper), authenticating with `Authorization: Bearer <secret>` when a secret is set; `gotify` sends Gotify's push-message JSON (`{title, message, priority}`), authenticating with `X-Gotify-Key`; `ntfy` sends ntfy's plain-text publish convention (message as the body, `Title`/`Priority`/`Tags` headers), authenticating with `Authorization: Bearer <secret>`; `slack` sends Slack's incoming-webhook JSON (`{"text": "..."}`) — a Slack target's secret, if set, is ignored, since the webhook URL itself already carries the authorization. Every delivery also carries an additive `X-Vnprox-Transition: new|escalated|resolved` header (docs/features/monitoring.md §5's transition vocabulary), which never changes the `generic` body's "Finding shape verbatim" contract.

**Delivery/retry.** A qualifying finding transition (Engine's existing once-per-transition firing — `internal/findings/notify.go`, unchanged by this task) is delivered to every enabled rule whose filters match, each independently, with up to 5 attempts and exponential backoff (1s, 2s, 4s, 8s, capped at 30s) between attempts. `AlertDelivery`: `{id, ruleId, findingId, at, attempt, status: "retrying"|"delivered"|"failed", error?}` — one row per HTTP attempt (not one row per logical delivery): `"retrying"` means this attempt failed and another is scheduled, `"delivered"`/`"failed"` are terminal (a `"failed"` sequence is never retried again past its 5th attempt — no indefinite retry queue, matching this codebase's "every storage deliverable states its bound" convention even though this table is small/event-driven rather than a sampled ring). `POST /alert-rules/{id}/test` bypasses the retry loop entirely (a single delivery attempt, `attempt: 1`) so the Settings UI's "Test" button returns promptly.

## Tokens & Webhooks (T-1104, automation)

Vnprox-local, capability-scoped bearer tokens a logged-in user mints, plus webhook registrations that receive the same event envelope the WS `"events"` topic (below) carries over HTTP. Both are explicitly **not** a second login/authentication path (docs/security.md's "No vnprox-local accounts" is about *login*; a token is a delegated credential a logged-in session mints, distinguished from the PVE ticket bridge in docs/security.md's Authentication section) and have no frontend UI in this task — they are an automation-only surface T-1105 (`vnproxctl`)/T-1106 (Terraform/Ansible) build on, not a Settings page feature yet.

| Method | Path | Purpose |
|---|---|---|
| POST | `/tokens` | mint a token: `{name, scopes: [string]}` → `201` with the token `AND` a one-time `token` field carrying the raw bearer value — never retrievable again |
| GET | `/tokens` | list the caller's own tokens (no secret, ever): `{items: [Token]}` |
| DELETE | `/tokens/{id}` | revoke one of the caller's own tokens; `204`; force-closes any open WS subscription that token authenticated within the same request |
| POST | `/webhooks` | register a delivery target: `{url, events?: [string], secret}` → `201` with the created `Webhook` (secret never echoed back) |
| GET | `/webhooks` | list registrations (no secret): `{items: [Webhook]}` |
| DELETE | `/webhooks/{id}` | remove a registration; `204` |

**Auth/gating.** `POST/GET/DELETE /tokens` require only an authenticated session (cookie or bearer) — no specific capability, since the real bound is per-scope (below); mutating calls (`POST`/`DELETE`) require CSRF like every other cookie-authenticated write. `GET`/`DELETE` are scoped to the caller's **own** tokens only (filtered/checked by the minting user) — this repo's interpretation of an unspecified visibility question, made to avoid a needless cross-user information-disclosure/DoS surface; flagged in `planning/reports/T-1104.md`. `POST/GET/DELETE /webhooks` require the `automation` capability (`internal/auth.CapAutomation`) — since that capability is **never** derived from a PVE privilege (only ever present on a bearer token's own minted scopes, see `GET /auth/me`'s note above), these three routes are automation-token-only in practice: a browser session alone can never reach them, only a token minted via `POST /tokens` with `automation` in its scopes can.

**`Token`**: `{id, name, scopes: [string], createdBy, createdAt, lastUsedAt?, revokedAt?}`. `scopes` is drawn from the exact capability vocabulary `internal/auth/caps.go` already defines (`netRead`, `netWrite`, `sdnRead`, `sdnWrite`, `fwRead`, `fwWrite`, `guestNet`, `audit`) **plus** the new `automation` scope — no other privilege surface. **A token's scopes can never exceed the creating user's own derived capabilities at creation time**: `POST /tokens` validates each requested scope against the minting session's current `GET /auth/me`-equivalent capability set and 400s (`validation_failed`, unrecognized scope name) or 403s (`forbidden`, a real scope the session doesn't itself hold) otherwise — `automation` is the one exception, always grantable to any authenticated session (it isn't PVE-derived, so there is nothing for it to "exceed"). A bearer request authenticated by a token carries that token's scopes as its `Capabilities` (a single cluster-wide entry, no per-node granularity), is rate-limited per token (burst 60, refill 1/s by default), and is audited (`token.use`, `{tokenId, path, method}`) on every use, in addition to `token.create`/`token.revoke` on the lifecycle routes themselves.

**`Webhook`**: `{id, url, events?: [string], createdBy, createdAt, consecutiveFailures, lastAttemptAt?, lastSuccessAt?, lastError?}`. `events` is the optional event-name allowlist (omitted/empty = every event, the same optional-filter convention Alert Rules' `sourceFilter`/`severityFilter` use); values are the WS `"events"` topic's own event-name vocabulary (`changeset.status`, `drift.changed`, `findings.changed`, `audit.appended`). `secret` (create-only, never returned) is the HMAC signing key: every delivery carries `X-VNPROX-SIGNATURE: <hex HMAC-SHA256 of the exact request body under secret>` — mirroring the peer API's HMAC construction (docs/security.md's Transport section: HMAC-SHA256, hex-encoded, verified with a constant-time compare), simplified to just the body (no method/path/timestamp canonicalization) since this is always vnprox-as-caller against an external, caller-chosen URL, not a mutually-authenticated intra-cluster request. Delivery is retried with exponential backoff (1s doubling to a 30s cap, 5 attempts) exactly like Alert Rules' webhook delivery; only the *sequence's* final outcome (not each attempt) updates `consecutiveFailures`/`lastError`. **N (3) consecutive failed sequences** raise a `webhook_unhealthy` finding (`source: "health"`, computed live from this table each findings cycle, no second persisted flag); a subsequent successful delivery resets the counter to 0, clearing the finding on the next cycle.

## Embeds (T-1706)

Read-only, token-scoped embeds of the map, home dashboard, and posture report for wikis / NOC screens / status pages, plus the Grafana panels backed by the Metrics exporter (T-1001) and the WS `"events"` topic (T-1104). An embed token is an ordinary `api_tokens` row (the Tokens section above) whose scopes are **all read-only** — it can never exceed its minting user's scope and never carries a write surface. There is no new privilege surface and no schema change: "embed" is defined structurally by the read-only scope set, re-checked on every embed request.

| Method | Path | Purpose |
|---|---|---|
| POST | `/embed/tokens` | mint a read-only embed token: `{name, scopes: [string]}` → `201` with the token, an `embed: true` marker, `AND` a one-time `token` field carrying the raw bearer value (never retrievable again). Scopes are restricted to the read-only subset `{netRead, sdnRead, fwRead, audit}`; **any other scope (`netWrite`, `sdnWrite`, `fwWrite`, `guestNet`, `capture`, `automation`) is rejected `400` `validation_failed` regardless of the minting user's own capabilities**, before the ordinary per-scope ceiling check (a scope the minting session does not itself hold is still `403` `forbidden`). |
| GET | `/embed/map?token=` | HTML shell for the read-only map embed |
| GET | `/embed/dashboard?token=` | HTML shell for the read-only home-dashboard embed |
| GET | `/embed/posture?token=` | HTML shell for the read-only posture-report embed; served as a documented "not yet available" dark state (`200`, an HTML fragment carrying `data-embed-state="posture-unavailable"`) on an instance where posture scoring (T-1607) is not wired |

**Auth/gating.** `POST /embed/tokens` requires only an authenticated session (cookie or bearer) plus CSRF like every other cookie-authenticated write — the real bound is the read-only-scope restriction above. The `GET /embed/{view}` shell routes are a **distinct middleware path** from every session-cookie route: they authenticate the embed token from the **`?token=` query parameter only** (an `<iframe>` cannot set an `Authorization` header, and a first-party session cookie is never accepted in its place — this is enforced, not conventional), never the session cookie. A missing/unknown/revoked token is `401`; a token that carries any non-read-only scope is `403` (a write-capable automation token is not an embed token). The embedded view then calls the ordinary `netRead`/`sdnRead`/… -gated read routes with the same token as an `Authorization: Bearer` credential (the Tokens section's bearer path), so an embed token scoped narrower than its minting user never surfaces data above its own scopes — no parallel read path exists.

**Grafana panels.** The panel *render components* and their data contracts live in this repo (`web/src/grafana/`, tested against fixture scrapes/event streams with no live Grafana); the packaged/signed Grafana plugin (`plugin.json`, `module.ts`) lives in an external repo per the "contract not source" boundary T-1106/T-1705 use — see `web/grafana-panel/README.md`. The metrics panel consumes the Metrics-exporter subsection's `GET /metrics` body; the live event-annotation panel consumes the WS `"events"` topic.
## Tenants & self-service (T-1703)

Delegated, server-side-scoped views on the federation-era permission model: a tenant sees only its own guests/VLANs/subnets and its members can **request** changes that route to an approver. Tenant scoping is enforced server-side at the data-access layer (docs/security.md's Tenant-authorization note) — it only ever narrows a member's view, and it adds no mutation path around the change engine.

**Tenant management (admin).** Reads require `netRead`; mutations require `netWrite` + CSRF.

| Method | Path | Purpose |
|---|---|---|
| POST | `/tenants` | create a tenant: `{id?, name}` → `201` `Tenant` (id defaults to a ULID) |
| GET | `/tenants` | list tenants: `{items: [Tenant]}` |
| GET | `/tenants/{id}` | one tenant incl. its `scopes` and `members` |
| DELETE | `/tenants/{id}` | delete a tenant (cascades scopes/members/request linkages); `204` |
| PUT | `/tenants/{id}/scopes` | add a visible-resource ref: `{scopeRef}`; `204` |
| DELETE | `/tenants/{id}/scopes?scopeRef=` | remove a scope ref; `204` |
| PUT | `/tenants/{id}/members` | add/promote a member: `{identity, role}` (`member`\|`approver`); `204` |
| DELETE | `/tenants/{id}/members/{identity}` | remove a member; `204` |

**`Tenant`**: `{id, name, createdBy, createdAt, scopes: [string], members: [{identity, role}]}`. `scopes[]` are inventory Ref strings (a guest/subnet, or a coarse VLAN/VNet expanded to its members live at read time).

**Request-changesets & approval.** A tenant member requests a change instead of writing directly:

| Method | Path | Purpose |
|---|---|---|
| POST | `/changesets` (with `tenantId`) | create a request-changeset: `{tenantId, title, ops:[Op]}` → `201` `Changeset` with `status: "requested"`. Every op must target a Ref within the tenant's scope (else `403`); a non-member's `tenantId` is `404` (existence not confirmed). Raises a routed approval notification to the tenant's approver group (via alert routing, T-1005). |
| POST | `/changesets/{id}/approve` | an **approver** of the owning tenant converts a `requested` changeset to an ordinary `draft` (`200` `Changeset`). A plain member gets `403`; an approver approving **their own** request gets `403`; a nonexistent/non-request changeset is `404`. Approval is not apply — the approver then drives the ordinary draft → apply → confirm/rollback flow. |

The `requested` status is additive to the changeset lifecycle (docs/architecture §4): its only transitions are to `draft` (approve) or `discarded` (reject) — there is no path from `requested` to `applying`, so no request-changeset can ever reach apply without an approver first converting it.

**Scoped dashboard.** `GET /dashboard?tenantId=` (`netRead`) returns the caller's scoped tile counts `{tenantId, visibleRefs, guests, subnets, vnets}`, computed only from the caller's own tenant scope. Asking for a tenant the caller doesn't belong to is `404`.

**Scoped reads.** For a caller who is a tenant member, `GET /topology`, `/findings`, `/ipam/subnets`, `/flows`, `/inventory/search`, and `GET /inventory/{ref}` are all filtered server-side to the tenant's scope; an out-of-scope `GET /inventory/{ref}` (or `/ipam/subnets/{cidr}/allocations`) is `404`. An ordinary (non-tenant) caller is unaffected.

## Ceph (T-1503)

Added by T-1503 (`internal/ceph`, `internal/api/ceph.go`). **Read-only forever** (the same carried-forward invariant T-1501's Kubernetes section states for its domain, `docs/roadmap-universal.md`'s Phase 15 Invariants section): every read in this section goes through the existing `internal/pve.Client` (`GET /cluster/ceph/config`, `GET /nodes/{node}/ceph/osd` — no new Ceph API client, no new credentials, mirroring T-1206's "read the owning system's own knowledge of itself" pattern this task's card cites). There is no route anywhere in this section, no `ceph.*` changeset op anywhere in `internal/change`, and no code path anywhere in `internal/ceph` that can write to Ceph — PVE's own Ceph tooling (`pveceph`, the GUI's Ceph panel) keeps sole, permanent ownership of Ceph configuration.

| Method | Path | Purpose |
|---|---|---|
| GET | `/ceph/status` | the map-layer projection: public/cluster network CIDRs, per-OSD-hosting-node physical bond attribution, per-OSD bond attribution |

`GET /ceph/status` is `netRead`-gated, node-local graph re-projected fresh on every call (`internal/ceph.Project` is pure and cheap — no caching layer, so this always reflects the daemon's current topology, not a stale poll snapshot). A cluster with no Ceph installed at all returns `{nodes: [], osds: []}` with both network fields omitted — never an error.

**Response shape** (`internal/ceph.Overlay`, JSON): `{publicNetwork?, clusterNetwork?, nodes: [CephNodeAttribution], osds: [CephOSD]}`. `CephNodeAttribution`: `{node, publicCarrier?, publicPath?: [string], publicRidingOn?, publicMtu?, clusterCarrier?, clusterPath?: [string], clusterRidingOn?, clusterMtu?}` — one entry per node hosting at least one OSD. `*Carrier` is the `inventory.Ref` string of the interface (always a Bridge or VlanIface — the only two kinds that declare an `Addresses` field) whose address falls inside the declared CIDR; `*Path` is the full physical walk from that carrier down to its terminal PhysNic(s) (`internal/topology.ResolvePhysicalPath`, the same carrier→parent-bridge→bond-slaves→PhysNics resolver T-702's management-path visibility already established — reused here, not re-implemented); `*RidingOn` is the single bond ref if the path is bonded, or the sole terminal PhysNic ref if it rides one bare NIC — the "which bond does this ride" answer T-1503's card names, left unset (never guessed) when the path resolves to zero or more than one terminal NIC with no bond present. Every `*Carrier`/`*RidingOn`/path entry is omitted (empty string / absent), never a wrong guess, when that network's CIDR isn't declared or no interface on that node carries a matching address. `CephOSD`: `{ref, id, node, device?, up, in, publicBond?, clusterBond?}` — `ref` is the OSD's own first-class `inventory.Ref` string (`Kind` `ceph-osd`, `"osd<id>"` scoped to `node` — docs/data-model.md §1), not itself graph/provenance-tracked (mirroring `VirtualFunction`'s identical pattern) but round-trippable through `GET /inventory/{ref}` the same as every other Ref this API surfaces. `publicBond`/`clusterBond` denormalize that OSD's node's own `publicRidingOn`/`clusterRidingOn` so the inspector/map layer never needs a second node lookup to answer "which bond does this OSD ride".

**Traffic attribution**: this package does not implement its own flow-classification logic — it registers `PublicNetwork`/`ClusterNetwork` with T-1504's `internal/flow.Classifier` via the generic `flow.NewCIDRSource(flow.NetworkSourceKindCeph, flow.ServiceClassCephPublic/CephCluster, ...)` constructor (`cmd/vnproxd/cephwire.go`), so `GET /flows`'s `serviceClass` field (see the Flows section above) tags `ceph-public`/`ceph-cluster` traffic the same way every other classified service does.

**Findings** (`source: "health"`, extending T-803's pack, same continuously-computed, hysteresis-gated convention — 2-cycle rise/fall, `docsLink` → `docs/features/monitoring.md#5-health-checks`): `ceph_corosync_shared_link` (a node's corosync ring address, from `corosync.conf`'s static ring addresses — the same substrate T-803's `corosync_link_degraded` check and T-1504's classifier already read — resolves to a carrier sharing at least one terminal physical NIC with that node's resolved Ceph cluster-network carrier: combined replication and quorum-heartbeat traffic risks saturating the shared link), `ceph_cluster_mtu_mismatch` (OSD-hosting nodes' resolved Ceph cluster-network carrier MTU disagrees — majority-vote comparison via `internal/xnode.MajorityInt`, the same tie-breaking rule `mtu_consistency`'s cross-node bridge comparison uses, reused directly rather than re-implemented, since Ceph's per-node cluster-network carrier is frequently a *different*-named interface across nodes and so cannot reuse `internal/xnode.CrossNodeMTU`'s same-named-bridge grouping itself), `ceph_single_nic` (an OSD-hosting node's Ceph public and cluster traffic both resolve to the exact same single, unbonded terminal NIC — no redundancy for either network). All three are `fixable: false` (no changeset op can safely re-cable or re-declare a Ceph network on the operator's behalf) and silent when the corresponding condition isn't met — never a guess when a carrier can't be resolved at all.

## Failure-impact simulation (T-1604)

Added by T-1604 (`internal/failsim`, `internal/api/failsim.go`). **Pure read-only simulation forever**: it answers "what breaks if X dies?" by removing an entity from a *copy* of the live inventory snapshot and recomputing connectivity — it never induces a failure, never mutates, and never persists a result (`Impact`/`SPOFEntry` are computed fresh over the current snapshot on every call, the same "never a shadow copy" boundary the Ceph overlay follows). There is no `failsim.*` changeset op anywhere in `internal/change`.

| Method | Path | Purpose |
|---|---|---|
| GET | `/failsim/spof-score` | the standing single-point-of-failure dashboard tile: `{score, entries: [SPOFEntry], generatedAt}` |
| POST | `/changesets/{id}/preflight-impact` | the failure impact of a changeset's worst-affected touched entity — the hook T-1103's scheduler consults at `windowStart`; `404 not_found` if `id` names no changeset |

Both are `netRead`-gated (read-only synthesis). `GET /failsim/spof-score` enumerates every node, bond, uplink bridge, uplink NIC, LLDP-discovered switch, and (where a WireGuard tunnel model is supplied) tunnel, simulates each element's removal, and returns those with a nonzero *known* impact — a purely-redundant element (its removal breaks nothing) is excluded. `score` is `100` minus each SPOF's severity weight, floored at `0` (fewer/lower-impact SPOFs score higher — the property T-1607's posture score consumes).

**`Impact`** (`internal/failsim.Impact`, JSON): `{target, severity, disconnectedGuests: [string], strandedVlans: [string], mgmtPathLoss: [string], notEvaluated: [string], quorumRisk, cephRisk}`. `target` and the ref slices are `inventory.Ref` strings (round-trippable through `GET /inventory/{ref}`); `mgmtPathLoss` is a list of node names. `severity` is `none`\|`info`\|`warning`\|`critical` — a coarse rollup, never a substitute for the structured fields.

**`notEvaluated` is the load-bearing honesty channel** (the "no silent approximation" contract `docs/features/firewall.md` §5/§6 binds every simulator in this codebase to): where a dimension cannot actually be assessed, its code appears here rather than the simulator emitting a confident "no impact". Codes: `quorum` (no corosync config, or a voting node's ring address resolves to no interface), `ceph` (no Ceph read model, or Ceph declares no networks), `tunnels` (no WireGuard tunnel model supplied), `guest-connectivity` (one or more guests have an unresolvable NIC attachment). A caller — including T-1103's scheduler — must treat a dimension named here as unknown, never as safe.

**`SPOFEntry`**: `{ref, impact}`. **Management-path loss** is computed by re-running the *shared* resolver (`internal/topology.ResolveMgmtPaths`, via `change.DetectProtectedRoles`) against the post-failure snapshot — the same function `GET /protected-interfaces/status` and the T-703 interlock use, never a parallel notion of "management connectivity". **Quorum risk** is computed from the corosync ring topology (a removal that drops reachable voting nodes below `floor(N/2)+1`). **Ceph risk** reuses T-1503's `internal/ceph.Project` read model over both snapshots (a node isolated from Ceph's public or cluster network).

**T-1103 pre-flight integration**: the scheduler calls the equivalent of `POST /changesets/{id}/preflight-impact` at `windowStart` re-validation and aborts an unattended apply on `quorumRisk` or nonempty `mgmtPathLoss`, audited distinctly (`changeset.schedule_fire_blocked` result `failure_impact_quorum_risk`/`failure_impact_mgmt_path_loss`). This is **additive** to — never an override of — T-1103's existing `touchesMgmtPath` exclusion, which is evaluated first and unconditionally: a changeset the failure-impact model rates "safe" that also touches the mgmt path still gets blocked. A pre-flight error fails closed (the unattended apply is aborted), since an unassessable impact is not a proof of safety.

## Posture score & report (T-1607)

Added by T-1607 (`internal/posture`, `internal/api/posture.go`, `internal/store/posturescores.go`). One periodically-recomputed network security/resilience score with **named, independently-inspectable** contributing factors — never an opaque single number. A supervised job (default daily) folds five surfaces into a score and persists it to the bounded `posture_scores` table (docs/data-model.md §2); the export extends T-605's `internal/docexport` renderer with a posture section rather than introducing a parallel one.

| Method | Path | Purpose |
|---|---|---|
| GET | `/posture` | the latest computed score: `Posture` (below); `404 not_found` before the first scheduled computation has run |
| GET | `/posture/history?limit=` | the bounded trend, newest first: `{items: [Posture]}` (`limit` defaults to 90, capped at 400) |
| GET | `/export/posture?format=md\|html` | the score + factor table + trend sparkline as a standalone Markdown or HTML report (`Content-Disposition: attachment`); `400 validation_failed` for any other `format`; `404 not_found` before the first computation |

All three are `netRead`-gated (a posture score is a derived, read-only artifact recomputed on a schedule, never written through a request).

**`Posture`** (`internal/posture.Posture`, JSON): `{overall, qualified, computedAt, factors: [Factor]}`. `overall` is `0..100`, the weighted mean of the **evaluated** factors only. **`qualified`** is the load-bearing honesty flag: `true` means at least one dimension could not be fully assessed, so the score is partial and must **not** be read as a clean bill of health.

**`Factor`**: `{name, detail, caveat?, value, contribution, weight, scorePct, evaluated}`. The five `name`s are `spof_resilience` (T-1604's SPOF inventory), `segmentation` (fraction of guests carrying an *applied* T-1602 microsegmentation policy — a merely-proposed/dry-run policy counts unsegmented, since only applied rules appear in the resolved firewall view), `exposed_ports` (guest-scope inbound rules permitting any-source access with no narrower rule ahead, via `internal/fw`'s resolver), `anomaly_rate` (T-1601 `source: "baseline"` findings per guest), and `drift_hygiene` (`GET /drift` open-finding count per node). Each factor's `weight`/`value`/`scorePct`/`contribution` are independently inspectable — the score is never folded into one number with no factors.

**Honesty contract** (inherited from `internal/failsim`/`internal/sim`'s "no silent approximation"): a factor that cannot be assessed at all — a cold-start `anomaly_rate` with no learned baseline profiles, where "zero anomalies" means "we have never looked" — is reported `evaluated: false` with `scorePct: -1`, `contribution: 0`, a `caveat`, and is **excluded** from `overall` rather than silently contributing a perfect 100. A factor computed over an incomplete underlying picture (`spof_resilience` when failsim reports `notEvaluated` dimensions) still counts but carries a `caveat` marking the score a ceiling. Either case sets `qualified: true`.

## Plugins (T-1702)

Added by T-1702 (`internal/plugin`, `internal/api/plugins.go`, `internal/store/plugins.go`). A capability-scoped extension SDK: stable, versioned extension points third parties implement — switch drivers, flow ingestors, finding producers, ingress discoverers, and dashboard tiles — installed into a registry with an audited capability scope. The registry is **not a second mutation path**: the only change-engine surface handed to plugin code is stage-only (`Create`/`Validate`), never `Apply`/`Confirm`/`Rollback`. See `docs/architecture.md` §11 (extension points + deprecation policy) and `docs/security.md` (plugin capability-scope model).

| Method | Path | Cap | Purpose |
|---|---|---|---|
| GET | `/plugins` | `netRead` | list installed plugins: `{items: [Plugin]}`, newest first |
| POST | `/plugins/{id}/enable` | `netWrite` + CSRF | re-enable a disabled plugin's extension points; `204`, `404 not_found` for an unknown id |
| POST | `/plugins/{id}/disable` | `netWrite` + CSRF | stop dispatching a plugin without uninstalling it; `204`, `404 not_found` |
| DELETE | `/plugins/{id}` | `netWrite` + CSRF | uninstall a plugin (tears down any out-of-process subprocess); `204`, `404 not_found` |

Installing a plugin (loading code / spawning a subprocess) is a config-time / Hub (T-1705) operation and is **not** a bare API write here. Every lifecycle transition — `plugin.install`/`plugin.enable`/`plugin.disable`/`plugin.uninstall` — writes an audit row recording the plugin's capability scope.

**`Plugin`** (JSON): `{id, name, version, apiVersion, transport, extensionPoints, capabilities, installedBy, installedAt, enabled}`. `apiVersion` is the frozen SDK interface version the plugin was built against (`"v1"`); `transport` is `"in-process"` or `"grpc"` (an out-of-process supervised subprocess); `extensionPoints` is a subset of `switchDriver`/`flowIngestor`/`findingProducer`/`ingressDiscoverer`/`dashboardTile`; `capabilities` is the declared capability scope (a subset of the `caps.go` vocabulary) — the **ceiling** on which seams the plugin may touch and which change-engine op classes it may stage. The internal launch `endpoint` is deliberately omitted from the response.

### Hub (T-1705)

The Hub install path (`POST /hub/install` with `type: "plugin"`) is how a plugin is installed from the public registry. It verifies the downloaded manifest's Ed25519 signature against the same trust store blueprint bundles use, then registers it through this exact plugin registry (`Registry.Install`, which independently re-validates the capability scope) — the Hub adds no bypass around the scope check. See the **Hub (T-1705)** section below for the routes and the trust gate.

## Hub (T-1705)

Added by T-1705 (`internal/hub`, `internal/api/hub.go`). An **opt-in client** for a public registry of signed blueprint bundles (T-1107) and SDK plugins (T-1702): browse, then install with signature verification and a per-installation trust decision. **This repo ships the client and the registry-index contract, not the registry service** — the registry (index + artifact hosting) lives in a separate repo (mirrors T-1106's provider/collection-source boundary). The Hub is a catalog/install-orchestration layer, **not a new trust boundary**: it inherits T-1107's signature + trust-store gate and T-1702's capability-scoped registry wholesale; it never introduces an implicit-trust path.

The Hub is off unless `[hub] registry_url` is configured (`packaging/config/vnprox.toml`); with no registry configured its routes are not mounted.

| Method | Path | Cap | Purpose |
|---|---|---|---|
| GET | `/hub/index` | `netRead` | proxy/cache the registry index; `?type=blueprint\|plugin` filters. Returns `{items: [HubEntry]}`. `400 validation_failed` for an unknown `type`; `502 registry_unavailable` if the registry can't be reached |
| POST | `/hub/install` | `netWrite` + CSRF | download and install the named entry: `{type, id, version?, trustUnsigned?, trustNewKey?}` |

**Registry index contract** (`GET <registry>/index.json`, the shape this card specifies but does not host): `{schemaVersion: 1, entries: [{type, id, name, version, publisher?, description?, artifactUrl, signature?, transport?, capabilities?, extensionPoints?}]}`. `artifactUrl` must resolve to the registry's own host (an off-host artifact URL is refused — the fetched index is not signed as a whole, so it can never redirect an install off-origin). `signature` is the publisher's signer identity for display/vetted-badge; the **authoritative** signature gate is the downloaded artifact's own signature.

**`HubEntry`** (JSON): `{type, id, name, version, publisher?, description?, artifactUrl, signerFingerprint?, transport?, capabilities?, extensionPoints?, signed, vetted}`. `vetted` means the entry's signer fingerprint is in this node's `[hub] vetted_signers` allowlist — **purely informational**; it never bypasses the trust decision (a vetted-but-untrusted signer still requires an explicit trust step). `capabilities`/`extensionPoints`/`transport` are populated for plugins so an operator can review a plugin's declared capability scope before confirming an install.

**`POST /hub/install`** — the install runs the same gate as a direct import/plugin-install:
- **blueprint**: downloads the bundle and runs it through T-1107's *exact* `POST /blueprints/import` path (verify → trust decision → save), reused not duplicated. Response mirrors that route: `{type: "blueprint", status: "imported"|"unsigned"|"untrustedSignature"|"invalidSignature", blueprint?, signer?}`. An unsigned or untrusted-signer bundle returns the corresponding status (a normal `200`) and is **not** installed unless the request sets `trustUnsigned: true` / `trustNewKey: true`. Audited as `blueprint.import` (identical shape to a direct import).
- **plugin**: downloads the `{manifest, signature}` artifact, verifies the Ed25519 signature over the canonical manifest against the same trust store, applies the identical unsigned/untrusted/invalid gate, then — only once trust permits — installs the manifest through T-1702's registry (which re-validates the capability scope). Response: `{type: "plugin", status: "installed"|"unsigned"|"untrustedSignature"|"invalidSignature", plugin?, signer?}` where `plugin` is `{id, name, version, capabilities, extensionPoints}`. Audited as `hub.install`.

`404 not_found` if no index entry matches `type`+`id` (+`version` when given). `501 not_available` if the node isn't configured for that install type (blueprint installs need the blueprint service + trust store; plugin installs need the plugin installer + trust store). Only out-of-process (`grpc`) plugins are installable from the Hub — an in-process plugin is build-time Go code and cannot be materialized from a downloaded manifest.

## Kubernetes (T-1501)

Added by T-1501 (`internal/k8s`, `internal/api/k8s.go`, `internal/store/k8sclusters.go`). **Read-only forever** (carried-forward invariant, `docs/roadmap-universal.md`'s Phase 15 Invariants section): a minimal, hand-rolled kubeconfig parser + `net/http`-only REST client (deliberately not `client-go` — see `internal/k8s`'s package doc comment for the flagged new-dependency decision) that issues exclusively `GET` requests against a registered cluster's `/api/v1/nodes`, `/api/v1/pods`, `/api/v1/services`, and `/apis/apps/v1/namespaces/kube-system/daemonsets`. There is no route anywhere in this section, and no code path anywhere in `internal/k8s`, that can write to a k8s cluster — POST/DELETE below only ever add/remove vnprox's own *local* registration row.

| Method | Path | Purpose |
|---|---|---|
| GET | `/k8s/clusters` | list every registered cluster: `{items: [K8sCluster]}` (kubeconfig never echoed back) |
| POST | `/k8s/clusters` | register a cluster: `{name, kubeconfig}` → `201` with the created `K8sCluster`; `400 validation_failed` if `name` is empty or `kubeconfig` doesn't parse/resolve to a usable credential |
| DELETE | `/k8s/clusters/{id}` | deregister a cluster; `404 not_found` if `id` doesn't name a cluster (unlike most delete routes in this doc, existence is checked first so a genuinely-absent id is distinguishable from an idempotent re-delete in the audit log) |
| GET | `/k8s/{clusterId}/overlay` | live poll: pod CIDR / node<->guest correlation / detected CNI / NodePort-exposure findings, computed fresh on every call (never cached as authoritative — see below) |

`GET /k8s/clusters` and `GET /k8s/{clusterId}/overlay` are `netRead`-gated; `POST`/`DELETE /k8s/clusters` are `netWrite` + CSRF — the same split every other read/write route family in this doc uses. Registering a cluster is audited `k8s.cluster.add`; deregistering is audited `k8s.cluster.remove`.

**`K8sCluster`**: `{id, name, addedBy, addedAt, cniDetected, status}`. `kubeconfig` is accepted only on create (raw kubeconfig YAML text) and is never returned by any route in this section, plaintext or encrypted — encrypted at rest with the identical AES-256-GCM primitive `sessions.pve_ticket_enc`/`alert_rules.target_secret_enc`/`ingress_targets.credential_enc`-shaped columns elsewhere in this codebase use (`internal/store/cipher.go`'s `SessionCipher`, not a second cipher or key pair). `cniDetected` (`"flannel"`\|`"calico"`\|`"cilium"`\|`"unknown"`\|`""` before the first poll) and `status` (`"unpolled"`\|`"ok"`\|`"unreachable"`) are the last poll's own cached summary — purely so `GET /k8s/clusters` can render a listing without a live poll on every call; they are never treated as authoritative by `GET /k8s/{clusterId}/overlay`, which always recomputes fresh (docs/architecture.md §7's new-domain invariant, identical to every other app-owned registration table in this codebase).

**`GET /k8s/{clusterId}/overlay` response** (`internal/k8s.Overlay` plus the poll's own findings): `{clusterId, cni, podCidrs: [{node, cidr}], services: [{namespace, name, type, clusterIp?, ports: [{name?, port, nodePort?, protocol}]}], pods: [{namespace, name, node?, podIp?, phase?}], nodes: [{k8sNode, internalIp?, guestRef?, matched}], generatedAt, nodePortFindings?: [K8sNodePortFinding]}`. `podCidrs` is real, per-node data (`Node.spec.podCIDR`/`podCIDRs`, as advertised by the cluster's own API) — this route deliberately **never** claims a "service CIDR": none of the four endpoints this client reads exposes kube-apiserver's own service-CIDR flag, so computing one by bounding-boxing observed `ClusterIP`s would be a guess dressed up as a fact (see `internal/k8s`'s package doc comment, "Pod/service network model" section, for the full reasoning). `nodes[].matched`/`guestRef` is T-1501 AC2's node<->guest correlation: a k8s node's reported `InternalIP` resolved against the same IPAM-allocation-based lookup `GET /edge/nat`/`GET /ingress/status` use elsewhere in this codebase — `matched: false` (never a wrong `guestRef`) when nothing in the live inventory/IPAM data claims that address. `503`/`502`-shaped failure: a poll that cannot reach the cluster at all (network error, auth failure, stored kubeconfig no longer parses) returns `502 k8s_unreachable` rather than a partial/empty overlay, and marks the cluster's cached `status` `"unreachable"`.

**`K8sNodePortFinding`** (also surfaced in the unified stream, `GET /findings`'s `source: "k8s"`, `check: "k8s_nodeport_exposed_without_fw_rule"` — see the finding-shape section above): `{clusterId, namespace, service, port, nodePort, proto, refs: [string], detail}`. Fires once per NodePort/LoadBalancer service port that has at least one correlated (`matched: true`) k8s node whose backing PVE guest — or the cluster-scope firewall ruleset every guest also sees — carries no enabled, inbound, `ACCEPT` rule covering that port; `refs` names every such uncovered guest's ref. A service/port with zero matched nodes produces no finding either way (this check never asserts anything about a node it cannot resolve to a guest). Metadata-only, no live probe and no payload inspection, the same honesty contract every other check in this codebase follows.

**CNI detection** (`internal/k8s.DetectCNI`, best-effort): Calico (`calico-node` DaemonSet in `kube-system`) and Cilium (`cilium` DaemonSet in `kube-system`) are recognized from their default install's own DaemonSet name; Flannel is recognized from the `flannel.alpha.coreos.com/backend-type` node annotation its kube-subnet-manager writes. Anything else — a different CNI, a non-default install, or no recognizable marker at all — reports `"unknown"` rather than guessing.

## Federation (T-1201 registry, T-1202 global read surfaces)

Added by T-1201 (`internal/federation`, `internal/api/federation.go`, `internal/store/clusters.go`) and T-1202 (`internal/api/federationtopo.go`). Federation federates *views and workflows*, never config ownership: Proxmox stays each attached cluster's own source of truth, and **there is no cross-cluster mutation primitive** anywhere in this section — every route here is a read/aggregate or a change to vnprox's own local registry row, never a write to an attached cluster's config.

**Cluster registry (T-1201)** — one app-owned row per attached cluster; the PVE credential is sealed at rest with the identical AES-256-GCM primitive `sessions.pve_ticket_enc` uses and is never returned by any route:

| Method | Path | Description |
|---|---|---|
| GET | `/federation/clusters` | list attached clusters: `{items: [Cluster]}` (credential never echoed) |
| POST | `/federation/clusters` | attach a cluster: `{name, apiUrl, credential}` → `201` with the created `Cluster`; `400 validation_failed` on a bad body/credential |
| GET | `/federation/clusters/{id}` | one attached cluster (credential-free); `404 not_found` if absent |
| PUT | `/federation/clusters/{id}` | edit name/apiUrl and, only when `credential` is present, re-seal it (a rename never forces re-entering the token); `404 not_found` if absent |
| DELETE | `/federation/clusters/{id}` | detach a cluster; `204` whether or not it existed |

**`Cluster`**: `{id, name, apiUrl, status, addedBy, addedAt, wgTunnelId?, wgTunnelSource?}`. `credential` is accepted only on create/update — one of `{kind:"ticket", username, password, realm?}` or `{kind:"token", token}` — and never returned. GET routes are `netRead`-gated; POST/PUT/DELETE are `netWrite` + CSRF. Attach/edit/detach are audited `federation.cluster.add`/`.update`/`.remove`.

**Tunnel-aware federation transport (T-1407).** `PUT /federation/clusters/{id}` additionally accepts an optional `wgTunnelId` (a T-1401 tunnel id this daemon manages) marking that cluster as reachable only via that WireGuard tunnel — omitting the field leaves the existing linkage untouched, an explicit `""` clears it, the same convention `credential` already uses. When the linked tunnel's live handshake goes stale, `internal/federation.Aggregator` excludes that cluster from `GET /federation/topology`, `GET /audit`, and the cross-cluster IPAM conflict view **without** adding it to those responses' `partial`/`failedClusters` — instead, exactly one `tunnel_down_peer_unreachable` finding (`source: "federation"`, see the `GET /findings` finding shape below) names the cluster and tunnel, collapsing what would otherwise be three redundant per-surface "unreachable" signals for the same root cause. It carries no `fix` — the only remediation is a human applying an ordinary `wg.*` changeset through the tunnel's own editor; nothing re-applies or restarts a tunnel automatically. A cluster with no `wgTunnelId` set is entirely unaffected — it keeps T-1201's ordinary unreachable-cluster handling.

**Where a cluster's tunnel linkage comes from — `wgTunnelSource`.** The same fact is recorded at two granularities: a WireGuard peer can be annotated with the federation cluster it *is* (`wireguard_peers.cluster_id`, carried on the ordinary `wg.peer.add` op as `clusterId`), and a cluster can name the tunnel it is *reached over* (`clusters.wg_tunnel_id`). Rather than letting the two drift, every read resolves **one effective linkage**: an explicit `wgTunnelId` set through `PUT /federation/clusters/{id}` always wins; otherwise the linkage is derived from a peer tagged with this cluster. Responses report which applies as the read-only `wgTunnelSource`: `"explicit"` or `"peer"` (absent when the cluster isn't tunnel-linked at all, as `wgTunnelId` then is too). Everything downstream — the aggregator's suppression and the `tunnel_down_peer_unreachable` finding — consumes that one effective value, so they cannot disagree about which tunnel a cluster rides. Two consequences worth knowing: `PUT` always writes the *explicit* column, never the derived link, so clearing `wgTunnelId` with `""` on a cluster that still has a tagged peer leaves it linked (now sourced `"peer"`) — undoing a peer-derived link means retiring or retagging that peer through an ordinary `wg.peer.*` changeset; and when the same cluster is tagged on peers of two different tunnels, the lowest tunnel id wins deterministically, so the derived link never flaps between reads. The connect-clusters wizard's optional "Federated cluster" field on its *Other side* step is the UI for this: picking a cluster there tags the peer inside the very changeset that creates the tunnel, so the linkage lands if and only if that changeset is applied — no side-channel write to the cluster registry.

**`GET /findings` finding shape, `source: "federation"` (T-1407).** Its own top-level source (like `flow`/`probe`/`capacity`), since it names a federation cluster rather than a node/interface the inventory graph knows about. Sole check: `tunnel_down_peer_unreachable` — `id` is `"federation:tunnel_down_peer_unreachable|<clusterId>"`, `refs` names the linked tunnel (`"wg-tunnel:<node>:<ifName>"`, the same ref `source: "wireguard"` findings use), `nodes` names the tunnel's node, severity `warning`, `fixable: false`, `docsLink` points at this section. Hysteresis-debounced identically to `wg_handshake_stale` (2-cycle rise/fall) so a single missed poll doesn't flap it.

**`GET /findings` finding shape, `source: "peer"` (T-1906).** Its own top-level source (like `federation`), since it describes the cluster's peer transport rather than a node/interface the inventory graph knows about — and because the untrusted case must be legible as a security signal, not buried in generic `health`. Three checks, all `fixable: false` (a certificate trust problem is never something a generated changeset should paper over), all with `docsLink` pointing at `docs/security.md`'s Transport section:

| check | id | severity | when |
|---|---|---|---|
| `peer_untrusted` | `peer:peer_untrusted\|<node>` | `error` | that peer answered on the peer API port and its certificate did not verify against the pinned cluster CA. **Not** hysteresis-debounced — a security signal is not a noisy counter (the same treatment `source: "rogue"` gets) |
| `peer_unreachable` | `peer:peer_unreachable\|<node>` | `warning` | nothing answered. 2-cycle rise/fall debounce, so one missed poll does not flap it |
| `peer_trust_degraded` | `peer:peer_trust_degraded\|<cause>` | `warning`/`error` | this daemon's own posture is weaker than the pinned default. `<cause>` is `unpinned` (an explicit `[peer] tls_trust = "system"`, or a caller-supplied HTTP client), `unverified` (`tls_trust = "insecure"`), `anchor_unavailable` (the pinned CA is unreadable, so peer TLS fails closed), or `plaintext` (the peer client dials `http`). Causes are independent findings, so two simultaneous problems never hide one another |

`peer_untrusted` and `peer_unreachable` name the affected peer in `nodes` and carry `refs: ["peer:<node>"]`; `peer_trust_degraded` names the local node, since it describes this daemon's configuration.

**Global read surfaces (T-1202)** — backed by `internal/federation.Aggregator`, which fans reads out to every attached cluster's own `internal/pve.Client` concurrently with per-cluster failure isolation. Every response carries the standard `partial`/`failedClusters` envelope (mirroring `/audit`'s `partial`/`failedNodes` peer fan-out): a single unreachable cluster degrades its own contribution — never blanks the whole response. All three are `netRead`-gated reads (no CSRF). They are mounted only when federation is wired; a single-cluster deployment (zero attached clusters) never exposes them, and the frontend keeps its existing per-cluster topology unchanged until a *second* cluster is attached.

| Method | Path | Description |
|---|---|---|
| GET | `/federation/topology` | per-cluster capsule summaries: `{clusters: [ClusterSummary], partial?, failedClusters?}`. Always cheap (a `/cluster/status` + `/cluster/resources` fan-out per cluster) — one summary per attached cluster, including unreachable ones (`reachable:false`, so the capsule renders greyed rather than dropping). |
| GET | `/federation/topology/clusters/{id}` | one cluster's full projected topology, fetched lazily on drill-down: the same body `GET /topology` returns, projected from that cluster's PVE API alone (nodes, PVE-parsed network, guests, SDN). `404 not_found` for an unknown id; `502 cluster_unreachable` if the attached cluster can't be reached/projected. |
| GET | `/federation/search?q=` | cluster-namespaced global entity search: `{results: [SearchHit], partial?, failedClusters?}`. Fans a substring query (node names, guest names, VMIDs) out to every attached cluster; a blank query returns no results without any fan-out. |

**`ClusterSummary`**: `{clusterId, clusterName, reachable, nodes, nodesOnline, guests, findings, drift}`. `findings`/`drift` are the summary altitude's honest, PVE-observable health signal (an offline member node counts as one finding and sets `drift`); deeper per-cluster findings/drift analysis lives behind the full drill-down projection, not the capsule summary.

**`SearchHit`**: `{clusterId, clusterName, ref, kind, label, node, matchedField}` — a single-cluster `SearchResult` plus the `clusterId`/`clusterName` the command palette groups by. `ref` is an inventory Ref triplet unique within its own cluster; `(clusterId, ref)` is globally unique.

## Migration planner (T-1507)

Added by T-1507 (`internal/migration`, `internal/api/migration.go`). A **purely advisory, read-only** pre-flight bandwidth-headroom check for a live migration/evacuation an operator is about to trigger *in PVE itself*: bandwidth headroom on the migration network versus a guest's configured RAM size and a best-effort dirty-page-rate estimate, warning before a Friday-night evacuation saturates a shared link. It never triggers, blocks, or otherwise participates in an actual migration — there is no code path anywhere in `internal/migration` that calls a PVE migration-start/evacuate endpoint (a mechanical regression test asserts this: the package's only PVE-facing interface, `GuestConfigReader`, exposes exactly one read-only method).

| Method | Path | Purpose |
|---|---|---|
| POST | `/migration/preflight` | pre-flight assessment: `{guest, targetNode}` -> `Assessment` |

`POST /migration/preflight` is `netRead`-gated (a live-network-state read, not a mutation — the same class of route `POST /simulate/path` already is). Request body: `{guest: string, targetNode: string}` — `guest` is a guest `Ref` string (`"guest:<node>:<vmid>"`); `400 validation_failed` if `targetNode` is empty or `guest` doesn't parse to a `guest`-kind `Ref`.

**`Assessment`** (the pinned response shape both this route and `internal/migration.Planner.Plan` return — the stable interface Phase 16's `T-1604` failure-impact simulator, and through it the already-shipped `T-1103` maintenance scheduler, depend on): `{headroomMbps, estimatedTransferSec, verdict, bestEffort, caveats}`. Every field is always present; `caveats` is an empty array (never omitted, never `null`) when nothing needs flagging.

- `headroomMbps` (number): estimated spare bandwidth on the resolved migration-network proxy (see below) after subtracting current `serviceClass: "migration"` traffic volume (T-1504's classifier) — never negative, floored at 0.
- `estimatedTransferSec` (number): guest RAM size (bits) divided by `headroomMbps` — the documented sentinel **`-1`** when `headroomMbps` is `0` (no finite estimate is possible).
- `verdict` (string): `"ok"`\|`"tight"`\|`"insufficient"` — advisory only, never causes or blocks any action. `"insufficient"`: no headroom remains, the estimated dirty-page rate would exceed it (migration may not converge), or the resolved link is severely degraded. `"tight"`: headroom is thin relative to the estimated dirty-page rate, or the link shows mild latency/loss degradation. `"ok"`: ample headroom.
- `bestEffort` (bool): **unconditionally `true`** on every response — this arc has no live guest instrumentation (no dirty-bitmap read, no QMP `query-migrate` telemetry); the dirty-page-rate figure is a fixed, documented fraction of the guest's configured RAM, a heuristic proxy, never a measurement.
- `caveats` (`[string]`): human-readable notes on which inputs were estimated, substituted, or unavailable (e.g. "no shared bridge with resolvable NIC speed found ... assuming a conservative 1000 Mbps link", "the corosync link between pve1 and pve2 shows elevated latency/loss ...", "the dirty-page rate ... is a best-effort estimate ... derived only from PVE's own guest config").

**"The migration network" — a proxy, not a live PVE reader.** No live reader of PVE's own `datacenter.cfg` `migration: network=...` exists anywhere in this codebase (the same documented gap `internal/flow/classify.go`'s `NewMigrationNetworkSource` doc comment and `internal/latmesh`'s package doc comment both already carry — see `planning/reports/needs-hardware-validation.md`'s T-1303 entry). Absent that reader, `Plan` resolves two proxies instead, both flagged in `caveats` whenever used:

- **Capacity**: the highest-capacity bridge the source and target node carry in common (`internal/xnode.BridgesByName`, the identical shared-bridge grouping T-1303's own guest-fabric `Discoverer` already uses), summing that bridge's member `PhysNic`/`Bond` `speedMbps` on each node and taking the lesser of the two nodes' figures — the same bridge migration traffic actually rides when (the common case) no dedicated migration network is configured. Falls back to a conservative 1000 Mbps assumption when no such shared bridge resolves.
- **Congestion**: T-1303's latency mesh has no distinct migration fabric either (only `"corosync"` and `"guest"` — see the Latency mesh section above), so `Plan` reads the corosync fabric's rolling loss/RTT first — the literal risk this task exists to warn about, "a Friday-night evacuation saturates the corosync link" — falling back to the guest fabric otherwise, and derates the resolved capacity by the observed loss percentage.

**Guest inspector integration**: the guest inspector's migration action surfaces this pre-flight check before the operator confirms a migration in PVE itself — vnprox never triggers or manages the migration; this stays a read-only advisory call, consistent with `docs/architecture.md`'s "Proxmox is the source of truth" invariant.

## WebSocket `/api/ws`

One connection multiplexes all topics; every frame (both directions) is a JSON text message.

**Client → server (subscribe).** The only client message is `{"subscribe": ["topology", "changesets", "metrics:<ref>", "tasks", "firewall.log", "flows", "events"]}`. Each subscribe message **replaces** the connection's entire topic set (it is not additive); an empty array unsubscribes from everything. Malformed messages are ignored. **`"events"` (T-1104)** additionally requires the connection's session/token to carry the `automation` capability — a subscribe request naming `"events"` from a connection that doesn't is silently dropped from that connection's topic set (it simply never receives anything on it), the same fail-closed, ack-less treatment a malformed message gets.

**Server → client (events).** Each event is a **flat** JSON object carrying the event name in an `"event"` field with the payload fields alongside it at the top level — there is no nested payload wrapper. Example `topology.delta` push:

```json
{"event": "topology.delta", "added": [], "updated": ["node/pve1/iface/vmbr0"], "removed": []}
```

(Producers: `internal/topology/hub.go` `deltaEvent`, `internal/change/service.go` `statusEvent`; consumer: `web/src/api/ws.ts`. All future event producers must keep this envelope.)

| Event | Payload fields (alongside `event`) |
|---|---|
| `topology.delta` | `{added, updated, removed: [Ref]}` — Refs as strings; client refetches affected |
| `changeset.status` | `{id, status, confirmDeadline?}` — `confirmDeadline` is unix seconds, omitted unless `awaiting_confirm`; drives the confirm countdown UI |
| `metrics.sample` | `{ref, at, rates}` |
| `drift.changed` | `{count}` |
| `firewall.log.batch` | `{entries: [FwLogEntry], droppedTotal}` — pushed by `internal/fwlog.Service`'s poll loop whenever new log lines were parsed since the previous tick; `entries` is already rate-capped (see the `GET /firewall/log` section above for both shapes) — a client subscribed to `firewall.log` should append `entries` to its own bounded, client-side-capped view and show `droppedTotal` as the storm/drop indicator, never render an unbounded list |
| `findings.changed` | `{count}` — T-602's unified-stream counterpart of `drift.changed`; fires whenever the unified findings ID set changes between the engine's ~30s cycles (subscribe to WS topic `"findings"`). Additive: `drift.changed` keeps firing independently on its own (drift-only) cycle. |
| `flow.batch` | `{entries: [flow.Record], droppedTotal}` — T-1002: pushed by `internal/flow.Service.Ingest` whenever a listener decodes new records; `entries` is rate-capped per push (default cap 200 — see the Flows section above for `flow.Record`'s shape), same "keep the newest N, count the rest" convention as `firewall.log.batch`'s `droppedTotal`. A client subscribed to `"flows"` should append `entries` to its own bounded, client-side-capped view. |
| `audit.appended` | `{id, at, username, action, target?, changesetId?, result, detail?}` — T-1104: fired for **every** `audit_log` row this daemon appends (login/logout, `token.use`, changeset lifecycle, snapshot restore, `webhook.create`, ... — the exact same fields `GET /audit`'s own `items[]` rows carry), the moment `store.AuditRepo.Append` commits. Only ever delivered on the `"events"` topic (below), never a topic of its own. |

**The `"events"` topic (T-1104, automation-scope-gated).** A superset envelope that reuses `changeset.status`/`drift.changed`/`findings.changed` **verbatim** — the identical encoded bytes a subscriber of those topics would receive are additionally fanned out to every `"events"` subscriber (a connection subscribed to both a source topic and `"events"` is never sent the same message twice) — plus `audit.appended` above, which exists only on this topic. No new producer logic duplicates `internal/change.Service`'s changeset-status broadcasts or `internal/drift`/`internal/findings`' own change-detection; `internal/topology/hub.go`'s `Broadcast` is the single fan-in point for both this topic and the webhook deliveries the Tokens & Webhooks section above describes (`Hub.SetEventSink`), so WS subscribers and webhook targets always see exactly the same event stream.

## Automation contract (T-1106)

**Scope.** This repository's deliverable for external automation is this stable API contract plus a conformance test suite (`internal/apicontract/`, run as part of `make check`) — **not** a Terraform provider or Ansible collection. `terraform-provider-vnprox` and `ansible-collection-vnprox` are separate, publishable repositories this task does not create; no source for either exists anywhere in this repository (grep-verifiable: those two strings match nothing under this tree). Both are expected to be thin shims over the routes below: plan = validate+diff, apply = apply+confirm.

**Auth.** T-1104 bearer tokens (`Authorization: Bearer <token>`, minted via `POST /tokens`) are the only documented/supported auth path for external providers/collections. No PVE username/password or ticket flow is ever exposed to automation callers — a token is a delegated, capability-scoped credential a logged-in human mints, distinct from the PVE ticket bridge (docs/security.md's Authentication section; T-1104's own note in the Tokens & Webhooks section above).

**The minimal, intentional route checklist external tooling depends on** (every route below is covered by `internal/apicontract`'s golden-fixture conformance suite; nothing outside this list is part of the automation contract, even if reachable with a bearer token):

| Method | Path | Used for |
|---|---|---|
| POST | `/tokens` | mint the bearer token automation authenticates with |
| GET | `/spec` | render current cluster intent as `specVersion: 1` YAML (the file a provider/collection tracks in version control) |
| POST | `/spec/import` | diff the tracked spec against live state → draft changeset + `notInSpec` (also this contract's `terraform plan` drift-detection primitive — see below) |
| POST | `/changesets` | create a draft changeset directly (for callers that build ops themselves rather than only via `/spec/import`) |
| GET | `/changesets/{id}` | poll changeset status/findings |
| POST | `/changesets/{id}/validate` | re-run validation (`plan`'s "does this still apply cleanly" check) |
| GET | `/changesets/{id}/diff` | rendered diff (`plan`'s human-readable change summary) |
| POST | `/changesets/{id}/apply` | apply (`terraform apply`'s mutating step) |
| POST | `/changesets/{id}/confirm` | commit-confirm within the window (auto-confirming on a successful apply is the caller's own responsibility — this contract does not change docs/architecture.md §4's commit-confirm model) |
| POST | `/changesets/{id}/rollback` | manual rollback |
| DELETE | `/changesets/{id}` | discard an unwanted draft |

**Drift detection for `terraform plan` (specified, not left implicit).** The route external tooling uses to answer "would `apply` change anything" is **`POST /spec/import`'s empty-ops response**: importing the tracked spec's exact current content returns a draft changeset; `len(ops) == 0` (and, for a caller also asserting nothing live is silently unmanaged, `len(notInSpec) == 0`) is a clean `terraform plan` — a non-empty `ops` list is the pending diff, renderable via that same draft changeset's `GET /changesets/{id}/diff`. This is idempotent by construction: re-importing the same unchanged content repeatedly always yields zero ops (`internal/apicontract`'s `TestSpecImportIdempotency`, run against `single-node` and `three-node-vlan`), and needs no server-side prerequisite beyond the caller's own tracked spec file — no pin, no prior stored state. **`GET /findings?source=drift&check=spec_drift`** (T-1102) is the *other* drift-detection surface this API exposes, and is deliberately **not** the one this contract specifies for `terraform plan`: it requires an operator to have separately called `POST /spec/pin` first (continuous GitOps reconciliation against a server-side pinned desired state, not a one-shot stateless plan) — a `terraform plan` run against a cluster with nothing pinned would see no `spec_drift` findings at all regardless of actual drift. A provider may additionally watch `spec_drift` findings for continuous drift alerting between its own `plan` runs, but must not use them as its only "would apply change anything" signal.

**Stability/versioning.** The changeset API (`POST/GET/PUT /changesets*`, `.../validate`, `.../diff`, `.../apply`, `.../confirm`, `.../rollback`) is declared stable at v1.7 (`docs/roadmap-next.md`'s Phase 11 compatibility note: "automation consumers get a documented deprecation policy from that point"). Concretely: a stable route's request/response shape is additive-only going forward (new optional fields, new optional query params) — any breaking change ships behind an explicit version bump this document will call out, never a silent field rename or removal. `internal/apicontract`'s golden fixtures are this repo's own enforcement of that promise: a handler change that breaks one of the routes above fails `make check` in this repository, before it can reach a released daemon build an external provider/collection would otherwise silently break against.

## Peer API (`/api/peer/*`, internal only)

HMAC-authenticated (cluster secret) endpoints between daemons: `GET /api/peer/host/interfaces`, `/api/peer/host/lldp`, `/api/peer/host/stats`, `/api/peer/host/services`, `/api/peer/host/links`, `/api/peer/host/fdb`, `/api/peer/host/neighbors`, `/api/peer/host/conntrack`, `/api/peer/host/ipv6-ra`, `/api/peer/host/frr/bgp-summary`, `/api/peer/host/frr/evpn-vni`, `/api/peer/host/dhcp-leases`, `/api/peer/host/container-interior`, `/api/peer/host/container-ping`, `GET /api/peer/firewall/log`, `GET /api/peer/flows`, `POST /api/peer/host/stage-interfaces`, `POST /api/peer/host/ifreload`, `POST /api/peer/host/restore`, `POST /api/peer/host/discard-staged`, `POST /api/peer/host/lldp/install`, `GET /api/peer/health`, `GET /api/peer/version`, `GET /api/peer/audit`, `GET /api/peer/snapshots`, `POST /api/peer/timer/arm`, `POST /api/peer/timer/cancel`, `GET /api/peer/timer/status`, `POST /api/peer/capture/start`, `POST /api/peer/capture/stop`, `GET /api/peer/capture/status`, `GET /api/peer/capture/download`, `POST /api/peer/ha/replicate`. Never exposed in the SPA; rejected without valid HMAC + timestamp (±30s replay window). Protocol version 2 (T-304 added `discard-staged` and the `timer/*` routes below — a peer still advertising protocol 1 cannot serve them, so a coordinator refuses to route multi-node steps to it per the version-skew rule in `docs/architecture.md` §5); T-404's two `frr/*` routes, T-406's `host/dhcp-leases` route, T-505's `firewall/log` route, T-602's `host/services` route, T-805's `host/neighbors` route, T-1002's `flows` route, T-1304's two `host/container-*` routes, T-1301's three `capture/*` routes, T-1302's `capture/download` route, T-1404's `host/ipv6-ra` route, and T-1704's `ha/replicate` route below are additive at the same protocol version 2, following the precedent T-303's `links` and T-306's `fdb` routes already set (new observability routes do not themselves force a version bump — only routes the write/coordination path depends on do, per those tasks' own reports).

**Peer TLS trust (T-1906).** A calling daemon verifies every peer's TLS certificate against the **cluster's own root CA** (`/etc/pve/pve-root-ca.pem` by default, `[peer] ca_file` to override) and never against the host system certificate pool — see `docs/security.md`'s Transport section for the full posture, escape hatches, and rotation behaviour. Consequences visible at this API's edges: a peer whose certificate does not verify yields the error code **`peer_untrusted`** rather than `peer_unreachable`, and every cluster fan-out response's `failedNodes` entry keeps that distinction; a daemon with no readable trust anchor treats *every* peer as unverifiable (fails closed — it never falls back to the system pool), which shows up as all peers failing with `peer_untrusted`. `GET /findings` carries the operator-facing version (`source: "peer"`, below). Because an untrusted peer is also, practically, an unreachable one, `peer_untrusted` errors satisfy the same graceful-degradation handling as `peer_unreachable` everywhere in the daemon — nothing newly hard-fails.

**`POST /api/peer/ha/replicate`** (added by T-1704, `docs/architecture.md` §12): the HA active/standby state-replication push. The active daemon POSTs an opaque-JSON replication batch (changesets, `changeset_schedules`, `api_tokens`, the audit-log tail, and the in-flight pre-apply snapshots a rollback depends on — `snapshots`/`snapshot_files`/`blobs`; metrics rings excluded) to its **configured standby only**, which decodes it into `internal/ha.Manager.Receive` (fenced by lease term) and replies with an ack. It stays at **protocol version 2 (not a bump — decision D11, `docs/architecture.md` §13.4)**: an HA pair always runs the same build, and the route is **503-nil-safe** on any daemon without HA replication wired (a non-HA build, or one that simply never mounted the sink), so it forces no version skew on non-HA deployments or mixed-version rolling upgrades — HA replication only ever targets the operator-configured standby, never an arbitrary cluster peer. See `docs/architecture.md` §12 for the fenced-lease single-writer model this route feeds.

`GET /api/peer/host/container-interior?node=&vmid=` and `GET /api/peer/host/container-ping?node=&vmid=&ip=` (added by T-1304): the remote-node counterpart of a local `internal/host.Reader.ContainerInterior`/`ContainerPing` call — an lxc guest has no QEMU guest agent, so `GET /guests/{ref}/interior`'s lxc read path reaches a peer node's own container netns through these two routes instead (docs/architecture.md §1/§5's cluster-awareness invariant: a container on a peer node is inspectable exactly the way one on this node is). `container-interior` responds `{addrJson, routeJson, resolvConf, sockets}` (each the named command's raw text output, mirroring `host/dhcp-leases`' `{content}` convention rather than base64); `container-ping` responds `{reachable: bool}`.

**`POST /api/peer/capture/start` / `POST /api/peer/capture/stop` / `GET /api/peer/capture/status`** (added by T-1301): the multi-point-capture fan-out. A coordinating daemon (the one the operator's browser hit) resolves each target to its node and, for a node that isn't the coordinator itself, calls `capture/start` with the session spec `{sessionId, groupId, targetRef, node, iface, filter, caps, startedBy, startedAt, nodes}` (no file path travels the wire — the receiving node derives it from its own `[capture]` root). The **receiving node re-validates the filter and re-clamps the caps against its own `[capture]` config** before running — it never trusts the coordinator's arithmetic, so the un-overridable-cap guarantee holds independently on every capturing node. `capture/stop` `{sessionId}` and `capture/status?sessionId=` operate on that node's own session. All three reply `{status, packets, bytes}` — accounting only, **never payload bytes**. The captured file and its retention sweep are wholly owned by the capturing node (each daemon writes its own `capture_sessions` row and purges its own files).

**`GET /api/peer/capture/download?sessionId=`** (added by T-1302): the peer-download half of `GET /captures/{id}/download` above — fetches one *local-to-this-node* session's raw pcap bytes. Response `{content}` where `content` is the file's bytes, JSON-encoded (Go's `encoding/json` base64-encodes a `[]byte` field automatically) rather than served as a raw octet stream, keeping the peer wire format JSON end-to-end like every other peer route (`host/dhcp-leases`' text-content precedent, generalized to binary). This is the one payload-bytes-crossing-the-wire exception to every other peer route's "accounting only" rule above — it is exactly the same bytes a caller with `capture`+`netRead` is already entitled to read directly off this node's own disk, HMAC-authenticated like every other peer route, never logged or persisted by the handler itself.

**`GET /api/peer/flows?guest=&vlan=&subnet=&port=&proto=&fromTs=&toTs=&limit=&cursor=`** (added by T-1002): one node's own local `flow_samples` page, same filter set as `GET /flows` (`proto` here is already resolved to a numeric IP protocol — the peer route never re-parses a `protocol` name/number ambiguity, that happens once on the coordinating daemon). Response: `{items: [FlowRecord], nextCursor?}` — no `partial`/`failedNodes` (a peer only ever reports its own node-local page; the fan-out/merge happens on the calling daemon, mirroring `GET /api/peer/audit`/`GET /api/peer/snapshots` exactly). `FlowRecord` mirrors `flow.Record` field-for-field plus an `id` (int64) — a peer-wire-only field the calling daemon uses as the cluster-merge pagination tiebreak (unix-second timestamps alone collide often at realistic ingestion rates) and strips before returning `GET /flows`' own response.

`GET /api/peer/host/neighbors` (added by T-805, docs/features/ipam.md §1): a node's resolved ARP (IPv4) / IPv6-neighbor table (`{neighbors: [{IP, MAC, Iface, State}]}`), already filtered to resolved states (`REACHABLE`/`STALE`/`PERMANENT`) — the remote-node counterpart of a local `internal/host.Reader.Neighbors` call, letting `internal/neighbor.Service` fan the ARP/neighbor enrichment source out cluster-wide exactly like T-406's `host/dhcp-leases` route does for DHCP leases. Accepts `?node=`.

`GET /api/peer/host/conntrack` (added by T-1305): a node's own live conntrack/NAT table (`{entries: [ConntrackEntry]}`, `ConntrackEntry` as documented in the Conntrack section above) — the remote-node counterpart of a local `internal/host.Reader.Conntrack` call, `GET /conntrack`'s cluster fan-out dependency. Accepts `?node=` (like every other `host/*` read, `Real` only ever serves its own node regardless of the value passed). No `{available}`/filtering envelope: an empty table is itself a clean, unremarkable answer, the same convention `host/neighbors`/`host/fdb` already follow.

`GET /api/peer/host/ipv6-ra` (added by T-1404): a node's own bounded, host-local IPv6 RA/DHCPv6 observation (`{items: [IPv6RAObservation]}`, shape as documented in the IPv6 section above) — the remote-node counterpart of a local `internal/host.Reader.IPv6RA` call, `GET /ipv6/segments`' cluster fan-out dependency. Accepts `?node=`. Same no-envelope convention as `host/conntrack` above: an interface with no RA observed simply produces no entry.

**`GET /api/peer/firewall/log?node=&cursor=&maxLines=`** (added by T-505): the requesting daemon's own polling loop (`internal/fwlog.Service.Tick`) calls this once per known peer, per poll tick, exactly like it calls its local `Source.Tail` — `node` names which node's log to read (the peer serves only its own node, mirroring `host/*`'s "Real only ever serves its own node" convention), `cursor` resumes a previous call's `nextCursor` (opaque; omit for an initial tail), `maxLines` defaults to 500 and clamps to 5000 (a higher ceiling than the audit/snapshot pagination routes', since a real log-storm burst needs a single fetch able to catch up rather than trickling in). Response: `{lines: [string], nextCursor}` — raw, unparsed log lines; the requesting daemon parses/correlates them itself (this route has no knowledge of firewall rules, only bytes).

`GET /api/peer/host/services` (added by T-602): `{services: {"dnsmasq": true, "frr": false}}` — host.WatchedServices' unit set; a unit never installed on the node is simply absent from the map, not reported as down. Like the other host/* reads, it does not bump the protocol version since it is additive and callers degrade gracefully (internal/findings' service-down check simply has nothing to report from a peer still on an older build that lacks the route, the same "quietly absent" treatment every other optional producer input gets).

`GET /api/peer/host/links` (added by T-303, documented here retroactively per that task's report note): a node's netlink-equivalent link state (`{links: [LinkState]}`, one entry per physical NIC/bond/bridge/VLAN sub-interface) — the remote-node counterpart of `internal/host.Reader.Links`, letting a peer's daemon fan its host poller out cluster-wide instead of only ever seeing its own node's netlink state.

`GET /api/peer/host/frr/bgp-summary` and `GET /api/peer/host/frr/evpn-vni` (added by T-404): a node's raw `vtysh -c "show bgp summary json"` / `"show evpn vni json"` output, each wrapped as `{available, content?}` rather than passed through raw (unlike `/host/lldp`) — `available` is `false` (`content` omitted) when the node runs no FRR daemon at all, so "FRR entirely absent" travels over the wire as a clean, distinguishable 200 instead of an error status; `content` is the verbatim vtysh JSON otherwise, parsed by the caller (`internal/host.ParseBGPSummary`/`ParseEVPNVNI`). Both accept `?node=`, same convention as every other `/host/*` read. These back `GET /sdn/evpn/status`'s cluster fan-out above.

`GET /api/peer/host/fdb` (added by T-306, per that task's card — T-301's report flagged its absence as this task's deliverable): a node's bridge forwarding-database tables, flattened and bridge-tagged (`{entries: [{bridge, mac, port?, vlan?, master?, permanent?, stale}]}`) out of the same data `Links()` already carries in each entry's `Bridge.FDB` — this route exists as its own endpoint so a caller that only wants the FDB (the MAC/FDB browser, `GET /fdb` above) doesn't have to pull every bridge's full VLAN table and every physical NIC's link state over the wire to get it. `internal/collect`'s host poller does not call this route: bridge FDB reaches the inventory graph (and therefore cluster-wide `GET /fdb`) via the existing `Links()`-based host poll, exactly like every other netlink-observed field — `handleFDB` derives its response from the same `Links()` read `GET /api/peer/host/links` uses, not a second collection path.

`GET /api/peer/host/dhcp-leases` (added by T-406, docs/features/sdn.md §5): node's raw dnsmasq DHCP lease-file content, verbatim, wrapped as `{content: string}` — the same shape `/host/interfaces` uses (unlike `/host/frr/*`'s `{available, content?}` envelope: an empty result here is itself a clean "no leases" answer, not a distinct absent condition worth its own flag, since most nodes simply run no DHCP-managed SDN zone at all). Accepts `?node=`. `content` is the concatenation of every locally-configured zone's `.leases` file (`internal/host.Real`'s `DHCPLeaseGlob`, defaulting to `/var/lib/misc/dnsmasq.*.leases` — **needs hardware validation**, this glob is inferred rather than confirmed against a live PVE cluster; see T-406's completion report), parsed by the caller with `internal/host.ParseDHCPLeases` (defensive: skips and counts any malformed line rather than failing the whole read). `internal/dhcp.Service` fans this out across every reachable cluster node (local via `internal/host.Reader`, peers via this route) into `GET /sdn/dhcp`'s `leases` array, wired as the `dhcp-lease`-sourced enrichment `internal/ipam` reserved a slot for (see `GET /ipam/subnets/{cidr}/allocations`'s `Cell.sources` doc above).

`GET /api/peer/audit` and `GET /api/peer/snapshots` (added by T-303): each node's own local page of its `/audit`/`/snapshots` data — `{items: [...], nextCursor?}`, the same shapes as the public `/audit`/`/snapshots` list items, minus the cluster-fan-out `partial`/`failedNodes` fields (a peer only ever reports its own node-local page here; the fan-out/merge happens on the calling daemon, inside `GET /audit`/`GET /snapshots` themselves). `/api/peer/audit` accepts the same filter query params as `GET /audit` (`user`, `action`, `target`, `result`, `changesetId`, `from`, `to`) plus `limit`/`cursor`; `/api/peer/snapshots` accepts `limit`/`cursor` only.

T-304's local-timer protocol (`docs/features/change-management.md` §4: "each node arms its own local timer at step start"): `POST /api/peer/timer/arm` `{changesetId, node, content, deadline}` — persists `content` as the node's pre-apply state to restore and arms a real rollback timer for `deadline` (unix seconds); `POST /api/peer/timer/cancel` `{changesetId, node}` — stops it (idempotent); `GET /api/peer/timer/status?changesetId=&node=` — returns the current record, or 404 `timer_not_found` if this node never armed one for that key. All three return `{record: {changesetId, node, status, deadline, armedAt, resolvedAt?, error?}}`, where `status` is one of `armed|cancelled|rolled_back|rollback_failed`.

## MCP server (T-1701, AI operator readiness)

A first-class **Model Context Protocol** server (`internal/mcp`) exposing vnprox's **read** surfaces and its **draft-staging** surface to AI operators — and nothing more. It is the change engine's thesis applied to AI: *capability through the change engine, not around it*. **No apply/confirm/rollback/discard verb is reachable through MCP, by any tool, parameter, or combination** — a human (or T-1103's confirm machinery) remains the sole apply/confirm authority. This stage-only boundary is the card's central invariant and is enforced structurally (see docs/security.md's "MCP stage-only boundary").

**Enablement.** Off by default. Set `[mcp] enabled = true` in `vnprox.toml` to mount the transport; otherwise the surface ships dark (no route mounted at all), matching `[switches]`' feature-flag-dark precedent.

**Transport.** Mounted at `/api/v1/mcp` under the daemon's ordinary TLS/logging/security-header middleware, but — like `GET /metrics` — it does its **own** bearer-token auth, never a session cookie or CSRF header:
- **Streamable HTTP** — `POST /api/v1/mcp` carries one JSON-RPC 2.0 message and returns one JSON response (or, with `Accept: text/event-stream`, that response framed as a single SSE event); `GET /api/v1/mcp` with `Accept: text/event-stream` opens the server→client SSE stream, held open until the client disconnects or the token is revoked.
- **stdio** — the same server also speaks newline-delimited JSON-RPC over stdio (`internal/mcp.Server.ServeStdio`), for a locally-spawned MCP client.

**Auth & scoping (reuses T-1104 tokens unchanged).** A session authenticates with an `Authorization: Bearer <token>` token that **must carry the `automation` scope** (missing it ⇒ `403 forbidden`; no/invalid token ⇒ `401 not_authenticated`). Beyond that, each tool is exposed to the session only if the token's scopes cover the tool's required scope — exposure is derived from the token at connect time, never from a client-asserted capability list. Revoking the token force-closes the session within one revocation tick.

**Tool allowlist (fixed, enumerable — this is the security boundary).** Exactly these tools exist; there is no generic "call any route" bridge, and no tool names or reaches an apply/confirm/rollback/discard verb:

| Tool | Required scope | Wraps | Effect |
|---|---|---|---|
| `topology.get` | `netRead` | `GET /topology` | read |
| `findings.list` | `netRead` | `GET /findings` | read |
| `flows.query` | `netRead` | `GET /flows` | read |
| `ipam.subnets.list` | `netRead` | `GET /ipam/subnets` | read |
| `simulate.path` | `netRead` | `POST /simulate/path` | read (static analysis) |
| `diagnose.run` | `netRead` | `POST /diagnose` | read/advisory; **never escalates to capture** over MCP |
| `changesets.diff` | `netRead` | `GET /changesets/{id}/diff` | read |
| `changesets.create` | `netWrite` | `POST /changesets` | **stages a draft only** — labelled `origin: "mcp"`, never applied by this tool |
| `changesets.validate` | `netWrite` | `POST /changesets/{id}/validate` | re-validate a draft; does not apply |

A `{netRead, automation}` token therefore reaches every read/simulate/diagnose tool and `changesets.diff`, but never `changesets.create`/`changesets.validate` (both `netWrite`). Every MCP tool invocation is audited (`mcp.tool.invoke`, actor `mcp:<token-name>`), and every changeset it stages carries `origin: "mcp"` + `originTokenId` (see the Changesets section's provenance paragraph).
