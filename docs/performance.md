# Performance & scale verification (T-607)

This document records the actual, measured results of proving `docs/features/topology.md` §4's scale target and the daemon's long-run behavior, per T-607's release-gate mandate. Every number below comes from a real run executed as part of this task — none are estimates — with the sole, explicitly-flagged exception of the soak test's duration substitution (§3).

## 1. Scale fixture

`testdata/clusters/scale-lab.yaml` is a generated (not hand-written) pvemock fixture at exactly the topology-spec §4 target: **8 nodes × 6 NICs, 4 bridges/node (1 mgmt + 1 SDN-zone + 2 plain), 300 guests, 40 VNets** (1 cluster-wide VLAN zone, 40 subnets). Generated by `testdata/genscale/main.go`, which builds a `pvemock.Fixture` value directly (guaranteeing schema validity) and writes it via `yaml.Marshal` — regenerate with `go run ./testdata/genscale > testdata/clusters/scale-lab.yaml`. Confirmed post-generation: 8 nodes, 300 guests, 40 vnets, 1 zone, 40 subnets (`pvemock.LoadFixture` round-trip check).

## 2. API latency at scale

**Method:** `cmd/vnproxd/scale_bench_test.go`'s `BenchmarkAPIAtScale` boots the real production `runDaemon` path against an in-process `pvemock` server on `scale-lab.yaml` (same pattern `secretlog_test.go` already used for a different purpose), logs in for real, waits for the collectors to converge, then times 100 real HTTP round trips per endpoint. Run with:

```
go test ./cmd/vnproxd/ -run '^$' -bench 'BenchmarkAPIAtScale' -benchtime=100x -v
```

**No documented numeric API-latency target exists** in `docs/api.md` or `docs/features/topology.md` §4 (that section's only targets are frontend-rendering ones: 30fps pan/zoom, 2,000-element cap). In the absence of a specified target, this report adopts a provisional pass bar of **p95 < 300ms** for these endpoints — a common interactive-web-UX budget, and consistent with `internal/inventory`'s own existing (pre-T-607) 5ms p99 budget for the in-memory `Snapshot()` call these endpoints build on. This is a judgment call, not a re-litigated product decision; flagged here for product-owner review if a different number is wanted.

| Endpoint | p50 | p95 | p99 | max | Target (p95) | Result |
|---|---|---|---|---|---|---|
| `GET /topology` | 60.1 ms | 67.2 ms | 80.8 ms | 80.8 ms | < 300 ms | **PASS** |
| `POST /simulate/path` (cross-node, pve1→pve8, 8-node/300-guest/40-VNet graph) | 10.0 ms | 13.6 ms | 17.5 ms | 17.5 ms | < 300 ms | **PASS** |
| `POST /changesets/{id}/validate` | 20.2 ms | 23.1 ms | 33.5 ms | 33.5 ms | < 300 ms | **PASS** |

Environment: this benchmark ran on a shared virtualized dev host (QEMU vCPU, no dedicated hardware) with other processes concurrently active (soak test, background research agents) — these numbers are a conservative upper bound, not a best-case measurement; real PVE-node hardware with a dedicated core is expected to do at least as well.

## 4. Progressive disclosure at scale

Verified two ways:

1. **Real capture** (`web/src/topology/scaleLab.render.test.tsx`, `web/src/topology/__fixtures__/scale-lab-topology.json` — a real `GET /topology` response captured from the running scale-lab stack): the real projected topology has **203 nodes + 408 edges = 611 total elements**, comfortably under the ~2,000-element hard cap, and contains **24 collapsed `guest-group` pills**, every one with `collapsedCount > 8` (`internal/topology/collapse.go`'s `DefaultCollapseThreshold`) — collapse-by-default demonstrably engages at real scale. Without collapsing, the raw guest layer alone would be 300 guests × 2 (guest + guest-nic) = 600 elements; collapsing keeps the actual guest-layer element count far below that.
2. **Synthetic beyond-cap case** (same test file): since the documented scale target is, by design, sized to stay *under* the render cap (that is the point of progressive disclosure), there is no real fixture at >2,000 elements to capture. A synthetic `TopologyNode[]` array just under and just over `RENDER_CAP` (exported from `TopologyPage.tsx` for this purpose) is fed through the real `toFlowElements` pipeline, proving the cap arithmetic itself trips correctly once exceeded — this is the "filter prompt at the element cap" behavior the task names, verified as real, working logic rather than asserted by inspection.

Both are exercised together end-to-end in `web/e2e/scale.spec.ts`'s real-browser test, which additionally asserts: at least one `"N guests"` pill is visible in the live DOM, and the "above the ~2,000 render cap" banner is **not** showing (this fixture is deliberately at the "smooth" scale, not the "beyond it" one).

**Known gap, not fixed in this pass (flagged, see `docs/features/topology.md` §4 and `docs/roadmap.md`):** "physical layer collapses to per-node summary" was never implemented in any phase — only guest-layer collapse exists. Not release-blocking: the physical layer is only ~50-65 elements cluster-wide at the documented scale target, far below where collapsing would matter; guest-layer collapse (the actual pressure point, since 300 guests dominates the entity count) is real and verified above.

## 6. Soak test: methodology, substitution, and results

**Deviation from the literal task-card wording, stated plainly up front:** the task card asks for a 24-hour continuous daemon run. This was run as a background automated agent in a single session, not a setup that can be checked back on after a literal 24 wall-clock hours by a human — a genuine, uninterrupted 24h run was **not** executed. Instead, per this task's own explicit instructions for exactly this situation:

- A real soak was run continuously for **the longest span practically achievable in this session** (see the actual duration and sample count below — this section is updated with the final numbers once the run is stopped).
- RSS, goroutine count, and SQLite DB file size were sampled at a fixed 60s interval throughout (not estimated).
- The daemon was driven with real, continuous churn the whole time (not idle): read-path traffic (topology/findings/audit polling every 5s) plus draft-changeset churn (create→validate→delete, every 45s) plus periodic full apply→confirm cycles (every 20 minutes).
- The DB-growth claim is evaluated against **T-601's own measured ceiling** (its report: ~24.3 MiB measured for 100 entities × 2,880 buckets — a full 24h run at 30s resolution — cross-checked against a 1/10th-scale linear extrapolation; documented ceiling 200 MiB, ~8x headroom over actual usage), reused here rather than re-derived, per this task's instructions.
- The RSS/goroutine trend line from the real (shorter) run is the evidence for the 24h flatness claim — a flat trend over the achieved duration, with no growth pattern emerging, is the available evidence; it is explicitly not the same as observing 24 real hours.

**Harness:** `testdata/genscale/soak` — a real Go HTTP client driving a real `vnproxd` (via `testdata/dev-scale.toml`, `scale-lab.yaml`) exactly per `docs/development.md`'s dev-loop pattern. Goroutine count sampled via a new, off-by-default diagnostic endpoint (`cmd/vnproxd/debugpprof.go`, `VNPROX_DEBUG_PPROF_ADDR` env var — never part of the main TLS listener, no `docs/api.md` contract change; added because the task anticipated needing this and none existed).

**Results (actual run, stopped deliberately after ~61 minutes to free the machine for the rest of this task's verification work — not a crash or failure):**

- **Duration achieved: 3,662 seconds (~61 minutes) of continuous, real, churn-driven daemon runtime.** This is short of the "1-2 hours" this task's own instructions aimed for, and far short of 24h; stated honestly, not padded. 63 samples recorded at 60s+ intervals (`planning/reports/T-607-artifacts/soak-samples.csv`).
- **RSS:** ranged 43.6-57.2 MB across all 63 samples, with no sustained upward trend — the last 10 samples (t=3054s..3662s) span 43.6-54.8 MB, statistically indistinguishable from the first 10 (t=0..570s, 44.1-55.0 MB). Consistent with normal GC breathing room, not a leak.
- **Goroutines:** ranged 40-44 across the entire run, no growth trend (first 10 samples: 41-44; last 10 samples: 40-44).
- **DB file size** (incl. WAL/SHM sidecars): grew from an initial ~354 KB to 4.32 MiB by t≈1207s, plateaued exactly there through t≈1454s, stepped up once more to 4.37 MiB after a WAL checkpoint around t≈1900s, and then **held flat at exactly 4,365,816 bytes for the remaining ~29 minutes of the run** (36 consecutive samples, t=1903s through t=3662s) — textbook bounded, periodic-checkpoint growth, not unbounded growth.
- **Real apply/confirm cycles:** attempted every 20 minutes (2 attempts fit in the 61-minute run). Both times, the create half succeeded (real apply→confirm→committed, exercising the full lifecycle for real, each producing a genuine `changeset.apply`/`changeset.confirm` audit-log pair and a post-commit snapshot); both times, the reverse (delete) half failed validation with `referential.target_not_found`. Root-caused, not a mystery: in this dev/mock environment, `bridge.create`'s file write lands in the `dev_interfaces_dir` sandbox, but the mock PVE server's own in-memory network model (what the next changeset's validation reads back) is never updated by that write, since the apply engine never calls `pvemock`'s `PUT /nodes/{node}/network` handler for node-network ops at all (see `docs/architecture.md` §4's corrected note — this was found precisely because of this soak run). Dev/mock-only artifact, no production implication (a real PVE node's own API reads back the same file it writes to), and doesn't affect the RSS/goroutine flatness measurement above, which is what the soak actually exists to prove.
- **Analytical extrapolation to 24h (per this task's instructions, reusing T-601's own measurement rather than re-deriving it):** T-601's report measured **~24.3 MiB for a full, un-shortcut 24h run at 30s resolution, 100 entities × 2,880 buckets** (documented ceiling 200 MiB, ~8x headroom). This soak's own DB growth (4.37 MiB, driven mostly by draft-changeset WAL churn plus 2 real apply/confirm cycles, not metric-sample accumulation — this run's `scale-lab.yaml` fixture load is what feeds the metrics ring, at roughly the ~100-entity scale T-601 measured against) is consistent with, not contradictory to, that ceiling holding at 24h scale.
- **Honest bottom line:** RSS and goroutines are demonstrably flat over the ~61 minutes actually observed, with zero trend in either direction — the strongest evidence available without a literal 24h run. Whether that flatness holds unchanged for 23 more hours cannot be claimed as *observed* fact from this run; it is inferred from (a) the trend already being flat rather than slowly rising, (b) Go's runtime GC behavior not being scale-of-time-dependent (a 5s/45s/20min-period workload that doesn't leak in 61 minutes has no structural reason to start leaking at hour 6 or hour 20), and (c) the DB-growth ceiling argument above. This is the documented, justified substitution this task's instructions asked for — not a claim that 24h was actually run.

## 8. A real product bug found and fixed during this verification pass

While writing E2E coverage for the user-guide §3 "create an isolated test network"/"stretch a network with VXLAN" tasks, the SDN zone wizard's "Create draft" button was found permanently disabled for **any** real multi-node session, including root — `internal/auth.BuildCapabilities` only ever populates a `""` cluster-wide key in its returned capabilities map when the node list is empty; a real multi-node cluster's session has only per-node keys, so the five pre-existing SDN editor dialogs' `capsForNode(session, "").sdnWrite` check silently evaluated to `false` always. Every existing unit test's mock session fixture happened to include an artificial `""` entry, masking this from unit coverage entirely — it was only caught by actually driving the wizard to completion against the real stack. Fixed by switching to the already-correct, already-used-elsewhere `hasAnyCap(session, cap)` helper. The same investigation also found the SDN/Firewall write-trigger buttons (zone/vnet/subnet edit/delete, per-rule delete/enable/reorder) had no capability gating at all — a gap `docs/security-verification.md` had already flagged (T-604) but left unfixed; fixed here too. See `planning/reports/T-607.md` for the full writeup.

### 10.2 Federation aggregator latency at the profile

**Method:** `internal/federation/scale_bench_test.go` attaches the 3-cluster profile to one real `federation.Aggregator` (real `internal/pve.Client`s against real `httptest` listeners, real AES-256-GCM credential sealing) and times the two fan-out-and-merge calls that back the global endpoints. Reproduce with:


| Aggregator call (backs) | mean latency | allocs | Provisional bar (p95) | Result |
|---|---|---|---|---|
| `TopologySummary` (`GET /federation/topology`) | **~14.0 ms/op** | 1.38 MB/op, 7,716 allocs/op | < 300 ms | **PASS** |
| `Search` (`GET /federation/search`, cross-cluster fan-out) | **~11.0 ms/op** | 1.31 MB/op, 8,104 allocs/op | < 300 ms | **PASS** |

## 11. HA + multi-cluster genscale profile — T-1707 (v3.0)

The v3.0 arc adds optional daemon HA (T-1704) on top of the v2.0 multi-cluster federation profile
(§10). This section extends §10's genscale profile with the HA-standby dimension — active/standby
**replication lag** and **failover-promotion latency** as explicit outputs — and states honestly
which of those are proven deterministically here and which are hardware targets. **No number below
is fabricated.**

### 11.1 The profile (numbers stated)

The HA/multi-cluster genscale profile is §10.1's 3-cluster profile (24 nodes / 900 guests / 120
VNets / 120 subnets) with, on the designated primary, an **active/standby vnproxd pair** replicating
app-owned state (changesets, `changeset_schedules`, `api_tokens`, the audit tail, and the in-flight
pre-apply snapshots a rollback depends on — `snapshots`/`snapshot_files`/`blobs`; metrics rings
excluded) over the existing `internal/peer` TLS+HMAC channel. The standby carries the same read load
capacity as the active (it is a full daemon, not a thin follower) but drives no apply/confirm/
rollback while it holds no lease.

| Dimension | Value |
|---|---|
| Federation scale | 3 clusters × (8 nodes / 300 guests / 40 VNets) = 24 / 900 / 120 (§10.1) |
| HA replicas on the primary | 1 active + 1 standby |
| Replicated state classes | changesets, `changeset_schedules`, `api_tokens`, audit tail, pre-apply snapshots+blobs |
| Excluded from replication | metrics rings (bounded/ephemeral) |
| Lease TTL / renew / fencing margin (defaults) | `15s` / `5s` / `15s` (`docs/deployment.md` `[ha]`) |
| Replication-lag alarm threshold (default) | `500` audit rows behind → `ha_replication_degraded` |

### 11.2 What is proven deterministically here

The two-daemon HA harness (`internal/ha`, injected fake clock + injectable partition switch, no real
sleeps) proves the **safety** properties the profile depends on, across a **40-cycle failover soak**
(`TestFailoverSoak_NoDoubleApply_NoDroppedRollback`, T-1707) alternating the missing-ack (rollback)
and confirm (commit) outcomes:

- **Zero double-apply and zero dropped-rollback across all 40 cycles** — every promoted standby
  re-arms the *same absolute* commit-confirm deadline (never a promotion-relative one), a missing
  confirm always rolls back exactly once, and a confirmed change is never rolled back by a late
  timer fire.
- **Replication carries the in-flight rollback state** — a promoted standby holds the byte-exact
  pre-apply snapshot needed to complete a rollback (`internal/ha/replicate_test.go`,
  `internal/ha/failover_test.go`).

These are correctness invariants, measured on a fake clock — they are not wall-clock timings.

### 11.3 What is a target, flagged needs-hardware-validation (NOT measured here)

The following are **stated targets derived from the config defaults**, not measurements — the
deterministic harness advances a fake clock, so it cannot produce a real wall-clock promotion time
or a real replication-throughput number. Recorded in `planning/reports/needs-hardware-validation.md`
under "T-1704"/"T-1707":

| Metric | Target (design) | Status |
|---|---|---|
| Failover-promotion latency (active death → standby drives) | ≤ `lease_ttl + fencing_margin` (≈ **30 s** with defaults; tunable lower) — a standby promotes only after the last-observed lease has expired past the fencing margin | **needs-hardware-validation** — real value depends on real network RTT, clock skew, and the operator's VIP/ARP or DNS-TTL propagation, none of which the fake-clock harness models |
| VIP/ARP or DNS failover-announce propagation | operator-provided mechanism (gratuitous ARP or DNS repoint); vnprox only triggers it | **needs-hardware-validation** — vnprox neither ships nor times this; measure the operator's chosen mechanism |
| Replication lag under real primary load at profile scale | well under the `500`-row default alarm threshold in steady state | **needs-hardware-validation** — real throughput/lag under a real churn rate at 24-node/900-guest scale is a dev-host run |
| Full-daemon HA-pair RSS/goroutine overhead of the standby | standby ≈ active steady-state footprint (full daemon) | **needs-hardware-validation** — same end-to-end memory-profile gap §10.3 flags, now with a second daemon |

Setting a real number for the promotion-latency and replication-lag rows requires two real vnproxd
instances on real hosts with a real network partition — explicitly out of this environment's reach,
flagged rather than faked.
